# v0.21.8 · 逐帧批量预标注优化（消除段级重复下载 + 跑中进度落库）

状态：**已实现并整栈 E2E 验证通过（2026-07-05，v0.21.8）**。真实栈复跑 tracking_car.mp4（335 帧）：
`extract_frames_task` 每视频只跑 1 次（下载 12→1，段任务 gpu 下载行数 0）；`progress_pct` 跑中真实爬升
`0→17→35→53→71→91→100`（此前恒 0）；断点续跑补齐瞬时失败帧 → 335 全覆盖。**已知观察**：去掉 per-段
抽帧的天然错峰后 12 段几乎同时砸后端，8G GPU 峰值并发更猛，可能出瞬时 predict 失败（缓存 URL 全 ready，
非本改动缺陷），靠断点续跑重跑补齐。接续 [v0.21.7 单帧分支批量逐帧预标注](2026-07-03-v0.21.7-frame-batch-preannotation.md)——
功能已整栈验证通过，本计划收其两笔已知技术债（CHANGELOG v0.21.7 已注「每段重下整段视频」）。
纯性能/可观测优化，不改用户可见行为、不改落库 schema、无 alembic。

## 动机（v0.21.7 落地后实测的两个债）

### 债 1 · 段级重复下载整段视频（正主，性能）
`_run_segment`（`frame_preannotate.py:214`）每段调 `_ensure_frame_urls` → `_extract_video_frames`
（`media.py:846`）。后者**无条件先把整段源视频下载进临时文件**（`:874` `download_fileobj`），
再抽本段帧。帧级幂等（`:894` 跳过已 ready 的 `VideoFrameCache` 行）发生在**下载之后**，省不掉下载。

后果：一个视频 task 的帧被切成 `ceil(帧数 / chunk_size)` 段，**每段各下一次整段视频**。
tracking_car（335 帧 / chunk 30）= 12 段 = 12 次全量下载（实测 E2E 已发生）；900 帧上限 = 30 段 =
30 次。视频越大越痛（下载字节数 × 段数线性放大）。

### 债 2 · 跑中 `async_job.progress_pct` 停在 0（可观测）
段任务进度走 Redis 计数器 + SSE（`_bump_progress` → `_publish_frame_progress`，前端订 SSE 时**有**
实时进度）。但 `async_job.progress_pct` 跑中**不落库**，只有 chord 回调 `_finalize` 的
`mark_complete` 才置 100。故 `/ai-pre/jobs` 列表（读 DB progress_pct，非 SSE）跑中恒显 0%，
到点直接跳 100%——刷新页面 / 断线重连的用户看不到进度。

## 定稿决策（拟）

- **抽帧与预测两阶段化，抽帧每视频一次**。把「抽帧」从段任务里拆出，提为**每视频一个抽帧任务**
  （下载一次源视频 → 抽该视频所有计划帧 → `VideoFrameCache`），段任务退化为**纯预测**（读缓存帧
  URL 发 `/predict`，零下载）。跨视频并行保留（多视频 task 各自的抽帧任务并行）；单视频内下载收敛为 1 次。
  - **取舍**：单视频内抽帧从「多段并行抽」变「单任务顺序抽」。但抽帧是一次 ffmpeg 顺序 seek，相对
    GPU 预测极廉；换来的是消除 N-1 次全量下载（大视频主导成本）。净赢。
- **段任务跑中周期性把 Redis 进度写回 `async_job.progress_pct`**。每段收尾（或每 K 帧）用 Redis 的
  `done/total` 折算百分比 upsert 到 async_job，让 DB-backed 列表与 SSE 对齐。轻量、幂等（取 max 防回退）。

## 定稿架构（两阶段 per 视频）

```
batch_predict (orchestrator, execution_unit=frame 分支)
  └─ dispatch_frame_preannotate:
       plan_segments 后, 每个视频 task →
         chain(
           extract_video_frames_task.s(task, 该视频全部计划帧),   # 阶段 A: 下载 1 次 + 抽全帧 → cache
           chord(
             group(predict_video_segment.s(task, 段帧块) for 段 in 该视频的段),  # 阶段 B: 纯预测
             _agg_task_segments.s(...)                             # 该视频段聚合 (可选中间收束)
           )
         )
       所有视频的尾 chord → finalize_frame_job (总收尾, 不变)

extract_video_frames_task (新, 每视频一次)
  - _ensure_frame_row(所有计划帧) + _extract_video_frames(该视频全部帧)  # 一次下载
  - 幂等: 已 ready 帧跳过 (VideoFrameCache 命中)
  - 失败 → 该视频段全 skip + stats 标 extract_failed

predict_video_segment (改造: 去掉抽帧, 只读缓存 + 预测)
  - _ensure_frame_urls 改为「只读 VideoFrameCache 取 URL」(不再触发 _extract_video_frames)
  - 若某帧缓存未命中 (抽帧阶段漏/失败) → 记 failed, 不回退到下载
  - 逐帧 predict → to_video_bbox_result → 落库 (不变)
  - _bump_progress + 写回 async_job.progress_pct (债 2)
```

**多视频 fan-out 形态**：v0.21.7 是单层 `chord(group(所有段), finalize)`。两阶段化后每视频要先抽后测，
形态变「每视频 chain(抽, chord(段, 聚合))」+ 顶层等所有视频完成再 finalize。用 Celery `chord`/`chain`
嵌套表达；若嵌套 chord 收束复杂，退化方案：**抽帧阶段并入 orchestrator 同步预抽**（orchestrator 顺序
为每个视频抽帧，再发原单层段 chord）——牺牲跨视频抽帧并行，换实现简单，单视频场景（当前主用例）零差异。
选型在 Phase 1 spike 后定。

## 实现分阶段

- **Phase 1 · 抽帧/预测解耦 spike + 选型**：确认 `_extract_video_frames` 可安全在段外整段调用（幂等、
  并发安全）；验证「段任务只读缓存」路径（`_ensure_frame_urls` 拆出只读变体）；定 fan-out 形态
  （嵌套 chord vs orchestrator 预抽）。产出：一个视频端到端跑通新路径 + 下载次数实测降到 1。
- **Phase 2 · 落地两阶段**：`extract_video_frames_task` 新任务 + `predict_video_segment` 去抽帧改只读 +
  `dispatch_frame_preannotate` 改 fan-out 形态；抽帧失败 → 段 skip 语义；celery include/route 补新任务。
- **Phase 3 · 跑中进度落库**：段任务把 Redis `done/total` → `async_job.progress_pct`（max 防回退，
  低频写）；`/ai-pre/jobs` 列表跑中显真实百分比验证。
- **Phase 4 · 验证 + 版本**：E2E 复跑 tracking_car（335 帧）确认①下载次数 12→1、②跑中列表进度非 0、
  ③落库结果与 v0.21.7 逐字等价（幂等、帧号、框数不回归）；CHANGELOG + 版本 bump。

## 不在范围

- **采样步长降级**（每 N 帧抽一帧）：v0.21.7 既定的可选降级项，属**功能**非优化，另立；本计划只优化全帧路径。
- **源单阶段 → 多阶段逐帧 pipeline**：frame × depth 组合爆炸，v0.21.7 已判出范围，不在本计划。
- **真 GPU 批量**（backend 端 `predict(tasks=[...])` 堆 batch）：需 backend 改动 + 单独 ADR，见 ROADMAP
  §A `batchable 驱动源阶段分块预标（WS3）`，与本计划正交。

## 风险

- **fan-out 形态复杂化**：嵌套 chord（每视频 chain(抽, chord(段, 聚合)) + 顶层 finalize）比 v0.21.7 单层
  chord 难写难调；有 orchestrator 预抽的退化底牌兜底。
- **抽帧/预测竞态**：抽帧阶段须在段预测前**确保**帧已 ready；只读段遇缓存未命中要 fail-fast 记账，
  不能静默产 0 框（否则看着"成功"实则漏帧）。
- **回归面**：改的是 v0.21.7 刚验证的核心执行路径；Phase 4 必须逐字对齐落库结果（同一视频重跑，帧号/
  框数/幂等跳过数与 v0.21.7 一致）。
