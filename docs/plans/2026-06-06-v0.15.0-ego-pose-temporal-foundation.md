# v0.15.0 · ego_pose / 时间戳数据地基(scene 的时序骨架)

> 规划日期 2026-06-06 · 范围:给 scene 加「车体随时间的位姿轨迹 + 逐帧时间戳」。这是 nuScenes `sample_data.ego_pose` / `timestamp` 的平台等价物,是平台第一次能表达「车在动、帧之间有真实位移」。**本版只立地基、回填、透出,不做任何跨帧 UX**(与 v0.14.0 立 scene 地基同款策略)。Roadmap 见 [`2026-06-06-v0.15-temporal-fusion-roadmap.md`](2026-06-06-v0.15-temporal-fusion-roadmap.md)。
>
> **前置依赖**:v0.14.0(`scenes` 表 + `dataset_items.scene_id/frame_index`)、v0.14.2(`import_nuscenes_scene.py`,本版作为 ego pose 的第一个真实数据来源)。
>
> **为什么单独成版**:`get_next_task` 之外的一切「跨帧自动化」(插值 / Kalman / 跨相机 timestamp 补偿 / BEV 轨迹叠加)都需要「逐帧 ego 位姿 + 时间戳」。先把这套**只读地基**立稳并用真实 nuScenes 回填验证,v0.15.1 才能在其上做插值,且插值精度可被「轨迹是否连续」单独验证。

## 1. 背景与目标

### 1.1 现状:scene 只有「帧的顺序」,没有「帧的时空」

v0.14.0 给了 `scene_id + frame_index`——**帧的相对顺序**。但缺:

- **每帧车体在世界系的位姿**(ego pose):没有它,「上一帧的框搬到这一帧」只能假设车没动(`Shift+→` 直接复制 PSR);车一动,复制的框就偏。
- **每帧时间戳**:没有它,无法做 Kalman(需 Δt)、无法做跨相机微秒级 timestamp 偏差补偿(v0.14.2 `timestamp_delta_us` 已塞进 `scene.source_metadata` 但无结构、无逐帧粒度)。

nuScenes 的 `ego_pose.json`(ego→global 的 translation+rotation)+ `sample_data.timestamp` 正是这套数据;v0.14.2 脚本读了它算外参,但**没落库**。本版把它结构化落库。

### 1.2 设计选择:新建 `scene_frame_poses` 表(键 = scene_id + frame_index)

沿用 v0.14.0「表优于 JSONB」的同款论证:

- **为什么不塞 `dataset_items.metadata_` JSONB**?(a) 轨迹查询(取一个 scene 的有序逐帧位姿)会变成 JSONB 扫表;(b) 缺跨帧约束;(c) `dataset_items` 是图像/视频/点云通用表,挂 lidar 专属位姿列污染语义。
- **为什么不加列到 `scenes`**?一 scene 有 N 帧,位姿是逐帧的,不是 scene 级标量。
- **grain = (scene_id, frame_index)**:与 neighbors 查询、frame_index 语义对齐;一帧一行。

```
┌──────────┐  CASCADE  ┌──────────────────┐
│  scenes  │ ─────────►│ scene_frame_poses│
└──────────┘           │  scene_id  FK    │
                       │  frame_index int │
                       │  timestamp_us    │
                       │  ego_translation │  [x,y,z] 世界系(JSONB list[3])
                       │  ego_rotation    │  [w,x,y,z] 四元数(JSONB list[4])
                       │  source_metadata │  JSONB(自由:nuscenes ego_pose_token 等)
                       │  UNIQUE(scene_id,│
                       │     frame_index) │
                       └──────────────────┘
```

- **nullable 友好**:历史 scene 无位姿 → 无行;消费方(neighbors/manifest/UX)按「无轨迹」降级,不报错(与 v0.14.0 未 backfill task 的处理一致)。
- **坐标系约定**:`ego_translation/rotation` 存「ego→global(世界系)」,即 nuScenes ego_pose 原样;世界系本身是 ISO 8855。跨帧相对位移 = `inv(pose[i]) @ pose[j]`,由消费方算,不预存。
- **逐相机 timestamp 不在本表**:本版 frame 级时间戳取 LIDAR_TOP 的 timestamp(主帧时钟)。同 sample 跨相机微秒级偏差(v0.14.2 记的 `timestamp_delta_us`)留 v0.15.1 在 calib 旁路或扩展列处理——它服务跨相机补偿,不是 frame 级骨架。

### 1.3 成功判据

1. **migration `0098`**:建 `scene_frame_poses`(`display_id` 不需要——它不是用户实体),复合唯一 `(scene_id, frame_index)` + FK CASCADE。`uv run alembic upgrade head` 干净;down 可回滚。
2. **service**(`services/scene_pose.py`):`upsert_frame_poses(db, scene_id, poses)` / `get_trajectory(db, scene_id) -> list[FramePose]`(按 frame_index 升序)。
3. **API**:`GET /api/v1/scenes/{id}/trajectory` 返回有序逐帧 `{frame_index, timestamp_us, ego_translation, ego_rotation}`;无位姿 scene → 200 空数组。
4. **manifest 透出**:`GET /tasks/{id}/point-cloud/manifest` 增 `ego_pose`(本帧的 translation/rotation/timestamp,无则 null),前端调试可见,本版**不**消费。
5. **importer 回填**:`import_nuscenes_scene.py` 落 scene 后 upsert 每帧 ego pose + timestamp(读 `ego_pose.json` + `sample_data.timestamp`)。对真实 scene-0061:39 行 pose,逐帧位移差分连续(无跳变),时间戳单调递增 ~每帧 0.5s。
6. **回填脚本**:`scripts/backfill_frame_poses.py --dataset-id`(给已导入但缺 pose 的 nuScenes dataset 补);本机已存的 `DS-NU-*` 可补。
7. `uv run pytest -q` / `pnpm lint` / `pnpm test` 全绿;**v0.14.x 全部能力零回归**(本版纯增量)。

## 3. 各模块设计要点

### 3.1 ORM + 迁移

- `SceneFramePose`:`id` UUID PK、`scene_id` FK→scenes CASCADE、`frame_index` int、`timestamp_us` BigInteger(nuScenes 微秒)、`ego_translation` JSONB(`list[float]` 长 3)、`ego_rotation` JSONB(`list[float]` 长 4,wxyz)、`source_metadata` JSONB、`created_at`。
- 唯一约束 `uq_scene_frame_pose(scene_id, frame_index)`;索引随之(覆盖按 scene 取轨迹)。
- 校验:Pydantic `FramePose` 校验 translation 长 3 / rotation 长 4(类比 `SensorCalibration` 的长度校验,**注意用 `cast(:x AS t)` 不用 `:x::t`** —— 见 [[asyncpg-text-cast-bindparam-collision]],本版若有原生 SQL 同此坑)。

### 3.2 service

- `upsert_frame_poses(db, *, scene_id, poses: list[FramePose])`:按 `(scene_id, frame_index)` upsert(`ON CONFLICT DO UPDATE`),幂等可重跑。
- `get_trajectory(db, scene_id) -> list[FramePose]`:`ORDER BY frame_index`。
- **不**在 service 里算相对位移 / 插值(那是 v0.15.1 消费方的事);本版只存取原始 ego→global。

### 3.3 API + manifest

- `GET /scenes/{id}/trajectory`:鉴权同 scenes CRUD;空 scene 200 `[]`。
- manifest 增 `ego_pose: {translation, rotation, timestamp_us} | null`:在现有 manifest 组装处,按本 task 的 `(scene_id, frame_index)` 查 `scene_frame_poses` 单行。前端本版只在调试面板显示,不消费。

### 3.4 importer 回填

- `import_nuscenes_scene.py`:`assign_items_to_scene` 后,对每个 sample 读 `ego_pose.json`(用 LIDAR_TOP sample_data 的 `ego_pose_token`)拿 translation/rotation + `sample_data.timestamp`,组 `FramePose(frame_index=fi, ...)`,调 `upsert_frame_poses`。
  - **与 R2(v0.14.3 ego-frame)的关系**:若 v0.14.3 已落 `--frame ego`(点在 ego 系),ego pose 仍按 ego→global 存(不变);轨迹叠加在世界系。两者正交。
- `backfill_frame_poses.py`:对已导入的 nuScenes dataset(按 `scene.source_metadata.scene_token` 反查 nuScenes 根目录),补 pose 行。本机 `DS-NU-nu-mini-multi` / `DS-NU-nu-scene-0061` 可直接补。

### 3.5 lite 测试

- fake nuScenes fixture(复用 v0.14.2 的)加 `ego_pose.json` 多行(各 sample 不同 translation,造一段直线轨迹)+ `sample_data.timestamp` 递增。断言:每 scene 落 N 行 pose、frame_index 对齐、timestamp 单调、translation 差分 = 设定步长。

## 5. 已知风险 / 未尽事项

- **逐相机 timestamp 偏差**:本版只存 frame 级(LIDAR_TOP)时间戳;同 sample 跨相机 ~50ms 偏差留 v0.15.1(用本表 pose 插值补偿)。
- **ego_pose 仅 nuScenes 有来源**:SUSTechPOINTS 示例无 ego pose → 无轨迹行 → 跨帧自动化(v0.15.1)对这类数据自动降级回「假设车没动」。这是预期行为,不是 bug。
- **世界系一致性**:nuScenes ego_pose 在单个 log 内同一世界系;跨 log(跨 scene)世界系不可比——本表只在 scene 内用,不跨 scene 比较绝对坐标,规避此问题。
- **表名/grain 若将来要支持多 lidar**(v0.15.2+):ego pose 是车体级、与 lidar 路数无关,本表 grain 不受多 lidar 影响,前向兼容。

## 6. 验证策略

- **后端单测**:`test_scene_pose.py` 覆盖 upsert 幂等 / get_trajectory 有序 / 空 scene 200 空 / 长度校验拒非法 translation。
- **真实数据**:`import_nuscenes_scene.py` 重跑 scene-0061(或 `backfill_frame_poses.py` 补已存 dataset)→ `curl GET /scenes/{id}/trajectory` 返回 39 行、timestamp 单调递增、相邻 translation 距离合理(车速量级)。
- **回归红线**:本版纯增量,v0.14.x 全部 pytest/前端测试不得变动;`scene_frame_poses` 缺失时 manifest/neighbors 行为与 v0.14.x 完全一致。
