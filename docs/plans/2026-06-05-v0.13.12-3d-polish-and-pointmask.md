## 1. 背景与目标

### 1.1 v0.13.11 留下的口子

v0.13.11(`docs/plans/2026-06-05-v0.13.11-lidar-axis-convention.md`)已经把核心管线打通(dataset 声明 → manifest 透出 → 加载侧 positions / extrinsic 归一化),但留了 4 个收尾项,实测对生产可用很关键:

- **A1**:数据集没有 UI 入口去设 `axis_convention`,目前只能 API/SQL 操作 → 普通管理员用不上。
- **A2**:无自动嗅探,用户面对一个新数据集要手算外参 row 2,门槛太高。
- **A3**:annotation payload 不记 `convention_at_create`,中途切 convention 后旧框被静默重投影 → 用户无感知地被改坏。
- **A4**:导出端不知道 axis_convention 的存在,导出的 3D PSR 全在 ISO 系下;客户拿出去想还原源系格式做不了。

### 1.2 从研究里挑出的 3D 高 ROI 缺口(本期保留 C;B 延期)

调研报告 `docs/research/14-point-cloud-image-fusion.md` §14.8.2 / §14.7.1-2 提到 SUSTechPOINTS / xtreme1 / CVAT 三家都有但本平台还没做的两个能力,**本期只做 C**:

- ~~**B**(跨帧目标延续 / track)~~:**延期**。理由见顶部摘要 + §5。一句话:`group_id` 字段虽然就位,但平台缺少"同 scene 内的帧序"地基(`DatasetItem` 没有 `scene_id` + `frame_index`,任务调度不知道 scene 边界),直接做 propagate 会把"跨帧 UX"和"任务分配 / 锁"两个独立轴绕成死结。先在 v0.14.x 单独立项做帧序列地基(`scene` 概念建模 + `GET /tasks/{id}/neighbors` + 调度尊重 scene 边界),再回头加 propagate。
- **C**(点云分割工具 MVP):`PointMaskGeometry { type: "point_mask_3d", point_indices }` schema 早在 v0.13.0 落库(`_jsonb_types.py:529`),前端 `PointMaskGeometry` TS 类型也 codegen 了(`types/index.ts:302`),但工作台没有"画一个分割"的工具入口。v0.13.9 frustum 框选(`PointCloudScene.selectPointsInScreenRect`)的数学已经能选出真实点,**距离"持久化成 annotation"只差一脚**。研究里 SUSTechPOINTS 也叫 `point cloud segmentation`,是 3D 标注的第二大几何类型(仅次于 box)。

### 1.3 不在本版本

- **跨帧目标延续(B / propagate)**:整块延期到 v0.14.x。先做帧序列地基(`scene` 模型 / `frame_index` / `GET /tasks/{id}/neighbors` / 调度尊重 scene 边界),再上 propagate + 邻帧叠加显示。本期不留任何 B 相关代码 / hook / 端点雏形。
- 跨帧 Kalman / 高阶预测 / 线性插值(更上层,要等 B 落地以后)
- 多 lidar 不同坐标系(v0.13.11 ADR 已声明 v1 单 lidar)
- 大点云 worker 加速(留 v0.13.13 / v0.14.x)
- 标定增强(distortion 系数 / ego_pose 多帧聚合,留后续)

### 1.4 成功判据

1. 上传向导第一步(点云类型)与数据集设置面板都能下拉选 `axis_convention`,所选项立刻通过 PATCH 落库;切换时若存在 3D 标注弹"可能与历史标注约定不一致"的确认对话框。
2. `POST /datasets/{id}/sniff-axis-convention` 返回最匹配 convention + 相似度,前端在设置面板有"自动检测"按钮一键应用建议。
3. 新建 3D 框时 `convention_at_create` 写入 annotation payload;打开任一 3D 任务时若任意一框的 `convention_at_create` ≠ 当前 dataset convention → 工作台顶部出 banner 提示并提供"按新 convention 重投影选中"按钮(单框,不做 batch)。
4. AAP / COCO 3D 导出新增 `--axis-frame=iso|source` 选项(默认 `iso`)。`source` 时对每帧框跑 `unapplyConventionToPsr` 反向。
5. 主视图新增"分割工具"(P 快捷键)。框选 → 落地一条 `PointMaskGeometry { point_indices }` 标注;再次选中可在 3D 视图高亮所属点(半透明红描)。
6. 所有新代码有单测;`pnpm lint` / `pnpm test` / `uv run pytest` 全绿。

## 3. 各模块设计要点

### 3.1 AxisConventionPicker(A1)

8 项 + "raw" 折叠在"高级"里。每项右侧 24×24 SVG 直观画出该约定下 +X / +Y / +Z 三个箭头在屏幕坐标系的位置,让用户一眼对比"自己数据的车头到底朝哪"。

```
[图示]   ISO 8855 (+X 前 / +Y 左)       ← 推荐
[图示]   Apollo (+X 右 / +Y 前)
[图示]   KITTI camera (+X 右 / +Y 下 / +Z 前)
[图示]   SUSTechPOINTS demo (+X 左 / +Y 后)
...
[ 自动检测 ]   ← POST /sniff-axis-convention
```

切换 convention(数据集已有标注时):弹"⚠ 已有 N 条 3D 标注,这些标注的 `convention_at_create` 记录的是旧 convention;切换后渲染时会被按新 convention 重投影,可能与点云对不上"。提供"先重投影旧框再切"(走 §3.3 的 banner 流程批量重投影) / "强制切换"(只改 dataset)两个选项。

### 3.2 嗅探 sniff-axis-convention(A2)

服务端取数据集第一帧的 `camera_front` link 对应 DatasetItem(若无 front,退化到任一 `camera_*` 但成绩打折);读 `metadata_["calibration"]["extrinsic"]` row 2 前两位 `(e8, e9)`,归一化。

对 8 种 convention(忽略 `raw`),计算其"期望的 front 相机 forward 在源系下应该指向哪"——
具体推导:在 ISO 系下 front 相机光轴本来该是 +X = (1, 0, 0)。归一化数学契约 `E_iso = E_src · diag(R_normᵀ, 1)` 反推 `E_src` 的旋转块 row 2 = (R_norm 第 1 行,即 ISO +X 在 src 系下的方向)。所以**每个 convention 期望的 src-系 forward = R_norm[0]**(即矩阵第 1 行)。

```ts
// 实现入纯几何层 axisConvention.ts(前后端都用同一套)
export function sniffConventionFromForward(
  fx: number, fy: number,
): { best: LidarAxisConvention; score: number; candidates: Array<{ c: LidarAxisConvention; score: number }> };
```

返回 score = max(余弦相似度) ∈ [-1, 1];前端 UI 按 score 排序展示 top 3 让用户确认(避免低分情况盲信)。score < 0.85 时 UI 显示"不太确定,请人工核对"。

后端端点:

```python
@router.post("/datasets/{id}/sniff-axis-convention", response_model=SniffResponse)
async def sniff(...) -> SniffResponse:
    # 找 front 相机 → 取 row 2 → call axis_sniffer.sniff(fx, fy)
    # 不修改 dataset,纯查询;前端拿结果让用户决定是否 PATCH
```

### 3.3 annotation `convention_at_create`(A3)

`Box3DGeometry` 与 `PointMaskGeometry` 都加 `convention_at_create: LidarAxisConvention | None = None` 字段(`extra="allow"` 已经能透过,但加结构化校验避免拼错)。

前端 `psrFromPoints` / `coarsePsrFromGroundRect` 等所有"新建框"路径在落库时附 `convention_at_create = axisConvention`(当前 dataset 约定)。

打开任务时:扫描所有 annotation,若任一框的 `convention_at_create` ≠ 当前 `axisConvention` → 渲染 `ConventionMismatchBanner`:

```
⚠ 5 个 3D 框创建时约定为 sustechpoints_demo,数据集当前为 iso_8855。
   [按当前约定重投影所有] [仅高亮不同框] [忽略]
```

"按当前约定重投影"逻辑:对每个框,先 `unapplyConventionToPsr(psr, convention_at_create)` 取回源系下的"用户原意的几何",再 `applyConventionToPsr(psr_src, current_convention)`(这步用 R_new · psr_src,需要补一个 forward 版 `applyConventionToPsr`)。等价于矩阵作用 `R_new · R_oldᵀ` 一次性更新 center / rotation。

> 数学契约:同物体在两种 convention 下的 PSR 关系是 `psr_new = R_new · R_oldᵀ · psr_old`。Size 不变。

### 3.4 导出反向映射(A4)

后端复刻一份小巧的 Python `axis_convention.py`,包含 `R_NORM` 表与 `unapply_to_psr(psr, convention)`。AAP / COCO 3D 导出在序列化每个 box_3d 时,若 `axis_frame=="source"` 且 dataset 有 convention,调一次反向。

**不**与前端的 axisConvention.ts 做代码共享(实现量小,两边各自单测;避免 Python/TS 桥接复杂度)。

### 3.5 ~~跨帧 propagate(B)~~ — 整段移出本期

原 §3.5(`useFrameNeighbors` + `Shift+→` propagate + 邻帧叠加参考框)已删除。重新进入排期前要先把"帧序列地基"立住,否则 propagate 的"下一帧"语义无法稳定定义。详见 §5"延期细节"。

### 3.6 点云分割 MVP(C)

复用 v0.13.9 的 `selectPointsInScreenRect` 数学。新增 `setBoxSelecting` 的 sibling `setPointMaskSelecting`,效果一致(屏幕拖矩形),但松手时:

```ts
// 不再走 psrFromPoints + 新建 box,而是:
//   1. selectPointsInScreenRect 返回选中点
//   2. 但本期还要 indices —— 需要 selectPointIndicesInScreenRect 新版
//   3. 落地 annotation: { type: "point_mask_3d", point_indices: [...] }
// indices 是原始 PCD 索引(未 decimate 前)还是渲染后 indices? —— 先选渲染后 indices 简单;
```

## 5. 已知风险 / 未尽事项 → 后续 plan

### 5.1 延期细节:跨帧 propagate(B)为什么不能直接做

调研明明强调"跨帧目标延续"是 SUSTechPOINTS / xtreme1 都做了的核心生产力特性,本平台 `annotation.group_id`、三视图的 `selectedGroupId` 也都为它预留。**问题不在 propagate 本身,而在它依赖的"跨 task 帧序列"地基没建——单段 mp4 那种 task 内部的帧序列(`VideoFrameIndex`)早就有,跨 task 这一头点云 / 图像序列 / 多段视频都还没有。**具体缺三件事:

1. **`DatasetItem` 缺 scene 模型**:目前只有"一个 dataset 内所有 item 按 `file_name` 排序"的弱约定,没有显式的 `scene_id` + `frame_index` 列。当一个 dataset 跨多个 scene(如 nuScenes 一个 dataset 含 10 个 scene)时,跨 scene 边界的"下一帧"语义是错的。
2. **任务调度不知道 scene 边界**:`get_next_task`(`apps/api/app/services/task.py`)走 uncertainty / uniform / sequence 策略,**完全不**保证同 annotator 拿到的下一个 task 是同 scene 内的下一帧。直接做 `Shift+→` 会撞:跳到下帧 → 不在我的 batch → 拿不到锁 → propagate 失败但 UI 已经切走。
3. **2D 跨帧也只解决了一半,scene 模型是统一抽象**:平台已有 `VideoFrameIndex` 表(`apps/api/app/db/models/dataset.py:77`)和 `video_tracker_runner`(`apps/api/app/services/video_tracker_runner.py`),**单段 mp4 一个 task 时的内部 frame 跨帧 propagate 已经能跑**——但这只覆盖三种"时序录像"存法中的一种:

    | 存法 | 一个 task 是什么 | "下一帧"在哪 | 现状 |
    |---|---|---|---|
    | **A. 整段 mp4 一个文件** | 一段完整视频 | task 内 `VideoFrameIndex.frame_index` | ✅ 已支持 |
    | **B. 抽帧图像序列** | 一张 jpg | 跨 task | ❌ 跟 3D 同构,缺地基 |
    | **C. 多段 mp4 拼成长录像** | 一段视频片段 | 跨 task + task 内两种都要 | ❌ 缺 "哪些 task 属同 scene" |
    | **3D. 点云逐帧** | 一帧 `.pcd` | 跨 task | ❌ 缺地基 |

    **关键观察**:B / C / 3D 三个的形状一模一样——"一段录像被切成 N 个 task,跨帧 = 跨 task"。差别只在每个 task 装的文件类型不同(jpg / mp4 / pcd)。`scene_id + frame_index` 是一个**面向"时序录像"而非面向"具体文件类型"**的抽象,一立起来,B / C / 3D 三种场景能复用同一套 `GET /tasks/{id}/neighbors` API + `group_id` 跨帧延续逻辑;前端 `Shift+→` UX 写一份,三种数据形态都能用。这就是"ROI 更高"的实质:**地基代码是一份,解锁的是 3 种独立的标注场景**,不是只为 3D 做。

**正确做法分两步**(留 v0.14.x):

- **v0.14.x · 前置**:`scene` 概念建模(可能复用 `dataset_items` JSONB metadata 内的 `scene_id` + `frame_index`,或新建轻量 `scenes` 表 + FK),新增 `GET /tasks/{id}/neighbors` 端点(纯数据导航,绕过任务调度),让 `get_next_task` 在适合的策略下尊重 scene 边界(可选 flag,不强制全局)。**不**做 UX,只立模型。
- **v0.14.x+1 · UX**:回到本期原 §3.5 蓝图,做 `Shift+→` propagate + 邻帧参考框叠加。这时 `useFrameNeighbors` 就有合法 backing。

### 5.2 其它未尽事项

- **分割与 decimate stride 一致性**:本期存 stride + total 反推,如果未来引入 LOD 或多级缩略图会复杂化。留 v0.14.x 视情况换用空间哈希 / voxel index。
- **跨帧 Kalman / 线性插值**:等 B 落地后再做(SUSTechPOINTS `trajectory.py interpolate` 等价物),属于 propagate 的"高阶版"。
- **distortion / ego_pose**:研究里反复提的两个标定扩展,本期不做;若后续接 fisheye / 鱼眼相机或多帧聚合视图,再加。
- **3D AI 预标**:研究里 §14.7 没有任何工具有完整 3D 预标方案(SUSTechPOINTS 有手工辅助但无 ML 后端 → 框接);留 v0.14.x。
- **大点云 worker**:loadPcd 一次性主线程跑 PCD parse + decimate + axis rotation,1M 点实测 ~200-500ms 卡顿。worker 化是干净的优化,但需要把 PCDLoader 跨 worker 化(它本身没有 worker 版本),工作量中等;留 v0.13.13。
