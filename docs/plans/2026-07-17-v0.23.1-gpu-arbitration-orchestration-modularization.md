## 4. 目标与非目标

### 4.1 目标

- 将 gpu_arbiter.py 的 fence、runtime proof、control preparation、reconciliation、retirement、unregistered shadow logging 与 diagnostics 职责迁入 gpu_arbitration。
- 将六个平铺 sibling 一对一迁入 gpu_arbitration。
- 让 `gpu_arbiter.py` 和六个 sibling 旧文件最终只保留显式 alias、兼容说明和 `__all__`。
- 消除 retirement 中为规避历史环而保留的函数内 ml_client import。
- 让 ml_client 只依赖 cycle-safe 的 contracts、policy、rollout_state；高层 dispatch、retirement、membership、rollout control 可以依赖 ml_client，但不得形成反向边。
- 第一方生产代码、内部测试和脚本使用具体新模块；旧 GPU 路径只允许出现在 facade、兼容测试和具名历史 allowlist。
- 建立全符号兼容、相对 import、模块 SCC、层级方向、package 根懒加载、旧路径回流和关键冷启动守卫。
- 正式文档、docs impact map、CHANGELOG、版本源和运行态版本同步。

### 4.2 明确不做

- 不删除任何现有 facade，不发 DeprecationWarning。
- 不重切 ledger/scripts/lua_sources.py 或 ledger/store.py；15 个 Lua 最终字符串保持原样。
- 不修改 HTTP / WebSocket API、OpenAPI schema、数据库 schema、环境变量、Celery task 名称或 signature。
- 不重写 SQL、Redis key、Lua、锁顺序、事务边界、generation/control epoch、状态机、错误码或错误文本。
- 不开启或改变 GPU enforce / release latch。
- 不处理 video media 环、其它既有 service→worker allowlist 或无关业务缺陷。
- 不新增 BaseService、repository 层、依赖注入框架或泛化 utils.py。
- 不把本次审计发现但与结构迁移无关的业务 bug 夹带进来；它们另开 bugfix。

### 6.3 单向依赖

表中“可依赖”表示当前切片允许的领域内直接依赖；标准库、config、db models、schemas、协议包和 shared infrastructure 另按既有分层规则处理。

| 模块                  | 可依赖的领域模块                                                                  | 明确禁止                                         |
| --------------------- | --------------------------------------------------------------------------------- | ------------------------------------------------ |
| contracts             | 无                                                                                | policy 及所有 orchestration                      |
| policy                | contracts                                                                         | ledger、ml_client、高层 orchestration            |
| diagnostics           | contracts、policy                                                                 | ml_client、高层 orchestration                    |
| signing               | 无                                                                                | ml_client、orchestration                         |
| rollout_state         | 无                                                                                | ml_client、orchestration                         |
| collector_database    | 无                                                                                | 其它 GPU 领域模块                                |
| fences                | policy                                                                            | proofs 及所有高层模块                            |
| proofs                | contracts、policy、fences、ledger                                                 | ml_client、高层 orchestration                    |
| control_preparation   | contracts、fences、proofs                                                         | ml_client、dispatch、membership、rollout control |
| reconciliation        | policy、fences、proofs、ledger                                                    | ml_client、retirement、dispatch                  |
| retirement            | policy、fences、proofs、ledger、ml_client                                         | dispatch、membership、rollout control            |
| dispatch              | contracts、policy、signing、fences、proofs、ledger、ml_client                     | retirement、membership、rollout control          |
| membership_activation | contracts、signing、fences、proofs、control_preparation、ml_client                | dispatch、retirement、rollout control            |
| rollout_control       | contracts、signing、rollout_state、fences、proofs、control_preparation、ml_client | dispatch、retirement、membership                 |

ml_client 只能依赖 contracts、policy 与 rollout_state；这三个模块不得反向导入 ml_client。collector_database 是独立基础设施叶模块，只能由 collector/health orchestration 消费。

约束：

- contracts、policy、signing、rollout_state、collector_database、ledger 不导入高层 orchestration。
- diagnostics 可依赖 contracts / policy、数据库模型和 schema，但不导入 ml_client。
- proofs 可依赖 contracts、policy、fences、ledger、数据库模型与协议，不依赖 ml_client。
- control_preparation 消费 fences 与 proofs，避免把 proof 解析反塞进 fences 形成环。
- reconciliation 消费 proofs / fences / ledger，不导入 retirement、dispatch 或 ml_client。
- retirement 是允许依赖 ml_client 的高层模块；ml_client 不得反向导入 retirement。
- dispatch、membership_activation、rollout_control 可以依赖 ml_client 与低层模块，彼此不得形成环。
- package 根不 re-export 高层符号。
- 新模块不得通过自己的旧 facade 连接，也不得用函数内 import 掩盖环。
- app.services.gpu_arbitration.policy.record_gpu_shadow_dispatch 是 v0.23.0 已落地的新路径；v0.23.1 保留其对象与路径，不通过 policy ↔ diagnostics 相互 re-export 追求表面“纯化”。

## 7. 冻结合同

“结构迁移、行为零变化”至少冻结以下边界：

1. API 路径、状态码、错误 body、Retry-After 与 WebSocket 事件。
2. Celery task 名称、队列路由、worker 注册名、派发顺序与 job 状态。
3. SQL 文本与参数、行锁获取顺序、事务提交边界和数据库时钟读取位置。
4. Redis key、Lua SHA-256、KEYS / ARGV 顺序、TTL、CAS 与原子边界。
5. generation、control epoch、membership epoch、token horizon 与 retirement proof 的单调性。
6. admission token 的 alg、kid、aud、scope、claims、JTI、expiry 与签名 key 读取行为。
7. 公开函数和类的对象 identity、call signature、默认值、异常类型、枚举值与 dataclass 字段顺序。
8. rollout state、membership promotion、reset/mode ACK、dispatch outcome 与 tombstone receipt 的 reason/status。
9. 结构化日志事件名、reason、status 和 gpu_arbiter 文档字段。
10. 旧→新、新→旧冷导入顺序，以及 app.main、相关 API route、worker 入口和验证脚本的独立冷启动。

允许变化：

- 新实现对象的 `__module__`、traceback 文件路径和默认 logger 模块名。
- 第一方测试对私有函数、常量和模块对象的 patch 路径；测试必须改到真实实现模块。
- release commit 中的版本号；结构阶段 OpenAPI 必须零差异，发版时只允许 info.version 变化。

## 8. Facade 完整合同

v0.23.0 发布前先把现有 facade 补到 16/16；v0.23.1 完成后总计应有 23 个被自动验证的 facade。

| 领域         | 必须登记的旧 facade                                                                                                                                                       | 数量 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---: |
| GPU          | gpu_arbiter_store、gpu_arbiter、gpu_admission_signer、gpu_arbiter_rollout、gpu_collector_database、gpu_dispatch_authority、gpu_membership_activation、gpu_rollout_control |    8 |
| Video        | video_tracker_adapters、video_tracker_job_service、video_tracker_runner                                                                                                   |    3 |
| Export       | export、export_packaging、export_cache、export_davis、export_lidar、export_video                                                                                          |    6 |
| Data Manager | data_manager、task_views、data_manager_cursor、data_manager_entities、data_manager_entity_filter、data_manager_tracks                                                     |    6 |
| 合计         | 所有路径均使用 app.services. 前缀                                                                                                                                         |   23 |

每个 facade 必须满足：

1. 只有模块 docstring、future import、显式 from import、`__all__`。
2. 不得定义函数、类、wrapper、fallback、条件导入、import star 或 sys.modules 替换。
3. `__all__` 与冻结 inventory 完全一致；不能只验证“常用符号”。
4. 每个 old symbol 与对应 new symbol 对象 identity 相同。
5. 按 symbol kind 分别验证：可调用对象比较 inspect.signature，枚举比较 values，dataclass 比较 fields/defaults，typing alias 与常量比较冻结值。
6. 每个 facade 在独立进程执行旧→新、新→旧两种导入顺序，并验证全部符号。
7. 冷进程继续导入相关 API / worker 入口，防止模块缓存掩盖循环和注册副作用。

除旧平铺 facade 外，v0.23.0 已发布的新路径也属于冻结面。尤其 policy.record_gpu_shadow_dispatch、contracts 的公开 dispatch 类型和 ledger 的公开 API 必须保持可导入；本版本不得先移动再通过反向 re-export 制造新环。

gpu_arbiter.py 的一个 facade 会聚合多个新模块，因此 FacadeSpec 必须从“一个 facade 对一个 new module”升级为“每个 symbol 显式绑定来源 module”；不得用 package 根聚合来回避映射。

私有测试 patch 不属于外部兼容合同。P0 inventory 记录后，第一方测试应直接 patch 新实现模块；不得把私有全局重新暴露到 facade 只为让测试不改。

## 13. 回滚与停止条件

### 13.1 回滚

- 同一模块先回滚第一方调用方，再回滚新实现；旧 facade 始终存在。
- 高层 P6 依赖 P1–P5，回滚时严格按阶段逆序处理：P6 rollout_control / membership_activation / dispatch → P5 diagnostics / retirement / reconciliation → P4 control_preparation → P3 proofs → P2 fences / contracts → P1 collector_database / rollout_state / signing。每层先回滚调用方，再回滚实现与 facade，避免遗留导入断点。record_gpu_shadow_dispatch 从始至终留在 policy，无需跨模块还原。
- 本计划没有数据库或 Redis schema 变化，不需要数据回滚。
- 回滚代码后重启已加载旧模块的 worker；不通过 rebuild 掩盖 stale process。

### 13.2 立即停止

- v0.23.0 release baseline 不干净或版本源仍不一致。
- 目标文件出现并行 hotfix，冻结 inventory 已失效。
- 搬迁需要改变 SQL、Lua、锁序、事务、状态机、错误语义或公开签名。
- 新模块需要函数内 import、旧 facade 反向依赖或扩大循环 allowlist 才可启动。
- 定向或完整测试不能达到 0 失败。
- OpenAPI 在结构阶段出现任何差异。
- 冷导入、worker 注册或对象 identity 无法保持。
- 任一 PR 同时混入无关业务修复、格式化或相邻重构。
