## 1. Epic 结论

工作台布局升级采用“预设为起点、受约束自由调整、随时可重置”的 Docking Workspace，不建设无限自由的桌面窗口系统。

选用 `dockview-react@8.2.0` 作为空间布局引擎，仅使用 MIT 授权的 Core / React 能力；不引入 `dockview-enterprise`，不依赖商业版布局历史、键盘 Docking、自动隐藏等能力。Dockview 只拥有“空间结构”；路由、权限、任务、标注、工具、撤销、离线队列与 Stage 业务状态继续归 `WorkbenchShell` 及现有 hooks 所有。

交付拆成三个可独立发布版本：

## 3. 目标架构与所有权

```text
WorkbenchShell
├── Mode hooks / route / queries / mutations / history / offline / hotkeys
├── 固定 chrome
│   ├── Topbar / banners
│   └── modal / drawer / toast / object-anchored overlays
└── WorkbenchDockWorkspace                 ← 只管空间结构
    ├── WorkbenchPanelRegistry              ← 稳定 panel ID + 能力约束
    │   ├── canvas
    │   │   ├── ToolDock
    │   │   ├── WorkbenchStageHost       ← 单实例
    │   │   └── StatusBar
    │   ├── task-queue / class-palette
    │   ├── inspector / discussion
    │   └── ai-task / video-tracker      ← v0.25.2 可选注册
    └── WorkbenchWorkspaceLayoutOwner       ← 唯一快照写入者
        ├── account-scoped local cache
        └── PATCH current context only
```

组件内容从现有 Shell model 以 slots 注入，Dockview 不读取任务、标注或权限 store。这样不会建第二套工作台状态树，也不会把几何差异推进通用 Shell。

## 4. 跨版本不变量

### 4.1 画布与 Stage

1. 在同一 `taskId + stageKind` 中，停靠、浮动、预设、远端布局回灌和响应式切换不得改变 Stage DOM 身份。
2. `canvas` 是唯一必选 panel ID；快照必须恰好包含一个画布。
3. 画布禁止关闭、复制、同窗口浮动、浏览器 popout 和藏入非活动标签。
4. 工具坞、Stage 和状态栏作为画布整体移动；顶栏、横幅与模态层不参与 Docking。
5. 只有当前客户端支持且 sanitizer 已通过的本地信封，以及随后至多一次同样受支持的远端权威信封，才允许使用 `fromJSON(snapshot, { reuseExistingPanels: true })`；两次都必须通过 Stage DOM identity 门。较新 / 未知版本直接走只读标准布局，绝不传给 `fromJSON`。初始化完成后的预设、重置和面板命令只使用 move / resize / visibility API，不再全树恢复。

### 4.2 状态边界

1. 布局快照只含稳定 panel ID、分组树、顺序、比例、浮窗矩形和可见性。
2. 快照不保存 task / annotation / prediction ID、当前工具、选中集、当前帧、播放时间、相机、讨论草稿、未提交标注或后台任务状态。
3. Dockview panel `params` 不承载动态业务数据；业务数据由 Shell slots 与现有 hooks 注入。
4. 布局预设是一次性命令，不持久化“当前预设 ID”。用户手动改动后自然成为自定义工作副本。
5. 应用预设前保留一份会话级前态，通过成功 toast 提供一次“撤销布局替换”；不建持久化布局 history。

### 4.3 交互、响应式与可访问性

1. 自由布局仅在桌面工作台生效。`<=1024px` 使用运行时紧凑投影：远端初始化结算后先锁存桌面逻辑树，抑制 writer，再以原位 move / visibility API 将外围 panel 投影为单面板覆盖层；退出时由确定性布局执行器重放锁存树。紧凑期间只允许面板 show / focus / hide，预设、重置、布局撤销、dock、float 和 resize 全部禁用。整个过程不调用 `fromJSON`、不移动 canvas panel、不写回桌面快照；`<768px` 继续遵守现有工作台阻断策略。
2. 所有拖放能力都有“移到左 / 右 / 底部、浮动、隐藏 / 显示”等菜单式等价入口；不依赖企业版键盘 Docking。
3. Dockview tab、输入框和讨论草稿获得焦点时，不得触发画布单键快捷键。
4. Docking 拖放层要截止 pointer 事件，不得把拖动、松手或双击泄漏到标注画布。
5. 面板约束在每次冷恢复、预设和移动后重新应用；不假设 Dockview 会将应用自有的最小尺寸规则序列化。
6. 隐藏面板始终能从顶栏“布局 / 面板”菜单恢复；桌面模式下“重置当前布局”是最后兜底，紧凑模式仅展示为 disabled 命令。
7. “隐藏”把现有 panel 移入不可见 parking group 并保留返回位置，禁止调用 `close` / `removePanel`；`renderer: always` panel 因此不会因隐藏而销毁。

## 6. 布局持久化合同

### 6.1 作用域

`user.preferences.workbench.layout` 下新增可选 `workspace`，其合同固定为：

- `engine = "dockview@8"`，用于识别第三方快照系列，不跟踪小版本。
- `contexts` 只接受 `annotate:image`、`annotate:video`、`annotate:3d`、`review:image`、`review:video`、`review:3d` 六个稳定 key。
- 每个 context 是独立的 `{ schemaVersion, snapshot }` 原子信封，不保存 `activePresetId`。`schemaVersion = 1` 表示 v0.25.0 的五个核心 panel 且客户端锁定 canvas；`2` 表示 v0.25.1 的可移动 canvas；`3` 表示 v0.25.2 的七个 panel，且允许固定或可移动 canvas，因此 v0.25.2 不依赖 v0.25.1 是否发布。
- 单 context JSON 按 UTF-8 序列化后上限 64 KiB。
- panel ID 闭集从 v0.25.0 起固定包含 `canvas`、`task-queue`、`class-palette`、`inspector`、`discussion`、`ai-task`、`video-tracker`；每个 ID 最多一个实例，panel 总数最多 7。
- 用户 group 最多 7 个，另允许 1 个应用保留的不可见 parking group，总持久化 group 数最多 8。紧凑模式可临时增加 1 个不进入 snapshot 的 `compact-overlay` group，因此运行时硬上限是 9；后续若要增加 ID、持久化容量或布局语义必须新增 schemaVersion，不能随前端 registry 动态放宽服务端上限。

v0.25.0 后端从首版即验证版本 `1 | 2 | 3` 的闭集与各自 grammar。PATCH 不使用认证阶段加载的陈旧 `user.preferences`：必须在同一数据库事务中以 `SELECT ... FROM users WHERE id = :user_id FOR UPDATE` 重新读取并锁定用户行；查询显式刷新 ORM identity map（或只查询最新 `preferences` 标量），再在锁内基于最新 JSONB 合并、比较当前 context 已存版本并提交。请求版本低于锁内已存版本时返回 `409 layout_schema_downgrade`，不修改任何偏好。行锁同时保证不同 context 的并发 PATCH 依次从最新偏好合并，不会整列互相覆盖；同 context 且同 schemaVersion 仍按取得行锁后的提交顺序 last-write-wins。新 workspace writer 是该子树的唯一写入者，旧布局 writer 不得夹带过期 workspace 全量副本。

前端保留按账号分桶的 localStorage 快照用于首屏，但首个 preferences GET 成功或失败前禁用全部布局 mutation 与 workspace PATCH，业务标注仍可使用。只有该初始请求返回当前客户端支持且清洗通过的信封时，才可执行至多一次 `fromJSON(remote, { reuseExistingPanels: true })` 回灌；较新 / 未知版本改走只读标准布局，不调用引擎恢复。请求结算后才解除布局门，后续 refetch 永不全树回灌，因此迟到远端结果不能覆盖用户已开始的布局会话。回灌期间保持已有 panel ID 和 Stage DOM，并抑制 change listener；拖动中只更新引擎内存，顶层结构 mutation 结束后再防抖写入。

### 6.2 清洗与兼容

写入前和读取后都经过应用自有 sanitizer：

1. v0.25.0 客户端读写 v1；v0.25.1 读取 v1 / v2、写 v2；v0.25.2 读取 v1 / v2 / v3、写 v3。升级客户端在第一次布局 mutation 时把旧信封转换为自己的写入版本。
2. 客户端遇到高于自身能力的合法版本时不裁剪、不回写：当前 context 以“标准标注”只读临时布局进入工作台，禁用布局 mutation 并提示刷新到新版。服务端原信封保持不变。
3. 服务端按版本 grammar 接受对应 panel ID，并删除快照 `params` 中的业务数据。v3 在六个 context 中都固定保存七个 panel；当前 context 不适用的工具留在 `parking`，只由运行时菜单和预设过滤，权限与能力发现不参与 sanitizer 节点增删。
4. 拒绝缺失 / 重复 canvas、超限节点、非有限尺寸、popout 与不支持的结构；v1 只接受唯一、docked、非标签隐藏的 canvas，恢复后始终关闭其移动能力。合法 v2 不降级解释为 v1，因此无需从任意树猜测“中心”。
5. 浮窗矩形按工作区容器夹取，不使用全局 viewport 作为唯一坐标系。
6. 损坏、越界、未知 engine 或未知 schemaVersion 时，回退到当前 context 的“标准标注”临时布局，不阻断工作台；只有用户在受支持版本中显式“重置当前布局”才覆盖损坏值。

首次升级从旧 `leftOpen/rightOpen/floating*`、栏宽与右栏 split 解析一份初始快照。旧字段在整个 v0.25.x 期间保留、停止被新布局反向覆盖，用作前端回滚通道。不清理旧 localStorage key，不增加数据库迁移。

## 8. 明确非目标

- 不建无限嵌套、无约束尺寸或可将所有 overlay 变成窗口的通用桌面系统。
- 不支持浏览器独立 popout 窗口、多显示器坐标、跨窗口画布或多画布实例。
- 不建用户命名预设、预设 CRUD、导入 / 导出或项目 / 组织共享预设。
- 不建自定义快捷键、新命令面板或持久化布局 undo / redo。
- 不迁移对象锚定 popover、选中信息卡、桌宠、3D 三视图、相机或 PSR 浮层。
- 不重写标注 Stage、几何、视频 decoder、Three.js renderer、查询 / mutation 或权限逻辑。
- 不将个人布局写入项目 `rendering_config`，不增新数据库表。

## 9. 实体与维护增量

Entity delta：`+2 / -0`。

- `+1` 前端运行依赖：`dockview-react@8.2.0`，所有者为 Web 工作台；升级前必须过序列化、画布生命周期和 bundle-size 门。
- `+1` 可选偏好字段：`workbench.layout.workspace`，所有者为账号偏好 API；兼容成本由 schemaVersion、sanitizer 和旧字段回退吸收。
- `+0` API endpoint、数据库表 / 迁移、服务、环境变量、开关、命令、外部账号、密钥与付费能力。

实施面明显超过 8 个文件，原因是共享 Shell、偏好 schema、三种 Stage、六个上下文、依赖、分层测试、ADR 和正式文档必须同步；不借此重构与布局无关的 `useWorkbenchShellModel` 业务逻辑。

## 10. 风险攻击与最脆弱假设

### 10.1 依赖失效

截至规划日，npm 的 [`dockview-react` 版本页](https://www.npmjs.com/package/dockview-react?activeTab=versions) 列出 8.2.0 和 MIT 许可证；官方文档也确认 Core 提供 [panel / group 原位移动](https://dockview.dev/docs/core/panels/move/)、[同窗口 floating group](https://dockview.dev/docs/core/groups/floatingGroups/)、[`renderer: "always"`](https://dockview.dev/docs/core/panels/rendering/) 和带 `reuseExistingPanels` 的[冷恢复](https://dockview.dev/docs/core/state/load/)。布局历史与内置键盘 Docking 属于[单独的 Enterprise 能力](https://dockview.dev/docs/core/state/history/)，因此本 Epic 自建一次预设撤销和菜单等价操作。

Dockview 是浏览器内静态依赖，运行时不需要第三方服务。应用以自有 registry、快照包装和主题适配层隔离引擎 API；如需替换引擎，业务 panel 与账号合同不跟着重写。实际开始 v0.25.0 前重新核对锁定版本、许可证和构建产物；依赖升级失败时继续使用已验证的 lockfile 版本，不阻断现有构建。

### 10.2 规模爆炸

首版合同固定为最多 7 个 panel、7 个用户 group 加 1 个 parking group、UTF-8 64 KiB。拖动期间不序列化、不请求 API；顶层 mutation 结束后才保存。如节点或快照异常增长，sanitizer 拒绝载入并回退预设，不让过大 JSON 进入首屏路径。

### 10.3 回滚成本

整个 v0.25.x 保留旧布局字段与旧 localStorage key。默认回滚只替换前端，旧 UI 忽略新 `workspace`，后端 additive schema 作为兼容 tombstone 保留。

若必须把后端一同回滚到不识别新字段的严格 schema，固定执行以下维护窗口步骤：

1. 在入口停止 Web 流量，并用生产 Compose 叠加文件停止 API、Celery worker 与 beat；在部署目录执行下列 custom-format 全库备份与可读性校验。这里有意不使用升级指南中的 plain SQL 示例，因为后续恢复合同依赖 `pg_restore`。

   ```bash
   docker compose --env-file .env.production \
     -f docker-compose.yml -f docker-compose.prod.yml \
     stop api celery-worker celery-beat
   mkdir -p ./backups
   chmod 700 ./backups
   docker exec ai-annotation-platform-postgres-1 \
     pg_dump -U user -d annotation -Fc \
     > ./backups/workbench-layout-pre-rollback.dump
   test -s ./backups/workbench-layout-pre-rollback.dump
   docker exec -i ai-annotation-platform-postgres-1 \
     pg_restore --list \
     < ./backups/workbench-layout-pre-rollback.dump \
     > ./backups/workbench-layout-pre-rollback.list
   test -s ./backups/workbench-layout-pre-rollback.list
   sha256sum ./backups/workbench-layout-pre-rollback.dump \
     > ./backups/workbench-layout-pre-rollback.dump.sha256
   ```

2. 在旧后端部署前记录 `SELECT count(*) FROM users WHERE preferences #> '{workbench,layout,workspace}' IS NOT NULL;` 的受影响行数。
3. 单事务执行 `UPDATE users SET preferences = preferences #- '{workbench,layout,workspace}' WHERE preferences #> '{workbench,layout,workspace}' IS NOT NULL;`；提交前确认该计数归零，除 `workspace` 外不改任何偏好键。
4. 在 Web 入口仍阻断、worker / beat 仍停止时，只启动旧 API，对回滚测试账号完成 preferences GET / PATCH 与工作台进入 smoke；成功后才启动 worker / beat 并恢复 Web 流量。
5. 删除事务提交后的任一步失败都放弃本次后端回滚并保持入口停流，再次执行 `docker compose --env-file .env.production -f docker-compose.yml -f docker-compose.prod.yml stop api celery-worker celery-beat`，确认三个写入服务均停止后再校验 checksum 和恢复；不得在旧 API 仍连接数据库时运行 `pg_restore --clean`。dump 恢复后会重新包含 `workspace`，所以必须部署备份时正在运行、支持该字段的 v0.25.x API / Web，先只启动兼容 API 并跑第 4 步 smoke，成功后才恢复其他服务；绝不再次启动严格旧 API。备份文件在维护验收完成前不得删除。

   ```bash
   sha256sum -c ./backups/workbench-layout-pre-rollback.dump.sha256
   docker exec -i ai-annotation-platform-postgres-1 \
     pg_restore --clean --if-exists --exit-on-error --no-owner \
     -U user -d annotation \
     < ./backups/workbench-layout-pre-rollback.dump
   ```

### 10.4 最脆弱假设

本 Epic 有三级脆弱假设。第一，`renderer: "always"` 与 `fromJSON(..., { reuseExistingPanels: true })` 能让固定 canvas 在受支持信封的本地冷启动和单次远端权威回灌中保持 DOM 身份；这是 v0.25.0 的发布资格，失败时停止该版并重新评审“canvas 留在 Dockview 外”的架构。第二，panel / group move API 能在菜单换位时继续保持身份；失败时取消 v0.25.1，v0.25.0 和 v0.25.2 仍成立。第三，header drag 能可靠限制 drop 并截止 Stage 事件；只有第三级失败时，v0.25.1 缩窄为菜单换位，canvas header 保持不可拖。

任何一级都不允许通过 Konva / video / Three.js 重挂载、业务状态上移或额外 renderer 规避。

## 11. 跨版本验收矩阵

| 层级          | 必测路径                                                                                       | 发布阻断条件                                                     |
| ------------- | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 纯函数 / 单元 | 预设构造、快照清洗、未知 panel、重复 / 缺失 canvas、浮窗越界、schema 升级                      | 非法快照可进入引擎，或回退不确定                                 |

| 图片 E2E      | 绘制 / 选中 / 撤销、坐标对齐、auto-fit 开 / 关、annotate / review                              | 布局改动产生额外 annotation mutation 或几何偏移                  |

## 12. 文档、发布与回滚总策略

### 12.1 实施前门禁

1. v0.25.0 已完成并作为后续实现基线；v0.24.x 计划与 CHANGELOG 已归档。
2. v0.25.1 只放行画布根边缘菜单换位，继续锁住原生 DnD；资格证据写入已归档的 ADR-0072。
3. v0.25.2 使用既有 v3 七 panel wire contract；不适用于当前 context 的工具仍保留结构身份并停在 `parking`，运行时菜单按 context 过滤。

### 12.2 各版本正式文档

- 用户合同：`docs-site/user-guide/workbench/index.md` 与 `settings.md`。
- 开发者架构：`docs-site/dev/concepts/workbench-shell.md`。
- 架构决策：`docs/adr/archive/0072-workbench-dockable-layout.md`。

### 12.3 发布策略

后端 schema 先于会写入 `workspace` 的前端部署，避免 `extra="forbid"` 产生 422。`package.json` / `pnpm-lock.yaml` 改动后需重建 Web 生产镜像。任一版本未过自身发布门时，停在上一个可独立使用的版本，不携带半成品进入下一版。

每个真实版本发布都在同一提交中同步 `CHANGELOG.md`、`apps/api/app/config.py`、`apps/api/pyproject.toml`、`apps/web/package.json`，运行 `uv lock` 刷新 `apps/api/uv.lock`，由生成流程刷新 `apps/api/openapi.snapshot.json`。发布门要求 `pnpm openapi:check` 通过，且运行栈 `/health` 返回的版本与 CHANGELOG 一致。

## 13. Epic 完成条件
