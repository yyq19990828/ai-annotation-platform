# 3D 自由布局与画布工具栏方案

状态：已确认为下版本计划，已实施并通过本轮验收，待发版。基线：`83480a3e`。日常变更记录在 `CHANGELOG.md` 的 `Unreleased`，发版时统一确定版本号。

用户最终选择：三视图作为一个整体移动；相机悬浮时沿用当前模式，停靠时集中成一个组件，所有相机整组切换，不支持部分停靠、部分悬浮。将截图中的按钮优化作为本方案的第二项需求。

## 1. 用户可见结果

### 三视图与相机进入现有自由布局

| 内容       | 形态                                   | 默认打开方式                     |
| ---------- | -------------------------------------- | -------------------------------- |
| 三视图精修 | 一个面板，内部仍为俯视、侧视、正视三行 | 画布旁的一列；三行等分可用高度   |
| 相机视图   | 一个停靠组件，内部集中浏览全部相机     | 窄列纵向滚动，拉宽后自动变为网格 |
| 主画布     | 保留现有稳定 canvas 面板               | 保留用户已经选择的位置           |

三视图支持现有的左右/底部停靠、上下分割、合并标签、浮动、隐藏和找回。相机停靠组件作为一个整体支持停靠、分割、合并标签、隐藏和找回；其“悬浮显示”动作还原现有的各路相机浮层。左右区域按钮按实际位置控制停靠内容，悬浮相机沿用当前行为。新建列初始宽度为工作区的 15%，保留现有最小宽度约束；上下合并沿用目标列宽，后续可手动调整。

相机两种呈现的明确合同：

- **悬浮**：保留当前按朝向贴边、逐路拖动、折叠、归位与放大；保留每路已经记住的位置和折叠态。
- **停靠**：只出现一个“相机视图”面板。内部每路图像带名称和朝向，图像等比适配；可用宽度不足两张图时单列滚动，宽度足够时按最小图宽 240px、间距 8px 自适应网格，不出现横向滚动。
- 停靠组件头部提供“悬浮显示”；现有相机浮层菜单及顶部布局菜单提供“全部相机停靠”。切换覆盖所有相机，不逐路拆分进 Dockview。
- 首次停靠创建一列，之后优先恢复“相机视图”上次停靠位置。切回悬浮恢复原来的各路位置和折叠态；再次停靠恢复组件的列宽与位置。
- 同一时刻只有一种呈现，不同时渲染两套相机浏览组件。“隐藏相机”仅隐藏，重新打开沿用上次呈现模式。
- 不生成第三种“独立 Dockview 相机图库浮窗”。第一轮模式切换使用明确菜单动作；停靠组件仍可在各停靠区之间拖动，逐路拖入/拖出及混合模式不属于本次需求。

三视图的存在不再依赖是否选中框：没有选择时显示“选择一个 3D 框进行精修”，选中后更新同一面板。锁定或只读对象可查看，但不能编辑。每个对象的缩放和拖动中的冻结取景沿用现有行为。

相机图按面板内容区等比适配，保留投影、深度提示、点击选择及最佳相机提示。图像加载失败或当前帧缺少该相机时显示明确状态，不能残留上一帧画面。第一轮保留“放大”进入现有相机编辑层，继续使用种框、标定和 2D 成员编辑，不同时重写这些业务流程。

### 标题栏常驻快捷隐藏 ×

- 所有可隐藏的面板组标题栏右侧，在 `…` 旁常驻一个 `×`，无需先打开菜单，也不依赖 hover 才出现。覆盖现有辅助面板和新增的三视图、相机视图；主画布不提供隐藏按钮。
- `×` 隐藏当前活动面板。合并标签时只隐藏当前标签；上下分割时各面板分别提供按钮，不连带隐藏同列其他面板。最后一个面板隐藏后回收空组占位，保留其他列宽，剩余空间交给画布。
- 复用现有布局隐藏命令和返回位置，不直接调用 Dockview 删除面板。可从“布局”菜单找回，保留业务状态；相机停靠组件的 `×` 隐藏全部相机，保留呈现模式，不自动切成悬浮。
- 使用现有图标按钮与 Tooltip，命名为“隐藏{面板名称}”，支持键盘操作和清晰焦点。按钮点击不能启动面板拖动或穿透到画布；禁用条件与现有菜单动作一致。

### 截图中的两排按钮收为一条视角工具栏

当前的问题是外层容器和按钮各有边框，两排控件等权重排列，视角动作、布局预设及重置混在一起。

改后主画布左上只保留：

```text
┌─────────────┐
│ 俯视    ↺   │     ↺ 的提示和无障碍名称：重置视角
└─────────────┘
```

- 沿用产品字体及 `--sc-*` 语义颜色；一层弱边框，高度 32px，内部按钮高度 28px。按钮默认无独立边框，不再嵌套两层卡片。
- “俯视”保留当前动作和选中反馈；重置使用图标与 Tooltip，不新增一套视角模式。
- 点级分割工具启用时，在同一工具栏显示“选点方式”下拉。相机上色进度归入现有状态条。
- “框体精修 / 传感器融合 / 点级分割”放入顶部现有“布局”菜单的“3D 工作方式”分组。
- “重置相机布局”放入同一菜单的重置分组，并命名为“恢复相机排列”，与“重置为标准布局”区分。
- hover、按下、焦点及禁用态复用当前 Button/Tooltip，不增加持续动画；点击工具栏不能触发画布建框。

“恢复相机排列”在悬浮模式恢复当前默认贴边布局，在停靠模式恢复组件内部的朝向排序及滚动位置；不切换呈现模式，不移动三视图或其他工作台面板。三种工作方式只调整 3D 辅助面板的排列和显隐，保留主画布当前位置及任务队列、详情、讨论的位置；相机显隐沿用所选呈现模式，复用现有一次布局撤销。

| 3D 工作方式 | 结果                                     |
| ----------- | ---------------------------------------- |
| 框体精修    | 显示三视图，隐藏相机面板                 |
| 传感器融合  | 显示相机，沿用悬浮或停靠模式，隐藏三视图 |
| 点级分割    | 隐藏三视图和相机，扩大主画布可用空间     |

## 2. 接入方式与渲染边界

复用 Dockview、workspace executor、账号级布局 writer 及现有业务组件。保留用户要求的现有悬浮相机系统，不另写一套相机浮动壳。

```text
WorkbenchDockWorkspace
  ├─ 共享渲染 surface：一块 GPU canvas
  ├─ 主画布面板：主视图交互宿主 + 视角工具栏
  ├─ 三视图面板：三个可测量的 DOM 视口 + 编辑覆盖层
  └─ 相机视图面板：全部 CameraProjectionView 的响应式图库
             ↑ 只读取当前任务数据及调用现有编辑动作
ThreeDWorkbench / usePointCloudScene
  └─ 唯一 Scene、geometry、选择/草稿、渲染调度和回退 owner
  └─ 悬浮相机层：仅 cameraPresentation=floating 且相机显示时启用
```

三视图当前只绘制 DOM 编辑覆盖层，点云底图来自 `PointCloudScene` 的主 canvas。`PointCloudTriViewPass` 会裁掉主 canvas 范围外的视口，因此直接把 JSX 移进 Dockview 侧栏会得到空白底图。

具体调整：

1. 将 GPU canvas 的显示宿主扩展到工作区共享祖先，保留唯一 `PointCloudScene` 和 geometry。主画布及三视图都按各自 DOM 内容矩形设置 viewport/scissor，隐藏区域不绘制。
2. 分离渲染 surface 和交互宿主。主相机宽高比、OrbitControls、TransformControls、轴向辅助器、射线拾取、矩形/多边形选点均使用主画布内容矩形，不能使用整块共享 canvas 的矩形。
3. 共享 canvas 固定在 Dockview DOM 层后方，结构性容器背景透明。当前活动内容为主画布/三视图的 group 内容区透明，其他 group、标题和菜单保持不透明。三视图编辑 overlay 与输入仍在其原生 group DOM 内，位于 GPU canvas 上方。
4. 透明三视图浮窗在前时，不能让后面的不透明面板盖住其底图：根据 Dockview 浮窗的实际层级，用矩形相减得到每个较低 group 的可见区域，将同一批可见矩形用于 DOM clip-path 和 GPU scissor。裁剪覆盖该 group 的背景、标题、边框和独立 `dv-render-overlay`，不裁剪包含上层浮窗的公共祖先。viewport 和相机宽高比始终使用完整内容矩形，遮挡只改变 scissor，不能改变投影或命中坐标。将原相机图层的遮挡机制收敛为 `workbenchViewportRegions.ts` 中的共享矩形裁剪，不创建额外 renderer 或逐帧 readback。多个遮挡矩形先做相减，不能直接叠加 evenodd 洞，避免交叠处重新透出；隐藏、置顶、拖动和恢复时清理过期裁剪并重画旧位置。菜单/拖放提示/模态层仍在内容之上。现有悬浮相机模式保留其与三视图的当前优先级和避让行为。
5. 将 Dockview 的活动标签、group 显隐、parking 状态下发给视图内容。使用同一 RAF 合并 layout、尺寸、位置、group、层级和可见性变化后的 DOM 测量；纯位置拖动不能只依赖 ResizeObserver。相机停靠组件隐藏时暂停非必要的 2D 覆盖层绘制，业务状态保留。
6. 保留主 pass 先于三视图 pass 的同帧调度、geometry generation、`compileAsync` 预热去重及 device-lost 回退。停靠、隐藏和切换标签不得 dispose Scene、重新下载 PCD 或复制 GPU 资源。
7. `TriViewPanel` 保留为一个实例，不复制三份。相机停靠图库和现有浮层复用 `CameraProjectionView`，按模式互斥呈现；数据、投影及编辑回调继续由当前 3D owner 提供。

项目约束变化：本需求更新 ADR-0072 将三视图/相机留在 Stage overlay 的旧范围，也更新 ADR-0070“所有视图都在主 canvas 范围内”的前提。实施时新增 ADR 说明共享 surface 的位置与遮挡合同；保留单 renderer、单 context 的硬约束，不改写归档 ADR 的历史记录。

官方机制依据：Dockview 的 [panel rendering](https://dockview.dev/docs/core/panels/rendering/) 支持保持内容实例，隐藏时的业务和绘制暂停仍由应用负责；Three.js 的 [多视口绘制说明](https://threejs.org/manual/en/multiple-scenes.html) 展示了一个 canvas 按 DOM 矩形绘制多个视口的方式。具体事件与 API 以项目已安装的 Dockview 版本为准。

## 3. 布局身份、保存与迁移

- 固定增加 `tri-view` 和 `camera-view`，总计九个稳定 panel。相机 role 只属于组件内部的数据身份，不进入 Dockview panel 集合，数量变化不改布局树。
- workspace schema 升至 5，九个 panel 在六个 context 中始终存在，非 3D context 将两个新节点放在 parking 并隐藏入口。保留 64 KiB、深度 12 的限制；最多九个用户 group 加一个 parking，40 个树节点。同步更新 `views`、`panels`、`returns`、`floatingGroups` 及分支子节点的上限。schema 1–4 升级只补缺少的节点，保持旧树和尺寸；旧客户端继续受未来版本只读和降级 409 保护。
- 在 workspace 中记录 `cameraPresentation: floating | docked` 和 `visibilityIntent.camera-view: shown | hidden`。前者决定呈现，后者决定是否显示，关闭后重新打开可恢复原模式。floating 时 `camera-view` 固定停在 parking，现有悬浮相机层根据这两项启用；docked 时只启用停靠图库。模式切换、面板移动和显隐由同一布局命令原子更新，不在多个组件中分别推断。
- 相机停靠组件的 Dockview 原生浮动能力关闭，使用“悬浮显示”命令切回当前相机模式；从悬浮切回停靠时使用保存的返回位置。该限制不影响三视图及其他面板的浮动。
- 切帧仅更新图库和浮层内部的 role 数据。加载中、失败或缺相机不能移除 `camera-view` 或重排布局；不保留上一帧图像冒充当前帧，也不因 manifest 尚未返回而写出空相机布局。
- 初次升级相机默认继续悬浮，沿用当前账号权威偏好中的 `cameraPanels` 位置及折叠态。三视图仅从当前账号的权威 `triViewFloat` 读取一次显隐意图，采用新的停靠默认位置；不将旧绝对坐标直接换成列宽，也不读取无账号归属的历史 localStorage 坐标。
- **字段所有权**：workspace writer 管理三视图和相机停靠组件的空间状态，以及相机整体模式/显隐；`cameraPanels` 继续只保存悬浮模式的逐路坐标与折叠态。停靠切换不清空它。`triViewFloat` 则停止写入，并从 `useWorkbenchConfig` 的通用服务端和本地 writer 中排除；旧值保留以支持旧构建回滚。
- 缩放、视角、选中框、PSR 草稿及相机编辑状态仍由业务 owner 管理。runtime 更新使用现有实例及 move/visibility API，不以反复 `fromJSON` 重建 Stage。

最敏感的风险是共享 canvas 的遮挡和坐标体系：仅调整绘制矩形，会出现“图像正常但点击偏移”或菜单被盖住。验收必须同时检查视觉位置、命中位置和层级，不能以截图正常作为全部通过。

## 4. 实施顺序

### 第一批：工具栏减量与快捷隐藏

调整 `ThreeDWorkbench.tsx` 中的控件容器、按钮和状态位置；将三个既有预设及相机复位动作接到 `WorkbenchDockWorkspace` 的布局菜单。通过 Shell 的现有 props/ref 接线传递 3D 动作，不增加全局 store 或通用插件 API。

在 `WorkbenchDockWorkspace` 的面板组标题栏补充常驻 `×`，复用已有隐藏命令；第二批新增面板直接沿用这一入口。

这一批仍调用现有 3D 布局动作，独立上线即可改善截图中的观感，不依赖后续渲染改造。同步更新按钮定位测试和用户指南。

### 第二批：完整接入自由布局

把共享 surface、三视图/相机面板、schema 5、旧偏好迁移和菜单动作一起交付。它们是一组完整行为，不能先发布“能拖进侧栏但底图不可见”的半成品。

主要变更面预计超过 8 个文件，约 20–30 个生产、测试和文档文件：

- 布局：`workbenchPanelRegistry.tsx`、`workbenchLayoutSnapshot.ts`、`workbenchLayoutPresets.ts`、`workbenchLayoutExecutor.ts`、`WorkbenchDockWorkspace.tsx` 及样式。
- 接线：`WorkbenchLayout.tsx`、`useWorkbenchShellModel.tsx`、`ThreeDWorkbench.tsx`；只引入传递 scene/视口/动作所需的边界，不拆分无关业务。
- 渲染：`usePointCloudScene.ts`、`PointCloudScene.ts`、`PointCloudTriViewPass.ts`、`TriViewPanel.tsx`。复用现有 scheduler，按需要补充共享 surface 的宿主参数与可见性输入。
- 相机：新增一个 `CameraDockPanel.tsx` 作为响应式图库；复用 `FloatingCameraPanel.tsx`、`CameraProjectionView.tsx`、`useCameraPanels.ts`，保留悬浮模式的位置/折叠管理，增加整组停靠入口及模式启用边界。
- 偏好：`useWorkbenchWorkspaceLayout.ts`、`useWorkbenchConfig.ts` 及测试；前者保存模式/显隐，后者保留 `cameraPanels` 的悬浮偏好并停止写入退役的 `triViewFloat`。迁移读取当前账号的服务端权威旧值，不读取拼接后的本地兜底对象。
- 合同：`apps/api/app/schemas/workbench_workspace.py`、偏好验证测试、OpenAPI 快照和前端生成类型。
- 文档：工作台用户指南、workbench-shell 概念文档、新 ADR、CHANGELOG。

不新增依赖、后端 endpoint、数据库迁移、环境变量或外部账号。相机完整编辑层、PSR、选中信息卡、桌宠和时间轴的业务行为维持现状；不做浏览器独立窗口或多屏 popout。

部署时先更新后端 schema，再更新前端。回滚旧前端不删除 schema 5 快照，旧构建按未来版本只读处理，重新上线新版后恢复；标注数据不需要迁移或回滚。

### 本轮性能测量

2026-09-05，本机 macOS 原生 Chrome，1440 × 900、DPR 1，nuScenes mini scene-0061，约 3.5 万点、六路相机。使用现有 benchmark 脚本，各后端 20 次非相邻跳帧与 20 次相邻切帧；相邻帧提前预取 750 ms，两侧全部资源命中缓存的样本均为 20/20。计时从实际 history 导航开始，单独排除产品切帧防抖。

| 指标                       |   Legacy |   WebGPU |
| -------------------------- | -------: | -------: |
| 非相邻切帧 geometry p95    | 204.4 ms | 170.2 ms |
| 非相邻切帧 RGB p95         | 436.9 ms | 230.9 ms |
| 相邻切帧 geometry p95      |  51.7 ms |  51.2 ms |
| 全部资源命中缓存的 RGB p95 | 184.6 ms |  59.5 ms |
| 三视图首开                 |  46.8 ms |  47.0 ms |
| 三视图第一次重开           |  38.9 ms |  42.7 ms |
| 三视图第二次重开           |  37.3 ms |  42.8 ms |

WebGPU 缓存命中后的 RGB p95 较同轮 Legacy 改善 67.8%。现有性能门槛全部通过（promotionGate.passed=true）；首开与重开没有超过 100 ms 的帧隙，WebGPU 首开低于 50 ms，额外首开开销低于 10 ms。

两种后端均为一个 renderer，静止观测窗的提交增量为 0，均无运行时错误；WebGPU 全图 Canvas 回读为 0。此结果是本轮自由布局实现的测量，不替换历史报告，也不把实验渲染器改为默认开启。性能脚本中的临时布局操作不写入账号布局，临时上色偏好在结束时恢复。
