### 计划未预见的四项

1. **候选跨帧存活 → 采纳落到错误的帧**（用户实测发现）。风险清单里只写了「`mask_input` 回灌跨帧失效」，
   据此在 `cacheScope` 变化时 `resetPointSession()`——但**候选数组没清**。于是提示发生在 F20、Enter 时
   画布已到 F28，标注就落到 F28，当前帧看不见它。修法：切帧走 `cancel()`（清候选 + abort 在飞请求）。
   **教训**：「候选只属当前帧」这条设计声明，必须在切帧路径上真的执行，而不是只清会话状态。

2. **取帧谎报「当前帧尚未就绪」**（v0.21.4 起就有，本版本首次踩到）。`captureCurrentFrameJpeg` 只认解码
   位图缓存，而画布在缓存未命中时渲染的是 `<video>` 元素本身（`pickMediaImageSource` 的回退）——两者对
   「有没有帧」判断不一致，用户看得见画面却被拒绝。修法：取帧与渲染取同一源。

3. **交互工具浮条门控写死图片工具**（用户实测发现）。`InteractiveToolBar` 本就渲染在
   `stageHost.common.overlays`、视频分支也渲染 overlays，唯独门控是 `isAIToolId(s.tool)`。
   且光搬浮条不够——它上面的极性切换写 `s.samPolarity`，而 `samProbe` 只读 `altKey`，
   切「负向」仍落正点。**教训**：搬 UI 组件时要连同它驱动的状态一起接。

4. **SAM 候选顶点数失控**。一片占半屏的路面吐出 965 个顶点，采纳后满屏顶点句柄、无从编辑。
   固定像素容差不可用（能压平路面的 5px 会把宽 122px 的车从 24 顶点砍到 8 个）。改用**相对容差**：
   顶点偏移 ≤ 候选自身外接框对角线的 0.3%。落点在 `normalizeResult`，使预览 / 采纳 / 落库同一份顶点。

### 顺带发现（未修，非本版本范围）

- 视频侧 `polygon` / `polyline` / 两个 track 工具的 `G` / `L` / `Shift+G` / `Shift+L` 角标是**死标签**：
  `hotkeys.ts` 的 videoMode 分支从未绑定它们，按键无效。角标只由 `VIDEO_TOOLS[].hotkey` 渲染。

## 核心决策 1 · 帧图从哪来 —— 新增 `interactive-annotating-frame` 端点

这是本版本**唯一的架构问题**，初稿完全没有识别。

两个现成件恰好互补：

| 现成件 | 有什么 | 缺什么 |
|---|---|---|
| `interactive_annotating`（`ml_backends.py:538-580`） | `is_interactive` 校验、`client.predict_interactive(task_data, context)`、`mask_input_next` 回灌 | 图从 `_resolve_task_url(task)` 来 → 视频拿到 mp4 |
| `predict_frame`（`ml_backends.py:583-660`） | **客户端供图**：multipart JPEG → `storage.upload_crop_bytes()` → presigned URL | 调的是 `client.predict`（批量协议），非交互式 |

**定稿**：新增 `POST /projects/{pid}/ml-backends/{bid}/interactive-annotating-frame`
= `predict_frame` 的供图机制 + `interactive_annotating` 的交互调用。`predict_interactive(task_data, context)`
（`ml_client.py:218-220`）的 `task_data` 只是 `{"id", "file_path"}`，把 `file_path` 换成上传后的 frame URL 即可。

```python
# multipart: frame(JPEG) + task_id + frame_index + context(JSON, 同 InteractiveRequest.context)
# 1. 复用 interactive_annotating 的 backend 取用 + is_interactive 校验（:549-556）
# 2. 复用 predict_frame 的 upload_crop_bytes（:653-656），键名 frame-interactive/{task_id}/{frame_index}.jpg
# 3. client.predict_interactive(task_data={"id":..., "file_path": frame_url}, context=json.loads(context))
# 4. 原样返回 result / score / inference_time_ms / cache_hit / model_load_ms / mask_input_next
```

约 50 行 + 端点测试。**`context` schema 与图片侧完全一致**（`ml_backend.py:280-288`：`point` / `interactive_box` /
`exemplar`），ML backend 侧**真·零改**（它只看 `file_path` + `context`）。

> **不选的方案**：给 `interactive-annotating` 加可选 `frame_index` 让服务端 ffmpeg 抽帧。理由：引入服务端抽帧延迟与临时文件
> 生命周期，而前端 `captureCurrentFrameJpeg()` 已有解码好的当前帧（见决策 2），白白丢掉。

## 核心决策 2 · 前端复用 `useInteractiveAI`，注入 transport（不复刻）

`useInteractiveAI.ts`（~500 行）承载了 abort 取代（`:212`）、前端候选缓存（`:220-230`）、点会话累加（`:312-317`）、
multimask（`:319`）、`mask_input` 低分辨率 logits 回灌（`:252/:323`）、80ms/220ms 防抖（`:103/:106`）、
`normalizeResult`（`:648-692`）、`consume` 的按源语义（`:450-465`）。**这些视频侧一条不少地需要。**

它的唯一 HTTP 出口是 `dispatch` 内的 `mlBackendsApi.interactiveAnnotate(...)`（`:242-247`）。故：

- 加可选 `transport` 参数：默认图片版（`{task_id, context}`）；视频版闭包内 `captureCurrentFrameJpeg()`
  （`useWorkbenchShellModel.tsx:1525` 已有此方法，frame-AI 在用）→ multipart 打新端点。
- 加可选 `cacheScope`（视频传 `frameIndex`）进 `makeSamCacheKey`（现为 `{taskId, mlBackendId, ctxKind, ctx}`），
  **防跨帧串候选**。
- **切帧即 reset**：图片侧已在「切 task/backend/prompt 模式」时重置点会话（`:125-127` 注释）；视频加「切 `frameIndex`」
  为第四个重置触发点（否则上一帧的点会话会喂给这一帧）。

这是 epic「路 B 务实切分」在本版本的延续：复用纯逻辑，视频专属胶水（帧图、帧作用域）留在视频栈。

## 核心决策 3 · 交互 backend ≠ tracker backend

初稿未提。视频项目通常绑 `sam2_video` / `sam3_video`（**tracker**），而交互式 SAM 需要 `is_interactive` 的**图像** backend
（gsam2 / sam3 PCS）。二者是不同 backend，经全局 ML 注册表（v0.19.0）分别 link 到项目。

- 前端复用现成的 `routing.resolveInteractive(prompt)` → `interactiveBackendId`（`useWorkbenchShellModel.tsx:893`），
  与图片侧同一套「交互后端选择 + 持久化」机制（v0.18.29-31），**不复用 tracker 的 backend**。
- **E2E 前置**：`P-VIDEO-DEV` 需 link 一个 `is_interactive` 图像 backend。按 memory，本机 8G 卡跑得动图片侧 SAM3（:8002 PCS）
  / gsam2；`sam3_video` 视频追踪必 OOM——**本版本不碰视频 tracker，故不受该限制**。

## 核心决策 4 · 前置修复 `ai_interactive` 建模错误（跨图片/视频）

**必须在视频 AI 工具落地前修，否则视频侧会把同一个建模错误复制一遍。** 这是本版本的前置 PR0.5。

### 病灶：`ai_interactive` 被建模成「几何单位」，而它是「手段/能力」维度

`ToolUnitId` 含 `ai_interactive`（`constants/toolUnits.ts:16`），并在 `TOOL_UNIT_GROUPS:126-134` 注册为
一个带类别/属性编辑器的设置 tab；`TOOL_TO_UNIT:19-24` 把 5 个 AI 工具全映射到它。但 AI 交互**不产出独有几何**——
smart-point / smart-box / exemplar 产 polygon（本属 `region`），magic-box 产 bbox（本属 `bbox`），
text-prompt 产 bbox 批量召回。派生出两个症状：

| 症状 | 机理 | 证据 |
|---|---|---|
| **① 「AI 交互」enabled 开关对工作台零作用（死开关）** | 因为它不是几何单位，用「单位启用」过滤它会误伤能力协商，于是 ToolDock 写死一行豁免：`if (t.id === "select" \|\| t.requiredPrompt) return true;` | `ToolDock.tsx:214-215` |
| **② 伪类别域：AI 画的与手画的同物异单位** | 采纳落库 `tool_unit_id = toolUnitForTool(s.tool)` = `ai_interactive`，而几何是 bbox/polygon。类别按 `tool_unit_id` 隔离 → 手画 polygon 归 `region`、AI 画 polygon 归 `ai_interactive`，**两套类别列表互不相通**，须在两个 tab 各配一遍 | `useWorkbenchAnnotationActions.ts:210`；`transforms.ts:275-292` |

**存量实测（DB 实查，2026-07-07）**：`annotations` 中 `tool_unit_id='ai_interactive'` 共 **19 条**
（17 × `bbox` + 2 × `polygon`）；`predictions` **0 条**；**0 个项目**配过 `ai_interactive` binding
——即这个类别/属性设置**从未被真正使用过**，反证它不该存在。迁移风险极低。

### 定稿：AI 交互开关移入「ML 模型」设置项，`ai_interactive` 单位退役

「能不能用 AI 工具」完全取决于绑了什么 ML backend，归属 **ML 模型** tab（`ProjectSettingsPage.tsx:50`，
`MlBackendsSection`），而非「类别与属性」。

- **存储**：新增 `project.ai_interactive_enabled: bool = True` 列（与既有项目级 ML 配置 `box_threshold` /
  `text_threshold` 并列）。**不复用 `tool_bindings.ai_interactive.enabled`**——`ToolBinding` 带
  `classes` / `attribute_schema` / `keypoint_schema` / `video_modes`，给 AI 交互用会全部闲置，
  正是刚清理掉的 `VideoModesConfig` 死字段同款问题。
- **`TOOL_TO_UNIT` 改按产出几何归属**（`stage/tools/toolUnits.ts:19-24`）：
  `smart-point` / `smart-box` / `exemplar` → `region`；`magic-box` / `text-prompt` → `bbox`。
- **`ai_interactive` 从 `TOOL_UNIT_GROUPS` 移除**（不再渲染类别/属性 tab）。`ToolUnitId` Literal 前后端
  **保留**（存量 JSONB 兼容），标注为 deprecated。同步更新 `defaultEnabledUnits` 注释（`toolUnits.ts:164`）。
- **数据迁移（alembic）**：`UPDATE annotations SET tool_unit_id = CASE geometry->>'type'
  WHEN 'polygon' THEN 'region' ELSE 'bbox' END WHERE tool_unit_id = 'ai_interactive'`（19 行）。

| 视频工具 | wire mode | 采纳落几何 | `VIDEO_TOOL_TARGET` |

## 核心决策 5 · 候选渲染独立 overlay，不进 `VideoKonvaAiLayer`

新建 `VideoSamCandidateOverlay`（对齐图片侧独立组件 `ImageStage.tsx:296-388`），**不复用** `VideoKonvaAiLayer`：

- `aiBoxFrames.ts` 是**批量候选（落库 `Prediction`）**的帧作用域去重 SSOT；交互式候选是**瞬态、不落库、只属当前帧**，
  混入会污染该 SSOT（memory「AI候选帧SSOT」）。
- `resolveAiBoxAtFrame:43` 的 fallthrough 会把 polygon 候选当 Rect 画错。
- magic-box 预览需画 AABB `<Rect>` 而非 `<Line>`（图片侧 `ImageStage.tsx:350-368` 同款分支）。

## 全局红线

- **坐标 0-1 归一化全程**：图片侧在指针捕获处归一化一次（`ImageStage.helpers.ts:14-26`），prompt → HTTP → 候选 →
  `tightenBboxFromPolygon` → 落库全程 0-1 不变，**无任何 0-100 百分比**。视频侧沿用 `videoKonvaCoordinates.ts`。
  违反会重演 memory「交互候选坐标系」的 yolo exemplar 飞出画布 bug。
- **切帧清候选**：候选与点会话严格属于 `frameIndex`，切帧必须 `cancel()`，绝不串帧。
- **图片侧零回归**：`useInteractiveAI` 加参数须默认行为不变；图片 4 工具逐一回归。
- **候选不落 `Prediction`**：交互候选走前端 state，采纳时直接建 `Annotation`（对齐图片侧），
  与 frame-AI 的「落 Prediction → `/accept`」两条路不混。

## 风险

- **逐帧上传延迟**：图片侧交互**不传像素**（服务端按 URL 取图），视频侧每次 prompt 上传一帧 JPEG（~100–300KB）
  + 服务端上传对象存储换 presigned URL。首击延迟必然高于图片侧。缓解：`captureCurrentFrameJpeg` 复用已解码 bitmap（省解码）；
  同帧连击命中前端候选缓存（`useInteractiveAI.ts:220-230`）跳过 HTTP；点精修阶段 `mask_input` 回灌不重传图仍需重传帧
  （**待 PR1 实测**：若成瓶颈，可加「同帧 frame_url 复用」缓存，服务端按 `{task_id}/{frame_index}` 键去重上传）。
- **`VIDEO_TOOL_TARGET` 静默放行**（决策 4）：漏加映射 → 门控被绕过且无报错。**PR1 必须有单测**覆盖
  `videoToolEnabled("smart-point", {})`。
- **PR0.5 改 `TOOL_TO_UNIT` 波及图片存量类别解读**：AI 采纳的标注从 `ai_interactive` 改归 `region`/`bbox` 后，
  其 `class_name` 需在目标单位的类别列表中存在，否则成孤儿类别。缓解：DB 实查表明 **0 个项目配过 `ai_interactive`
  binding**（类别本就来自 fallback），19 条存量按几何类型迁移即自洽；迁移后须抽查这 19 条的类别解读。
- **`ai_interactive` Literal 不可删**：后端 `_jsonb_types.py` 的 `ToolUnitId` Literal 与存量 JSONB 绑定，
  PR0.5 只从 `TOOL_UNIT_GROUPS` 移除（不再渲染），Literal 保留并标 deprecated。贸然删会让历史 JSONB 校验失败。
- **`useInteractiveAI` 参数化回归图片侧**：该 hook 是图片交互的心脏，改签名有回归面。缓解：`transport` 默认值 = 现行为，
  纯增量；图片 4 工具逐一 E2E。
- **`mask_input` 回灌跨帧失效**：低分辨率 logits 绑定具体图像；切帧必须连同 `maskInputRef` 一起失效（`:127` 注释语义扩展）。
- **交互 backend 未 link**：视频项目历史上只 link tracker，用户会看到工具全灰。需在置灰 tooltip 明确指引「项目设置 → ML 后端」。
