## 1. 背景与动机

### 1.1 为什么是现在

v0.13.7 把相机从「沉底一字排」改成「按物理朝向悬浮环绕」,但**只在 3 相机示例集(front/left/right)验证**,并在 L4 明确把两件事 scope-out:窄屏自动折叠、上色 worker 化。v0.14.2 引入 nuScenes 脚本后,实测数据变成 **6 相机**(CAM_FRONT / FRONT_LEFT / FRONT_RIGHT / BACK / BACK_LEFT / BACK_RIGHT),3 相机时够用的布局到 6 相机就密了;同时 6 相机让「上色 / 深度栅格」逐点投影开销翻倍,主线程一次性算的卡顿肉眼可见。两条线在 6 相机实测下同时到了「该收尾」的点。

CHANGELOG 已多处自己挂账(直接引用):
- `[0.13.8]` 段:「上色 1e6 点 × N 相机为一次性计算(不进每帧);深度栅格同。**worker 化**、遮挡 z-test 留迭代。」
- 深度联动段:「1e6 点 × 3 相机量级 10ms 级,主线程仍可接受;**不进 worker 化(留 v0.14.x)**。」
- v0.13.7 L4:窄屏自动折叠「按 Simplicity First 不做……列 follow-up」;非目标列「6+ 相机(nuScenes FL/FR/RL/RR)实测调优」「上色 worker 化」。

本版就是把这三笔账一起结清。

### 1.2 三块目标(对应三个 scope)

| 块 | 现状痛点 | 本版目标 |
|---|---|---|
| **A · 6 相机布局收尾** | 面板固定贴边不可拖;同朝向多相机堆叠在 6 相机下太密 / 互相遮挡;窄屏只能由 `MobileWorkbenchBlock` 整页拦截或手动折叠 | 相机面板可**自由拖动**(复用 `FloatingPanelShell` / `useDragMove`);同列堆叠**避让优化**;窄屏**自适应折叠** |
| **B · worker 化** | `colorize.ts` / `depthmap.ts` / `projection.ts` 三个纯函数在主线程一次性跑,6 相机时投影 / 采样翻倍,跑时主线程卡顿 | 把这三类一次性计算移入 **web worker**;主线程不阻塞;worker 不支持 / 失败时**主线程兜底**回退现状 |
| **C · point_mask 分割深化** | v0.13.12 只落「拖屏幕矩形选点 → point_indices」(P 快捷键),无法精细圈选,选错无法补救 | **套索 / 多边形选点** + 已选点的**增删编辑**(加点 / 减点)+ **类别绑定**完善 |

### 1.3 定位铁律(贯穿全文)

**v0.14.6 必须纯前端、零后端改动、零数据迁移。**

- 不新增 / 不修改任何 API 端点、schema、alembic 迁移。
- `PointMaskGeometry`(`apps/web/src/types/index.ts:312`)落库字段不变:仍只有 `point_indices` + `convention_at_create` + `decimate_stride` + `source_point_count`。套索 / 多边形 / 加减点都只是**前端选点交互**,最终产物仍是同一个 `point_indices` 数组,后端无感知。
- worker 化是**前端内部重构**:三个纯函数的输入输出契约不变,只把执行从主线程搬到 worker 线程。

## 2. 分层范围(scope)

### A · nuScenes 6 相机实测布局收尾

> 这是 v0.13.7 的 follow-up。四角布局(front_left/right、back_left/right 沿竖边收拢)v0.14.2 已调过一轮,**剩下三项未做**:自由拖动、同列堆叠优化、窄屏自适应折叠。

**A1 · 相机面板自由拖动**
- 现状:`FloatingCameraPanel.tsx` 自身**不带定位**(`:1` 注释明示「位置由外层决定,本组件不自带定位」),位置由外层「按 anchor 分组的定位容器」(`ThreeDWorkbench.tsx:1563` `cameraGroups.map` → `.camGroup ${ANCHOR_CLASS[anchor]}`)用 CSS 贴边钉死,**不可拖**。v0.13.7 当时刻意「位置由朝向决定、不做自由拖动」,理由是「自由拖动会丢掉按朝向语义」。
- **本版决策**:保留**默认锚位 = 朝向**(不丢语义),但**允许用户拖离默认位**做临时避让;拖动后位置按 role 存 localStorage,**双击标题条 / 「归位」钮一键回锚**。即「朝向是默认,拖动是覆盖,可还原」。
- 复用 v0.13.10 通用浮窗壳:`FloatingPanelShell`(`apps/web/src/pages/Workbench/shell/FloatingPanelShell.tsx`)+ `useDragMove`(`apps/web/src/pages/Workbench/shell/useDragMove.ts`)。`useDragMove` 已提供:`handleProps`(挂标题条)、`clampFloatingPosition`(夹在 viewport `bounds` 内)、resize 时自动重夹(`useDragMove.ts:116`)、`isInteractiveTarget` 跳过按钮(`useDragMove.ts:34`,⛶ / 收起钮不触发拖动)。

**A2 · 同朝向多相机同列堆叠优化**
- 现状:`.camGroup`(`ThreeDWorkbench.module.css:485`)是同 anchor 相机的 flex 容器,`.camGroup > *`(`:493`)沿边堆叠。3 相机时每边至多 1 个;6 相机时 `top-left`/`top-right`/`bottom-left`/`bottom-right` 各 1、`top`/`bottom` 各 1,理论一边最多 1 个仍不挤。**但 anchor 推导退化 / 名字撞扇区时**(如多个相机都落 `top`),会在同一列竖排堆叠,6 相机比 3 相机更易撞,需更好的堆叠 / 避让。
- **本版决策**:同 anchor 多相机时,堆叠列做**间距 + 最大高度约束 + 超出折叠为小标签**:一列内超过 N 个(默认 2)的相机自动收起为贴边小标签(`.camPanelTab` 已有,`FloatingCameraPanel.tsx:60`),避免竖排顶满屏。堆叠顺序按 role 稳定排序(确定性,不随 map 顺序抖动)。

**A3 · 窄屏自适应折叠**
- 现状:`App.tsx:228` 在视口 `< 1024px` 时由 `MobileWorkbenchBlock`(`App.tsx:233`)**整页拦截**(「建议宽度 ≥ 1024px」),工作台根本进不去;`≥ 1024px` 进入后相机面板只能手动折叠 + localStorage 记忆(v0.13.7 L4)。
- **本版决策**(不动 `MobileWorkbenchBlock` 的 1024 整页门):在 `≥ 1024px` 但仍偏窄的中间档(如 1024–1366px),6 相机环绕会吃掉太多主视图。加一个**视口宽度阈值的「相机自动折叠」**:窄于阈值时所有相机面板**默认折叠为小标签**(用户仍可逐个展开),宽于阈值恢复默认展开。**关键:不覆盖用户手动态**——用 localStorage 已存的手动折叠态优先,自动折叠只对「用户没显式操作过的」相机生效(加一个 `auto` vs `manual` 来源标记,避免自动态把用户展开的又关上)。

### B · 上色 / 深度 / 投影 worker 化

> 三个纯函数已是**无 WebGL 依赖、可单测**的纯算术(各自带单测:`colorize.test.ts` / `depthmap.test.ts` / `projection.test.ts` 各 6 例),worker 化主要是**封装 + 数据传输设计**,不是重写算法。

**B0 · 哪些进 worker**

| 纯函数 | 当前调用点 | 一次性?进 worker? |
|---|---|---|
| `colorizePoints`(`geometry/colorize.ts:70`) | `ThreeDWorkbench.tsx:1103`,开上色开关时一次性算 | 是 → **进 worker** |
| `buildDepthRaster`(`geometry/depthmap.ts:58`) | `ThreeDWorkbench.tsx:1100`(上色前建栅格)+ `CameraProjectionView.tsx:69`(深度热力图 / hover) | 是,换帧 / 开关时一次性 → **进 worker** |
| `projectPoints`(`geometry/projection.ts:87`) | `CameraProjectionView.tsx:122`(画框线)+ `ThreeDWorkbench.tsx:1196`(算可见角点数) | **框角点投影是 8 点的轻量计算,不进 worker**;只有**点云级**的一次性投影(上色 / 栅格内部那条逐点投影链)进 worker。见下「边界」。 |

- **边界**:`projectPoints` 对外暴露的是「投影一组角点(8 个)」,这种 ≤ 几十点的调用**留主线程**(进 worker 反而被消息往返拖慢)。真正昂贵的是 `colorize` / `depthmap` **内部**那条「1e6 点逐点投影」(它们各自内联了 `projectOne`,见 `colorize.ts:33` / `depthmap.ts:32`)。所以本版 worker 化的单元是 **`colorizePoints` 整体 + `buildDepthRaster` 整体**,投影内核随之被搬进 worker;`projection.ts` 的对外 API 不动。

**B1 · worker 封装**
- 新增一个点云计算 worker(命名建议 `geometry/pointcloud.worker.ts`),用 Vite 原生 worker 导入(`new Worker(new URL('./pointcloud.worker.ts', import.meta.url), { type: 'module' })`,Vite 内置支持,无需改 `vite.config.ts` 的 build 配置)。
- worker 内 import 同一份 `colorize.ts` / `depthmap.ts`(纯函数,worker 与主线程共用一份实现,**保证 worker 与主线程兜底逻辑零分叉**)。
- 消息协议:请求 `{ kind: 'colorize' | 'depth', reqId, ... }`,响应 `{ reqId, ok, result | error }`。用 `reqId` 配对(换帧 / 反复开关上色会并发多请求,旧请求结果按 `reqId` 丢弃,等价现有 `cancelled` 闭包语义,`ThreeDWorkbench.tsx:1083`)。

**B2 · 数据传输策略(Transferable / 结构化克隆)**
- 入参 `positions: Float32Array`(N×3,1e6 点级 ≈ 12MB)**不能每次结构化克隆**(会复制 + 卡)。两条路二选一,本版取**前者**:
  1. **首选:Transferable 转移所有权**——把 `positions` 的 `ArrayBuffer` `postMessage(msg, [positions.buffer])` 转给 worker,零拷贝。**但转移后主线程那条 buffer 被 detach**;而 `positions` 来自 `scene.getPointPositions()`(`PointCloudScene.ts:552`,指向 GPU geometry 的 `position` attribute,**主线程渲染还在用,不能 detach**)。故**转移前先 `slice()` 出一份副本**再转移(一次 12MB 拷贝,远小于「克隆 + 算」的总开销,且拷贝在主线程一帧内完成可接受;后续可优化为常驻 worker 缓存当前帧 positions)。
  2. 备选(本版不做,列 follow-up):worker 持有当前帧 positions 副本,换帧才重传,开关上色 / 改相机不重传 positions。
- 相机采样 `CameraSample.data: Uint8ClampedArray`(RGBA 像素)同理:`loadCameraSample` 已在主线程 `getImageData`(`ThreeDWorkbench.tsx:1093`),把这些 buffer 一并 transfer 给 worker;每相机一份,6 相机 = 6 次 transfer。
- 出参 `colorizePoints` 返回 `Float32Array`(N×3)、`buildDepthRaster` 返回 `DepthRaster`(多个 typed array):worker 算完 transfer 回主线程(同样转移所有权,主线程接收后 `setPointColors` 写回 GPU)。

**B3 · 兜底:worker 不支持 / 失败时回退主线程**
- **必须有主线程兜底**,且兜底走**同一份纯函数**(B1 已保证 worker 内 import 的就是 `colorize.ts` / `depthmap.ts`):
  - 环境无 `Worker`(理论不会,Vite 目标都支持;但 SSR / 测试 jsdom 下可能没有)→ 直接同步调纯函数(现状路径)。
  - worker 构造抛错 / `onerror` / 超时(给一个保守超时,如 10s)→ fallback 到主线程同步算,并打一条 `console.warn`(可观测)。
  - **fallback 不改变结果**:worker 与主线程跑同一份纯函数,输出逐字节一致(单测已覆盖这些纯函数;worker 化不新增算法分支)。

**B4 · 与「一次性算不进帧」性能契约的关系**
- 现有契约(CHANGELOG 反复声明):上色 / 深度栅格是**一次性计算**(开关 / 换帧时算一次),**不进每帧 RAF**;每帧只做 WebGL 渲染。worker 化**不改这个契约**,只是把「那一次」从主线程搬到 worker 线程:
  - 搬之前:一次性计算在主线程跑 → 那一帧主线程卡(掉帧 / 拖拽卡顿)。
  - 搬之后:一次性计算在 worker 跑 → 主线程那段时间仍可流畅响应(orbit / 拖框 / 切相机),算完异步写回。
- 触发时机不变:依赖数组仍是 `[colorizeOn, cameras, stats]`(`ThreeDWorkbench.tsx:1111`),不会因为 worker 化变成每帧触发。

### C · point_mask_3d 分割工具深化

> v0.13.12 只落「屏幕矩形选点」MVP。本版深化为套索 / 多边形 + 加减点编辑,**产物仍是 `point_indices`**(零后端)。

**C0 · 现状(直接复用的地基)**
- 落库类型 `PointMaskGeometry`(`types/index.ts:312`):`{ type, point_indices, convention_at_create, decimate_stride, source_point_count }`,**本版不动**。
- 选点内核 `PointCloudScene.collectPointsInScreenRect`(`PointCloudScene.ts:466`):已把每个点用 view-projection 矩阵投到 NDC,判落不落选区(矩形:`ndcX/ndcY` 在 min/max 之间,`:499`),返回 `{ positions, indices }`(`indices` 已乘 `pointIndexStride` 回原始点序,`:501`)。
- 对外:`selectPointMaskInScreenRect`(`PointCloudScene.ts:516`)→ `PointMaskSelection { pointIndices, decimateStride, sourcePointCount }`。
- 高亮:`highlightPointMask(indices)`(`PointCloudScene.ts:578`),把选中点染红(`base` 色复位 + 选中点 RGB=(1,.12,.12))。
- 交互:工具 `point-mask`,P 快捷键(`ThreeDWorkbench.tsx:613`);`pointMasking` 态(`:323`)下拖屏幕矩形 → `handlePointMaskSelect`(`:857`)→ `createAnnotation`。类别由 `pointMaskPlaceClass`(`:327`,当前激活类或首个 point_mask 类)绑定。

**C1 · 套索 / 多边形选点**
- 把 `collectPointsInScreenRect` 的「矩形判落」泛化为「任意屏幕多边形判落」:新增 `collectPointsInScreenPolygon(polygon: {x,y}[])`,投点到 NDC 后做**点在多边形内**测试(ray-casting / 奇偶规则)。矩形是它的退化特例(可保留 rect 快路或统一走 polygon)。
- 两种交互:
  - **套索(lasso)**:按住拖动连续采样屏幕点 → 自由曲线闭合成多边形(松手闭合)。
  - **多边形(polygon)**:逐次点击落顶点,双击 / Enter / 回到起点闭合。
- UI:`point-mask` 工具下提供选点模式切换(矩形 / 套索 / 多边形),默认沿用矩形以不破坏既有肌肉记忆;模式状态可 localStorage 记忆。
- 屏上预览:复用现有框选预览矩形的渲染层(`isBoxSelecting` 相关,`ThreeDWorkbench.tsx:889`/`:1388`),改画多边形 / 套索路径(SVG / canvas overlay)。

**C2 · 已选点增删编辑(加点 / 减点)**
- 选中一个已存在的 point_mask 标注时,进入**编辑态**:在原 `point_indices` 基础上做增量:
  - **加点(add)**:再框 / 套一块 → 新选点**并入** `point_indices`(集合并,去重)。
  - **减点(subtract)**:按住修饰键(如 Alt)圈选 → 从 `point_indices` 中**移除**落入选区的点(集合差)。
- 实现:在主线程对 `Set<number>` 做并 / 差,产出新 `point_indices`,走现有 annotation 更新路径写回(geometry 仅 `point_indices` 变,其余字段不动)。
- 高亮实时反映:每次增删后调 `highlightPointMask(nextIndices)` 即时重染,所见即所得。
- 边界:`decimate_stride` / `source_point_count` 在抽稀场景下保持与首次选点一致(增删用的是同一帧同一抽稀 stride 的点序,`collectPointsInScreenRect` 已乘 stride 回原序,`:501`,天然一致)。

**C3 · 类别绑定完善**
- 现状 `pointMaskPlaceClass`(`ThreeDWorkbench.tsx:327`)取「激活类 ∈ point_mask 类集」否则首个。完善点:
  - 创建后允许在属性 / 列表里改 point_mask 标注的 `class_name`(走现有 annotation 更新,不新增字段)。
  - 选点工具激活但无可用 point_mask 类(`pointMaskClasses` 为空,`:316`)时,UI 明确禁用 + 提示,而非静默不放置(现状 `canPlacePointMask` 已判空 `:321`,补 UX 提示)。
- **不做**:类别相关的后端校验 / 新建类别流程(本版纯前端;类别体系是既有项目配置)。

## 3. 详细设计(带 file:line)

### 3.1 A1 自由拖动 — 复用 `FloatingPanelShell` / `useDragMove`

`FloatingCameraPanel.tsx`(整文件 1–100)当前是「标题条 + `CameraProjectionView`」的轻壳,**自身无定位**(`:1` 注释明示「位置由外层决定,本组件不自带定位」)。两种落地路线:

- **路线 A**:让 `FloatingCameraPanel` 在「自由拖动态」时改用 `FloatingPanelShell` 包裹(它已带 `data-floating-panel` + 拖动 header + clamp + resize,`FloatingPanelShell.tsx:159`/`:178`),默认锚位态仍用现有 `.camGroup` CSS 贴边。即「未拖过 = CSS 锚位;拖过 = `FloatingPanelShell` 绝对定位(position/size 存 localStorage)」。
- **路线 B(推荐)**:不引整个 `FloatingPanelShell`(它带 resize / merge-back / close 一堆相机面板用不上的钮),只复用 `useDragMove`(`useDragMove.ts:62`)给现有 `.camPanel` 挂 `handleProps`,position 用 CSS 变量注入(同 `FloatingPanelShell` 的 `--floating-panel-x/y` 写法,`FloatingPanelShell.tsx:171`)。

**取路线 B**(Simplicity First:相机面板要的是「能拖 + 能归位」,不要 resize / merge-back)。
- position 来源:默认 `null`(走 CSS 锚位);拖过后存 `{x,y}`,按 role 进 localStorage(key 同 `FloatingCameraPanel.tsx:32` `collapseKey` 风格,如 `pcwb:cam-pos:${role}`)。
- `bounds` = viewport(`.viewportWrap` 矩形),`clampFloatingPosition`(`useDragMove.ts:43`)负责不让面板被拖出屏。
- 归位:双击标题条 / 「归位」钮 → 清掉 localStorage pos,回 CSS 锚位。

### 3.3 B worker 化 — 数据流

```
主线程(ThreeDWorkbench effect, 现 :1076–1111)
  colorizeOn 开 + 换帧
   → positions = scene.getPointPositions()           // GPU attribute, 不可 detach
   → posCopy = positions.slice()                      // 一次 12MB 拷贝
   → samples = await loadCameraSample(...)             // 6 相机 RGBA buffer
   → worker.post({kind:'colorize', reqId, posCopy, samples, baseColors}, [posCopy.buffer, ...sample.buffers])
                                                       // Transferable 零拷贝转移
   ── worker 线程 ─────────────────────────────────
   → import { buildDepthRaster } from depthmap        // 同一份纯函数
   → import { colorizePoints } from colorize
   → rasters = samples.map(buildDepthRaster)           // z-test 用
   → out = colorizePoints(posCopy, baseColors, samples, rasters)
   → post({reqId, ok:true, out}, [out.buffer])
   ───────────────────────────────────────────────
  主线程 onmessage:
   if (reqId !== latestReqId) drop                     // 等价现有 cancelled 闭包
   else scene.setPointColors(out)                      // 写回 GPU
```

- 失败兜底(B3):worker 构造 / onerror / 超时 → 同步 `colorizePoints(...)`(现状 `:1103` 那行原地保留作 fallback 分支),`console.warn('[pointcloud-worker] fallback to main thread', err)`。
- 深度栅格的 `CameraProjectionView.tsx:69` 调用(hover / 热力图)同理可 worker 化,但它是 per-camera 较小栅格;**本版优先把 `ThreeDWorkbench` 那条点云级 colorize+栅格搬进 worker**(收益最大),`CameraProjectionView` 的栅格视体量决定是否一并搬(可作组内小项)。

### 3.4 C 分割深化 — 选点内核泛化

- `PointCloudScene.collectPointsInScreenRect`(`:466`)→ 抽出 `collectPointsInScreenPolygon(polygon)`:NDC 投影部分(`:482`–`:498`)复用,落选判定从「矩形 min/max」换成「点在多边形内」。`selectPointMaskInScreenRect`(`:516`)保留(矩形快路),并加 `selectPointMaskInScreenPolygon`。

- 高亮:增删后 `highlightPointMask(next)`(`:578`)即时重染。

## 6. 验证策略(可验证成功标准)

### 纯函数单测(可独立断言)
- `pointInPolygon`:凸 / 凹多边形、点在边上 / 顶点、自交多边形(奇偶规则);矩形退化等价旧 `collectPointsInScreenRect` 落选集。

- 既有 `colorize.test.ts` / `depthmap.test.ts` / `projection.test.ts`(各 6 例)全绿不回退(worker 与主线程共用这份实现)。

### 浏览器手测(含 6 相机实测)
用本机 nuScenes-mini(`DS-NU-*`,6 相机)进工作台:
- **A1 拖动**:拖某相机面板离锚位 → 跟手、不超出 viewport(clamp 生效);刷新后位置保留;双击标题 / 归位钮 → 回锚位。⛶ / 收起钮点击不误触发拖动。

- **A3 窄屏**:把窗口拉到 1024–1366px → 相机默认折叠为小标签,主视图够大;手动展开某相机后再 resize → 用户展开态不被自动折叠覆盖;拉回宽屏 → 恢复默认展开。
- **B 主线程不阻塞(可观测验证)**:开上色(6 相机 1e6 点)时,**同时持续 orbit 拖拽 / 切相机**——主线程应保持流畅,不出现「点上色开关后画面冻结一拍」。可观测手段:
  - Performance 面板录制:worker 化前主线程有一段长 task(colorize 同步耗时);化后该长 task 移到 worker 线程,主线程 main track 无对应长块。

  - worker 缺失兜底:DevTools 禁 worker / 模拟构造失败 → 上色仍出结果(走主线程),console 有 fallback warn,结果与正常一致。
- **C 分割**:
  - 套索圈一团点 → 红高亮、落库 `point_indices` 非空;多边形逐点点击闭合同效。
  - 选中已有 mask → 加点(再圈)使红点增多;Alt 减点使红点减少;`point_indices` 随之增减、去重无错。
  - 改 mask 的 `class_name` 生效;无可用 point_mask 类时工具禁用 + 提示。

## 8. 风险与依赖

- **Transferable detach 主线程 positions**:`getPointPositions` 指向 GPU geometry attribute,**绝不能直接 transfer**(detach 后渲染崩)。必须先 `slice()` 副本再转移(§B2 路线 1);单测 / code review 重点盯这一处。
- **worker 与主线程实现分叉风险**:靠「worker import 同一份 `colorize.ts` / `depthmap.ts`」根除——绝不在 worker 里复制一份算法。`pointcloudCompute.test.ts` 断言两路结果逐字节一致兜底。
- **自由拖动 vs 朝向语义**:v0.13.7 当初拒绝自由拖动是为保「位置=朝向」语义。本版用「默认锚位 + 可拖覆盖 + 一键归位」化解:语义仍是默认,拖动只是临时避让且可还原,不丢 v0.13.7 的价值。
- **窄屏自动折叠覆盖手动态**:自动态绝不写 localStorage,手动态优先;否则会出现「用户展开的相机一 resize 又被自动关上」的恼人 bug(三级来源设计,§3.2)。
- **抽稀下增删点序一致**:`collectPointsInScreenRect` 已乘 `pointIndexStride` 回原始点序(`:501`),加减点用同一帧同一 stride,集合并 / 差天然对齐;换帧 / 改抽稀阈值后再编辑旧 mask 属跨帧场景,本版不处理(同 v0.13.12 既有约束)。
- **Vite worker 在测试环境**:jsdom / vitest 下 `Worker` 可能不可用 → 正好走主线程兜底分支,单测即覆盖此路径(不需要为测试 mock worker)。
- 依赖均已就位(`FloatingPanelShell` / `useDragMove` v0.13.10;三个纯函数 + 单测 v0.13.6/8;point_mask MVP v0.13.12;6 相机数据 v0.14.2),本版**不新增第三方依赖**。
