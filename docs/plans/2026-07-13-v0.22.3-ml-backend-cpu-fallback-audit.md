# ML Backend GPU 失效诊断与 CPU fallback 地基审计

- 状态：**初始观测链已交付；P0a 语义纠偏已实现并验证**
- 日期：2026-07-13（初始计划），2026-07-14（复核与纠偏）
- 上层计划：[跨 Backend GPU 显存互斥编排实施计划](2026-07-14-v0.22.4-cross-backend-gpu-memory-arbitration.md)
- 架构依据：[ADR-0049](../adr/archive/0049-cross-backend-gpu-memory-arbitration.md)（Accepted；P0b 已冻结）

## 1. 结论

初始交付建立了五个 backend `/health.compute` 到平台、注册表快照和前端的传输链，但把“探测结果”“CPU fallback 能力”和“GPU 驻留”混成了同一件事。复核后确定：

- Grounded-SAM2 与 YOLO 支持受控 CPU fallback。
- SAM3 image、Multiplex video、PVS video 的 vendor 路径依赖 CUDA，本期明确为 GPU-only，不再执行虚假 CPU 重试。
- RapidOCR 与 ONNXTools 的启动 probe 只决定构造偏好；`effective_provider` 必须来自已加载业务 session，不能由 provider 偏好推断。
- `compute` 只描述计算路径诊断，不证明 GPU 模型、session 或 tensor cache 已释放；显存仲裁只能消费后续 P1 定义的 `residency.gpu_loaded`。

因此，本计划完成的是 ADR-0049 的 **D1 诊断地基纠偏**。它不代表 Redis 账本、准入、驱逐或受管全池卸载已经可用，也不直接解锁 L2 enforce。

## 2. 目标与非目标

目标：

- 让 torch 设备 latch 线程安全、向 CPU 单调，并区分设备错误与业务错误。
- 只在 CPU replacement 完整构建成功后提交 fallback 状态。
- 让 GPU-only backend 在模型加载检测到设备不可用时返回可重试的结构化 503。
- 让 ORT `effective_provider` 反映当前已加载业务 session 的真实 primary provider。
- 让注册表快照、实时 `/observe` 和 PerfHUD 使用一致的 `compute` 字段与 CPU fallback 判定。
- 用契约测试覆盖并发 latch、事务回退、GPU-only、ORT 内部 fallback 和平台透传。

非目标：

- 不实现跨 backend 显存仲裁、预算、Redis 锁、LRU 驱逐或多卡自动放置。
- 不在本期移植 SAM3 vendor 代码以支持 CPU。
- 不把 `compute` 当显存账本真值，不据此减记 allocation。
- 不抽取统一 backend 生命周期基类；受管 `residency`、generation、active/draining 和 full-pool unload 留在上层计划 P1。

## 3. 最终契约

五个 backend 保留顶层结构：

```json
{
  "compute": {
    "configured_device": "cuda",
    "effective_device": null,
    "effective_provider": null,
    "cpu_fallback_supported": true
  }
}
```

字段语义：

- `configured_device`：部署意图或模型/session 构造偏好。
- `effective_device`：torch 进程已确认的有效构造/回退路径；未加载或无法得出单一结论时为 JSON `null`。进程 latch 为 CPU 时仍可能有旧 GPU pool 暂存，不能据此推断所有请求或驻留都在 CPU。
- `effective_provider`：ORT 已加载业务 session 的单一实际 primary provider；空池、缺失 provider 或混合 provider 时为 JSON `null`。
- `cpu_fallback_supported`：`false` 表示 GPU-only；缺失或 `null` 为兼容旧 backend 的未知能力，只有显式 `false` 会抑制 CPU fallback 告警。

CPU fallback 角标只在以下条件同时成立时显示：

1. `configured_device` 是已知 GPU 配置：`gpu`、`cuda` 或 `cuda:*`；
2. 实际设备为 `cpu`，或实际 provider 为 `CPUExecutionProvider`；
3. `cpu_fallback_supported` 不是 `false`。

显式 CPU、未知配置、未加载、混合 provider 和 GPU-only 均不显示角标。实时 `/observe` 获得可解析的 HTTP 200 时以实时 `compute` 为准，即使 backend 自报 degraded 或字段为 `null`；只有实时 HTTP 探测不可达/失败时才回退到注册表缓存，避免复活陈旧的 CPU fallback 状态。

## 4. 实现结果

### 4.1 共享 torch runtime

`apps/_shared/backend_runtime/src/aap_backend_runtime/device.py`：

- probe 与状态读写使用锁保护；并发 CUDA probe 不能覆盖已经提交的 CPU latch。
- CUDA probe 用真实 tensor 分配并以 `.item()` 强制同步，避免异步错误漏检。
- `latch_cpu()` 单调且幂等；显式 CPU 配置不触发 GPU probe。
- 只把 CUDA、driver、cuDNN 等设备故障识别为 device error；OOM 和普通模型/配置错误不永久 latch。
- `require_gpu_device()` 为 GPU-only 路径提供统一加载前置检查。
- CUDA cache 清理由 `free_gpu_memory()` best-effort 执行，不覆盖主异常。

该 latch 仍是 backend 进程级诊断状态，不能表达多池 mixed residency，因而不得用于显存减账。

### 4.2 torch backend

| backend | 当前行为 | `/health.compute` |
|---|---|---|
| Grounded-SAM2 image | SAM 与 DINO 作为一个事务构建；任一设备错误触发整组 CPU replacement，只有两者都成功才提交 CPU latch | `cpu_fallback_supported=true` |
| Grounded-SAM2 video | video predictor 发生设备错误时先完整构建 CPU replacement，成功后提交 latch | `cpu_fallback_supported=true` |
| YOLO | 仅 device error 触发 CPU move；模型确认移动成功后才提交 latch，普通构建错误原样抛出 | `cpu_fallback_supported=true` |
| SAM3 image / Multiplex / PVS | builder 前强制验证 GPU；不做 CPU 重试。模型加载边界检测到 GPU 不可用时转换为协议 503，并带 `Retry-After` | `cpu_fallback_supported=false` |

SAM3 已加载后若推理阶段才发生新的 CUDA 故障，本计划未承诺统一转换为同一 503；后续应在受管生命周期契约中收口。

### 4.3 ORT backend

- RapidOCR 与 ONNXTools 的启动 probe 会核对临时 session 的 `get_providers()[0]`，内部静默落到 CPU 时只选择 CPU 构造偏好。
- `effective_provider` 不读取启动 probe 缓存，而是遍历当前 predictor pool 中实际业务 session。
- 所有可读 session 的 primary provider 相同才返回该 provider；空池、session 缺失、不可读或混合 provider 均返回 JSON `null`。
- ONNXTools 已在 `docker-compose.ml.yml` 定义；本轮构建了镜像并完成容器测试，但没有启动此前不存在的运行实例。

### 4.4 平台与前端

- API `ComputeInfo` 增加 `cpu_fallback_supported`，`ObserveTarget` 实时透传 `/health.compute`。
- 健康检查仍将完整 `compute` 写入注册表 `health_meta`；overview、PerfHUD 快照和实时 observe 均保留该字段。
- Runtime Observe 与 PerfHUD 复用 `isCpuFallback()`；torch、ORT、显式 CPU、unknown、`null` 与 GPU-only 使用同一判定。
- OpenAPI snapshot 同步新增字段和语义说明。

所有 pytest 均禁用 cache provider 并关闭字节码写入；镜像内临时 pytest 安装随 `--rm` 容器删除，没有留下测试中间产物。

### 5.2 镜像与运行态

- 五个 backend 镜像均已重新构建成功。
- 原本运行的 Grounded-SAM2、SAM3、YOLO、RapidOCR 已用新镜像重建，四个容器健康检查均为 `healthy`。
- 实际 `/health` 验证：未加载的 Grounded-SAM2 / YOLO 为 `effective_device=null` 且支持 fallback；SAM3 为 `effective_device=null` 且 `cpu_fallback_supported=false`；空 RapidOCR pool 为 `effective_provider=null`。
- ONNXTools 当前无运行实例，未改变既有服务状态；在完成真实部署验证前，上层仲裁继续将其视为 non-evictable。

## 6. 剩余风险与交接

- CI/mock 能覆盖错误分类与状态转换，但没有坏 GPU 上下文测试台，仍需真机故障演练。
- `compute` 不表达 pool/session residency；CPU 与 GPU 混合驻留是合法状态，必须由后续 `residency` 契约保守对账。
- RapidOCR 的 full-pool unload、Grounded-SAM2 image+video 全池卸载、五 backend active/draining 与 generation fencing 均未实现，属于上层计划 P1。
- ONNXTools lazy handle 构建/卸载尚无 active guard，RapidOCR 同 key 冷启动仍可能在池锁外重复构造；它们不影响 P0a provider 真值，但会造成并发峰值与卸载竞态，必须由 P1 收口。
- ADR-0049 已完成 P0b 整体重写并 Accepted；P1 的受管 residency / full-pool unload、active/draining 与 generation fencing 尚未实现，仍不能开启 enforce。

## Outcome

P0a 已关闭原地基的设备语义误报：Grounded-SAM2 / YOLO 提供事务性 CPU fallback，SAM3 明确 GPU-only，ORT 只报告实际业务 session provider，平台实时与缓存链路不再误报。P0b 已冻结并接受 ADR-0049；下一步是 P1 受管 backend 生命周期契约，Redis 仲裁器和自动驱逐尚未开始实施。
