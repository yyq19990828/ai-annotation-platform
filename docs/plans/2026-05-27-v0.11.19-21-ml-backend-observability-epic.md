# Epic · ML Backend 可观测性补全：Prometheus 抓取 + Grafana 可视化 + 告警

> 切片索引 · 横跨 v0.11.19 / v0.11.20 / v0.11.21 三个版本

## 背景

监控链路目前三层缺口不一：

| 环节 | 状态 |
|---|---|
| **埋点（backend）** | ✅ 两个 backend 都已全量埋点。`/health` + `/metrics` **共用同一次 NVML/psutil 采样**（见各 `observability.py`）：GPU 利用率/温度/功耗、推理延迟、embedding cache 命中、容器 CPU/内存；grounded-sam2 另有 `video_tracker_*`。 |
| **抓取（prometheus.yml）** | ❌ `scrape_configs` 只有 `anno-api`（`host.docker.internal:8000`）+ prometheus 自身。**两个 ML backend（8001/8002）都没有 scrape target**——埋点进不了 TSDB。 |
| **展示（grafana）** | ❌ 仅 `anno-overview.json` 一个 dashboard，只画 anno-api，**无任何 GPU / ML backend 面板**。 |

### 与超管 PerfHud 的关系（重要，决定本 epic 边界）

超管「模型市场 · ObserveBackendsPanel」的实时性能面板（PerfHud）与 Prometheus/Grafana 是**两套独立通道、同一数据源**：

| | 超管 PerfHud | Prometheus + Grafana |
|---|---|---|
| 取数 | backend **`/health`** JSON | backend **`/metrics`** exposition |
| 采集 | beat 任务 `ml_health.publish_ml_backend_stats` 每 1s 遍历 `ml_backends` 表（`state != disconnected`）拉 `/health` | Prometheus scrape |
| 通道 | WebSocket `/ws/ml-backend-stats` 推超管前端 | PromQL → Grafana |
| 存储 | `ml_backends.health_meta`（**仅当前快照**） | TSDB（留 14d） |
| 能力 | 实时一眼看，**无历史、无告警** | 趋势 / 对比 / 历史 / **告警** |

**结论**：两者互补不重复。PerfHud 满足"运营实时一眼看"，本 epic 补的是"SRE 趋势 + 告警 + 容量规划"。**PerfHud 全程零改动**——它读 `/health` JSON 的 `gpu_info` 字段，不读 `/metrics` 指标名，故下面的指标改名对它零影响（v0.11.19 回归点须验证）。

### 可扩展性现状（回应"后续加更多 backend 能否高效接入"）

- **PerfHud 已天生高效** ✅：新 backend 在超管注册进 `ml_backends` 表 + 实现标准 `/health`，beat 自动纳入，**零代码**。
- **Prometheus 目前低效** ❌：`static_configs` 写死 target，每加一个 backend 要手改 prometheus.yml + reload。

本 epic 的架构主线就是消除这个差距：让 Prometheus 也以 **`ml_backends` 表为单一真相源**自动发现 backend（见下）。

## 已锁定的设计基线

| 维度 | 决策 |
|---|---|
| 指标命名 | **统一为裸名 + `service` label 区分**。改 sam3 `observability.py` 去掉 `sam3_` 前缀，与 grounded-sam2 对齐（`gpu_utilization_percent` 等）。符合 Prometheus 惯例（同语义同名、靠 label 区分实例），一张 panel 可同时画两个 backend。现无存量 dashboard 引用，改名代价最低。 |
| 服务发现 | Prometheus v2.55 `http_sd_config` 指向 API 新端点，API 从 `ml_backends` 表生成 backend target 列表 → **注册即被 scrape**，与 PerfHud 共用真相源。 |
| 告警通知 | 新增 `alertmanager` service（`monitoring` profile），receiver **复用平台 `SMTP_*` 配置**发邮件，不引入新通知渠道。 |
| PerfHud | **不动**。仅在 v0.11.19 做回归验证（改名后 PerfHud 仍正常）。 |
| 兜底 | http_sd 端点不可达时，prometheus.yml 保留**注释掉的 static target 示例**，供"无 API 自动发现"的生产部署手填。 |

## 统一抽象

```
ml_backends 表（单一真相源）
  ├─ PerfHud:    beat 1s 遍历 → 拉 /health → WS 推前端           (已实现)
  └─ Prometheus: http_sd 拉 API 端点 → scrape 各 backend /metrics  (本 epic 新增)

API 新端点  GET /internal/metrics-targets   （内网/token 鉴权）
  从 ml_backends（state != disconnected 且有 endpoint）生成 http_sd JSON:
  [{ "targets": ["<host:port>"],
     "labels": { "service": "<name>", "backend_id": "<uuid>" } }, ...]
```

两个被现状逼出来的前置动作（详见 v0.11.19）：
- **补 GPU 显存 gauge**：`/metrics` 现在只有 GPU 利用率/温度/功耗，**没有显存**（显存只在 `/health`）。不补则 Grafana 画不了显存趋势。命名统一时一并加 `gpu_memory_used/total_mb`。
- **`ml_backends` 是 project-scoped**（有 `project_id`）：同一物理 backend 可能多条记录，http_sd 端点须**按 host:port 去重**，避免重复 scrape。

**待解决的网络视角风险**（v0.11.19 重点）：`ml_backends.url` 存的是 **API 视角**的 base_url（dev 常是 `host.docker.internal` / `ML_BACKEND_DEFAULT_URL`），而 Prometheus scrape 时是 **prometheus 容器视角**，两者可达地址可能不同。
- dev：prometheus 与 backend 同 compose 网 → 端点应吐 service DNS（`grounded-sam2-backend:8001`）。
- 生产：backend 在独立 GPU 机 → 吐注册 url 的 host:port，文档须声明"prometheus 与 backend 网络需互通"。
- 初版策略：端点直接解析 `ml_backends.url` 的 host:port 产出 target，dev 提供 service 名映射开关；网络不通的 target 表现为 `UP=0`（无害，可诊断）。

### 每版本验证标准

- **v0.11.19**：① `--profile monitoring` + `--profile gpu`/`gpu-sam3` 起齐后，Prometheus `/targets` 自动出现两个 backend；② Grafana Explore 查 `gpu_utilization_percent{service="grounded-sam2"}` 与 `{service="sam3"}` 都有数据；③ 新注册一个 backend，无需改配置即出现在 targets；④ **PerfHud 回归**：超管面板 sam3 的 GPU/cache 数据仍正常。
- **v0.11.20**：dashboard 自动加载，两个 backend 在同 panel 双线呈现，`$service` 切换生效。
- **v0.11.21**：`docker stop` 一个 backend → 5m 后 Prometheus alert `firing` → mailpit（dev）收到告警邮件。

## 跨切片约束

- **命名统一（v0.11.19）是 Grafana（v0.11.20）的硬前置**：不统一则每 panel 要写两套 query。
- **PerfHud 零影响是红线**：每个切片若触碰 backend `observability.py`，都要回归 PerfHud（读 `/health` 不读 `/metrics`，理论安全，仍须验证）。
- **单一真相源**：禁止在 prometheus.yml 写死 backend static target（兜底注释除外）；新 backend 接入两个模块都应"注册 `ml_backends` 即生效"。
- **文档同步**：deploy 指南 §8.5 / §2.8 监控段、`docs-site/ops/observability/`；新端点 → `docs-site/api/`（OpenAPI 自动，注意 `/internal/*` 是否纳入快照）；新 env（如 http_sd token、alertmanager SMTP 映射）→ `.env.example` + `pnpm docs:gen-env-vars`。
- **CHANGELOG**：三版各一段 `## [0.11.x] - 2026-xx-xx`（feature，记 CHANGELOG）。
- **profile 与网络**：backend 在 `gpu`/`gpu-sam3`、prometheus/alertmanager 在 `monitoring`；target `UP=0` 在 backend 未起时属正常，告警规则 `up==0` 要排除"未部署"误报（如只对 `state != disconnected` 的 backend 告警，或 alert 加 `for: 5m` + 维护静默）。
