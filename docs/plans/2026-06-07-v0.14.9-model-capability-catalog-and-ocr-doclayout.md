# v0.14.9 · ML Backend 能力声明协议 v2(多模型目录 + infra)+ OCR / Doc Layout 首发

> 规划日期 2026-06-07 · 修订 2026-06-07
>
> 范围:把"能力建模"从**单模型 capability snapshot** 升级为面向**多模型 backend** 的**能力声明协议 v2**(一个 backend 暴露 model list,每个 model 自带 能力 + infra + variants),并在此地基上落地首批新模型族 OCR / Doc Layout。
>
> 平台方向不变:模型运行在独立 ML Backend,前端不下载模型、不直连本地推理。`/setup` 仍是能力的唯一真相源(SoT),目录是派生缓存 + UI 视图。

---

## 0. 本次修订相对原计划改了什么

原计划(单模型版)的隐含假设是 **1 个 backend ≈ 1 个模型族**(grounded-sam2 / sam3 各占一个,`/setup` 返回单个能力快照)。但未来企划要补两类 **1 个 backend = N 个模型** 的 backend:

- **ONNX 聚合 backend**:一个进程聚合多个异构模型(检测 / 关键点 / OCR / 抠图…),各带不同能力。
- **YOLO 官仓 backend**(基于 ultralytics):一个仓覆盖 `系列(v8/v11/v12) × 任务(det/seg/pose/obb/cls) × 尺寸(n/s/m/l/x)`,上百个权重。

因此本次修订:

1. 新增**能力声明协议 v2**:`/setup` 顶层增 `infra` + `models[]`;能力声明、目录、校验全部下沉到 **model 粒度**(§3)。
2. **复用而非新造**:几何输出复用现有 `supported_geometric_outputs`(不再用原计划的 `output_geometry_types`);系列/尺寸复用现有 `supported_variants` 多轴结构。
3. 新增 **`infra` 字段**(pytorch / onnx / paddle / …),贯穿协议 → 缓存 → UI(§3.3.4、§4.6)。
4. 存储策略从"直接建表"改为**先复用 `health_meta` JSONB、独立表作为 Phase 2**(§4.2),呼应原计划"不要为每个模型族扩表"的风险约束。
5. OCR / Doc Layout 保留为本版**首发验证实例**,改挂到协议 v2 之下(§3.6、§4.4、§5C)。

**两个已确认决策**:
- 承载方式 = 升级当前 v0.14.9 计划(本文件),版本切分见 §8。
- 目录粒度 = **按任务能力分条目**(det/seg/pose/obb/cls 各一条,由输出几何决定边界;series/size 作 variant 维度)。

## 1. 背景

平台已有:

- ML Backend `/health` / `/predict` / `/setup` / `/versions` 协议(见 `docs-site/dev/reference/ml-backend-protocol.md`)。
- `/setup` 能力协商:`supported_prompts` / `supported_trackers` / `supported_text_outputs` / `supported_geometric_outputs` / `supported_variants`(多轴) / `params`(JSON Schema)。
- 能力快照持久化:`check_health` → `extract_capabilities`(`services/ml_capabilities.py`)→ `ml_backends.health_meta["capabilities"]`(无 alembic 迁移,`HealthMeta` schema `extra="allow"`)。
- Grounded-SAM2 / SAM3 两个官方 backend;图像批量预标、交互式 point/bbox/text/exemplar prompt;video tracker job;prediction import / accept / reject。

X-AnyLabeling 的启发不是"再做一个 SAM",而是它把 OCR、doc layout、pose、OBB、tracker、depth 等放进一个**模型能力目录**。平台需要同类目录,但不照搬桌面端本地下载和 Qt 推理 —— 目录只声明"远端 backend 能做什么",不托管权重。

---

## 2. 设计原则

1. **`/setup` 是 SoT,目录是派生缓存**:首版不要求用户手填 manifest;目录由 `/setup` 派生 + 缓存 + UI 视图。
2. **向后兼容是硬约束**:老 backend(无 `models[]` / 无 `infra`)必须零改动继续工作 —— 平台把顶层能力字段合成**一个隐式 model**(§3.4)。
3. **复用 > 新造**:能复用现有字段名(`supported_geometric_outputs` / `supported_variants` / `params`)与现有 result schema 的,一律复用,不发明并行词汇。
4. **简洁优先,延迟建表**:能力存储首版走现有 JSONB,独立表等到有明确跨 backend 查询需求再上(§4.2)。
5. **协议演进,不动 predict**:`infra` / `models[]` 只影响能力声明与目录展示,**不改 `/predict` 请求/响应 schema**,不新增 prediction 表结构。

## 3. 能力声明协议 v2(核心)

### 3.1 `/setup` 顶层结构

```jsonc
{
  // ── 必填三元组(协议 v1 已有,不变)──
  "name": "yolo-ultralytics-backend",
  "version": "0.1.0",              // backend 镜像/代码版本
  "model_version": "ultralytics-8.3.x",

  // ── v2 新增 ──
  "infra": "pytorch",             // backend 默认基础设施;可被 model.infra 覆盖
  "models": [ /* §3.2 model 条目数组 */ ],

  // ── v1 顶层字段:仍可用,作为"隐式单 model"的兜底(§3.4)──
  "is_interactive": false,
  "supported_prompts": [],
  "supported_geometric_outputs": [],
  "supported_variants": [],
  "params": {}
}
```

- `models[]` 存在 ⇒ 平台按多模型目录解析,**忽略顶层能力字段**(顶层仅留 name/version/infra 等 backend 级元数据)。
- `models[]` 缺省 ⇒ 平台用顶层字段合成一个隐式 model(老 backend 路径)。

### 3.2 model 条目结构

```jsonc
{
  "id": "detect",                       // 必填. backend 内唯一,(backend_id,id) 构成目录主键
  "display_name": "YOLO 目标检测",       // UI 展示名
  "task": "detection",                  // 必填. 受控词表,条目边界,决定输出几何与项目兼容性(§3.3.1)
  "model_family": "yolo",               // 可选. 家族标签(yolo/sam/paddleocr…),UI 二级分组用
  "infra": "pytorch",                   // 可选. 缺省继承 backend.infra(§3.3.4)
  "is_interactive": false,              // 该 model 是否支持交互式 /predict

  "supported_prompts": ["none"],        // 受控(§3.3.5). none = 纯批量,无交互 prompt
  "supported_geometric_outputs": ["bbox"],   // 受控(§3.3.2),复用现有字段名
  "output_attribute_types": [],         // 受控(§3.3.3). OCR: ["text","language"]; cls: ["class"]
  "supported_text_outputs": [],         // v1 已有,text 路径专用(box/mask/both)

  "supported_variants": [ /* series/size 多轴,§3.5 */ ],
  "default_thresholds": { "conf": 0.25, "iou": 0.7 },
  "resource_profile": { "device": "gpu", "batchable": true },
  "params": { /* 该 model 专属 JSON Schema(Draft-07 子集),前端 schema-form 渲染 */ }
}
```

### 3.3 受控词表(capability vocabulary)

能力声明的关键是**一套受控枚举**,且与平台内部类型锚点对齐(`TOOL_UNIT_IDS` / LabelStudio result type / `data_type`)。

#### 3.3.1 `task`(任务能力,条目边界,必填)

| `task` | 输出几何 | 对应 result type | 备注 |
|---|---|---|---|
| `detection` | `bbox` | `rectanglelabels` | |
| `obb` | `rotated_bbox` | `rectanglelabels`(带 `rotation`) | 与 detection 输出几何不同,单列 |
| `segmentation` | `polygon` | `polygonlabels` | 实例/语义分割统一 polygon 落地 |
| `keypoint` | `keypoint` | `keypointlabels` | pose / 关键点 |
| `classification` | `none` | 无几何,写 attribute | 整图/区域分类 |
| `ocr` | `bbox`/`rotated_bbox`/`polygon` | 对应几何 + `attributes.text` | §3.6 |
| `doc_layout` | `bbox`/`polygon` | 对应几何,class=版面类别 | §3.6 |
| `tracker` | per-frame geometry | (video tracker 协议) | 模态=video |
| `interactive_seg` | `polygon`/`mask` | `polygonlabels` | SAM 类,prompt 驱动 |

> `task` 是**项目兼容性校验**的主轴。`model_family` 仅作展示分组,不参与校验。

#### 3.3.2 `supported_geometric_outputs`(几何输出,复用现有字段)

枚举与 `TOOL_UNIT_IDS` 对齐:`bbox` / `rotated_bbox` / `polygon` / `polyline` / `keypoint` / `none`。
(3D 的 `lidar_box_3d` / `point_mask_3d` 暂不在本版 backend 范围,留位。)

#### 3.3.3 `output_attribute_types`(属性输出,半开放)

`text`(OCR 文本) / `language` / `orientation` / `class`(分类标签)。其余按需扩展;layout 版面类别走 `class_name`(而非 attribute)。

#### 3.3.4 `infra`(基础设施,受控,本次新增)

`pytorch` / `onnx` / `paddle` / `tensorrt` / `openvino` / `other`(兜底)。
- **层级**:backend 顶层声明默认值;model 条目可覆盖(如 YOLO 仓里部分条目导出 onnx)。
- **缺省**:老 backend 不报 `infra` ⇒ 缓存标 `unknown`,UI 不渲染 badge 或显示"未声明"。
- 用途与边界见 §4.6。

#### 3.3.5 `supported_prompts`(沿用 v1,新增 `none`)

`none`(纯批量,无交互) / `point` / `bbox` / `text` / `exemplar` / `sketch` / `scribble`。
YOLO / OCR / layout 是 `["none"]`(批量自动);SAM 类仍是 point/bbox/text/exemplar。

### 3.4 向后兼容规则

| backend 形态 | 平台解析 |
|---|---|
| 无 `models[]` | 顶层 `supported_*` / `params` 合成 1 个隐式 model:`id="default"`,`task` 由现有信号推断(`supported_trackers`→`tracker`、`supported_prompts` 含 point/bbox→`interactive_seg`、否则 `detection`),`infra="unknown"` |
| 无 `infra` | model.infra = backend.infra = `"unknown"` |
| 有 `models[]` 但条目缺 `task` | 该条目按 `unknown` task 入目录,UI 标"能力未声明",兼容性校验 fail-open(放行,留到 `/predict` 暴露) |

老 backend(grounded-sam2 / sam3 / echo)**不需要任何改动**即可继续工作 —— 它们落到"隐式单 model"路径。

### 3.5 范例:YOLO 官仓 backend(按任务分条目 + series/size 多轴)

```jsonc
{
  "name": "yolo-ultralytics-backend",
  "version": "0.1.0",
  "model_version": "ultralytics-8.3.x",
  "infra": "pytorch",
  "is_interactive": false,
  "models": [
    {
      "id": "detect", "display_name": "YOLO 目标检测",
      "task": "detection", "model_family": "yolo",
      "supported_prompts": ["none"],
      "supported_geometric_outputs": ["bbox"],
      "supported_variants": [
        { "key": "series", "title": "版本系列", "variants": [
          { "value": "yolov8", "label": "YOLOv8" },
          { "value": "yolo11", "label": "YOLO11", "recommended": true },
          { "value": "yolo12", "label": "YOLO12" } ] },
        { "key": "size", "title": "尺寸 / 精度档", "variants": [
          { "value": "n", "label": "nano",  "vram_gb": 1, "tier": "fast" },
          { "value": "s", "label": "small", "vram_gb": 2, "tier": "balanced", "recommended": true },
          { "value": "m", "label": "medium","vram_gb": 4 },
          { "value": "l", "label": "large", "vram_gb": 6 },
          { "value": "x", "label": "xlarge","vram_gb": 8, "tier": "accurate" } ] }
      ],
      "default_thresholds": { "conf": 0.25, "iou": 0.7 },
      "resource_profile": { "device": "gpu", "batchable": true },
      "params": { "type": "object", "properties": {
        "conf":   { "type": "number", "minimum": 0, "maximum": 1, "default": 0.25, "title": "置信度阈值" },
        "iou":    { "type": "number", "minimum": 0, "maximum": 1, "default": 0.7,  "title": "NMS IoU" },
        "series": { "type": "string", "enum": ["yolov8","yolo11","yolo12"], "default": "yolo11" },
        "size":   { "type": "string", "enum": ["n","s","m","l","x"], "default": "s" } } }
    },
    { "id": "segment",  "task": "segmentation",   "supported_geometric_outputs": ["polygon"],       "model_family": "yolo", "/* variants 同上 */": null },
    { "id": "pose",     "task": "keypoint",       "supported_geometric_outputs": ["keypoint"],      "model_family": "yolo", "/* … */": null },
    { "id": "obb",      "task": "obb",            "supported_geometric_outputs": ["rotated_bbox"],  "model_family": "yolo", "/* … */": null },
    { "id": "classify", "task": "classification", "supported_geometric_outputs": ["none"], "output_attribute_types": ["class"], "model_family": "yolo", "/* … */": null }
  ]
}
```

**关键红利**:det/seg/pose/obb 的输出几何恰好命中现有 4 种 result type(`rectanglelabels` / `polygonlabels` / `keypointlabels` / `rectanglelabels+rotation`),所以 **YOLO backend 的 `/predict` 输出零 adapter**,直接落现有渲染链路。只有 `classify` 的 class 需走 attribute(§4.4)。

### 3.6 范例:ONNX 聚合 backend(一个 backend,多家族多任务,统一 infra)

```jsonc
{
  "name": "onnx-zoo-backend",
  "version": "0.1.0", "model_version": "onnxruntime-1.x",
  "infra": "onnx", "is_interactive": false,
  "models": [
    { "id": "yolov8n-coco", "task": "detection",      "model_family": "yolo",      "supported_geometric_outputs": ["bbox"] },
    { "id": "rtmpose",      "task": "keypoint",        "model_family": "rtmpose",   "supported_geometric_outputs": ["keypoint"] },
    { "id": "ppocr",        "task": "ocr",             "model_family": "paddleocr", "supported_geometric_outputs": ["polygon"], "output_attribute_types": ["text","language"] },
    { "id": "u2net",        "task": "segmentation",    "model_family": "u2net",     "supported_geometric_outputs": ["polygon"] }
  ]
}
```

> 这里 model 都继承 `infra="onnx"`,但 `model_family` / `task` 各异 —— 正是"聚合模型带不同能力"。若某 PaddleOCR 条目用 paddle 运行时,在该条目写 `"infra": "paddle"` 覆盖即可。

### 3.7 OCR / Doc Layout 输出约定(本版首发,挂到协议 v2)

**OCR**(`task: "ocr"`):
- 检测文本区域:几何 = `bbox` / `rotated_bbox` / `polygon`。
- 识别文本:写入 prediction result 的 `attributes.text`(必要时 `attributes.language` / `attributes.orientation`)。
- 采纳后生成普通 annotation + text 写入 attributes;**项目未配置 text attribute 时不静默丢文本**,前端提示"可采纳几何,文本字段不会入库"或要求先配置(§5C、§11)。

**Doc Layout**(`task: "doc_layout"`):
- 输出区域 class:`title` / `paragraph` / `table` / `figure` / `formula` / `list` / `header` / `footer`,落 `class_name`。
- 几何 = `bbox` / `polygon`,可选 OCR text。
- 目标场景:文档图片标注、OCR 校对、表格/版面区域检测。

## 4. 后端设计

### 4.1 capability 派生升级

`extract_capabilities(setup)`(`services/ml_capabilities.py`)从"抽单层快照"升级为"遍历 `models[]` 派生 model 列表":

```jsonc
// health_meta["capabilities"] 目标形态
{
  "infra": "pytorch",                 // backend 默认
  "models": [
    { "id": "detect", "task": "detection", "model_family": "yolo", "infra": "pytorch",
      "supported_prompts": ["none"], "supported_geometric_outputs": ["bbox"],
      "output_attribute_types": [], "supported_variants": [/*…*/],
      "default_thresholds": {/*…*/}, "resource_profile": {/*…*/}, "modality": "image" },
    /* … */
  ],
  // 兼容字段:老消费方仍能读到"扁平并集"(所有 model 的 prompts/geometry 去重合并)
  "supported_prompts": ["none"], "supported_geometric_outputs": ["bbox","polygon","keypoint","rotated_bbox"],
  "modalities": ["image"]
}
```

- 无 `models[]` ⇒ 按 §3.4 合成单 model 后走同一派生路径。
- 保留顶层"扁平并集"字段,让现有 `useMLCapabilities` / 绑定校验在改造完成前零回归(渐进迁移)。

### 4.2 能力存储:health_meta(首版)vs 独立表(Phase 2)

| 方案 | 优点 | 成本 | 适用 |
|---|---|---|---|
| **A. `health_meta["capabilities"]["models"]`(首版推荐)** | 零迁移;复用现有 `check_health → extract_capabilities → health_meta` 链路;改动面最小 | 跨 backend 按 task/infra 聚合查询要 JSONB 展开,不便 | 当前 `MAX_ML_BACKENDS_PER_PROJECT=1`,目录视图按项目/按 backend 看,够用 |
| **B. 独立表 `ml_model_capabilities`(Phase 2)** | per-model 行,可 SQL filter / 跨项目聚合("哪些 backend 有 OCR");每 model 独立 `last_seen_at` | alembic 迁移 + model/CRUD + 派生写两处 + 同步一致性 | backend 配额放开后、或要做"模型市场全局检索"时 |

**推荐**:首版走 A;把 B 列为 Phase 2,**触发条件** = `MAX_ML_BACKENDS_PER_PROJECT > 1` 或需要跨 backend 模型检索。这呼应原计划风险条"不要为每个模型族扩表"。Phase 2 表结构(备查):

```text
ml_model_capabilities
  id PK · backend_id FK · model_id · display_name
  task · model_family · infra · modality
  supported_prompts[] · supported_geometric_outputs[] · output_attribute_types[]
  supported_variants JSONB · default_thresholds JSONB · resource_profile JSONB
  params_schema JSONB · setup_snapshot JSONB · last_seen_at
  UNIQUE(backend_id, model_id)
```

### 4.3 模态派生升级(per-model)

现状 `derive_modalities` 只看 `supported_prompts`(非空⇒image)/`supported_trackers`(非空⇒video)。多模型后改为**先按 model 派生、再 backend 汇总**:

- `task=tracker` 或 `supported_trackers` 非空 ⇒ `video`。
- 几何含 `lidar_box_3d` / `point_mask_3d` ⇒ `lidar`(留位)。
- 否则 ⇒ `image`(含 `supported_prompts=["none"]` 的批量模型)。

backend `modalities` = 各 model modality 去重并集。保持向后兼容(老 backend 信号不变)。

### 4.4 prediction result 映射

- **YOLO det/seg/pose/obb**:输出几何命中现有 result type,**零 adapter**(§3.5)。
- **classification**:无几何,class 写 `attributes.class`(或按项目 schema 落 choices)。
- **OCR / layout**:统一 adapter(沿用原计划),不新增 prediction 表:
  - `ocr_text` → `attributes.text`
  - `layout_type` → `class_name`
  - `orientation` → `attributes.orientation`

### 4.5 API

能力目录(派生自 health_meta,首版):

```text
GET  /projects/{pid}/ml-backends/{bid}/capabilities       # 返回 models[] 目录(含 infra/task/variants)
POST /projects/{pid}/ml-backends/{bid}/capabilities/refresh # 强制重探 /setup 并刷新缓存
```

> 复用现有 `POST …/{bid}/setup`(30s TTL 缓存)的探测链路;`capabilities` 端点是其派生视图。Phase 2 起独立表后再考虑 `GET /ml-backends/capabilities`(全局聚合)。

批量预标入口扩展:

- 新增 `model_id`(指向目录条目;缺省 = backend 隐式单 model,兼容老路径)。
- variant / threshold 经 `context` / `params` 透传(series/size 复用现有 variant 透传机制)。
- `task_type=ocr` / `doc_layout` 作为便捷别名(等价于选中对应 task 的 model)。

### 4.6 `infra` 字段的用途与边界

**做什么**:
1. UI 目录显示 `pytorch / onnx / paddle` badge,用户一眼知运行时。
2. 配合 `resource_profile.device` 表达部署预期(onnx/openvino/tensorrt 常暗示 CPU 友好 / 加速)。
3. 排障 / 复现:同模型 pytorch vs onnx 数值可能微差,infra 标注便于追溯 prediction 来源。
4. (Phase 2)多 backend 放开后,可作调度路由提示(CPU-only 任务优先 onnx/openvino backend)。

**不做什么**:`infra` 是纯元数据 —— 不改 `/predict` 协议、不影响 result schema、不参与项目兼容性的硬校验(仅展示/提示)。

## 5. 前端设计

### A. 能力目录视图(模型市场 / backend 观察页)

- 列表粒度 = **model 条目**(一个 backend 展开多个 model)。
- filter 轴:`task`(能力) / `model_family`(家族) / `infra` / `modality`。
- 每条展示:display_name、task badge、infra badge、输出几何、输出属性、variants(series/size)、batchable、资源要求、`last_seen_at`(stale 标记)。
- 对当前项目 `tool_bindings` 做兼容性 check(§5D)。

### B. 工作台模型选择(多模型选择器)

- 现状:选 backend → prompt/variant。
- 升级:选 backend → **选 model**(按 task 分组)→ 选 variant(series/size)→ prompt。
- **兼容单模型**:backend 只有 1 个 model(grounded-sam2/sam3/echo)时,不渲染 model 选择器,直接展开 variant,行为与今天一致。

### C. OCR / Layout 预标入口

AI Pre-Annotate 新增:`OCR text regions` / `Document layout`。
Dry-run preview:检测到的区域数、文本字段样例、class 映射缺失警告。
Workbench 候选展示:OCR 文本摘要、layout type badge、confidence;采纳时文本写入 attributes。

### D. 兼容性校验(前端 + 绑定时)

- 输出几何 ∈ 项目 `tool_unit`(如 seg model 配到只有 bbox 工具的项目 → 警告)。
- 输出 class ∈ 项目类别。
- `output_attribute_types` 含 `text` 但项目无 text attribute → 警告(OCR 文本落点)。
- 校验主轴是 `task` / 几何;不匹配为**警告/提示**,不硬阻断(fail-open,留到 `/predict` 暴露),与现有绑定校验风格一致。

## 11. 风险

- **schema 膨胀**:不要为每个模型族扩 prediction 表;统一走 result + adapter。能力存储首版走 JSONB,延迟建表(§4.2)。
- **协议分裂**:几何/变体一律复用现有 `supported_geometric_outputs` / `supported_variants`,不新造并行词汇(本次已纠正原计划的 `output_geometry_types`)。
- **向后兼容**:`models[]` / `infra` 缺省路径必须用真实老 backend `/setup` 回放测试,防止"隐式单 model"合成漏掉信号。
- **文本属性落点**:项目 schema 未配置 text 时不能静默丢文本(§5C/§5D)。
- **目录与真实 backend 漂移**:能力快照必须带 `last_seen_at`,UI 标明 stale。
- **模型市场误导**:目录只说明能力,不承诺平台托管权重;`infra` 是声明值,不是平台探测保证。
- **组合爆炸**:YOLO 按 task 分条目(≤ ~6 条)+ series/size 作 variant,避免上百条扁平条目;若未来要"具体权重级"检索,再评估 Phase 2 扁平索引。
