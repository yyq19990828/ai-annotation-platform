## 1. 独立交付结果

本版在 v0.25.0 已稳定的 Docking Workspace 上解锁 canvas group 的受约束换位。用户可从“布局”菜单将画布放到工作区根部的上、下、左、右，调整它与其他 panel 的比例，并执行最大化 / 恢复。画布继续隐藏 header 并锁住原生 DnD，避免 Stage pointer、Dockview drop overlay 和画布快捷键形成新的竞争面。

画布仍是必选单例；禁止关闭、复制、同窗口浮动、浏览器 popout，也禁止与其他 panel 成为可能隐藏画布的标签组。ToolDock、`WorkbenchStageHost` 和 StatusBar 始终作为一个 CanvasPanel 整体移动。

预估量级为 4–6 个工程日。主要成本不在 Dockview API，而在图片、视频、3D 的生命周期、坐标和资源资格验证。

## 2. 前提与实体增量

v0.25.0 必须已交付 `canvas` 稳定 panel ID、`renderer: "always"`、恰好一个 canvas 的 sanitizer、panel registry、当前 context snapshot writer、预设命令以及冷启动 / 运行时恢复的分离。

Entity delta：`+0 / -0`。本版把发生首次布局 mutation 的当前 context 信封从 schemaVersion v1 提升为 v2，但复用 v0.25.0 已预留的后端 grammar 与版本降级 409，不增 API endpoint、数据库迁移、依赖、环境变量或长期 feature flag。版本提升明确标识“canvas 可移动”语义，避免旧标签页误写未来结构。

## 3. 目标与明确不做

### 3.1 目标

- 画布必须能通过菜单命令换到工作区根部四个方向；本版不开放专用 header 拖放。
- 画布可与外围面板调整分屏比例，可最大化并精确恢复前态。
- 同一 `taskId + stageKind` 中，拖动、命令换位、resize、最大化、预设、远端回灌和跨响应式阈值不重挂载 Stage。
- 容器变化只驱动已有 ResizeObserver / fit / renderer resize，不新建缓存、decoder 或图形 context。

### 3.2 明确不做

- 不建第二画布、对比画布、多 Stage 标签或跨任务画布。
- 不允许 canvas 变为浮窗、popout、非活动 tab 或可关闭 panel。
- 不将图片缩放、视频 currentTime、3D camera 或其他业务状态写入布局快照。
- 不修改 3D 四视图单 context 架构，不让三视图离开 CanvasPanel 容器。
- 不迁移 AI / 视频原生浮窗，该范围属于 v0.25.2。

## 4. 画布交互合同

### 4.1 合法换位

四个命令把同一个 canvas leaf 从当前树中取出，再作为根 branch 的首项或末项放回：左右使用水平根，上下使用垂直根。原外围 subtree、group、tab、浮窗和 `parking` 顺序不变，运行时 executor 只移动既有 panel，不调用 `fromJSON`，也不重建 React 内容。

`480×320` 指 Dockview canvas group 外框。工作区无法同时满足 canvas 和其他可见 group 的最小尺寸时，命令保持现状并显示非阻断错误；不自动隐藏外围 panel。窄屏继续进入不持久化的紧凑投影，四方向命令禁用。

### 4.2 菜单等价操作

顶层“布局”菜单固定包含：画布移到左侧、移到右侧、移到上方、移到下方、最大化 / 恢复、重置当前布局。不显示关闭、隐藏、浮动或新窗口动作。

菜单移动和拖放使用同一个 normalization 与保存管线，使纯键盘与辅助技术用户也能完成等价操作。

### 4.3 最大化、预设与回灌

- 最大化是临时空间状态，不删除其他 panel；恢复回到同一棵布局。
- “专注画布”继续使用最大化；其他预设根据当前 canvas 位置重排已有 panel，不重建 Stage。
- 冷启动仅将本版支持的 v1 / v2 snapshot 清洗为恰好一个合法 canvas group，再使用 `reuseExistingPanels` 恢复；v3 / 未知版本走只读标准布局。
- 初始远端权威布局只有在属于 v1 / v2 且清洗通过时，才沿用 v0.25.0 的单次 `fromJSON(..., { reuseExistingPanels: true })` 回灌与 identity 门；初始化结束后的预设、菜单和拖放只使用 move / resize API。

## 5. 生命周期与坐标合同

```text
CanvasPanel header drag / move command
  -> validate edge-only destination
  -> move existing panel/group
  -> same CanvasPanel DOM changes size/position
  -> existing ResizeObserver paths
       image: measure + optional final fit
       video: measure + optional final fit
       3d: renderer resize + scissor rect refresh
  -> save one sanitized snapshot after mutation
```

单实例的可测定义：

- 图片 / 视频：`WorkbenchStageHost` 和具体 Stage 的 mount effect 计数不增，原 DOM marker 仍在。
- 3D：`PointCloudScene` / renderer / graphics context 的 create / dispose 计数不变，四视图仍共享单 context。
- 视频：decoder、bitmap cache、currentTime、播放态和轨迹草稿在移动前后保持。
- 图片：auto-fit 关闭时保持用户缩放 / 平移；开启时只在 resize 稳定后执行最终 fit。
- 3D：camera、选中、gizmo 草稿、三视图和相机面板状态保持；内部浮层边界使用 CanvasPanel client rect。

不在布局层假设可以拦截浏览器原生 ResizeObserver。图片、视频和 3D 各自在现有 observer consumer 内按 animation frame 合并连续通知；容器短暂出现 `0×0` 时保持上一有效尺寸，不把零尺寸传入 Stage fit / renderer。

## 6. 快照与回滚兼容

本版客户端读取 v1 / v2，所有布局写入统一产出 v2。v2 sanitizer 增加：

1. canvas 只能在非 floating / non-popout group 内出现一次。
2. canvas group 不得含其他 tab，不得处于 hidden / inactive 状态。
3. canvas 尺寸低于安全下限且无法在不改变面板可见性的前提下修复时，回退标准 / 紧凑布局，不自动隐藏外围 panel。
4. 读取 v1 时保留其中心布局；第一次菜单移动、拖放、resize、预设、重置或其他布局 mutation 后，以同一棵已清洗树写 v2。画布换位只在操作结束后触发一次防抖 save，不发新类型 API 请求。

回滚到 v0.25.0 时不猜测任意 Dockview 树的“中心”算法：v0.25.0 看到 v2 后以只读“标准标注”临时布局进入工作台，禁用布局 mutation 并提示升级，服务端 v2 原值不变。即使旧标签页在 v2 保存前已加载 v1，其随后 PATCH 也会被 v0.25.0 后端以 `409 layout_schema_downgrade` 拒绝。重新部署 v0.25.1 后可原样恢复 v2 布局；不需要数据清理或破坏性 normalization。

## 7. 精确变更面

本版预计触及 10–14 个生产、测试与文档文件，超过 8 个文件是因为一个共享 CanvasPanel 必须分别通过图片、视频和 3D 真实资源验收。

### 7.1 生产代码

- `layout/workbenchPanelRegistry.tsx`：标记 canvas 允许受约束 dock，继续禁止 tab、float 与 hide。
- `layout/workbenchLayoutExecutor.ts`：增加根边缘换位与最大化 / 恢复命令，复用既有原位 replay。
- `layout/WorkbenchDockWorkspace.tsx`：在顶层布局菜单接入四方向命令及最大化状态。
- `layout/workbenchLayoutSnapshot.ts` 与 `state/useWorkbenchWorkspaceLayout.ts`：客户端读取 v1 / v2、统一写 v2，较新版本只读。

以上相对路径均以 `apps/web/src/pages/Workbench/` 为根。如实施需要修改标注 geometry、video decoder、Three.js renderer owner、API schema 或工具状态，停止扩面并回到计划评审。

### 7.2 测试与文档

- 扩展 `workbenchLayoutExecutor.test.ts`、`WorkbenchDockWorkspace.test.tsx`、`workbenchLayoutSnapshot.test.ts` 与 workspace owner 测试。
- 扩展 `apps/web/e2e/tests/workbench-layout.spec.ts`，并复跑图片、视频和点云 smoke，证明 Stage DOM 与业务状态保持。
- 修改 `docs-site/user-guide/workbench/index.md`、`docs-site/dev/concepts/workbench-shell.md`、`docs/adr/archive/0072-workbench-dockable-layout.md` 和 `CHANGELOG.md`。

## 8. 可独立合并切片

### Slice A · 菜单换位与快照安全

1. 实现画布的四方向菜单移动、最大化 / 恢复和 snapshot normalization。
2. 暂不开放鼠标拖动，但用户已能可预期地调整画布位置。
3. 同切片覆盖三 Stage 的 mount / context / decoder 保持。

独立验收：仅用键盘和菜单能完成四方向换位、最大化、恢复和重置，Stage 生命周期不变。

### Slice B · Header 拖动

本版不实施。只有后续产品明确需要直接拖动画布，并能提供独立 header、根边缘 drop overlay 与三种 Stage 的 pointer 隔离证据时再单独规划；当前菜单能力已经覆盖完整可访问操作。

### 9.2 人工与真实资源矩阵

| Stage | 必测状态                                                                         | 合格标准                                                            |
| ----- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| 图片  | auto-fit 开 / 关、已缩放 / 平移、绘制中、有选中                                  | 关闭 auto-fit 时视口不跳；开启时只在稳定尺寸后 fit；几何坐标不偏移  |
| 视频  | 播放 / 暂停、非零 currentTime、轨迹草稿、缓存命中                                | 帧、播放、decoder / bitmap cache 与草稿不变；最小尺寸下时间线可操作 |
| 3D    | Legacy / WebGPU、orbit / BEV、gizmo 草稿、三视图展开、相机放大、device lost 回退 | renderer / context 不重建；相机和草稿不变；三视图、相机不漂移或穿透 |

所有 Stage 在 1366×768 和 1920×1080 下各执行 20 次四方向换位、20 次 sash resize 和 10 次最大化 / 恢复。记录 mount / dispose、renderer context、decoder 身份和主线程 long task，不增产品遥测。

### 9.3 发布阻断条件

- 任一 Stage mount 计数增加，或 DOM marker 身份变化。
- 3D renderer / context、video decoder / bitmap cache 或图片核心资源因布局操作重建。
- canvas 可被关闭、浮动、popout、复制或藏入非活动 tab。
- tab / menu 焦点时触发工具快捷键。
- 画布出现 `0×0`、低于安全下限且无恢复，或关键工具 / 时间线 / 提交入口不可达。
- 图片标注坐标偏移，视频 currentTime / 播放态丢失，或 3D camera / gizmo / 三视图状态重置。
- 菜单换位一次操作产生多个最终 PATCH。
- v2 保存后旧 v1 标签页仍能覆盖该 context，或 v0.25.0 回滚客户端裁剪并写回 v2 树。

若 Slice B 纳入发布物，还必须阻断：header drag 期间 Stage pointer 仍触发绘制 / 选中、出现非法 center / float / popout drop、拖放与菜单生成不同快照。任一项失败就从发布物移除 header drag，不降低这些门槛。

## 10. 成功指标

1. 用户能在一次菜单命令内将 canvas 放到四个方向中的任一位置；若 header drag 资格通过，拖放结果与菜单完全一致。
2. 连续换位、resize、最大化、预设和刷新后，每个 context 仍只有一个 canvas，且恢复到最后有效位置。
3. 六个 context 的 Stage mount 计数在单任务布局操作前后为 1，3D context 数不增，video decoder 身份不变。
4. 布局换位不产生 annotation / task / prediction mutation，不修改布局之外的账号偏好。

## 11. 最脆弱假设、失败路径与回滚

本版最脆弱的假设是：Dockview 对 `renderer: "always"` panel 执行 group / panel move 时，能保持 CanvasPanel React 实例与 DOM，且 Konva、video 和 Three.js 能安全处理容器被重新放置。

若菜单 / API 换位使任一 Stage 在真实浏览器中重挂载、重建 renderer / decoder 或丢失当前业务状态，本版不发布，回到 v0.25.0 的永久中心 canvas。若只有 header 拖动无法满足事件或 drop 安全门，发布已完整验收的菜单换位并保持 header 不可拖。周边面板 Docking、预设、持久化和 v0.25.2 均不受影响。

已保存的 v2 快照不需要数据清理。回滚 v0.25.0 时只读标准布局保障工作台可用且不覆盖 v2；重新部署 v0.25.1 即恢复原树。若产品要求旧版仍可编辑，则必须另做有明确 schema 的降级转换并重新评审，不能在本版加入猜测式 normalization。
