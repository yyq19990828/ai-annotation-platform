# v0.14.12 · YOLO ML Backend（ultralytics 多任务多系列）

> 规划日期：2026-06-08 · 单线版本。承接 v0.14.9（能力声明协议 v2）/ v0.14.10（模型市场三视图）/ v0.14.11（协议能力目录解耦）。
>
> 本版交付一件事：把 `ultralytics` 官仓接成平台第三个 ML backend，覆盖 **detection / segmentation / pose / obb** 四任务 × **v8 / v9 / v10 / v11 / v12 / v26 / rt-detr** 七系列的预训练权重矩阵。**纯批量推理（`supported_prompts: ["none"]`），不进交互式 workbench。**

## 1. 背景

平台已有两个 ml backend：

- `apps/grounded-sam2-backend`（端口 8001，profile `gpu`）—— GroundingDINO 文本提示框 + SAM 2 mask，交互式 + 批量。
- `apps/sam3-backend`（端口 8002，profile `gpu-sam3`）—— SAM 3.1 高精度交互式。

两者都是「文本 / 点 / 框」提示驱动的开放词汇分割（segmentation-first），形态偏交互式。**缺一块「闭集预训练分类 + 检测 + 关键点 + 朝向框」的批量预标能力**——这正是 YOLO 系所长。

协议层已经为此铺好路：

- §4.1 协议 v2 把能力声明下沉到 model 粒度，明确允许一个 backend 暴露多个 model（一个 backend = N 个 model）。
- §4.1.6 把 **YOLO 官仓** 列为 v2 的 canonical example：按 task 拆条目（det/seg/pose/obb/cls），series × size 两轴 `supported_variants`。
- §4.1.10 已有 `docs-site/dev/examples/mock-v2-backend/` 参考实现，schema 形态已经跑通。

零 adapter 红利：det → `rectanglelabels` / seg → `polygonlabels` / pose → `keypointlabels` / obb → `rectanglelabels + rotation`，全部命中现有 result type。

## 2. 目标

### 2.1 目标

- **G1**：新增 `apps/yolo-backend/`，FastAPI 进程暴露 `/health` `/setup` `/versions` `/predict`，协议 v2 合规。
- **G2**：`/setup` 暴露 4 个 model 条目（`detect` / `segment` / `pose` / `obb`），每个条目 `supported_variants` 走两轴 `series × size`，**series 选项按预训练权重矩阵严格过滤**（前端选不到不存在的组合）。
- **G3**：`/predict` 按 `context.type` 分发到对应 task，结果零 adapter 落现有 result type。
- **G4**：模型按需 lazy load + LRU 池化（参考 `grounded-sam2-backend/model_pool.py`），单 GPU 显存预算可控。
- **G5**：Dockerfile + docker-compose profile `gpu-yolo`，端口 **8003**，与 gsam2 / sam3 三 backend 解耦可独立启停。
- **G6**：轻量重构 —— 抽 `apps/_shared/protocol_v2/`（Pydantic schemas + 受控词表常量），sam3 / gsam2 / yolo 三家共享。**不引入 base class、不引入 SDK 抽象**。

### 2.2 非目标

- **NG1**：**不做** classification 任务（ImageNet-1k 与项目 LabelConfig 几乎对不上，强行映射降低可用性）。
- **NG2**：**不做** YOLO26 的 sem / depth / reid / s3d / objv1 头（协议词表无对应 task，前端无渲染器）。
- **NG3**：**不做** tracker / video 时序（ByteTrack / BoT-SORT 等），与 v0.10.35 sam2_video 路线无关。
- **NG4**：**不做** 训练（`/fit` 端点），只做推理。
- **NG5**：**不做** TensorRT / ONNX / OpenVINO 加速，`infra` 这版固定 `pytorch`。
- **NG6**：**不做** batch 推理优化（`model.predict(list[img])`），单图单次走，性能优化留二期。
- **NG7**：**不做** ML backend base class / SDK 框架。N=3 backend 尚不足以判定共性，参考 [§7 抽象层决策](#7-抽象层决策推迟到-n4-后再评估)。
- **NG8**：**不动** 平台 API / 前端的 result type 渲染逻辑；若 pose / obb viewer 缺失，对应 task 本版**不开放**（见 §6.1 前置验证）。


**关键设计点**：

1. **series 按 task 过滤**：每个 model 条目自己的 `supported_variants[series].variants` 只列该 task 有预训练的 series，不依赖 v9 的 size 子集（`t/s/m/c/e`）在 UI 层再过滤——这个交互复杂度本版不做，**v9 在 seg 任务直接只暴露 `c`/`e` 两 size**（即 v9 单独在 seg 条目内 size 轴改写）。
   - 实现上：`supported_variants` 不是全 model 共享，而是 **每个 model 条目独立 supported_variants**，序列化时按 `MODEL_MATRIX` 生成。
2. **不齐组合不出现在选项里**：v9 + det 出 `t/s/m/c/e`、v9 + seg 出 `c/e`、rtdetr 任意 task 出 `l/x`——这些都在每个 model 条目自带的 variants 里如实声明。
3. **`recommended: true` 标记**：series 推 `yolo11`（成熟稳定）、size 推 `s`（4060/3060 友好），UI 默认选中。
4. **params** 只暴露三个超参，全部 Draft-07 JSON Schema 子集合规。`agnostic_nms` / `classes filter` / `imgsz` 留二期。

### 3.5 `/predict` 行为

**入参**（沿用协议 v2，本仓特有约束）：
```jsonc
{
  "context": {
    "type": "detection",           // or segmentation/keypoint/obb
    "variants": { "series": "yolo11", "size": "s" },
    "params":   { "conf": 0.25, "iou": 0.7, "max_det": 300 }
  },
  "tasks": [{ "id": "t1", "data": { "image": "<url|base64>" } }]
}
```

**流程**（`predictor.py:predict`）：

1. `task = context.type`；`series, size = context.variants`；校验 `(task, series, size) ∈ MODEL_MATRIX`，否则 400 `INVALID_VARIANT`。
2. `model = model_pool.get((task, series, size))`：
   - hit → 直接用。
   - miss → 解析文件名（`model_registry.resolve_weight_filename`，如 `yolo11s-seg.pt`）→ 若 `checkpoints/<filename>` 存在则加载；缺失时 `STRICT_OFFLINE=1` 报 400 `WEIGHT_MISSING`，否则走 ultralytics 默认 GH download（`YOLO(filename)` 自动下到 `checkpoints/`）。
   - pool 满 → LRU evict + `torch.cuda.empty_cache()`。
3. 解码 task 图像（base64 / `httpx.get(presigned_url)`）→ PIL.Image。
4. `results = model.predict(img, conf=, iou=, max_det=, device=DEVICE, verbose=False)`。
5. **结果映射**（task 分支）：
   - **det**：`results[0].boxes` → 每框生成一个 `rectanglelabels` result，`value.x/y/width/height`（归一化百分比），`value.rectanglelabels = [class_name]`，`score = confidence`。
   - **seg**：`results[0].masks.xy` → polygon 点列 → `_shared/mask_utils` 简化（沿用既有 tolerance）→ `polygonlabels`。
   - **pose**：`results[0].keypoints` (17 × 3) → `keypointlabels`，每点 `x/y/keypointlabels=[coco_kp_name]`，附 `visibility`。**前置依赖**：平台 keypoint result type 渲染（见 §6.1）。
   - **obb**：`results[0].obb.xywhr` → `rectanglelabels` + `rotation`（弧度→度）。**前置依赖**：平台 obb viewer。
6. 返回 `PredictResponse{ results: [{ task: t.id, result: [...] }, ...] }`。

**默认类名约定**：
- det / seg / pose 走 COCO-80 类名（ultralytics 内置 `model.names`）。
- obb 走 DOTA-15 类名。
- **不做** label 映射到项目 LabelConfig，平台侧已经在 v0.14.11 capability_registry 时段处理"未匹配"分桶。

### 3.6 模型池

`model_pool.py`（结构对齐 `grounded-sam2-backend/model_pool.py`，简化版）：

- `key = (task: str, series: str, size: str)`
- 容量 env `MODEL_POOL_CAP`（默认 **2**，单 4060 8G 可装 2 个 small/medium）
- `get(key) -> YOLO`：双检锁，miss 时同 key 并发只 build 一次（其它等待 `BUILD_TIMEOUT`，默认 30s）
- LRU evict：`del model; torch.cuda.empty_cache()`；evict 计数走 Prometheus
- idle unload：`YOLO_IDLE_UNLOAD_SECONDS`（默认 600，<=0 关闭），后台 task 周期扫
- **不预热**任何 (task, series, size)，全程 lazy

### 3.7 Dockerfile

```dockerfile
FROM pytorch/pytorch:2.6.0-cuda12.4-cudnn-runtime

ENV DEBIAN_FRONTEND=noninteractive \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /app

RUN apt-get update && apt-get install -y --no-install-recommends \
        curl libgl1 libglib2.0-0 ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# 平台共享包（同 gsam2/sam3 模式，build context = ./apps）
COPY _shared/protocol_v2/ /app/protocol_v2/
RUN pip install --no-build-isolation -e /app/protocol_v2

COPY _shared/mask_utils/ /app/mask_utils/
RUN pip install --no-build-isolation -e /app/mask_utils

# 本仓代码
COPY yolo-backend/pyproject.toml ./
RUN pip install --no-build-isolation -e .

COPY yolo-backend/main.py yolo-backend/predictor.py yolo-backend/schemas.py \
     yolo-backend/model_pool.py yolo-backend/model_registry.py \
     yolo-backend/observability.py ./
COPY yolo-backend/scripts/ ./scripts/
COPY yolo-backend/tests/ ./tests/

RUN mkdir -p /app/checkpoints

EXPOSE 8003

ENTRYPOINT ["/bin/bash", "-c", "exec uvicorn main:app --host 0.0.0.0 --port 8003 --workers 1"]
```

依赖锁在 `pyproject.toml`：`fastapi>=0.110`、`uvicorn[standard]>=0.27`、`pydantic>=2.5`、`ultralytics>=8.4.0,<8.5`、`pillow>=10.0`、`prometheus-client>=0.20`、`structlog>=24.1`、`httpx>=0.27`。

### 3.9 env-only 观测对接

`settings.ml_backend_observe_urls`（CSV / JSON 数组，v0.14.10 引入）允许超管 `GET /admin/ml-integrations/observe` 探测未注册到任何项目的 backend。**追加 `http://yolo-backend:8003` 到默认 CSV**，让模型市场 `tab=catalog` 在零项目注册时也能看到 yolo 的 4 个 model 卡。

## 4. 平台侧改动

**核心原则**：本版只新增一个 backend 进程 + 重构 `_shared/protocol_v2`，**不改 apps/api / apps/web 业务逻辑**。

## 7. 抽象层决策（推迟到 N≥4 后再评估）

**决策**：v0.14.12 **不** 引入 `LabelStudioMLBase` 式的 ML backend 基类 / SDK 框架，**仅** 抽 `apps/_shared/protocol_v2/`（Pydantic schemas + vocab 常量）。

**理由**（写入 `docs/adr/0038-defer-ml-backend-base-class.md`）：

1. **样本量不足**：sam3 / gsam2 / yolo = 3 个 backend，且形态差异巨大：
   - sam3：交互式 + embedding cache + 单模型族 + 静态变体
   - gsam2：交互式 + model_pool + video_pool + GroundingDINO 编译扩展
   - yolo：纯批量 + model_pool + 多任务多 series + 闭集类名
   - 共性约 30%（FastAPI 端点形态 + Pydantic schema）；70% 是各自 predictor 生命周期。
2. **`label-studio-ml-backend` 的教训**：他们的 `LabelStudioMLBase` 在维护 10+ 示例 backend 后才稳定，且至今仍有"绕不开框架做特殊事"的痛点（参考 docs/research/01-label-studio.md）。我们在 N=3 时拍 base class，等于在样本不足时锁死接口，反复打补丁的代价比手写更高。
3. **可逆性**：monorepo 同仓，所有 backend 代码相互可见。等 N=4（如 OCR / PaddleOCR backend、或 ONNX 聚合 backend）时回顾，那时能清晰判断"哪些是共性、哪些是偶然相似"，再决定要不要抽基类。
4. **CLAUDE.md §2 显式反对**为未来灵活性预先抽象。

**未来触发条件**（满足任一即重新评估）：

- 接入第 4 个 backend，发现 sam3/gsam2/yolo 之外仍有 ≥50% 代码可机械抽取。
- 协议 v3 落地，需要在 3+ backend 同步改 schema 形态。
- 外部开发者反馈"接入门槛太高，希望有 SDK"——这是 v0.15.2 `ML Backend Starter` 计划要解决的问题（参考 `2026-06-07-v0.15.2-sdk-cli-and-ml-backend-starter.md`），但 starter 是模板代码不是基类。
