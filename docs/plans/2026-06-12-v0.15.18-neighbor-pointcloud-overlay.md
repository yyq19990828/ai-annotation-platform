# v0.15.18 · 邻帧点云叠加(多帧点云 ego 融合渲染)

> 规划日期 2026-06-12 · 范围:把 v0.15.1 的「邻帧**框**叠加」延伸到「邻帧**点云**叠加」——用 ego 轨迹把前后 K 帧的点云变换到当前帧 ego 系一起渲染。解决车端采集「背景相对车也在动」时如何有意义地叠点云的问题。本版只做**可视化叠加**(辅助标注观察),不改标注落点、不做点云融合标注。框叠加产品化见 [`2026-06-12-v0.15.17-crossframe-box-overlay-productization.md`](2026-06-12-v0.15.17-crossframe-box-overlay-productization.md)。
>
> **前置依赖(硬)**:v0.15.0(`scene_frame_poses` + `GET /scenes/{id}/trajectory`)、v0.15.1(`egoAlign.ts` 的 ego 变换、`useSceneTrajectory`)。**无 ego pose 的 scene 本能力自动禁用**(叠加无意义)。

## 1. 背景与核心疑惑

### 1.1 用户的疑惑(本版要正面回答)

> 「车端采集的数据怎么叠点云?背景相对于车也是运动的。」

**关键洞察**:当前帧点云是「**当前帧 ego 系**」下的点。直接把邻帧点云原样叠到当前帧 → 因为车在动,邻帧的静止背景(墙/路/楼)会沿 ego 运动方向**整体平移数米**,叠出来是一团错位的乱影,毫无价值。这正是用户担心的。

**解法**:用 ego 轨迹做**运动补偿**——和 v0.15.1 叠框用的是**同一个变换**(`egoAlign.ts:38` 的 `rel = inv(T_当前) · T_邻帧`),只不过作用对象从「框的中心/朝向」换成「邻帧点云的每一个点」:

```
p_当前系 = rel · p_邻帧系 = inv(T_当前) · T_邻帧 · p_邻帧系
```

补偿后会出现两种本质不同的叠加效果(这就是叠点云的价值与噪声所在):

| 物体类型 | 补偿后表现 | 价值/噪声 |
|---|---|---|
| **静止背景**(路面 / 墙 / 建筑 / 杆) | 邻帧点与当前帧点**重合 → 加密** | ✅ 价值:远处/稀疏处点变密,小目标和远处边界更易标准 |
| **动态目标**(其他车 / 行人) | 补偿只抵消「车的运动」,抵消不了「目标自身的运动」→ 留下**沿目标运动方向的拖影/重影** | ⚠️ 双刃:可看出目标轨迹趋势,但也是遮挡当前帧的噪声 |

所以答案是:**车端运动场景必须、且只能靠 ego 运动补偿来叠点云**;补偿后静止背景自动对齐加密,动态目标留有意义的拖影。无 ego pose 就别叠(会乱)。

### 1.2 现状(已读源码)

- 点云**逐帧单独加载**,无任何多帧融合(`ThreeDWorkbench.tsx:841-862` 只加载当前帧 `manifest.point_cloud_url`;`PointCloudScene.ts` 单 Points 对象)。
- v0.15.1 的 overlay **只叠框**(ReferenceBox),不碰点云。
- ego 变换纯函数已存在(`egoAlign.ts:17-46`),可直接复用到点变换。
- `useSceneTrajectory` 已能按 frame_index 取各帧 pose。

### 1.3 本版做什么 / 不做什么

**做**:
- 设置开关 `workbench.pointcloud.neighborPointOverlay`(默认 off)。
- 开启后,取当前 K 邻帧(复用 v0.15.17 / v0.14.x 的 neighbors 反查)的点云,经 ego 补偿变换到当前帧 ego 系,作为**独立的弱化 Points 对象**渲染(单色 + 低透明,与当前帧点区分)。
- 邻帧点**强制下采样**(性能,见 §3.3)。
- 无 ego pose 时禁用 + 提示(复用 v0.15.17 的降级 badge 语义)。

**不做**(明确边界):
- **点云融合标注**:不允许在「合并后的点云」上直接画框/点掩膜并落到各帧。叠加纯为观察,标注仍只针对当前帧。点掩膜(`point_mask_3d`)跨帧无意义(v0.15.1 已定论),本版同样不碰。
- **动静分离 / 动态点剔除**:ego 补偿不区分动静,动态目标必然拖影。自动剔除动态点(如用 box 轨迹挖洞)是另一套重活,留后。
- **Kalman / 非线性补偿**:点变换用与叠框一致的刚体 ego 变换,不引入运动模型。
- **多 lidar 合并**:延续 roadmap §4.1,本版一帧仍一个 primary_lidar。

### 1.4 成功判据

1. **默认零回归**:`neighborPointOverlay` 默认 off,不开的用户渲染与 v0.15.17 一致。
2. **静止背景加密**:scene-0061 开 K=3 邻帧点叠加 → 远处路面/墙面点肉眼变密、与当前帧点重合(不是错位乱影)。证明 ego 补偿生效。
3. **动态拖影**:同场景里一辆行驶中的车 → 邻帧点在其运动方向留可辨认拖影(弱化色),不与当前帧当前位置混淆。
4. **区分度**:邻帧点用单色 + 低透明,与当前帧点(高度/相机上色)一眼可分;关开关即时消失。
5. **降级**:无 ego pose 的 scene,开关禁用(灰置)+ badge「无 ego 轨迹,无法叠加点云」;不出现错位乱影。
6. **性能**:K=3 下交互帧率不显著掉(邻帧点下采样后总增量点数受控,见 §3.3 上限);加载有 loading 态,不阻塞当前帧。
7. `uv run pytest -q` / `pnpm test` / `pnpm lint` 全绿。

## 3. 各模块设计要点

### 3.1 点变换核心(`egoAlign.ts` 扩展,复用 v0.15.1 的 rel)

- 已有 `alignPsrToFrame` 给框算 `rel = inv(T_当前)·T_邻帧`。新增 `transformPointsToFrame(points: Float32Array, fromPose, toPose): Float32Array`:对每个点 `applyMatrix4(rel)`。
- 同一个 `rel` 矩阵复用到整帧所有点(只算一次矩阵,循环里只做矩阵×向量),性能可控。
- 任一帧缺 pose → 该邻帧点云**跳过**(不叠),与叠框降级一致;不退化为「原样叠加」(原样叠点云就是乱影,宁可不叠)。

### 3.2 加载与编排(`useNeighborPointClouds` + ThreeDWorkbench)

- 复用 v0.15.17 / 既有 neighbors 反查拿到 ±K 邻帧 task → 各自的 `point_cloud_url`。
- **异步、不阻塞当前帧**:当前帧点云照常先渲染;邻帧点云后台加载 + 变换 + 下采样,完成后增量加进场景。loading 态指示。
- 切帧/关开关时清理邻帧 Points,避免内存堆积(点云对象大,务必 dispose geometry)。

### 3.3 性能(核心约束)

点数是当前帧的 (2K+1) 倍,必须压:

- **强制下采样邻帧点**:邻帧点云在加载后下采样到每帧软上限(如 ≤ 50k 点,体素或随机抽样)。当前帧点云**不动**(标注精度优先),只压邻帧。
- **K 上限**:点云叠加可单独限制最大 K(如 ≤ 3),比框叠加(K≤7)更保守——点云比框重得多。
- **下采样在 worker 里做**:复用项目既有 worker 化路径(roadmap v0.14.6 提到 worker 化),不卡主线程。
- **设置项** `neighborPointDownsample`(比例或目标点数),默认偏激进;高配用户可放宽。
- **不静默截断**:实际下采样比例/被丢点数在 UI 透出(呼应平台「no silent caps」原则)。

### 3.4 渲染区分(弱化样式)

- 邻帧点:**单色**(如灰/冷色)+ **低透明度**(alpha < 当前帧),小点。与当前帧(高度色带 / 相机上色)形成强对比,避免误把邻帧点当当前帧点去框。
- 颜色用 `tokens.css` 既有语义色或点云专用弱化色;若需新色,先在 tokens 补 light+dark 再用(CLAUDE.md §6)。
- 可选:前帧/后帧用两种弱化色微分(过去 vs 未来),实施时按手感定,非必须。

### 3.5 门控(与 v0.15.17 一致)

- 仅 `manifest.scene_id != null` 且该 scene 有 ego pose 时,开关可用;否则灰置 + badge。
- 与框叠加(v0.15.17)共用「无 ego 轨迹」的降级提示语义,文案区分(框:未对齐;点云:无法叠加)。

## 5. 已知风险 / 未尽事项

- **动态目标拖影是「特性」也是「噪声」**:文档要讲清——叠点云利于看静止结构/远处稀疏,标动态目标时可能想关掉。不试图自动剔除动态点(留后)。
- **内存**:多帧点云占用大,务必 dispose;K 上限 + 下采样是硬约束,不可省。
- **下采样损失**:邻帧点下采样后「加密」效果打折;比例需在真实数据上调到「肉眼明显加密又不卡」的平衡点。
- **无 pose scene 的体验**:开关灰置而非报错;用户能理解「这份数据没有轨迹所以叠不了」。
- **与相机上色/深度提示的叠加**:邻帧点是否参与相机上色?默认**不**(邻帧点只用弱化单色,省一次性上色开销,也强化区分)。

## 6. 验证策略

- **纯函数单测**:`transformPointsToFrame` —— 造一段平移+小转向的两帧 pose,断言静止世界点经「邻帧系→当前系」变换后,与当前帧同一世界点坐标一致(守恒);缺 pose 时返回空/跳过。
- **真实数据**:scene-0061 回填 pose 后,K=3 叠加:① 远处路面/墙点肉眼加密且不错位(静止补偿正确);② 行驶车辆留拖影(动态补偿不抵消目标自身运动);③ 关开关即时还原。
- **性能**:开 K=3 + 下采样,交互(旋转/平移)帧率与关时对比无显著恶化;DevTools 内存不持续增长(切帧后邻帧几何被释放)。
- **降级**:无 pose 的 SUSTech scene,开关灰置 + badge,绝不出现错位乱影。
- **回归红线**:默认 off 时渲染管线与 v0.15.17 一致;当前帧点云加载/下采样阈值不被邻帧逻辑污染。
