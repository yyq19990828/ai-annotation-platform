# v0.10.57 · 按来源清理预测 + 导入 overwrite 默认开 + 多文件 purge 修正

- 日期：2026-05-24

- 前置：[v0.10.55 来源可见](2026-05-24-v0.10.55-prediction-source-visibility.md)(先做;可见+筛选降低 destructive 清理的日常必要性)

## 1. 背景与决策依据

ML 预标(`source='ml_backend'`)与外部导入(`source='external_import'`)在同 task 并存、互不删。当前只有"导入时 overwrite 清之前的导入"(只清 external_import),缺：
- 主动清 ML 预标的入口;
- 重导幂等(默认 overwrite 关 → 忘勾就堆叠)。

**安全前提(已验证)**:`annotation.parent_prediction_id` **无外键约束**([annotation.py:45](../../apps/api/app/db/models/annotation.py#L45) 纯 UUID 列)。→ purge 预测**不会级联破坏已接受的人工标注**,只清未采纳候选;唯一副作用是悬空溯源指针(无害)。故"粗粒度暴力清理"在当前阶段安全、可取,不必上合并/去重引擎(YAGNI)。

**设计原则**:
- ML 预标贵(重跑 batch_predict 耗算力/token)、导入文件便宜(重导免费)→ 清 ML 必须**显式 + 默认关 + 警告 + 计数确认**,绝不并入默认。
- purge 维持 **per-task 作用域**(只动指定 task,不 project-wide 误伤,除非显式选项目级)。

## 2. 目标 / 非目标

**目标**
- A：独立「清理预测」动作 —— 按 `source`(ml_backend / external_import / all)+ scope(task / project)清理,显式确认 + 审计。
- B：导入端 `overwrite_existing` 默认翻为 **开**(语义仍只清 external_import,**不**碰 ML),使重导幂等。
- C：多文件导入对**同一 task 只 purge 一次**(整批共享 purge 作用域),修掉 v0.10.53 残留的欠 purge / 堆叠。

**非目标**
- 合并/去重/冲突消解引擎。
- 清理触发模型重跑等联动。

## 3. 设计

### 3.A 独立「清理预测」动作
- 端点:`POST /projects/{project_id}/predictions/purge`(destructive,`require_project_owner`)。
  - 入参:`source_scope: ml_backend | external_import | all`;`task_ids: list[uuid] | None`(None = 项目级全清)。
  - 复用/泛化 [`_purge_existing_external_imports`](../../apps/api/app/services/predictions_import.py#L226) → `_purge_predictions(db, *, project_id, task_ids, source_scope)`(先删 PredictionMeta 再删 Prediction,沿用现有顺序)。
  - 返回清理计数(按 source 分)。
- 审计:记一条 destructive 审计(参照 `PREDICTIONS_IMPORT` 既有动作,新增 `PREDICTIONS_PURGE`)。
- 前端:`source_scope=ml_backend|all` 时**二次确认 + 显示将删除条数 + 警告"需重跑模型恢复"**。入口建议挂项目设置(danger 区)或 Dashboard ⋮(与导入/导出同处),task 级可后续在工作台补。

### 3.B 导入 overwrite 默认开
- [predictions.py:268](../../apps/api/app/api/v1/predictions.py#L268)：`overwrite_existing: bool = Form(True)`(默认翻开);wizard 复选框默认勾上。
- 语义不变:**只清 external_import,绝不碰 ml_backend**(ML 清理是 3.A 的职责)。
- 向后兼容提示:API 默认值变更需在 CHANGELOG 显著标注;显式传 false 仍可关。

### 3.C 多文件 purge 修正(取代临时补丁)
v0.10.53 的临时补丁是"仅首文件带真实 overwrite"——默认开后会导致后续文件的同 task 旧导入不被清 → 重导堆叠。**正解:整批共享 purge 作用域**:
- 后端导入端点改接 `files: list[UploadFile]`,**一次调用**内循环各文件,共用一个 `purged_tasks: set`(跨文件去重)→ 同一 task 整批只 purge 一次,且每个出现过的 task 都被正确 purge。
- 需顺改:`import_aap_json`/`import_coco`(及未来 `import_yolo`)支持传入共享 `purged_tasks`;async_job payload;前端改为一次上传多文件、合并响应(可移除 v0.10.53 的客户端逐文件循环 + 首文件补丁)。
- **验证**:多文件含同一 task + overwrite → 整批只 purge 一次、各文件预测全部保留、无堆叠;disjoint task 各自被正确 purge。

## 6. 风险

| 风险 | 缓解 |
|---|---|
| 误清 ML 预标(贵) | 显式 source_scope + 默认 external_import + 二次确认 + 计数 + 审计 |
| overwrite 默认开属行为变更,旧 API 调用方受影响 | CHANGELOG/文档显著标注;显式 false 可关;端点本就 owner 权限 |
| 多文件改单次上传是 API 契约变更 | 与 v0.10.53 客户端循环二选一,实现时一次切换 + 补测;保留单文件兼容 |
| purge 留悬空 parent_prediction_id | 已评估无害(无 FK);如需洁净可选 null 化,本版不做 |
