# v0.11.21 · ML Backend 告警（Alertmanager）

> Epic 切片 3/3 · 见 [observability epic](2026-05-27-v0.11.19-21-ml-backend-observability-epic.md)
> 依赖：[v0.11.20](2026-05-27-v0.11.20-grafana-ml-backend-dashboard.md)（指标与面板已就绪） · 用户可见：是（告警邮件）

## 目标

补上 PerfHud 完全没有的能力：backend 离线 / 显存打满 / 推理延迟劣化时**主动告警**。引入 Alertmanager，通知渠道复用平台现有 SMTP，不新增依赖。

## 任务

### A. compose 新增 alertmanager service

文件：`docker-compose.yml`（`monitoring` profile，与 prometheus/grafana 同组）。

```yaml
  alertmanager:
    image: prom/alertmanager:v0.27.0
    profiles: ["monitoring"]
    ports:
      - "9093:9093"
    volumes:
      - ./infra/alertmanager/alertmanager.yml:/etc/alertmanager/alertmanager.yml:ro
      - alertmanager_data:/alertmanager
    command:
      - "--config.file=/etc/alertmanager/alertmanager.yml"
    extra_hosts:
      - "host.docker.internal:host-gateway"   # dev 走 host 上的 mailpit 时需要
```

末尾 `volumes:` 段加 `alertmanager_data:`。

### B. prometheus.yml 接入 alertmanager + 规则

文件：`infra/prometheus/prometheus.yml`，加两段；并把 `alerts.yml` 挂进 prometheus 容器。

```yaml
alerting:
  alertmanagers:
    - static_configs:
        - targets: ["alertmanager:9093"]
rule_files:
  - "/etc/prometheus/alerts.yml"
```

`docker-compose.yml` 的 prometheus `volumes:` 增挂：
```yaml
      - ./infra/prometheus/alerts.yml:/etc/prometheus/alerts.yml:ro
```

### C. 告警规则

文件：`infra/prometheus/alerts.yml`（新建）。

```yaml
groups:
  - name: ml-backends
    rules:
      - alert: MLBackendDown
        expr: up{job="ml-backends"} == 0
        for: 5m
        labels: { severity: critical }
        annotations:
          summary: "ML backend {{ $labels.service }} 离线 ≥5m"
      - alert: GPUMemoryHigh
        expr: gpu_memory_used_mb / gpu_memory_total_mb > 0.9
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.service }} 显存占用 >90% 持续 10m"
      - alert: InferenceLatencyHigh
        expr: histogram_quantile(0.95, sum by(le,service)(rate(inference_latency_seconds_bucket[5m]))) > 10
        for: 10m
        labels: { severity: warning }
        annotations:
          summary: "{{ $labels.service }} 推理 P95 >10s 持续 10m"
```

> **误报防护**（epic 已记）：`MLBackendDown` 只对 `job="ml-backends"` 的 target 生效，而该 job 由 http_sd 从 `state != disconnected` 的 backend 生成——主动 disconnect 的 backend 不在 target 列表里，不会误报。`for: 5m/10m` 再挡瞬时抖动。

### D. alertmanager 配置（SMTP 复用平台邮件）

文件：`infra/alertmanager/alertmanager.yml`（新建）。

```yaml
global:
  smtp_smarthost: "${SMTP_HOST}:${SMTP_PORT}"     # dev: host.docker.internal:1025 (mailpit)
  smtp_from: "${SMTP_FROM}"
  smtp_require_tls: false                          # dev mailpit 无 TLS; 生产按真实 SMTP 调
route:
  receiver: ops-email
  group_by: ["alertname", "service"]
  group_wait: 30s
  repeat_interval: 4h
receivers:
  - name: ops-email
    email_configs:
      - to: "ops@your-org.com"
```

- alertmanager **不读 `.env`**，`${VAR}` 需在 alertmanager 自身的 env 注入（compose `environment:` 透传 `SMTP_*`），或用启动期 envsubst。动手时确认 alertmanager 版本对 config 内 `${}` 展开的支持，必要时改 compose `environment:` + entrypoint envsubst。
- 收件人 `to` 建议做成 env（如 `ALERT_EMAIL_TO`）而非写死。

## 验证

1. `docker compose --profile monitoring --profile gpu up -d`（+ 注册 backend + 起 mailpit）。
2. `docker stop` 一个 backend 容器 → 等 5m → Prometheus `/alerts` 显示 `MLBackendDown` `firing`。
3. Alertmanager `http://localhost:9093` 看到该 alert 已 route 到 `ops-email`。
4. mailpit `http://localhost:8025` 收到告警邮件。
5. 重启 backend → alert 转 `resolved`，收到恢复邮件。

## 风险 / 决策点

- **通知渠道**：当前定 SMTP 邮件。若团队用钉钉/飞书/Slack，改 alertmanager `receivers` 为 webhook（飞书/钉钉自定义机器人）或 `slack_configs`——本切片范围相应替换 D 节，其余不变。
- **alertmanager 配置变量展开**：`${SMTP_*}` 在 alertmanager.yml 内能否展开取决于版本/启动方式，是本切片最易卡的点（见 D）。
- **生产 SMTP**：dev 走 mailpit 无 TLS；生产真实 SMTP 多需 `smtp_require_tls: true` + `smtp_auth_*`，文档要给生产示例。
