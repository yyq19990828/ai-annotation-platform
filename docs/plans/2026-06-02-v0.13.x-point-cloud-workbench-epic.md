## 背景

平台当前只支持 2D(图像/视频)标注。自动驾驶 / 机器人 / AR 场景需要 **LiDAR 点云 + 相机图像联合标注**:在 3D 里画框,经相机标定投影到各路图像,2D-3D 共享同一物体身份。

调研结论(详见 research §14):
- **骨架已预留**:`DatasetDataType.POINT_CLOUD`、`ToolUnitId.lidar_box_3d`(留位)、`ProjectTypeKey.lidar`、Geometry discriminated union、`tool_bindings` —— 后端改动以**新增**为主,几乎无破坏性迁移。
- **三工具谱系**:CVAT(只关联不投影,反面)→ SUSTechPOINTS(轻量但完整投影,算法可移植)→ xtreme1(工程化最完整,数据模型可借鉴)。
- **六个缺口** G1~G6(见 §14.8.2),核心是 G1(任务-数据项 1:N 关联)与 G2/G5(标定存储 + 投影)。

## 数据流(目标形态)

```
导入(一个 scene):
  lidar/<frame>.pcd  +  camera/<cam>/<frame>.jpg  +  calib/camera/<cam>.json
    → 每帧建一个 Task
    → TaskDatasetItemLink: {role:primary_lidar} + {role:camera_front} + ...
    → SensorCalibration 写入各相机 DatasetItem.metadata_

标注:
  3D 工作台画 Box3DGeometry(center/size/rotation)
    → 用 calib 实时投影到各相机视图(8 角点 → 2D)
    → 同物体 3D 框 + 各 2D 框共享 group_id
```

## 跨切片约束

- **向后兼容**:所有改动是新增(几何 union 成员、中间表、metadata key、工具单位),**不动现有 2D 图像/视频流程**;`task.dataset_item_id` 1:1 路径保留。
- **双栈隔离**:3D 前端是独立模块(目录 / package 级隔离),不污染现有 Konva 工作台;两者通过工作台壳层路由按 `data_type` 分流。
- **标定降级**:无 calib 的 scene 退化为「3D-only 标注」(画框可用,投影联动不可用),不阻断。
- **文档同步**:新表 / 协议 → `docs-site/dev/`;新几何类型 → `docs-site/dev/reference/`;新 API → OpenAPI 自动;架构决策(多文件关联模型、标定存储约定、双画布架构)→ 各补一条 ADR。
- **CHANGELOG**:各子版本一段 `## [0.13.x] - 2026-xx-xx`(feature,记 CHANGELOG)。

## 风险

- **前端 3D 是工作量大头**(§14.8.4):v0.13.2~v0.13.4 占整个 epic 绝大部分,需独立排期。
- **大点云性能**:百万点级需 LOD / 抽稀 / 分块加载,v0.13.2 起就要把渲染规模化纳入设计,别等卡了再补。
- **标定数据质量**:外参不准 → 投影框偏移,需提供标定可视化校验(后续版本)。
- **中间表与 1:1 共存**:查询 / 导出路径要同时处理「单 item(2D)」与「多 item(3D)」两种 task,service 层需清晰分流。

## 验证策略

- **现成测试夹具**:`third-party/SUSTechPOINTS/data/example` 内含真实 scene(`lidar/` + `camera/<cam>/` + `calib/camera/*.json` + `label/`),可直接作端到端导入 / 投影 / 标注的测试数据。
- **投影正确性对拍**:同一 scene,本平台投影结果 vs SUSTechPOINTS 投影结果,8 角点像素坐标应一致(同为 `extrinsic·pt → intrinsic → 透视除法`)。
- 各切片自带 `uv run pytest`(后端)/ 前端单测 / e2e;迁移 `alembic upgrade/downgrade` 往返;OpenAPI snapshot 由 pre-commit 钩子生成(勿手动 dump)。
