# v0.20.3 · ML Backend 共享层抽取（五 backend 共性收敛）

状态：草案（draft）。**纯方案文档，不含落地代码**——记录五个 ML backend 并存后的重复面盘点、
风险分层与抽取边界判断，供后续版本择机动手。排在 v0.19.2 衍生序列尾部
（v0.20.1 OCR 属性语义角色 → v0.20.2 writeKeys 一键填充 → **v0.20.3 本方案** → v0.21.0 全局编排选择器），
落地为独立 patch 版本 v0.20.3。

> 触发：v0.20.0 上线 rapidocr-backend 后(本方案排在其后续衍生序列尾部 v0.20.3)，平台在维护的 ML backend 增至五个
> （yolo / sam3 / grounded-sam2 / onnxtools / rapidocr）。是否继续推进「抽共性做模板 / 共享函数」？

## 0. 一句话结论

**抽「纯函数」，别抽「脚手架」。** 把无状态叶子函数收进现有共享包（回报最高、争议最小）；
有状态脚手架（pool / observability / app 骨架）已各自漂移，更适合「被复制的 starter 模板」而非共享 import。

## 1. 现状：已经共享了什么

| 共享包 | 内容 | 谁在用 |
|---|---|---|
| `aap_protocol_v2`（`apps/_shared/protocol_v2`） | 协议 schemas（`PredictionResult` / `BatchPredictResponse` / `WarmupResponse` / `PoolStatus` …）、错误类（`VariantNotSupportedError` / `ModelUnavailableError`）、受控词表（`TASK_VALUES` / `GEOMETRY_VALUES` …）、`mask_codec`、variant normalize（`normalize_context_model_variants`） | **五个 backend 全部** |
| `mask_utils`（`apps/_shared/mask_utils`） | mask → polygon 简化等几何工具 | sam3 / gsam2 等掩码类 |

**关键前提 —— 分发通道现成**：每个 backend 的 Dockerfile 都是
`COPY _shared/protocol_v2/ /app/protocol_v2 → pip install -e /app/protocol_v2`。
**往共享包加东西，五个 backend 零接线自动获得。** 抽取的边际成本极低，判断只剩「该不该抽」。

## 2. 重复面盘点（基于实测相似度，非猜测）

| 重复面 | 复制份数 | 实测相似度 | 抽取风险 | 档位 |
|---|---|---|---|---|
| **图片下载**（`http(s)` presigned URL / `data:` base64 / 本地路径 → PIL.Image，httpx） | 5（yolo `_load_image`、sam3/gsam2 `_fetch_image`、onnxtools/rapidocr 内联） | 同契约同实现 | 极低 | **一档 ✅** |
| **`_free_gpu_memory`**（`gc.collect` + `torch.cuda.empty_cache` + `ipc_collect`） | 3 | sam3/gsam2 **完全相同**，yolo 是子集 | 极低 | **一档 ✅** |
| **`/versions` 载荷**（`{versions:[MODEL_VERSION], backend_version, …}`） | 5 | 近乎一致 | 极低 | **一档 ✅** |
| **`gpu_info` 快照**（torch 读显存 used/total） / **`_normalize_predict_context`** | 3 | 薄包装，已半共享（normalize 本就调共享函数） | 低 | **一档候选** |
| **`model_pool.py`**（多键 LRU + `build_timeout` + `free_gpu_memory` 回调） | yolo + gsam2 各 1 | **419 行差异**（已大幅漂移；gsam2 另有 `video_pool`） | 高 | **二档 ⚠️** |
| **`observability.py`**（prometheus 指标 + gpu_info） | 3 | yolo↔sam3 差 107 行、yolo↔gsam2 差 131 行（已漂移） | 高 | **二档 ⚠️** |
| **FastAPI app 骨架**（`lifespan` / `/health` / `/setup` / `_idle_watcher` 空闲卸载循环） | 5 / 4 | 结构像、细节各异 | 高 | **三档 ⚠️** |

## 3. 分层判断

### 一档 · 无状态叶子函数 —— 建议抽（共享 import）

纯函数、同契约、零 per-backend 状态。收进共享包后每个 backend 只是「删本地函数 + 换 import」。

- `fetch_image(file_path, *, timeout=10.0) -> PIL.Image`：统一三种来源（presigned URL / `data:` base64 / 本地绝对路径）的下载与解码。**一次消灭 5 份复制**，回报最高。
- `free_gpu_memory()`：以 sam3/gsam2 的完整版为准（`gc.collect` + `empty_cache` + `ipc_collect` 容错），torch 不可用时 no-op。
- `versions_payload(model_version, backend_version, **extra) -> dict`：统一 `/versions` 载荷形状，`extra` 收 backend 特有字段（如 yolo 的 `ultralytics` 版本）。
- `gpu_info_snapshot() -> dict`（候选）：torch 读显存 used/total/free 的统一快照；observability 与 `/health` 都消费它。

**落点选择**：放进 `aap_protocol_v2`，还是新建一个 `aap_backend_runtime` 子包？
- 倾向**新建 `aap_backend_runtime`**：`aap_protocol_v2` 是「协议契约」语义（纯 schema/常量，无运行时依赖 torch/httpx/PIL）；把 torch/httpx/PIL 这类**运行时依赖**塞进协议包会污染它的依赖面（协议包本应能被纯客户端轻量引入）。
- 但分发通道要复制一遍（再加一条 `COPY _shared/backend_runtime + pip install -e`）。若嫌麻烦，折中是放进 `aap_protocol_v2` 的可选 extra（`aap_protocol_v2[runtime]`）。**此决策留到动手时定。**

### 二档 · 有状态脚手架 —— 暂缓 / 不抽成共享 import

**核心论据：`model_pool.py`（419 行差异）和 `observability.py`（107–131 行差异）已经各自漂移。
这个漂移本身就是证据 —— 它们不是「忘了抽」，而是每个 backend 真有不同需要**：
- gsam2 多一套 `video_pool` / `video_predictor`（图像池之外的视频追踪池）；
- sam3 是**单 predictor** 的 load/unload，不是多键 LRU；
- onnxtools / rapidocr 是**内联小 OrderedDict 池**，量级不配独立 `model_pool.py`。

强行抽成一个共享 `ModelPool`，要么塞满注入回调变成漏抽象，要么逼五个 backend 收敛到它们并不想要的形状。
**若未来真做，只该把最接近的 yolo + gsam2 两份先调和，且作为独立小重构验证收益后再外推；onnxtools/rapidocr 内联池不动。**

### 三档 · app 骨架 / 模板 —— 用「被复制的 starter」，不用共享 import

`lifespan` / `/health` / `/setup` / `_idle_watcher` 这类天生要被每个 backend 改的脚手架，
适合 **cookiecutter 风格的复制模板**，而非 `create_app()` 共享工厂。这块**需求已被文档覆盖**：
- echo 示例（`docs-site/dev/examples/echo-ml-backend/`）= 最小 starter；
- rapidocr-backend = 真实推理 + 原子/composite 参考实现（`starter.md` 已指向）。

结论：三档**不新增代码资产**，至多在 `starter.md` 把「复制哪个目录起步」说得更明确。

## 4. 建议落地顺序（动手时）

1. 新建 `apps/_shared/backend_runtime`（或定 `aap_protocol_v2[runtime]` extra），实现一档四个函数 + 单元测试。
2. 五个 backend 逐个替换：删本地 `_fetch_image`/`_load_image`/`_free_gpu_memory`/`/versions` 实现，换 import；每替换一个跑该 backend 的 contract test。
3. 各 backend Dockerfile 补 `COPY` + `pip install -e`（若新建子包）。
4. 二档、三档**本次不动**；二档（yolo+gsam2 pool 调和）留独立 plan。

## 5. 明确不做（避免范围蔓延）

- ❌ 一个「大一统 backend 模板框架」（`create_app()` 工厂）——漂移数据反对。
- ❌ 抽 `observability.py` 成共享 import——三份已漂移，且 prometheus 指标命名各 backend 不同。
- ❌ 动 onnxtools / rapidocr 的内联池。
- ❌ 改任何 `/predict` 推理逻辑——本方案只碰「跨 backend 重复的非推理样板」。
