## 1. 本版目标

本版不再扩张功能面，而是用真实浏览器、真实 H.264 bytes 和确定性帧标记证明前两版的 pipeline 可以
上线供实验开关用户使用，并把诊断、排障、文档和 ROADMAP 一次收口。

成功后：

- Chromium E2E 能证明 key / P / B 帧与平台 `frameIndex` 一致；
- 能证明快速 seek、pending、signed URL、CORS / 网络失败和 unsupported codec 的降级合同；
- 能证明 flag off 和连续播放没有新增逐帧请求；
- `window.__videoWorkbenchDiagnostics` 能看到精确帧状态、资源预算、延迟和 fallback；
- BugReportDrawer 自动附带经过裁剪且不含敏感媒体数据的诊断；
- 固定测试矩阵给出延迟、长任务、资源稳定性和 fallback 结果；
- 根据主线程测量做出明确的 Worker 实现 / 不实现决定；
- 旧 `VideoStage`、`VideoBitmapLayer` 和“demux 尚未接入”的文档全部改成当前 Konva 架构；
- `ROADMAP.md` 与视频专项路线移除本 Epic 的遗留项；
- 实验开关仍默认关闭，默认开启留给后续独立产品决策。

## 4. 确定性媒体 fixture

### 4.1 生成策略

不提交大体积二进制视频。扩展仅在 `ENVIRONMENT=development` 且 `E2E_SEED_ENABLED=true` 时注册的
`apps/api/app/api/v1/_test_seed.py`：

```text
POST /api/v1/__test/seed/video-webcodecs
POST /api/v1/__test/seed/video-webcodecs/transition-ready
```

seed route 使用系统 `ffmpeg` / `ffprobe` 和现有媒体 probe / codec helper，在 `mktemp -d` 中生成小视频与
chunk。生成完成后：

1. 写入 E2E 隔离数据库的 dataset item / task / `VideoChunk`；
2. 写入现有测试 MinIO bucket；
3. 把 packet samples、codec string、description 与 diagnostics 写成生产同结构；
4. 返回 task id、frame expectations 和场景 id；
5. `finally` 删除临时目录；
6. 全局 `/seed/cleanup` 删除对象和数据库行。

测试不能等待 Celery；现有 Playwright server 没有媒体 worker。ready 数据由 seed 直接建立，pending 场景
由 test-only transition endpoint 确定性切到 ready。

若 E2E 主机缺少 `ffmpeg` / `ffprobe`，seed 必须以明确的 prerequisite error 失败，CI 不能 silent skip
核心 H.264 用例。

### 4.2 帧身份编码

每一帧使用高对比度、无需字体的机器可读图案：

- 左上 / 右上 / 左下 / 右下四个采样区编码 frame index 的低位；
- 中心区域编码场景 id；
- 背景亮度按 frame index 分组，辅助识别相邻帧误取；
- 采样区离边缘和宏块边界留足距离。

E2E 从 Konva media canvas 读取固定像素区域，按容差判定每个 bit。不能依赖 OCR、截图人工目测或有字体
依赖的 `drawtext`。

H.264 有色度抽样和有损压缩，验证使用亮度阈值 / 色距容差，不比较完全相同的 RGBA hash。

### 4.3 必备素材矩阵

| fixture                   | 编码特征                                         | 用途                                  |
| ------------------------- | ------------------------------------------------ | ------------------------------------- |
| `h264-baseline-gop12`     | baseline、无 B 帧、30 fps                        | key / P 帧基本路径                    |
| `h264-main-bframes-gop30` | main 或 high、2 个 B 帧、30 fps                  | decode / presentation 顺序            |
| `h264-boundary-gop8`      | 短 GOP、至少 3 个 GOP                            | GOP / chunk 边界与 reset              |
| `h264-vfr`                | 交替帧时长或非整数 fps                           | timestamp / duration，不以 fps 猜 PTS |
| `unsupported-config`      | test-only metadata 改成明确不支持的 codec string | config fallback                       |
| `malformed-samples`       | 越界 offset、缺 key 或缺 description             | demux fallback                        |

可选 HEVC：

- 若 `VideoDecoder.isConfigSupported()` 返回 supported，执行精确帧断言；
- 否则执行 fallback 断言；
- 可选用例不影响 H.264 核心资格结论。

素材控制在几秒、低分辨率以保证 E2E 速度；1080p / 4K 只进入性能脚本，不进入每次基础功能 spec。

### 5.2 测试可观察面

在 Konva stage 容器添加稳定、无视觉影响的属性：

```text
data-video-frame-source="webcodecs|native-bitmap|video"
data-video-precise-state="disabled|loading|decoding|ready|fallback"
data-video-frame-index="<number>"
```

这些属性只表达 UI 当前状态，不泄露 URL、codec description 或媒体元数据。像素正确性仍从实际画布采样，
不能仅断言 data attribute。

### 5.3 核心用例

#### A. 开关与播放边界

1. 默认关闭：
   - localStorage 无 flag；
   - 打开视频任务、暂停、逐帧；
   - 断言没有 manifest v2、chunk samples 和 chunk bytes 请求；
   - source 保持 native bitmap / video。
2. 开启并刷新：
   - localStorage 写 `video.experimental.webcodecs`；
   - 暂停后出现 precise 请求；
   - ready 时 source 为 webcodecs。
3. 连续播放：
   - 播放 3 秒；
   - source 为 video；
   - 播放期间 samples / bytes / decoder request 计数不随 frame 连续增长。

#### B. 精确帧

- baseline 素材：key 帧和两个 P 帧；
- B-frame 素材：至少选一个 decoder output 顺序不同于 presentation rank 的 B 帧；
- GOP boundary：前一 GOP 末帧、下一 GOP key、下一 GOP 第二帧；
- VFR：选择两个 duration 不同的帧；
- 每次同时断言：
  - timeline / state 的 frame index；
  - `data-video-frame-index`；
  - `data-video-frame-source=webcodecs`；
  - Konva 像素标记是目标 frame；
  - diagnostics 的 active target timestamp 与 frame expectation 一致。

#### C. 竞态与缓存

- 以不等待中间画面的方式请求 `3 → 12 → 7 → 29`，最终只能显示 29；
- 同 GOP 顺序逐帧后 encoded chunk submit 增量满足预算；
- 后退触发一次 reset，不能出现黑屏；
- 切 task 后旧 task bitmap 不出现；
- cache hit 不重复 fetch chunk bytes；
- 降低性能档位后 cache bytes 回到预算。

#### D. pending 与 signed URL

- pending：
  - 第一次 chunk metadata 返回 pending；
  - 按 `retry_after` 轮询；
  - 触发 test-only ready transition；
  - fallback 画面保持可见；
  - ready 后自动切 precise。
- signed URL：
  - 第一次 bytes 请求通过 test route / object-store fixture 返回 403；
  - metadata refresh 一次；
  - 第二次成功；
  - 断言没有第三次 refresh。

#### E. 故障降级

逐项验证：

- unsupported codec；
- samples 404；
- description 缺失；
- offset / size 越界；
- chunk bytes 404 / 500；
- CORS 等价的浏览器 fetch rejection；
- decoder error；
- `createImageBitmap` failure。

每个场景都要满足：

- source 退到 native bitmap 或 video；
- 时间轴和标注仍可交互；
- 无黑屏；
- 无未处理 promise rejection；
- 无全局 toast 风暴；
- diagnostics 给出稳定 fallback reason；
- 下一张健康素材仍能恢复 precise，不需整页重开。

#### F. 当前帧 JPEG 同源

从 UI 触发实际使用 `captureCurrentFrameJpeg` 的单帧 AI / SAM 前置路径，或通过已有受控 test hook 调用
controls：

- 画布 precise frame 为 N；
- 导出的 JPEG 对同一机器标记采样；
- 断言不是隐藏 `<video>` 尚未追上的 N-1 / N+1；
- fallback 时 JPEG 与当前 fallback 显示源一致。

不得在 E2E 中直接调用 demux 纯函数代替这一端到端断言。

### 5.4 浏览器范围

核心 gate 使用 Playwright `chromium` project。Firefox / WebKit 可增加能力降级 smoke，但在当前代码和
CI 尚未支持其 WebCodecs 时不得设为精确解码必过项。

报告必须明确区分：

- tested and supported；
- capability unavailable, fallback verified；
- not tested。

不能把“测试未运行”写成“自动回退已验证”。

## 6. 全局诊断接入

### 6.1 producer

当前 `apps/web/src/utils/videoWorkbenchDiagnostics.ts` 已能读取
`window.__videoWorkbenchDiagnostics`，BugReportDrawer 也会附加快照，但当前 Konva 视频栈没有完整 producer。

在 `VideoKonvaStage` 或现有最接近 stage 生命周期的位置写入：

```ts
interface VideoPreciseFrameDiagnosticsSnapshot {
  enabled: boolean;
  supported: boolean;
  state: string;
  source: "webcodecs" | "native-bitmap" | "video";
  frameIndex: number;
  chunkId: number | null;
  gopStartDecodeIndex: number | null;
  targetTimestampUs: number | null;
  codec: string | null;
  fallbackReason: string | null;
  lastDecodeMs: number | null;
  cache: {
    bitmapBytes: number;
    bitmapBudgetBytes: number;
    chunkBytes: number;
    chunkBudgetBytes: number;
  };
  counters: {
    sessionCreates: number;
    sessionResets: number;
    encodedChunksSubmitted: number;
    staleResults: number;
    prefetchRequests: number;
    prefetchHits: number;
  };
}
```

把它作为当前 task snapshot 的 `preciseFrame` 字段，并保持已有：

```text
activeTaskId
byTask[taskId]
updatedAt
route
frameClock
bitmap / viewport / minimap
```

### 6.2 数据最小化

诊断禁止包含：

- signed URL、Authorization、cookie；
- chunk bytes、base64 description；
- 原始视频文件名或用户上传路径；
- annotation 内容和用户输入；
- 无限增长的逐帧数组。

允许：

- codec string；
- 数值型 chunk / GOP / frame id；
- 聚合计数、耗时、预算；
- 枚举型 state / reason。

诊断每个 task 只保留最新快照；离开 task 后按现有 store 规则删除或有界淘汰。

### 6.3 生命周期

- stage mount：注册当前 task；
- frame / source / precise diagnostics 更新：覆盖 snapshot；
- task 变化：activeTaskId 切换，旧异步结果不能写新 task；
- unmount：清 active pointer；若 store 保留历史，必须有最大 task 数；
- route 不匹配时，现有读取器继续拒绝附加旧快照。

不要为逐帧诊断触发 React 重渲染风暴；用已有 ref / effect 节流，更新频率上限为 5 Hz，状态错误与
fallback 转换可以立即写入。

## 7. Bug report 接入

扩展 `BugReportDrawer.test.tsx` 与 diagnostics 工具测试，断言：

- 当前视频 task 的 `preciseFrame` 会进入描述和 console entry；
- route 不匹配不附加；
- 非 UUID task id 不错误写入后端 `task_id`；
- snapshot 超过字符上限时稳定截断；
- signed URL、description 和 bytes 不可能从 typed snapshot 进入；
- drawer 开关不改变 decoder 状态；
- 无视频诊断时保持现有 bug report 行为。

不新增 bug report DB 字段，复用已有 description / console diagnostics。

## 8. 性能资格

### 8.1 工具

扩展现有 `apps/web/scripts/video-bench/`，新增 precise-frame 场景，而不是建立第二套 benchmark runner。
输出结构化 JSON 与一份人类可读摘要；临时媒体、trace 和 profile 放临时目录，运行结束清理。若用户明确
要求保留报告，再复制到指定 artifact 目录。

记录环境：

- Chromium 版本；
- OS / CPU / GPU adapter（可得时）；
- hardware acceleration 状态（可得时）；
- fixture codec、分辨率、fps、GOP；
- performance tier；
- flag 状态。

### 8.2 矩阵

| 分辨率 / fps | 场景                                              |
| ------------ | ------------------------------------------------- |
| 1080p / 30   | cold 首帧、同 GOP 顺序、同 chunk 随机、快速 scrub |
| 1080p / 60   | 同上，重点看 decoder queue                        |
| 4K / 30      | 同上，重点看 bitmap bytes 与稳定内存              |

每组至少：

- cold ready chunk 的首次 precise frame；
- warm same-GOP 30 次；
- warm same-chunk random 30 次；
- 跨 GOP 往返 20 次；
- 连续播放 60 秒；
- 逐帧 / scrub 稳定性 30 分钟或 5,000 次操作，取先达到者。

### 8.3 指标与门

| 指标                                 | 退出门   |
| ------------------------------------ | -------- |
| warm same-GOP seek p95               | ≤ 80 ms  |
| warm same-chunk random seek p95      | ≤ 200 ms |
| flag off 新增 precise 请求           | 0        |
| 连续播放逐帧 precise 请求            | 0        |
| stale frame 激活                     | 0        |
| 预算淘汰后的持续内存增长             | 0        |
| 活动 decoder                         | ≤ 1      |
| 操作结束 live `VideoFrame`           | 0        |
| pipeline JS blocking p95             | ≤ 16 ms  |
| 归因于 pipeline 的 ≥ 50 ms long task | 0        |

绝对延迟受硬件影响。CI 以固定 runner 阈值和相对 baseline 判定，开发机结果用于记录，不用一台开发机的
数字宣称所有硬件 SLA。若 codec 落到软件解码，报告必须注明。

### 8.4 内存判断

不能只读 `performance.memory`：

- Chromium 可用时同时采集 `performance.measureUserAgentSpecificMemory()`；
- 记录应用自身 bitmap / chunk bytes 账本；
- 操作结束后 dispose、等待两次 GC-friendly idle window，再判断趋势；
- CI 无法强制 GC 时，以账本归零、资源 close 计数和多轮 plateau 为主；
- 不能把浏览器媒体进程缓存的短时波动误判为泄漏。

## 9. Dedicated Worker 决策门

### 9.1 不触发时

若全部资格矩阵满足：

- pipeline JS blocking p95 ≤ 16 ms；
- 无归因于 precise pipeline 的 50 ms long task；
- 交互帧率无可复现下降；

则不引入 Worker。在本计划 Outcome、性能文档和 CHANGELOG 中记录：

```text
主线程只负责编排，VideoDecoder 异步执行；现有测量未达到 Worker 触发门。
```

这不是“以后一定不做”，而是避免没有收益证据的线程协议、structured clone 与错误面。

### 9.2 触发时必须本版完成

新增：

```text
apps/web/src/pages/Workbench/stage/videoPreciseFrame.worker.ts
apps/web/src/pages/Workbench/stage/videoPreciseFrameWorkerClient.ts
apps/web/src/pages/Workbench/stage/videoPreciseFrameWorkerClient.test.ts
```

职责冻结为：

- main thread：
  - manifest / chunk metadata / samples query；
  - generation 与显示状态；
  - signed URL 403 后 refresh；
  - bitmap LRU、Konva 与 JPEG；
- worker：
  - chunk bytes fetch 与 byte cache；
  - byte range 验证和 `EncodedVideoChunk` 构造；
  - `VideoDecoder` session；
  - `createImageBitmap`；
  - 把 bitmap transfer 给 main。

消息：

```ts
type WorkerRequest =
  | { type: "decode"; requestId: string; generation: number; source: DecodeSource }
  | { type: "cancel"; generation: number }
  | { type: "reset"; reason: string }
  | { type: "dispose" };

type WorkerResponse =
  | {
      type: "bitmap";
      requestId: string;
      generation: number;
      bitmap: ImageBitmap;
      diagnostics: object;
    }
  | { type: "url-expired"; requestId: string; generation: number }
  | { type: "fallback"; requestId: string; generation: number; reason: string };
```

约束：

- bitmap 使用 transferable，不复制像素；
- main 不把同一 `ArrayBuffer` 再保留一份；
- `cancel` 是 latest-wins，不假设能中断已经提交硬件 decoder 的 chunk；
- worker 收到新 signed URL 后最多重试一次；
- worker crash 自动清理 client 状态并 fallback；
- 不启用 SharedArrayBuffer / COOP / COEP；
- Worker 路径必须重跑本文件全部功能与性能 gate；
- 若迁移后不改善触发指标，应撤回 Worker，保留测量结论。

### 9.3 能力边界

若目标 Chromium 支持主线程 WebCodecs 但不支持 worker 中所需的 `VideoDecoder` 或
`createImageBitmap`，Worker client 必须保留主线程 pipeline；不能把“优化不可用”变成“功能不可用”。

## 16. 风险

| 风险                                          | 缓解                                                             |
| --------------------------------------------- | ---------------------------------------------------------------- |
| Headless Chromium codec 与用户 Chrome 不同    | 记录浏览器 / GPU / codec support；至少补一轮有头 Chrome 手工资格 |
| H.264 压缩导致像素不完全一致                  | 高对比图案、宏块中心采样、容差判定                               |
| CI 缺 ffmpeg 或 MinIO                         | 明确 prerequisite 失败；不 silent skip                           |
| pending E2E 依赖无 worker                     | test-only deterministic transition                               |
| long task 归因错误                            | performance mark 包围 pipeline JS 阶段，并和页面其它任务分开     |
| Worker structured clone / transfer 引入新竞态 | 只在门触发时实现；保留 generation 与主线程 fallback              |
| 诊断泄露 signed URL                           | typed allowlist + 单测，禁止任意对象 spread                      |
| 文档提前宣告完成                              | ROADMAP 删除放在最后退出门之后                                   |
