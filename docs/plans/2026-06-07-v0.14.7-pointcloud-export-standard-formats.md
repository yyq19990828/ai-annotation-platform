# v0.14.7 · 点云标注导出标准训练格式(纯新增 serializer,零迁移)

> 规划日期 2026-06-07 · 范围:给点云项目补上 **KITTI label** / **nuScenes json** 两种标准 3D 训练格式导出,导出包内一并打进**多相机图像 + 每相机标定**(对齐 xtreme1 `LidarFusionDataExportBO`),并为 `point_mask_3d` 分割设计一个可消费的逐点导出。后端改动**以「新增导出器 / 序列化分支」为主,不动数据模型,不加迁移**,复用既有导出管线(`export.py` / `export_packaging.py`)、axis_frame 反映射(`axis_convention.py`)与导出缓存(`export_cache.py`)。
>
> **前置依赖**:
> - v0.14.0~v0.14.4(scene 模型 / scene 连续调度 / nuScenes 脚本 / scene_mode 项目 + `by_scene` 分包)均已合入,本版导出按 scene 组织多帧。
> - **v0.14.5(不归本版)**给 `box_3d` 补 `occluded` / `truncated` / `visible` 属性。本版导出 schema **必须为这些属性留位**(KITTI label 有 `occluded` / `truncated` 列,nuScenes 有 `visibility`),即便 v0.14.5 尚未合入,本版也按「属性缺失即降级为默认值」实现,合入后自动透传。
> - v0.14.6(6 相机体验 + 性能)不归本版,本版导出对相机数量不设上限,N 相机自适应打包。
>
> **本版是 0.14.x 点云收尾 patch 线的第三版(收尾闭环)**。定位铁律:**新增 serializer,不加表、不加列、零迁移**。

> **本轮开源平台调研补充**:标准 3D 导出是点云线与 SUSTechPOINTS / xtreme1 的主要剩余差距之一。本版先补可训练的最小标准包;完整 nuScenes global 轨迹导出依赖 v0.15.0 的 ego pose 地基,不在本版伪装完成。

## 1. 背景与目标

### 1.1 现状:点云项目只能导平台原生 AAP JSON

点云项目导出当前只有一条路径:`export.py:855-1007` `export_aap_json`,在 line 953 把 `media_type` 声明为 `"lidar"`,`box_3d` / `point_mask_3d` 的 geometry 原样落进 AAP JSON。这套格式无损、自洽,但:

| 缺口 | 现状 | 后果 |
|---|---|---|
| **G1 无标准 3D 训练格式** | 只有 AAP JSON,下游训练框架(OpenPCDet / mmdetection3d / nuScenes devkit)都不直接吃 | 标注数据无法喂给主流 3D 检测训练 pipeline,要用户自己写转换 |
| **G2 导出不带标定 / 多相机图像** | AAP JSON 只含 box geometry + file_path,不打包每相机标定 extrinsic/intrinsic 与图像 | 下游无法复算 3D→2D 投影,联合标注退化成「只有框、没有可投影上下文」 |
| **G3 `point_mask_3d` 无标准落地** | `geometry.point_indices` 原样落 JSON | 没有逐点 label 文件 + 类别映射,下游分割训练无法直接消费 |
| **G4 导出目标枚举未给点云列目标** | `export_packaging.py:59-63` 只为 image / video 列了 `coco/yolo/.../kitti/mot...`;`clean_export_targets`(line 66)对 `data_type` 只识别 `video`/`image`,**lidar 落 `else` 分支(全集)**,且 `build_export_zip`(line 318)在 `data_type != "video"` 的非 yolo 分支只接受 `coco`/`aap_json`(line 374),点云实际只能出 `aap_json` | 点云项目导出菜单只有 AAP JSON 一项可用,新格式无路由 |

### 1.2 目标:点云项目可导出标准 3D 训练格式 + 标定 + 多相机

本版新增三类导出目标,全部**复用既有加载 + 缓存 + 打包骨架**,仅新增序列化分支:

1. **`kitti` 3D label**(逐帧 `label_2/<frame>.txt`):每行 `type truncated occluded alpha bbox_2d(4) h w l x y z ry`,坐标在 **KITTI camera 系**。
2. **`nuscenes` json**(关系型 schema 轻量版):`sample_annotation` 风格的 box 列表 + `category` / `attribute` / `calibrated_sensor` / `sample_data`。坐标在 **ego 系**(无 ego_pose 时降级为单帧 sample 风格,见 §1.4)。
3. **`pointmask`**(`point_mask_3d` 分割):逐帧逐点 label 文件(`segmentation/<frame>.label`)+ 索引列表 + `category_map.json` 类别映射。

外加 **G2 闭环**:KITTI / nuScenes / pointmask 三种导出包都一并打进**每相机标定 + 多相机图像**(`calib/` + `images/`),对齐 xtreme1 `LidarFusionDataExportBO = {lidarPointClouds[], cameraImages[], cameraConfig}`(调研 `docs/research/14-point-cloud-image-fusion.md` §14.7.2),使下游能复算 3D→2D 投影。

### 1.3 设计决策(已拍板)

| 维度 | 选择 | 含义 |
|---|---|---|

### 1.4 ego_pose 缺失对 nuScenes 导出的限制(关键诚实标注)

nuScenes 官方 schema 的核心是**全局坐标系 + 时序**:`sample_annotation.translation` 在 **global 系**,需 `ego_pose`(车体→global 4x4)+ `calibrated_sensor`(传感器→车体)两级变换把 box 从传感器系抬到 global。

**本平台当前没有 ego_pose**(它是「多帧聚合 / 全局轨迹」才需要的高保真字段,见调研 §14.7.4 / §14.8.2,留 v0.15.0)。因此本版 nuScenes 导出**只能到 ego 系,导不到 global 系**:

- 导出的 `sample_annotation.translation` 实际是 **ego 系坐标**(标注时即在该帧 ego/lidar 系),不是 nuScenes 规范的 global 系。
- `ego_pose` 记录写**单位位姿占位**(`translation=[0,0,0]`,`rotation=[1,0,0,0]`),并在导出包 `README.txt` + 每条 `ego_pose` 的 `_aap_note` 字段明确标注「占位,无真实车体轨迹」。
- `instance` 跨帧 track 串联:有 `track_id`(若 v0.14.x 跨帧 propagate 已写 `group_id`)即按 `group_id` 串 `instance_token`;无则每帧每框独立 instance。
- **结论(文档必须点明,不可隐瞒)**:本版 nuScenes 导出是**「单帧 sample 风格、ego 系、占位 ego_pose」的子集**,可喂给「逐帧 3D 检测」训练,但**不能直接喂 nuScenes devkit 的多帧聚合 / 跟踪评测**。完整 global 轨迹待 v0.15.0 补 ego_pose 后再升级。

KITTI 格式**不受此限制**:KITTI 本身就是逐帧、相机系、无全局轨迹,本版可完整导出(这也是优先把 KITTI 做扎实的原因)。

### 1.5 不在本版本(out of scope)

- **任何加表 / 加列 / 迁移**(纯新增 serializer 铁律)。
- **属性面板本身**(→ v0.14.5):本版只**消费** `attributes` 里的 `occluded`/`truncated`/`visible`,不做属性录入 UX;缺失则降级默认。
- **6 相机体验 / worker 性能**(→ v0.14.6):本版导出对相机数不设上限,但不优化 6 相机渲染。
- **ego_pose / 时间戳数据模型**(→ v0.15.0):见 §1.4,nuScenes 导出据此降级,文档诚实标注。
- **Waymo / TFRecord / COCO-3D** 等更多格式(留更后)。
- **`point_mask_3d` 适配某个重型框架**(如 nuScenes lidarseg 的 bin 格式严格对齐):本版只做「逐点 label 文件 + 索引列表 + 类别映射」的通用可消费导出,不强求适配特定框架的字节布局。
- **前端导出 UX 大改**:本版只在导出目标下拉里给 lidar 项目补出新目标项(随 codegen / 目标列表自动出),不重构导出向导。

### 1.6 成功判据

1. **KITTI 导出**:lidar 项目 `POST /projects/{id}/export?targets=kitti` 产出 ZIP,含 `label_2/<frame>.txt`(每行 15 字段,KITTI 相机系坐标)+ `calib/<frame>.txt`(投影矩阵)+ `images/<cam>/<frame>.png` + `velodyne/`(或 pcd 回源脚本)。`occluded`/`truncated` 列正确取自 attributes(缺失填默认)。
2. **nuScenes 导出**:`targets=nuscenes` 产出 ZIP,含 `sample_annotation.json` / `category.json` / `attribute.json` / `calibrated_sensor.json` / `sample_data.json` / `ego_pose.json`(占位)。`README.txt` 明确标注「ego 系 + 占位 ego_pose,完整轨迹待 v0.15.0」。
3. **pointmask 导出**:含 `point_mask_3d` 的项目 `targets=pointmask` 产出逐帧 `segmentation/<frame>.label`(逐点类别 id)+ `category_map.json`。
4. **标定 + 多相机随包**:三种新目标的导出包都含 `calib/` 与 `images/<cam>/`,标定来自 `DatasetItem.metadata_.calibration`(extrinsic[16]/intrinsic[9]/rect[16]),图像来自 `camera_<name>` link item;下游可据此复算 3D→2D 投影。
5. **目标枚举接线**:`export_packaging.py` 为 `lidar` 列出 `LIDAR_EXPORT_TARGETS = {aap_json, kitti, nuscenes, pointmask}`;`clean_export_targets` 对 lidar 项目只接受这些目标,跨模态目标(coco/yolo)返回 400。
6. **axis_frame 衔接**:KITTI 走相机系反映射、nuScenes 走 ego 系,坐标正确(见 §6 端到端反投影对拍)。
7. **缓存正确**:KITTI 与 nuScenes 两次导出落不同 `cache_key`(targets 不同),不互相串包。
8. **回归红线**:既有 `aap_json` 点云导出、image/video 全部既有导出目标 byte 级不变。
9. `pnpm lint` / `pnpm test` / `uv run pytest -q` 全绿;`pnpm dump-openapi` 后 snapshot 只多新目标枚举值的 diff。

**属性映射(为 v0.14.5 留位)**——单一 helper,三格式共用:

```python
def _map_box_attributes(attrs: dict) -> BoxExportAttrs:
    # v0.14.5 给 box_3d 补的属性从 attributes 取;缺失即降级默认
    occluded  = int(attrs.get("occluded", 0))          # KITTI: 0..3
    truncated = float(attrs.get("truncated", 0.0))      # KITTI: 0.0..1.0
    visible   = attrs.get("visible", attrs.get("visibility", ""))  # nuScenes: "" / "v0-40" ...
    return BoxExportAttrs(occluded=occluded, truncated=truncated, visibility=str(visible))
```

- **KITTI**:`occluded` → 第 3 列(整数 0-3),`truncated` → 第 2 列(浮点 0-1),`alpha`(观测角)由 `ry` 与 box 中心方位角算出(KITTI 标准式)。
- **nuScenes**:`visible`/`visibility` → `sample_annotation.visibility_token`(映射到 `visibility.json` 的 4 档 token)。
- v0.14.5 未合入时:全部走默认值,导出仍合法(KITTI `0 0.00`,nuScenes 空 visibility),合入后自动透传,**本版与 v0.14.5 无硬编码耦合**。

### 3.2 坐标系衔接(复用 axis_frame 反映射)

这是本版最需要讲清的一块。现有 `transform_box_geometry_axis_frame`(`axis_convention.py:216`)的契约:
- `axis_frame="iso"` → 原样返回(平台归一化 ISO 系:+X 前 / +Y 左 / +Z 上)。
- `axis_frame="source"` → 经 `unapply_to_psr` 用 `R_NORM[convention]` 把 PSR **从 ISO 系反映射回数据集源系**。

各导出格式期望的目标系与 `R_NORM`(`axis_convention.py:47-56`)的关系:

| 格式 | 期望目标系 | 与平台 ISO 系的关系 | 复用现有反映射? |
|---|---|---|---|
| **AAP JSON**(既有) | iso 或 source(用户选) | `axis_frame` 参数直控 | 是,line 904 已用 |
| **KITTI** | **camera 系**(+X 右 / +Y 下 / +Z 前) | 即 `R_NORM["kitti_camera"] = (0,0,1,-1,0,0,0,-1,0)` | **复用**:对每个 box 调 `unapply_to_psr(psr_iso, "kitti_camera")`,把 ISO 系 box 映射到 KITTI camera 系。**与数据集源系无关**(KITTI 永远输出 camera 系),所以这里**不**走用户的 `axis_frame`,而是 serializer 内部固定按 `kitti_camera` 反映射。 |
| **nuScenes** | **ego 系**(≈ lidar 系,+X 前 / +Y 左 / +Z 上) | 本平台 ISO 系即 +X 前/+Y 左/+Z 上,**与 nuScenes ego 系同向** | **几乎恒等**:box 直接用 ISO 系坐标即可(ISO == nuScenes ego 系约定)。无需反映射;`size` 维度顺序(nuScenes 用 `w,l,h`)在 serializer 里换序。 |
| **pointmask** | 无几何变换(只导索引) | N/A | 不涉及坐标变换 |

**关键澄清**:KITTI 的相机系映射**走 serializer 内部固定 `unapply_to_psr(..., "kitti_camera")`**,而不是导出 API 的 `axis_frame=source` 参数。原因:`axis_frame=source` 是「映射回该数据集原本的导入源系」(可能是 sustechpoints_demo / apollo 等),而 KITTI 要的是「camera 系」这一**固定目标**,两者语义不同。serializer 拿到的 annotation geometry 始终是 ISO 系(DB 里就是归一化后的),直接 `unapply_to_psr(psr, "kitti_camera")` 即得 KITTI camera 系——`R_NORM["kitti_camera"]` 正是 ISO↔camera 的旋转矩阵,数学上自洽。

> 实现上优先**零改动 axis_convention.py**:`unapply_to_psr` 已是 public,serializer 直接 import 调用。仅当发现 ry/alpha 的角度约定需要额外 helper 时,才在 `axis_convention.py` 补一个 `box_iso_to_kitti_camera()` 薄封装(并加测试),避免在 serializer 里散落矩阵乘。

### 3.3 标定 + 多相机随包(G2 闭环,对齐 xtreme1)


- **标定来源**:每相机 item 的 `DatasetItem.metadata_.calibration`(`SensorCalibration`,`_jsonb_types.py:704`)。task→相机 item 经 `TaskDatasetItemLink`(`role=camera_<name>`,`task_dataset_item_link.py`)反查;`role=primary_lidar` 拿点云 item。
- **KITTI calib 文件**:由 `extrinsic`(velo→cam,即 `Tr_velo_to_cam`)、`intrinsic`(→ `P2`)、`rect`(→ `R0_rect`)拼出 KITTI 标准 `calib.txt`。这让 KITTI devkit 能直接复算 3D→2D。
- **无损保底**:同时落 `calib_raw/<cam>.json` 原始 16/9/16 矩阵,避免 KITTI calib 拼装有损时下游无从校正。
- **图像 / 点云回源**:沿用现有 `export_packaging.py` 的预签名 manifest + `fetch_*.py` 脚本范式(`_FETCH_IMAGES_TEMPLATE`,line 113),本机已有数据则免跑。
- **nuScenes 包**:`calibrated_sensor.json` 直接由 `SensorCalibration` 填(`camera_intrinsic` ← intrinsic[9],`translation`/`rotation` ← extrinsic[16] 拆 R|t),无需 KITTI 风格拼装。

## 5. 已知风险 / 依赖 / 未尽事项

### 5.1 nuScenes 导出的 ego_pose 降级(最关键依赖)

见 §1.4。本版 nuScenes 导出**不是完整 nuScenes**:无 ego_pose → box 停在 ego 系、`ego_pose` 占位、不可做多帧聚合 / 跟踪评测。**文档与导出包 README 必须诚实标注**,前端 tooltip 同步提示。完整 global 轨迹待 **v0.15.0** 补 ego_pose 数据模型后升级。这是与下游用户预期最容易产生落差的点,务必前置说明,不可隐瞒。

### 5.2 v0.14.5 属性依赖(软依赖,已解耦)

`occluded`/`truncated`/`visible` 由 v0.14.5 写入 `annotation.attributes`。本版通过 `_map_box_attributes`(§3.1)**缺失即降级默认**,与 v0.14.5 无硬编码耦合:v0.14.5 未合入时导出仍合法(填默认),合入后自动透传。风险:若 v0.14.5 最终用了不同的属性 key 名(如 `occlusion` 而非 `occluded`),需在 `_map_box_attributes` 调整一处 key 映射——属性 key 名应与 v0.14.5 plan 对齐确认(实现时核对)。

### 5.3 KITTI 坐标系 / alpha 约定的精度

KITTI camera 系映射走 `unapply_to_psr(..., "kitti_camera")`(§3.2),`alpha`(观测角)与 `ry` 的换算遵循 KITTI 标准式。风险:不同导入源系(sustechpoints_demo / apollo)的数据归一化到 ISO 后再映射到 camera 系,角度链路较长,须用 §6 的反投影对拍兜底(导出框反投影回相机像素应与标注时所见一致)。

### 5.4 标定缺失 / 部分相机无 calib

部分 dataset 可能只有点云无标定,或部分相机缺 `calibration`。此时:KITTI 的 `calib/<frame>.txt` 用单位矩阵占位 + README 警告;2D bbox 列填 `-1 -1 -1 -1`(KITTI 约定的「无 2D 框」);nuScenes `calibrated_sensor` 对缺标定相机跳过该 sensor。不静默失败,notes 报警。

### 5.5 point_mask_3d 与点云回源的耦合

逐点 label 文件的语义依赖「点云点序与 `point_indices` 一致」。本版导出 label 文件 + 回源脚本,但**不重排点云**;下游必须用导出包回源的同一份点云(回源脚本保证)。若用户用自己另存的点云,索引可能错位——README 须明确「label 索引对应回源包内的点云,勿换源」。

### 5.6 大 scene 导出体积

一个 1000 帧 scene × 6 相机 × 图像随包,体积可能很大。本版沿用现有落盘 tempfile + 流式 ZIP(`build_export_zip` 已落盘,line 330),图像走预签名 manifest 回源(不把图像 bytes 塞进 ZIP,只放 URL + 脚本),控制包体。`velodyne`/`images` 默认走回源脚本而非内嵌,与既有 image 导出一致。

### 5.7 与既有 video `kitti` 目标的命名共存

§3.4 已说明靠 `data_type` 分流。风险点在文档与前端:同名不同义,须在导出格式文档明确「video.kitti = MOT 跟踪 / lidar.kitti = 3D 检测」,避免用户混淆。
