## 1. 结论与目的

GPU Arbiter 的平台代码、Redis 原子账本、PostgreSQL fence、有界 FIFO、空闲/忙碌驱逐、
signed lifecycle control 与单卡/多卡/跨宿主验收器已在 v0.22.4 完成。当前阻塞不是再造
一套仲裁器，而是将五个第一方 GPU Backend 的部署级生命周期资格、能力声明、密钥和平台
证明链全量收口。

本计划的目的是：

1. 让 YOLO、Grounded-SAM2、SAM3、ONNXTools 与 RapidOCR 在当前部署通过同等强度的
   真实 GPU 全池加载、并发保护、受管卸载与显存回落验收。
2. 只有验收证据与当前镜像、权重、pool 拓扑和物理 GPU 匹配时，`/setup` 才发布严格九字段
   `managed_lifecycle` 声明。
3. 让平台的 challenge-bound health 同轮获得 `/setup` 声明、residency、boot/resource identity 和
   capability SHA-256，五个 Backend 都可形成 enforce promotion 所需的非空证明。
4. 将当前 `off` 环境安全提升到 `observe`，收集真实 would-admit / would-evict / would-reject 数据，
   为后续逐卡 `enforce` 提供准入证据。

本版完成后，“五个第一方 Backend 全部可声明、可验证、可进入 promotion”必须成立。
不得仅因为环境变量设为 `1` 就宣称 enforce 已就绪。

## 2. 全量开启后能获得什么

### 2.1 GPU Arbiter (`GPU_ARBITER_MODE=enforce`)

完整开启并通过验收后，平台可以：

- 按真实 `gpu_resource_id` 管理每张物理 GPU / MIG，不会把不同宿主的 `cuda:0` 误当同一张卡。
- 在任何可能加载 GPU 的 predict / interactive predict / warmup / reload 前，以静态显存预算和实时
  allocation 原子准入，在 Backend HTTP 前阻止可预见 OOM。
- 允许小模型在同卡可控共驻；超出 `allocatable_mb` 时，按 `eviction_priority + LRU` 选择可驱逐
  Backend，高优先级驻留保护不被低优先级请求赶走。
- 对后端级并发与卡级容量使用独立、有界 FIFO 排队；超时返回结构化 `503 + Retry-After`，不会
  无界占用 worker。
- 对忙碌 victim 执行 signed drain，等 active / builder / borrower 归零后全池 unload；放弃时以更新
  generation cancel drain，不会卸载正在被底层 future 使用的模型。
- 以 PostgreSQL 单调 generation/control fence、Redis lease 和 Ed25519 admission token 阻止旧请求、重放 token
  或迟到 unload 破坏新一代模型。
- 在 Redis、signer、证明、identity 或 rollout 不可信时 fail-closed，不会静默退化成未受管 GPU 加载。
- 同一台双卡可并行执行，一张卡的队列、驱逐、device lost 或账本故障不会污染另一张卡。
- 管理面可分开展示 desired / rollout / effective mode、allocation、lease、queue、residency、fallback 与
  blocker，支持逐卡灰度和可回滚 demotion。

### 2.2 ML Backend Router (`ML_BACKEND_ROUTER_MODE=enforce`)

服务池路由与 GPU Arbiter 正交，不能互相替代。如果也将其全量开启，平台还能在“同能力、
多实例”之间做平滑加权轮询、per-instance 并发上限、traffic drain 和被动熔断。路由先选定
registry instance，GPU Arbiter 再对该实例的物理卡做显存准入。

本计划只处理受管 GPU 生命周期声明与 GPU Arbiter 就绪，不将服务池路由与 GPU 仲裁一起强制切换。
当前没有多副本的 Backend 即使不开 Router，也能完整使用 GPU Arbiter。

### 3.2 开关与证明

- `GPU_ARBITER_MODE=off`，两张 resource 的 mode 也是 `off`。
- `GPU_ARBITER_ROLLOUT_ENABLED=false`，`gpu_arbiter_rollouts` 尚无持久灰度记录。
- 平台 signer 私钥文件和 Backend 公钥 keyring 均未部署。
- Grounded-SAM2、SAM3、ONNXTools、RapidOCR 的
  `*_MANAGED_LIFECYCLE_VERIFIED` 均未设置，按默认 `0` 运行。
- 当前四个运行实例均为 `residency.state=unloaded`、`lifecycle_gate=legacy`、`evictable=false`。

## 4. 范围与非目标

### 4.1 本版范围

- 五个第一方 GPU Backend 的声明策略一致性。
- 五套独立、可复核的真实 GPU lifecycle 验收器与共享证据 schema。
- 当前双 RTX 3090 环境的镜像/权重/pool 拓扑/显存回落验收。
- Ed25519 密钥生成、服务级 secret 隔离、公钥扩展和轮换流程。
- registry claim、budget、priority、max concurrency、membership、fence 与 challenge proof 校验。
- `off` 下的声明就绪和 `observe` 影子决策验证。
- 进入逐卡 enforce 所需的明确交接门，但不在未通过证据时自动将全部卡提升。

### 4.2 非目标

- 不重写 `gpu_arbitration` 领域包、Redis Lua 或 rollout 状态机。
- 不抽取五个 Backend 共享的模型池基类；只共享 wire 和验收证据 schema。
- 不将 `compute` 或 `nvidia-smi` 整卡用量当作 allocation 释放真值。
- 不让未经验收的第三方 Backend 变成 `evictable=true`。
- 不引入多卡自动放置、Kubernetes scheduler、MPS/time-slicing 或动态显存预算。
- 不在同一发布中强制将 `ML_BACKEND_ROUTER_MODE` 切到 enforce。

## 5. 不可变安全合同

1. `/setup.managed_lifecycle` 必须是完整、精确九字段对象；缺字段、额外字段或类型转换均不得
   被平台接受。
2. 声明代表当前部署完成 full-pool unload 资格，不只代表源码里有端点。
3. 只有 `active_requests=builders=borrowers=0`、所有 pool 明确非驻留、cache/session 已清理时才可
   返回 `gpu_loaded=false` 并减账。
4. 底层 executor / threadpool future 未真正结束时，HTTP 取消不得提前减 active、builder 或 borrower。
5. workload、mode、reset、drain、cancel 和 unload token 必须绑定 exact backend/resource/boot/epoch/generation/
   owner/operation/JTI；旧代、重放或部分 header 一律 fail-closed。
6. 平台私钥不得进入 ML Backend、Web、CPU/export/beat 容器；Backend 只持公钥环。
7. `off/observe` 不得读 signer、签业务 token、建 Redis admission lease、排队、拒绝或驱逐业务请求。
8. 任一证明不确定时保守计费为 Resident / Unknown，不得猜测已卸载。
9. 任一逐卡 promotion 失败都不得影响另一张卡；未就绪卡 effective mode 保持 off。
10. 任一回滚都先完成 signed demotion 和 fresh legacy health，不删表、不清 Redis、不倒退 fence。

## 6. Backend 验收矩阵

### 6.1 共享证据 schema

五个验收器输出同一份严格 JSON 外壳，但各自调用本 Backend 真实模型池与业务端点：

- `schema_version`、`backend_name`、`generated_at`、`passed` 和结构化 blockers；
- git commit、image ID/digest、Python/CUDA/torch/ORT 版本；
- 权重路径与 SHA-256 清单摘要，以及经审批 fixture 摘要；
- GPU UUID、driver、runtime 和容器单卡可见性；
- 空池基线、加载峰值、卸载后连续显存样本和工作集回收率；
- 每个稳定 pool id 的 provider/device/resident、builder/borrower 和 generation 状态；
- 两轮“空池 → 真实推理 → 全池驻留 → signed drain/unload → 稳定回落”结果；
- busy unload、请求取消、旧 generation、token replay、partial header 和 full cleanup failure 的合同结果。

证据文件写到仓库外的受限目录，不包含私钥、admission token、原始业务图像或签名 URL。
仓库只保留 schema、脱敏样例和结果摘要，不将一次机器证据当成通用硬件资格。

### 6.2 固定门槛

- 稳定显存窗口：连续 5 个样本，间隔 0.5 秒，最大波动不超过 64 MiB。
- 每轮卸载后至少回收本轮模型工作集的 90%，并回到经验收的 CUDA context 稳定基线。
- 最终 `state=unloaded`、`gpu_loaded=false`、`evictable=false`、active/builder/borrower 全为 0、所有 pool
  `resident=false`。
- 真实 GPU 路径不得意外转 CPU；允许 CPU fallback 的 Backend 须用独立用例验证，不得以 fallback
  替代 GPU unload 证据。
- 任一 unknown provider、不可观测私有 session、清理异常、多卡可见或权重摘要漂移都使该部署不得声明。

### 6.3 逐 Backend 覆盖

| Backend       | 必须验证的真实资源面                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------------------- |
| YOLO          | 模型池 cap、不同权重 key 的 single-flight/LRU，detect/segment/pose/OBB 中的代表路径，tracker stream 正常关闭，全池 unload |
| Grounded-SAM2 | image + video 双池、DINO/SAM 与 video predictor、embedding cache，双池共享冷建锁与 full cleanup                           |
| SAM3          | image、multiplex video、PVS video 三池，两类视频状态关闭，BF16 路径和三池 full cleanup                                    |
| ONNXTools     | pipeline/detector/va 三句柄与四个业务 ORT session，provider chain 全为 GPU，四 session 完整释放                           |
| RapidOCR      | det/cls/rec 三 session composite engine，多权重 key LRU，默认 cap=3 时最多九 session，引擎全池释放                        |

## 7. 工作分解

### P0 · 声明策略和当前真值冻结

- 固定五个 Backend 的当前 image ID、权重摘要、GPU UUID、pool 拓扑、运行端口和 registry id。
- 对比每个 `/setup`、`/health.residency`、managed endpoints 和环境变量，生成基线矩阵。
- 统一规则：五个 Backend 都使用部署级 `*_MANAGED_LIFECYCLE_VERIFIED=0|1`；YOLO 不再无条件
  宣告能力。
- 环境变量只是“运维已复核证据”的显式选择，不代替验收器；默认始终为 `0`。
- 检查旧计划/文档中“五个已实卡验收”与当前实例“四个未发布能力”的口径，保留历史证据但
  不将其当成当前部署证明。
- 搜索 lifecycle 兼容 facade、重复验收 helper 和永远不可达分支；只删除本计划使用统一策略后确认
  无消费者的死代码，不顺手重构仲裁核心。

P0 exit criteria：五个 Backend 在未验收时均不声明，在验收开关为 `1` 时均输出同一份严格
九字段对象；平台 strict parser 对五份 golden 均得到同一 capability SHA-256。

### P1 · 验收器全量补齐

- 复核并加固 SAM3、ONNXTools 现有 `scripts/validate_managed_lifecycle.py`，使其输出共享证据 schema。
- 为 YOLO、Grounded-SAM2、RapidOCR 增加对等的部署级验收器，不复制伪造结果的 mock 路径。
- 在每个 Backend 镜像中包含本验收器，但默认启动不自动执行真实加载/卸载。
- 为证据 schema、显存样本稳定性、权重摘要、provider 判定、回收率和脱敏规则补纯函数单测。
- 为五个 Backend 补验收开关 0/1、非法值、keyring 缺失、声明哈希漂移和 enforce 拒绝合同测试。

P1 exit criteria：五个镜像均能在仓库外目录生成同 schema 证据；验收失败时不修改运行配置，
不留下加载模型、临时 fixture 或中间密钥。

### P2 · 当前双 RTX 3090 部署实卡资格

执行顺序固定为每次只验收一个 Backend，验收期间暂停同卡其他业务流量：

1. YOLO 卡 0；
2. Grounded-SAM2 卡 0；
3. RapidOCR 卡 0；
4. SAM3 卡 1；
5. 启动并注册 ONNXTools，明确绑定卡 0 或独立维护窗后验收。

每个 Backend 必须：

- 以当前生产形态镜像、完整权重和实际 pool cap 运行，不以小模型、空 fixture 或临时降 cap 替代。
- 通过两轮完整验收，并将脱敏证据摘要与 image/model/GPU 指纹关联。
- 从实测峰值、最大并发临时 buffer 和安全余量重新校准 `vram_budget_mb`；现有 4000/9000/10000/12000
  只作起始配置，不作为验收结论。
- 对加载、卸载、busy 保护、重启后空池与物理卡身份做二次人工复核。
- 只在证据通过后将对应 `*_MANAGED_LIFECYCLE_VERIFIED=1`，重创 Backend 容器并读回
  `/setup` 与 `/health`。

P2 exit criteria：五个 Backend 全部能返回严格声明；空池时仍是 legacy/non-evictable，不因声明存在就
伪造 enforce 驻留。ONNXTools 必须已有 registry claim，不得以“当前没有业务使用”跳过。

### P3 · 密钥、身份与平台证明链

- 在仓库外生成 Ed25519 seed 与 public key；固定 non-secret `kid`，私钥文件权限 `0400`。
- 先将新公钥环并行部署到五个 Backend，确认非空非法 keyring 会阻止启动，空 keyring 仍仅 legacy。
- 私钥只挂载到 API、通用 worker、GPU worker 和 `gpu.control`；对容器 mount 执行负向检查。
- 配置独立 collector 数据库角色，证明普通应用角色无 membership/fence DELETE，collector 不可写 registry。
- 验证 registry URL 唯一、boot id 无 alias、resource UUID 精确、claim 完整、membership/fence 高水位单调。
- 强制运行新鲜 health scan，读回五个 exact capability SHA-256，确认 registry snapshot 与 challenge probe
  一致且无 stale observation overwrite。

P3 exit criteria：`validate_gpu_arbitration.py preflight` 对两张卡和五个 Backend 全部通过；任意移除一个
声明、公钥、identity 或 collector 权限后必须稳定阻断而不是部分就绪。

### P4 · `observe` 真实流量阶段

- 先将全局 mode 与两张 resource mode 设为 `observe`，保持 `GPU_ARBITER_ROLLOUT_ENABLED=false`。
- 统一重启 API、通用/GPU/control worker；Backend 继续 legacy gate，不调用 mode/reset，不签业务 token。
- 覆盖 predict、interactive predict、warmup、reload、registered smoke、batch pipeline、frame pipeline 和 video tracker
  的真实调用。
- 按 backend/resource 汇总 would-admit / would-evict / would-reject、预算差额、冷建频率、静态 claim 偏差、
  Unknown/fallback 和 shadow 失败原因。
- 证明 observe 期间业务成功率、路由、返回码和延迟不被 shadow 修改；Redis 断开或平台证明失败仍只记录诊断。

P4 exit criteria：每个运行 Backend 都至少覆盖一次冷启动、一次 warm 请求和一次可解释的容量决策；
零影子决策影响业务，零未解释 `gpu_config_invalid`，零 capability hash 漂移。

### P5 · 逐卡 enforce 交接门

本阶段交付“可提升”证据与操作顺序，不把所有卡一次性切到 enforce：

1. 优先选只有 SAM3 的卡 1 做独卡 canary，验证 signer、signed reset、mode enforce、Redis ready、
   cold/Resident admission、generation fence 和 signed demotion。
2. 通过后再选卡 0，覆盖 YOLO + Grounded-SAM2 + RapidOCR + ONNXTools 的共驻、刚好容量、容量拒绝、
   空闲驱逐、busy drain/cancel、cooldown/FIFO 和多 victim 场景。
3. 保留卡 1 enforce / 卡 0 observe 和反向组合，验证逐卡隔离与独立回滚。
4. 每张卡均运行 `single-card-co-residency`、`single-card-eviction`、
   `single-card-capacity-rejection`；双卡另运行 `dual-card`。
5. 将每次 rollout transition id、原 manifest、脱敏报告、系统日志和 blocker 归档到仓库外证据库。

P5 exit criteria：任一目标卡只有在完整场景通过后才可进入 `enforcing`；任一场景 blocked/Unknown/
资源污染都使该卡保持 observe/off。全量开启操作另作为维护窗的明确运维决定。

## 8. 测试与验收

### 8.1 代码门禁

- 五个 Backend 的 lifecycle、pool、endpoint、取消、builder/borrower、provider 和验收器单测。
- 共享 protocol v2 的 strict setup/residency/claims/error/replay golden tests。
- API 的 capability extraction、health observation window、membership activation、proof recovery、rollout control 和 dispatch
  authority tests。
- Redis ledger 的 allocation/lease/queue/transition/cooldown Lua golden SHA 与竞态测试；本版若没有修改 Lua，
  摘要必须保持不变。
- Compose 配置渲染测试：默认全部未验收，部署证据通过配置才显式为 1；私钥不得
  出现在 ML Backend 容器。

### 8.2 真实 GPU 门禁

- 五个 Backend 各至少两轮 full-pool 加载/卸载与 90% 工作集回收门。
- 卡 0 上的共驻、低/高优先级驱逐、刚好容量、超容量拒绝和 busy victim。
- 卡 0 / 卡 1 的真实 HTTP 执行重叠至少 500 ms，一卡故障不污染另一卡。
- response lost、cancel after grant、health timeout、Redis 断开、Backend 重启、device/provider unknown 故障注入。
- 运行结束 `runtime_ephemera_clean=true`，无遗留 lease、ticket、queue、transition 或验收子进程。

### 8.3 回归门禁

- `GPU_ARBITER_MODE=off` 下业务 transport、本地 semaphore、legacy unload 和结果 lineage 零回归。
- `observe` 下零拒绝、零排队、零驱逐、零 signer/Redis authority I/O。
- 声明开关从 1 回到 0 时，只有在 backend 已 legacy、rollout 已 off 后才允许隐藏能力。
- CPU 明确部署不得被要求 GPU claim 或 managed declaration；第三方无声明 Backend 继续按 non-evictable 兼容运行。

## 9. 回滚顺序

### 9.1 声明或 observe 阶段

1. 将全局/resource desired mode 改回 `off`。
2. 统一重启 API 和相关 worker，确认不再产生 shadow 决策。
3. 保留 Backend 声明和公钥环无害；如需隐藏声明，在确认从未进入 enforce 后单独将对应验收开关置 0。

### 9.2 enforce 阶段

1. 先将目标 resource desired mode 降为 `observe`，保持 `GPU_ARBITER_ROLLOUT_ENABLED=true`。
2. 等 signed demotion、runtime 静默、legacy ACK 和 fresh health 使持久 rollout 收敛为 off。
3. 确认平台与 Backend 都为 legacy，对应 Redis 账本无活动 transition/lease。
4. 所有卡都已收敛后才关闭 rollout latch；不清 Redis、不删 fence、不倒退 epoch。
5. 旧 token、lease 和 replay tombstone 过期后才能从 Backend 公钥环和平台私钥文件移除旧 key。
