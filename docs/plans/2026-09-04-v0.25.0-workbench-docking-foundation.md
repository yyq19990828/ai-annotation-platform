## 1. 独立交付结果

本版将现有固定左右栏和四套 `FloatingPanelShell` 收口为一个受控 Docking Workspace。任务队列、类别面板、标注详情和讨论 / Issue 可在左、右、底部停靠，可组成标签，可在同一浏览器窗口内浮动，也可隐藏并从面板菜单找回。

画布从本版起进入 Dockview，但固定为唯一中心 group，不允许用户拖动、关闭、浮动或将其藏进标签。这使本版在不承担画布换位风险的前提下，已经交付完整、可恢复的外围面板自由布局。

本版同时交付：

1. “标准标注 / 专注画布 / 审核协作”三组代码内置预设。
2. “布局 / 面板”菜单、一键重置与预设替换后的一次会话级撤销。
3. `annotate|review × image|video|3d` 六个上下文的账号级持久化。
4. 旧布局初始转换、损坏快照恢复、桌面 / 紧凑布局隔离和前端回滚通道。

预估量级为 7–10 个工程日，包括三种 Stage、annotate / review、偏好 API、深浅色和真实浏览器回归；这是复杂度估算，不是发布日期承诺。

## 2. 当前事实

- `apps/web/src/pages/Workbench/shell/WorkbenchLayout.tsx` 用固定四列 CSS Grid 组装左栏、ToolDock、Stage 和右栏，右栏内又有独立的上下 split 状态。
- `apps/web/src/pages/Workbench/state/useWorkbenchShellModel.tsx` 计算栏宽、四个 detached 面板和窄屏降级，并把所有 panel props 注入 `WorkbenchLayout`。
- `apps/web/src/pages/Workbench/shell/FloatingPanelShell.tsx` 已支持拖动、右下角 resize、折叠、关闭和合并，但没有 dock drop zone、tab group、完整 z-order 或统一布局树。
- `apps/web/src/pages/Workbench/state/useWorkbenchConfig.ts` 已有本地即时更新、按账号 localStorage 缓存、同页 hook 广播和防抖 PATCH。
- `apps/api/app/api/v1/me.py` 对偏好执行递归深合并，但只对 `cameraPanels` 有原子 map 特例；新 context 快照不能直接依赖递归 map 删除语义。
- `apps/api/app/schemas/user.py` 对布局使用 `extra="forbid"`；前端写新字段前必须先部署后端 schema。
- 图片、视频和 3D Stage 已观察容器尺寸。当前 3D 三视图与主视图共用一个 renderer / canvas，该合同受 ADR-0070 保护。
- `apps/web/src/pages/Workbench/stages/three-d/ThreeDWorkbench.helpers.ts` 已证明“代码内置布局预设 → 一次性 patch → 用户继续自由调整”不需要持久化活动预设 ID。

## 3. 目标与非目标

### 3.1 目标

- 四个外围面板能在同一受控布局中停靠、标签化、浮动、隐藏与恢复。
- 画布从第一天起就是 `renderer: "always"` 的单实例 panel，但本版位置锁定。
- 布局按模式与 Stage 分开恢复，不再用一份全局布局强行适配全部工作台。
- 预设只改空间，不改业务语义；错误快照不能阻断工作台。
- 保留旧布局读取和前端回滚能力，不为 JSONB 偏好增加数据库迁移。

### 3.2 明确不做

- 不开放画布换位；该能力属于 v0.25.1 的单实例资格门。
- 不迁移 `AIPredictionPopover` 或视频追踪面板；本版它们继续按现有 Stage overlay 运行。
- 不迁移 3D 三视图、相机面板、PSR、选中信息卡、桌宠、对象锚定 popover、Drawer、Modal 或 Toast。
- 不允许浏览器 popout 或多屏拖放，不引入 `dockview-enterprise`。
- 不建用户命名、项目共享、导入 / 导出或持久化布局 history。
- 不拆分 `AIInspectorPanel` 或 `DiscussionPanel` 的内部业务 tab，不重写 `useWorkbenchShellModel` 中的非布局逻辑。

## 4. 用户交互合同

### 4.1 布局与面板菜单

Topbar 新增单一“布局”入口，菜单内固定包含：

1. 三个通用预设命令。
2. “面板”列表，显示当前 context 支持的面板及可见性。点击隐藏面板时优先恢复其最后合法位置；该位置已失效时使用 registry 的确定默认区。点击已显示面板时聚焦它，不新建重复实例。
3. “重置当前布局”，等价于应用当前 context 的“标准标注”预设。

每个面板 tab / header 提供可达菜单：移到左侧、移到右侧、移到底部、变为同窗口浮窗、隐藏。鼠标拖放与菜单命令使用同一组布局 API。

浮窗仅在工作区根容器内移动，获得焦点时由 Dockview 管理层级。不展示“在新窗口打开”。

适配层不向其他模块暴露原始 Dockview API，也不调用 `addPopoutGroup`；tab menu 不注册 popout，`onWillShowOverlay` / `onWillDrop` 拒绝任何 popout 目标，sanitizer 同时剔除伪造的 popout 快照。

“隐藏”不等于关闭：所有 panel 都保留在布局实例中。命令先记录其 group / index / floating rect，再将 panel 移入应用 parking group，并保持 `parkingGroup.api.setVisible(false)`。恢复时若原 group 仍存在且不是 canvas / parking / compact group，就回到原 index；否则由 executor 创建 / 复用 registry 默认 sibling group：`task-queue` / `class-palette` 在 canvas 左侧，`inspector` 在右侧，`discussion` 在底部，并使用各自默认尺寸。不得回退到任意“当前活动 group”，也不得 center-move 进 canvas。任何工作台入口都不得调用 Dockview `close` / `removePanel`。

旧入口在同版完成确定映射，不留下 `leftOpen/rightOpen` 双真值：

- Topbar 左栏按钮改为显示 / 隐藏并聚焦 `task-queue`，tooltip 同步改名；`class-palette` 由面板菜单独立控制。
- Topbar 右栏按钮改为显示 / 隐藏并聚焦 `inspector`，tooltip 同步改名。
- Issue FAB、评论跳转和 `requestIssuesTab()` 先 open-or-focus `discussion`，再切内部 issues tab，不再读取或写入 `rightOpen/floatingDiscussion`。
- `leftOpen/rightOpen` 和四个旧 detached 值只参与首次快照转换，转换后不再驱动运行时 UI。

默认“标准标注”沿用现有 `15% / 70% / 15%` 左 / canvas / 右比例，右侧 inspector 初始 360px 高、discussion 使用余量；任务 / 类别最小宽 180px，inspector / discussion 最小宽 220px，canvas 最小 `480×320`，浮窗默认 `360×480`、约束 `320×320` 至 `720×900`。“审核协作”为 canvas / 详情 `65% / 35%`，discussion 占工作区底部 30%。

### 4.2 画布约束

- Canvas group 无关闭按钮、无浮动 / popout 菜单、无可拖动 tab。
- `onWillDragPanel` / `onWillDragGroup` 拦截 canvas；`onWillShowOverlay` / `onWillDrop` 拒绝把其他面板放到 canvas group 中心形成标签，但允许放到 canvas 的边缘形成分屏。
- Canvas 内部顺序固定为 ToolDock、Stage、StatusBar；Stage overlay 继续锚定到 Stage 内，不因外层 Dockview 改变定位语义。
- “专注画布”使用 group maximize / restore，不删除其他 panel；退出后恢复原树。

### 4.3 预设与撤销

应用预设前，内存中保留一份已清洗的当前 context 快照。应用成功后显示可撤销 toast；撤销只恢复该份前态，每次新预设替换上一份撤销点，不跨刷新持久化。

预设在运行时通过引擎 move / resize / visibility API 重排已有 panel，不在已挂载工作台上调用全量 `fromJSON`。预设不变更 tool、selected IDs、task / frame、annotation / prediction、video currentTime / playback、3D camera 或未提交草稿。

### 4.4 紧凑布局

`<=1024px` 时进入运行时紧凑模式，采用“锁存桌面树 → 运行时投影 → 确定性重放”，不另建响应式快照：

1. 仅在本地冷启动与远端权威初始回灌都已结算后进入紧凑模式。进入前把已清洗桌面模型锁存在内存；模型包含 docked 二叉树的方向 / 权重、稳定 group ID、tab 顺序 / active tab、浮窗矩形、隐藏 panel 与返回位置。
2. 进入时抑制 writer，canvas group 留作唯一锚点；使用现有 move / visibility API 把所有外围 panel 移入不可见 parking group。用户从“面板”菜单选择一个 panel 时，将同一实例移入唯一 `compact-overlay` 同窗口浮动 group；切换 panel 时把上一实例放回 parking。紧凑模式不提供 dock / resize，overlay 使用 `min(360px, workspaceWidth - 32px) × min(480px, workspaceHeight - 32px)` 并保留 16px 内边界。
3. 紧凑模式只允许“面板”列表的 show / focus / hide；预设、重置、布局撤销、dock、float 与 resize 项保留在菜单中但 disabled，并说明需回到桌面宽度。跨入阈值时若仍有预设撤销 toast，就关闭 toast 并丢弃对应的一次性 undo token；不允许任何命令修改锁存桌面模型。可选 panel 的运行时能力变化也只能改变 parking / `compact-overlay` 投影：桌面返回描述记为内存 pending action，退出并完成锁存树重放后才执行，紧凑 hide 则清除它。
4. 退出阈值时，`workbenchLayoutExecutor` 以现有 canvas group 为锚点：沿锁存树的 canvas 路径由内到外建立 sibling split，再以前序建立其余叶 group；每个 group 先用 `ensureGroup(stableGroupId)` 创建 / 复用目标，再 move 第一个现有 panel 到目标边缘，随后按锁存 index 以 center move 恢复其余 tab。最后依次恢复 active tab、浮窗、parking / 可见性，并自底向上恢复 split 权重；只删除已空的临时 `compact-overlay` group，不 close / remove 任何 panel。
5. 重放后规范化结果的 group / tab / visibility 必须与锁存模型完全一致，按实际 client rect 换算的 split 与浮窗边界误差不得超过 1 CSS px。失败时不 PATCH、不覆盖锁存或服务端快照，当前会话显示只读“标准标注”布局和重新加载动作；用户回到桌面模式后显式重置，才可写入标准布局。

该状态机不在阈值切换中调用 `fromJSON`，跨阈值必须保持相同 Stage React key、DOM marker 和 3D context。刷新或崩溃时紧凑投影本来就未持久化，下次仍从最后桌面快照恢复。`<768px` 继续由现有阻断页处理。

## 5. 架构、渲染与事件合同

```text
useWorkbenchShellModel
  │ existing business props and callbacks
  ▼
WorkbenchLayout
├── Topbar / banners / modal overlays
└── WorkbenchDockWorkspace
    ├── panel registry
    │   ├── canvas            always; locked
    │   ├── task-queue        onlyWhenVisible
    │   ├── class-palette     onlyWhenVisible
    │   ├── inspector         always; preserve local edit drafts
    │   └── discussion        always; preserve draft DOM
    ├── preset commands           mutate existing panels
    ├── layout executor           replay presets / compact projection
    └── workspace layout owner    serialize after mutation
```

Panel registry 的每个条目固定包含：稳定 ID、中文标题、支持的 mode / stageKind、渲染槽、renderer 策略、可停靠位置、是否允许标签 / 浮动 / 隐藏 / 关闭、默认尺寸与最小尺寸。不将 React props、callback 或当前业务数据写入可序列化 `params`。

隐藏 tab 的生命周期不统一粗暴处理：

- canvas、inspector 与 discussion 使用 `always`，分别保持 Stage DOM、采纳前属性等本地编辑草稿和未发送输入。
- task queue 与 class palette 使用 `onlyWhenVisible`，它们的真值位于 Shell / query 状态，重新显示时可从现有真值源重建。
- `always` 面板监听 visibility 变化，隐藏时停止非必要 animation / polling，但不卸载 DOM。
- parking group 是唯一隐藏通道，不渲染 tab/header、不接受用户 drop，快照中 ID 固定；canvas 永不进入该 group。

Dockview drag overlay 在工作台截止 pointer / dblclick，不触发 Stage 选中、绘制或提交。Dockview tab / menu / input 获得焦点时，现有 `useWorkbenchHotkeys` 按 editable / interactive target 规则忽略单键标注快捷键。

## 6. 快照、API 与兼容合同

### 6.1 前端快照包装

`apps/web/src/api/auth.ts` 的 `WorkbenchLayoutPreferences` 新增可选 `workspace`，包含引擎系列 `engine = "dockview@8"`，以及六个闭集 context key 对应的 `{ schemaVersion, snapshot }` 原子信封。本版客户端只读写 `schemaVersion = 1`；v1 grammar 固定为五个核心 panel，canvas 恢复后始终锁定。后端从首版预留并验证版本 `1 | 2 | 3`，其中 v2 给 v0.25.1 可移动 canvas，v3 给 v0.25.2 的七 panel 且允许固定或可移动 canvas。

快照 sanitizer 对读取与写入使用同一条路径：

1. 将 JSON 的 UTF-8 序列化结果限制在 64 KiB，拒绝非有限尺寸、超过 7 个 panel、超过 7 个用户 group 加 1 个 parking group 的快照。紧凑模式临时 `compact-overlay` 不序列化；持久化 group 上限为 8、运行时含 overlay 上限为 9。
2. 服务端 panel ID 闭集从首版即包含 `canvas`、`task-queue`、`class-palette`、`inspector`、`discussion`、`ai-task`、`video-tracker`，但按 schemaVersion grammar 限制实际集合；v1 前端仅恢复五个核心 ID，剔除业务 params、popout 与不支持的引擎字段。
3. v1 要求恰好一个唯一、docked、非标签隐藏的 canvas；缺失、重复、无效 group 或引擎 `fromJSON` 失败时应用只读标准布局。恢复后 canvas movement 始终关闭；合法 v2 / v3 不降级解释为 v1，因此不需要从任意树猜测“中心”。用户显式重置后才把标准 v1 写回。
4. 浮窗矩形按 WorkbenchDockWorkspace 实际 client rect 夹取；约束在冷恢复后重新应用，不假设第三方 JSON 持久化应用规则。
5. 遇到合法 v2 / v3 信封时不把未知 panel 过滤后覆盖原树：本版显示只读标准布局，禁用布局 mutation 并提示刷新到新版；服务端原值保持不变。

预设与 sanitizer 是应用自有纯函数，不让其他工作台代码直接依赖 Dockview 原始 JSON 结构。

### 6.2 单一写入者

新 `useWorkbenchWorkspaceLayout` 是 `layout.workspace.contexts[currentContext]` 的唯一写入者：

- 冷启动先读按 `userId + context` 分桶的 localStorage 并可渲染业务内容，但在首个 preferences GET 成功或失败前，禁用 sash、drag、hide / show、预设、重置等全部布局 mutation，也不启动 workspace PATCH。只有该初始请求返回本版支持且清洗通过、并与本地不同的 v1 信封时，才允许一次 `fromJSON(remote, { reuseExistingPanels: true })` 回灌；v2 / v3 / 未知版本直接进入只读标准布局，不调用 `fromJSON`。初始请求结算后才解除布局门，后续 refetch 永不全树回灌；因此不存在“用户先改 B、迟到 GET 再覆盖为 A”的交叉窗口。以上路径都以相同 canvas DOM marker、Stage mount 计数和 3D context 身份为发布硬门。
- 引擎顶层 mutation 发生时只更新内存；操作结束后防抖 300ms 并 PATCH 当前 context。
- 同一时间最多一个快照请求在途；在途期间又变更时仅记录最新 dirty snapshot，前一请求完成后继续提交最新值，避免同页乱序落库。
- 冷启动与远端初始回灌、紧凑投影 / 重放期间抑制 change listener，不回写中间树；初始化门解除后不接受第二次全树 `fromJSON`，预设、面板命令和响应式切换只走原位 API。
- 普通 `setLayout` / `setFields` 继续负责旧字段，但其 PATCH 不携带一份过期的 workspace 副本。

同 context 且同 schemaVersion 的多标签页 / 多设备采用 last-write-wins；本版不引入 revision / ETag。服务端已有版本高于请求版本时返回 `409 layout_schema_downgrade`，writer 立即丢弃待写 v1、切为只读标准布局并提示刷新，不重试降级写入。其他 PATCH 失败时保留本地 dirty 快照和非阻断错误提示，本次会话不回滚用户已看到的布局；下次远端成功 hydrate 时仍以服务端为准。

### 6.3 后端合并与部署顺序

- `apps/api/app/schemas/user.py` 增加严格 workspace / context 模型，按 v1 / v2 / v3 grammar 执行大小、节点、panel 集合、canvas 位置和有限值验证；v3 从本版即预留两个工具 panel 的 `visibilityIntent` 与受限 return descriptor，只接受稳定 ID、group / index 和有限矩形，不接受业务状态。
- `apps/api/app/api/v1/me.py` 将 `workbench.layout.workspace.contexts.<context>` 视为原子替换路径。每次 PATCH 在单事务中以 `SELECT ... FOR UPDATE` 重新读取用户行，并用 `populate_existing` 刷新 ORM identity map（或只查最新 `preferences` 标量），再在锁内合并并比较 schemaVersion；一个 context 删除 panel / group 不留递归深合并残影，不同 context 并发也不整列互相覆盖。请求版本低于锁内已存版本时返回 `409 layout_schema_downgrade`，绝不落库。
- 复用现有 `GET/PATCH /auth/me/preferences`，不增新 endpoint。
- 部署顺序固定为后端 schema 先、可写新字段的前端后。

### 6.4 旧状态转换与回滚通道

用户没有当前 context 快照时，从旧 `leftOpen/rightOpen`、四个 `floating*`、`common.leftWidthPct/rightWidthPct` 和右栏 split 构造一份初始布局。转换成功后保存新快照，但不删除旧偏好字段或 localStorage key，也不用新布局反向更新它们。

若用户从新前端回滚到旧前端，会回到升级前最后一份旧布局，而不是新 Docking 树的精确映射。这是为了保证回滚可靠而接受的单向转换语义。

## 7. 精确变更面

本版明显超过 8 个文件，原因是新核心布局依赖、应用适配层、偏好 schema、现有 Shell 装配、三 Stage 回归、ADR 和正式文档必须同版闭环。除下列范围外不做顺手重构。

### 7.1 依赖与架构决策

- 修改 `apps/web/package.json` 和 `pnpm-lock.yaml`：精确引入 `dockview-react@8.2.0`，不引入 enterprise package。
- 修改 `apps/web/vite.config.ts`、`.size-limit.json` 与必要的 `scripts/check-bundle-size.mjs` 测试：固定生成 `vendor-dockview-*.js`，设置 `required: true`、原始 JS 上限 300 KiB；零匹配也必须失败，不能跳过预算。
- 新增 `docs/adr/archive/0072-workbench-dockable-layout.md`：记录所有权、单实例画布、快照包装、MIT / Enterprise 边界、FlexLayout / 自研备选和退出路径。

### 7.2 前端生产代码

- 新增 `apps/web/src/pages/Workbench/layout/workbenchPanelRegistry.tsx`：稳定 panel ID、capability、renderer 策略与 slots。
- 新增 `apps/web/src/pages/Workbench/layout/workbenchLayoutPresets.ts`：三组预设、context 过滤与运行时布局命令。

## 8. 可合并实施切片

下列切片按顺序完成，每个切片后主干均保持可构建、可使用与可回滚；不建空壳页或不可达占位入口。

### Slice A · 偏好合同与布局纯函数

1. 增加后端可选 schema、context 原子替换与 API 测试。

独立验收：新旧 preferences 均能通过严格验证；不同 context 互不覆盖；旧版本写入无法覆盖较新 schema；恶意 / 超限快照被拒绝；现有客户端无行为变化。

1. 引入锁定版本依赖和 ADR，建立 panel registry / slots。
2. 用 Dockview 恢复当前默认空间结构，canvas 始终固定中心。
3. 接入快照 owner，首次从旧状态转换，默认布局视觉和现状保持。

独立验收：用户不操作 Docking 时，六个 context 的可见内容、Stage 生命周期、快捷键和宽高与替换前等价；新 snapshot 可跨刷新恢复。

### Slice C · 外围面板自由布局与预设

独立验收：用户能仅用拖放或仅用菜单完成同一组布局结果；任意自定义树都能一键恢复标准预设。

### 9.2 功能与故障矩阵

| 维度     | 覆盖                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------- |
| context  | annotate / review × image / video / 3d                                                                  |

| 面板     | 四个面板单独、标签组、左 / 右 / 底部、多浮窗、全隐藏后恢复                                              |
| 持久化   | 初始 GET pending 禁止布局 mutation、成功 / 失败结算、后续 refetch；并发写同 / 不同 context 与版本竞态   |
| 故障     | localStorage 不可用、离线、PATCH 409 / 422 / 500、损坏 JSON、未知 panel、缺失 / 重复 canvas、越界浮窗   |
| 业务回归 | 图片绘制 / 选中 / 撤销，视频播放 / 帧 / 轨迹，3D gizmo / 点选 / 三视图 / 相机                           |
| 可访问性 | tablist 焦点、中文 aria label、面板菜单等价命令、焦点时快捷键隔离                                       |

### 9.3 发布阻断条件

- 任意 Docking / 预设 / 恢复动作使 Stage mount 计数增加，或 3D renderer / context 被 dispose 再创建。
- 画布可被关闭、浮动、复制或藏入非活动 tab。
- 预设改变任务、工具、选中、帧、相机、标注、候选、播放或未提交草稿。
- 恢复期触发循环 PATCH，同一拖放产生多个最终快照请求，或一个 context 覆盖另一 context。
- 初始 preferences GET 未结算时可产生布局 mutation / PATCH，或后续 refetch 仍能 `fromJSON` 覆盖当前布局。
- 旧 v1 标签页能覆盖 v2 / v3 context，或遇到较新 schema 后仍裁剪、重试或写回 workspace。
- `FOR UPDATE` 前使用认证阶段陈旧 preferences 做版本判断 / 合并，或两个 context 的并发 PATCH 丢失其中一方。
- 远端权威初始回灌改变 canvas DOM marker、增加 Stage mount 计数、重建 3D context，或初始化结束后仍执行全树 `fromJSON`。
- 非法快照导致空白工作台，隐藏面板无法找回，紧凑模式覆盖桌面布局，或紧凑退出重放与锁存树不一致。
- 紧凑模式可执行预设 / 重置 / undo / dock / float / resize，或跨入阈值后仍保留会作用于投影树的 undo token。
- 紧凑模式中的能力恢复执行桌面返回描述、创建桌面 sibling 或改写锁存模型；或退出重放前执行 pending 桌面恢复。
- 任意隐藏路径调用 `close` / `removePanel`，或旧左右栏 / Issue 入口仍读写 `leftOpen/rightOpen/floatingDiscussion`。
- 隐藏恢复退化为任意活动 group、进入 canvas tab，或原位置失效后未使用 registry 默认 sibling。
- Dockview pointer 事件泄漏到 Stage，输入框聚焦时触发标注快捷键，或关键提交 / 退出入口不可达。
- context menu、拖放、恢复或内部 API 可产生浏览器 popout；`dockview-enterprise` 进入 lockfile；或 `vendor-dockview` 未唯一匹配 300 KiB size gate。

## 10. 成功指标

1. 用户可在 30 秒内将任一外围面板移到左 / 右 / 底部、放入标签组、浮动、隐藏并恢复，拖放和菜单两条路径结果一致。
2. 从任意自定义树到三个通用预设中任一布局只需一次命令；撤销能精确回到应用前的布局。
3. 每个 context 连续执行 50 次 dock / tab / float / resize 后，刷新和远端恢复的树与最后一次有效快照一致。
4. 六个 context 中 Stage mount 计数在布局操作前后不增加；3D 不创建第二个图形 context。
5. Dockview 布局交互不产生 annotation / task mutation，不增新 API endpoint、数据库实体、环境变量、长期 flag 或外部账号。

## 11. 风险、最脆弱假设与回滚

| 风险                              | 化解                                                                                    |
| --------------------------------- | --------------------------------------------------------------------------------------- |
| Dockview 默认渲染策略卸载隐藏 tab | canvas / inspector / discussion 明确使用 `always`；其余 panel 只依赖 Shell / query 真值 |
| 初始化 `fromJSON` 重建 Stage      | 仅受支持 v1 冷启动 / 回灌启用 `reuseExistingPanels` 并过 identity 门；高版本不进引擎    |
| 快照与旧布局双写分叉              | 新 snapshot 是单向转换后的新真值；旧字段冻结为回滚快照，不反向更新                      |
| 紧凑模式或外接屏让浮窗丢失        | 锁存桌面树、原位投影并做重放等价校验；失败不写回，面板可恢复，桌面模式下可重置          |
| Dockview CSS 破坏深色模式         | 只从 `--sc-*` 映射自定义主题，通过 `pnpm --filter @anno/web lint:css-tokens` 与截图回归 |
| 前后端滚动部署出现 422            | 后端 schema 先部署，前端再开始写 workspace                                              |

本版最脆弱的假设是：即使 canvas 本版不移动，Dockview 也能在周边 panel 变化、group maximize / restore 和紧凑切换中保持 canvas DOM。若该假设失败，停止发布，不用任务状态外移或强制重挂载规避；改为画布永久留在 Dockview 外，只对外围面板使用并列 Docking 区，并新建 ADR 修正本决策。

回滚顺序：

1. 优先只回滚前端 Dockview 适配层，恢复旧 `WorkbenchLayout`；后端 additive schema 和 JSONB 新字段保留为兼容 tombstone。
2. 若必须回滚后端到旧严格 schema，先停止 Web 流量，并用生产 Compose 叠加文件停止 API / Celery worker / beat；在部署目录执行以下 custom-format 备份。这里不使用升级指南的 plain SQL 示例。

   ```bash
   docker compose --env-file .env.production \
     -f docker-compose.yml -f docker-compose.prod.yml \
     stop api celery-worker celery-beat
   mkdir -p ./backups
   chmod 700 ./backups
   docker exec ai-annotation-platform-postgres-1 \
     pg_dump -U user -d annotation -Fc \
     > ./backups/workbench-layout-pre-rollback.dump
   test -s ./backups/workbench-layout-pre-rollback.dump
   docker exec -i ai-annotation-platform-postgres-1 \
     pg_restore --list \
     < ./backups/workbench-layout-pre-rollback.dump \
     > ./backups/workbench-layout-pre-rollback.list
   test -s ./backups/workbench-layout-pre-rollback.list
   sha256sum ./backups/workbench-layout-pre-rollback.dump \
     > ./backups/workbench-layout-pre-rollback.dump.sha256
   ```

3. 记录带 `preferences #> '{workbench,layout,workspace}'` 的用户数，在单事务中用 `preferences #- '{workbench,layout,workspace}'` 只删除该路径；提交前计数必须归零，否则回滚事务。
4. Web 入口保持阻断、worker / beat 保持停止，只启动旧 API 后用回滚测试账号完成 preferences GET / PATCH 与六类工作台 smoke；成功后才启动 worker / beat 并恢复流量。提交后失败则放弃本次后端回滚并保持停流，再次执行 `docker compose --env-file .env.production -f docker-compose.yml -f docker-compose.prod.yml stop api celery-worker celery-beat` 并确认三个写入服务均停止，然后校验 checksum、恢复并重跑 smoke：

   ```bash
   sha256sum -c ./backups/workbench-layout-pre-rollback.dump.sha256
   docker exec -i ai-annotation-platform-postgres-1 \
     pg_restore --clean --if-exists --exit-on-error --no-owner \
     -U user -d annotation \
     < ./backups/workbench-layout-pre-rollback.dump
   ```

   dump 恢复后包含原 `workspace`，因此必须重新部署备份时正在运行、支持该字段的 v0.25.x API / Web；先只启动兼容 API 做 preferences 与六类工作台 smoke，成功后再启动 worker / beat 并恢复 Web 流量，绝不再次启动严格旧 API。

5. 旧布局字段和 localStorage key 未被删除，用户回到升级前最后布局；新 Docking 细节不做反向映射。备份文件在维护验收完成前不得删除。
