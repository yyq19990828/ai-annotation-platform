# Plan · Data Manager 聚合、结构化搜索与模态化视图

状态：**已完成 2026-07-11 · 版本锚点 v0.21.29 · 产品边界已锁定**。本计划接续已占用 v0.21.28 的视频 AI 追踪候选审阅工作，已把 `/projects/:id/data-manager` 从“保存视图 + 任务筛选表”升级为项目级数据探索入口。

> 本版本采用 task-centric 方案并已实现；object-centric 方案仍独立进入 [v0.21.30 计划](2026-07-11-v0.21.30-data-manager-object-track-explorer.md)。

## 1. 本轮重新探查后的结论

### 1.1 当前页面的真实定位

当前路由不是全局 `/data-manager`，而是项目内的 `/projects/:id/data-manager`。现有能力以 task 为粒度：

- 左侧展示内置视图、我的视图、项目共享视图；
- 通过受控 AND DSL 筛选任务；
- 支持保存筛选、排序和列配置的后端模型；
- 主表展示任务状态、人员、批次、标注数、prediction 行数、反馈、Scene/帧和最近活动；
- 非特权用户只可查询其 batch 可见范围内的任务。

现状适合作为下一版的查询内核，但还不是完整的数据探索器：缺少项目聚合、关键词搜索、来源/轨迹/属性筛选、按模态变化的字段，以及匹配对象的解释能力。

### 1.2 先修复的现有正确性问题

下一版开始扩展前，先处理以下基线问题：

1. 前端把后端内置“全部任务”的空过滤 `{}` 转成了 `status=pending`，导致左侧总数、表格总数和实际过滤条件不一致。
2. 后端默认列包含 `file_name`，前端列设置与单元格渲染未完整支持，当前会出现一列 `—`，而文件名又重复显示在任务编号下。
3. 页头“共 N 个任务”当前使用过滤后的数量，未区分“项目/可见范围总量”和“当前视图匹配量”。
4. 普通 video 项目也显示 Scene/帧列，但普通视频的帧语义位于视频元数据和 compact geometry 内，该列通常为空且语义错误。
5. 后端保存了排序，前端表头没有排序入口；切换视图会静默丢弃未保存编辑；保存仍使用 `window.prompt`；缺少加载、空、错误和成功反馈。

### 1.3 “AI 待审”必须改成真实候选口径

当前内置“有预测候选”实际只判断 `Task.total_predictions > 0`。该值是 prediction **行数**，不是尚未处理的 shape 数；一条 prediction 可以包含多个 shape，拒绝和接受也都发生在 shape 粒度。

下一版定义两个可分别筛选、可合并展示的待审量：

- **AI 检测候选待审**：`prediction.result` 中全部 shape，排除 `rejected_shape_indexes`，再排除已有 active annotation 对应的 `(parent_prediction_id, attributes._shape_index)`。
- **AI 追踪结果待审**：`video_tracker_jobs.status=pending_review`，以及仍带 `staged_result`、允许审阅的取消任务。

汇总卡可以显示“AI 待审总量”，但筛选器和明细必须保留两个来源，不能继续用 prediction 行数代替。

### 1.4 人工、AI、轨迹、属性不是一个枚举

下一版按互相正交的维度建模，避免出现“AI 轨迹究竟算 AI 还是轨迹”的冲突：

| 维度 | 计划字段 | 语义 |
|---|---|---|
| 候选生命周期 | `ai.pending_prediction_shape` / `ai.pending_tracker_job` | 尚未转成正式 annotation 的 AI 结果 |
| 标注来源 | `annotation.source` | `manual`、`prediction_based`、`ai_tracker`、`interpolated` |
| 导入方式 | `annotation.imported` | 是否由导入链路写入；不覆盖原始来源 |
| 结构 | `annotation.has_track` / `annotation.track_id` | 单帧对象或轨迹成员 |
| 几何/工具 | `annotation.annotation_type` / `annotation.tool_unit_id` | bbox、region、3D box、point mask、video track 等 |
| 类别 | `annotation.class_name` | 项目工具配置中的类别 |
| 属性值 | `annotation.attribute.<unit>.<key>` | 由项目 attribute schema 生成的类型化字段 |
| 属性来源 | `annotation.attribute_origin.<unit>.<key>` | 每个属性键仍为 AI 产物或已由人工确认/修改 |
| 视频关键帧来源 | `keyframe.source` | manual、prediction、interpolated；仅视频轨迹能力启用时出现 |

任务审核状态、审核退回和 annotation feedback 也保持为三个不同维度，不互相替代。

## 2. 下一版目标与非目标

### 目标

1. 同时看清“项目/当前用户可见范围总量”和“当前视图匹配量”。
2. 在同一查询范围内查看任务状态、AI 待审、标注来源、结构、几何、类别、属性完整度和值分布等聚合。
3. 支持任务编号/文件名关键词搜索，以及来源、轨迹、类别、属性等结构化搜索。
4. 让不同项目形态显示真正有意义的默认列、筛选器、聚合和内置视图。
5. 保持 saved view、权限范围与查询/聚合口径一致，不能通过聚合泄露不可见任务数量。
6. 修复现有视图的正确性和可用性问题，并建立前后端测试。

### 非目标

- 不在本版本加入批量改状态、批量分配、批量删除等写操作；Data Manager 仍是只读探索入口。
- 不复制 image、video、lidar 三套独立页面或独立 DSL。
- 不开放任意 JSONB key 的自由查询，也不把 raw geometry、完整属性 JSON、关键帧列表或标定矩阵塞进任务主表。
- 不在本版本统一迁移 prediction 候选和 video tracker staged result 到新的候选表；先建立统一读模型和明确口径。
- 不把跨项目分析或跨项目 saved view 纳入本版本。

## 3. 产品形态：统一壳层，按项目能力变化

项目能力的权威组合是：

```text
data_type (image | video | lidar)
× scene_mode
× enabled tool_units
× attribute_schema
```

`type_key` 只用于选择默认 preset，不能单独决定字段；Scene 也不是第四种数据类型，它是 image/lidar 上的跨 task 帧序列能力。

因此保留一个 `/projects/:id/data-manager` 页面和一套查询/权限/saved-view 内核，由后端 capability schema 告诉前端应展示哪些字段、操作符、列、指标和内置视图。

### 3.1 共通能力

- 关键词：任务编号、文件名；Scene 项目可补充 Scene 名称。
- 工作流：任务状态、标注员、审核员、批次、提交/审核时间、退回原因。
- 数据质量：annotation 数、未解决反馈、最近活动。
- 来源：人工、接受的 AI prediction、AI tracker、插值、导入。
- 候选：AI 检测候选待审、AI 追踪结果待审。
- 结构：单帧对象、含轨迹、缺少 track ID。
- 类别与项目配置的属性字段。

### 3.2 模态能力矩阵

| 项目形态 | 默认增加的列与聚合 | 不应默认展示 |
|---|---|---|
| 普通 image | 分辨率、启用的 2D tool unit 数量、类别、属性完整度、AI 检测候选 | Scene/帧、视频关键帧 |
| scene image | image 能力 + Scene、帧序号、序列进度、跨帧 track、插值对象 | 视频时长/fps |
| 普通 video | 时长、fps、frame count、单帧 shape、track、关键帧、outside/occluded 摘要、tracker 待审 | Scene/帧 |
| 普通 lidar | 3D box、point mask、传感器角色、类别和属性 | 视频关键帧 |
| scene lidar | lidar 能力 + Scene、帧序号、相机路数、distinct track、未跟踪 3D box、插值对象、标定异常摘要 | 视频时长/fps |

具体项目没有启用 track 或某种 tool unit 时，对应列、筛选和空聚合不出现。

### 3.3 聚合单位必须随模态解释

- image：一条 active annotation 通常对应一个对象。
- compact video track：一条 track annotation 通常对应一条轨迹，内部包含多个 keyframe。
- scene image/lidar：跨帧对象由多条 annotation 共享 `track_id`，项目轨迹数必须 `count(distinct track_id)`，不能累计每个 task 的轨迹数。

## 4. 页面信息架构

### 4.1 已锁定的 v0.21.29 页面层级

保留左侧 saved views，但允许折叠；主区分为两层：

1. **概览区**：展示项目/可见范围基线与当前视图匹配量，并提供可展开的分布面板。
2. **任务探索区**：搜索、筛选、排序、列设置、任务表和匹配对象抽屉。

不在任务表中把 `颜色=红`、`track_id=...` 伪装成 task 的单值。任务行只显示摘要，例如“红 ×3 / 缺失 ×1”或“轨迹 ×5”；点击行或“匹配对象”打开抽屉，列出真正命中的 annotation/track，并可跳转工作台定位。

### 4.2 概览区

顶部固定显示两种范围：

- **可见任务总量**：当前用户在该项目内有权看到的全部任务；管理员通常等于项目总量。
- **当前视图匹配量**：应用 saved view、关键词和临时筛选后的任务数。

核心卡片控制在 5–6 个：任务、active annotation、AI 待审、人工/AI 来源摘要、轨迹/对象、未解决反馈。其余分布进入可展开面板：

- 任务状态；
- annotation source / imported；
- AI 候选来源；
- tool unit / geometry / class；
- 属性完整度和值分布；
- 当前模态的专属指标。

所有图表默认跟随当前过滤条件，同时保留可见范围基线，避免用户把过滤结果误认为整个项目。

### 4.3 任务探索区

- 顶部使用有 debounce 的关键词搜索框；搜索条件规范化为 DSL 字段，随 saved view 保存。
- 已应用条件显示为紧凑 chips；“添加筛选”使用按字段类型生成的 popover 控件，而不是裸 input/select。
- 列设置、排序和视图操作进入独立 popover/menu；删除视图不再占据主操作位。
- 保存使用 Dialog，明确名称、可见性、覆盖/另存；切换视图前提示未保存修改。
- 表头和任务/文件列 sticky；仅请求和计算可见列；分页时保留筛选、排序和选列状态。
- 提供 skeleton、空状态、请求错误、保存成功/失败 toast。
- 默认列来自 capability schema，用户列设置继续由 saved view 覆盖。

## 5. 搜索结果粒度：已锁定 task-centric

“支持按轨迹和属性搜索”存在 task-centric 与 object-centric 两种不同产品。本版锁定前者。

### v0.21.29：task-centric

- 条件命中任意 active annotation/track 后，结果仍是一行 task。
- 任务行展示命中摘要，抽屉展示匹配对象/轨迹并可跳回工作台。
- 继续复用 `ProjectTaskView`、现有权限和 saved-view 模型。
- 能完整回答“哪些任务包含 AI 待审、人工标注、某条轨迹或某种属性”。

### v0.21.30：object-centric

- 搜索结果一行就是 annotation 或 track，可跨任务直接查看 track ID、类别、属性、关键帧和跨度。
- 需要新增 `entity_scope=tasks|objects`、对象查询响应、独立分页/排序、saved-view 兼容与工作台定位契约。
- 对 video compact track 与 scene lidar 跨 task track 还需两种不同的行模型。

该能力已明确移交 [v0.21.30 对象/轨迹探索计划](2026-07-11-v0.21.30-data-manager-object-track-explorer.md)，不进入本版关键路径。v0.21.29 的匹配对象响应仍设计为可复用 read model，避免下个版本推倒重做。

## 6. 后端契约

### 6.1 Capability schema

新增：

```text
GET /projects/{project_id}/data-manager/schema
```

返回：

- `project_kind`：`data_type`、`scene_mode`、`type_key`；
- 启用的 tool units、classes、attribute fields；
- 可用 filter fields 与按类型限制的 operators；
- 可用 columns、default columns、sort fields；
- 可用 aggregate dimensions、built-in views；
- 字段的用户标签、值类型、是否昂贵、是否仅某模态可用。

后端是字段和操作符的唯一真值。前端不再维护一套容易漂移的静态字段表。

### 6.2 Task query

保留并兼容现有接口，不为改名制造无必要迁移：

```text
POST /projects/{project_id}/tasks/query
```

扩展 DSL 字段：

```text
task.keyword
annotation.source
annotation.imported
annotation.annotation_type
annotation.tool_unit_id
annotation.class_name
annotation.has_track
annotation.track_id
annotation.attribute.<unit>.<key>
annotation.attribute_origin.<unit>.<key>
keyframe.source
ai.pending_prediction_shape_count
ai.pending_tracker_job_count
feedback.status
```

规则：

- annotation 条件只匹配 active、非 cancelled annotation。
- 多个 annotation 条件在同一规则组内默认要求“存在同一对象满足全部对象条件”，避免“红色来自 A、car 来自 B”却误报为命中；跨对象语义以后再显式增加。
- `task.keyword` 首版搜索 display ID、文件名；Scene 名称仅 capability 支持时加入。
- 属性字段只从项目配置生成白名单，删除/停用字段后 saved view 显示“字段已失效”并允许移除，不能让整个视图永久 422。
- `columns_json` 必须真正控制昂贵聚合是否计算，而不是只控制前端显示。

属性操作符按 schema 类型限定：

| 类型 | 操作符 |
|---|---|
| text | `eq`、`contains`、`exists`、`missing` |
| number / range | `eq`、`gt`、`gte`、`lt`、`lte`、`between`、`exists`、`missing` |
| boolean | `eq`、`exists`、`missing` |
| select | `eq`、`in`、`exists`、`missing` |
| multiselect | `contains_any`、`contains_all`、`exists`、`missing` |

### 6.3 Aggregate summary

新增：

```text
POST /projects/{project_id}/data-manager/summary
```

请求复用 task query 的 `filter_json` 和 `sort` 以外的 scope；响应至少包含：

- `scope.visible_task_total` 与 `scope.matched_task_total`；
- task status；
- active annotation 总量和按 source/imported/class/tool unit/geometry 的分布；
- AI pending prediction shapes 与 pending tracker jobs；
- single-frame object / tracked object / distinct track；
- unresolved feedback；
- 属性完整度、缺失数与按 schema 允许的值分布；
- capability 驱动的 video / lidar / scene 专属指标。

summary 与 task query 必须复用同一个“可见 task scope”构造器。非管理员看到的是其可见范围汇总，不能直接按 `project_id` 聚合。

聚合按 `filter_json` 缓存，不能因翻页 offset 改变而重算；分页请求也不重复携带完整 summary。

### 6.4 匹配对象抽屉

方案 A 下新增只读明细接口或 query expansion：

```text
POST /projects/{project_id}/tasks/{task_id}/data-manager/matches
```

它接收当前 annotation/track/attribute 条件，返回命中的最小对象摘要：annotation ID、track ID、class、tool unit/geometry、source、相关属性、视频关键帧/Scene 定位信息。响应不返回 raw geometry 大对象，工作台通过稳定 ID 与帧定位参数加载权威数据。

## 7. 数据一致性与性能设计

### 7.1 Track ID 一致性

compact video track 的 geometry 内含 `track_id`，数据库也已有 `Annotation.track_id` 一等列。当前部分创建、拆分、合并或更新路径仍可能只写 geometry。

本版在开放轨迹搜索前必须：

1. 审计并统一所有 video track 写路径，同步 `Annotation.track_id`；
2. 增加一次 geometry → column 的幂等回填迁移；
3. 过渡期读路径使用 `coalesce(Annotation.track_id, geometry->>'track_id')`；
4. 为项目/任务范围内的 track 查询增加合适的 partial/复合索引；
5. 用测试覆盖创建、拆分、合并、导入和 tracker 接受后的列/geometry 一致性。

### 7.2 查询执行策略

现有列表会为每一行无条件运行多组相关子查询，下一版改为：

1. 先构造权限安全的 visible task scope；
2. 应用过滤和排序得到当前页 task IDs；
3. 对当前页 IDs 批量 `GROUP BY task_id` 计算实际请求的列；
4. summary 在独立查询中对 matched scope 聚合；
5. 禁止逐 task / annotation N+1；
6. 先保留现有分页契约，只有基准确认大 offset 成为瓶颈时才引入 keyset cursor。

### 7.3 JSONB 与搜索索引

- 不直接复用当前把全部 attributes 拉到 Python 的 class-usage 实现。
- select/boolean/exists 等高频属性条件优先使用受控 JSONB containment；是否增加 attributes/attributes_meta GIN 由 `EXPLAIN ANALYZE` 决定。
- 任意 text contains 和动态数值范围不承诺自动高性能；先测常用字段，再选择 GIN/表达式索引或派生 projection。
- 文件名 contains 搜索先记录真实查询计划；需要时增加 `pg_trgm` GIN，display ID 优先 exact/prefix。
- AI pending shape 首版用 SQL CTE/JSONB 展开并做规模基准；达不到门槛时才考虑物化计数，避免过早引入新的候选决策表。

性能验收基准使用至少 100,000 tasks、包含多 shape prediction、视频轨迹和属性数据的种子集：

- 首屏 task query 不出现 N+1，并仅计算请求列；
- 常用过滤的第一页查询目标 P95 ≤ 800 ms；
- summary 冷查询目标 P95 ≤ 2 s，缓存命中目标 P95 ≤ 500 ms；
- 如果基准环境无法稳定复现绝对时间，至少保存 `EXPLAIN (ANALYZE, BUFFERS)` 和前后对比，不允许执行计划退化为对全部 JSONB 的无界重复扫描。

## 9. 测试与验收

### 后端

- DSL 字段和类型化 operator 的合法/非法组合。
- 同一对象满足多条件的 exists 语义。
- prediction shape 接受/拒绝后的 pending 数准确；tracker pending/cancelled-with-staged 口径准确。
- manual、prediction_based、ai_tracker、interpolated、imported 与 attribute origin 分桶准确。
- video compact track 与 scene lidar distinct track 口径准确。
- track ID 写路径与回填迁移一致。
- 普通用户的 query、summary、match detail 均严格受 batch visibility 限制。
- 删除 attribute schema 字段后旧 saved view 可解释地降级。

### 前端

- “全部任务”无隐式 pending 过滤。
