# v0.13.1 · 点云 scene 统一资产导入 + 标定存储

> Epic:[点云 + 图像联合标注工作台](./2026-06-02-v0.13.x-point-cloud-workbench-epic.md) 第二切片。
> 主题:把一套 **scene 目录**(`lidar/` + `camera/<cam>/` + 可选 `calib/camera/<cam>.json`)导入为「每帧一个 Task + 多文件 link + 各相机标定」。**仅 API,无前端可见变化。**
> 依赖:v0.13.0(`TaskDatasetItemLink` / `Box3DGeometry` / file_type / 工具单位)。
> 调研对应:research §14.7.1(标定投影)/ §14.8.3 第 2 层(标定存储 G2)。

## 背景

v0.13.0 落了「多文件关联表 + 3D 几何」的静态地基,但还没有任何东西去**填充**它。本切片补上导入管线:把自动驾驶常见的 scene 目录结构一次性转成平台的 Task + DatasetItem + link + 标定。

解掉 epic 六缺口里剩下的后端项 **G2(标定存储)**,并首次让 G1(link 表)有真实数据流过。

### scene 目录形态(以测试夹具 `third-party/SUSTechPOINTS/data/example` 为准)

```
<scene>/
  lidar/000970.pcd                      # 主点云,文件名 stem = frame id
  camera/front/000970.jpg               # 各相机同名帧
  camera/left/000970.jpg
  camera/right/000970.jpg
  calib/camera/front.json               # 每相机一份标定(对该相机所有帧通用)
  calib/camera/left.json
  calib/camera/right.json
```

标定 JSON:`{ "extrinsic": [16 floats, row-major 4x4], "intrinsic": [9 floats, row-major 3x3] }`(KITTI 另有可选 `rect`[16])。投影链(v0.13.4 才用,这里只存):`extrinsic·[x,y,z,1] → 取 xyz → intrinsic·xyz → 透视除法 → 像素`。

## 范围(做什么)

### 0.13.1-1 标定 schema · G2(`_jsonb_types.py`,无迁移)
- 新增 `SensorCalibration` Pydantic 子 schema:`extrinsic: list[float]`(len 16)、`intrinsic: list[float]`(len 9)、`rect: list[float] | None`(len 16,KITTI 可选)。`field_validator` 校验长度。
- **存储约定**:写进 `DatasetItem.metadata_` 的约定 key `"calibration"`(不加列)。在 `DatasetItem` 的 Pydantic 出/入 schema(`schemas/dataset.py`)里把该 key 声明为可选 `SensorCalibration`,让 codegen 出强类型。
- 同一相机标定对该相机所有帧通用 → 写进**每个**该相机 DatasetItem(去规范化,简单;不引相机维度新表)。

### 0.13.1-2 scene 感知的建任务分流(挂在现有管线上,不另起入口)

> 现有管线(经勘探确认):**文件入库**(`ingest_one` / `add_item`,`dataset.py:315/356`)→ **关联项目**(`POST /{id}/link` → `link_project`,`dataset.py:631`)→ **建 Task**(`build_tasks_for_link`,`dataset.py:54-129`,当前每 DatasetItem 建一个 Task,1:1,`NOT EXISTS` 去重)。
>
> 复用前两段(文件照常进 `datasets` bucket 成 DatasetItem,`.pcd` 已被 v0.13.0 推断为 `point_cloud`),**只在第三段按 `project.data_type` 分流**:

- 在 `build_tasks_for_link` 内按项目 `data_type` 分流:`image`/`video` 走现有 1:1 路径不动;`point_cloud` 走新 `build_pointcloud_tasks_for_link`。
- **新建任务器** `build_pointcloud_tasks_for_link`:
  1. **帧分组**:扫该 dataset 的 DatasetItem,按 `file_path` 结构解析 —— `.../lidar/<frame>.pcd` 取 frame id 与「主点云」,`.../camera/<cam>/<frame>.{jpg,png}` 取 (frame, cam)。
  2. **每帧一个 Task**(`file_type=point_cloud`,`dataset_item_id` = 该帧 primary_lidar item,见 0.13.1-3),用 v0.13.0 `link_items` 关联 `primary_lidar` + 各 `camera_<cam>`。
  3. **帧级去重**:幂等键从「(project, item)」改为「(project, frame 的 lidar item)」,重跑不双建。
  4. **缺帧容错**:某相机缺某帧 → 该帧只 link 存在传感器,log warning,不报错。
- **标定写入**:`calib/camera/<cam>.json` 文件也作为 DatasetItem 入库(`.json`→`other`)。新建任务器(或独立 `attach_calibration` 步)从 storage 读这些 JSON → 解析为 `SensorCalibration` → 写进该相机各帧 DatasetItem 的 `metadata_["calibration"]`;**无 calib 则跳过**(标定降级,3D-only,不阻断)。

### 0.13.1-3 task.dataset_item_id 共存策略(关键决策)
- **3D task 的 `task.dataset_item_id` 指向该帧 primary_lidar item**(非 null),沿用 `build_tasks_for_link` 现有写法(它本就给每 task 设 dataset_item_id + 复制 file_name/path/type)。理由:导出 / task 列表 / 缩略图等大量消费方假设 task 有单一 dataset_item;指向主点云让它们看到「主资产」不炸,link-aware 新消费方再走 link 表取全部。
- **明确不采纳**勘探报告末尾的「引入 Scene 模型 + `Task.scene_id` + 改 `dataset_item_id` 为 nullable」方案 —— 那与 epic 已锁定设计(link 表 + dataset_item_id=lidar)冲突,且是破坏性迁移。本切片零迁移。
- 1:1 假设兼容面(导出 / task 列表 / 缩略图)在实现期对照勘探报告第 7 节逐一核对;消费方真正消费多 item 是后续切片的事,本切片只保证不炸。

### 0.13.1-4 入口:复用现有,不新增导入 API
- **文件入库复用**现有 `import-from-connection`(S3/MinIO/SFTP)或 `upload-zip`,无需新端点 —— scene 目录就是带 `lidar/`、`camera/<cam>/`、`calib/camera/` 子目录的一批文件,`ingest_one` 已保留子目录层级进 `file_path`。
- **建任务复用** `POST /{id}/link`(同步小 / Celery 大,阈值 `task_create_sync_threshold`),分流在 `build_tasks_for_link` 内,异步 worker `run_create_tasks` 自动覆盖。
- 由此**本切片几乎不碰 API 层**,改动集中在 service(分流 + 帧分组 + 标定写入)+ schema(`SensorCalibration`)。

## 不做(明确排除)
- 不做任何前端(3D 查看器是 v0.13.2)。
- 不做投影计算 / 可视化(v0.13.4);本切片只**存**标定,不算投影。
- 不做 3D 标注工具 / label 导入(SUSTechPOINTS `label/` 暂不解析)。
- 不做 KITTI / nuScenes 等具体数据集格式适配(未来)。
- 不加任何数据库列 / 迁移(标定进 metadata_,关联进既有 link 表)。

## 风险
- **`task.dataset_item_id` 多义**:见 0.13.1-3,需对照管线图核对单 item 假设的消费方。
- **帧对齐**:相机间帧不全、文件名格式差异(stem 提取规则);先按 SUSTechPOINTS 的零填充数字 stem,容错缺帧。
- **标定去规范化**:同一标定写多份(每帧每相机),scene 大时 metadata 冗余;可接受(标定体积小),未来若需相机维度再抽表。
- **存储来源**:scene 文件可能来自本地上传 / MinIO / storage_connection;首版聚焦一种来源(对照管线图选最贴近的),其余后续。

## 验证(成功标准)
- **端到端**:导入 `third-party/SUSTechPOINTS/data/example` → 每帧一个 Task,link 含 1 primary_lidar + 3 camera,各相机 DatasetItem.metadata_ 有 `calibration`,值与源 JSON 一致。
- `SensorCalibration` round-trip;非法长度(extrinsic≠16 / intrinsic≠9)被拒。
- 无 calib 的 scene:Task + link 照建,metadata 无 calibration,不报错。
- 缺帧 scene:该帧只 link 存在传感器。
- `task.dataset_item_id` = primary_lidar,且 `get_linked_items` 返回全部关联。
- OpenAPI snapshot 经 pre-commit 重生(`SensorCalibration` 进 DatasetItem schema),前端 codegen 同步。
- `uv run pytest`(含新端到端导入测试,用夹具)/ `uvx ruff check` / `pnpm lint`。
