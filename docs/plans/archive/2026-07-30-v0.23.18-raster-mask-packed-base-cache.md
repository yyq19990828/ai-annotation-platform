> Status: Released · default-off candidate · 2026-07-30
>
> 父计划：[v0.23.17 Raster Mask WebGPU packed 输入与 XOR 回读优化](2026-07-30-v0.23.17-raster-mask-webgpu-packed-xor-pipeline.md)

>
> 固定基线：`710c3249`（v0.23.17 封版提交）

## 1. 本版结论

v0.23.18 继续优化默认关闭的 Raster Mask WebGPU `square dilate` 候选，但优化对象不再是 shader。
v0.23.17 已把 GPU 成功链路从约 `167–269 ms` 降到约 `38–61 ms`；最新分段数据同时证明，GPU
upload / submit / pass / readback 只占约 `4–7 ms`，Worker 每次从 column-major RLE 重建 packed ROI
的 prepare 已占 `17–29 ms`，成为第一瓶颈。

冻结方向如下：

1. **建立 Worker 内、按 session 隔离、按 tile 惰性填充的 immutable packed base cache。** cache 只表示
   注册时的 canonical base RLE，不表示当前编辑真值。
2. **ROI source 改为 word-oriented assemble。** 命中 tile cache 时按 32-bit span 拷入 row-aligned
   scratch；dirty overrides 仍由本次请求声明，并以 overwrite 语义覆盖 base。
3. **缓存必须有独立硬上限并计入 compute ledger。** 多 session 共用 owner Worker 的全局 LRU；不能因
   8K / 16K mask 或频繁切题无界增长。
4. **cache 是加速层，不是正确性依赖。** miss、预算不足、Worker replacement 或 cache 丢失时可重新从
   immutable RLE 填充；若当次无法接纳 cache，则继续走 v0.23.17 direct-RLE packed prepare，不降级为
   dense CPU，也不改变 store/history 合同。
5. **本版不维护 mutable current shadow。** `sourceRevision`、dirty tile revision、undo / redo 与保存真值
   仍由主线程 `SparseMaskTileStore` 持有；Worker 不猜测“未出现在请求中的 dirty tile”状态。
6. **本版不做 GPU-resident source。** 当前 upload / submit p95 仅 `0.2–0.6 ms`，即使完全消除也不足以
   支撑一版复杂的 revision replay、partial `queue.writeBuffer()` 与 device-lost 重建协议。
7. **本版不做 GPU atomic compaction。** XOR patch build 已是第二瓶颈，但应先消除 prepare 主瓶颈并
   重新测量；compact records、overflow 与 dense XOR 二次回读另立后续版本。
8. **默认 gate 继续关闭。** 本版只改善已验证 Linux/NVIDIA 强制 Vulkan 路径，不替代 macOS、Wayland、
   Windows 无 flag 资格矩阵。

## 2. 为什么是 cache，而不是继续调 WebGPU

### 2.1 v0.23.17 固定证据

环境：Linux X11、Chrome `150.0.7871.114`、RTX 3090、driver `595.84`、有头 Chrome、强制 Vulkan。
每轮 `3 warmup + 10 iterations`，production store / pool / Worker / provider / history / save 全链路。

| ROI       | round | candidate p95 | packed prepare p95 | GPU wall p95 | patch build p95 | upload / submit p95 | readback p95 |
| --------- | ----: | ------------: | -----------------: | -----------: | --------------: | ------------------: | -----------: |
| 2048²     |     1 |       37.7 ms |            16.9 ms |       4.8 ms |         10.3 ms |              0.3 ms |       4.4 ms |
| 2048²     |     2 |       40.9 ms |            17.6 ms |       4.0 ms |         10.2 ms |              0.2 ms |       3.9 ms |
| 3840×2160 |     1 |       61.4 ms |            28.8 ms |       6.5 ms |         15.6 ms |              0.5 ms |       6.0 ms |
| 3840×2160 |     2 |       57.0 ms |            27.4 ms |       6.0 ms |         15.3 ms |              0.6 ms |       5.4 ms |

由此可得：

- packed prepare 占总 p95 的约 `43%–51%`；
- patch build 占约 `25%–27%`；
- upload / submit 低于总 p95 的 `1.1%`；
- GPU pass 与 readback 已不是第一优化对象；
- 继续微调 workgroup 或建立 GPU-resident source，都无法解释一版应有的端到端收益。

### 2.2 当前 prepare 为什么仍是 O(N)

v0.23.17 每次请求都会：

```text
for each input column
  binary-search RLE run index
  walk column runs
  for each foreground pixel
    set one bit in row-aligned sourceWords
for each dirty override
  for each covered pixel
    set / clear one target bit
```

即使同一 viewport 连续执行相同尺寸操作，immutable base 的 RLE → row-major packed 转换也会完整重复。
GPU buffer 已持久化，但 CPU/Worker 侧 packed base 没有复用。

### 2.3 选项比较

| 方案                             | 可消除的瓶颈                          | 正确性 / 生命周期成本                              | 本版结论     |
| -------------------------------- | ------------------------------------- | -------------------------------------------------- | ------------ |
| immutable packed base tile cache | 重复 RLE scan 与逐 foreground bit set | 低；base 由 sha256 固定，可随时重建                | **采用**     |
| full-image packed base plane     | 同上，assemble 更简单                 | 大图首用冷启动与常驻字节不可控                     | 拒绝         |
| mutable current packed shadow    | base assemble 与部分 dirty overlay    | 高；revision、undo/redo、stale、replacement replay | 拒绝         |
| GPU-resident current source      | JS assemble 与 upload                 | 很高；收益上限当前不足 1 ms                        | 拒绝         |
| shader workgroup / subgroup 调优 | GPU pass                              | 当前 GPU wall 仅 4–7 ms，跨设备风险较高            | 推迟         |
| GPU sparse XOR compaction        | readback 与 patch scan                | 需要 atomic records、overflow 与 dense fallback    | 下一测量阶段 |
| 多 Worker / SharedArrayBuffer    | prepare 并行                          | COOP/COEP 与复制、调度复杂度高                     | 拒绝         |

## 3. 目的与成功定义

### 3.1 本版目的

把 warm / overlap ROI 的成功 GPU 路径从：

```text
immutable column-major RLE
  → 每次 direct packed scan
  → dirty override per-pixel overlay
  → queue.writeBuffer
  → GPU XOR
  → CPU patch build
```

收敛为：

```text
immutable column-major RLE
  → lazy 512² row-aligned packed base tiles（跨请求复用）
  → word-oriented ROI assemble 到复用 scratch
  → dirty override masked overwrite
  → queue.writeBuffer
  → GPU XOR
  → CPU patch build
```

### 3.2 完成条件

本版只有同时满足以下条件才算完成：

1. 同 session 同 tile 的 immutable base 在未被 LRU 淘汰前只从 RLE 解码一次。
2. cache tile、assembled ROI 与 v0.23.17 direct packed source 对任意合法 rect、edge tile、非 32 对齐
   origin / width、空/满 RLE 和 dirty set/clear 都 bit-exact。
3. dirty override 仍由每次请求的显式列表决定；缓存中存在旧 revision 不得让未声明 tile 覆盖 base。
4. cache 不成为第二份 mutable current truth，不新增 commit/ack/replay 协议。
5. cache retained bytes、source scratch、request output 与 GPU allocated bytes 均有可解释账本；任何时刻不
   超过本请求 compute budget，session release / Worker replacement / dispose 后归零。
6. cache admission 失败时仍可使用 v0.23.17 direct packed prepare + WebGPU；不得仅因 cache miss 回退 CPU。
7. warm same-ROI packed prepare p95 相对 v0.23.17 至少改善 60%，两轮任一轮不得低于 50%。
8. 2048² 与 4K warm 端到端 candidate p95 相对 v0.23.17 至少改善 20%，任一轮不得低于 15%。
9. cold first-use 使用同 candidate、同 bundle、只通过预算绕过 cache 的 direct-RLE control，wall time 不得
   恶化超过 10%；50% overlap pan 不得退化成全量 miss。
10. gate-off、adapter unavailable、cache disabled / exhausted、GPU runtime failure 的 exact fallback 与 p95
    不得明显回归；successful GPU 仍保持 `inputAlphaBytes = 0`。
11. 主线程 Long Task 为 0，GPU owner <= 1，cache / scratch / GPU 容量进入 plateau。
12. 默认构建继续零 provider chunk、零 shader、零 `requestAdapter()`。

## 4. 范围与非目标

### 4.1 本版范围

- Worker session 增加 immutable packed base tile cache；
- 512×512 canonical tile layout与 edge tile tail 规则；
- word-oriented base assemble 与 dirty overwrite；
- source scratch 的有界复用；
- 全局 LRU、逐 session purge、精确字节账本；
- direct-RLE cache bypass；
- cache hit/miss/fill/evict/assemble/overlay 分段指标；
- same-ROI、overlap pan、disjoint ROI、dirty churn 与 eviction production A/B；
- runtime、Worker、pool、store、history/save、real GPU 测试与文档。

### 4.2 明确非目标

- 不新增 erode、open、close、disk kernel；
- 不扩大 `square dilate` 的现有 radius 上限；
- 不将 gate 默认开启；
- 不创建 full-image dense alpha 或 full-image packed plane；
- 不持久化 mutable current mask；
- 不省略请求中的 dirty override manifest；
- 不把主线程 tile cache 的 `baseBits/currentBits` 直接转交 Worker 所有权；
- 不新增 SharedArrayBuffer / COOP / COEP 部署要求；

- 不实现 GPU sparse record compaction、atomic count/bounds、readback ring；
- 不用 timestamp-query 作为产品依赖；
- 不顺带处理 WebCodecs、Konva 合成或服务端 GPU。

## 5. 目标架构

### 5.1 session 与 cache 所有权

```text
SparseMaskTileStore（mutable current truth）
  ├─ sourceRevision / mutationGeneration
  ├─ dirty tile currentBits + tile revision
  └─ history / undo / redo / save
          │ 每次请求显式 dirtyOverrides
          ▼
RasterMask Worker owner slot 0
  ├─ Session RLE（immutable canonical base）
  ├─ PackedBaseTileCache（immutable、可丢、LRU）
  ├─ PackedSourceScratch（单作业复用）
  └─ WebGPU provider（单 owner、持久 buffers）
```

cache 不是主线程 store 的镜像：

- cache key 只由 `sessionId + sha256 + tileX + tileY` 决定；
- cache value 只来自该 session 注册时 RLE；
- `sourceRevision` 不进入 base cache key；
- dirty override 只在当次 scratch 上覆盖，绝不写回 base cache；
- session release 后对应 entries 必须同步删除；
- Worker replacement 只 replay RLE，cache 从空开始，结果仍正确。

### 5.2 成功 warm 路径

```text
validate request
  → WebGPU route + provider preflight
  → cache budget admission
  → lookup intersecting base tiles
      ├─ hit: reuse immutable packed tile
      └─ miss: decode tile from session RLE, admit or use transiently
  → assemble base spans into row-aligned source scratch
  → overwrite listed dirty tile spans
  → clear every output row tail bits
  → WebGPU square dilate + core XOR
  → existing XOR word patch builder
  → store validates and atomically applies patches
```

### 5.3 cache bypass 路径

```text
provider ready
  → cache cap = 0 / admission impossible / cache invariant failure
  → v0.23.17 preparePackedRasterMaskMorphologyRoi()
  → WebGPU + XOR patch
```

`cache bypass` 是 prepare 策略，不是 morphology backend fallback。response 仍为 `backend: webgpu`，并通过
metrics 记录 `prepareStrategy: direct-rle`；只有 provider / GPU 本身失败才进入既有 CPU 路径。

## 6. packed base tile 合同

### 6.1 canonical tile

复用 `MASK_HISTORY_TILE_SIZE = 512`：

```ts
interface RasterMaskPackedBaseTile {
  tileX: number;
  tileY: number;
  x: number;
  y: number;
  width: number;
  height: number;
  wordsPerRow: number; // ceil(width / 32)
  words: Uint32Array; // row-major, row-aligned
  byteSize: number;
  lastUsedSequence: number;
}
```

约束：

- `words.length === wordsPerRow * height`；
- word 内 bit `n` 表示该 row 的 `x = wordX * 32 + n`；
- edge tile 每行最后 word 的无效尾位必须为 0；
- tile rect 必须与 session 512 网格完全一致；
- cache value 创建后只读，不允许 dirty overlay 原地修改。

### 6.2 RLE → tile fill

允许复用现有 `runIndexAt()` 与 column-major RLE 语义，但 fill 单元从整个 ROI 改为 canonical tile：

1. 校验 tile rect；
2. 为每个 local x 找到 RLE 起始 run；
3. 只遍历 tile y span；
4. foreground run 直接写入 row-aligned tile words；
5. 清理 row tail；
6. 在 admission 成功后才发布到 cache map。

创建失败或取消不得留下半初始化 entry。

### 6.3 不采用 full-image plane

即使 8K packed plane 约 8 MiB，full-image eager cache 仍会：

- 首次只编辑小 viewport 时扫描整图；
- 多 session 时按图片面积而非工作集增长；
- 让 16K/超长边 mask 冷启动不可预测；
- 与现有 sparse viewport 策略相冲突。

因此只缓存真正与 production ROI 相交的 512 tile。

## 7. ROI word assemble

### 7.1 source scratch

owner Worker 同时最多执行一个 morphology 作业，可持有一个 grow-only `Uint32Array` scratch：

- logical length 为 `ceil(input.width / 32) * input.height`；
- capacity 只按已成功 admission 的最大请求增长；
- 每次仅清零 logical span；
- provider 只接收 logical `subarray()`；
- scratch 不转移、不写回 session；
- reset provider 不必释放 scratch，release last session / Worker terminate 必须释放；
- scratch capacity 计入 compute ledger 和资源快照。

如果 grow 后会超过 budget，则本次使用 exact-sized transient source，或沿 direct-RLE 路径；不得先扩大后
再宣告预算不足。

### 7.2 base span copy

输入 origin 不保证 32 对齐，tile 边界也不保证与 source word 对齐。实现统一 bit-span copy helper：

```text
copyPackedSpan(
  sourceWords, sourceWordsPerRow, sourceBitOffset,
  targetWords, targetWordsPerRow, targetBitOffset,
  bitLength,
  mode = overwrite
)
```

要求：

- 支持 source / target offset `0..31` 任意组合；
- 读取相邻 source word 进行 shift/or；
- 首尾 word 使用 mask，不写出 span；
- 不逐 pixel 循环；
- 同一 base tile span 对 target 使用 overwrite；target 预先为 0，tile 之间不得重叠；
- 1/31/32/33、511/512、edge width 与跨 tile row 必须 golden exact。

### 7.3 dirty overwrite

dirty override 的 `bits` 是 tile 内连续 row-major bitset，语义是 current tile 的完整值，不是 XOR delta。
因此 overlay 必须同时能 set 与 clear：

```text
target = (target & ~spanMask) | (dirtyBits & spanMask)
```

禁止使用 OR-only merge。每个请求仍执行：

- duplicate tile 拒绝；
- tile rect、byte length、tail bits、revision 校验；
- 只应用与 input 相交部分；
- 未出现在请求列表的 cache entry 不参与 current truth；
- overlay 完成后再次清理 source row tail。

本版可以按 tile revision 缓存“格式转换结果”，但不得让该缓存取代本次 manifest；若收益未被分段指标证明，
不增加 revision cache。

## 8. cache 预算与 LRU

### 8.1 两层硬限制

新增 cache cap：

```text
packedBaseCacheCap = min(32 MiB, floor(computeBudgetBytes * 0.25))
```

候选初值：

| compute budget | packed base cache cap | 512² tile capacity |
| -------------: | --------------------: | -----------------: |
|         64 MiB |                16 MiB |          512 tiles |
|        128 MiB |                32 MiB |         1024 tiles |

单个标准 512² packed tile 为 32 KiB。上表只是理论 entry 数；实际 admission 还必须满足总 compute ledger。

### 8.2 总 compute ledger

每次 route-before-materialize 必须估算：

```text
retained packed base cache bytes
+ prospective source scratch capacity bytes
+ logical packed source bytes
+ logical XOR result bytes
+ GPU source / XOR / readback / params allocated bytes
<= computeBudgetBytes
```

其中：

- 已有 RLE counts/runEnds 是 session 基础结构，不因本版重复计费；
- cache miss 临时 tile 在发布前计入 prospective bytes；
- 同一 ArrayBuffer 不得重复计费；
- transient tile 用完即释放，不进入 retained cache；
- response transfer 后的 XOR result 仍按当次 live bytes 计费；
- 预算判断必须在分配大对象前完成。

### 8.3 全局 LRU

owner Worker 的多个 session 共享一个 LRU ledger：

- key 包含 session identity；
- hit 更新单调 `lastUsedSequence`；
- admission 先淘汰非本次 working-set tile；
- 本次 ROI 所需 tile 在 assemble 完成前 pinned；
- session release 优先 purge 该 session 的全部 entries；
- last session release 清空 cache 与 scratch；
- replacement/terminate 依赖进程释放，但 snapshot 必须在主线程归零；
- 不用定时器或后台预热制造额外工作。

## 9. 路由、失败与原子性

### 9.1 路由顺序

```text
validate request
  → gate / operation / pixel threshold / profile budget
  → provider state + exact GPU preflight
  → packed cache / scratch admission
  → cached or direct packed prepare
  → GPU run
  → XOR patch build
  → response
```

cache 初始化不得发生在 gate off、unsupported、below threshold、adapter unavailable 或 GPU budget reject 的
请求上，避免 CPU fallback 请求偷偷建立缓存。

### 9.2 失败分类

- cache miss：正常事件，不是 fallback；
- cache cap exhausted：evict 或 direct-RLE bypass；
- cache invariant failure：丢弃相关 entry，direct-RLE 重建；重复失败才让该请求报错；
- provider initializing/unavailable：既有 CPU 路径，cache 不启动；
- GPU runtime failure：惰性 dense CPU fallback；base cache 可保留，因为与 device 无关；
- Worker cancel/timeout：替换 Worker，session RLE replay，cache 从空开始；
- session stale/sha mismatch：拒绝，不读取其它 session cache。

### 9.3 store 原子性不变

cache 与 scratch 全部位于 Worker 内。主线程仍在 response 返回后验证：

- session / sha / sourceRevision；
- mutationGeneration 与 tile revisions；
- patch 唯一性、维度、core bounds、tail；
- changed pixels / bounds；
- history command changed count。

任何 cache 错误、取消或 stale response 都不得产生部分 store 写入。

## 10. 可观测性

### 10.1 response metrics

在 v0.23.17 metrics 基础上增加最小决策字段：

```ts
prepareStrategy: "packed-cache" | "direct-rle" | "dense-cpu";
baseCacheFillMs: number;
packedAssembleMs: number;
dirtyOverlayMs: number;
baseCacheHitTiles: number;
baseCacheMissTiles: number;
baseCacheEvictedTiles: number;
baseCacheRetainedBytes: number;
sourceScratchCapacityBytes: number;
```

保留：

- `backendPrepareMs` 作为 fill + assemble + overlay 总和；
- `computeMs`、`diffOrPatchMs`；
- upload / submit、readback、optional GPU pass；
- input alpha、packed source、XOR readback、GPU 三类 capacity；
- fallback materialize。

不保留含义重叠的 `cacheMs` 或旧字段别名。

### 10.2 pool / diagnostics counters

新增累计与峰值：

- cache prepared jobs / direct-RLE prepared jobs；
- hit / miss / eviction tiles；
- peak retained cache bytes；
- peak source scratch bytes；
- cache invariant rebuilds；
- session purge count。

snapshot clone 必须深拷 metrics；dispose 后 live bytes 为 0，历史累计 counters 可保留到 pool dispose 前。

### 10.3 benchmark raw samples

每个 iteration 输出原始：

- cold / warm / overlap / disjoint 分类；
- total、prepare、fill、assemble、overlay、GPU、patch；
- hit/miss/evict tiles；
- cache/scratch/GPU bytes；
- exact patch/save checksum；
- owner、session、Worker、Long Task 与 dispose snapshot。

聚合报告不能只留 p95，必须保留 raw sample 供退化分析。

## 11. 实施阶段

- 指标和总时间在误差范围内闭合；
- 证明 prepare 的 RLE scan 或 dirty overlay 真实占比；
- 不改变结果与 backend route。

### M1 — immutable packed base tile

交付：

- canonical 512 tile fill；
- row tail 归零；
- session identity / rect validation；
- runtime golden 覆盖空、满、稀疏、edge 与非对齐。

退出门：

- cached tile 与 dense/direct packed exact；
- entry 创建失败不发布；
- 无 production full-image plane。

### M2 — word-oriented ROI assemble

交付：

- bit-span copy helper；
- source scratch；
- dirty masked overwrite；
- cache/direct strategy response metrics。

退出门：

- arbitrary alignment 与跨 tile exact；
- dirty set/clear exact；
- successful GPU alpha bytes 保持 0；

### M3 — LRU、预算与恢复

- cap - 1 byte 边界 exact；

### M4 — production real GPU A/B

交付：

- warm prepare 与端到端性能门通过；
- cold / fallback / resources 门通过；

## 16. 风险与缓解

| 风险                              | 后果                                | 缓解                                                |
| --------------------------------- | ----------------------------------- | --------------------------------------------------- |
| cache 被误作 current truth        | undo/redo 或 dirty clear 后结果错误 | 只缓存 immutable base；每请求 manifest 决定 overlay |
| input / tile 非 32 对齐           | 串位、越界 patch                    | 统一 bit-span helper + 边界 golden                  |
| dirty overlay 使用 OR             | 无法清除 base 前景                  | masked overwrite，set/clear 双向测试                |
| cold fill 比 direct RLE 更慢      | 首次操作尾延迟恶化                  | cold 独立门；必要时按策略 direct bypass             |
| 多 session cache 无界             | 长会话内存增长                      | global hard cap + LRU + per-session purge           |
| working set 被自身淘汰            | thrash、性能抖动                    | assemble 期间 pin intersecting tiles                |
| scratch grow 后预算才失败         | 短时越界                            | prospective admission 先于分配                      |
| cache invariant failure 静默污染  | GPU exact 失败                      | entry 发布前校验；失败丢弃并 direct 重建            |
| cache 提升后 patch 成主瓶颈       | 总收益低于预期                      | 端到端退出门；下一版再评估 sparse XOR compaction    |
| 为省 0.5 ms 建 GPU current shadow | 协议复杂度远高于收益                | 本版明确拒绝 GPU-resident source                    |
| Linux 单机结果外推                | 错误默认开启                        | release 与 default-enable 门分离                    |

### 18.3 封版补证

1. benchmark 支持显式 candidate compute budget，并在 `3 MiB` 下只准入 dense WebGPU buffers、稳定绕过
   cache。相同 v0.23.18 candidate 与 Chrome 150 的 direct-RLE cold control 为 `128.5 / 134.7 ms`，packed
   cache cold 为 `130.4 / 138.1 ms`，total 只回归 `1.5% / 2.5%`；prepare 为 `13.0 → 13.4 ms` 与
   `11.7 → 9.8 ms`。跨 dev server 重放 v0.23.17 的 cold wall 受 Vite 首次编译与调度影响明显，因此封版门
   采用同 bundle、同 provider、只改变 cache admission 的 paired control。
2. Linux default X11、Chrome 150、无 unsafe Vulkan 时 provider 稳定为 `adapter-unavailable`；operation
   返回 exact CPU patch，save / reload checksum 一致，GPU/cache/scratch bytes 为 0。
3. gate off 即使 unsafe Vulkan 可用，也保持 `initAttempts=0`、GPU/cache/scratch bytes 为 0，patch、save、
   reload exact。
4. cache budget bypass 保持 `backend=webgpu`、`prepareStrategy=direct-rle`，两轮 cache/scratch bytes 为 0，
   Long Task 为 0，dispose 后全部归零；provider injected write failure 单测保持 `gpu-runtime-failed`，不误记
   device lost，并销毁全部 buffers。
5. release runner 在 2048² / 4K、gate off、adapter unavailable 与 cache bypass 中都将 merge 后 RLE 重新注册
   为新 session，reload checksum 与 save checksum exact。
6. macOS / Wayland / Windows 无 flag 继续明确 not tested，因此 gate 不默认开启。下一阶段只由新分段触发：
   patch build p95 已约 `10–16 ms`，高于 warm prepare 与 GPU wall。

## 19. 后续版本触发条件

v0.23.18 只处理 prepare。封版后按新的 stage 占比选择后续：

1. **patch build + readback 成为第一瓶颈**：规划 v0.23.19 GPU sparse XOR record compaction；同一 pass
   用 bounded atomic append 输出 `(wordIndex, xorWord)`，必须设计 capacity、overflow、stable ordering 与
   dense XOR exact fallback。
2. **ROI assemble 仍是第一瓶颈**：先检查 word copy、dirty span 与 cache miss，不直接跳到 GPU current
   shadow；只有 upload 与 assemble 合计占比足够大，才设计 revisioned GPU source。
3. **GPU pass 成为第一瓶颈**：再做 workgroup、两段 separable morphology、subgroup 的跨平台 A/B。
4. **cache cold fill 成为产品痛点**：评估受 viewport 驱动的 idle prefetch，但必须有取消、预算和零后台
   thrash 证据，不默认预热整图。
5. **跨平台无 flag 矩阵通过**：另立 default-enable 决策，不在性能版本中翻转 gate。
6. **更多 kernel 有真实生产需求**：逐 kernel 建 exact golden、crossover 与 fallback，不批量移植。

任何后续项都必须由 v0.23.18 raw stage 数据触发，不能因“WebGPU 能做”而预先实现。
