# [SDK] Python SDK / CLI / TUI 能力追平与独立版本计划

> Status: implemented
>
> 规划日期：2026-08-14
>
> 证据基线：AAP OpenAPI `0.23.32`；Python 包元数据 `0.15.17`；运行时
> `ai_annotation.__version__` `0.15.16`；SDK 测试 `150 passed`；锁定的 Textual `8.2.7`
> 下 TUI 专项 `33 passed`，声明下限 Textual `0.80.1` 下为 `30 passed, 3 failed`。

## 1. 结论

本 Epic 不追求把全部 Web API 机械复制进 Python，而是让 SDK / CLI 覆盖稳定、可自动化、可在无
浏览器环境中闭环的生产工作流，并把 TUI 从固定条数的监控页升级为可扩展的终端运维台。交付拆成
五个可独立合并、测试和发版的 SDK minor release：

1. `0.16.0`：先修复版本来源、OpenAPI 契约守卫和能力盘点机制。
2. `0.17.0`：补齐项目、数据集、成员和批次的资源管理写能力。
3. `0.18.0`：补齐批次流转、任务生命周期、审核、批量标注和失败任务重试。
4. `0.19.0`：补齐模型实例、服务池、健康检查、项目 enablement 与运维拓扑。
5. `0.20.0`：优化 TUI 加载、分页、过滤、错误反馈和窄终端布局，补齐数据集/批次下钻、失败任务
   重试、个人绩效和项目服务池视图。

SDK、随包 CLI 与 `[tui]` extra 共用一个发行物和一个 SemVer；不再复制 AAP 主仓库版本。可安装版本始终保持
PEP 440 兼容的 `X.Y.Z`，AAP 对账基线作为独立元数据记录。以当前证据基线发布时：

```text
Python package version: 0.16.0
AAP target version:     0.23.32
CLI display:            aap 0.16.0@AAP0.23.32
Git tag:                sdk-v0.16.0
```

`@AAP0.23.32` 只用于人类可读标签，不进入 `project.version`。PEP 440 中 `@` 用于 direct reference，
而 local version 形式 `+aap.0.23.32` 也不适合作为公共索引上的上游版本，因此不把两种版本压进一个
安装版本：

- [PyPA Version specifiers](https://packaging.python.org/en/latest/specifications/version-specifiers/)
- [Setuptools dynamic metadata](https://setuptools.pypa.io/en/latest/userguide/pyproject_config.html#dynamic-metadata)

## 2. 审计结果

### 2.1 已有能力

当前实现是一个同步、手写、薄封装客户端，核心依赖仅为 `httpx` 与 `pydantic`；CLI 使用已经安装的
`typer` 与 `rich`，TUI 使用可选 extra。TUI 已有 Projects / Datasets / Jobs / ML Backends / 看板 /
绩效六个主视图、项目详情五个子视图、导出/取消动作和 Backend WebSocket 实时曲线，并非需要重写的
MVP。已有 SDK 命名空间如下：

```text
Client
├── projects       ├── datasets       ├── tasks
├── annotations    ├── predictions    ├── jobs
├── exports        ├── ml_backends    ├── batches
├── members        ├── dashboard      ├── api_keys
└── me()
```

CLI 已覆盖登录、项目列表/创建、数据集创建/上传/关联、预测导入、异步任务等待/取消、项目导出、
模型后端查询、批次/成员查询、个人信息、统计和 dashboard。`--json` 已形成 stdout JSON、stderr 错误和
非零退出码的基础约定；新增命令应复用该约定。

### 2.2 已确认的缺口

| 缺口                 | 仓库证据                                                              | 影响                                              |
| -------------------- | --------------------------------------------------------------------- | ------------------------------------------------- |
| 版本来源漂移         | `pyproject.toml` / `uv.lock` 为 `0.15.17`，`__init__.py` 为 `0.15.16` | `aap --version` 与安装元数据不一致                |
| AAP 基线不可查询     | 包内没有独立 target metadata                                          | 无法回答某一 SDK release 对账到哪个 AAP           |
| 契约清单漏报         | `client.py` 有 39 个 HTTP 调用，`USED_ENDPOINTS` 只有 29 项           | 当前测试绿灯不能证明所有已用端点仍存在            |
| 新端点无提醒         | contract test 只检查手写清单，不检查稳定 API 新增                     | AAP 迭代时 SDK 影响不可见                         |
| 核心写流程缺失       | 多数 projects / datasets / batches / tasks 方法仍为只读               | 自动化脚本需要绕过 SDK 直接请求 API               |
| 模型运维边界缺失     | 已有项目后端查询，但没有 registry / service pool / enablement         | 无法通过 SDK 管理当前模型服务拓扑                 |
| 文档滞后             | quickstart 与包 README 仍描述早期的八类工作流                         | 已有 batches / members / dashboard 等能力不可发现 |
| 独立发版链路不完整   | CI 仅执行 SDK pytest，仓库内未发现 SDK publish workflow               | 版本可构建但没有经验证的发布门                    |
| TUI 启动请求过重     | 挂载时并发加载全部主视图；ML 总览先拉项目再逐项目请求                 | 有 P 个项目时启动至少 P+6 次请求                  |
| TUI 列表会静默截断   | datasets 固定 100、jobs 固定 50；项目 jobs 拉全局 100 条后客户端过滤  | 大实例看不到完整结果，也不知道还有下一页          |
| TUI 错误与新鲜度混淆 | 只有全局刷新时间；项目详情 `_safe_list` 把异常变成空列表              | 403/网络错误表现为“空数据”，后台刷新覆盖前台错误  |
| TUI 无查询和窄屏门   | 没有 search/filter/page；图表固定宽 64，测试只覆盖 100/120 列         | SSH 小终端与大数据量下可用性下降                  |
| TUI 依赖范围失真     | extras 声明 `textual>=0.80`，锁文件为 `8.2.7`；下限专项测试 3 项失败  | 安装元数据声称支持实际未通过的版本                |


### 2.3 问题根因

SDK / CLI / TUI 的能力差距不是单个方法遗漏，而是缺少四个稳定闭环：

```text
AAP routers ──> openapi.snapshot.json ──> 端点契约 + 能力分类守卫
    │                                             │
    └────────────────> SDK public methods ──┬──> CLI commands
                                            └──> optional TUI
                                                   ├── per-view state
                                                   └── Textual widgets / workers

_version.py ──> Python package metadata
       ├──────> Python runtime constants
       └──────> aap --version
```

当前第一条链路依赖人工维护的不完整元组，第二条链路只覆盖最早期工作流，版本链路有两个手写来源，
TUI 又把所有视图的加载/错误压进一个全局状态栏。计划先修复共享根因，再增加领域方法和 TUI 消费面，
避免每次 AAP 发版继续靠人工记忆对账。

## 3. 目标、成功标准与非目标

### 3.1 目标

- SDK / CLI / TUI 独立于 AAP 使用同一 SemVer，并能从 Python 与 CLI 查询已验证的 AAP target。
- 所有 SDK 实际 HTTP 调用都被当前 OpenAPI 快照验证，不能再由手写清单漏掉。
- SDK 关心的 API tag 中，每个 operation 都有 `covered`、`planned` 或 `excluded` 分类；AAP 新增稳定
  operation 时 CI 明确报出未分类项。
- 补齐资源管理、标注生产流和模型运维三类可脚本化闭环。
- CLI 只通过 SDK 公共方法发请求；所有新增写命令都有 `--json`、确定退出码和破坏性操作确认。
- TUI 只通过 SDK 公共方法加载数据，以按需加载、服务端分页/过滤和逐视图错误态适应大实例；只增加
  与监控直接相邻的 retry 动作，不复制 Web 的资源编辑表单。
- 每个 release 都有独立 changelog、构建产物、测试结果和 `sdk-vX.Y.Z` tag 规则。

### 3.2 验收标准

1. `importlib.metadata.version("ai-annotation-sdk")` 与 `ai_annotation.__version__` 完全相同。
2. `ai_annotation.__aap_target_version__` 等于该 release 验收所用
   `apps/api/openapi.snapshot.json.info.version`。
3. `aap --version` 输出 `aap X.Y.Z@AAPX.Y.Z`，且测试不再写死第二份 SDK 版本。
4. contract test 自动抽取 `client.py` 的每一个 HTTP method/path 并在 OpenAPI 中找到匹配 operation。
5. 受监控 tag 出现未分类 operation 时 `python-sdk-pytest` 失败并打印 method/path。
6. 每个新增 SDK 方法至少覆盖成功响应与一个服务端错误映射；破坏性 CLI 命令还覆盖无 `--yes` 拒绝
   和带 `--yes --json` 成功两条路径。
7. `uv run --extra test pytest -q`、`uv build` 和 docs build 全部通过。
8. TUI 初始挂载只请求 Projects、Jobs 与当前主体；其余主视图首次激活才加载。任一视图失败时保留
   最近成功数据并在该视图显示错误，不再伪装成空列表。
9. Datasets / Jobs / 项目 Jobs 能前后翻页并显示 `当前范围 / total`；查询条件透传 SDK，而不是只过滤
   当前截断页。
10. TUI 在 `80x24` 和 `120x32` Pilot 尺寸下均可完成主 tab、详情、modal、返回和键盘动作。
11. 五个 phase 均可单独合并与发版；后一个 phase 不影响前一个 release 的使用。

### 3.3 非目标

- 不生成全量 OpenAPI Client，也不替换现有手写 `Client`。
- 不为每个 Web 页面、工作台内部请求或后台维护端点提供 CLI。
- 不把 SDK、CLI、TUI 拆成多个 Python distribution；它们仍共享版本和发布物。
- TUI 不提供项目/数据集 CRUD、标注绘制、审核表单、服务池成员变更或 capability drift accept；这些
  高密度或高风险操作留在 Web / CLI。TUI 仍是可整体移除的 `[tui]` extra。
- 不修改 AAP API、数据库、环境变量或权限规则；SDK 原样暴露服务端的 401/403/409/422。
- 不在本 Epic 建 PyPI trusted publisher。仓库当前没有可验证的发布凭据/绑定，先完成可重复构建与 tag
  约定；确定发布账户后另立短计划接入。
- 不承诺一个 SDK release 与所有更早/更晚 AAP 版本兼容；target 仅表示该版本完成过验收的基线。

## 4. 版本与发布规则

### 4.1 单一来源

新增 `packages/python-sdk/src/ai_annotation/_version.py`，只保存静态字面量：

```python
__version__ = "0.16.0"
__aap_target_version__ = "0.23.32"
```

- `pyproject.toml` 改用 setuptools dynamic version，读取
  `ai_annotation._version.__version__`。
- `ai_annotation.__init__` re-export 两个常量。
- CLI 从这两个常量拼出显示标签，不增加第三个版本常量。
- `uv.lock` 只通过 `uv lock` 生成，不手改。
- 新增 `packages/python-sdk/CHANGELOG.md`，作为 SDK / CLI / TUI 的 release history；版本真值仍是
  `_version.py`，避免再把 changelog 变成运行时解析源。

如果实施 phase 1 时主分支 OpenAPI 已不是 `0.23.32`，实施者必须先读取 snapshot 的
`info.version`，将那个确切值写入 `__aap_target_version__` 并更新本计划证据基线。后续 phase 同理：
每次 release 在代码冻结后记录当时实际跑过测试的 snapshot 版本，而不是预估未来 AAP 版本。

### 4.2 SemVer 规则

- SDK 公共方法、命令或模型新增：minor bump。
- 向后兼容的错误修复、文档或宽松模型字段修复：patch bump。
- 删除/重命名公共方法、改变默认行为或 JSON 输出结构：major bump；在 `1.0.0` 前表现为下一个 minor，
  同时至少提前一个 minor 提供 deprecation warning。
- AAP target 更新但 SDK 行为不变：只有在重新验收并确实需要发包时才 patch bump；AAP 每次发版不强制
  SDK 跟发。
- tag 使用 `sdk-vX.Y.Z`；AAP 主仓库继续使用自己的 `vX.Y.Z`，两者互不修改。
- 已发布版本和 tag 永不复用；回滚通过发布新的 patch 或安装上一个 SDK 版本完成。

### 4.3 Release checklist

```bash
cd packages/python-sdk
uv lock
uv run --extra test pytest -q
uv build
python -c 'import json; from pathlib import Path; print(json.loads(Path("../../apps/api/openapi.snapshot.json").read_text())["info"]["version"])'
```

然后确认：

- `_version.py` 的 target 与上一步输出相等；
- `packages/python-sdk/CHANGELOG.md` 已把 Unreleased 内容归入本次 SDK 版本；
- wheel 与 sdist 文件名只含标准 SDK 版本，不含 `@AAP`；
- 根 `CHANGELOG.md` 只记录对 AAP 用户/开发者可见的 SDK 能力变化，不承担 SDK 每次 patch 的流水账；
- 合并后创建 `sdk-vX.Y.Z`。没有经过发布账户确认时只保留构建产物与 tag，不假定已上传 PyPI。

## 5. OpenAPI 契约与能力台账

### 5.1 替换不完整的 `USED_ENDPOINTS`

删除 `_http.py` 中的手写 `USED_ENDPOINTS`。在 `test_openapi_contract.py` 使用 Python stdlib `ast`：

1. 扫描 `client.py` 中每个 `self._http.request` 调用的前两个参数（HTTP method 与 path）。
2. 支持字符串字面量和简单 f-string；将 f-string expression 归一化为 OpenAPI `{parameter}`。
3. 遇到动态拼接、变量 path 或无法静态解释的表达式直接让测试失败，要求调用点改回可审计写法。
4. 逐一断言 method/path 存在于当前 `openapi.snapshot.json`。

测试中保留一条边界说明：

```python
# ponytail: only literal/simple f-string paths; introduce Endpoint constants only if paths become dynamic.
```

不引入解析库、运行时代码生成或 `Endpoint` 抽象。现有路径都是字面量/简单 f-string，stdlib 足够；只有
将来真实出现动态 path 且无法保持可读性时才升级。

### 5.2 新增 `api-coverage.toml`

新增 `packages/python-sdk/api-coverage.toml`，使用 stdlib `tomllib` 读取。最小结构为：

```toml
snapshot = "0.23.32"
watched_tags = ["projects", "datasets", "batches", "tasks", "annotations", "async-jobs", "ml-backends", "admin-ml-integrations"]

[operations]
"GET /api/v1/projects" = { status = "covered" }
"PATCH /api/v1/projects/{project_id}" = { status = "planned", release = "0.17.0" }
"POST /api/v1/tasks/{task_id}/mask-content" = { status = "excluded", reason = "workbench-internal" }
```

守卫规则：

- 当前 OpenAPI 中这些 tag 的每个 operation 必须恰好出现一次。
- `covered` 集合必须包含 AST 自动抽取的所有 SDK 调用；SDK 新增方法时同一提交改为 `covered`。
- `planned` 必须带本计划中的 release；release 完成时不得残留该 release 的 `planned` 项。
- `excluded` 必须使用固定 reason：`workbench-internal`、`web-only`、`maintenance-risk`、
  `separate-connector-epic`、`no-external-demand`。
- OpenAPI 新增 operation 时先失败并打印 copy-ready 的 `METHOD path`；开发者只需分类，不强制立刻实现。
- `snapshot` 是上次完成台账对账的版本。它与 `_version.py` 的 target 在 release 时一致；日常 AAP 开发
  可以先分类新 operation，而不触发 SDK 发包。

首轮分类边界如下，实施时按此机械写入台账，不再临场决定产品范围：

| 领域                  | `planned`                                                                    | `excluded`                                                                    |
| --------------------- | ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| projects              | update/delete、member add/remove                                             | class usage/rename、orphan cleanup、pipeline apply、preannotate、transfer     |
| datasets              | update/delete、items、linked projects、preview unlink/unlink                 | backfill/scan/sniff/maintenance、connection import                            |
| batches               | create/update/delete、transition/reject/reset/distribute、指定 bulk、export  | admin lock/unlock、audit logs、split、unclassified count、bulk archive/delete |
| tasks                 | submit/skip/withdraw/reopen/accept-rejection、review claim/approve/reject    | workbench、锁、媒体、video、mask、AI/prediction 内部调用                      |
| annotations           | bulk-update                                                                  | mask content 与工作台分页内部接口                                             |
| async-jobs            | retry-failed                                                                 | 已有 list/get/cancel 保持 covered，无额外排除                                 |
| ml-backends           | available、instance/pool enablement、health                                  | 直接 predict、workbench predict、capability setup、warmup/reload              |
| admin-ml-integrations | registry CRUD/health/unload、service pool CRUD/member/drift/topology/runtime | GPU overview、observe/probe/smoke、runtime hints                              |

`data-manager`、notifications、audit 等 tag 本轮不加入 watched list：它们主要服务 Web 查询 DSL 或治理页面，
不属于已选择的自动化闭环。出现明确外部集成需求时先扩展 watched tag，再立独立 plan。

## 7. Phase 2 — SDK 0.17.0：资源管理写能力

### 7.1 Python 公共接口

复用现有 `Projects`、`Datasets`、`Members`、`Batches` 类和 `Page[T]`，不增加 service/repository 层。

## 9. Phase 4 — SDK 0.19.0：模型服务运维

### 9.1 边界

## 10. Phase 5 — SDK 0.20.0：TUI 终端运维台增强

### 10.1 定位与现状

TUI 继续定位为 SSH / 服务器环境中的监控与轻运维入口，而不是字符版 Web。现有 1,855 行
`tui/app.py` 已包含六个主视图、五个项目子视图、三个 modal、导出/取消、实时 WebSocket 曲线和
Textual worker 边界；816 行 Pilot 测试已覆盖主要导航和动作。Phase 5 在现有结构上做增量改造，不重写
导航、不引入状态管理框架，也不因为文件较长先做无用户收益的模块拆分。

当前启动请求模型是：

```text
mount
├── projects.list()
├── datasets.list(limit=100)
├── jobs.list(limit=50) ──> 后续每 3s
├── projects.list() + P × ml_backends.list(project_id)
├── projects.stats()
└── me() ──> super_admin 时立即 dashboard.people()
```

有 P 个项目时，初始挂载至少产生 P+6 次请求；用户没有打开 Datasets / ML / 看板 / 绩效也会付出成本。
项目详情又调用 `jobs.list(limit=100)` 后在客户端按 `project_id` 过滤，既过取数据，也会漏掉不在全局前
100 条内的本项目 job。`_safe_list` 把 batches/members 的 403、404 和网络错误都转为空列表，使“真的
没有数据”和“请求失败”不可区分。

### 10.2 按需加载与逐视图状态

挂载阶段只加载 Projects、Jobs 和 `me()`：

- Projects 是默认活动 tab，立即加载。
- Jobs 保持全局 3 秒轮询，确保用户停留在其他 tab 时仍能收到完成通知；该行为是监控核心，不改为
  lazy。
- `me()` 只解析权限，不再因为 super_admin 身份立即请求 people。
- Datasets、ML Backends、看板和绩效在第一次激活对应 tab 时加载；后续激活展示缓存，`r` 明确刷新。
- 移除 ML Backends 主表的 5 秒 N+1 自动轮询。第一次激活和 `r` 才聚合；单 Backend 详情继续使用
  现有 1 秒 WebSocket 实时流，因此没有损失真正需要的实时性。

状态只用三个现有 App 字段字典实现，不创建 store/reducer：

```text
_loaded_tabs: set[str]
_last_success: dict[str, datetime]
_view_errors: dict[str, str]
```

- worker 发起时设置对应 table/pane 的 Textual 原生 `loading=True`；成功后关闭 loading、更新该视图
  `last_success` 并清除该视图错误。
- 失败时关闭 loading、保留最近一次成功行，只更新该视图的错误文本和状态栏；后台 Jobs 成功刷新不得
  清除当前 Datasets/ML 的错误。
- 空结果显示“0 条”；错误显示 `HTTP status + detail` 或连接异常摘要，二者视觉和文案不同。
- ProjectDetailScreen 删除 `_safe_list`。jobs、batches、members、backends 四个 worker/结果分别落地；
  一个 pane 失败只在该 pane 显示错误，不影响其他 pane。
- ProjectDetail jobs 改为 `jobs.list(project_id=project.id, limit=50, offset=offset)`，不再拉全局 100 条后过滤。

### 10.3 查询、过滤与分页

使用 Textual 已有 `Input`、`Select`、`Button`、`DataTable` 和 timer，不增加依赖或自定义 query DSL：

| 视图         | 查询条件                      | 执行位置                                                                            | 分页                           |
| ------------ | ----------------------------- | ----------------------------------------------------------------------------------- | ------------------------------ |
| Projects     | name/display_id search        | `projects.list(search=search)` 服务端                                               | 无；端点返回完整可见列表       |
| Datasets     | search + data_type            | `datasets.list(search=search, data_type=data_type, limit=50, offset=offset)` 服务端 | 50/页，offset 分页             |
| Jobs         | status + kind                 | `jobs.list(status=status, kind=kind, limit=50, offset=offset)` 服务端               | 50/页，offset 分页             |
| Project Jobs | 固定 project_id + status/kind | 上述 Jobs 参数再加 `project_id=project.id`                                          | 50/页，offset 分页             |
| ML Backends  | name/project/state            | 已聚合缓存上的本地过滤                                                              | 无；标题明确显示 `可见数/总数` |

- 每个列表 tab 使用一行紧凑 filter bar；`/` 聚焦当前 filter，`esc` 清空并回到表格。
- 文本输入用单个可重置 300ms timer 防抖；新条件把 offset 归零并发起 exclusive worker，旧请求结果不得
  覆盖新条件。
- Datasets / Jobs 提供「上一页 / 下一页」按钮和 `p` / `n` binding；显示
  `第 start–end 条 / total`。第一页禁用上一页，`offset + limit >= total` 时禁用下一页。
- 表格刷新继续按 row key 恢复光标；如果原 row 不在新结果中，落到新页首行，不保留失效 cursor。
- 不增加“点击列头排序”。服务端当前没有统一 sort 参数，只排当前页会制造全局有序的错觉。

### 10.4 下钻与轻运维增强

所有新增内容只消费 Phase 2–4 已落地的 SDK 公共方法：

1. **DatasetDetailScreen**：替换裸 `_format_fields` 详情，提供 Overview / Items / Linked Projects 三个
   子 tab。Items 调用 `datasets.list_items(dataset.id, limit=50, offset=offset)` 并分页；Linked Projects 调用
   `datasets.list_projects()`。保持只读，不提供 delete/unlink。
2. **BatchDetailScreen**：项目详情批次行支持 Enter / `o` 下钻，使用当前列表对象立即画 Overview，`r`
   通过 `batches.get(project_id, batch_id)` 刷新。展示状态、进度、审核/退回数、优先级、deadline、
   annotator/reviewer；不提供 transition/reset/reject 表单。
3. **项目服务池**：ProjectDetailScreen 增加 `Pools` 子 tab，调用
   `ml_backends.list_available_pools(project_id)`，展示 pool logical ID/name、pool enabled、项目 enabled、
   member_count、routing_generation 和 default_variants。只读；enablement、member drain/resume、
   drift accept 留在 CLI。
4. **失败 Job 重试**：failed job 详情增加「重试失败项」动作，确认后调用 `jobs.retry_failed(job.id)`。
   TUI 不复制服务端可重试 kind 清单；服务端拒绝时展示原始 status/detail。成功后刷新 Jobs 并提示
   queued/skipped。
5. **个人绩效**：绩效 tab 对所有角色先调用 `dashboard.me_performance()` 显示本人摘要；super_admin 再
   加载现有 people 排行。project_admin 的跨成员榜单仍需项目上下文，不在 TUI 默认猜一个项目。

TUI 写动作因此只从现有 export/cancel 增加 retry-failed。项目/数据集 CRUD、批次状态写入、模型
enablement 和服务池变更已由 CLI 覆盖，不在 TUI 再做一套复杂 modal。

### 10.5 窄终端与依赖边界

使用 Textual 原生 responsive classes 和 widget 行为，不造替代层：

- [App horizontal breakpoints](https://textual.textualize.io/api/app/#textual.app.App.HORIZONTAL_BREAKPOINTS)
- [Widget loading state](https://textual.textualize.io/widgets/loading_indicator/)
- [Exclusive workers](https://textual.textualize.io/guide/workers/)
- [DataTable row keys and scrolling](https://textual.textualize.io/widgets/data_table/)

具体规则：

- `AapTuiApp.HORIZONTAL_BREAKPOINTS = [(0, "-compact"), (100, "-wide")]`。
- `-compact` 下隐藏动作栏中的刷新/打开次要按钮，保留键盘 `r` / `o` 和有业务含义的动作按钮；Footer
  继续展示可用 binding。
- `AxisChart` 改为 `width: 1fr; max-width: 64; min-width: 24`，不再固定 64 列。
- modal 改为 `width: 90%; max-width: 72`，避免 64/72 列固定宽度在 80 列终端被裁切。
- DataTable 固定第一列并保留原生横向滚动；不为窄屏维护第二套列定义。

依赖 metadata 同步改为：

```toml
tui = ["textual>=8.2,<9", "typer>=0.12", "rich>=13.0", "websockets>=12"]
test = [
  "pytest>=8.3",
  "respx>=0.21",
  "typer>=0.12",
  "rich>=13.0",
  "textual>=8.2,<9",
  "websockets>=12",
  "pytest-asyncio>=0.24",
]
```

选择 `8.2` 是因为当前锁文件 `8.2.7` 的 33 个 TUI/WS 测试全过，而声明下限 `0.80.1` 实测有 3 项
失败。上界 `<9` 防止未验证的 Textual major 被现有 SDK release 自动解析；升级 major 时单独跑 Pilot
与手动布局验收后再放宽。不新增主题、分页或状态管理依赖。

## 11. 横切实现约束

### 11.1 HTTP 与错误

- 继续使用 `HttpTransport.request`、`APIStatusError`、`AuthenticationError` 和既有 timeout/retry 行为。
- 不为新 namespace 创建第二套 transport，不在 CLI 直接 import `httpx`。
- SDK 不吞服务端 `detail`；JSON 模式错误保持机器可读，stderr 不混入 Rich 表格。
- 分页优先复用 `Page[T]`；只有服务端现有响应形状不同且无法正确解析时才加领域模型。

### 11.2 兼容性

- 新字段模型保持 optional + `extra="allow"`，避免 AAP 增加响应字段时破坏旧 SDK。
- CLI 已有命令、参数与 JSON key 不重命名。
- 对需要改变的旧行为先发 deprecation warning；本 Epic 当前没有必须删除的公共 API。
- `api-coverage.toml` 只守 operation 存在与分类，不做全量 JSON Schema hash。字段兼容由领域 mock test 与
  release smoke test 保证；只有真实发生 schema drift 事故时再评估局部 schema fingerprint。

### 11.3 文档

每个 phase 同步更新：

- `packages/python-sdk/README.md`
- `docs-site/dev/sdk/quickstart.md`
- `docs-site/dev/sdk/python-client.md`
- `docs-site/dev/sdk/cli.md`
- `docs-site/dev/sdk/tui.md`（Phase 5）
- `docs-site/dev/sdk/cookbook.md`（仅在有完整流程示例时）
- `packages/python-sdk/CHANGELOG.md`
- 根 `CHANGELOG.md` 的 Unreleased（仅 material change）

正式文档写当前状态，不在正文堆叠“自某版本起”；AAP target 与 SDK release history 只出现在 SDK
changelog、CLI version 输出和必要的 metadata 示例中。

Phase 2–5 每次合并前还应使用本地运行中的 AAP 做一个最小 smoke：创建临时测试资源、执行本 phase

## 13. 风险、回滚与前提失效

| 风险                   | 控制                                                     | 回滚                                               |
| ---------------------- | -------------------------------------------------------- | -------------------------------------------------- |
| AAP 在实施前继续演进   | 开始每个 phase 时先运行 coverage guard 并冻结实际 target | 更新台账和 target 后再实现，不伪造旧基线           |
| 手写模型遗漏新字段     | 稳定子集 + `extra="allow"`                               | patch release 补字段，不需服务端回滚               |
| CLI 破坏性误操作       | preview、`--yes`、服务端权限/409、JSON 禁止 prompt       | 操作本身由服务端事务语义处理；SDK 无数据迁移可回滚 |
| bulk 部分成功被误重试  | 原样返回 succeeded/skipped/failed，不自动重试            | 调用者按失败项显式重试                             |
| pool/instance 身份混淆 | 分 namespace、分模型、分参数名                           | 回滚 SDK release；AAP 拓扑不受安装包影响           |
| TUI 大实例请求放大     | 非活动 tab lazy；取消 ML N+1 自动轮询；服务端分页        | 安装 `0.19.x`；不产生服务端状态迁移                |
| Textual 版本漂移       | 声明并锁定 `>=8.2,<9`；major 升级前跑 Pilot/窄屏验收     | 恢复上一个 `[tui]` artifact                        |
| 公共发布渠道尚未配置   | CI 只 build，不假装 publish                              | 保留 tag/artifact；安装上一个已知版本              |

本计划成立的前提是：OpenAPI 中所列资源写 API、任务生命周期和模型服务池已经是主仓库认可的稳定
外部边界。如果某一组端点在实施前被标记 internal 或准备删除，应从对应 phase 移到 `excluded`，并在
SDK changelog 解释范围收缩；不通过 SDK 固化即将废弃的服务端接口。

## 14. 已拒绝的方案

| 方案                                  | 不采用原因                                                                            |
| ------------------------------------- | ------------------------------------------------------------------------------------- |
| `project.version = 0.16.0@AAP0.23.32` | 不是合法的公共 Python 包版本语义；`@` 已有 direct reference 含义                      |
| `0.16.0+AAP.0.23.32` 作为发布版本     | local version 不应作为公共索引上的上游版本，且会把兼容信息误装成版本排序信息          |
| SDK 版本继续等于 AAP 版本             | 平台与 SDK 发布节奏不同，会继续制造空发版或版本漂移                                   |
| SDK / CLI / TUI 分包、分版本          | CLI/TUI 都是 SDK 的可选入口，没有独立发布需求，增加多个 release train 没有收益        |
| 全量 OpenAPI codegen                  | 会生成大量 Web/internal API、改变现有易用接口并扩大 review 面；当前手写薄封装仍可维护 |
| 继续人工维护 `USED_ENDPOINTS`         | 已证实会漏项；AST 可从真实 callsite 得到同一事实                                      |
| 包装全部 API tag                      | 工作台内部、维护和治理接口不适合作为长期公共 SDK 承诺                                 |
| SDK 自动重试写请求或自动切批          | 可能重复副作用并掩盖部分失败，调用者应显式决定                                        |
| 把 TUI 做成字符版 Web                 | 表单、标注与高风险管理动作在 Web/CLI 已有入口，会扩大维护面并破坏可删除性             |
| 为 TUI 引入状态管理/分页依赖          | 三个字典与 Textual 原生 Input/Select/loading/timer 足够                               |
| 先拆分 1,855 行 `app.py`              | 当前屏幕共享导航、样式与 action，机械拆分不解决请求/反馈问题；先交付用户可见改进      |
| 保持 `textual>=0.80`                  | 下限版本专项测试已失败，继续声明会发布虚假兼容性                                      |

## 15. 实施顺序与交付

每个 phase 使用独立 PR / commit 组，依次执行：

1. 从当时主分支重新读取 OpenAPI 和 SDK 测试基线。
2. 更新 `_version.py`、SDK changelog 和台账 planned 状态。
3. 先写/扩展失败测试，再实现本 phase 的最小 public method、CLI command 或 TUI view/action。
4. 更新正式文档与根 `CHANGELOG.md`。
5. 运行第 12 节矩阵；只在全绿后创建 `sdk-vX.Y.Z`。
6. phase 全部完成后，在本文件末尾追加 `## Outcome`，记录实际 release、commit、正式文档与未交付项；
   同时从 `ROADMAP.md` 移除已完成条目或缩减为真实剩余项。

五个 phase 之间没有数据库或服务端迁移依赖。若业务优先级变化，可在 phase 1 后只交付 phase 2 或 3；
但 phase 2–5 都必须建立在 phase 1 的版本和契约守卫之上，Phase 5 的 Dataset/Batch/Pool/Retry 视图还依赖
Phase 2–4 对应公共方法。任何前置 phase 未交付时，Phase 5 必须删除对应视图，而不是绕过 SDK 直连 HTTP。
