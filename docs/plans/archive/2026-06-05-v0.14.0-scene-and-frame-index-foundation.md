# v0.14.0 · 跨 task 帧序列地基(scene 模型 + neighbors API)

> 计划日期 2026-06-05 · 范围:为所有"一段录像被切成多个 task"型场景(3D 点云逐帧 / 2D 抽帧图像序列 / 多段 mp4 拼接长录像)提供共用的**数据模型 + 后端 API + 导入端口 + manifest 透出**地基。**本期不做任何跨帧 UX**(`Shift+→` propagate / 邻帧叠加 / 跨帧 track 等),那些留 v0.14.1+ 的"跨帧体验"plan,本期只确保它们落地时有合法 backing。
>
> 直接动因:v0.13.12 原本规划的跨帧 propagate 因为"跨 task 帧序"地基不存在被拆出来(见 `docs/plans/2026-06-05-v0.13.12-3d-polish-and-pointmask.md` §5.1)。本期把那块地基补上。

## 1. 背景与目标

### 1.1 问题:平台对"跨 task 时序"无表示

现状:
- **task 内的帧序列已有**:`VideoFrameIndex`(`apps/api/app/db/models/dataset.py:77`)+ `video_tracker_runner.py` 解决了"单段 mp4 一个 task,内部跨帧 propagate"——case A。
- **task 之间的帧序列缺失**:`DatasetItem` 没有 `scene_id` / `frame_index` 列;"哪些 task 是同一段录像的连续帧"靠 `file_name` 字符串排序的弱约定推断,跨多 scene 直接破。
- **`get_next_task` 调度不知道帧序**:`apps/api/app/services/scheduler.py:70` 走 `sampling=uncertainty/uniform/sequence`,任一策略都不保证同 annotator 拿到的下一个 task 是同 scene 内的下一帧;`prefer_same_scene_continuation` 之类的 hint 完全没有挂入点。

后果(已在 v0.13.12 §5.1 量化):
- 跨帧 propagate / track / 邻帧叠加这三类 UX **没有合法实现路径**。
- 一个 dataset 跨多 scene(典型:nuScenes 一个 dataset 含 10 个 scene)时,`file_name` 排序会让 scene-A 末帧"邻居"是 scene-B 首帧——语义错误。
- 2D 图像序列(case B)与多段 mp4 拼接(case C)两种 2D 形态完全没有"跨帧延续"能力。

### 1.2 目标:把 4 种"时序录像"形态统一到同一地基

| 存法 | 一个 task = | "下一帧"在哪 | 本期解决? |
|---|---|---|---|
| **A. 整段 mp4 一个文件** | 一段视频 | task 内 `VideoFrameIndex.frame_index` | 保留现状,不动 |
| **B. 抽帧图像序列** | 一张 jpg | 跨 task | ✅ |
| **C. 多段 mp4 拼成长录像** | 一段 mp4 片段 | 跨 task(段级) + task 内(段内) | ✅ 段级跨 task;段内沿用 A |
| **3D. 点云逐帧** | 一帧 `.pcd` | 跨 task | ✅ |

**关键设计观察**:B / C / 3D 三个的形状一模一样——"录像被切成 N 个 task,跨帧 = 跨 task"。差别只是每个 task 装的文件类型不同(jpg / mp4 / pcd)。`scene_id + frame_index` 是面向"时序录像"的抽象,**与文件类型正交**。一立起来三种场景共用,前端跨帧 UX 写一份就够。

### 1.3 不在本版本

- **任何跨帧 UX**(`Shift+→` propagate / 邻帧参考框叠加 / `useFrameNeighbors` hook / `selectedGroupId` 跨帧高亮)→ 留 v0.14.1。本期前端只让 manifest 暴露 `scene_id` / `frame_index`,工作台不消费。
- **跨 scene 边界连续导航**(case C 段内末帧 → 段间首帧的"无感跨段"):留 v0.14.2+。本期 case C 的 neighbors 只返回段级邻居。
- **跨帧自动插值 / Kalman 预测**(SUSTechPOINTS `trajectory.py` 等价物):留 v0.14.2+,需要 UX 先在 v0.14.1 落地。
- **task 调度的 `prefer_same_scene_continuation` flag**:本期只把"哪些 task 同 scene"建模出来,*不*改 `get_next_task` 行为(避免回归既有项目的分配模式)。挂入点设计好但默认 OFF,实际生效留 v0.14.1。
- **scenes 概念的多 dataset 跨表**(一个 scene 横跨 lidar dataset + image dataset):留 v0.15+。本期 `scenes.dataset_id` 强 FK,一 scene 隶属一 dataset。
- **历史数据自动迁移到 scene**:本期写显式 backfill 脚本,**不**在 alembic migration 里悄悄重写数据;管理员人工跑、确认结果。

### 1.4 成功判据

1. **DB schema 落地**:`scenes` 表 + `dataset_items.scene_id (FK, nullable)` + `dataset_items.frame_index (int, nullable)` migration 上线,`alembic upgrade head` 无误,`downgrade` 干净回退。

   - **nuScenes 转换脚本**(留给 v0.14.2)走"显式 `scene_svc.create_scene` + `assign_items_to_scene`"路径,不依赖启发式;本期不做。
5. **Manifest 透出**:点云 `GET /tasks/{id}/point-cloud-manifest` 响应附 `scene_id` / `frame_index` / `scene_total_frames`;2D 任务 manifest(若有等价端点)同样附。前端只接住、显示在调试面板,不消费跨帧 UX。
6. **测试覆盖**:
   - 单测:Scene 模型 CRUD;`scene_inference` 服务(单 scene / 多 scene 用例);backfill 幂等性;neighbors 端点的 k=1 / k=5 / 同 scene 边界(首帧 prev 为空、末帧 next 为空)。

## 3. 各模块设计要点

### 3.1 数据模型

**新表 `scenes`**:
```python
class Scene(Base):
    __tablename__ = "scenes"
    id:           UUID PK
    display_id:   str  unique  # "SCN-000001",走 display_seq_scenes
    dataset_id:   UUID FK datasets ondelete=CASCADE  index
    name:         str  # 业务名(如 "scene-0061"、"downtown_2026_06_05_run1")
    source_format: str | None  # "sustechpoints" | "nuscenes" | "manual" | "kitti_raw" ...
    source_metadata: JSONB  # 自由格式,各 importer 自填(如 nuScenes 存 scene_token / duration_s)
    created_by:   UUID FK users  nullable
    created_at:   datetime
    updated_at:   datetime
    # 唯一性:同一 dataset 下 name 唯一(允许跨 dataset 同名)
    __table_args__ = (UniqueConstraint("dataset_id", "name", name="uq_scenes_dataset_name"),)
```

**`dataset_items` 加两列**:
```python
scene_id:    UUID | None  FK scenes(id) ondelete=SET NULL  index
frame_index: int  | None  # 在该 scene 内的有序位置;同 scene 同 frame_index 允许重复(lidar + 多 cam + ... 共享 frame 号)
```

**索引**:
- `idx_dataset_items_scene_frame` on (scene_id, frame_index) — neighbors 查询核心索引
- 不加 UNIQUE(scene_id, frame_index)。原因:多模态场景同 frame_index 行很正常(`000950.pcd` + `front/000950.jpg` + `left/000950.jpg` 三行共享 frame_index=0),且 calib 之类的 scene-level 元数据需要 frame_index=NULL 多行共存。

**关于设计选择**:
- **为什么单独建 `scenes` 表,而不只在 `dataset_items` 加 `scene_id` 字符串**?调研结论是 nuScenes 范式胜出(详见 `docs/research/14-point-cloud-image-fusion.md` §14.7),scene 有自身元数据(scene_token / duration / 备注 / 创建者);单字符串约束不出唯一性也不便管理。
- **为什么不复用 v0.13.0 已有的 `metadata_` JSONB**?可以,但 (a) 索引性能差(JSONB GIN 不如 BTree 直查 FK)、(b) 缺乏跨 item 一致性约束、(c) 跨 dataset 的 scene 列表查询会变成 JSON 扫表。地基级抽象就该走结构化列。
- **为什么 scene_id 在 dataset_items 是 nullable**?向后兼容。历史所有 dataset_items 不动,新建项目默认有 scene,旧数据靠 backfill。

**migration `0096_scenes_and_frame_index.py`**(略表伪代码,真实文件遵循已有 alembic 规范):
```python
def upgrade():
    op.execute("CREATE SEQUENCE IF NOT EXISTS display_seq_scenes;")
    op.create_table("scenes", ...)
    op.add_column("dataset_items", sa.Column("scene_id", UUID, nullable=True))
    op.add_column("dataset_items", sa.Column("frame_index", sa.Integer, nullable=True))
    op.create_foreign_key("fk_dataset_items_scene", "dataset_items", "scenes",
                          ["scene_id"], ["id"], ondelete="SET NULL")
    op.create_index("idx_dataset_items_scene_frame", "dataset_items",
                    ["scene_id", "frame_index"])

def downgrade():
    op.drop_index("idx_dataset_items_scene_frame", "dataset_items")
    op.drop_constraint("fk_dataset_items_scene", "dataset_items", type_="foreignkey")
    op.drop_column("dataset_items", "frame_index")
    op.drop_column("dataset_items", "scene_id")
    op.drop_table("scenes")
    op.execute("DROP SEQUENCE IF EXISTS display_seq_scenes;")
```

### 3.3 Scene inference(`services/scene_inference.py`)

唯一职责:**给一个已有 dataset 自动建 scene + 给 items 赋 frame_index**。本期覆盖**两种 mode**:

```python
async def infer_and_apply(db, *, dataset_id,
                          mode: Literal["single", "per_subdirectory", "auto"] = "auto",
                          dry_run: bool = False) -> InferenceResult
    # mode="single":全 dataset = 1 个 scene;scene.name 默认取 dataset.name
    # mode="per_subdirectory":按 file_path 顶层目录名分组,每组一个 scene
    # mode="auto":先看顶层目录是不是"全已知角色名"(下文 §3.3.2 算法)→ 命中即 single,否则 per_subdirectory
    # 默认 mode="auto":wizard 上传后调用方不需要预先判断 dataset 形状
    # 幂等:dataset 已有 scene → 跳过;dataset_items 已有 scene_id → 跳过
    # dry_run:全程不写库,返回会创建/赋值的统计
```

#### 3.3.1 共用:frame_index 赋值算法(`single` 与 `per_subdirectory` 都用)

给定一组属于同一 scene 的 dataset_items:
1. 调 `pointcloud_import.group_frames(items)` 拿到 `{frame_stem: {lidar: ..., cameras: {cam: ...}}}` 字典 + `calib_items` 列表
2. 按 frame_stem 排序(human-readable sort:`000001 < 000002 < ... < 000010`,不是字符串字典序)
3. 对每个 frame_stem 分配 `frame_index = 0, 1, ..., N-1`:lidar 和该帧所有 cam 共用同一个 frame_index
4. calib_items 仅写 `scene_id`,`frame_index = NULL`
5. 对**非点云 dataset**(纯图像 / 视频):整套退化成"按 `dataset_items.file_name` 自然排序赋 0..N-1",所有 items 都有 frame_index(图像序列 / 单段视频每个文件就是一帧 / 一段)

#### 3.3.2 `per_subdirectory` 拆分算法

输入:一个 dataset 的所有 dataset_items,各有 `file_path`(MinIO key,形如 `<ds_name>/<rest>/<file>`)。

```python
# 已知角色名集合(与 pointcloud_import.group_frames 的 magic word 对齐)
ROLE_DIR_NAMES = {"lidar", "camera", "calib", "image", "video"}

def split_into_scene_groups(items: list[DatasetItem]) -> list[tuple[str, list[DatasetItem]]]:
    """把 items 按"file_path 中 dataset_name 之后第一段"分组。

    跳过开头 dataset_name 段;若第一段是已知角色名 → 整 dataset 为单 scene(返回单组,scene_name=dataset.name);
    否则该段就是 scene 名(典型:nuScenes scene_token / SUSTech 多 scene zip 的顶层目录名),返回多组。
    """
    by_scene: dict[str, list[DatasetItem]] = {}
    for item in items:
        parts = PurePosixPath(item.file_path).parts
        if len(parts) < 2:  # 无子目录,纳入"_root" 组(理论不应出现)
            by_scene.setdefault("_root", []).append(item)
            continue
        # parts[0] 是 dataset name 前缀,parts[1] 是关键判定段
        first = parts[1]
        scene_key = "_single" if first in ROLE_DIR_NAMES else first
        by_scene.setdefault(scene_key, []).append(item)
    return list(by_scene.items())

# auto 模式:若 split 只产 1 组且 key=="_single" → 走 single mode
# 否则按多 scene 分组,每组调 §3.3.1 算法赋 frame_index 0..N(每 scene 内部独立编号)
```

**正确处理的几种 ZIP 布局**:

| ZIP 顶层(dataset_name 之下) | 推断结果 | scene.name |
|---|---|---|
| `lidar/ camera/ calib/`(SUSTech 单 scene) | 单 scene | dataset.name |
| `scene_a/lidar/ scene_a/camera/ scene_b/lidar/ scene_b/camera/` | 2 scene | `scene_a`, `scene_b` |
| `nu-scene-0061/lidar/ nu-scene-0061/camera/ nu-scene-0103/lidar/ ...` | N scene | `nu-scene-0061`, ... |
| `lidar/ camera/ scene_extra/`(混搭,边界情况) | 走 `per_subdirectory`(2 scene:`_single` + `scene_extra`)+ note 警告 | "用户布局非常规,人工 review" |

**不**自动处理的(本期不做,docs 说清楚不要这么打包):
- 顶层文件混在子目录里:如 `<ds>/000970.pcd` 与 `<ds>/lidar/000971.pcd` 并列 → `_root` 组警告,不参与建 scene
- 顶层文件名作为 scene 标识:如 `<ds>/scene_a_000001.pcd`(scene 信息编码在文件名前缀)→ 走 single,docs 提示走转换脚本

**关键约束**:`per_subdirectory` 模式下,每个 scene 组内部仍按 §3.3.1 走 group_frames + 自然排序;**绝不**跨 scene 组共用 frame_index。这是 v0.14.2 多 scene 测试的判据 3 直接验证的事。

#### 3.3.3 边界 / 错误处理

- 该 dataset 已有 scene → 跳过整个 inference,不报错(幂等)
- 部分 items 已有 scene_id、部分没有 → InferenceResult.notes 报警 "部分迁移状态,人工检查";不动已 assigned 的,只对 NULL 的跑;**不**跨已有 scene 强行重赋
- per_subdirectory 推断出超过 100 个 scene → 报错(防误识别巨型 dataset 的 jpg 序列为 N 万个伪 scene),建议显式指定 `mode="single"`
- per_subdirectory 推断出 0 个 scene(整 dataset 空)→ no-op,return InferenceResult(created_scenes=0)

`InferenceResult` 给 backfill 脚本和 API 端点共用:
```python
class InferenceResult(BaseModel):
    dataset_id: uuid.UUID
    created_scenes: int
    assigned_items: int
    skipped_items: int     # 因为已有 scene_id 而跳过
    dry_run: bool
    notes: list[str]       # human-readable 提示(如 "11 calib items 无 frame_index")
```

### 3.4 Neighbors API(`api/v1/tasks.py`)

```
GET /tasks/{task_id}/neighbors?k=1
```

- 鉴权:沿用本路由现有 `get_current_user` + 项目可见性约束(防止借此枚举别人项目的 task_id)。
- 200:`NeighborsResponse`
- 404:task 不存在 / 用户无访问权
- 409:task.dataset_item 有 scene_id 但 frame_index=NULL(异常状态,backfill bug 兜底)
- 200 + 空 prev/next:task 无 scene_id(历史未 backfill 数据)→ 与"首尾帧"返回值一致,前端不区分

`k` 范围限制:1 ≤ k ≤ 20,超出 400。原因:邻帧叠加 UX(v0.14.1)极少超过 ±10,k=20 给余量;无上限会被滥用成"取整 scene 列表",有专门的 list-scene-frames 端点干这事(本期不做)。

**性能预期**:scene 内 1000 帧 + 多模态(3 cam)= dataset_items 4000 行。neighbors 查询命中 `idx_dataset_items_scene_frame` BTree,理论 ≤ 5ms。本期不加缓存层。

### 3.5 导入端口对齐(三处一起改)

**A. `pointcloud_import.build_pointcloud_tasks_for_link`**:函数顶部增加:
```python
# 若该 dataset 还没 scene,自动跑 single-mode inference(SUSTechPOINTS 例 8 帧建出 1 scene)
existing_scenes = await scene_svc.list_for_dataset(db, dataset_id)
if not existing_scenes:
    await scene_inference.infer_and_apply(db, dataset_id=dataset_id, mode="single")
    await db.flush()
```
这意味着所有走 link 接线的点云项目(seed / wizard 上传)自动有 scene,前端可立刻消费。

**B. `seed_pointcloud.py`**:不改 `seed_pointcloud()` 函数体——上面的 hook 已经覆盖;只在测试 / docstring 里写明"SCN-PC-DEV"会被自动创建。

**C. `upload-zip` 端点**:成功 ingest 完后,若 dataset 还没 scene,**对所有 data_type 都默认跑 single-mode inference**。这给纯 2D 图像数据集也送上 scene(虽然 v0.14.0 没 UX 消费它,但 v0.14.1 即可启用)。

### 3.6 Backfill 脚本(`scripts/backfill_scenes.py`)

```bash
# 单 dataset
uv run python scripts/backfill_scenes.py --dataset-id <uuid>

# 全部缺 scene 的 dataset
uv run python scripts/backfill_scenes.py --all-missing

# 预览
uv run python scripts/backfill_scenes.py --all-missing --dry-run
```

实现就是 `scene_inference.infer_and_apply(mode="single")` 的薄包装,加 CLI / 日志 / 错误码退出。**不**在 docker 容器启动时自动跑——管理员人工 review。

**幂等性**:对已有 scene 的 dataset 跳过;对部分 items 已有 scene_id 的 dataset 也跳过(报错"部分迁移,人工检查"),避免 inference 对不全状态做错误假设。

### 5.2 ~~多 scene 启发式~~(已在本期 §3.3 实现)

本节原写"留 stub";按 v0.14.2(原 v0.13.13)的多 scene 实测需要,本期已把 `per_subdirectory` mode 升级成完整算法(§3.3.2),并支持 `auto` mode 在 ZIP 上传后自适应选择。仍**不**做的启发式:

### 5.3 task 调度的 scene 偏好(本期不挂入)

`get_next_task` 不动。挂入点设计在心里(`prefer_same_scene_continuation: bool = False` 加到 project 或 batch 配置;在 sequence 策略下加 `order_by` 同 scene + frame_index 邻近度);本期不加列、不动调度。

延迟到 v0.14.1+ 的原因:
1. 不动调度可让本期纯增量上线,既有项目零回归
2. 真实需求要 UX 先跑过才知道:也许跨帧 propagate 本身就够好用、不需要调度配合 always 给"下一帧"
3. 多 annotator 同时标同 scene 的锁/分配语义复杂(同一个 scene 应不应该独占给一个人?),需要单独决策

### 5.4 跨 scene 段内段间无感导航(case C)

多段 mp4 拼接长录像,段内末帧跳段间首帧的"无感"切换,本期 neighbors 端点只返回段级邻居(下一个 mp4 task),不返回段内末帧 → 段间首帧的"半个跨段"组合。原因:段内 frame_index 是 `VideoFrameIndex.frame_index`(task 内),段间 frame_index 是 `dataset_items.frame_index`(scene 内段序),两个 frame_index 命名空间。统一 API 表达需要更深的抽象(类似 nuScenes 的 `sample_data` 全局 timestamp),留 v0.15+。

### 5.5 ego_pose / 时间戳

研究里 §14.7.4(nuScenes)反复提到的 ego_pose / sample timestamp,本期完全不动。这些是"高保真度多帧聚合"才需要的,跨帧 propagate 用单帧 PSR 复制就够 90% 场景。留 v0.15+。

### 5.6 历史 dataset 的 backfill 决策

`backfill_scenes.py` 默认走 `mode="auto"`(本期 §3.3 升级后),对历史 dataset 在多数情况下能正确识别单/多 scene 布局。但对**文件名编码 scene 信息**的 dataset(如 `<ds>/scene_a_000001.pcd <ds>/scene_a_000002.pcd <ds>/scene_b_000001.pcd` 平铺一层)会误判为单 scene。**本期接受这个**:backfill 跑完报告里给 notes 提示"非角色顶层目录数 < 2,按单 scene 处理";管理员 review 有问题可显式重跑 `--mode=per_subdirectory` 或人工 PATCH 切分。基于文件名前缀的启发式留 v0.15+。
