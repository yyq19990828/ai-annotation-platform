## 待决策项

### 1. kind 专属字段去哪（核心）

三个候选：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. metadata JSONB** | 统一表加 `metadata JSONB`，bug 诊断上下文 / reopen 计数、comment mentions/canvas_drawing、reject reason_type 全塞进去 | 真正单表 | 弱 schema，专属字段查询/索引退化为 JSONB 操作 |
| **B. 索引/线程层 + detail 表** | 统一表存公共字段+锚点+线程，专属字段留旧表（feedback_id 关联） | 保留强 schema | 没真正"收敛成一张表"，仍是 join |
| **C. 分级** | comment/issue 完全并入（字段少）；bug/reject 走 B（专属字段多 + 各自 state machine/子资源/前端 UI） | 务实，按复杂度区别对待 | 模型不完全统一 |

**推荐：refined-C（比上表 C 更进一步）。** 关键洞察——`v_annotation_feedback_unified` view **已经免费提供了统一读表面**（UNION ALL 4 源），所以「物理把 4 类合进一张表」这个前提本身是过头的。物理合并只对真正需要"写新 kind / 被 FK 引用 / 查真表"的 kind 有价值：

| kind | 决策 | 理由 |
|---|---|---|
| **issue** | 已单源在 `annotation_feedbacks` | 新 kind，无旧表，天生在此 |
| **comment** | **单源进 `annotation_feedbacks`** | 反馈原型；`attachments` 统一表已有，`is_resolved`→status、`anchor`→anchor_position 平移；唯一该真迁的旧表 |
| **reject** | **权威留 `tasks`**，统一读走 view | 本质是 task 状态机字段，非独立行；reviewer 驳回必写 tasks，单源到别处反而横跨两表写 |
| **bug** | **权威留 `bug_reports`**，统一读走 view | 是产品 issue 跟踪而非标注反馈；`display_id`/triage 状态机/`BugComment`/诊断上下文最重，迁移代价最高收益最低 |

`annotation_feedbacks` 最终只装 comment + issue（原生标注反馈）；view 把 bug/reject 从源表拼进统一视图。LLM 聚类去重 / Webhook fan-out 都能在 view 或事件上跑，**不需要物理合并**。

### 2. status 值域映射 — refined-C 下基本消解

bug status（`triaged/fixed/duplicate/wontfix`）留在 `bug_reports`，无需无损映射进统一表。view 维持现有展示映射即可（仅用于联合视图，不回写）。

### 3. `bug_reports.project_id IS NULL` 行 — refined-C 下消解

bug 不迁，该行继续留 `bug_reports`，无需处理统一表 `project_id NOT NULL` 冲突。

### 4. 退役顺序 — 大幅简化

- v0.11.9 撤 bug/reject 冗余双写（refined-C 下它们不进统一表）。
- v0.11.10 comment 切单源（唯一实质迁移）。
- v0.11.11 收尾：只 drop `annotation_comments`，view 转正为永久读表面。
