## 背景与现状

结构勘察结论：

- `WorkbenchShell.tsx`：第 88–1104 行是 hook / state / handler 装配（约 1000 行），第 1104–1480 行是 JSX。
- StageHost 不在 Shell 里直接渲染：Shell 在 JSX 里组装一个 `stageHost={{ ... }}` 字面量（**第 1179–1291 行，约 110 行**）传给 `WorkbenchLayout`，后者以 `<WorkbenchStageHost {...stageHost} />` 展开（`WorkbenchLayout.tsx:74`，类型为 `ComponentPropsWithoutRef<typeof WorkbenchStageHost>`）。
- `WorkbenchStageHost.tsx` 在函数头**平铺解构**全部 ~80 个 prop（第 174–262 行），组件主体直接使用解构出的局部变量。

→ **关键影响面收窄**：嵌套 props 改造只需动「interface + 函数头解构 + Shell 调用字面量 + 测试」，组件主体逻辑无需改动（在函数头做二次解构 `const { stageKind, ... } = props.common` 即可还原所有局部变量名）。

## Item 1 · WorkbenchStageHostProps 类型嵌套重构

把平铺的 ~80 prop interface 改为按已有 JSDoc 分组的嵌套形态：

```ts
interface WorkbenchStageHostProps {
  common: { stageKind; overlays; readOnly; activeClass; selectedId; annotations; onSelectBox; onCursorMove };
  video?: { videoManifest; ...; onPropagateVideoTrack };   // stageKind="video" 才消费
  image?: { fileUrl; ...; onSamPrompt };                   // stageKind="image" 才消费
  ai?:    { samCandidates; samActiveIdx; samSubTool; samPolarity; onRefineSamCandidate; ... };
  editors?: { polygonDraft; keypointDraft; canvas*; maskEditor; projectRenderingConfig; issue* };
}
```

分组直接沿用 `WorkbenchStageHost.tsx:34-42` 已就位的 JSDoc 注释（common / video / image / ai / editors）。

**改动点**
1. `WorkbenchStageHost.tsx`
   - interface（44–171 行）：平铺字段按 5 组重组为嵌套对象。
   - 函数头解构（174–262 行）：先 `const { common, video, image, ai, editors } = props`，再对各组做二次解构还原原局部变量名 → **组件主体一行不动**。
   - `video`/`image`/`ai`/`editors` 标为可选，需对二次解构加空值兜底（如 `const { fileUrl, ... } = image ?? ({} as NonNullable<...>)`），按 stageKind 保证消费侧安全。
2. `WorkbenchShell.tsx`：`stageHost={{ ... }}`（1179–1291 行）字面量按 5 组重写为嵌套。
3. `WorkbenchLayout.tsx`：无需改（`{...stageHost}` 展开对嵌套同样成立，类型自动跟随 `ComponentPropsWithoutRef`）。
4. 测试：`WorkbenchStageHost.test.tsx`、`WorkbenchLayout.test.tsx` 的 props 构造按嵌套更新。

**风险**：可选组的空值兜底若处理不当，类型会从「必填」松成「可选」，可能漏传不报错。缓解：对各 stage 分支用 `stageKind === "image" ? <require image> ...` 的类型收窄，或在组件入口断言。

## Item 2 · `useWorkbenchShellModel` 装配 hook

把 `WorkbenchShell.tsx` 第 88–1104 行的 state / hook / handler 装配抽到 `../state/useWorkbenchShellModel.tsx`，返回一个 model 对象；组件本体只保留 `const model = useWorkbenchShellModel({ mode })` + JSX（1104–1480 行）。

**改动点**
1. 新建 `apps/web/src/pages/Workbench/state/useWorkbenchShellModel.tsx`：迁入装配逻辑，`return { ...所有 JSX 消费的值与回调 }`。
2. `WorkbenchShell.tsx`：瘦身为 `model = useWorkbenchShellModel(...)`，JSX 引用从 `foo` → `model.foo`（或对 model 做一次解构，保留 JSX 不动）。
3. 这是**机械搬运**：不改逻辑、不改 hook 调用顺序（避免触发 React hooks 规则报错），只移动位置。

**与 Item 1 的耦合**：JSX 里的 `stageHost` 字面量同时是两项的交汇点——Item 1 改它的形状（嵌套），Item 2 改它的取值来源（`model.*`）。

**顺序建议**：**先 Item 1，后 Item 2**，分两个 commit。
- Item 1 是类型级、自包含的低风险改动，可作为中间检查点（tsc/测试绿后再进）。
- Item 2 在 Item 1 已嵌套的字面量基础上做取值来源替换，diff 更可读。
- 反过来（先抽 hook）会让 Item 1 在「刚搬完的 model 引用」上再改形状，两次大 diff 叠加，难 review。

**验证**
- `pnpm -C apps/web tsc --noEmit` 绿。
- `pnpm -C apps/web test WorkbenchShell WorkbenchStageHost WorkbenchLayout` 绿。
