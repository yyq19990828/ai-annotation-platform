# v0.18.0 — onnxtools 第四 backend + 二阶段车辆属性预标注（路径 A 前哨）

> 状态：**待实施 plan**（不开干）。创建于 2026-06-23。
>
> 定位：本特性是「多阶段预标注」的**第一块垫脚石**。它用 onnxtools 把「检测→ROI→分类→写属性」整条数据通路在 backend 内部串通并落地验证，同时把会被未来通用编排（[路径 B ROADMAP](../../ROADMAP/2026-06-23-staged-preannotation-pipeline-roadmap.md)）复用的产出（独立微服务、协议自报 attribute schema、前端枚举属性链路）一次做对。**onnxtools 内部把检测/分类拆成独立单元**，B 上线后可直接拆出原子 model 编排，不返工。

## 1. 目标 / 非目标

**目标**
1. onnxtools 新增 `VehicleAttributePipeline`：rtdetr 检测 → 对「机动车」框裁剪 ROI → va 模型出车型+颜色 → 写入属性。固化模型 `models/rtdetr-2024080100.onnx` + `models/va_260612.onnx`。
2. 新建独立微服务 `apps/onnxtools-backend`（第四个 backend，与现有三个同构，HTTP 协议 v2.1）。
3. 协议③扩展：`/setup` 的 model 条目自报 attribute schema（含 select options），平台「从 backend 导入」一键生成项目 `attribute_schema`。
4. 补平台 select 属性链路缺口（采纳校验为**必补**，采纳前预览为**选补**）。

**非目标**
- 不做平台层跨 backend 编排（那是 B）。
- 不做车-牌父子层级（车牌作为独立类别，本期不涉及）。
- 不放开 `MAX_ML_BACKENDS_PER_PROJECT`（A 是单 backend 复合 model，B 才需要多 backend）。

## 2. schema 约定（已拍板）

一个机动车框：

```jsonc
{
  "class_name": "car",                 // rtdetr 粗检测类 (car/truck/heavy_truck/van/bus/motorcycle)
  "geometry": { "type": "bbox", ... },
  "attributes": {
    "vehicle_type": "school_bus",      // va 细车型 (13 类, select)
    "color": "blue"                    // va 颜色 (11 类, select)
  }
}
```

**机动车 class_id**（喂 va 的）：`[0 car, 1 truck, 2 heavy_truck, 3 van, 4 bus, 14 motorcycle]`（`onnxtools/configs/det_config.yaml`）。非机动车框（pedestrian/plate/cone…）只出检测框，不跑 va。

**va 枚举（写进项目 `attribute_schema` + backend 自报，三处 key 必须逐字对齐）**

`vehicle_type`（13，源 `onnxtools/config.py:VEHICLE_TYPE_MAP`）：
`car 小车` / `truck 卡车` / `bus 公交` / `tanker 油罐车` / `slagcar 渣土车` / `fire_engine 消防车` / `mixer 混凝土搅拌车` / `ambulance 救护车` / `police_car 警车` / `engineering_truck 工程车` / `hazardous_goods_vehicle 危险品运输车` / `manned_sweeping_vehicle 有人扫路车` / `school_bus 校车`

`color`（11，源 `VEHICLE_COLOR_MAP`）：
`black 黑` / `white 白` / `gray 灰` / `red 红` / `yellow 黄` / `green 绿` / `blue 蓝` / `purple 紫` / `brown 棕` / `pink 粉` / `other 其他`

> 注意：va 的 `vehicle_type` 与 det 粗类有重叠（都含 car/truck/bus）。约定取「det 粗类进 `class_name`、va 细类进 `attributes.vehicle_type`」，二者独立保留，不做去重。

## 3. 详细设计

### 3.1 onnxtools — `VehicleAttributePipeline`

- 复用现有 `onnxtools/pipeline.py` 的「检测→ROI→下游分类」范式（车牌 OCR/颜色层级已是这个模式，ROI 裁剪逻辑见 `pipeline.py:394-407`，含 10% 边界扩展）。
- 新增 `VehicleAttributePipeline`（`InferencePipeline` 子类）：`detector = create_detector('rtdetr', ...)`，`va = VehicleAttributeORT('models/va_260612.onnx')`；遍历检测框，`cls in [0,1,2,3,4,14]` 时裁剪 ROI → `va(roi)` → `ClsResult.labels=[type, color]` → 写 `attributes`。
- `detector` 与 `VehicleAttributeORT` 本就是独立 `__call__` 单元（已确认），**保持解耦**：复合 pipeline 只是恰好串起来，将来 B 可分别独立暴露。
- 导出：`onnxtools/__init__.py` 的 `_LAZY_EXPORTS` + `__all__` 各加一行。
- 测试：va 单测（crop 推理）、检测+ROI+va 集成测、输出结构断言。

### 3.2 `apps/onnxtools-backend` — 独立微服务

抄 `apps/yolo-backend/` 骨架（`main.py` / `model_pool.py` / `model_registry.py` / `schemas.py` / `Dockerfile` / `pyproject.toml`）。

- **`/setup`**：声明一个复合 model 条目：
  ```jsonc
  {
    "id": "vehicle-attr", "task": "detection", "model_family": "rtdetr",
    "infra": "onnx", "is_interactive": false,
    "supported_geometric_outputs": ["bbox"],
    "output_attribute_types": ["class"],          // 兼容旧
    "output_attribute_schema": [ /* ③ 见 3.3 */ ],
    "default_thresholds": { "conf": 0.5 }
  }
  ```
- **`/predict`**：批量，每个 task 跑 `VehicleAttributePipeline`，按协议 §3 返回 `result[]`：`type=rectanglelabels`、`value`(bbox + `rectanglelabels:[det类]`)、`attributes:{vehicle_type, color}`。**零 adapter 命中现有 `to_internal_shape`**。
- 依赖：`onnxruntime-gpu`、`opencv`、onnxtools（以本地路径/可编辑安装引入）。模型文件挂载或 COPY。
- docker-compose 接入 + 平台 ml_backend 注册（注册到目标项目；模型只对注册项目可见）。

### 3.3 协议③ — `/setup` 自报 attribute schema（填缺口 C）

model 条目新增 `output_attribute_schema`（数组），每项是一个完整 attribute field 定义（与平台 `AttributeField` 同构）：

```jsonc
"output_attribute_schema": [
  { "key": "vehicle_type", "type": "select", "label": "车型",
    "options": [ {"value":"car","label":"小车"}, /* …13 项… */ ] },
  { "key": "color", "type": "select", "label": "颜色",
    "options": [ {"value":"blue","label":"蓝色"}, /* …11 项… */ ] }
]
```

- 平台 capabilities 端点（`GET …/ml-backends/{bid}/capabilities`）透传该字段。
- 项目配置页「从 backend 导入属性」：把 `output_attribute_schema` 一键合并进项目 `attribute_schema.fields`，保证 backend 输出 key ↔ 项目字段 key ↔ select options **三处对齐**。
- 文档：更新 `docs-site/dev/reference/ml-backend-protocol.md`（§4.1.8 邻近，新增「属性输出自描述」小节）。

### 3.4 平台 select 链路缺口

主链路（采纳→落库→编辑）已通（`accept_prediction` 原样拷贝 `attributes`；`AttributeForm` 支持 select/multiselect 渲染编辑）。本期补：

- **缺口 B（必补）— 采纳校验**：`accept_prediction`（`apps/api/app/services/annotation.py:199-205`）注入项目 `attribute_schema`，对 select 值做 options 校验。**采用宽松策略**：非法/未定义 key 不报错丢弃，而是保留入库 + 记一条软告警（避免预标因模型抖动整框失败）；硬校验留给人工提交时。
- **缺口 A（选补）— 采纳前预览**：选中预标候选框（`AiBox`）时，在 `AIInspectorPanel` 以只读方式渲染其 `attributes`（车型/颜色），让标注员采纳前可见。优先级低于 B。
- **缺口 C** 由 3.3 协议自报解决。

## 4. 实施步骤（每步带 verify）

1. onnxtools `VehicleAttributePipeline` + 导出 → verify：`examples/` 写个 demo 脚本，对样图输出含 `vehicle_type/color` 的 JSON；单测/集成测过。
2. `apps/onnxtools-backend` `/setup`+`/predict` → verify：`uvicorn` 起服务，curl `/setup` 看到 model 条目 + `output_attribute_schema`；curl `/predict` 返回带 attributes 的 result[]。
3. 协议③ 平台侧透传 + 项目导入 → verify：项目配置页能从该 backend 导入 vehicle_type/color 两个 select 字段（options 齐全）。
4. 端到端预标 → verify：建项目→注册 onnxtools-backend→导入属性→批量预标→工作台看到车型/颜色候选→采纳→框带正确属性且可编辑。
5. 缺口 B 校验 → verify：构造非法 color 值，确认软告警入库不崩。
6. （选）缺口 A 预览 → verify：选中预标框侧栏只读显示属性。
7. 版本收尾（CLAUDE.md §10）：bump `CHANGELOG.md` / `apps/api/app/config.py` / `apps/api/pyproject.toml` / `apps/web/package.json`，`uv lock` 刷 `uv.lock`，pre-commit 重生 openapi 快照；`curl localhost:8000/health` 验证 0.18.0。

## 5. 验收标准

- 一张含多辆车的图，批量预标后每个机动车框带 `class_name`(det类) + `attributes{vehicle_type, color}`，非机动车只出框。
- 采纳后属性入库、工作台 select 可编辑、值显示为中文 label。
- backend `/setup` 自报的属性 schema 能一键导入项目，无需手抄 options。
- 非法属性值不导致预标整批失败。

## 6. 风险 / 开放问题

- **GPU 显存**：onnxtools-backend 与现有 backend 并存的显存预算（rtdetr 169MB + va）。MVP 单实例，监控即可。
- **det 类 ↔ rectanglelabels 映射**：det 15 类要进项目 classes 配置（机动车那几类至少要在 `tool_binding[bbox].classes` 里）。
- **协议③形态**：`output_attribute_schema` 是否未来要支持 `range`/`multiselect` 的自描述（本期只用 select，结构already通用）。
- **缺口 B 校验严格度**：宽松（软告警）vs 严格（拒绝）的最终策略，按实测数据质量再定。

## 7. 与路径 B 的衔接

- onnxtools 内 `detector` / `VehicleAttributeORT` 保持独立 → B 时拆成 `detection` / `classification` 两个原子 model 暴露。
- 协议③ `output_attribute_schema` 是 B 跨 backend 编排时属性对齐的同一套机制。
- 前端 select 链路（B 缺口 A/B/C）本期打通后 B 直接复用。
