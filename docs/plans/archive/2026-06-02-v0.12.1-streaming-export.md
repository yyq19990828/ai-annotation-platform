# v0.12.1 · 导出流式化（streamed-archive）

> 路线图：[大数据集规模化加固](./2026-06-02-large-dataset-scale-hardening-roadmap.md) 的第三版（B6）。
> 主题：把导出从「全量进内存 + 单 BytesIO 攒整包」改为「分块读 DB + 落盘式 ZIP」，使 worker 内存与 task 数解耦。
> **风险中（导出链路重写），挂触发条件**：单 project/batch 导出 task > ~3 万，或 worker OOM / 导出超时实际发生。

## 背景（先纠正一个常见误判）

导出走 Celery worker（`workers/export.py:85 run_export` → `:169 _run_export` → `:258 build_export_zip`），不阻塞主线程。真正的瓶颈是**内存**，不是网络：

- `ExportService._load_data` 把 Task / Annotation **全量 `list(...).all()` 进内存**；`_load_dataset_items` 同理（`export_packaging.py:308-311`）。十万 task + 其全部 annotations 的对象列表是内存大头。
- `build_export_zip` 用**单个 `io.BytesIO()`**（`export_packaging.py:338`，视频路径 `:642`）把**整包压缩 ZIP 攒在内存**，再作为 `bytes` 返回（`:258 data, file_count = ...`）后整体上传对象存储。ZIP 全量驻留 RAM。
- ⚠️ **不是网络瓶颈**：图片**不内嵌**导出包——只写 manifest + `fetch_images.py`（`:430`）。`generate_download_url`（`:408/:777`）是**本地 HMAC 预签名，非网络往返**；十万次是 CPU + manifest 行写入开销，可优化但非首要。

合计：十万级导出的内存峰值 ≈ 全量 ORM 对象 + 整包 ZIP bytes，worker 易 OOM。

## 范围（做什么）

### B6-1 DB 读分块化（`services/export.py`，无迁移）
- `_load_data` 不再 `list().all()`：改 `stream()` / `yield_per(N)` 的服务端游标，按 task 分块产出 `(task, [annotations])`。
- 用 `ExportService` 暴露一个**异步生成器** `iter_export_units(project_id, batch_id) -> AsyncIterator[ExportUnit]`，每个 unit = 一个 task + 其 annotations + dataset_item，**惰性**拉取（annotations 按 `task_id` 分块 IN 查询，避免一次拉全表）。
- 保留旧 `_load_data` 给小项目快路径（< 阈值），避免给小导出引入游标开销。

### B6-2 落盘式 ZIP（`services/export_packaging.py`）
- `build_export_zip` / `_build_video_export_zip` 的 `io.BytesIO()` → `tempfile.NamedTemporaryFile(dir=...)`，`zipfile.ZipFile(tmp, "w", ZIP_DEFLATED)` **边遍历 unit 边 `writestr`**，ZIP 落盘而非驻留 RAM。
- worker 上传改**流式 put 文件句柄**（`storage_service` 的 put 支持文件流 / 分块 multipart），不再 `return bytes`。
- 内存与 task 数解耦：峰值 ≈ 单 unit + 压缩缓冲，常量级。

### B6-3 预签名 manifest 优化（次要，按需）
- manifest 行生成保持本地签名，但**批量化**写入（chunk flush）避免十万次单行 IO；可选并发签名。
- 评估把预签名**延后到下载时**（导出包只存相对路径，下载端点临时签名）——更省，但改下载协议，**本版仅评估不强做**。

## 不做（明确排除）
- 不改导出格式 / 目标（YOLO / COCO 等输出不变，仅改产出机制）。
- 不内嵌图片进 ZIP（维持 manifest + fetch 脚本的现有设计）。
- 不做增量 / 断点续导（十万级单次落盘已够；百万级再议）。
- 不强做 B6-3 的下载时签名（仅评估，避免动下载协议）。

## 风险
- **流式与现有派生 schema 的耦合**：`build_export_zip` 先扫全量 annotation 派生 classes/属性 schema（`classes.txt` 等头部文件，`:341`）。流式下需**两遍**：第一遍轻量扫只取类别/属性集合（可只 select 需要的列，不实例化全对象），第二遍流式写 label。需确认第一遍的轻量查询不抵消收益。
- **临时文件清理**：worker 异常 / 超时要保证 `tempfile` 清理（`try/finally` 或 context manager），否则磁盘泄漏。
- **对象存储流式 put**：确认 `storage_service` 后端（MinIO/S3）支持 multipart / 文件流上传；不支持则退化为落盘后整文件上传（仍省了 BytesIO 的 RAM，但上传瞬时读全文件——可接受）。
- **视频导出**：`_build_video_export_zip`（`:601`）是独立路径，同样改造，单独验证（帧序列体量更大）。

## 验证
- 复用种子脚本：10 万 task + 每 task N 条 annotation 的 project。
- **内存基准**：导出 worker 进程 RSS 峰值，改前（全量 BytesIO）vs 改后（落盘流式）——期望从「随 task 数线性增长」变「常量级」。
- **正确性对拍**：同一 project 改前/改后导出 ZIP 解包后**逐文件 diff 一致**（classes.txt / label 文件 / manifest / annotations.json 内容等价，允许顺序差异）。
- **计时**：十万级导出端到端耗时不劣化（流式不应显著变慢）。
- 图像 + 视频两条路径各跑一遍。
- `uv run pytest`（export / workers）；`uvx ruff check`；导出相关 e2e；docs（user-guide 导出章节注明大项目行为）。
