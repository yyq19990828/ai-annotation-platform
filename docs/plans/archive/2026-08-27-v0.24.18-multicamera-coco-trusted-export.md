# v0.24.18 合并式多相机 COCO 可信导出

## 状态

- Date: 2026-08-27
- Status: Completed
- Release target: v0.24.18
- Scope: LiDAR 项目与批次导出、持久化人工相机 bbox、可信媒体回源

## 目标

把 LiDAR 工作台已经持久化的人工相机 bbox 交付为一个标准 COCO Instances 文档，覆盖导出范围内的全部相机 role。产物只声明人工 2D 真值，不把 3D 投影框、缺失关系或漂移媒体伪装成 COCO 标注。

默认输出是一个合并文档；相机 role、Scene、帧和 Scene Track 身份作为兼容的扩展字段保留。普通 COCO 消费方可以忽略这些字段，确需按相机训练的下游可按 `sensor_role` 确定性分片。

## 不做什么

- 不使用 3D→2D 派生投影补齐缺失的人工 bbox。
- 不新增相机 polygon / mask，不改变现有 bbox 数据模型。
- 不要求完整 Scene，不实现官方 benchmark ontology 或 train/val/test split。
- 不扩大 nuScenes 单次导出的规模预算，不建设点云空间流式加载。
- 不新增数据库迁移、环境变量、第三方服务或长期 feature flag。
- 不在本实施提交中切换四处运行版本；日常变更先进入 `CHANGELOG.md` 的 `Unreleased`，发版时再统一切到目标版本。

## 决策

### 1. 公开目标与文件布局

新增 LiDAR 导出目标 `coco-multicamera`。单目标产物落在 ZIP 根目录；与其他目标混选时沿用现有 `{target}/` 子目录规则。

```text
annotations.json
media_manifest.json
fetch_media.py
export_report.json
README.txt
```

`annotations.json` 是一个 COCO Instances 文档。`images[].file_name` 固定为
`images/{sensor_role}/{task_uuid}/{source_basename}`，下载脚本按同一路径物化媒体，避免跨相机、跨数据集同名覆盖。

### 2. 真值与 COCO 映射

- 只查询活跃、未取消、`sensor_role IS NOT NULL` 且 `geometry.type=bbox` 的持久化人工成员。
- 每个相机 DatasetItem 生成一个 image；无人工框的相机图仍保留为负样本。
- bbox 从归一化 `[x,y,w,h]` 转为原图像素，`area=w*h`，`iscrowd=0`。
- category 按项目 `tool_bindings` 的类别顺序生成；未知类别在预检阶段拒绝。
- image 和 annotation 使用输入 UUID/role/version 的 SHA-256 截断值生成不超过 JavaScript 安全整数范围的稳定 ID，并显式检测碰撞。
- `images[]` 扩展保留 `task_id`、`dataset_item_id`、`sensor_role`、可选 `scene_id` 与 `frame_index`。
- `annotations[]` 扩展保留 `scene_track_id`、`track_id`、`sensor_visibility`、标定 revision/digest、`relation_status`；启用属性导出时再携带 `attributes`。
- 标定变化不会改写人工 bbox，也不阻断纯 2D 导出；`relation_status=stale` 和报告计数明确说明它与当前 3D 投影关系已过期。

### 3. 严格预检

项目和批次继续复用现有 LiDAR preflight 端点及导出前/worker 内双重检查。`coco-multicamera` 不要求主点云轴约定或完整 Scene，但必须满足：

- 范围非空，每个任务至少有一个相机 link，且同一任务不能把同一 DatasetItem 绑定给多个相机 role。
- 相机媒体存在，类型为 image，宽高和文件大小为正，S3 对象大小与 DatasetItem 一致。
- 每个相机成员指向当前 task 同 role 的 DatasetItem，bbox 有限、在 `[0,1]` 内且面积为正。
- 每个成员对应同 task、同 Scene Track 的活跃 `box_3d` 主成员，类别和 track identity 一致。
- 类别存在于项目导出类别表，标定 revision/digest 与传感器上下文字段完整。

规模上限固定为单次 20,000 张相机图、100,000 个人工 bbox、20 GiB 媒体总字节，单图不超过 256 MiB。超限在预检阶段以稳定问题码拒绝，避免 worker 为生成 SHA-256 无界读取。

### 4. 可信媒体合同

worker 逐对象流式计算 SHA-256 和实际字节数，不把图片整体载入内存。manifest 保存 DatasetItem、task、role、相对路径、大小、SHA-256、预签名 URL 与过期时间。

`fetch_media.py` 只使用标准库，并执行路径穿越拒绝、已有文件大小/SHA 校验、临时文件下载、下载后校验和原子替换。任何不匹配返回非零状态，绝不把错误媒体当作可训练数据。

导出缓存指纹除标注状态外，还纳入 task/link/DatasetItem/Scene、标定历史和每个相机对象的 HEAD size/ETag；媒体原位替换后不会命中旧包。

### 5. 数据流

```text
项目/批次范围 + coco-multicamera
              │
              ▼
LiDAR preflight ──► link / bbox / parent / media / scale issues
              │ ready
              ▼
API 创建 AsyncJob ──► worker 重检 ──► 媒体 HEAD 纳入 cache key
                                           │
Task + camera links ───────────────────────┤
manual camera bbox + SceneTrack ───────────┼─► 合并 COCO
DatasetItem size + streamed SHA-256 ───────┘       │
                                                   ▼
                         annotations + manifest + fetch + report
```

链路单向，无导出结果回写数据库。

8. 后端/前端测试、Roadmap、用户/开发/API 文档和 `CHANGELOG.md`。

## 验收标准

- 两帧、两个相机、多个持久化人工 bbox 只生成一个 `annotations.json`，全部引用闭合且可由 `pycocotools.COCO.createIndex()` 加载。
- 相同数据库快照重复序列化得到完全相同的 COCO JSON；相机 role 不影响 category identity，也不会产生 ID/path 碰撞。
- 没有人工 bbox 的相机图保留为空标注负样本；没有相机、坏尺寸、坏 bbox、悬空 Scene Track、未知类别和对象漂移均在创建 job 前失败。
- 标定 stale 的人工 bbox正常导出，扩展字段和 `export_report.json` 的 stale 计数一致。
- 下载脚本拒绝 `/`、`..`、反斜杠、盘符、NUL 和重复目标路径；错误大小/SHA 不覆盖已有文件，成功下载原子落盘。
- 项目与批次都能选择目标；与 KITTI/nuScenes/Point Mask 混选时目录互不覆盖。
- cache key 随相机 link、DatasetItem、标定、人工 bbox或对象 ETag 改变。
- 后端定向与全量测试、Web 全量测试、lint、typecheck、OpenAPI 快照和文档构建全部通过。

## 脆弱假设与回滚

本计划假设主流 COCO 消费方会忽略 image/annotation 上的扩展字段。标准必需字段保持原样，因此即使该假设不成立，也只需提供一个剥离扩展字段的后处理，不需要改变数据库或重新导出 bbox 几何。

若上线后发现合并文件不适合某训练链路，下游可按 `sensor_role` 确定性拆分；平台默认仍保持合并，不新增第二个目标或配置开关。若合同本身有误，隐藏 `coco-multicamera` UI/API 目标即可回滚，现有数据、KITTI、nuScenes、AAP JSON 和 Point Mask 不受影响。
