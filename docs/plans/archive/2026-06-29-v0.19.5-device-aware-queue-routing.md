# v0.19.5 · `resource_profile.device` 设备感知队列路由

状态：**已实现**（后端 63 测通过；dev 栈 3 组 worker 已重建并实测队列订阅正确）。消费 v0.19.2
留下的**唯一闲置能力字段** `resource_profile.device`。触及 Celery 队列拓扑 + worker 部署。

**实现要点 / 与草案的偏差**：
- **队列命名复用而非新建**：GPU/缺省队列**复用现有 `ml`**（非草案的 `preannotate.gpu`），仅新增 `ml.cpu`。
  好处: 现有 task_routes / 队列监控 / 排障习惯零改动, GPU 路径与拆分前字节级等价、零退化。
- **路由判据**为纯函数 `resolve_preannotate_queue(devices, gpu_queue, cpu_queue)`（在 `pipeline_validation.py`），
  保守语义: 仅当所有阶段显式 `device=cpu` → cpu 队列; 任一 gpu/未自报(None→gpu) → gpu 队列。单测覆盖。
- **派发**: `batch_predict.delay(...)` 改 `apply_async(args=, kwargs=, queue=)`；device 经 `_stage_device` 从
  health_meta 读（源 + 各下游阶段）。`_mock_celery` fixture 同步改 patch `apply_async`。
- **worker 三组拆分**: 主(`default,media,cleanup,audit`) + gpu(`ml,gpu` 低并发) + cpu(`ml.cpu` 高并发) + 既有 export。
  并发经 `CELERY_GPU_CONCURRENCY`/`CELERY_CPU_CONCURRENCY` env。每队列恰一组消费者, dev 同样可验。
- **实测**: `celery inspect active_queues` 确认四组 worker 订阅 default·media·cleanup·audit / ml·gpu / ml.cpu / export, 全 healthy。
- **未做**（仍在「不在范围」）: 阶段级细粒度跨设备投递；vram_gb 驱动并发。压测(OOM/吞吐)需真实 GPU 负载, 留待生产观测。

## 背景

v0.19.2 WS2 消费了 `resource_profile.batchable`，但 `resource_profile.device`（`gpu` / `cpu`）
至今**完全没被消费**（v0.19.2 附录 sweep 标「暂缓到 registry 调度」）。现状所有预标任务进同一个
Celery 队列、同一组 worker，GPU 模型和 CPU 模型抢同一并发池：

- GPU backend 显存有限，多个 GPU 预标任务并发会 OOM / 排队劣化；CPU 模型（如未来的 OCR det）本可高并发却被 GPU 任务拖。
- v0.19.0 registry 已有 `max_concurrency`（每物理 backend 的并发闸，`ml_backends.extra_params.max_concurrency`），
  但那是「单 backend 限流」，不是「按设备分池」。

## 目标

按模型自报的 `device` 把预标任务路由到对应 Celery 队列（GPU 队列低并发护显存 / CPU 队列高并发），
worker 分组消费，与既有 `max_concurrency` 闸正交叠加。

## 落点

- **读 device**：`apps/api/app/workers/tasks.py::batch_predict` / `_run_batch` 触发时，从 health_meta
  能力快照取源（及各阶段）model 的 `resource_profile.device`，缺省回落 `gpu`（保守，与现状等价）。
  复用 v0.19.2 新建的 `_stage_model()` helper（`projects.py`，可上提到 `pipeline_validation.py`）。
- **路由队列**：`batch_predict.apply_async(queue=...)`，队列名按 device 派生（`preannotate.gpu` / `preannotate.cpu`）。
  Celery app 配置（`app/workers/celery_app.py`）声明两队列 + 默认路由。
- **worker 分组**：`docker-compose.yml` 起两组 worker（`-Q preannotate.gpu --concurrency=1~2` /
  `-Q preannotate.cpu --concurrency=N`），或单 worker 多队列 + 并发上限差异化。dev 可合并为一组消费两队列。
- **多阶段编排的混合 device**：一条流水线里源（GPU detect）+ 下游（CPU classify）device 不同时，
  task 级路由按**整条 pipeline 的最高约束**（有 GPU 阶段 → 进 GPU 队列）保守处理；细粒度按阶段拆队列留后续。
- **配置项**：队列名 / 默认 device / 各队列并发 走 env（`.env.example` 同步 + `pnpm docs:gen-env-vars`）。

## 风险

中。触及任务派发路径 + worker 部署拓扑：
- 队列声明与 worker `-Q` 不匹配 → 任务静默积压（无消费者）。须验证 dev 单 worker 仍消费两队列。
- 回落策略必须保证「老 backend / 无 device → 与现状完全等价」（缺省 GPU 队列、单一 worker 场景零退化）。
- 与 `max_concurrency` 闸的叠加语义要测：队列并发是「设备级」上限，max_concurrency 是「单 backend」上限，二者取小。

## 验收

- GPU 模型预标任务进 `preannotate.gpu`、CPU 模型进 `preannotate.cpu`（celery inspect 可见）。
- dev 单 worker 配置 `-Q preannotate.gpu,preannotate.cpu` 时两类任务都被消费，行为与现状等价。
- 无 device 自报的老 backend → 进默认队列，零退化。
- 压测：GPU 队列并发=1 时多 GPU 预标串行不 OOM；CPU 队列高并发不被 GPU 任务阻塞。

## 排期与依赖

- 依赖 health_meta 可读（已有）。建议复用 v0.19.3 抽出的 `pipeline_validation.py` / `_stage_model`。
- 与 RapidOCR（v0.20.0）有协同：OCR det/rec 若声明 `device=cpu` 正好验证 CPU 队列分流，但二者无强依赖。
- 单独评估部署侧（compose worker 分组），建议先 dev 单 worker 多队列验证再上生产分组。

## 不在范围

- 阶段级细粒度队列拆分（一条 pipeline 跨设备分别投递）：先整条保守路由，按需再细化。
- GPU 显存自动编排（`vram_gb` 驱动并发）：`vram_gb` 当前无 backend 填，归后续。
