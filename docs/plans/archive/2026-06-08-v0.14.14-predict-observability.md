# v0.14.14 · 预标注可观测性 & 协议增强（冷启动真信号 / pool 状态统一 / ModelMarket 运行时态）

> Created: 2026-06-08
> Status: Draft
> 依赖：v0.14.13（预标注交互闭环 · variant 选择器 + 冷启动 UX 本地猜测）

## 0. 背景与动机

v0.14.13 让 yolo 的 variant 选择能在预标注链路上贯通，并给了一个 **"前端本地 sessionStorage 猜测是否首次"** 的冷启动反馈。但这个猜测有明显缺陷：

| 场景 | 问题 |
| ---- | ---- |
| backend pool LRU evict 了某个 variant，前端缓存还在 | 用户切回此 variant 实际是冷加载，但 UI 误判为热命中 |
| 服务重启 / 容器重建 | backend 内存清零，但前端 sessionStorage 还在 |
| 多人协作同项目 | A 用户预热的 variant，B 用户首次用还是冷加载，但 B 的 sessionStorage 是空的 |
| ModelMarket 列表展示 | 现在只能看到"有哪些 variant"，看不到"哪些已加载在内存里" |
| 运维排查显存压力 | `/health` 看不到上次 evict 的原因 / 时间 |

本版本目标：**把"猜"换成"知"**。让 backend 在 `/predict` 响应、`/health.pool` 状态、`/setup` 元数据三个层面输出真实的运行时观测信号，前端基于真信号给精准 UX，运维基于真信号做容量规划。

同时本版顺手统一 3 个 backend 的 `/health.pool` 数据格式（v0.14.12 时三种各异），让前端只写一套渲染逻辑。

## 1. 目标 & 验收

### 1.1 用户视角

- [ ] **冷启动反馈准确**：首次切到尚未加载的 variant 时，按钮文案 `加载模型中（约 8s）…`；命中已加载 variant 时直接 `预标注中…`；同次会话 backend pool evict 后，前端能正确再次进入"加载中"提示。
- [ ] **ModelMarket 显示运行时态**：列表视图新增"运行时"列，每行 variant 显示 `已加载 ◉` / `未加载 ○`，hover tooltip 显示「最近一次推理时间 / 累计调用次数」。
- [ ] **点击预热**：未加载 variant 行的"运行时"列旁边出现 ⚡ 按钮，点一下触发 backend 用 dummy input 预热权重（不需要真实图片），按钮变 loading；完成后状态变 `已加载 ◉`。
- [ ] **运维能看到 evict 历史**：ModelMarket 卡片视图（按 backend 分组）顶部显示 `池容量 3/4 · 上次 evict: 5 分钟前 (lru)`。

### 1.2 协议视角

- [ ] `PredictionResult` schema 新增可选字段：
  - `cache_hit: bool`（True = variant 已在 pool 内、跳过加载）
  - `model_load_ms: int | None`（缺省 = 0，cache_hit=true 时；否则记录加载耗时毫秒）
  - `pool_state: {current_size: int, cap: int} | None`（轻量快照，可选）
- [ ] `/health` 响应 `pool` 字段三 backend 统一为：
  ```json
  {
    "cap": 4,
    "current_size": 2,
    "loaded_keys": [
      {"key": "yolov11-s-detect", "loaded_at": "...", "last_used_at": "...", "hit_count": 12}
    ],
    "last_evict": {"key": "yolov8-x-detect", "at": "...", "reason": "lru"} | null
  }
  ```
  - `key` 是 backend-defined 的 opaque string（yolo 用 `series-size-task`，gsam2 用 `sam=tiny/dino=T`）
  - sam3 单档时 `loaded_keys` 是 `[{"key": "sam3.1", ...}]` 或 `[]`（未加载）
- [ ] `/setup` 新增 `warmup_endpoint: bool`（声明本 backend 是否支持 POST /warmup 接口）。
- [ ] 新接口 `POST /warmup`（仅声明支持的 backend）：
  - Request body: `{variants: {axis_key: value}, ...}` 跟 predict 同结构
  - 行为：加载权重到 pool（不做真实推理），返回 `{ok: true, model_load_ms: int, cache_hit: bool}`
  - 等价于一次"零图片"的 predict，但不消耗推理算力。

### 1.3 验收

- [ ] 后端单测：每 backend 一组测，验证 cache_hit 标志在冷/热场景下的正确性。
- [ ] 后端 e2e 测：连续两次同 variant predict → 第一次 `cache_hit=false`, 第二次 `cache_hit=true`；evict 后再请求 → `cache_hit=false`。
- [ ] 前端 vitest：`usePreannotation` 在 mock backend 返回 `cache_hit` 时按钮文案切换正确；ModelMarket "运行时"列 snapshot。
- [ ] 手测脚本：见 §5。
- [ ] 文档：`docs-site/dev/reference/ml-backend-protocol.md` §4.1/4.2 补三个新字段 + warmup 端点；`docs-site/ops/observability.md`（新建或更新）记 pool 状态可观测口径。
- [ ] CHANGELOG v0.14.14 段：Added / Changed / Tests / Docs。

## 3. 任务清单

### 3.1 Backend：PredictionResult 加 cache_hit / model_load_ms

**文件**：
- `apps/_shared/protocol_v2/predict.py`（或 schema 定义处）
- `apps/yolo-backend/main.py` + `model_registry.py`
- `apps/grounded-sam2-backend/main.py` + `model_pool.py`
- `apps/sam3-backend/main.py`

**任务**：
1. 协议 schema 加 `cache_hit: bool = False`、`model_load_ms: int | None = None`、`pool_state: dict | None = None` 到 `PredictionResult`。
2. yolo-backend：
   - `ModelPool.get_or_load(key)` 改造：返回 `(model, was_cache_hit, load_ms)` 三元组。
   - `/predict` 端点：把 `was_cache_hit` 和 `load_ms` 透传到响应。
3. gsam2-backend：
   - 当前 `_observe()` 已经记录 hit/miss 到 prometheus，改为同时返回到响应体。
   - SAM 和 DINO pool 分别可能 cache hit，组合时 `cache_hit = sam_hit and dino_hit`，`model_load_ms = max(sam_load_ms, dino_load_ms)`。
4. sam3-backend：
   - 单档 model，第一次 predict 触发懒加载时 `cache_hit=false`，已加载时 `cache_hit=true`。
   - Idle unload 后再次 predict 也是 `cache_hit=false`。

**验证**：
```bash
# 第一次 (冷)
curl -X POST localhost:8003/predict -d '{...yolov11-s...}' | jq '.cache_hit, .model_load_ms'
# false  4823

# 第二次 (热)
curl -X POST localhost:8003/predict -d '{...yolov11-s...}' | jq '.cache_hit, .model_load_ms'
# true  null
```

### 3.2 Backend：/health.pool 三家统一

**文件**：同 3.1

**任务**：
1. 在 `apps/_shared/protocol_v2/health.py`（新建 or 复用）定义统一 `PoolStatus` schema：
   ```python
   class LoadedKey(BaseModel):
       key: str
       loaded_at: datetime
       last_used_at: datetime
       hit_count: int = 0

   class EvictRecord(BaseModel):
       key: str
       at: datetime
       reason: Literal["lru", "manual", "idle_timeout"]

   class PoolStatus(BaseModel):
       cap: int
       current_size: int
       loaded_keys: list[LoadedKey] = []
       last_evict: EvictRecord | None = None
   ```
2. yolo-backend：
   - ModelPool 已有 `loaded_keys()`，加 `last_used_at` / `hit_count` 字典维护。
   - evict 时记录到 `_last_evict` 字段。
3. gsam2-backend：
   - 当前 `pool.loaded_variants() / per_variant_lru_ts` 已经接近这个 schema，按需重命名 + 补 `hit_count`。
4. sam3-backend：
   - 当前 `/health.loaded: bool` 改成 `pool: PoolStatus(cap=1, current_size=0|1, loaded_keys=[...])`，cap 永远是 1。

**验证**：3 个 `curl /health | jq '.pool'` 结构一致。

### 3.3 Backend：POST /warmup 端点

**文件**：同 3.1

**任务**：
1. 协议 schema `setup.warmup_endpoint: bool = false`，三 backend `/setup` 都填 `true`。
2. yolo-backend 新增 `POST /warmup`：
   ```python
   @app.post("/warmup")
   async def warmup(req: WarmupRequest) -> WarmupResponse:
       key = _key_from_variants(req.task, req.variants)
       was_hit, load_ms = await _model_pool.warmup(key)
       return WarmupResponse(ok=True, model_load_ms=load_ms, cache_hit=was_hit)
   ```
3. gsam2 / sam3 类似。gsam2 的 warmup 同时预热 SAM + DINO。
4. 行为：加载权重但不跑 forward pass。如果 backend 实现上必须跑一次 dummy forward（如需要 input shape），用最小可能 input（1×1 dummy tensor），不消耗显著算力。

**验证**：
```bash
curl -X POST localhost:8003/warmup -d '{"task":"detection","variants":{"series":"yolov11","size":"s"}}'
# {"ok":true,"model_load_ms":4500,"cache_hit":false}
```

## 6. 风险 & Tradeoff

- **cache_hit 在 gsam2 是组合判断**：SAM hit + DINO miss 时 `cache_hit=false`，但实际只加载一半权重。tradeoff：用户感知"是不是冷启动"层面这个粒度够；如果将来要分轴显示加载耗时，再扩字段。
- **/warmup 可能消耗显存导致 evict 其他 variant**：用户点 ⚡ 期望"预热"，但触发 LRU evict 让另一个 variant 掉出 pool。处理：warmup 响应里加 `evicted: string | null` 字段，前端 toast 提示"已加载 yolov11-x，evict 了 yolov8-n"。
- **多人并发预热**：A 用户点 ⚡ 时 B 同时调 predict，可能竞争同一加载锁。tradeoff：backend pool 已经有 per-key lock（gsam2 有，yolo 需确认），不在本版改造，行为是后到的请求等前一个加载完成、共享同一加载结果。
- **`pool_state` 字段大小**：predict 响应每次带 pool 状态会增加响应体大小；改为可选（默认 None），客户端只在需要时显式请求（query param `?include_pool_state=1`），避免常态开销。
- **sessionStorage deprecate 一版**：v0.14.13 引入的 sessionStorage 命中集合在本版还在跑（作为 fallback），下版才删，避免老客户端突然失去冷启动反馈。

## 7. 与现有版本的关系

- **依赖 v0.14.13**：项目级 `default_variants` 持久化 + VariantSelector + sessionStorage 猜测。本版替换"猜测"为真信号。
- **依赖 v0.14.12**：协议 v2 `supported_variants` / `variant_combinations`。
- **铺垫 v0.14.15**：本版统一了 `/health.pool` 格式但没改 variant 字段名（仍然 series/size vs sam_variant/dino_variant），下版才动协议字段名。
- **不影响 v0.14.9 OCR/doc_layout**：OCR/doc_layout 是 task_type 层面，跟 variant 是不同维度，本版改动正交。
