# v0.19.1 — Python SDK 与全局 ML Backend 注册表对齐（草案）

> 状态：**已实现**（2026-06-29）。承接 [v0.19.0 全局注册表](2026-06-25-v0.19.0-global-ml-backend-registry-draft.md)（ADR-0044）落地后对 `packages/python-sdk` 的兼容性收尾。决策落定：D1=去重合并成一行（修了 TUI `DuplicateKey` 崩溃，非仅展示问题）、D2=平台一并 cut 0.19.1。SDK 测试 150 passed。
>
> 定性：**patch 级**。0.19.0 对 SDK 运行时**已向后兼容、不会崩**（评估见 §1），本版只做「诚实对齐 + 文档纠偏 + 测试补缺」，不引入新 SDK 能力。

## 0. 背景

0.19.0 把 ML backend 从「项目子资源」上提为「全局注册表项 + 项目启用关联」。SDK 仅通过两个只读端点接触 backend：

- `MLBackends.list(project_id)` → `GET /projects/{id}/ml-backends`（`client.py:388`）
- `MLBackends.get(project_id, backend_id)` → `GET /projects/{id}/ml-backends/{backend_id}`（`client.py:392`）

两端点 0.19.0 **保留**，后端 `_out(b, project_id)`（`ml_backends.py:41`）在序列化时把路径里的 project_id **回填**进 `MLBackendOut`，故 SDK 侧必填的 `MLBackend.project_id`（`models.py:187`）运行时仍总有值——**当前不会触发 pydantic 校验错误**。

## 1. 兼容性评估结论（已验证）

## 2. Goals / Non-Goals

### Goals

1. **`project_id` 诚实对齐**：`models.py` 的 `MLBackend.project_id` 从必填 `UUID` 改为 `UUID | None`，反映「全局/admin 场景该字段为 None」的真实 schema（`MLBackendOut.project_id: UUID | None`，`schemas/ml_backend.py:187`）。项目作用域路径下仍由后端回填，行为不变；改的是「未来若 SDK 走全局端点也不炸」的健壮性。
2. **`id` 语义纠偏（文档 + docstring）**：`MLBackend.id` 现在是**全局 registry id**，不再是 per-project 行 id。docstring（`models.py:184`）与 SDK README 说明：同一物理 backend 在不同项目的 `list` 里返回**相同 id**；用户脚本里硬编码的旧 per-project backend UUID 在 0.19.0 迁移后已被 registry_id 取代，需更新。
3. **`list` 语义说明**：`GET /projects/{id}/ml-backends` 现走 `list_enabled_for_project`（`ml_backends.py:114`），只返回该项目**已启用**的全局 backend（迁移把存量 backend 都置为已启用，现网行为一致）。在 `MLBackends` docstring（`client.py:383`）点明「已启用」语义。
4. **测试补缺**：新增 `project_id=None` 的 `MLBackend.model_validate` 反序列化用例，锁住 Goal 1。

### Non-Goals

- **不封装新端点**：全局注册表 CRUD（`/admin/ml-integrations/registry`）、项目启用清单（`/ml-backends/available`、`/{rid}/enablement`）属新增能力，是 **feature 而非 patch**，推到独立的 SDK feature（暂记 0.20.x / 后续 SDK minor），不进 0.19.1。
- 不改 backend 协议、不碰平台端代码。

## 3. 待决策项

### D1 — TUI 多项目共享 backend 的展示重复（本版是否修）

`_render_ml_backends`（`tui/app.py:1494`）用 `self._ml_backends = {str(b.id): b for _, b in rows}` 按 id 去重明细，但 `table.add_row` 逐项目追加（`app.py:1496`）。0.19.0 后同一物理 backend 在 N 个启用项目里返回**同一 registry id**，于是：表格出现 N 行（每项目一行），但点击任意一行的明细 dict 已被去重折叠为一份。**不崩，是轻微展示重复 / 明细错配。**

- **选项 A（推荐，patch 范围内）**：`_load_ml_backends`（`app.py:1361`）聚合时按 `b.id` 去重，多项目共享的 backend 只展示一行；或在「名称」列附所属项目数。
- **选项 B**：本版仅文档标注已知行为，去重留到 SDK feature 版随「全局 backend 列表」一起做。

> 建议在动手前用 `AskUserQuestion` 或口头确认 A/B，避免擅自扩大 TUI 改动面。

### D2 — 版本号承载

SDK 包有**独立版本** `0.15.16`（`packages/python-sdk/pyproject.toml:7`），与平台 `app_version=0.19.0`（`config.py:30`）**不同步**。本「0.19.1」是平台 patch 语境的叙事编号，落到代码：

- SDK 包自身 bump：`packages/python-sdk/pyproject.toml` → `0.15.17`（patch）。
- 平台 `CHANGELOG.md` 在 `## [Unreleased]` 下记 SDK 对齐条目；是否同时把 `app_version`/`apps/web/package.json` 推到 `0.19.1`，取决于本版是否还捎带其他平台改动——**纯 SDK 收尾可不动平台版本号**。动手时确认。
