# v0.18.7 — M7 · 并行扇出规模化（Celery chord）

> 状态：**待实施 plan / 规模驱动按需启动**（不开干）。创建于 2026-06-23。
>
> 定位：路径 B 的吞吐优化，**最大但风险最高**的一项，且**由实测规模压力驱动**——在出现「批量大 + 多分类器，串行 wall-clock 不可接受」之前不启动（ROADMAP §7.1 / CLAUDE.md §2：不为对称而做）。当前 `_run_batch`（`tasks.py:228`）是 `for task in tasks` 串行，且每 task 内下游阶段 + 并行兄弟也顺序跑（`_run_task_pipeline`）；wall-clock ≈ Σ(检测 + Σ各分类)。本期把无交叉依赖的并行单元拆成 Celery `chord` / `group`。

## 1. 目标 / 非目标

**目标**
1. **并行兄弟拆 `group`**：同一父阶段下的并行兄弟分类阶段（无交叉依赖，各写不同键）是天然并行单元，拆成 `group` 并发跑，结果 `chord` 回调合并。
2. **task 级并发**：批内多 task 的检测/富集可在 backend 并发上限内并行分发（受 `MLBackendClient` 的 per-backend semaphore 约束，不打爆后端）。
3. **进度 / 取消 / 失败聚合适配并发**：现有逐 task 串行的进度推送、`_cancel_requested`、`failed_predictions`、逐阶段统计累加，需改造成并发安全的聚合。

**非目标**
- 不改编排语义 / 校验 / 数据模型。
- 不改前端（运行态可视化 v0.18.6 已就绪，消费同样的 `result.pipeline_stages`）。
- 不在无规模压力时启动（本 plan 是 backlog，触发条件见 §5）。

## 2. 详细设计

### 2.1 并发单元划分

- **task 间**：批内各 task 的整条 pipeline 相互独立 → 可并发。受 backend 并发上限（`MLBackendClient._semaphore`，per-backend）天然限流，避免显存爆炸。
- **task 内并行兄弟**：同 `parent_stage` 的下游阶段彼此独立、各写不同键 → `group` 并发；父框检测（源阶段）是它们的共同前驱（`chord` 的 header→body 结构）。
- **顺序链部分**：源阶段 → 下游 是真依赖，保持顺序。

### 2.2 Celery 编排形态（候选）

两种粒度，按实测选：
- **粗粒度（推荐先试）**：保持单 Celery task 内用 `asyncio.gather` 并发跑 task 间 / 兄弟间的 `client.predict`（async 并发，受 semaphore 限流），**不拆多 Celery task**。改造面小、进度/取消仍在一个进程内聚合，多数规模够用。
- **细粒度（真 chord）**：把每 task（或每阶段）拆独立 Celery task，`chord(group(...), merge_callback)`。吞吐上限更高但进度/取消/失败聚合要跨 task 重做，复杂度与风险显著上升。

> 决策：**先做粗粒度 asyncio 并发**（覆盖绝大多数规模），真 `chord` 仅在单进程并发仍不够时再上，避免过度工程。

### 2.3 并发安全的聚合

- 进度：并发下「已完成 task 数」用原子计数 + 节流推送（替换现 `for i, task` 的顺序 `i`）。
- 取消：`_cancel_requested` 改为并发循环中周期检查 + 协作式中断（取消 in-flight 的 gather）。
- 统计：`pipeline_stage_totals` 累加改并发安全（单进程 asyncio 下用顺序回调累加即可；真 chord 下用回调聚合）。
- 失败：`failed_predictions` 收集在并发下保持每 task 独立 try/except，不互相影响。

## 3. 实施步骤（每步带 verify）

1. 基线测量 → verify：固定批量 × 多分类器，记录现串行 wall-clock 作对照。
2. 粗粒度 asyncio 并发（task 间 + 兄弟间，semaphore 限流） → verify：相同输入结果**逐字一致**（与串行对照），wall-clock 下降；后端并发不超上限。
3. 进度/取消/统计并发适配 → verify：并发下进度单调推进、取消能及时停、`result.pipeline_stages` 聚合正确。
4. （仅当粗粒度不够）真 `chord` 拆分 → verify：跨 task 聚合正确、失败隔离、吞吐进一步提升。
5. 版本收尾：bump 四处 + `uv lock` + openapi 快照；重启 worker；`curl /health` 验证 0.18.7。

## 4. 验收标准

- 并发执行结果与串行**逐字一致**（无竞态导致的属性错位 / 框丢失）。
- 多分类器批量 wall-clock 显著下降，后端并发不超 per-backend 上限。
- 进度、取消、逐阶段统计、失败软记录在并发下全部正确。

## 5. 风险 / 开放问题 / 启动条件

- **启动条件（gate）**：仅当实测出现「批量规模下串行 wall-clock 不可接受」时启动；否则维持 v0.18.x 现状（同步顺序）。无压力即上属过度工程。
- **竞态风险**：并发改造是路径 B 最易引入隐蔽 bug 的一步（属性错位、统计错算、取消不干净）。第 2 步「与串行逐字一致」是硬关卡。
- **后端过载**：task 级并发须严格受 `MLBackendClient` per-backend semaphore 限流，否则打爆下游显存。
- **粗 vs 细粒度**：优先粗粒度 asyncio，真 chord 仅按需——避免为吞吐上限牺牲可维护性。
