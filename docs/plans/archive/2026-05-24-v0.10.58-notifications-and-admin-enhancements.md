## A. 通知中心:分组 + 筛选 + 图标 + 加载更多

### A.1 背景
当前 [NotificationsPopover.tsx](../../apps/web/src/components/shell/NotificationsPopover.tsx) 把 21 种类型通知**混成一列纯文字**,无日期分隔、无类型筛选、无图标;`useNotifications` 固定 `limit=30` 且无"加载更多",历史通知看不到。这是体验最大短板。

### A.2 目标 / 非目标
**目标**
- G1:列表按 `created_at` 分组:**今天 / 本周 / 更早**,带分组小标题。
- G2:面板顶部加类型筛选 tab(基于 `target_type`):**全部 / 任务 / 批次 / 反馈 / 后台任务 / 导出**,本地过滤即可(已加载项)。
- G3:每行左侧加类型图标 + 语义色(退回/失败=danger、完成/通过=success、后台任务=ai、反馈=accent),色值**全部取自 tokens.css**(CLAUDE.md §6,禁硬编码/禁 fallback)。
- G4:列表底部「加载更多」,用 `offset` 翻页累积。

**非目标**
- 全文搜索框(可后续);优先级/置顶;声音通知。

### A.3 实施步骤
- **Step A1 — 加载更多(分页)**
  - [useNotifications.ts](../../apps/web/src/hooks/useNotifications.ts):`useNotifications` 改用 `useInfiniteQuery`(getNextPageParam 按 `offset += limit`,`total` 判断是否还有);保持 30s `refetchInterval`。
  - [notifications.ts](../../apps/web/src/api/notifications.ts):`list` 已支持 `offset`,无需改。
  - **验证**:>30 条通知时出现「加载更多」,点击累积加载;30s 轮询不打断已加载页。
- **Step A2 — 类型筛选 tab**
  - `NotificationsPanel` 内维护 `activeFilter` state;tab → `target_type` 集合映射(任务=`task`、批次=`batch`、反馈=`bug_report`、后台任务=`async_job`、导出=`export`)。
  - 本地 `items.filter(...)`(不改后端;已加载数据足够;"全部"不过滤)。
  - **验证**:切 tab 只显示对应类型;空集合显示空状态。
- **Step A3 — 日期分组**
  - 过滤后的 items 按 `created_at` 归入 今天/本周/更早 三组,渲染 `<分组标题 + 行*>`;组内仍按时间倒序。
  - **验证**:跨天通知正确落组;组为空则不渲染该组标题。
- **Step A4 — 类型图标 + 语义色**
  - 在 `NotifRow` 左侧(替换/增强现有 `unreadMarker`)按 `item.type` 前缀渲染 `Icon`:
    - `task.rejected`/`*.failed`/`export.failed` → `alert-triangle` / danger
    - `task.approved`/`*.succeeded`/`*.completed`/`export.ready` → `check-circle` / success
    - `job.*`/`failed_prediction.*` → `cpu`(或现有 AI 图标)/ ai
    - `bug_report.*` → `message-circle` / accent
    - `batch.*` → `layers` / 默认
  - 新增的语义色若 tokens.css 没有,先在 [tokens.css](../../apps/web/src/styles/tokens.css) 补 light+dark 再用。
  - **验证**:`pnpm lint:css-tokens` 通过;暗色模式下图标色可读(preview resize/dark)。

### A.4 验证(整体)
- preview 打开通知面板:分组标题、tab 切换、图标色、加载更多齐全;`pnpm test` 既有 popover 测试(若有)不回归;新增分组/筛选的单测。

## B. 通知:多端已读同步

### B.1 背景
同一用户多设备登录,一端标记已读后,**其他端要等 30s 轮询才刷新**(WS 通道已存在但只推新通知,不推 read 状态)。

### B.2 目标
- G1:`mark_read` / `mark_all_read` / `clear_read` / `delete` 后,经 Redis pub/sub 向 `notify:{user_id}` 广播一条轻量"已读/列表变更"事件。
- G2:前端 WS 收到该事件 → invalidate `["notifications"]`(已有逻辑会刷新);**但不弹 toast、不触发 task.rejected 等业务副作用**。

### B.3 实施步骤
- **Step B1 — 后端广播 read 事件**
  - [services/notification.py](../../apps/api/app/services/notification.py):在 `mark_read` / `mark_all_read` / `clear_read` / `delete_for_user` 成功后,复用现有 `_publish`(发 notify 用的同一通道),发 `{"type": "notifications.sync", "reason": "read"|"deleted"}`。异常不阻断(与现有 pub/sub 容错一致)。
  - **验证**:两个 ws 客户端连同一 user,A 端 mark_read → B 端收到 `notifications.sync`。
- **Step B2 — 前端消费(去副作用)**
  - [useNotificationSocket.ts](../../apps/web/src/hooks/useNotificationSocket.ts) onmessage:对 `type === "notifications.sync"` 仅 `qc.invalidateQueries(["notifications"])` 后 `return`(跳过 task.rejected toast / job invalidate 等业务分支)。
  - **验证**:A 端 mark_read,B 端铃铛未读数与列表即时刷新,无误弹 toast。

### B.4 风险
| 风险 | 缓解 |
|---|---|
| 发起端自己也收到 sync → 多余 invalidate | 无害(React Query 去重);如要省可带 origin 标记,**本版不做** |
| 事件风暴(批量 mark) | mark_all/clear 是单次操作 → 单条事件,无放大 |

## C. 后台:超管「系统健康面板」

### C.1 背景
超管后台**无系统健康视图**(DB/Redis/MinIO/Celery 队列积压、worker 心跳),运维盲区。好消息:[api/health.py](../../apps/api/app/api/health.py) 已实现全部检查(含 Celery `inspect` 队列长度 + 心跳),只需聚合 + 鉴权 + 前端展示。

### C.2 目标 / 非目标
**目标**
- G1:新增 `GET /admin/system-health`(super_admin),聚合 `/health` 各 check + Celery 队列/worker 明细 + 简单阈值判定(ok/degraded/down)。
- G2:前端 `SystemHealthPage`(路由 `/admin/health`),卡片展示各组件状态 + latency + 队列积压,自动刷新(10~15s 轮询)。
- G3:Sidebar 超管区入口 + `permissions.ts` 页面访问。

**非目标**
- 历史趋势图(Prometheus 已有 Gauge,接 Grafana 更合适);告警推送;阈值可配置 UI。

### C.3 实施步骤
- **Step C1 — 后端聚合端点**
  - 新增 `apps/api/app/api/v1/admin_system_health.py`:复用 `health.py` 的 `_check_db/_check_redis/_check_minio/_check_celery`(若为模块私有函数则抽到可复用处或在新端点内并发调用);`Depends(require_roles(UserRole.SUPER_ADMIN.value))`。
  - 返回:`{ status, components: [{name, status, latency_ms, detail}], celery: {workers[], queues[]} }`。
  - 在 [api/v1/router.py](../../apps/api/app/api/v1/router.py) 注册 `prefix="/admin/system-health"`。
  - **验证**:super_admin 拿到聚合;非超管 403;停掉 redis/worker 时对应组件 down/degraded。
- **Step C2 — 前端 API + hook**
  - 新增 `apps/web/src/api/adminSystemHealth.ts`(仿 [adminAnalytics.ts](../../apps/web/src/api/adminAnalytics.ts));hook `useQuery(["admin","system-health"], … refetchInterval: 12_000)`。
- **Step C3 — 前端页面**
  - 新增 `apps/web/src/pages/Admin/SystemHealthPage.tsx`(仿 [AnalyticsPage.tsx](../../apps/web/src/pages/Admin/AnalyticsPage.tsx)):组件状态卡(绿/黄/红用 tokens 色)、Celery 队列积压表(queue/length)、worker 心跳(last_heartbeat_seconds_ago)。CSS module 仅用 tokens。
  - 路由:[App.tsx](../../apps/web/src/App.tsx) 加 `/admin/health`;[constants/permissions.ts](../../apps/web/src/constants/permissions.ts) `super_admin` 加 `admin-health`;[Sidebar.tsx](../../apps/web/src/components/shell/Sidebar.tsx) 超管区加入口。
  - **验证**:preview 以 super_admin 登录 → 入口可见 → 页面渲染各组件状态;非超管路由不可达。

### C.4 风险
| 风险 | 缓解 |
|---|---|
| `celery inspect` 超时拖慢响应 | 复用 health.py 已有 `timeout=2`;端点整体可设短超时 |
| health.py check 函数私有不可复用 | 抽到 `services/health.py` 或新端点内重新实现(优先抽取,避免重复) |

## D. 后台任务模块:进度条 + 详情下钻 + 重试 + 成本

### D.1 背景
[AIPreAnnotateJobsPage.tsx](../../apps/web/src/pages/AIPreAnnotate/AIPreAnnotateJobsPage.tsx) 列表仅表格数值:**无进度条**、`progress_pct` 未可视化;**无详情下钻**(payload/result JSONB 看不全);失败任务**无"重试"按钮**(虽有 `prediction_retry` kind);`result.total_cost` 已记录但**列表/详情未展示**。

### D.2 目标 / 非目标
**目标**
- G1:列表 running/pending 行展示进度条(复用 JobsBell 的进度条思路:按 status 着色,宽度 = `progress_pct`)。
- G2:行点击/「详情」打开 modal,展示 payload(输入摘要)+ result(success/failed/duration/cost)+ error_message 完整内容。
- G3:失败的 `batch_predict` 任务在详情 modal 提供「重试失败项」入口(若已有失败预测重试链路 [predictions_retry.py](../../apps/api/app/workers/predictions_retry.py) 可触发则复用)。
- G4:列表展示成本(`result.total_cost`),详情显示明细。

**非目标**
- 批量取消/重试;优先级队列;高级搜索;video_tracker 取消(单独评估)。

### D.3 实施步骤
- **Step D1 — 进度条(列表)**
  - 列表「状态」列或新增「进度」列:running/pending 渲染进度条(width=`progress_pct`,色按 status,取自 tokens);终态显图标/百分比。
  - **验证**:跑一个 batch_predict,列表进度条随 5% 步长前进(WS/轮询刷新)。
- **Step D2 — 详情 modal**
  - 新增 `JobDetailModal`(或复用现有 Modal/Drawer 组件),点击行打开;调用 [asyncJobs.ts](../../apps/web/src/api/asyncJobs.ts) `get(id)` 取全字段;分区展示 payload / result / error / 时间线(created/started/completed)。
  - **验证**:各 kind 详情字段正确;失败任务显示完整 error_message(列表是 50 字截断)。
- **Step D3 — 重试入口**
  - 调研 `prediction_retry` 现有触发路径(是否有 REST 端点);若有,详情 modal 对失败 batch_predict 显「重试失败项」按钮 → 调用之 → 新建 async_job;若**无现成端点**,标记为本步前置 TODO,本版仅做 D1/D2/D4,D3 拆到后续版本。
  - **验证**:点击重试生成新 job,可在列表追踪。
- **Step D4 — 成本展示**
  - 列表加「成本」列(`result.total_cost`,无则 `—`);详情显示明细;可选:页脚当前筛选结果成本合计(前端汇总已加载项)。
  - **验证**:有 cost 的 job 正确显示;无 cost 显占位。

### D.4 风险
| 风险 | 缓解 |
|---|---|
| 重试链路无现成端点 → D3 范围膨胀 | D3 设为可选,前置调研后决定是否本版做;D1/D2/D4 不依赖它 |
| 进度条频繁重渲染 | 沿用现有 30s staleTime + WS invalidate,不额外加高频拉取 |
