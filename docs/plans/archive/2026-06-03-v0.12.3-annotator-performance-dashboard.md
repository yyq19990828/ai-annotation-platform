## ⚠️ 范围修订（2026-06-03，实施期发现）

> 本文档下方 §1–§8 是**初始设计**，基于「数据源已齐、缺前端面板」的假设设计了一个 DuckDB 后端的 `/admin/performance` 新页。
> 实施期发现该假设**部分错误**，已据此修订范围。保留原设计供追溯。

**关键发现**：`/admin/people`（AdminPeoplePage，v0.8.4）**早已是一个比设计稿更强的标注员绩效页** —— 走实时 PG，已含今日/本周/本月筛选、产能/质量/活跃/周环比排序、人均卡片 + 下钻抽屉（Sparkline 趋势 + Histogram 耗时直方图 + p50/p95 + 项目分布）。§4.1 实际已被它完成约 70%，ROADMAP 该条是 stale。原计划的 DuckDB `/admin/performance` 是在**重造一个已存在且更弱的轮子**（无「今日」、隔夜数据），已废弃。

**v0.12.3 实际落地范围**（补真实缺口，surgical）：
1. **`/me/performance` 标注员自助页**（纯增量）：新端点 `GET /dashboard/me/performance`（强制 self）+ `MyPerformancePage`，recharts 画 4 周产出趋势对标团队均线 + 耗时直方图 + hero KPI。**不触碰已上线的 `/admin/people` detail 端点**（避免回归）。
2. **导航孤儿补全**：`/admin/people` + `/admin/analytics` 此前仅 Dashboard 卡片 / 直达 URL 可达，补 super_admin Sidebar 入口。
3. **保留 recharts**（按用户要求用上图表库，落在 `/me` 的趋势/直方图）。

**诚实延后**：
- **project_admin 项目级绩效**：`/admin/people` 的吞吐/质量聚合当前**不按项目维度切分**，直接放行 RBAC 会让 project_admin 看到用户的跨项目全局数字（误导）。正确做法需给每个聚合加项目过滤 + owner 校验，是对已上线页的实打实手术，留后续版本独立做。
- **IAA / Agreement 面板**：依赖 `precomputed_agreement` 计算管线，独立 epic（同原设计）。

## 1. 背景与现状（已摸底，带出处）

数据源**已基本齐备**，主要缺前端面板与 per-user / 项目级 / 自助维度的聚合查询。

- **`task_events` 表**（[task_event.py](../../apps/api/app/db/models/task_event.py)，migration [0040](../../apps/api/alembic/versions/0040_task_events.py)，v0.8.4）每条标注/审核会话记录：`user_id` / `project_id` / `kind`(`annotate`|`review`) / `duration_ms` / `annotation_count` / `was_rejected` / `created_at`。索引含 `(user_id, started_at)` / `(project_id, started_at)`。
- **DuckDB 离线分析基建**（v0.10.16，§1.6）已就位：`sync_to_duckdb` Celery beat 每日 **02:30 UTC** 增量同步（[duckdb_sync.py](../../apps/api/app/services/duckdb_sync.py) / [workers/analytics.py](../../apps/api/app/workers/analytics.py)），同步时反向 join `Task.reject_reason_type` 捎带进 DuckDB `task_events`。
- **已有 3 个固定面板**（[admin_analytics.py](../../apps/api/app/api/v1/admin_analytics.py) + [analytics_queries.py](../../apps/api/app/services/analytics_queries.py)）：`throughput_daily` / `reject_rate_by_type` / `duration_dist`，`require_roles(SUPER_ADMIN)` 守卫。前端 [AnalyticsPage.tsx](../../apps/web/src/pages/Admin/AnalyticsPage.tsx) 用纯 CSS 条形图渲染。
- **关键缺陷（本版顺手修）**：`/admin/analytics` 路由在 [App.tsx](../../apps/web/src/App.tsx) 存在且带 `admin-analytics` 守卫，但 **Sidebar 没有任何入口指向它 → 导航孤儿**（[Sidebar.tsx](../../apps/web/src/components/shell/Sidebar.tsx) 只挂了 `/admin/health`）。且 [AdminDashboard.tsx](../../apps/web/src/pages/Dashboard/AdminDashboard.tsx) L91-98 有一张「成员绩效」卡片却跳 `/admin/people`（人员管理），命名被占用，需理顺。
- **零图表库**：`package.json` 无 recharts/echarts/...，现有图表是手搓 CSS 条。
- **IAA**：`Task.precomputed_agreement` 字段存在但**无计算逻辑、未同步到 DuckDB** → 本版不做，留 Phase 3 单独 epic。

## 2. 关键决策（已拍板）

| 决策 | 选择 | 理由 |
|---|---|---|
| 图表库 | **引入 recharts**（~40KB gzip） | 直方图/趋势线/排名榜手搓成本高；绩效面板是引库的合理时机点 |
| MVP 范围 | super_admin 全局 + **project_admin 项目级** + **`/me/performance` 个人页** | §4.1 三个受众都覆盖；IAA 延后 |
| DuckDB 时效 | **接受 T+1 陈旧**，面板顶部标「数据截至 \<last_synced_at\>」 | 每日 02:30 同步；"今日"维度先不做实时（实时需双源查 PG，留后续） |
| 命名 | 新页叫 **PerformanceDashboard**（`/admin/performance`），把 AdminDashboard「成员绩效」卡片**重指向**到它 | 与现有 DuckDB AnalyticsPage 区分；消除「成员绩效→人员管理」误导 |
| 复用 | 新面板挂在 DuckDB 同一套查询/同步/RBAC 模式下扩展，**不另起基建** | 决策底线：不为分析重复造数据层 |

## 3. 非目标

- 不做 IAA / Agreement 分布（依赖 `precomputed_agreement` 计算管线，独立 Phase 3）。
- 不做"今日"实时数据（DuckDB T+1，实时需双源，留后续）。

## 4. 后端改动

### 4.1 新增 per-user / 排名 / 自助查询（[analytics_queries.py](../../apps/api/app/services/analytics_queries.py)）

沿用「enum 面板 + 参数化、不收任意 SQL」铁律，新增函数，全部支持可选 `project_id` 过滤、可选 `user_id` 过滤：

- `user_performance_summary(days, project_id=None)` → 按 `user_id` 聚合窗口内：`task_count`（annotate 提交）、`avg_duration_ms`、`total_annotations`、`reject_count`、`reject_rate`（被 review 驳回数 / 提交数）。
- `user_ranking(days, metric, project_id=None, limit=20)` → 按 `metric`(`throughput`|`avg_duration`|`reject_rate`) 排序的 TOP N。
- `user_daily_trend(days, user_id, project_id=None)` → 单用户逐日 `task_count` / `avg_duration_ms` 时间序列（喂 `/me` 趋势线）。
- `team_daily_baseline(days, project_id=None)` → 团队逐日均值（`/me` 对标团队均线用）。

> DuckDB `kind` 维度区分 annotate/review；reject 维度走 `was_rejected` + join 来的 `reject_reason_type`。

### 4.2 新增端点（新建 [admin_performance.py](../../apps/api/app/api/v1/admin_performance.py) + 复用现有 router 风格）

- `GET /admin/performance/summary?days=&project_id=` — 人均绩效汇总
- `GET /admin/performance/ranking?days=&metric=&project_id=&limit=` — 排名榜
- `GET /me/performance?days=` — 自助：返回 `{ self_trend, team_baseline, self_summary }`

**RBAC 收敛**（核心新增点，需新 dependency）：

- super_admin：`project_id` 可空（全局）或任意项目。
- project_admin：`project_id` **必填**，且必须是其拥有/管理的项目（查 `project_members` / owner 校验）；越权返回 403。
- `/me/performance`：任意已认证用户，**强制 `user_id = current_user`**，不接受他人 user_id。

### 4.3 迁移 / 同步

- **无需新表、无需新迁移**：所有维度已在 `task_events` / DuckDB 表内。
- 确认 DuckDB `task_events` 已含 `reject_reason_type`（✓ duckdb_sync.py L52）。
- 若 `user_performance_summary` 的 reject 口径需要 review 事件 join 原 annotate 事件，评估是否在 `analytics.py` 同步阶段补一列，避免查询期重 join——**优先纯查询期解决**，能不动同步管线就不动。

## 7. 风险 / 已知限制

- **DuckDB T+1 陈旧**：面板数据滞后最多 ~24h；MVP 明示"数据截至昨日同步"，"今日"维度暂缺。若客户要实时，后续做"近 24h 走 PG live + 历史走 DuckDB"双源。
- **DuckDB 未初始化**：现有面板已有 503 NotReady 兜底（无 DuckDB 时），新面板复用同一兜底。
- **reject 口径**：reject 归因到 annotate 事件需 review→annotate 关联，注意别把 review 事件自身计入分母；查询期 join 成本可控（已有索引），实测慢再考虑同步期物化。
- **bundle 增量**：recharts ~40KB gzip，过 `check-bundle-size.mjs` 前确认阈值（必要时调 size-limit 预算并在 PR 说明）。
