# v0.22.1 · 视频 AI 追踪入口重构 —— 能力(多目标)↔ 入口(单轨迹)错配治理

- 状态:draft
- 目标版本:0.22.1(A 阶段首发;B 阶段发布号见 §10)
- 日期:2026-07-13
- 关联诊断:能力层彻底多目标,入口层死绑单轨迹,详见 `docs-site/dev/concepts/video-ai-tracking.md`(两类追踪语义)。

---

## 1. 背景与问题

视频 AI 追踪的**能力**(capability 契约 + 三个 ML backend + runner 落库)早已是彻底多目标的:`/predict` 返回带 `instance_id` 的序列,runner 通过 `_partition_results_by_instance` + `_new_discovered_track` 把一次 job fan-out 成多条轨迹。但**发起入口**仍停在"选中一条轨迹、在它身上延展"的旧范式:

- 唯一触发路径要求先选中一条 track(`useWorkbenchShellModel.tsx` 的 Shift+T / Ctrl+B / 卡片按钮 / 右键全部 gated on `selectedTrack`)。
- HTTP 路径把追踪建模成某条 track 的动作:`POST /tasks/{task_id}/video/tracks/{annotation_id}:propagate`。
- DB `video_tracker_job.annotation_id` 是**非空单 FK**。

由此产生三个症状:

1. **入口悖论**:想让 AI"从空白画面按文本发现所有目标",却必须先随便选一条轨迹当锚,而这条轨迹与检测结果无关。
2. **命名混乱**:UI 混用"AI 传播 / AI 追踪 / AI 追踪传播";"传播(propagate)"本义是延展已有轨迹,却背着"文本检测发现新目标"的语义;更与另一套**无关**的"标注传播"(纯几何 + ego pose 运动补偿,`usePredictionPropagation.ts`)撞名。
3. **类别继承坑**:`_new_discovered_track` 里 `class_name=source.class_name` —— 文本检测发现的新目标会盲目继承那条偶然选中的轨迹类别(选中 car 轨迹 + 文本 `pedestrian` → 检出的行人被打成 car)。

> 关键设计约束:架构文档已明确"两类语义(种子驱动 / 文本发现)**都可以多目标,不要用是否多目标区分它们**"。因此本重构**不按单/多目标切开功能**,而是按"追踪对象从哪来"重构入口。

## 2. 目标 / 非目标

**目标**

- 消除入口悖论:AI 追踪成为画布级能力,空画面也能发起。
- 消除命名混乱与类别继承坑。
- 让"文本检测 / 多目标"成为一等公民,同时**不牺牲**"延展单轨迹"的顺手路径。

**非目标(本次不做)**

- 不改动 ML backend 模型层与 runner 的多实例/跨窗关联算法(已就绪)。
- 不做"多选多条已有轨迹一次性追踪"的入口——已排入**下一版本独立 epic**(见 §13);本次只把"选中轨迹"降级为可选来源之一。
- 不重构标注传播(几何那套 `usePredictionPropagation`),仅做命名去撞车。

## 4. 阶段 A — 命名与语义消歧(纯前端,快速止痛)

范围:**不动后端、不动 DB、零迁移**,仅前端文案与展示层。目标是本阶段独立可发布。

### A1 · 命名统一

- 对外统一为「**AI 追踪**」,退役面向用户的"传播"一词(技术内部词保留)。
- `VideoTrackerPropagateDialog.tsx`:`aria-label` "AI 追踪传播" → "AI 追踪";动作按钮"发起传播" → "开始追踪";主标题"AI 追踪"保持。
- 排查并统一残留文案:`rg -n "AI ?传播|发起传播|追踪传播" apps/web/src`。
- **不要**改动 `usePredictionPropagation` / 标注传播那套的用户文案(它是另一套功能),但确认二者文案不再共用"AI 传播"字样。
- 验收:UI 中不再出现"AI 传播/发起传播";`VideoPlaybackOverlay.test.tsx`、`VideoTrackerPropagateDialog.test.tsx` 相应断言更新且通过。

### A2 ·「本次将影响」摘要条

- 在对话框主行下方(或次行)加一条只读摘要,动态显示本次会动哪些轨迹:
  - 有选中轨迹且无额外种子 → "延展轨迹 #{track} · {class_name}"。
  - 有 obj≥2 种子 → "延展 #{track} + 新建 {N} 条轨迹"。
  - 文本检测 → "按文本检测,新建轨迹(暂继承 {class_name} 类别)"。
- 数据来源:`seedTargetCount`、`propagateDialogTrack`、`textDrivenActive` 已在 props 中,纯派生,无新状态。
- 验收:三种场景摘要文案正确;新增单测覆盖派生逻辑。

### A3 · 类别继承显式警示(A 阶段只警示,不修根)

- 文本检测 / obj≥2 模式下,在摘要条内以 `text-status-caution` 提示"新目标将继承选中轨迹类别 {class_name}",让用户知情(根治在 B5)。
- 验收:选中 car 轨迹 + 切文本检测时,可见类别继承提示。

> A 阶段完成即可发 0.22.1(见 §10)。B 阶段可随后迭代。

## 5. 阶段 B — 入口解耦(前端 + API + DB)

核心:把"选中轨迹"从**必要前提**降级为**可选来源之一**;新增不依赖选中轨迹的画布级入口与任务级 API。

### B1 · 前端画布级入口

- **入口落点**:`ToolDock` 视频模式的 **`ai` 工具组**(现有 `smart-point` / `smart-box` / `exemplar` / `magic-box` 之后,`VIDEO_TOOLS` 数组,`ToolDock.tsx:113-116`)新增一项「AI 追踪」。
- **动作型而非模式型**:同组现有工具点击是 `onSetVideoTool(id)` 切画布工具;「AI 追踪」点击应触发 `openPropagateDialog(null)` 打开画布级对话框。ToolDock 对该项特殊分派(不走 `onSetVideoTool`),或引入一个"动作工具"小类型。
- **门控复用**:沿用 AI 组现有三层门控;把 `requiredPrompt`/`isPromptSupported` 换成 tracker 能力协商——`allSupportedTrackers` 非空才可点,否则置灰 + "当前后端不支持追踪" tooltip(与 smart-\* 一致)。
- 与手动 `track`(轨迹 T,`track` 组)天然区分:手画轨迹 vs AI 生成轨迹,分属不同组。
- `openPropagateDialog(annotation)` → `openPropagateDialog(annotation: TrackerSourceAnnotation | null)`;`propagateDialog.annotation` 允许 `null`。
- 保留快捷路径:卡片按钮 / 右键 / Ctrl+B / Shift+T 仍对选中轨迹发起,预填为"延展"模式(annotation 非空)。
- 备选次入口:顶部 AI 按钮(`AIPredictionPopover`)发现性最高,可留一个次要入口;不推荐在时间轴另造孤立入口(脱离已建立的 AI 工具组心智)。
- 验收:无选中态可从工具栏打开对话框;项目未绑 tracker 后端时该工具置灰;有选中态快捷路径行为与今日一致(回归)。

### B2 · 对话框「追踪对象」区

- 把今天隐式的 obj1/obj≥2 显性化为一个「追踪对象」区,明确区分**延展已有** vs **新建**:
  - annotation 非空 → 顶部固定一项"目标① = 轨迹 #{track}(延展)"。
  - annotation 为空 → 无"延展"项,首个种子/文本即目标①(新建)。
- `isPolylineTrack`、`nextKeyframeAfter`、`prevKeyframeBefore` 等依赖 track 的 props 在 annotation 为空时安全降级(range 以当前帧派生)。
- 验收:无源打开时对话框不报错、范围可选、种子/文本可用。

### B3 · 任务级 API(源可选)

- 新增 `POST /tasks/{task_id}/video:track`(命名待定,与既有 `:propagate` 并存),payload 在现 `VideoTrackerPropagatePayload` 基础上增加:
  - `source_annotation_id?: uuid`(可选;给出即"延展"该轨迹)。
  - `target_category?: { class_name: string; tool_unit_id?: string }`(无源 / 文本检测时,新建轨迹用的显式类别)。
- 旧路径 `/tracks/{annotation_id}:propagate` **保留**,内部委托到同一 service,`source_annotation_id` = 路径参数(零回归、平滑迁移)。
- 前端 `videoTracker.ts` 增加 `track(taskId, payload)`;`handlePropagateSubmit` 在无 annotation 时走新方法。
- 验收:新旧两条路径都能建 job;OpenAPI 快照更新。

### B4 · DB 迁移

- `video_tracker_job.annotation_id`:`nullable=False` → `nullable=True`(alembic 迁移;存量数据天然满足,无需回填)。
- 新增列 `target_class_name: str | None`、`target_tool_unit_id: str | None`(无源时落库用)。
- 验收:`alembic upgrade head` 通过;`alembic downgrade -1` 可回滚;既有 job 读写不受影响。

### B5 · runner 无源分支 + 类别显式(根治类别坑)

- `_new_discovered_track(source, output_geometry)` → 类别参数化:优先 `job.target_class_name / target_tool_unit_id`,缺省才回退 `source.class_name`。
- `_persist_tracker_results`:当 `source is None`(无源检测)时,**主实例也走新建**(不再 `apply_tracker_results(source, ...)`),用 `target_category` 建 track;`source` 非空时行为不变。
- `create_tracker_job`:`annotation_id` 变可选,透传 `target_category`;`dataset_item_id` 改从 task/frame 解析(不再只经 annotation 拿)。
- 验收:新增/扩展 `test_video_tracker_multi_instance.py` —— 无源 + 文本检测 → N 条新轨迹且类别取自 `target_category`(不继承任何 source);有源延展路径断言不变。

## 13. 下一版本 epic:多选批量追踪(独立计划,0.22.1 之后)

把"多选多条已有轨迹 → 一次性发起追踪"作为本重构之后的独立计划立项。本次 B 阶段已为它铺好地基,届时是自然扩展而非重写:

- **前端**:复用已有多选态 `selectedIds`(roster / 画布多选)→ 批量「AI 追踪」动作;复用 B 的画布级入口与「追踪对象」区(天然容纳多源)。
- **API**:B3 的任务级 endpoint 从 `source_annotation_id?` 扩展为 `source_annotation_ids: []`。
- **runner**:每条源轨迹作为一个 obj 种子,沿用 B5 的多实例落库(主实例集合各自回填对应源轨迹)。
- **参照物**:几何传播那套已有的多选批量范式 `crossFramePropagateBatch`(`usePredictionPropagation.ts`)可直接借鉴交互。

> 待 B 落地后展开成独立 plan 文件(`docs/plans/<date>-multi-track-batch-tracking.md`)。
