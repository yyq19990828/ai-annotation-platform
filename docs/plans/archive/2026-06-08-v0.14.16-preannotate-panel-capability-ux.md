本计划是「预标注设置深度优化」讨论的落地。讨论结论：
1. **预标注配置面板应常驻**，现在必须先勾选 batch 才出现整块配置区。
2. **面板应按 backend 能力变形**——不同 backend 字段集天然不同（YOLO 闭集检测器无 prompt、输出形态固定；OCR/版面无几何选择），不该用一套写死的面板硬套。
3. **推理参数命名预设**——用户在「AI 预标注」页可保存具名预设（variant + params）并一键复用。
4. **一次只跑一个 backend**——多 backend 仅是"可切换的选项"，不并发、不合并结果，backend 选择器维持单选切换。

按改动性质拆两版：
- **v0.14.16（本版）**：①面板常驻 + ②capability 驱动变形 + ③命名预设。纯前端，消费 v0.14.15 已落地的 capability 字段，低风险。
- **v0.14.17（预案，§5）**：YOLO 闭集类别白名单（暴露 `classes`，渲染 `[index]类名` 勾选）+ 采纳时选类（accept 加 `override_class_name`）。**不做平台类别映射**（用户决策：模型出啥渲染啥，采纳时人选项目类别；NG6 保留）。单独成版。

## 0. 背景与动机

当前批跑预标面板（`apps/web/src/pages/AIPreAnnotate/components/ProjectDetailPanel.tsx`）有两类历史包袱：

**包袱 A — 整块配置区被 batch 选择 gate 住。**
`ProjectDetailPanel.tsx:620` 一行 `{selectedBatchIds.size > 0 && (` 把任务类型 / prompt / backend 选择 / 推理参数 / 输出形态 / 已预标模式 / 运行按钮**全部**包住。未选批次时用户看不到任何配置项，无法预先调参、存预设，交互上"必须先选批才知道这后端能配什么"。

**包袱 B — 面板假设所有 backend 长一样。**
协议 v2（v0.14.12+）已经能逐 model 声明 `task` / `supported_prompts` / `supported_geometric_outputs` / `params`，且 VariantSelector / SchemaForm 已通用化。但**面板整体布局**仍残留"所有 backend 共用同样字段"的痕迹：

| 字段 | 现状 | 对 YOLO(detection) | 对 OCR/doc_layout | 应有行为 |
| ---- | ---- | ---- | ---- | ---- |
| Prompt 文本框（`:654`） | `!isDocMode` 时总显示 | 实为"类别白名单"，非 prompt | 已隐藏 ✅ | 闭集→标签改为"类别筛选(可选)"；开放词表→保留 prompt |
| 输出形态 框/掩膜/全部（`:767`） | 总显示 | 只能 bbox，三选无意义 | 无几何概念 | `supported_geometric_outputs.length<=1` → 隐藏 |
| 任务类型 Tab（`:629`） | 半动态（text 兜底 + ocr/layout 叠加） | — | — | 严格按该 backend `models[].task` 渲染 |

**包袱 C — 参数无具名预设。**
参数值已按 `backend_id` 分桶存 localStorage（`useAiToolParamPrefs`），但只有"上次用的一份"，无法保存多套具名配置（如"高召回档" vs "高精度档"）切换。

本版目标：**让面板常驻、按 capability 变形、支持命名预设**，把"预标前的配置体验"做扎实，且不触碰后端协议（零后端风险）。

## 5. v0.14.17 预案 · YOLO 闭集类别白名单 + 采纳时选类（NG6 保留，不做平台映射）

> 这是用户最初的核心诉求（YOLO 改 `[index]类名` 勾选）。**用户决策（2026-06-08）**：开集模型（gsam2.1 / sam3）走文本 prompt 现状够用；YOLO 这类固定类别模型**不强行做平台层映射**——"模型出啥预标就渲染啥，采纳时由人选项目里设置的类别"。据此本版**不引入 `class_mapping` 通道、不在 worker 改写类名**，NG6「平台不做类别映射」实质**保留**（映射仍由项目 alias 配置 + 人工采纳承担）。因牵动后端协议（仅新增 `classes` 暴露），单独成版，落地时拆独立 plan。

### 5.0 设计基线：映射由 alias 配置 + 人工采纳承担（NG6 不反转）
现状已有一条与 NG6 自洽的链路，本版在其上补缺，不改其性质：
- **alias 自动映射**（`annotation.py:197-231`）：项目标签可配 `alias`；采纳时若预测类名命中某标签的 alias（如"行人".alias=`person`），自动落回项目标签。映射规则由**项目配置**驱动，非平台写死。
- **采纳后改类**（`useImageAnnotationActions.ts:799`，`ClassPickerPopover`）：已支持单条/批量把标注改成项目标签。
- **真缺口**：采纳时若类名既不在标签集、又无 alias 命中 → `_validate_class_name`（`annotation.py:98-130`）**直接 422 拒**，且 accept API 无 body、无法当场选类，用户卡死在"接受不了"。本版补这一刀。

### 5.1 缺口
- **模型原生类别表未暴露**（仅为白名单 UI 服务，不为映射）：`/setup` 的 `labels: []` 被刻意留空；`ModelCapability`（`apps/api/app/schemas/ml_backend.py:85-116`）无 `classes` 字段。⇒ YOLO 无法渲染 `[index]类名` 勾选白名单。
- **类别逐 task 不同，必须逐 model 声明**（探查结论）：yolo-backend 注册 4 个 task，类别**不统一**——
  | task | 权重后缀 | 类别集 |
  | ---- | ---- | ---- |
  | detection | （无） | COCO-80 |
  | segmentation | `-seg` | COCO-80（同 detection） |
  | keypoint | `-pose` | COCO-80 检测类 + 17 个写死关键点名（`predictor.py:34` `COCO_KEYPOINT_NAMES`） |
  | obb | `-obb` | **DOTA-15（plane/ship/…，与 COCO 完全不同）** |
  ⇒ `classes` **必须逐 model（逐 task）声明**，绝不能 backend 全局一份。
- **类别从权重 metadata 读，不要硬编码**：ultralytics `.pt` checkpoint 自带 `model.names`（官方权重与**用户自训练权重一视同仁**），`predictor.py:184` 已在用 `getattr(model, "names", {})` 读取。⇒ `classes` 一律从权重 `model.names` 取，**不写死 COCO-80/DOTA-15 常量**（写死会丢自训练的自定义类别）。唯一约束是**时机**：`/setup` 阶段权重可能尚未下载、names 读不到。落地方案：在 **warmup / `capabilities/refresh`**（健康探测时已 probe）权重加载后，把该 (task, series, size) 的 `model.names` 填进 capability 快照的 `models[].classes`；可只 `torch.load` checkpoint 读 names、不必跑推理，成本低。前端在 `classes` 尚未就位时回退到文本筛选框，预热后自动升级为勾选白名单。
- **采纳时无法选类**（见 §5.0 真缺口）：accept API 无 body，类名不匹配即 422 拒。

### 5.2 协议补丁（最小，仅 `classes` 暴露 + accept 选类）
1. **逐 model** 给 `ModelCapability` 加结构化类别表（YOLO 各 task 各带自己的表；开集模型缺省/空）：
   ```jsonc
   // models[].classes —— 每个 task 条目各带自己的表
   "classes": [ { "index": 0, "name": "person" }, { "index": 2, "name": "car" } ]   // detection/seg
   "classes": [ { "index": 0, "name": "plane" }, { "index": 1, "name": "ship" } ]   // obb (DOTA)
   ```
   `classes` 非空 ⇒ 闭集 ⇒ 前端渲染勾选**白名单**；空/缺省 ⇒ 开集/未知 ⇒ 文本 prompt。同时驱动 §1.2 的 `promptKind` 判定（v0.14.16 暂用 `supported_prompts===['none']` 近似，本版收敛为以 `classes` 为准）。
   - **keypoint 特例**：其"类别"语义分裂（检测 80 类 + 17 关键点名），白名单对 keypoint 的呈现单独设计；不处理则退回文本框，不要套 detection 的勾选。
   - **闭/开集判定必须逐 model，不可按 backend 名硬分**（前向兼容，见 §8）：YOLO 官仓已有 YOLO-World / YOLOE（yolo26e）这类**开集检测/分割**模型，未来同一 yolo-backend 可能同时挂闭集（detect/seg/obb，有 `classes`）与开集（yolo-world/yoloe，`supported_prompts` 含 `text`、无固定 `classes`）。`panelShape` / `promptKind` 一律以**该 model 的 `classes`+`supported_prompts`** 为准，严禁 `if backend.name==='yolo'` 之类按 backend 名的分支。
2. **不新增 `class_mapping`**（用户决策）。预标结果照旧携带模型原生类名（`person`/`car`），渲染即原样——与现状一致，零改动。
3. `accept_prediction`（`apps/api/app/api/v1/tasks.py:1490`）加**可选请求体** `{ override_class_name?: str }`：传入时以它替代预测类名、并照走 `_validate_class_name`；不传时维持现状（alias 映射 + 软校验）。

### 5.3 前端：YOLO 类别勾选**白名单**（无映射下拉）
替换 YOLO 的"car, person"文本框为每类一行勾选（去掉右侧映射下拉，仅决定"跑哪些类"）：
```
☑ [0] person
☑ [2] car
☐ [1] bicycle   （不检出）
```
勾选集合 = 类别白名单，随请求下发。预标结果渲染模型原生类名，不在此处映射。
> **已验证（2026-06-08）**：YOLO backend **当前完全忽略 prompt，不做任何类别过滤** —— worker 把 prompt 放进 `context.text`（`tasks.py:113`），但 yolo `Context` schema 无 `text` 字段（`schemas.py:56`），`predictor.predict_one` 只读 `variants`/`params`，`_emit_*` 直接输出全部检出类（`predictor.py:200`）。⇒ **v0.14.17 必须在 yolo-backend 新增按类别子集过滤的能力**（最优雅：把白名单类名→`model.names` 的 index，传 ultralytics `model.predict(classes=[...])` 原生过滤）。这也意味着 v0.14.16 没有改 YOLO 文本框语义是对的（只改 UI 标签而无后端过滤＝过度承诺）。
>
> 🔴 **已复现的真 bug（2026-06-08，对运行中的 yolo-backend:8003 实测）：YOLO 批量预标当前必然 422 失败。**
> - worker 给文本批量预标发 `context.type="text"`（`tasks.py:115`），但 yolo `Context.type` 是 `Literal["detection","segmentation","keypoint","obb"]`（`schemas.py:59`）。
> - 直接 `curl POST /predict` 带 `context.type="text"` → **HTTP 422** `{"type":"literal_error","loc":["body","context","type"],"msg":"Input should be 'detection', 'segmentation', 'keypoint' or 'obb'"}`。
> - 链路确认无 task 派生：`ml_client.predict` context 直传（`ml_client.py:177`）；endpoint `trigger_preannotation` 把 `task_type=body.task_type` 直传 worker、**不从 `project.type_key` 派生**（`projects.py:1269`）；前端非 doc 分支**不发 `task_type`**（ProjectDetailPanel onRun 非 doc baseArgs 无 task_type）。⇒ task_type=None ⇒ worker `context.type="text"` ⇒ YOLO 422。
>
> **这是 v0.14.17（乃至 YOLO 预标可用性）的前置阻塞，必须先修：** 把 YOLO 的 task 路由接通。需要决策"YOLO task 怎么选"——候选：① 输出形态 框/掩膜 直接映射 detection/segmentation（最贴合现有 UI，但 keypoint/obb 无对应）；② 由 `project.type_key`（image-det→detection / image-seg→segmentation）在 endpoint 或 worker 派生 `task_type`；③ 面板显式让用户选 YOLO task。修通前，v0.14.17 的"类别白名单过滤 / classes 暴露"都无法端到端验证。
>
> **对 v0.14.16 的影响**：本版的"输出形态按 capability 隐藏"对 YOLO 无功能回退（YOLO 现在 predict 直接 422、且 predictor 忽略 `context.output`，输出形态对 YOLO 本就 no-op）；但若上面选了方案①（框/掩膜=YOLO task 选择器），则 YOLO 不应隐藏输出形态——需在修 bug 时一并复核 `derivePanelShape` 对 YOLO 的输出形态策略。

### 5.4 采纳时选类（补真缺口）

### 5.5 v0.14.17 验收要点

## 6. 风险 & Tradeoff
- **v0.14.16 面板常驻后空状态体验**：未选项目/backend 时面板可能大片空白。落地：无 backend 时显示引导文案（"请先在项目设置绑定 ML Backend"），不渲染空参数面板。
- **capability 变形误判**：若某 backend capability 声明不全（无 `supported_geometric_outputs`），变形逻辑要有安全兜底（缺字段时维持现状显示，不强行隐藏），避免把可用字段藏没了。
- **预设 localStorage 跨设备不同步**：用户换浏览器/设备预设丢失。本版接受此限制，§2.2 已列 DB 化为后续。
- **16/17 衔接**：16 对 YOLO 只正名不换控件，保证不丢"类别白名单"能力；17 再换结构化控件。两版之间 YOLO 始终可用文本框填类别名。
- **promptKind 判据演进**：16 用 `supported_prompts===['none']` 近似闭集，17 引入 `classes` 后改以 `classes` 非空为准——需在 17 同步收敛 `panelShape` 判据，避免双标准并存。

## 7. 与现有版本的关系
- 依赖 v0.14.15：capability 派生视图（`models[].supported_prompts/supported_geometric_outputs/task`）、model_variants、SchemaForm/VariantSelector 通用化。
- v0.14.16 纯前端，不影响后端/外部 backend。
- v0.14.17 触动协议（`ModelCapability.classes` minor 增字段，向后兼容：老 backend 不声明即视为开放词表），不破坏现有 backend。
