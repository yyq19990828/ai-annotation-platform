# v0.23.33 · 连接器运维闭环与可靠性优化

> Status: completed · 2026-08-14
>
> 触发来源：[ROADMAP「连接器主机白名单的超级管理员 UI」](../../../ROADMAP.md)

## 1. 结论

本版建设一个小而完整的「连接器运维闭环」：超级管理员可在系统设置中查看、编辑和恢复部署默认的
连接器主机白名单；后端对条目做统一语法校验与规范化；同时修复现有 SFTP 私钥在“测试连接”和
“实际导入”两条路径解析能力不一致，以及连接器操作失败缺少明确反馈的问题。部署方显式配置目标
主机后，超级管理员还可从“部署主机 SFTP”快捷项预填现有 SFTP 表单，再补专用账号凭据完成创建。

不新增连接器类型、数据库表、后台服务或依赖，也不把本版扩成通用集成平台；只增加一个非敏感、
默认关闭的部署主机地址环境变量，继续复用现有 SFTP 连接器、白名单和密钥加密能力。

备选方案是只补白名单 UI、完全不动后端合同；本计划不采用，因为它会把非法条目继续写进数据库，
且保留已经公开记录的 SFTP 测试漂移。两项根因修复都能复用现有代码，额外风险很低。

## 2. 现状证据

- 后端已有仅超级管理员可用的 `GET/PUT /storage-connections/allowlist`，白名单已经在连接器创建、
  更新、测试和导入前强制执行；前端 `storageConnectionsApi` 与 hooks 尚未暴露这两个端点。
- 历史设计已决定白名单属于全局安全控制，应放在“设置 → 系统设置”，而不是数据集页的连接器入口。
- 当前 PUT 只做 trim 和去空，非法 CIDR、URL、通配符或带路径的域名会被保存后静默失效。
- DB override 一旦写入，没有 HTTP/UI 入口调用既有 `SystemSettingsService.reset()` 回退到
  `CONNECTOR_HOST_ALLOWLIST` 部署默认值。
- `SftpSource` 计划支持 RSA / Ed25519 / ECDSA 私钥，连接测试仍只调用 `paramiko.RSAKey`；旧实现还
  引用了当前 Paramiko 5 已移除的 DSS 类型，导致私钥解析路径可能先行报错。
  用户手册因此不得不提示“测试失败但导入可能成功”。
- `StorageConnectionsPanel` 对 create/update/test/delete 的 4xx mutation 缺少本地失败反馈；全局 API
  客户端只自动提示 403 与 5xx，白名单拒绝等 400 响应可能只留下 rejected promise。
- 本地开发库当前没有 `storage_connections` 行，也没有连接器相关 Bug Report。没有证据支持本版增加
  目录浏览器、持久化健康状态或连接器使用分析。
- 数据导入由容器内 `celery-worker` 执行；仓库没有把宿主机任意目录挂进 worker，因此新增“本地文件”
  连接器会扩大文件系统信任边界。现有 SFTP 已能覆盖部署主机文件导入。
- Compose 只为监控服务配置 `host.docker.internal:host-gateway`，API 与通用 worker 没有共同、稳定的
  “部署主机”别名；由应用自动猜测宿主地址会在 Linux、Docker Desktop 和自定义网络间漂移。
- 通用 worker 已只读挂载 `config/ssh/known_hosts`，生产 API 容器尚未挂载；这会让 SFTP“测试连接”与
  worker 实际导入使用不同的 host-key 信任环境。

## 3. 目标与成功标准

1. 超级管理员无需调用 API 或修改数据库，即可管理连接器主机白名单。
2. UI 明确区分“部署默认”与“数据库覆盖”，并能删除 DB override、恢复部署默认。
3. 非法条目不能落库；合法条目按稳定规则规范化、去重后保存。
4. 保存空白名单前明确提示会阻断连接器创建、更新目标、测试与导入。
5. SFTP 当前支持的 RSA / Ed25519 / ECDSA 私钥在测试与导入路径使用同一个解析函数，测试结果不再因
   key 类型漂移；移除 Paramiko 5 已删除的 DSS 引用。
6. 连接器创建、编辑、测试和删除失败均有可见错误，不产生未处理 Promise rejection。
7. 新建 S3/OSS 连接器默认启用 HTTPS；编辑已有连接器保持其已存 `use_ssl` 值。
8. 部署方显式配置目标主机后，超级管理员可一键打开已预填 host/port 的 SFTP 表单；未配置时不展示
   快捷项，也不自动探测、自动放行或自动写入凭据。
9. 生产 API 与 worker 使用同一份只读 `known_hosts`，SFTP 测试与导入不再因容器挂载差异漂移。

通过标准：超级管理员完成“查看 → 修改 → 保存空名单确认 → 恢复部署默认”闭环；项目管理员看不到
白名单及部署主机快捷项，直接调用端点仍得到 403；lint、类型、前后端定向测试、OpenAPI 和生产构建
全部通过。

## 4. 明确不做

- 不做连接器源目录浏览器、分页列目录或文件预览；继续手填 `source_path`。
- 不持久化 last-tested-at、健康状态或连接器使用次数，不新增迁移。
- 不做保存前 DNS 影响面 dry-run；白名单改错不会阻断平台登录，管理员可立即改回或恢复部署默认。
- 不做 SFTP host key 的 TOFU、上传 known_hosts 或指纹管理 UI；继续由部署侧可信 known_hosts 管理。
- 不自动探测 Docker gateway、请求 Host、网卡地址或公网域名作为部署主机；目标必须由部署方显式配置。
- 不自动把部署主机加入白名单，不自动采集 SSH 密码，也不推荐使用 root 或日常部署账号；使用专用、
  只读、最好禁用 shell 的 SFTP 账号，私钥优先，密码只作为现有表单支持的次选。
- 不新增能读取任意宿主路径的 `local` 连接器或 bind mount；若以后确有无 SSH 的离线导入需求，另行
  设计固定只读 staging 目录，不与本版快捷项混合。
- 不做 webhook、邮件、第三方 SaaS connector 或通用 connector SDK。
- 不改变复制入库、owner/global 作用域、密钥加密和导入上限。

## 5. 选定方案

### 5.1 入口与数据流

白名单 UI 放在 `设置 → 系统设置`，作为独立 Card 和独立保存状态，不并入现有注册/SMTP 表单，避免
两个安全配置共享 dirty state 或一次提交互相覆盖。

```text
SettingsPage (super_admin)
  └─ ConnectorAllowlistSettings
       ├─ GET /storage-connections/allowlist
       ├─ PUT /storage-connections/allowlist
       └─ DELETE /storage-connections/allowlist
                         │
                         ▼
              SystemSettingsService
              connector_host_allowlist
                         │
                         ▼
              connector_guard（运行时门禁）
                 ├─ create / update
                 ├─ test
                 └─ dataset import
```

拒绝把白名单放进“数据集 → 数据连接器”标签：那里是连接器的管理和使用入口，白名单是影响全平台出网
能力的安全策略；沿用既有系统设置归属能保持产品语义与权限边界一致。

### 5.2 白名单 API 合同

扩展现有响应，不另建通用 settings API：

```jsonc
{
  "entries": ["10.0.3.0/24", ".aliyuncs.com"],
  "source": "database", // "database" | "environment"
}
```

- `GET /storage-connections/allowlist`：返回当前有效条目及来源。DB 有 override（包括显式空数组）时
  `source=database`，否则返回 `CONNECTOR_HOST_ALLOWLIST` 并标记 `environment`。
- `PUT /storage-connections/allowlist`：校验、规范化并去重后写 DB override；返回
  `source=database`。空数组仍是合法的显式 deny-all。
- `DELETE /storage-connections/allowlist`：调用既有 `SystemSettingsService.reset()` 删除 DB override，
  返回回退后的有效条目与 `source=environment`。
- 三个端点均只允许 `super_admin`；PUT/DELETE 沿用 `connector.allowlist_update` 审计动作，detail 只记
  `mode=override|reset` 与条目数量，不记录完整策略值。

`source` 是向后兼容的新增响应字段；没有数据库迁移。

### 5.3 条目校验与规范化

在 `connector_guard.py` 增加一个纯函数，PUT 与测试共用；运行时匹配仍沿用现有
`assert_host_allowed()`：

- 请求最多 256 条，每条最多 253 个字符；超限返回 422。
- trim 空白，域名转小写并移除末尾 `.`；保留后缀域名前导 `.`。
- 单 IP 由 `ipaddress.ip_address()` 规范化；CIDR 由 `ipaddress.ip_network(strict=False)` 规范化。
- 精确/后缀域名按 IDNA 后的 label 规则校验：label 1–63 字符，只允许字母、数字和中划线，且首尾
  不能是中划线。
- 明确拒绝 scheme、路径、端口、`*` 通配符、空后缀和无法解析的 CIDR/域名。
- 规范化后按首次出现顺序去重。
- 不禁止大网段或宽域名后缀；UI 给出“范围越宽，出网授权越大”的警告，HARD_BLOCK 仍在每次实际
  连接前无条件生效。超级管理员对策略范围负责。

环境变量继续由现有 Settings validator 解析为列表；DB override 通过新校验后写入。现有部署默认不做
自动改写，避免一次 UI 功能升级改变生产 env 语义。

### 5.4 超管 UI

新增 `ConnectorAllowlistSettings`：

- 标题“连接器主机白名单”，状态 Badge 显示“部署默认”或“数据库覆盖”。
- 用可删除的条目行展示当前值；单一输入框 +“添加”按钮，回车等价添加。
- 输入阶段即复用前端等价的轻量语法检查；服务端仍是最终信任边界，400/422 错误显示在 Card 内。
- 提供四种示例与永久拒绝说明，不隐藏“空名单 = 全拒”。
- `保存覆盖` 只在 dirty 时可用；空数组保存前使用既有 `AlertDialog` 二次确认。
- `恢复部署默认` 仅在 `source=database` 时可用，确认后调用 DELETE；不修改 env。
- loading、读取失败、保存失败、恢复失败分别有独立状态；失败不清空当前编辑草稿。
- 非超级管理员不渲染系统设置 tab，因此组件不发请求；后端 403 仍是最终边界。

### 5.5 连接器可靠性小修

- 将 `services/sources/sftp.py` 的私钥解析函数作为唯一实现，连接测试直接复用，不再在
  `storage_connection.py` 单独写 RSA-only 分支。
- `StorageConnectionsPanel` 的 create/update/test/delete mutation 全部补 `onError`/catch toast，直接展示
  API detail；成功行为不变。
- 新建 S3 表单的 `use_ssl` 初值改为 `true`；编辑态仍读取连接器已存值。

这三个修复相互独立于白名单 UI，可单独合并；即使可靠性小修延期，白名单运维闭环仍可发布。

### 5.6 部署主机 SFTP 快捷项

复用现有 SFTP 创建表单，不新增 `local` kind 或系统生成连接器：

- 新增 `CONNECTOR_DEPLOYMENT_SFTP_HOST`，默认空。它只保存一个可由 API 与导入 worker 共同访问的
  hostname/IP，不包含用户名、密码、私钥、路径或放行规则。
- 新增仅 `super_admin` 可读的 `GET /storage-connections/deployment-sftp-preset`；固定返回
  `enabled`、`host` 和默认端口 `22`。env 为空时 `enabled=false`，不从请求域名或容器网络推断地址。
- 数据连接器页仅在 `enabled=true` 且当前用户为超级管理员时显示“添加部署主机”快捷按钮。点击后复用
  现有新建弹窗，预填名称、SFTP、host、port，作用域默认 `owner`；用户名、认证方式、凭据和
  `base_path` 仍由超管填写，切换 `global` 必须显式操作。
- 快捷项不绕过 `connector_guard`。目标仍须在有效白名单内，且部署侧必须把对应 host key 写入
  `config/ssh/known_hosts`；缺任一项时沿用现有明确错误，不做隐式修复。
- 生产 API 增加与 worker 相同的只读 `known_hosts` 挂载，使 test/import 共享信任源。
- 文档推荐创建只能读取导入 staging 目录的专用 SFTP 账号。密码仍由现有 Fernet 密文存储支持，但
  私钥优先；平台一旦失陷可能解密连接器 secret，因此最小主机权限仍是必要边界。

选择这个方案而不是“直接读取部署服务器目录”：现有 SFTP 已覆盖需求，新增一种连接器、迁移和宿主
目录挂载只会扩大攻击面。选择显式 env 而不是自动探测：API 与 worker 的网络命名空间不同，自动值
无法保证两条路径都可达。

## 6. 实施切片

### 切片 A：白名单运维闭环

1. 扩展 allowlist schema、来源判定、规范化与 DELETE reset API。
2. 补后端纯函数/API 权限、来源、空 override、reset、审计测试。
3. 增加前端 API/hooks、超管设置 Card 与组件测试。
4. 更新 OpenAPI、用户/开发/API 文档。

验收后系统已可独立使用；不依赖切片 B。

### 切片 B：连接器可靠性小修

1. 连接测试复用 SFTP 三类当前私钥解析函数并补参数化测试。
2. 补连接器四类 mutation 失败反馈测试。
3. 新建 S3 表单默认 HTTPS，编辑旧配置回归不变。

验收后单独提升现有连接器体验；不依赖切片 A。

### 切片 C：部署主机快捷添加

1. 增加单一非敏感 env 与超级管理员 preset 只读端点。
2. 在现有连接器面板增加条件式快捷按钮，复用现有 SFTP 表单与创建 mutation。
3. 为生产 API 补齐只读 `known_hosts` 挂载，并更新部署与连接器安全文档。

验收后部署主机可作为现有 SFTP 的快捷目标；不依赖切片 A/B，也不改变未配置部署的行为。

内置浏览器实操：

1. 超管进入 `/settings` → 系统设置，确认白名单 Card 和来源 Badge。
2. 保存域名、后缀域名、IP、CIDR，刷新页面确认规范化结果持久化。
3. 尝试 URL、带端口 host 和通配符，确认不能保存且错误明确。
4. 保存空名单，确认二次警告；到数据连接器页创建/测试连接器，确认被 deny-all 拒绝且 UI 可见错误。
5. 恢复部署默认，确认来源切回 environment；项目管理员登录后看不到白名单 Card。
6. 用一条白名单内的可达 S3/MinIO 连接器测试成功；SFTP 若本地没有可信 known_hosts/密钥，仅验证表单
   与自动测试，不把外部环境缺失判为功能失败。
7. 以显式 `CONNECTOR_DEPLOYMENT_SFTP_HOST` 启动 API，超管确认出现快捷按钮并预填 host/22；确认仍须
   输入用户名、凭据和路径，且未被自动加入白名单。去掉 env 后重启，确认快捷按钮消失。
8. 若本机已有受限 SFTP 测试账号与可信 host key，完成“快捷创建 → 测试 → 发起小目录导入”；没有该
   外部条件时以 preset、权限、门禁自动测试和浏览器表单实操为验收，不输入日常部署账号密码。

## 9. 风险、失败处理与回滚

- **最脆弱前提**：部署方能提供一个 API 容器与导入 worker 都可达的 SSH 地址，以及最小权限 SFTP
  账号。无法满足时 preset 保持关闭；不以自动猜测地址或挂载整个宿主文件系统兜底。
- 超级管理员当前需要的是可安全编辑策略，而不是保存前查看“哪些连接器会被阻断”的影响面。若生产
  出现多连接器批量改名单或误切断事故，再增加只读 dry-run；本版不提前建设。
- 外部 DNS/S3/SFTP 故障不影响白名单保存：PUT 只做语法校验，不发起网络连接。运行时 test/import
  继续按现有门禁失败并给出明确原因。
- 256 条上限限制匹配开销；当前校验仍是 `解析 IP 数 × 白名单条目数`，在该上限内无需索引结构。
- 回滚 UI/API 不触碰连接器或导入数据；若需撤回 DB override，先调用 DELETE 恢复 env，再回滚代码。
- SFTP 复用解析函数只删除重复实现，回滚可恢复原 RSA-only 调用，不迁移密钥。
- 关闭部署主机快捷项只需清空 env 并重启 API；已创建的 SFTP 连接器保持普通连接器语义，不受 preset
  开关影响。
- 不需要新 API key、第三方账号或 CLI；浏览器实操只使用现有本地登录态与可选本地存储/SFTP 服务。
