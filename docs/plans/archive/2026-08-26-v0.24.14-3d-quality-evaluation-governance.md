## 1. 结论

本版本把已上线的 3D Quality 从“能发现问题”推进到“能用真实处置数据评估、比较和安全调整规则”。系统会保存显式人工判定、冻结评估样本与候选配置，按规则和类别计算观察精度、误报率和已确认问题保留率，通过晋级门后才能替换项目生效配置。

人工处置不是 Ground Truth：本版本不计算绝对 recall，不引入隐式 honeypot，不把同一标注的单次审核冒充 Consensus / IAA。只有未来引入独立、不可变的 GT 标注集后，才允许显示绝对 precision / recall。

## 2. 用户闭环

```text
3D Quality Issue
      │ reviewer verdict: confirmed / false_positive / accepted_exception / uncertain
      ▼
Frozen Evaluation Snapshot ── baseline config + candidate config
      │ replay tunable rule predicates
      ▼
Per-rule / Per-class Metrics
      │ sample gate + FP gate + confirmed-retention gate
      ▼
Promotion Decision ── atomic project config revision update ── next quality run
```

评估快照创建后不随 issue 之后的处置修改而漂移。晋级只改项目规则配置，不自动修改 issue、Annotation、SceneTrack 或历史 Run；新配置的效果由下一次显式质量扫描产生。

## 3. 人工判定与指标口径

### 3.1 判定与工作流状态分离

- `confirmed`：审核者确认规则发现了真实问题；对应 issue 通常进入 `resolved`。
- `false_positive`：规则误报；对应 issue 进入 `wont_fix`，并必须记录原因。
- `accepted_exception`：信号本身真实，但当前项目接受该例外；不纳入精度分母。
- `uncertain`：当前证据无法判断；不纳入精度分母。
- `open / resolved / wont_fix / stale` 仍表达工作流状态，判定表达评估语义，两者不再混用。重新打开 issue 会清除旧判定，避免把已推翻的结论纳入新评估。

### 3.2 指标

- 观察精度 = `confirmed / (confirmed + false_positive)`。
- 观察误报率 = `false_positive / (confirmed + false_positive)`。
- 候选确认保留率 = 候选阈值仍会触发的 `confirmed / baseline confirmed`。这是在已发现样本上的保留代理，不是 recall。
- `accepted_exception / uncertain / unreviewed / stale` 单独计数，不静默混入好样本或坏样本。

报告同时按 rule code 和 class name 切片。轨迹级问题的 class 取 SceneTrack 权威类别；无类别的历史数据显示为 `__unknown__`，不猜测。

## 4. 配置与晋级门

`PointCloudQualityConfig` 升级为 schema revision 2，新增：

- `class_thresholds`：按 class name 保存稀疏阈值 override，未覆盖字段回退全局阈值。
- `governance.minimum_reviewed_per_rule`：变更规则进入晋级判定前的最小可判定样本数。
- `governance.maximum_false_positive_rate`：候选触发集的最大观察误报率。
- `governance.minimum_confirmed_retention`：候选阈值对 baseline 已确认问题的最小保留率。

读取现有 schema revision 1 配置时由服务层补齐缺省字段并规范化为 revision 2，不需要批量改写所有项目 JSONB。存储新配置时只接受 revision 2。

晋级必须同时满足：

1. 候选配置与 baseline digest 不同，且至少改动一个可重放规则。
2. 每个被改动的规则达到最小可判定样本数。
3. 每个被改动的规则同时通过误报率与确认保留率门限。
4. 晋级时项目当前 config revision/digest 仍等于快照 baseline，否则以冲突拒绝。
5. 只有项目 owner / super admin 可创建候选评估和执行晋级；reviewer 可读取报告和写 issue 判定。

## 5. 持久化与 API

### 5.1 领域变更

`point_cloud_quality_issues` 新增 `class_name` 及 review verdict / actor / timestamp / note。`point_cloud_quality_evaluations` 保存 project、creator、baseline/candidate revision + digest + config snapshot、cutoff、冻结 sample snapshot、按规则/类别 summary、gate status、promotion actor/time/revision 和时间戳。

样本快照最多 20,000 条，按稳定 id 排序后写入 JSONB。只冻结重放需要的指标、阈值、规则版本、类别与人工判定，不复制点云或标注几何。
原始冻结样本只在服务端用于重放和取证，API 只返回聚合报告，避免用 issue id 绕过任务可见性边界。

### 5.2 端点

- `PATCH /point-cloud-quality/issues/{issue_id}`：扩展显式 `review_verdict` 和 `review_note`。
- `POST /projects/{project_id}/point-cloud-quality/evaluations`：冻结已处置非 stale 样本，重放候选阈值并生成门禁结论。
- `GET /projects/{project_id}/point-cloud-quality/evaluations`：列出最新评估摘要。
- `GET /projects/{project_id}/point-cloud-quality/evaluations/{evaluation_id}`：读取冻结报告。
- `POST /projects/{project_id}/point-cloud-quality/evaluations/{evaluation_id}/promote`：在锁定项目、复核 baseline 与 gate 后原子晋级。

创建评估、人工判定和候选晋级都写入 audit log。

## 6. 可重放规则

| 规则               | 冻结指标                  | 候选触发语义                                         |
| ------------------ | ------------------------- | ---------------------------------------------------- |
| `low_point_count`  | `point_count`             | 小于类别合并后的 `minimum_points`                    |
| `size_outlier`     | `robust_z[]`              | 最大值大于类别合并后的 `size_mad_z`                  |
| `ground_clearance` | `clearance_m`             | 低于 `-ground_penetration_m` 或高于 `ground_float_m` |
| `temporal_jump`    | center / size / yaw delta | 任一维度超过类别合并后的时序阈值                     |

`track_gap / track_identity_drift / duplicate_track_member` 没有数值阈值，本版本报告它们的观察精度/误报率，但不允许通过阈值候选自动晋级启停状态。

## 7. 前端交互

3D 质量面板新增“问题 / 规则治理”分页：

- 问题页不再只有模糊的“无需处理”，而是显式提交确认问题、误报、接受例外或不确定，并显示已记录判定。
- 治理页显示最新评估的样本数、按规则的 baseline/candidate 误报率、确认保留率与门禁原因。
- owner 可以从当前配置创建候选，按全局或类别调整阈值、生成冻结评估，且仅在 gate 通过时晋级。
- 每个指标显示口径说明；不显示虚构总分，不用红绿单色代替数值和原因。

## 8. 性能与一致性

- issue 列表 stale 检查改为页内批量读取 Run、Annotation、Task/primary LiDAR item 和 SceneTrack，避免随 issue 数量线性增长的 N+1 查询。
- 评估仅扫描项目下已有明确判定且非 stale 的 issue，不重读 PCD，不重跑规则内核。
- 晋级使用 project row lock 和 optimistic config revision 双重保护，一个评估只能晋级一次。
- 评估快照保存 baseline/candidate digest；同一冻结样本上相同配置必须生成相同指标和 gate 理由。

## 9. 实施切片与回滚

本版本横跨迁移、模型、配置、服务、API、工作台、测试与文档，预计超过 8 个文件，分为四个可独立验证切片：

1. 配置与判定：schema revision 2、类别 override、issue review 字段与 worker class 落库。
2. 评估与晋级：不可变快照、确定性重放内核、读/创建/晋级 API 及审计。
3. 工作台：明确判定、治理报告、候选阈值编辑与晋级反馈。
4. 回归与文档：nuScenes mini 外部下载 seed 生成的 golden disposition、权限/冲突/边界/性能测试、OpenAPI 和用户/开发文档。

应用回滚时先隐藏治理入口并禁止新建评估，表与历史判定保留只读；不使用 downgrade 删除已有生产快照。候选晋级只改 JSONB 配置，可以从审计记录中取出上一个 snapshot 建立新候选，不覆盖历史。

## 10. 验收矩阵

### 10.1 自动化

- 配置 v1 加载升级、v2 严格校验、类别合并和 digest 稳定性。
- 四个可调阈值规则的 baseline/candidate 正反例重放；三个非调阈值轨迹规则只报告不晋级。
- 无样本、样本不足、误报率超限、确认保留率超限、未变更候选和通过 gate。
- reviewer 读、owner 创建/晋级、非成员隔离、已晋级重放、baseline 冲突、并发修改和 audit detail。
- 列表 stale 页面批量读取，用 query count 或大页样本确认不随 issue 数量 N+1 增长。
- Alembic `0158 → 0159 → 0158 → 0159`，后端全量 pytest/Ruff/OpenAPI，前端全量 Vitest/ESLint/TypeScript/CSS token，VitePress build。

### 10.2 nuScenes mini 与浏览器

- seed 继续从本机 cache 读取脚本下载的 nuScenes mini，数据集不入库；评估 golden 只保存 issue metric + verdict + expected gate 等小型结构化数据。
- 在浏览器中对 nuScenes 问题提交确认/误报/例外，新建阈值候选，检查规则/类别切片及门禁原因。
- 未通过 gate 时晋级按钮不可用；通过后晋级使 config revision 只增加一次，刷新页面仍可追溯评估快照。
- 确认质量报告始终使用“观察误报率”和“已确认问题保留率”，不出现未有 GT 支撑的“召回率”。

## 11. 非范围与后续

- 不建立真实 GT、Consensus / IAA、标注员评分或单一“质量分”。
- 不自动生效配置，不自动重扫全项目，不根据小样本隐式关闭规则。
- 不实现稳定全局点 ID 或点掩码重叠；不实现持久化多相机对象和投影残差。
- 本版本通过后，下一版优先建立持久化多模态对象、标定 revision 与投影残差 Quality rule，继续沿用本版的评估/晋级合同。
