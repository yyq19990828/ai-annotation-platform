# v0.11.25 · 删批次保护：默认拒删含进行中成果的批次 + 显式强制删除

> Epic 切片 3/3 · 批次解绑状态修复
> 依赖：[v0.11.23](2026-05-29-v0.11.23-batch-delete-reset-cascade.md)（强制删除走其清理逻辑）· 用户可见：是（删除确认流程变化）
> 背景：[ROADMAP §A 删除批次时 task 状态去向 · 长期项](../../ROADMAP.md)

## 目标

长期 UX：保护「已有进行中/待审/已完成成果」的批次不被误删。把 v0.11.23 的「无条件重置+解绑」升级为**有保护的选择**：

- **默认**：删除一个含**非 pending** 或**被 AI 预标过**的 task 的批次 → **拒绝**，引导用户「归档代替删除」或「显式强制删除」。
- **显式 opt-in**：`force=true` 时执行 v0.11.23 的清理（非 pending→pending、留人工标注、删 AI 预标）后删除。
- 纯 `draft`/纯 pending 且无预标的批次 → 一如既往直接删（无摩擦）。

> 取代「删了才发现 task 被重置」的隐式行为；owner 想清空重来仍可一键强制。

## 决策

- 「需要保护」判定：批次内存在 `status != 'pending'` 的 task **或** 存在已预标 task（`total_predictions>0` / 存活 prediction_based annotation）。
- 拒绝用 HTTP 409 + 结构化 detail（含 `requires_force=true` 和受影响计数），前端据此弹强制确认。
- 归档是既有能力（`active/annotating/... → archived`），文案引导即可，不新增后端。

## 任务

### A. delete 端点/Service 加 force

文件：`apps/api/app/api/v1/batches.py` · `delete_batch`（约 171-197）；`apps/api/app/services/batch.py` · `BatchService.delete()`

- 端点加查询参数 `force: bool = False`，透传 `svc.delete(batch_id, force=force)`。
- `delete(batch_id, force=False)`：
  - 计算受保护 task 数（非 pending + 已预标）。
  - `force=False` 且 >0 → `raise HTTPException(409, detail={"code": "batch_has_active_work", "requires_force": True, "non_pending": N, "predicted": M, "message": "..."})`。
  - `force=True` 或无受保护 task → 走 v0.11.23 的 `_reset_and_clean_batch_tasks` + 解绑 + 删除（draft/纯 pending 时清理是 no-op，零副作用）。
- `bulk_delete` 同步加 `force`；非 force 时受保护的批次计入 `failed`（reason=`requires_force`），干净的照删（已有 partial success 语义）。

### B. 审计

文件：删除审计处（`batches.py` delete 后的审计日志）。`force=true` 删除额外记录 `forced=true` + 受影响计数，便于追溯"谁强制删了带成果的批次"。

### C. 前端删除确认流程

文件：`apps/web/src/pages/Projects/sections/BatchesSection.tsx`（`confirmDelete` 流程 + `handleDelete`）；`apps/web/src/api/batches.ts`（delete 加 `force` 参数）；`apps/web/src/hooks/useBatches.ts`（`useDeleteBatch` 透传 force）。

流程：
1. 点删除 → 先发非 force 删除。
2. 后端 409 `requires_force` → 升级确认框：展示「该批次有 N 个进行中/已完成任务、M 个已 AI 预标，删除将重置为待标注并清除 AI 预标」，给两个出口：**归档代替删除** / **仍要强制删除**。
3. 选强制 → 带 `force=true` 重发。
4. 纯 draft/pending 批次 → 一次成功，无升级框。

- bulk delete 同理：批量结果里区分"已删 / 需强制（被跳过）"，提供"对需强制的再强制删除"二次操作。

### D. 测试

后端 `apps/api/tests/test_batch_delete_force.py`（新增）：
1. 纯 pending 无预标 → 非 force 直接删成功。
2. 含 review/completed task → 非 force 返回 409 `requires_force`，批次与 task 不变。
3. 同上 + `force=true` → 删除成功且走清理（task 回 pending、AI 预标清）。
4. 含已预标 pending task → 非 force 也 409（预标也算成果）。
5. `bulk_delete` 非 force：干净的删、受保护的进 failed。
6. 审计：force 删除记录 forced 标记。

前端 `BatchesSection.test.tsx` 补：409 → 升级确认框 → 强制重发 的交互。

## 风险 / 决策点

- **判定口径与 v0.11.23/24 对齐**：「已预标」判定三版必须用同一函数（见 v0.11.24 风险）。
- **409 detail 结构**：前端依赖 `requires_force` 字段；约定好 schema，避免前后端漂移。OpenAPI 快照会变（pre-commit 自动生成）。
- **bulk 的 force UX**：批量场景"部分需强制"的二次操作别做得太绕；可先简单实现（结果区给"强制删除剩余 N 个"按钮）。
- **归档路径前提**：`draft` 不能直接 archive（状态机需先 active）。若受保护批次恰是 draft 但含已预标 pending task，"归档代替删除"的引导要给对路径（可能需先激活或直接走强制）。动手时核对状态机允许的归档来源。
