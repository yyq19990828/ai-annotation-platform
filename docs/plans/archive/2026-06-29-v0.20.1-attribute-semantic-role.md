# v0.20.1 · OCR 属性落点校验硬化（轻量版）

状态：草案（draft）。让 v0.19.2 WS1 的 `text`/`language`/`orientation` 落点校验在「手工建字段」
场景下不再脆弱——**零迁移、零后端 schema 改动、纯前端**。依赖 v0.20.0（RapidOCR 提供真实 producer）。

> **范围已收敛（2026-06-30 探讨后定稿）**：早期草案曾提「给 `AttributeField` 加持久化 `semantic_role`
> 字段 + alembic 迁移 + WS2 双路径回落」。实测三个事实后判定其**过度工程**，改为轻量版。决策依据见下「为什么不做 semantic_role」。

## 背景

v0.19.2 WS1 给 `text`/`language`/`orientation` 加了落点校验（`useCapabilityValidation.ts`，**非阻断条幅**
warning「采纳后该属性丢失」，不挡任何操作）。承接位判定：

```ts
type === "text"          ? hasFieldType("text")                              // 任一 text 类型字段
: type === "orientation" ? enabledToolUnits.has("rotated_bbox") || hasFieldKey("orientation")
:                          hasFieldKey(type)                                  // language: key === "language"
```

## 为什么不做 semantic_role（关键判断）

实测三个事实，推翻了「加持久化语义角色」的必要性：

1. **WS1 只是非阻断提示**（`useCapabilityValidation.ts:16` 明写「非阻断条幅」）——暴露面本就小，不值得重型基础设施。
2. **「从 backend 导入属性」已天然 key 对齐**：`ImportAttributesFromBackendDialog.itemToField` 用 `key: item.key`
   直接保留 backend 自报 key，而 RapidOCR 自报的 key 就是 `text`/`language`/`orientation`（catalog.py `_ATTR_*`）。
   → 走导入路径建的字段 key 本就是 `language`，现状 `hasFieldKey("language")` **已命中**。
3. **`semantic_role` 唯一多覆盖的 case 极窄**：只剩「用户**纯手工**建字段、且把 key 取成 `lang`/`语言` 等非语义名」。
   为这一个长尾上 JSONB 迁移 + 跨前后端字段 + WS2 三层判据叠加，性价比不成立。

**且「统一判据」方向本身可疑**：`text` 走**类型**、`language`/`orientation` 走 **key 具名**，不是异味而是**本质差异**——
`text` 是「类型槽」（任何文本字段都能装识别文本），`language`/`orientation` 是「具名值槽」（固定取值域的具体属性）。
强行用一个 `semantic_role` 维度抹平两种语义，反而引入复杂度。**保持判据现状不动。**

## 目标

不新增持久化元数据、不动校验判据，只在**字段创建入口**降低「key 取错」概率，让手工建的字段天然落在承接位上。

## 工作项

### WS1 · 手工建字段时推荐 key（纯前端，唯一实质改动）

- 属性字段编辑 UI（`ClassesSection` 的字段编辑器）：当**当前项目已绑定**能输出 `text`/`language`/`orientation`
  的 backend（从已加载的能力实例 `output_attribute_types` 即可判定）时，在字段 `key` 输入处提供**推荐 key 快捷填入**
  （`language` / `orientation` / `text`）或占位提示，引导用户对齐协议 key。
- 纯 UI 引导：**不写任何新持久化字段、不发迁移、不改后端 schema**。用户仍可自由命名，只是默认更易对齐。

### WS2 · 固化「导入即对齐」+ 注释定调（防回归 + 防后人误改）

- 加一条前端单测：固定「从 RapidOCR `output_attribute_schema` 导入的字段 key == `text`/`language`/`orientation`」，
  防止未来改 `itemToField` 时悄悄破坏现成的 key 对齐。
- `useCapabilityValidation.ts` 补注释：说明 `text`(按 type) 与 `language`/`orientation`(按 key 具名) 的**判据差异是有意的**
  （类型槽 vs 具名值槽），避免后人当异味去「统一」。

## 风险

低。纯前端 UI 引导 + 单测 + 注释，无迁移、无 schema 变更、无后端改动，老项目零退化。

## 验收

- 手工新建语言字段时，项目若绑了 RapidOCR，UI 推荐 `key=language`，一键填入后 WS1 不再误报缺承接位。
- 老项目（key 恰为 `language`）/ 导入路径 → 行为完全同 v0.19.2，零退化。
- 单测锁定 RapidOCR 导入字段 key == 语义名。

## 排期与依赖

- **依赖 v0.20.0**（RapidOCR 提供真实 `text`/`language`/`orientation` 输出与 `output_attribute_schema`）。
- 与 v0.20.2（一键补全）同窗口：二者都动 `ImportAttributesFromBackendDialog` + 属性链，建议紧邻排。

## 不在范围（明确砍掉）

- ❌ 持久化 `semantic_role` 字段 + alembic 迁移 + WS2 双路径回落 —— 过度工程，依据见上。
- ❌ 改动 WS1 三类判据的口径（type vs key）—— 是本质差异，保持现状。
- ❌ 逐框语言（per-line language）落到不同字段：归属取值层，另议。
- ❌ 把推荐 key 升级为强约束 / 禁止自定义 key：仅引导，不限制。
