# v0.11.30 · 大表查询地基（indexed-compass）

> 路线图：[大数据集规模化加固](./2026-06-02-large-dataset-scale-hardening-roadmap.md) 的第一版（B1/B2/B3）。
> 主题：把万级 → 十万级 task 下最热的两条读路径（取下一题、列任务）从「全表扫 / 全表 COUNT」降到「索引命中」。**纯后端，零 UI，可独立回滚。建议立刻做。**

## 背景

- `get_next_task`（`services/scheduler.py:70-154`）是最热路径，每次「下一题」都跑，但有两处大表放大：
  - `~Task.id.in_(already_annotated_subq)`（`scheduler.py:100-112`）：标注员标得越多，`NOT IN` 集合越大，Postgres 可能物化临时集合。
  - uncertainty 采样 `outerjoin Prediction ... order_by Prediction.score`（`scheduler.py:134-137`）：对**整个候选集**做外连 + 排序只为 `limit(1)`；且一 task 多 prediction 会行扇出。
- `list_tasks`（`api/v1/tasks.py:174-252`）：cursor 分页本身没问题，但 `total = count_q`（`:227`）**每翻一页都全表 COUNT**；虚拟滚动滚到底逐页触发 → 一次浏览重复 COUNT 几十次；非特权用户还要 `JOIN TaskBatch`（`:194-200`）。
- Task 表只有单列索引，**`created_at` 无索引**（`models/task.py:92`），而两条路径都 `ORDER BY ... created_at`。这是 B1/B2 的共同地基。

## 范围（做什么）

### B3 复合索引（迁移 0090，最高杠杆，先落）
**经 10 万行 EXPLAIN ANALYZE 实测，最终保留 2 个**（候选的第 3 个实测无用，已删）：
- ✅ `ix_tasks_project_created_id` ON `tasks (project_id, created_at, id)` — 撑 `list_tasks` 的 `WHERE project_id ORDER BY created_at, id`。实测 Index Scan，首页 100 行 **0.088ms**（改前全表 cost 24144）。
- ✅ `ix_tasks_batch_unlabeled` ON `tasks (batch_id) WHERE is_labeled = false` — 撑 scheduler 的 `batch_id` 过滤分支（实测 Bitmap Index Scan，**7.9ms**）+ 未归类池 `batch_id IS NULL`（**0.13ms**，v0.12.0 复用）。
- ❌ ~~`ix_tasks_project_unlabeled (project_id, sequence_order, created_at) WHERE is_labeled=false`~~ — **实测任何路径都未被 planner 选中**：默认 scheduler 的 `ORDER BY` 以 join 表 `batch.priority` 打头必须排序，`is_labeled=false` 在新项目无选择性走 seq scan、成熟项目走已有的 `ix_tasks_is_labeled`。建它只是写放大 → **不建**。

> 迁移用普通建索引 + `IF NOT EXISTS`（本项目迁移跑在事务内，`CONCURRENTLY` 不能在事务内执行）；生产大表的在线建索引路径见迁移 docstring 的手动 `CONCURRENTLY` 预建说明。

### B1 scheduler 热路径重写（`services/scheduler.py`，无迁移）
- `NOT IN 子查询` → **相关 `NOT EXISTS`**：
  ```python
  from sqlalchemy import exists
  not_annotated = ~exists().where(
      and_(Annotation.task_id == Task.id,
           Annotation.user_id == user_id,
           Annotation.is_active.is_(True)))
  candidates = candidates.where(not_annotated)
  ```
- uncertainty 去扇出：把 `outerjoin Prediction` 改为**相关标量子查询**取每 task 最小 score，消除行扇出：
  ```python
  min_score = (select(func.min(Prediction.score))
               .where(Prediction.task_id == Task.id).scalar_subquery())
  candidates = candidates.order_by(TaskBatch.priority.desc(), min_score.asc().nullslast())
  ```
- 行为不变（同样选「最不确定的一条」），仅去掉扇出与全集物化。

### B2 list_tasks COUNT 优化（`api/v1/tasks.py`，无迁移）
- **仅首页（`cursor is None`）计算精确 `total`；带 cursor 的后续页跳过 COUNT**，`total` 复用首页值（前端缓存）。
- `TaskListResponse.total` 在后续页返回 `None`（schema 改为 `int | None`）；前端 `useTasks` 在首页落地 total，翻页不覆盖。
- 收益：一次列表浏览的全表 COUNT 从「页数 × N」降到「1 × N」。

## 不做（明确排除）
- 不引入 `reltuples` 估算 COUNT（首页仍要精确数；估算留到百万级再议）。
- 不动 cursor 分页协议 / 虚拟滚动（已良好）。
- 不改 batch 可见性语义（`batch_visibility_clause` 原样）。
- 不碰 B4/B5/B6（属后两版）。

## 风险
- **`CREATE INDEX CONCURRENTLY` 不能在事务内跑**：alembic 默认包事务。迁移需 `op.execute("COMMIT")` 后裸建 / 或用 `with op.get_context().autocommit_block():` + `op.create_index(..., postgresql_concurrently=True, if_not_exists=True)`。dev 小表可省 CONCURRENTLY，生产大表必须用（否则锁写）。在迁移里同时给两种路径。
- `total=None` 的前端兼容：确认 `useTasks` / 任意展示「共 X 条」的位置只在首页读 total，不在翻页时依赖（已核 infinite query 用 `next_cursor` 判 `hasNextPage`，不依赖 total）。
- NOT EXISTS 改写需保证语义等价（已标注 = 该用户 active annotation 存在）——用 §验证 的对拍覆盖。

## 验证（已执行 ✅）
- **种子脚本** `apps/api/scripts/seed_scale.py`（本版产出，后两版复用）：10 万 task / 50 batch / 标注员留 active 标注。~30s 生成。
- **EXPLAIN ANALYZE 实测**（见上 B3 / B1 数字）：
  - `list_tasks` 首页：`Index Scan using ix_tasks_project_created_id`，**0.088ms**。
  - scheduler 默认 sequential：`NOT EXISTS` → **Hash Anti Join**（不再物化 NOT IN 集合）；本规模 ~36ms（seq scan 因全未标注无选择性，属正常）。
  - scheduler batch_id 分支 / 未归类池：命中 `ix_tasks_batch_unlabeled`，7.9ms / 0.13ms。
  - 旧 NOT IN 对照：本规模被优化成 hashed SubPlan（~32ms），**重写的收益是健壮性**（NULL 语义正确 + 保证 anti-join + 无 hash 内存爆风险），而非本规模的戏剧性提速。
- `uvx ruff check` ✅；`uv run pytest`（scheduler / task_batch_visibility / v0_7_2）30 passed ✅；迁移 0090 down→up 可逆 ✅。
- **首页 total 兼容**：`test_task_batch_visibility` 的 `total==1`（首页）断言仍过；前端两个消费点均读 `pages[0].total ?? fallback`，翻页 `null` 无影响。
