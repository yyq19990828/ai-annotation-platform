## 2. 目标 / 非目标

**目标**

- 多选 N 条已有轨迹,一次发起、**一个 job 聚合追踪**,各回填各自源轨迹(路径 2)。
- B-combo:一次 job 内 multiplex 文本自动发现目标 → 逐对象 PVS memory 追踪,兼得「自动发现」与「干净身份」。
- 收尾 U7 / U8,epic 视觉与反馈闭环。

**非目标(本次不做)**

- **不做逐轨迹/逐帧接受**:路径 2 下多源作为**一个可接受单元**(整 job accept/discard),沿用 v0.21.28 的 job 级粒度;逐源接受留 backlog。
- **不改 ML backend 模型层**:multiplex / PVS 两个原语已就绪,B-combo 只在 runner 编排,不新增 backend 推理代码(除非显存实测逼出 backend 侧卸载调度,见 §10 风险)。
- **不引画布轨迹多选**:画布轨迹层 `listening=false`,多选批量入口只挂 roster/浮卡侧。
- **不动几何「标注传播」**(`usePredictionPropagation`)。

## 3. 核心洞察:0.22.1 多实例骨架是共享地基,三块在其上各走不同落库分支

一度以为「M + 多源回填 + B-combo 三块共缺同一个 obj_id↔源账本」,勘察后**收窄**:

- **共享地基(已就位,v0.21.26/0.22.1)**:按 `instance_id` 分组落库、`_continuation_seeds` per-instance 跨窗续种(obj_id 已跨窗稳定)、`source=None` 无源新建路径。三块都复用它,**不重写**。
- **各自扩展**:

| 块                    | 落库分支                       | 需新增                                                                                                                               |
| --------------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| **M · 多选批量**      | 多个 instance **各回填各自源** | **多源回填账本**:`prompt.seeds[]` 每条带 `source_annotation_id`,`_persist_tracker_results` 从单 source 升为 `{instance_id: 源}` 映射 |
| **B-combo**           | 发现对象**无源 → 新建**        | **不需要源账本**;走已成熟的 `source=None` extras 新建。只需 runner 两趟编排                                                          |
| CA 逐轨迹接受(非本版) | per-source accept              | (backlog)                                                                                                                            |

即:**「多源回填账本」只服务多选批量 M;B-combo 无源、复用无源新建**。这修正了「三块共享一个新账本」的过度概括。

**关键机制依据**(agent 勘察):PVS 落库里 `instance_id == str(obj_id) == caller 指定`(`video_tracker_runner.py:335-338` `_instance_seed_obj_id`),`_continuation_seeds`(`:341-352`)已为每实例下发稳定 obj_id。因此只要窗 1 用 N 条 `{obj_id:k, geometry:源_k 几何, source_annotation_id:源_k.id}` 播种,落库按 `k → 源_k` 回填,身份链路 by construction 成立、无需 IoU。

## 5. 阶段 M · 多选批量追踪(路径 2 · 后端单 job 多源)

### M0 · 后端多源落库底座(核心,先行)

- `prompt.seeds[]` 每条约定携带 `source_annotation_id?`(无 → 新建;有 → 回填该源)。
- `_persist_tracker_results`:参数从 `source` 改 `source_map: dict[instance_id, Annotation]`;遍历所有 instance,map 命中→`apply_tracker_results(源)`,未命中→`_new_discovered_track(target)`。
- `_partition_results_by_instance`:全量按 instance 分组(去掉「单 primary 坍缩」),回填/新建交给 `source_map`。
- 孤儿泛化:现单源「源软删→丢弃孤儿候选」(`accept_tracker_job:621`)扩成 **per-source** —— 某源在 job 期间被删,仅该 instance 降级为无源新建或跳过,不整 job 失败。
- 多源回传:`_persist_tracker_results` 内部 `created` 列表透出到 `VideoTrackerJobOut.touched_annotation_ids`。
- **验证**:扩 `tests/test_video_tracker_multi_instance.py` —— 2 源各带几何 → 1 job → 各回填各自源(源 A/B 帧被更新、instance 不串)、`touched_annotation_ids` 含两源;一源运行中删 → 另一源正常、被删源不崩。

### M1 · endpoint / schema / service 多源

- `VideoTrackerPropagateRequest` 增 `source_annotation_ids: list[UUID] | None`(单数保留)。
- `create_tracker_job`:接 `source_annotation_ids`,逐源读当前帧几何 + 类别,构 `prompt.seeds[]`(obj_id=1..N、各 `source_annotation_id`、各 geometry)。
- `track_video`:读多源;旧 `:propagate` 单源 endpoint 不动。
- **验证**:OpenAPI 快照更新;新旧 endpoint 各建 job;多源 job 的 `prompt.seeds` 结构正确(N 条带 source_id)。

### M2 · 前端 roster 批量入口 + 对话框多源 + 单 job 多源提交

- roster 批量条 + `VideoTrackBatchCardContent` 各加「批量 AI 追踪」,门控与现批量动作一致(`batchCount>1 && trackFilter==="current"`);点击 `openPropagateDialog(videoBatchTracks)`。
- `propagateDialog` 扩持列表;对话框影响摘要多源叙事(「延展 N 条轨迹」+ 混类);种子/范围以多源共同当前帧派生。
- `handlePropagateSubmit` 多源→ `track(taskId, {source_annotation_ids, …})` 发 1 job;`useVideoTrackerJobs` 候选/审阅按 `touched_annotation_ids` 归并(1 审阅条覆盖 N 源)。
- **验证**:组件测试(多源摘要 / 提交 payload 含 ids);浏览器 E2E —— roster 选 2 轨迹 → 批量 AI 追踪 → 1 job/1 审阅条 → 接受 → 两源各自帧被回填。

## 6. 阶段 B-combo · multiplex 发现 → PVS 追踪(seam A · runner 编排)

**做法(seam A,改动集中在 runner,backend 零改)**:新增编排 model_key(建议 `sam3_video_combo`),runner 分派到「两趟」:

1. **发现趟**:对种子帧(或首窗)按 `text` 调 multiplex(`sam3_video` backend,`video_predictor.py:94`)→ 拿每个发现对象在该帧的 per-obj 框。
2. **种子铸造**:每个发现框 → PVS seed `{obj_id:k, bbox}`(**无 `source_annotation_id`** → 落库走无源新建);复用 `_bbox_of_geometry`(`runner:361`)。
3. **追踪趟**:用这些 seeds 跑现有 PVS 窗循环(`sam3_video_interactive` backend,`pvs_video_predictor.py:105`),`_continuation_seeds` 跨窗续种、逐对象 memory。
4. **落库**:发现对象无源 → `source_map` 为空 → 全部 `_new_discovered_track`(已成熟路径)。候选/接受走 job 级 CA(与 B-mx 一致)。

- runner 侧接线:`_associate_multiplex_window` 门控(现 `== "sam3_video"`,`:817`)与 `_tracker_windows` 分窗(`:129`)需认 combo key;combo 的发现趟用 multiplex 小分窗、追踪趟用 PVS 分窗。
- **显存**:两趟**串行**(先 multiplex 发现完再 PVS 追踪),中间 idle 卸载 multiplex 再载 PVS,避免同容峰值。**必须真机实测**三模型(图像 sam3.pt + multiplex + PVS)单卡 24GB 编排,确认不 OOM / 不静默退化。
- **验证**:单测(发现框→PVS seeds 铸造纯函数 + runner combo 两趟 E2E 合成);真机 GPU E2E(`tracking_car.mp4`,text="car" → 发现 N 车 → PVS 各自 memory 追踪 → 候选 pending_review → 接受落 N 新轨迹);显存曲线记档。

## 10. 风险

- **多源 primary 语义**:现 `_partition_results_by_instance` 只产一个 primary。多源要么让每个源各是「自己那条的回填实例」、要么改用 `source_map` 命中判定落库去向(推荐后者,primary 概念对多源退化)。落库层最易漏。
- **候选/审阅归并**:1 job 映射 N 源,`byAnnotation`/`candidateByAnnotation`(`useVideoTrackerJobs.ts:528/543`)现按单 annotationId 归并,需支持一 job 多轨迹,否则画布候选层挂不到多源。
- **B-combo 显存(真实部署风险)**:图像 sam3.pt + multiplex + PVS 三者单卡。已知 multiplex 18.9GB@16f、PVS 4.1GB@7f。串行 + idle 卸载是对策,但**必须实测**;极端场景可能逼出 backend 侧卸载调度(超本版范围,记 ROADMAP 显存互斥条)。
- **孤儿源**:多源 job 运行期某源被删,per-source 降级/跳过要覆盖 accept 与 preview 两处,别整 job 崩。
- **UX 混类**:多选轨迹可能跨类,批量对话框类别叙事需明确「各留各类」(不强并一类)。
- **暗色/token 红线**:M2/U7/U8 全走语义类 + `--sc-*`,状态色配对 `dark:`(CLAUDE.md §6)。
