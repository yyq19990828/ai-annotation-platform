## 1. 决策

本版本先收口 WebGPU Pilot 的剩余切帧瓶颈，再决定是否把实验功能转为正常功能。当前代码已经证明相机纹理 GPU 直采样能删除 Canvas 全图回读和 CPU 逐点上色，但 WebGPU 路径仍在每次切帧时为最多六路相机重新生成低分辨率遮挡深度栅格；现有相邻帧预取只覆盖解析后的 PCD 与 `ImageBitmap`。

选定方案是：让 Worker 只生成 GPU 实际需要的 `cols + rows + depth`，不再分配或结构化克隆 hover 深度图使用的 `x/y/z/u/v`；以点云 URL、点数、相机尺寸和标定矩阵为键缓存结果，并仅在实际 WebGPU backend 下随相邻帧预取。缓存命中、图片解码、深度计算、texture 创建和最终 paint 都进入同一浏览器性能事件流。

不直接实施 GPU depth pass。它会引入 render target、相机批次、主视图与三视图 owner 生命周期等更高复杂度，而当前约 90 ms 的 CPU 阶段可以先通过预取从热切帧关键路径移除。只有本版本的分段埋点证明 texture upload 或 CPU depth 仍阻断门槛，才单独立项。

## 2. 目标与成功标准

- 已预取相邻帧进入 WebGPU 相机上色时，深度栅格报告 `cacheHit=true`，不重复向 Worker 发同键请求。
- 深度结果只包含 GPU 需要的单个 `Float32Array`，空格在 Worker 中直接写为 shader 可采样的有限大值，主线程不再逐格改写。
- 缓存最多保留 8 个 frame key、最多占用 8 MiB；失败 Promise 会被移除，淘汰后允许重新计算。
- Legacy backend 不启动深度栅格预取，不为默认关闭的实验功能增加后台 CPU 负载。
- A/B 报告分别给出 PCD frame、camera bitmap、camera depth 和 texture prepare 的 p50/p95，并保证临时 benchmark 3D 框在成功或失败后都被删除。
- nuScenes mini 隔离 E2E 同时覆盖 WebGPU backend、单 Worker、零 Canvas 全图回读、选中框和三视图精修。
- 完整资格仍沿用 Pilot 的 10 次冷样本、20 次 warm 样本、真实 WebGPU、功能 parity、资源 plateau 和跨设备门槛；本版本不会因为一次本机提升自动转正。

## 3. 范围与非范围

### 3.1 范围

- 新增 GPU depth-only raster 合同与 Worker 消息返回。
- 在既有点云资源缓存中加入有界 depth-raster Promise LRU、并发合并、失败移除和调试快照。
- WebGPU 当前帧读取缓存；Scene 时间轴只在实际 backend 为 WebGPU 时预取相邻深度栅格。
- 扩展 point-cloud performance event，使 benchmark 能报告各资源阶段和 cache hit。
- benchmark 无框时创建一个临时 `box_3d`，从项目 `lidar_box_3d` binding 读取合法类别，并在 `finally` 删除。
- 单元测试、E2E、类型检查、lint 和浏览器 A/B 验证。

### 3.2 非范围

- 不改变实验开关默认值，不删除 Legacy renderer 或 CPU colorizer。
- 不新增 API、数据库字段、环境变量、路由、服务、依赖或第三方账号。
- 不实现 GPU depth pass、octree、3D tiles、服务端点云转码或新点云格式。
- 不把 benchmark 临时标注写入 seed，也不要求仓库保存 nuScenes 数据；数据仍由现有 seed 下载到用户缓存。
- 不在本版本发版或提交；完成验证后由独立发布动作决定版本推广。

Entity delta: **+0 / -0**。新增内容全部是实验 renderer 内部缓存、埋点和测试基础设施。

## 4. 数据流与生命周期

```text
nuScenes manifest
  ├─ decoded PCD cache ───────────────┐
  └─ decoded ImageBitmap cache ───────┤
                                      ▼
                           depth-only Worker request
                                      │
                                      ▼
                         8 MiB / 8-key Promise LRU
                           │                    │
                current frame acquire    adjacent prefetch
                           │                    │
                           └─────────┬──────────┘
                                     ▼
                         DataTexture + camera texture
                                     ▼
                              GPU direct sampling
```

缓存 key 包含 `pointCloudUrl`、`positions.length`，并按相机顺序包含图片宽高、`extrinsic`、`intrinsic` 和可选 `rect`。相同 key 的并发请求共享一个 Promise；调用方的页面 Abort 只阻止旧帧提交，不破坏可供下一帧复用的共享计算。失败会删除 key，后续切帧可重试。

LRU 只持有 CPU `Float32Array`，GPU `DataTexture` 仍归当前 renderer resources 所有并在换帧时显式 `dispose()`。淘汰 depth array 依赖 JS 回收，不持有外部资源。

相邻预取继续共用一个持久 Worker。为避免默认 Legacy 用户付出额外开销，只有 `actualBackend === "webgpu"` 才请求 depth；WebGL2 fallback 也不预算。当前请求和预取共享同键 Promise，避免同一帧重复排队。

## 6. 测试矩阵

### 6.1 单元测试

- depth-only 与完整 `buildDepthRaster` 在同一标定下每格深度一致；空格为有限大值。
- 同 key 并发请求只调用 Worker 一次，并分别标记 miss/hit。
- Worker 失败后 key 被删除，第二次调用会重新计算。
- 超过 8 个 key 时淘汰最旧 settled entry；总估算字节数不超过 8 MiB。
- 相机纹理资源在 cache hit/miss 下都能创建、释放 texture 和 bitmap handle。
- Legacy 时间轴不预取 depth；真实 WebGPU 时间轴才启用。

### 6.2 自动化与浏览器

- 运行相关 Vitest、前端 typecheck、ESLint/CSS token gate。
- E2E seed 优先使用本机缓存或自动下载的 nuScenes mini，并保留 CI 的真实负载兼容夹具。
- WebGPU E2E 选择 seed 3D 框、打开三视图，断言 backend/Worker/Canvas readback/runtime error。
- benchmark 在目标任务无框时创建临时框，完成 Legacy/WebGPU 两组后删除；失败路径同样清理。
- 快速浏览器验证可用 3+3 样本观察功能与方向；正式资格报告必须跑满 Pilot 门槛，快速结果不能触发转正。

## 7. 风险、回退与判断条件

最脆弱假设是：约 90 ms 的深度栅格仍是 warm RGB 的主要剩余可移动阶段。如果分段埋点显示 `camera-depth-ready` 命中后端到端 RGB 没有显著下降，说明瓶颈已经转移到图片 texture upload、TSL shader 首次编译或 GPU submit；届时保留本版本的轻量缓存与埋点，但停止扩大 CPU 预取，另立 GPU depth/upload 方案。

相邻预取可能与当前帧争用单 Worker。缓解方式是只在真实 WebGPU 下预取、同键合并，并保持最多相邻 `±1` 的既有调用范围；若同一 WebGPU 路径关闭 depth 预取的对照实验显示 geometry p95 因预取回退超过 10%，立即关闭 depth 预取调用，缓存仍可保留用于同帧重开和调色。

所有改动都可通过关闭实验开关回退，且不修改标注数据合同。benchmark 唯一外部写入是临时 3D 框，脚本保存其 ID 并在最外层 `finally` 删除；删除失败会让命令以错误结束并打印明确 ID，便于人工清理。

## 8. 实施与验证结果

实现完成后，在同一台开发机、同一 Chromium Vulkan/WebGPU 进程和 `P-PC-DEV / nuScenes mini scene-0061` 上跑满 20 次非相邻跳帧与 20 次相邻 warm 切帧。benchmark 在首帧临时创建真实 `box_3d`，Legacy/WebGPU 两组都完成框体精修测量后将其软删除；数据库复核活动 benchmark fixture 为 0。

| p95 指标              | Legacy WebGL2 |   WebGPU |       变化 |
| --------------------- | ------------: | -------: | ---------: |
| 冷跳帧 geometry       |      324.4 ms | 297.6 ms |  改善 8.3% |
| 冷跳帧 RGB            |      446.5 ms | 348.6 ms | 改善 21.9% |
| 已预取相邻帧 geometry |       93.9 ms | 121.9 ms | 回退 29.8% |
| 已预取相邻帧 RGB      |      336.0 ms | 167.8 ms | 改善 50.1% |
| 首次展开框体精修      |      184.2 ms | 125.7 ms | 改善 31.8% |

WebGPU warm depth cache 命中率为 100%，`camera-depth-ready` p50 约 0.1 ms、p95 约 15.1 ms；cold 样本命中率为 80%，p95 约 56.1 ms。相比 Pilot 中每帧约 90 ms 的完整深度栅格，这证明 depth-only + 预取方向有效。实验路径 `getImageData()` 为 0、持久 Worker 为 1、运行时错误为 0；真实 WebGPU E2E 也通过了框选择与三视图展开。

推广门仍为失败：cold geometry 未达到 250 ms，warm geometry 以 1.9 ms 超出 120 ms 门槛且相对 Legacy 有明显回退，warm RGB 相对改善为 50.1% 而非要求的 60%。框体精修 rAF p95 与 Legacy 同为显示器刷新率附近，最大帧间隙 99.9 ms，尚不能替代跨 GPU 的 GPU frame-time 资格。Linux 样本还依赖 Chromium unsafe Vulkan flags，因此不能据此转为正常功能。

下一轮若继续优化，应优先定位 WebGPU instanced point sprite 在 warm geometry 提交阶段的约 28 ms 相对开销，并把相机 bitmap 偶发 31–43 ms warm 解码等待纳入预取命中诊断；GPU depth pass 暂无必要，因为当前 depth 阶段已不再是 warm 主瓶颈。

上述 geometry / shader 提交优化已在 [3D WebGPU 稳定帧提交](2026-08-24-v0.24.7-3d-webgpu-stable-frame-submit.md) 实施并复测；后续以新计划的结果与剩余门槛为准。
