# v0.24.8 · 3D 跨帧任务中心 MVP

> Status: implemented and verified
>
> Approved on: 2026-08-25
>
> Implementation authorization: 用户要求在 0.24.7 发布提交后直接确定并实施
>
> Baseline: `70ba473a134c5f2c2cf208f087b10fac709f17be` (`v0.24.7`)
>
> Scope owner: 3D Scene 跨帧传播的任务合同与工作台任务中心

## 1. 结论

本版本交付一个持久、可恢复的 3D 跨帧任务中心，把已有的 ego-aware `box_3d`
传播能力接入统一 `AsyncJob`。用户必须显式确认对象范围、方向、目标帧范围和冲突策略；任务可在
Scene 时间轴中查看进度、取消，并只对失败或 stale 的帧发起重试。

首版不引入新跟踪算法。registration 仍受准确率、失败识别、运行预算和无 GPU 路径门控，不能因为
任务中心已经存在就提前开放。区间插值继续保留现有同步入口，不在本版本内改写语义。

## 2. 转定稿校准

- `Annotation.track_id` 仍是 Scene 跨帧对象身份；现有单框 / 批量传播会在缺失时创建它。
- `Scene + DatasetItem.frame_index` 仍是帧序真值，Scene 时间轴已经提供任务锚点和权限脱敏。
- `AsyncJob` 已具备 owner 可见性、进度、终态、取消入口、通知和 30 天清理，不需要新建任务表。
- 现有传播端点只处理一个目标 task，无法表达长区间进度、部分完成和刷新恢复。
- 现有 `AnnotationService.propagate_batch()` 可作为 operation adapter；MVP 不复制几何算法。
- 0.24.7 已形成干净提交，当前工作树无需要避让的用户变更。

原研究草案中仍成立的是显式 scope、方向、范围、冲突策略、快照、取消、部分失败和重试。不再把
registration 与任务中心绑在同一版本；“所有既有 operation 一次统一”也拆分为先接传播、后接插值。

## 3. 用户可见范围

### 3.1 启动作业

Scene 时间轴标题栏增加“跨帧任务”入口。任务中心的启动表单固定显示：

1. `operation=propagate`：文案为“传播 3D 框”，首版不可切换。
2. `scope=selected|all`：selected 必须至少包含一个当前帧 `box_3d`；all 显示当前帧框数。
3. `direction=forward|backward`：决定目标范围必须位于当前帧之后或之前。
4. `range`：用户填写目标结束帧；起点自动固定为相邻帧，确认区明确显示闭区间和逻辑帧数。
5. `conflict_policy=skip_existing`：首版唯一策略，但仍在界面和请求中显式呈现。

单个作业最多覆盖 100 个逻辑帧、最多携带 500 个源框。缺失帧、不可访问帧和不可编辑帧不泄露 task id，作为跳过结果
对账；至少要有一个可执行目标，否则拒绝启动。

### 3.2 任务中心

- 展示当前 Scene、当前用户最近 20 个跨帧作业。
- pending / running 展示进度；终态展示成功、跳过、失败、stale 和取消数量。
- pending / running 可取消。取消不回滚已经成功写入的 annotation，只停止后续帧。
- 包含 `failed` 或 `stale` 目标的作业可“重试失败帧”；重试建立带 `parent_job_id` 的新作业。
- 刷新页面或切到同 Scene 的其它帧后，继续从服务端恢复同一批作业状态。
- 作业有写入进展或终态后失效 annotations 与 Scene 时间轴查询。

## 4. 明确非范围

- 不实现 registration、ICP、Kalman、学习式跟踪或候选接受流程。
- 不把区间插值迁入异步任务；现有单目标插值入口保持不变。
- 不提供 overwrite。已有同 `track_id` 的目标框始终跳过，不覆盖人工真值。
- 不做跨 Scene、跨项目或 `point_mask_3d` 传播。
- 不建设通用 DAG、独立任务表、WebSocket 专用频道或新的数据库迁移。
- 不承诺取消是事务级回滚；任务中心会明确保留已完成帧。

## 5. 冻结 API 合同

### 5.1 创建

```http
POST /api/v1/tasks/{source_task_id}/cross-frame-jobs
```

```json
{
  "operation": "propagate",
  "scope": "selected",
  "annotation_ids": ["uuid"],
  "direction": "forward",
  "start_frame": 13,
  "end_frame": 24,
  "conflict_policy": "skip_existing"
}
```

`selected` 要求非空 `annotation_ids`；`all` 要求 `annotation_ids` 为空。forward 必须满足
`current < start <= end`，backward 必须满足 `start <= end < current`。范围最多 100 帧，源框最多 500 个。

响应为现有 `AsyncJobOut`，HTTP 202。完全相同的 source 快照与目标范围若已有 pending / running
作业，则返回该作业，不重复入队。

### 5.2 Scene 作业列表

```http
GET /api/v1/tasks/{task_id}/cross-frame-jobs?limit=20
```

只返回当前用户在该 task 所属 Scene 的 `point_cloud_cross_frame` 作业；super admin 仍只在通用
`/async-jobs` 中拥有全局视角，工作台内不混入他人的写任务。

### 5.3 重试失败帧

```http
POST /api/v1/tasks/{task_id}/cross-frame-jobs/{job_id}/retry-failed
```

仅 owner 可重试同 Scene 作业。新作业只继承原结果中具有 task id 的 `failed|stale` 目标，重新冻结
当前 source annotation 版本，并写 `parent_job_id`。没有可重试目标返回 409。

取消复用：

```http
POST /api/v1/async-jobs/{job_id}/cancel
```

## 6. AsyncJob payload / result 合同

`kind=point_cloud_cross_frame`，payload 固定 `contract_version=1`，包含：

- source task / scene / frame、operation、scope、direction、闭区间、conflict policy；
- source annotation `id + version` 快照；
- 按方向排序的目标 `{frame_index, task_id|null, preflight_state}`；
- singleflight key、可选 parent job id、总逻辑帧数。

result 固定包含：

```json
{
  "contract_version": 1,
  "total_count": 12,
  "success_count": 8,
  "skipped_count": 2,
  "failed_count": 1,
  "stale_count": 1,
  "cancelled_count": 0,
  "created_annotation_count": 16,
  "items": [
    {
      "frame_index": 13,
      "task_id": "uuid-or-null",
      "status": "success|skipped|failed|stale|cancelled",
      "created_count": 2,
      "skipped_count": 0,
      "reason": "short-machine-code-or-null"
    }
  ]
}
```

progress 以已终结逻辑帧数计算。任何 failed / stale 使作业终态为 failed 并保留完整 result；全成功或
仅 skip 为 completed；取消为 cancelled。错误消息不包含内部异常堆栈。

## 7. 执行、并发与真值边界

```text
Scene 时间轴任务中心
        │ 显式 scope / direction / range / policy
        ▼
POST cross-frame-jobs ──► AsyncJob(payload snapshot) ──► Celery default queue
        │                                                   │
        │                                                   ├─ 每目标帧检查取消
        │                                                   ├─ source version 复核
        │                                                   ├─ skip existing track
        │                                                   └─ propagate_batch adapter
        ▼                                                   │
GET Scene jobs ◄──── polling / 通知 ◄──── progress + result ┘
        │
        └─ invalidate annotations / Scene timeline
```

- 每个目标 task 是一个提交边界；单帧内 selected/all 全部成功或全部回滚。
- 写入前按固定顺序锁定 source / target task，并锁 source annotations，降低反向作业死锁和重复写风险。
- 每帧重新复核 source version。传播首次创建 `track_id` 导致的内部版本递增会更新 worker 的期望版本；
  外部编辑导致不匹配时，当前及剩余帧标记 stale，不读取新几何继续传播。
- target 中已经存在同 `track_id` 的活跃 `box_3d` 时只跳过该对象；同帧其它对象仍可写入。
- 取消通过 `AsyncJob.status/cancel_requested` 协作检查，已提交帧保留。
- Celery 派发失败将 job 标记 failed；worker crash 由既有 Celery signal 兜底。

## 11. 回滚

前端可先移除 Scene 时间轴的任务中心入口；已有单帧传播和插值不受影响。后端停止暴露创建 / 重试
端点并从 Celery include / route 移除 worker 即可。`AsyncJob` 使用既有 JSONB 和字符串 kind，无迁移
需要回滚；已经创建的 annotation 和审计记录必须保留，终态 job 按既有 30 天策略清理。

## 12. 最脆弱假设

MVP 假设“一帧一个提交边界 + 最多 100 帧”足以在当前 Scene 规模下提供可接受吞吐，同时让取消和
部分失败可解释。若真实 nuScenes 长区间压测显示数据库往返而非点云算法成为瓶颈，下一版应做安全的
批次提交与进度分片；不得在本版预先引入更复杂的分布式 fan-out。

## 13. 实施结果

- 创建、Scene 作业列表、失败 / stale 帧重试与通用取消 API 已接入 OpenAPI。
- default queue worker 已按目标帧分段执行快照复核、权限复核、`skip_existing`、进度持久化和终态通知。排队中任务可立即取消，运行中任务在下一帧边界协作停止。
- Scene 时间轴已接入任务中心，支持 selected / all、方向、显式闭区间、持久进度、取消和失败帧重试；只读 task 不能启动写任务。
- 跨帧 / Scene / 通用作业回归、OpenAPI 合同、前端组件用例、类型检查、ESLint / 色彩门禁和文档构建通过。
- Chromium 在 nuScenes 测试 Scene 中验证了任务中心入口、全部框范围、精确请求体、轮询恢复的 completed 摘要和零 console error。API / worker 真实写入链路由 PostgreSQL 集成测试验证，浏览器用例只 mock 作业终态，不污染开发数据集真值。
