# v0.10.46 · WebCodecs 精确帧解码：mp4 demux 链路接入

> **来源**：`ROADMAP.md` § 视频工作台 Phase 1「遗留待续」+ `2026-05-21-video-workbench-roadmap.md` Phase 1 尾注。
> **触发条件（P2）**：有真实高帧率视频卡顿反馈，或 seek 精度 bug 被客户明确提出，再开工。当前 feature flag 默认关闭（零副作用），本 plan 等触发后再执行。

## 实现说明（落地后补记，与本计划的差异）

落地时相对原计划有 4 处偏差，均已在 v0.10.46 实现：

1. **后端用 `ffprobe -show_packets` 而非 PyAV**：项目根本没装 PyAV（`av`），全程用 ffprobe/ffmpeg subprocess。改用 `ffprobe -show_packets`（`packet=pts_time,dts_time,duration_time,size,pos,flags`），与既有 `parse_ffprobe_frame_timetable` 同风格，零新依赖。新增 `parse_ffprobe_packet_samples` / `probe_chunk_samples` / `_extract_chunk_samples` / `_webcodecs_codec_string`。
2. **`frame_index` 用 presentation rank**：packet 解码顺序入 `samples` 数组（满足 `VideoDecoder` 喂入要求），`frame_index = start_frame + 按 pts 排序的名次`。完全自包含，**不需要** §1.4 / §4-A / §6 提到的 `frame_timetable` 传参与 N+1 查询。
3. **`VideoDecoderConfig` 字段是 `codedWidth/codedHeight`**（lib.dom），不是计划里的 `displayWidth/displayHeight`。
4. **前端类型用 snake_case**（匹配 API JSON，与 `videoChapters.ts` 约定一致），故 `buildEncodedVideoChunks` 读 `frame_index/pts_ms/...`；`VideoStage` 通过 `GET /chunks` 列表拿 `chunk_size_frames` + 每 chunk 的 signed url（`TaskVideoManifestResponse` 不含这些）。引入 `useQuery` 后 `VideoStage.test.tsx` 需包一层 `QueryClientProvider`（已通过本地 render 包装统一注入）。

## 0. 一句话目标

把 `useVideoChunkDecoder`（已实现解码核心，但缺 demux 输入）与 `VideoChunk`（已存储 mp4 字节，但缺 sample 列表）接通：后端 chunk 生成时用 PyAV 扫包提取 sample manifest 写入 `diagnostics`，前端按 frameIndex 定位 chunk → 拉 samples → 切割字节 → 构造 `EncodedVideoChunk[]` → 走现有 `VideoDecoder` 精确解码。

## 2. 架构决策

| # | 决策 | 备选（不选） | 理由 |
|---|---|---|---|
| **D1** | **后端预 demux**：chunk 生成时用 PyAV 扫包存 sample manifest | 前端实现轻量 mp4 box 解析（moov/stbl/stco）| 前端 box 解析脆弱；后端已有 `av` 库；`_store_video_chunk` 本就有 chunk 文件路径 |
| **D2** | **manifest 存入 `diagnostics["samples"]`**（JSONB 追加 key）| 新建 `video_chunk_samples` 表 | 零 schema 迁移；查询路径不变；样本量小（每 chunk 512 帧以内） |
| **D3** | **新端点 `/chunks/{cid}/samples`** 暴露 manifest | 直接在 `VideoChunkOut` 里内联 | `samples` 体积较大（每帧约 50 bytes × 512 帧 ≈ 25 KB），不适合嵌入 chunk 列表的每行 |
| **D4** | **codec_string 采用安全默认值** `"avc1.4d001e"` 加可选精确值 | 精确解析 SPS NAL extradata | SPS 解析需额外字节操作；浏览器对 `4d001e`（Main Profile L3.0）兼容性好；精确值可后续升级 |
| **D5** | **前端按 frame→chunk 映射缓存 samples**，chunk 粒度 | 全局 frameIndex → sample 缓存 | chunk 粒度缓存与 `useVideoBitmapCache` 一致；无 chunk 边界的越界问题 |

## 3. Sample Manifest 数据模型

### 3.1 后端 `SampleEntry`（dict，存入 diagnostics）

```python
class SampleEntry(TypedDict):
    frame_index: int       # 源视频帧号（chunk start_frame + i，PyAV 无法直接取，估算或从 timetable 对齐）
    pts_ms: int            # 展示时间戳（毫秒）= pts * time_base * 1000
    duration_ms: int       # 帧时长（毫秒）= duration * time_base * 1000
    is_keyframe: bool      # packet.is_keyframe
    size_bytes: int        # packet.size（encoded 字节数）
    offset_in_chunk: int   # packet.pos（chunk 文件内字节偏移）
```

`diagnostics["samples"]` 示例：
```json
{
  "codec_string": "avc1.4d001e",
  "width": 1920,
  "height": 1080,
  "samples": [
    {"frame_index": 0, "pts_ms": 0, "duration_ms": 33, "is_keyframe": true,  "size_bytes": 45123, "offset_in_chunk": 1024},
    {"frame_index": 1, "pts_ms": 33, "duration_ms": 33, "is_keyframe": false, "size_bytes": 3201, "offset_in_chunk": 46147},
    ...
  ]
}
```

**`frame_index` 对齐策略**：从 `VideoFrameIndex`（已有 `pts_ms`）按 `pts_ms` 最近邻匹配推算；若匹配失败，退化为 `chunk.start_frame + i`（序号估算）。精度不影响 `VideoDecoder`（timestamp 用 pts_ms 即可），仅影响 `showFrame` 的缓存 key。

### 3.2 前端 `VideoChunkSampleEntry`

```typescript
export interface VideoChunkSampleEntry {
  frameIndex: number;
  ptsMs: number;
  durationMs: number;
  isKeyframe: boolean;
  sizeBytes: number;
  offsetInChunk: number;
}

export interface VideoChunkSamplesResponse {
  chunkId: number;
  codecString: string;          // e.g. "avc1.4d001e"
  width: number;
  height: number;
  samples: VideoChunkSampleEntry[];
}
```

### 阶段 A · 后端：chunk 生成时写 sample manifest

**文件**：`apps/api/app/workers/media.py`

**新增函数** `_extract_chunk_samples(chunk_path: Path, start_frame: int, frame_timetable: dict[int, int]) -> dict`:

```python
def _extract_chunk_samples(
    chunk_path: Path,
    start_frame: int,
    frame_timetable: dict[int, int],   # frame_index → pts_ms，由 VideoFrameIndex 预先加载
) -> dict:
    """
    用 PyAV 扫 chunk mp4，提取 sample manifest。
    返回 {"codec_string": ..., "width": ..., "height": ..., "samples": [...]}
    失败时返回 {}（由调用方安全跳过）。
    """
```

**实现要点**：
- `av.open(str(chunk_path))` → `stream = container.streams.video[0]`
- `container.demux(stream)` 遍历所有 packet
- `packet.pos` 可能为 None（fragmented mp4 的第一个 packet）→ 跳过该 packet
- `pts_ms = int(packet.pts * float(stream.time_base) * 1000)` if `packet.pts is not None` else 估算
- `frame_index`：用 `pts_ms` 在 `frame_timetable` 中二分查找最近邻
- `codec_string`：固定用 `"avc1.4d001e"`（smart_copy h264）或 `"hev1.1.6.L93.B0"`（hevc）；transcode 输出固定 h264 → `"avc1.4d001e"`
- 提取 `stream.codec_context.width` / `height`
- try/except 包住全部，失败返回 `{}`，不中断 chunk 生成

**插入位置**（`_store_video_chunk`，`media.py:952` 附近，`row.diagnostics = diagnostics` 之前）：

```python
# 扫 sample manifest（WebCodecs demux 用，失败静默跳过）
sample_meta = _extract_chunk_samples(chunk_path, row.start_frame, frame_timetable)
if sample_meta:
    diagnostics.update(sample_meta)   # 追加 codec_string / width / height / samples
row.diagnostics = diagnostics
```

`frame_timetable` 从 `VideoFrameIndex` 查询，可在调用 `_store_video_chunk` 的上层函数传入（批量 query 避免 N+1）。

**verify**：生成一个视频项目 chunk，`SELECT diagnostics->'samples' FROM video_chunks LIMIT 1;` 确认 samples 非 null；长度 == chunk 内实际帧数；第一条 `is_keyframe=true`（smart_copy chunk 起始必为 keyframe）。

### 阶段 D · 前端：buildEncodedVideoChunks 工具函数

**新文件**：`apps/web/src/pages/Workbench/stage/videoChunkDemux.ts`

```typescript
import type { VideoChunkSamplesResponse, VideoChunkSampleEntry } from "./types";

/**
 * 从 chunk bytes + sample manifest 构造 GOP（从最近 keyframe 到 targetFrameIndex）
 * 返回 {config, chunks}，直接传给 decodeChunkToBitmap()。
 *
 * 若 targetFrameIndex 在 samples 中找不到，返回 null（调用方降级回 <video> 路径）。
 */
export function buildEncodedVideoChunks(
  chunkBytes: ArrayBuffer,
  samplesResp: VideoChunkSamplesResponse,
  targetFrameIndex: number,
): { config: VideoDecoderConfig; chunks: EncodedVideoChunk[] } | null {
  const { samples, codecString, width, height } = samplesResp;

  // 找 targetFrameIndex 在 samples 数组中的位置
  const targetIdx = samples.findIndex((s) => s.frameIndex === targetFrameIndex);
  if (targetIdx === -1) return null;

  // 找最近的 keyframe（含 targetIdx 本身）
  let gopStart = targetIdx;
  while (gopStart > 0 && !samples[gopStart].isKeyframe) gopStart--;

  // 构造 EncodedVideoChunk[]（GOP 范围）
  const chunks: EncodedVideoChunk[] = [];
  for (let i = gopStart; i <= targetIdx; i++) {
    const s = samples[i];
    const data = chunkBytes.slice(s.offsetInChunk, s.offsetInChunk + s.sizeBytes);
    chunks.push(
      new EncodedVideoChunk({
        type: s.isKeyframe ? "key" : "delta",
        timestamp: s.ptsMs * 1000,  // μs
        data,
      })
    );
  }

  const config: VideoDecoderConfig = {
    codec: codecString,
    displayWidth: width,
    displayHeight: height,
  };

  return { config, chunks };
}
```

**verify**：单元测试（vitest）：
- 构造 mock samplesResp，mock ArrayBuffer，断言输出 chunks 数量 = gopStart → targetIdx 的帧数；第一个 chunk `type === "key"`；timestamp 单位为微秒。
- targetFrameIndex 不在 samples 中 → 返回 null。

**seek 时触发 demux decode**（在 `currentFrameIndex` 变化的 useEffect 内）：

```typescript
useEffect(() => {
  if (!chunkDecoder.active || currentFrameIndex == null) return;
  if (!chunkSamples || !chunkMeta?.url) return;

  // 已在缓存则直接展示
  if (chunkDecoder.showFrame(currentFrameIndex)) return;

  // 下载 chunk bytes → demux → decode
  let cancelled = false;
  (async () => {
    try {
      const resp = await fetch(chunkMeta.url!);
      const bytes = await resp.arrayBuffer();
      if (cancelled) return;

      const built = buildEncodedVideoChunks(bytes, chunkSamples, currentFrameIndex);
      if (!built) return; // 找不到 frame，降级到 <video>

      await chunkDecoder.decodeChunks(built.config, built.chunks, currentFrameIndex);
    } catch {
      // 静默失败，displayBitmap 降级使用 activeBitmap
    }
  })();

  return () => { cancelled = true; };
}, [currentFrameIndex, chunkSamples, chunkMeta?.url, chunkDecoder.active]);
```

## 5. 不做 / 留作触发项

- **前端 mp4 box 解析**（D1 决策，明确不做）：`moov/stbl/stco` box 手写解析，引入任何 mp4box.js / demuxer 库。
- **ffmpeg.wasm / Broadway.js**（ROADMAP 决策底线）：任何重型 WASM 视频库。
- **精确 codec_string 解析（SPS NAL）**：现阶段用安全默认值（`"avc1.4d001e"`）；如遇解码失败，后续可通过读取 `stream.codec_context.extradata` 提取 `profile_idc` / `level_idc` 精确拼装。
- **旧 chunk 补 samples**（不 backfill）：旧 chunk 的 `diagnostics.samples` 为 null，`/chunks/{id}/samples` 返回 404，前端静默降级到 `<video>` 路径，无用户感知。视频重新生成 chunk 时自然补全。
- **fragmented mp4 支持**：`packet.pos = None` 时跳过，整个 manifest 留空；fragmented mp4 的 demux 需要不同策略，等真实遇到再处理。
- **feature flag 默认 true**：Phase F 完成、监控确认 `errors/decodes < 1%` 后，再切换默认值；本版不改。
- **WebCodecs 在 Safari 的兼容性**：`detectWebCodecsSupport()` 已处理能力检测，Safari 15.4+ 支持 `VideoDecoder`；不另做 polyfill。

## 6. 风险 / 注意

- **`packet.pos` None 的边界**：fragmented mp4（`fmp4`，常见于 HLS segment）的 packet.pos 可能为 None，整个 sample manifest 生成跳过（返回 `{}`）；`smart_copy` 生成的是标准 mp4（`faststart`），`packet.pos` 一般有效；`transcode` 输出也是标准 mp4。生产中若出现 fragmented mp4，chunk 状态仍 ready，只是 `/samples` 返回 404，前端降级无影响。
- **chunk 文件路径时序**：`_extract_chunk_samples` 必须在 chunk 文件上传到 MinIO **之前**调用（文件还在 `tmp_dir` 中），且必须在 `row.status = "ready"` 赋值之前完成，否则前端拿到 ready 状态但 diagnostics.samples 还未写。检查 `_store_video_chunk` 写入顺序（`row.diagnostics = diagnostics` → `await db.commit()` → `row.status = "ready"` 再 commit）。
- **samples 体积**：每帧约 50 bytes × 512 帧 = 25 KB per chunk。1000 个 chunk = 25 MB 写入 `diagnostics` JSONB。PG JSONB 存储经 toast 压缩，实际磁盘占用更小；查询时 `diagnostics->'samples'` 单字段访问不影响索引。若量大可独立表（Phase 2 选项）。
- **`frame_timetable` 传入 `_store_video_chunk`**：当前函数签名需新增 `frame_timetable: dict[int, int]` 参数；确认调用方（`ensure_video_chunks` Celery task）能提供（从 `VideoFrameIndex` 批量 query frame_index→pts_ms）。若不方便传入，可在 `_extract_chunk_samples` 内自行 select。
- **GOP 超出 chunk 边界**：若 GOP 起始帧在上一个 chunk 内（当前 chunk 没有 keyframe），`gopStart` 会停在 chunk 第一帧（non-keyframe），`VideoDecoder` 解码出花帧（正常行为）。缓解：chunk 生成时的 `keyframe_aligned = True` 策略（已落地，smart_copy chunk 保证起始是 keyframe）；transcode 也可加 `-force_key_frames "expr:gte(t,0)"` 强制起始关键帧。Plan 中记录但不阻断本版。
- **内存**：`fetch(chunkMeta.url)` + `arrayBuffer()` 会把整个 chunk（可能几十 MB）载入内存；解码完成后由调用方 GC；不缓存 ArrayBuffer（只缓存解码后的 ImageBitmap，LRU 48 项）。高帧率超长视频需监控内存。
- **docker restart**：`_extract_chunk_samples` 修改的是 `media.py`（Celery worker），修改后需 `docker restart ai-annotation-platform-celery-worker-1`（CLAUDE.md §8）；API 新端点在 `videos.py`，uvicorn `--reload` 自动生效。
