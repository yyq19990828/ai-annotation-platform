# v0.24.7 · 3D WebGPU 稳定帧提交

> Status: implemented；本机三轮性能门、资源 plateau 与受控 device-lost 回退已通过，跨厂商 GPU 仍为 not tested，实验继续默认关闭
>
> 规划与实施日期：2026-08-24—2026-08-25
>
> Implementation authorization: yes

## 1. 问题与根因

上一轮完整资格中，已预取相邻帧的 PCD 解码 p95 已约 3 ms，但 WebGPU geometry 首次绘制 p95 仍为 121.9 ms，比 Legacy 慢 29.8%。临时分段埋点进一步确认，CPU 几何对象构建仅约 2.4 ms；主要差值发生在对象提交后的浏览器绘制窗口。

调用链显示两个重复工作进入了每次切帧的首帧：

- `PointCloudScene.loadPcd()` 销毁并重建实例属性、Sprite、`PointsNodeMaterial` 和 selection buffer；
- `setCameraColorization()` 为当帧相机重新生成最多六路 TSL 节点图并设置 `material.needsUpdate`，使 shader/pipeline 更新与 geometry 的两次 `requestAnimationFrame` 竞争。

关闭相机上色的隔离样本中，WebGPU / Legacy warm geometry 中位数只相差约 4 ms；开启相机上色后差距扩大到约 26 ms，证明相机采样图重建是 warm 尾延迟的主要来源。

## 2. 方案

1. WebGPU 主场景持有容量分级的动态 position/color/selection buffer；nuScenes 当前点数落在 65K 档内，切帧只原地写入并更新实例数，超过容量才按 2 倍扩容。
2. 切帧开始把实例数归零并隐藏对象，`getPointPositions()` 返回 `null`，继续保证旧帧不会暂留或参与相机计算。
3. `PointsNodeMaterial` 持有固定六路相机采样拓扑。每帧只替换 color/depth texture 引用和 extrinsic、rect、intrinsic、宽高及启用状态 uniform，不再改写 `material.colorNode` 或触发 shader 重建。
4. 三视图复用主 geometry 时同步真实 draw count，避免容量 buffer 的未使用尾部被渲染或拾取。

不改变 Legacy 路径、实验开关默认值、点云数据合同、API、数据库或 seed。

## 3. 验证结果

在同一开发机、同一 Chromium Vulkan/WebGPU 进程和 `P-PC-DEV / nuScenes mini scene-0061` 上完成 20 次非相邻冷跳帧与 20 次相邻 warm 切帧：

| p95 指标              | Legacy WebGL2 |   WebGPU |   同轮对比 | 相对优化前 WebGPU |
| --------------------- | ------------: | -------: | ---------: | ----------------: |
| 冷跳帧 geometry       |      340.9 ms | 267.1 ms | 改善 21.6% |        改善 10.2% |
| 冷跳帧 RGB            |      440.9 ms | 317.8 ms | 改善 27.9% |         改善 8.8% |
| 已预取相邻帧 geometry |       98.4 ms |  99.9 ms |  回退 1.5% |        改善 18.0% |
| 已预取相邻帧 RGB      |      343.9 ms | 142.0 ms | 改善 58.7% |        改善 15.4% |
| 首次展开框体精修      |      178.6 ms | 129.2 ms | 改善 27.7% |                 — |

实验样本为真实 `WebGPU` backend，持久 Worker 数量为 1，Canvas 全图回读为 0，浏览器运行时错误为 0。warm depth cache 命中率为 100%，p95 为 14.0 ms；warm camera bitmap 仍呈 0 ms / 约 28 ms 两档，因此继续做了预取时序诊断。

诊断样本确认，慢样本没有重新发起网络请求，而是在当前帧进入时命中尚未完成的 `createImageBitmap` Promise。原先同时预取前后帧会占满 18 张图的三帧缓存；把后续前进帧预取提前到导航成功时，又会形成第四帧竞争，使尚未被当前渲染器 pin 的目标帧先被 LRU 逐出。最终策略改为只自动完整预取前进方向，回退帧保留悬停和键盘聚焦预取。

修正后再次完成 20 + 20 浏览器样本：

| p95 指标                  | Legacy WebGL2 |  WebGPU |        同轮对比 |
| ------------------------- | ------------: | ------: | --------------: |
| 已预取相邻帧 geometry     |      101.4 ms | 99.6 ms |       改善 1.8% |
| 已预取相邻帧 RGB          |      341.3 ms | 99.6 ms |      改善 70.8% |
| 相机 ImageBitmap 就绪等待 |             — |  0.1 ms | ready 命中 100% |
| 相机深度栅格就绪等待      |             — |  0.1 ms | cache 命中 100% |

三视图精修首次展开从 Legacy 的 177.1 ms 降到 118.5 ms，WebGPU rAF p95 为 16.8 ms、最大帧隙为 100 ms；真实 backend、零 Canvas 全图回读和零运行时错误保持不变。

## 4. cold 诊断与修复

将 decoded PCD 的 Promise 命中和真正 ready 分开后，10 个受控 cold 样本得到：

| 导航方式              | geometry p95 | PCD ready 等待 p95 | PCD ready 后绘制 p95 |
| --------------------- | -----------: | -----------------: | -------------------: |
| 直接点击              |     296.8 ms |           176.9 ms |              35.6 ms |
| 先悬停 350 ms，再点击 |     120.1 ms |             4.0 ms |              45.6 ms |

资源侧继续确认：原有 ASCII PCD 每帧约 2.0 MiB，而 nuScenes 原始帧约 678 KiB；Vite proxy 与对象存储直连读取同一个升级后的对象都约 3 ms，预载 ArrayBuffer 后浏览器解码 p95 约 3.4 ms，相机并发下载也不会把 PCD 请求推高到原来的等待时间。因此 cold 的主要问题不是 WebGPU shader、对象存储或 Worker 算力，而是两个时序叠加：

1. nuScenes 导入器将原始二进制点云膨胀为 ASCII PCD，增加了首次传输和解析成本；
2. `SceneTimeline` 点击后立即切换任务，目标 `prefetchFrame()` 仍在 pending，React 路由与工作台更新又延迟了主线程消费 Worker 完成消息。

修复后，nuScenes 导入器输出 little-endian binary XYZ PCD，并能在不重建任务、标注和 scene 的前提下原位升级旧对象；时间轴则先等待目标帧预取 settle，再执行任务导航。开发数据的 39 帧已从约 2.0 MiB/帧缩小到约 416–417 KiB/帧。

浏览器完整样本中，WebGPU cold geometry p95 从修复前的 283.9 ms 降到 159.0–164.1 ms，PCD ready 等待 p95 降到 11.4–13.5 ms，低于 250 ms cold 门。Legacy cold geometry 同轮为 151.9–159.0 ms，说明 cold 路径已不再由实验 renderer 主导。

## 5. 资格判断与下一步

cold 门已经达标，但实验仍不转为正常功能。固定同一 Chromium/WebGPU 进程、相同帧序列连续完成三轮 20 cold + 20 warm 后，WebGPU warm geometry p95 分别为 119.9、136.4 和 147.9 ms，没有随 GPU 进程复用而下降；四类资源仍全部命中。逐样本 Long Tasks、rAF 和 history 分段进一步得到两个独立根因。

### warm 导航

慢样本中，点击到 `history.pushState/replaceState` 占 64.6–68.4 ms，history 提交到 PCD effect ready 只有 17–18 ms，PCD ready 到 geometry paint 约 36–41 ms。`SceneTimeline.handleNavigate()` 在真正导航前等待完整 `prefetchPointCloudFrameAssets()`，而 depth raster 缓存的 `cacheHit` 只表示已有 Promise，不表示计算已经 settle；因此目标帧的后台 depth Worker 仍在运行时，导航会被非 geometry 关键资源阻塞。

两组隔离样本验证了这一点：

| 策略                              | warm geometry p95 |   warm RGB p95 | depth cache hit |
| --------------------------------- | ----------------: | -------------: | --------------: |
| 当前路径，直接点击                |    122.3–147.9 ms | 140.2–153.5 ms |            100% |
| 点击前提供 100 ms 预取领先量      |           98.5 ms |        98.5 ms |            100% |
| 完全关闭相邻 depth 预取           |           91.1 ms |       120.4 ms |              0% |
| 启动 depth 预取但导航不等待其完成 |          113.4 ms |       118.4 ms |            100% |

最后一项同时通过 warm geometry、warm RGB、RGB 相对 Legacy 改善和 depth 命中率门，说明最小修复应保留 depth 预取，但把其完成从导航关键路径移出。

### 三视图展开

CDP CPU trace 在首次 WebGPU 展开中捕获到 60.9–64.7 ms Long Task，其中 `TriViewRenderer.render()` 单独占 54.6–58.5 ms。连续收起再展开时主线程 Long Task 消失、open 降到 83–104 ms，但仍可见 100–116.7 ms rAF presentation gap。源码生命周期与数据一致：`ThreeDWorkbench` 在 collapsed 时条件卸载 `TriViewPanel`，后者 cleanup 会 dispose renderer；再次展开会重新创建 WebGPU renderer、point layer 并提交三路 viewport。

本切片保持实验开关默认关闭，并完成两项有界改动：

1. depth raster 继续在后台启动，但 `SceneTimeline` 只等待 PCD 与相机位图关键资源后就导航；回归测试用未 settle 的 deferred depth Promise 证明导航 Promise 已先完成。
2. 收起三视图时保留 renderer 生命周期；实验 WebGPU 在已有首个框与点云后于隐藏面板完成一次 pipeline/geometry 提交，随后暂停不可见提交，展开时再恢复按需渲染。

`pointCloudAssetCache` 与 `FloatingPanelShell` 都已完成真实 red → green 回归；定向 14 个 Vitest、TypeScript 和相关 ESLint 通过。首次保留挂载后仍捕获到一次 65 ms pipeline Long Task，提前隐藏预热后 Long Task 消失；再暂停预热完成后的隐藏提交，避免三视图随每次换帧争抢首帧。

最终在同一 Chromium/WebGPU 进程连续完成三轮 20 cold + 20 warm，并在每轮首次展开后再收起/重开一次：

| 轮次 | WebGPU cold geometry p95 | WebGPU warm geometry p95 | WebGPU warm RGB p95 | warm depth 命中 | 首开 / 重开 Long Task | 首开 / 重开最大帧隙 |
| ---: | -----------------------: | -----------------------: | ------------------: | --------------: | --------------------: | ------------------: |
|    1 |                 148.6 ms |                 122.7 ms |            125.8 ms |            100% |                 0 / 0 |      16.8 / 16.8 ms |
|    2 |                 140.3 ms |                 116.8 ms |            121.7 ms |            100% |                 0 / 0 |      16.8 / 16.8 ms |
|    3 |                 154.7 ms |                 123.1 ms |            148.7 ms |            100% |                 0 / 0 |      16.8 / 16.8 ms |

上述三轮中的 elapsed 起点位于 Playwright `locator.click()` 之前，实际把 actionability 检查、鼠标移动和跨进程协议开销计入了应用延迟。warm 慢样本的所谓 click 到 history 因此达 35–60 ms，不是 React 导航路径的真实耗时。精修旧口径同样只等浮窗标题可见，没有等三视图实际提交首帧；而 Legacy 在选中框后也被意外提前挂载，导致对照组同样被预热。

最终收口同时修正了产品路径和测量边界：Legacy 折叠时不再因选中框而创建第二个 WebGL context；实验 WebGPU 仍保留一次隐藏预热。帧导航以浏览器实际 `click` 事件为起点，精修则以三视图 renderer 首次 active 提交为终点。修正后在同一 Chromium/WebGPU 进程再跑三轮 20 cold + 20 warm：

| 轮次 | Legacy warm geometry p95 | WebGPU cold geometry p95 | WebGPU warm geometry p95 | WebGPU warm RGB p95 | warm RGB 相对改善 | Legacy / WebGPU 精修首帧 |
| ---: | -----------------------: | -----------------------: | -----------------------: | ------------------: | ----------------: | -----------------------: |
|    1 |                  59.0 ms |                 113.9 ms |                  62.7 ms |             75.9 ms |             74.9% |          129.8 / 24.1 ms |
|    2 |                  61.1 ms |                 106.9 ms |                  58.7 ms |             66.8 ms |             77.3% |          104.3 / 25.2 ms |
|    3 |                  59.9 ms |                 126.5 ms |                  66.9 ms |             67.0 ms |             77.0% |          110.1 / 38.8 ms |

三轮全部通过原有 120 ms warm geometry、250 ms cold geometry、60% warm RGB 相对改善和 20% 精修首帧改善门，没有移动门槛。WebGPU 精修 Long Task 三轮均为 0，rAF p95 与最大帧隙都不超过 16.8 ms，真实 backend 和零运行时错误也保持通过。

当前机器只有 NVIDIA RTX 3090，标准有头与无头 Chromium 虽暴露 `navigator.gpu`，但
`requestAdapter()` 都返回空；只有 unsafe Vulkan 参数能取得 NVIDIA Ampere adapter。跨 NVIDIA、
Intel/AMD 的验证因此在 `ROADMAP.md` 明确记为 `not tested`；本地资格已稳定通过，但在硬件可用并补齐跨设备证据前不得移除实验标记或默认启用。

标准无 GPU 参数的 Chromium 已完成真实工作台回退验证：开启实验设置后实际 backend 为
`webgl2-fallback`，原因明确为 `webgpu-adapter-unavailable`，34,720 点正常显示且无 console/page error。
`usePointCloudScene` 同时增加 device-lost 守卫，确认旧场景会释放、当前页面熔断实验路径并以 Legacy renderer 重建，状态栏保留原始丢失原因。随后用 CDP 受控终止测试 Chromium GPU 进程，验证主视图和三视图的旧 canvas 都会卸载、页面重建 Legacy renderer、点云统计仍可见且无 console/page error。这覆盖了显存压力最终表现为 device lost 时的应用熔断路径；没有在开发机上主动制造不可控的物理 OOM。

### 长会话资源 plateau

20 个离散 cold 帧与其相邻 warm 帧连续往返时，初始基准只在单轮结束后销毁浏览器 context，无法区分
缓存预热与跨轮泄漏。基准现支持同页 1–5 轮，并在每轮后台 settle、强制 V8 GC 后记录 JS heap、
backing storage、renderer/GPU 进程 RSS、点云缓存 owner 和 Worker pending。

修复前的三轮 WebGPU 样本中，深度缓存已经稳定为 8 项 / 4,339,200 B、ImageBitmap 为 18 项 / 6 个
当前引用且 Worker pending 为 0，但 backing storage 仍从 36,610,865 B 增至 37,154,229 B、
37,696,877 B，每轮约增加 542 KiB。该增量与单帧六路深度栅格的 542,400 B 一致：
`DataTexture.dispose()` 已释放
GPU 纹理，但 Three.js WebGPU 后端暂留的 Texture 包装仍通过 `image.data` 强引用 CPU Float32Array。

纹理 dispose 后同步清空 depth payload，完全相同的 20 cold + 20 warm × 3 轮得到：

| 检查点  | WebGPU backing storage | WebGPU GPU RSS | depth cache | Bitmap / 当前引用 | Worker pending |
| ------- | ---------------------: | -------------: | ----------: | ----------------: | -------------: |
| 第 1 轮 |           36,068,957 B |  329,924,608 B | 8 / 4.34 MB |            18 / 6 |              0 |
| 第 2 轮 |           36,069,777 B |  331,669,504 B | 8 / 4.34 MB |            18 / 6 |              0 |
| 第 3 轮 |           36,070,025 B |  324,239,360 B | 8 / 4.34 MB |            18 / 6 |              0 |

第 2→3 轮 backing storage 仅增加 248 B，GPU RSS 回落 7,430,144 B（约 7.1 MiB）；真实 WebGPU、
零 Canvas 全图回读、
零运行时错误保持不变。cold RGB p95 为 166.9 ms，warm RGB p95 为 123.9 ms，相对同轮 Legacy 分别
改善 62.2% 和 61.7%，资源修复没有牺牲上色收益。Chromium renderer RSS 在两种 backend 下都包含
路由历史和分配器预热，5 个离散帧的五轮对照中 WebGPU RSS 为 429.67、458.63、486.11、471.11、
497.45 MB，缓存稳定后不呈逐轮单调增长。WebGPU 自有资源 plateau、本机三轮性能门和受控 device-lost 回退均已通过；剩余阻塞项只是跨厂商 GPU 证据，所以实验标记与默认关闭状态保持不变。
