# v0.10.45 · async_jobs Phase 1：前端切换消费 /async-jobs 统一端点

> **来源**：`ROADMAP.md` §B「async_jobs 统一表收敛（P3）」Phase 1 子集。本版只做前端消费层切换 + 必要的后端 payload enrich 与端点补参，不涉及状态机合并或原表退役。
> **性质**：后端轻量 enrich（workers + API endpoint）+ 前端 `AIPreAnnotateJobsPage` 两个 Panel 替换 API 消费方。
> **前置**：无强前置；async_jobs 索引表（v0.10.16）与 `AIPreAnnotateJobsPage` 双 tab（v0.10.38）均已落地。
> **后续**：Phase 2（async_jobs 升级为单一真值，退役原表）属客户驱动触发项，本版不含。

---

## 0. 一句话目标

`/ai-pre/jobs` 页的图像 / 视频两个 Tab 从直查源表（`/admin/preannotate-jobs`、`/video-tracker-jobs`）切换为消费统一的 `/async-jobs` 端点，使 TopBar 铃铛与历史页共享同一数据源。

## 1. 现状事实（已读码确认）

### 1.1 两条并行的读路径

| Tab | 当前 API | 数据源 | 状态机 |
|---|---|---|---|
| 图像 | `GET /admin/preannotate-jobs` | `prediction_jobs` 表 | 3 态：running / completed / failed |
| 视频 | `GET /video-tracker-jobs` | `video_tracker_jobs` 表 | 5 态：queued / running / completed / failed / cancelled |
| TopBar 铃铛 | `GET /async-jobs` | `async_jobs` 索引表 | 5 态：pending / running / completed / failed / cancelled |

`/ai-pre/jobs` 完全绕过 `async_jobs`，只有 `JobsBell.tsx`（5 s 轮询）真正消费它。

### 1.2 async_jobs 端点现有 query 参数（`async_jobs.py:29-60`）

- `status: Literal["pending","running","completed","failed","cancelled"] | None`（单值）
- `kind: str | None`
- `limit: int = 50`（1-200）
- `offset: int = 0`（offset 分页）
- 无 `project_id` 过滤、无 `search`、无 `status[]` 多选

## 2. 已定决策

1. **payload enrich 在写入时快照**：worker 创建 async_job 时一次性快照显示名称（project_display_id、batch_display_id、ml_backend_name、output_mode、task_display_id、direction），不靠 endpoint 实时 JOIN 额外表；项目名来自 endpoint 对 `projects` 表的一次轻量 JOIN（project_id 已是外键，零成本）。
2. **保留原表端点**：`/admin/preannotate-jobs` 和 `/video-tracker-jobs` 不删，其他消费方（工作台内预标流程）不受影响；本版仅停用 `AIPreAnnotateJobsPage` 内对它们的调用。
3. **分页保持 offset**：当前 `/async-jobs` 用 offset 分页，Panel 列表条目数少（每页 20），cursor 迁移收益低，保持不变。
4. **运行中 failed_count 退化为 `—`**：running 状态下 `result.failed_count` 尚未写入；Panel 展示 `—` 代替实时数字，属已知可接受降级（仅 `batch_predict` 受影响）。
5. **状态 badge 统一用 `AsyncJobStatus` 枚举**：图像 Tab 原来 3 态（无 queued/pending/cancelled），切换后与视频 Tab 使用同一 badge 逻辑；`PENDING` 视觉上等同 `running`（待调度）。

## 3. 后端改动

### 3.1 `apps/api/app/workers/tasks.py` — batch_predict async_job payload enrich

**改动位置**：第 157-177 行，`create_job` 调用处的 `payload` dict。

需在 payload 写入前额外查询：
- `batch_display_id`：`await db.get(TaskBatch, batch_id)` → `.display_id`（nullable，batch_id 可为 None）
- `ml_backend_name`：`await db.get(MLBackend, ml_backend_id)` → `.name`（nullable）
- `output_mode`：已作为 worker 参数传入，直接取

新 payload 结构（在原有 4 个字段基础上追加）：
```python
payload={
    "prediction_job_id": str(job_id),
    "batch_id": batch_id,
    "batch_display_id": batch.display_id if batch else None,   # 新增
    "total_tasks": total,
    "prompt": (prompt or "")[:200],
    "ml_backend_name": ml_backend_name,                        # 新增
    "output_mode": output_mode,                                # 新增
}
```

**约束**：两次额外 `db.get` 包在原有 `try/except` 内，失败时对应字段留 `None`，不阻断主流程。

**补充发现（实施中确认）**：`/async-jobs` 对非 super_admin 按 `user_id` owner-scope 过滤，`batch_predict` 旧 worker 签名未携带触发人；本版需从 `POST /projects/{id}/preannotate` 透传 `current_user.id` 到 `batch_predict(..., user_id=...)`，并在 `create_job` 写入 `user_id`，否则切换后项目管理员看不到自己触发的图像 job。

### 3.2 `apps/api/app/workers/video_tracker.py` — video_tracker async_job payload enrich

**改动位置**：第 28-56 行，`create_job` 调用处的 `payload` dict。

需额外查询：
- `task_display_id`：`task.display_id`（`task` 对象在同作用域已有，直接取）
- `project_display_id`：`await db.get(Project, project_id)` → `.display_id`
- `direction`：`job.direction`（已有）

新 payload 结构：
```python
payload={
    "video_tracker_job_id": str(job.id),
    "task_id": str(job.task_id),
    "task_display_id": task.display_id if task else None,      # 新增
    "project_display_id": project.display_id if project else None,  # 新增
    "from_frame": job.from_frame,
    "to_frame": job.to_frame,
    "model_key": job.model_key,
    "direction": job.direction,                                # 新增
}
```

同样，`project` 查询失败留 `None`，不阻断。

### 3.3 `apps/api/app/api/v1/async_jobs.py` — 端点补参 + JOIN

**改动点**：

**① 新增 query 参数**：
```python
project_id: uuid.UUID | None = Query(default=None)
search: str | None = Query(default=None, max_length=200)
status_in: list[str] | None = Query(default=None, alias="status")
```
- `project_id`：过滤 `AsyncJob.project_id == project_id`
- `search`：ILIKE 匹配 `payload->>'prompt'` OR `payload->>'batch_display_id'` OR `payload->>'model_key'`（`cast(JSONB, Text)`）
- `status_in`：替换现有单值 `status`，支持 `?status=running&status=pending` 多值（`AsyncJob.status.in_(status_in)`）

**② 暴露 `payload` / `result` 字段**：确认 `AsyncJobOut` Pydantic 模型包含：
```python
payload: dict = {}
result: dict = {}
error_message: str | None = None
```
若当前 `AsyncJobOut` 未含这些字段，补上。

**③ 轻量 JOIN projects**：在查询中加 `outerjoin(Project, AsyncJob.project_id == Project.id)` 并在 response 中附加：
```python
project_display_id: str | None = None
project_name: str | None = None
```
或者在 service 层执行一次 `db.get(Project, job.project_id)`（逐行，代码简单，量少不成瓶颈）。

**选择方案**：逐行 `db.get`（代码量少，接口简单；Panel 每页 20 条 = 20 次查询，接受）。

### 3.4 `AsyncJobOut` schema 变更摘要

新增字段：
```python
payload: dict = {}
result: dict = {}
project_display_id: str | None = None
project_name: str | None = None
```

现有字段保留（`id, kind, user_id, project_id, status, progress_pct, error_message, celery_task_id, started_at, completed_at, created_at, updated_at`）。

## 7. 风险 / 注意

- **旧 async_job 行的 payload 缺新字段**：Phase 1 落地前已有的历史行 payload 无 `output_mode` / `batch_display_id` 等新字段；Panel 显示"—"，不影响功能。无需 backfill。
- **`search` 在 payload JSONB 上用 ILIKE**：需 `cast(payload->>'prompt', Text) ILIKE :pattern`，无 GIN index 时对大表全扫；当前 async_jobs 行数小，接受；量上来时补 GIN index。
- **`status[]` 多值参数序列化**：前端用重复 key（`?status=running&status=pending`），FastAPI 用 `list[str]` 接收；注意现有 `JobsBell.tsx` 调用仍用单值 `status` 参数，不改（向后兼容）。
- **Celery task 失败时 payload enrich 可能被跳过**：worker 的 try/except 已包住 create_job，额外的 db.get 放在 try 内；若在 db.get 时 DB 连接异常，async_job 行仍创建（payload 无新字段），不阻断主流程。
