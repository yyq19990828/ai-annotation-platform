## 背景与定位红线

`aap tui` 当前是纯只读监控面板（Projects / Datasets / Jobs 三 tab，jobs 3s 轮询）。
两条不可破的设计红线（写在 `tui.md` + `app.py` docstring）：

1. **TUI 只消费 SDK 公开 API**，绝不碰 `_http` / 内部实现。
2. TUI 被限定在 `[tui]` extra 内，**可整体删除而不影响 SDK / CLI**。

本版补两类东西：jobs/export 的**动作**（写操作），以及 ML Backend 的**健康监控**（只读）。
凡 TUI 要调而 Client 还没暴露的能力，**先补进 `client.py`（顺带进 CLI），TUI 再消费**，
不让 TUI 直接拼 HTTP。破坏性动作（cancel）统一走二次确认弹窗（评审已拍板）。

## 范围

### A 档 · 导出（公开 API 已就绪，纯加 UI）

Projects tab 选中项目 → 触发导出 → 完成后下载 / 复制 url。依赖的公开 API 已存在，无需改 `client.py`：

- `client.exports.create(project_id, targets=[...])` → 返回 `job_id`
- 导出 job 完成后 `job.result["download_url"]`，`client.exports.download(job, dest)` 落地
- targets 取值参考 CLI：`aap_json` / `coco`

### B 档 · 取消 job（后端有端点，Client 未暴露 → 先补 SDK）

后端 `POST /async-jobs/{job_id}/cancel`（软取消）已存在，但 `Client.jobs` 只有
`list / get / wait`，**没有 `cancel`**。需先补：

- `client.py`：`Jobs.cancel(job_id)` → `self._http.request("POST", f"/async-jobs/{job_id}/cancel")`
- CLI：`aap jobs cancel <job_id>`（与新方法对齐，保持 CLI/TUI 能力同步）
- 后端约束需在 UI 侧尊重：仅 `kind ∈ CANCELLABLE_KINDS` 且 `status ∈ {pending, running}` 可取消；
  其余后端返回 400/409 —— TUI 对不可取消的行**禁用/灰掉取消键**，避免必然失败的请求。

### C 档 · ML Backend 健康监控（新增 SDK 资源 + 只读 tab）

这是本版主体新增。后端 `GET /ml-backends?project_id=...` 返回的 `MLBackendOut` 字段很丰富，
天然适合「SSH 下盯 backend 健康」：

- `state`（`connected` / `error` 二态，由 `check_health` 写入）、`error_message`、`last_checked_at`
- `health_meta`：`gpu_info`（显存 used/total/free、利用率%、温度℃、功耗 W）、`host`（容器 CPU/内存%）、
  `cache`（hits/misses/hit_rate/size/capacity）、`model_version`、`capabilities`

**SDK 侧（先补）**：Client 目前**完全没有 ml_backends 资源**，需新增：

- `client.py`：`MLBackends.list(project_id)` / `get(project_id, backend_id)`（**只读**）
- `models.py`：`MLBackend` + `HealthMeta` / `GpuInfo` / `HostInfo` / `CacheStats` 子模型
  （字段对齐后端 schema；可宽松解析，`extra="allow"`）
- CLI（顺带）：`aap ml-backends list --project <id>` / `get`，与新资源对齐

**TUI 侧**：新增 **ML Backends tab**（第 4 个 tab）。

- **project-scoped 聚合**：列表端点要 `project_id`，所以 tab 数据 = 遍历 `client.projects.list()`
  逐项目 `ml_backends.list(pid)` 聚合（N+1，放单个 thread worker，对典型项目数可接受）。
  > 备选：后端有跨项目的 `GET /admin/ml-integrations/all`，但**仅 SUPER_ADMIN**，不能假设 API key 有此角色，
  > 故默认走 project-scoped 聚合；若将来有 API-key 可达的全局端点再换。
- **列**：name / project / state / model_version / GPU 利用率% / GPU 显存 / last_checked_at
- **state 着色**：复用 jobs 着色范式 —— `connected` 绿 / `error` 红
- **详情面板**（回车）：完整 `health_meta`（GPU 温度/功耗/显存、cache hit_rate、host CPU/内存%、
  capabilities、`error_message`）
- **轮询**：健康指标服务端缓存（`last_checked_at`），tab 单独定时刷新（建议 5s，比 jobs 略慢）

### 不在本版范围（明确划走）

- **ML Backend 动作**（`unload` / `reload` / `warmup`）：偏运维、权限更重，本版只做**只读监控**，留待后续。
- 重试失败项（retry-failed）：本版不做。
- 建项目 / 建数据集 / predictions import（表单类）：留在 CLI，**不进 TUI**，守住「不复刻 Web 前端」。

## 设计要点

### 二次确认弹窗（Textual ModalScreen）

- 新增轻量 `ConfirmModal(ModalScreen)`：展示动作描述 + 目标摘要，`y` 确认 / `n`·esc 取消。
- cancel：选中 jobs 行 → 按 `c` → 确认框 → 确认后 thread worker 调 `client.jobs.cancel()`，
  结果经 `call_from_thread` 回 UI，状态栏回显，并立即 `_refresh_jobs()`。
- export：选中 projects 行 → 按 `e` → 确认框（target 先用默认 `aap_json`，不引入表单）→
  `exports.create`，job 进 Jobs tab 由现有轮询接管进度。

### 线程模型（沿用现状）

同步 Client 的所有网络调用继续放 `run_worker(thread=True)`，经 `call_from_thread` 回 UI 线程，
事件循环零阻塞 —— 与现有 `_load_*` 范式一致。ML Backends 的 N+1 聚合也在单个 worker 内串行完成。

### 按键与状态栏

- 新增键写进 `BINDINGS` 与底部 hint：`e=导出`（Projects tab）/ `c=取消`（Jobs tab）。
- ML Backends tab 复用 `r` 刷新、回车看详情，无新增动作键（只读）。
- 不可执行的上下文（如非 pending/running 的 job）按键给状态栏提示而非静默。

## 风险与取舍

- **定位漂移**：动作越加越多会把「监控面板」推成「半个前端」。本版动作只收口到导出 + 取消，
  ML Backend 严格只读；表单类、运维类（unload/reload/warmup）一律拒之门外。
- **N+1 聚合**：ML Backends tab 每次刷新 = 1 次 list projects + N 次 list backends。典型项目数下可接受，
  放单 worker 串行；若项目数大需限流或改全局端点（届时再议）。
- **取消的协作语义**：batch_predict 是软取消（worker 下一条预测边界落 cancelled），UI 不能假设
  「点了就立刻 cancelled」；确认框文案与状态栏体现「已请求取消」，最终终态由轮询反映。
- **Textual 社区维护**：新加 ModalScreen / 第 4 tab 仍只依赖 Textual 公开 widget，保持「可整体删除」。
- **角色可达性**：project-scoped ml-backends 列表对 `_MANAGERS / REVIEWER / ANNOTATOR` 开放，API key
  解析为带 role 的真实 User，故可达；但若某 API key 角色更低（未来新增更低角色），需在状态栏回显 403。
