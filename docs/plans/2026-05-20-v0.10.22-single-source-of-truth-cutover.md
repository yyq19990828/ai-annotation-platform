# v0.10.22 · tool_bindings 单源真值收口（删除派生 classes_config / classes / attribute_schema 列）

> 计划日期：2026-05-20
> 关联 ADR：[0026](../adr/0026-tool-unit-class-and-attribute-binding.md)
> ROADMAP 来源：§A「删除派生 classes_config / attribute_schema 字段」（标 v0.10.18 计划，实际未做）+ 决策底线表「标注配置 / 类别绑定」行

## 背景与问题

v0.10.17（ADR-0026）引入 `tool_bindings` JSONB 作为类别 / 属性配置的「单源真值」，但旧扁平字段 `classes` / `classes_config` / `attribute_schema` 仍在 **写时双写派生**：`apps/api/app/services/project.py:96` 的 `apply_tool_bindings_legacy_sync` 在每次项目 / 模板创建 / 更新 / 改名时把 `tool_bindings` 派生回三个旧列。`projects` 与 `project_templates` 两张表都如此。

结果是 ADR-0026 宣称的「单源」当前是谎言——存储层仍有两份会漂移的真值，且双写逻辑渗进 project / template / export / clone 多处，每加一个 tool_unit 相关功能都要同步维护两套。

## 关键设计决策

### 决策 1：删存储层双写，但保留 `*Out` 响应里的扁平字段（改为序列化时派生）

**不直接删 `ProjectOut` / `ProjectTemplateOut` 的扁平字段**。原因：grep 确认这三个字段被 **8+ 处活跃前端代码**直接消费，不是单一死 fallback：

- `WorkbenchShell.tsx:760,1020`、`AIInspectorPanel.tsx:470` — 读 `classes_config`（跨工具的全局调色板，无 active tool 上下文）
- `useWorkbenchTaskFlow.ts:96`、`useWorkbenchHotkeys.ts:277` — 读 `attribute_schema`
- `useProjectToolBindings.ts:70`、`GeneralSection.tsx:42` — 读 `classes` / `classes_config`
- `ProjectDetailPanel.tsx:92`（AI 预标）— 读 `classes_config`

逐一改造为遍历嵌套 `tool_bindings` 是大而危险的扫荡（部分场景本就需要「跨所有工具的合并视图」，正是 `derive_*` 提供的）。

**「单源真值」的目标是存储层无双写漂移，而非强迫每个读端遍历嵌套结构。** 序列化时从 `tool_bindings` 计算出的扁平投影是合法的「派生只读」视图，与 ADR-0026 决策底线表「`classes_config` 派生只读」完全一致。

### 决策 2：保留反向兼容输入路径 `coalesce_legacy_into_tool_bindings`

该函数把旧客户端 / 旧 AAP JSON（schema 1.0，只带 `classes_config`）的扁平输入反推进 `tool_bindings`。它**只写 `payload["tool_bindings"]`，不依赖被删的列**，删列后照常工作。AAP JSON 是外部格式（有 schema_version 边界），保留输入兼容。`ProjectCreate` / `ProjectUpdate` 的扁平输入字段也保留。

### 决策 3：`derive_legacy_*` 去掉「legacy」语义，升格为规范的「读时派生」helper

`derive_legacy_classes_config` / `derive_legacy_classes_list` / `derive_legacy_attribute_schema` 是纯函数（仅 import typing），正是导出 / 序列化所需的「把 tool_bindings 拍平」逻辑。**保留并重命名**为 `derive_classes_config` / `derive_classes_list` / `derive_attribute_schema`。**只删** writer `apply_tool_bindings_legacy_sync`（它写已删除的列）。

## 实施步骤

### 后端

1. **migration `0078_drop_derived_class_columns.py`**
   - `op.drop_column("projects", "classes" / "classes_config" / "attribute_schema")`

3. **`apps/api/app/services/project.py`**
   - 删 `apply_tool_bindings_legacy_sync`（96-117）。

   - 更新模块 docstring（去掉「v0.10.18 起删除」措辞，改为「读时派生」）。

4. **调用点删 `apply_tool_bindings_legacy_sync`**

   - `:629`（AAP JSON `AAPProjectMeta`）：`classes_config=` / `attribute_schema=` → `derive_*(project.tool_bindings)`。AAP envelope schema 形状不变。

8. **`apps/api/app/services/project_clone.py`**

## 风险与回滚

- **最大风险**：删列后某个被遗漏的写端仍尝试写 `project.classes_config` → `AttributeError` / DB 错误。缓解：步骤 4 + 8 grep 全部写端；先跑全量后端测试再合。
- **回滚**：migration `downgrade -1` 恢复三列；但删列是破坏性 DDL，生产前需快照。dev 环境直接 `alembic downgrade`。
- **不在本版范围**：ADR-0027 第三段（annotation feedback 切单源）；reject_reason_type 已 v0.10.16 落地（ROADMAP 该条陈旧）；`alias_to` / ToolDock 过滤等 P3。

## 验收标准

1. `\d projects` / `\d project_templates` 不含 `classes` / `classes_config` / `attribute_schema` 三列。
2. `apply_tool_bindings_legacy_sync` 及其调用全部移除；`derive_*` 仅作读时派生。
3. `GET /projects/{id}` 响应仍含正确的 `classes` / `classes_config` / `attribute_schema`（从 tool_bindings 派生）。
4. COCO / YOLO / AAP JSON 导出 categories 与属性 schema 正确。
5. 工作台调色板、AI Inspector、热键属性、项目设置类别编辑全部正常（手验）。
6. `uv run pytest` + `pnpm test` 全绿；`pnpm lint` 通过。
