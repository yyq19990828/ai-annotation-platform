## 1. 本版结论

v0.23.19 继续优化默认关闭的 Raster Mask WebGPU `square dilate` 候选，但不预设“atomic compaction
一定比 CPU 更快”。v0.23.18 warm 数据已经把 packed prepare p95 降到约 `2–7 ms`，新的第一 CPU 阶段是
core XOR words → history tile patches，p95 约 `10–16 ms`；完整 GPU wall 仍约 `5–6 ms`，其中 readback
约占主要部分。

冻结方向如下：

1. **先把现有 per-set-bit patch builder 改成 word-oriented scatter 候选。** dense XOR readback 保持不变，
   每个 non-zero `u32` 通过 popcount、首尾 bit 与最多两段 tile span 构造 patch，避免逐 set-bit 映射。
2. **同时建立有硬上限的 GPU sparse XOR records 候选。** 同一 shader 继续写 dense core XOR 作为 exact
   recovery，同时用一个 atomic counter 将 non-zero words 追加为 `(wordIndex, xorWord)`。
3. **records 明确无序，最终 patch 明确有序。** 不为 atomic append 伪造跨运行稳定顺序；Worker 校验
   bounds、non-zero、tail 与 duplicate 后，按 `(tileY, tileX)` 排序最终 patches。
4. **record capacity 固定有界，overflow 不丢结果。** 初始 production 候选上限为 core words 的 `1/4`；
   overflow 或 record invariant failure 时不重算 morphology，直接从同一次 shader 已写好的 dense XOR
   target 做第二次 copy / map，再走统一 word-patch builder。
5. **以联合阶段和端到端收益决定是否保留。** sparse records 只有在 `readback + patch build` 联合 p95、
   operation total p95、典型 workload overflow rate 与资源门同时通过时才进入 production；否则删除 atomic
   buffer / shader 分支，只保留更简单且有收益的 CPU word-scatter。
6. **不改变真值和 history 合同。** 主线程仍接收现有 `MaskHistoryPatch[]`，store、revision、undo / redo、
   save / reload 与 canonical COCO RLE 不感知 sparse records。
7. **不建立 GPU-resident current source。** v0.23.18 upload / submit 仍低于约 1 ms；没有证据支持新增
   revision replay、partial upload、device-lost reconstruction 或 brush 同步协议。
8. **不扩大 kernel 与默认支持面。** 仍只处理已有 `square dilate` 候选；gate 继续默认关闭，Linux RTX
   3090 强制 Vulkan 结果不能替代 macOS、Wayland、Windows 无 flag 资格矩阵。

## 2. 目的与成功定义

### 2.1 本版目的

v0.23.18 warm 成功路径为：

```text
immutable packed base cache
  → word-span ROI assemble + dirty overwrite
  → queue.writeBuffer(source)
  → GPU square dilate + dense core XOR target
  → copy / map / clone 全量 core XOR words
  → Worker 扫描每个 word
  → 对每个 set bit 计算 image/tile/local index
  → byte-packed MaskHistoryPatch[]
```

v0.23.19 候选路径为：

```text
immutable packed base cache
  → word-span ROI assemble + dirty overwrite
  → queue.writeBuffer(source)
  → 单一 GPU pass
      ├─ 始终写 dense core XOR target（exact recovery）
      └─ non-zero word → bounded atomic append record
  → map 固定上限 sparse record buffer
      ├─ valid / no overflow → word-scatter patches
      └─ overflow / invalid → copy + map dense XOR → 同一 word-scatter patches
  → existing response validation / history / save
```

本版优化的是 GPU 输出到现有 history patch 之间的数据面，不改变 morphology 语义，不把 records 暴露给
主线程，也不把计算移回 UI thread。

### 2.2 完成条件

本版只有同时满足以下条件才算完成：

1. dense word-scatter、sparse record word-scatter 与 v0.23.18 per-set-bit builder 对任意合法 core、图片 edge、
   非 32 / 8 / 512 对齐、空/满/稀疏/高密 XOR 都产生 bit-exact patches、changed pixels 与 bounds。
2. shader 每个 non-zero core word 最多发布一个 record；record 为两个 `u32`：row-major `wordIndex` 与
   已清除 tail 的 `xorWord`。
3. sparse record capacity 有固定公式、硬上限和 prospective budget；shader 不得越界写，Worker 不得按
   header count 分配无界数组。
4. overflow、count > capacity、duplicate、zero record、out-of-range word index 或 non-zero tail 都不得产生
   partial patch；dense XOR recovery 成功时仍返回 `backend=webgpu`。
5. dense recovery 使用同一次 compute 已生成的 XOR target，不重复 dispatch；只有 dense copy / map 也失败
   才进入既有 `cpu-fallback`。
6. records 的 append 顺序不进入协议语义；最终 `MaskHistoryPatch[]` 必须稳定按 tile row-major 排序。
7. sparse target / readback、dense target / readback、validator scratch、JS output 与已有 source/cache/scratch
   全部计入 compute ledger，grow-only capacity 进入 plateau，dispose 后归零。
8. dense word-scatter 相对 v0.23.18 patch build p95 至少改善 35%，两轮任一轮不得低于 25%；若未通过，
   不进入 GPU compaction 实施。
9. sparse candidate 相对最终 dense word-scatter 对照的 `gpuReadbackMs + diffOrPatchMs` p95 至少再改善
   15%，两轮任一轮不得低于 10%。
10. 最终候选相对 v0.23.18 的 2048² 与 4K operation total p95 至少改善 15%，两轮任一轮不得低于 10%。
11. 典型 production fixture 的 sparse overflow rate 不高于 5%；专门的高密 fixture 必须稳定 overflow 并
    exact recovery，p95 相对 dense word-scatter 不得恶化超过 10%。
12. Long Task 为 0，GPU owner <= 1，取消 / timeout / stale / device lost 零部分写入，默认构建继续零
    provider chunk、零 shader、零 `requestAdapter()`。

### 2.3 草案阶段不宣称的结论

- 不宣称 sparse records 一定减少 patch build；逐 bit 写 patch 可能才是主要成本。
- 不宣称 readback bytes 减半就会线性降低 `mapAsync()` wall time。
- 不宣称 RTX 3090 的 global atomic contention 可外推到 Intel、AMD、Apple GPU。
- 不宣称 v0.23.18 的 Linux RTX 3090 结果可替代 macOS、Wayland 或 Windows 客户端资格矩阵。
- 不宣称本版完成后即可默认开启 WebGPU。

### 3.2 v0.23.18 当前 warm 证据

环境：Linux X11、Chrome `150.0.7871.114`、RTX 3090、driver `595.84`、有头 Chrome、强制 Vulkan。
两轮均为 `3 warmup + 10 iterations`。

| ROI         | total p50 / p95 round 1 | total p50 / p95 round 2 | prepare p95 两轮 | patch build p95 两轮 | GPU wall p95 两轮 |
| ----------- | ----------------------: | ----------------------: | ---------------: | -------------------: | ----------------: |

由此只能证明：

- patch build 已是最大单一 CPU stage；
- patch build + readback 是下一条值得测量的数据面；
- total 已较低，新方案必须避免用 2–3 ms 的额外同步吞掉理论收益；
- 不能再用旧版本约 100 ms 级总耗时设置宽松退出门。

### 3.3 当前证据仍缺什么

现有 runner 没有持久化以下决定 compaction 成败的字段：

- total core words；
- non-zero XOR word count 与 word density；
- changed pixel density；
- touched history tile count；
- dense builder 的 zero-word scan、set-bit expansion、tile allocation / scatter 分段；
- mapped range wait 与 clone 的分离时间；
- 不同 XOR 形态下的 overflow 概率。

因此 M0 必须先补 dense baseline instrumentation；不能直接从 changed pixels 猜 non-zero word density。

## 4. 规范事实与约束

### 4.1 storage atomic 可作为核心能力，但只使用 `u32`

现行 WGSL Candidate Recommendation Draft 允许 `atomic<u32>` / `atomic<i32>` 出现在 `workgroup` 或
`read_write storage` 中；`atomicAdd()` 原子地返回加法前的值，适合为每个 non-zero word 分配唯一 slot。
本版只用 WebGPU 核心 `atomic<u32>`，不请求 optional feature，不依赖 subgroup 或 vendor extension。

参考：

- [WGSL Atomic Types](https://www.w3.org/TR/WGSL/#atomic-types)
- [WGSL atomicAdd](https://www.w3.org/TR/WGSL/#atomic-builtin-functions)

### 4.2 atomic counter 不提供跨运行稳定 record 顺序

同一个 atomic object 的修改有共同顺序，但不同 invocation 获得 slot 的先后不应被当成可复现的 row-major
顺序。协议因此规定：

- record list 是 unordered set of unique word records；
- Worker 不按 append 顺序决定 patch order；
- patch 内容使用 OR / span write 合并；
- response 前统一按 `(tileY, tileX)` 排序 patches。

不做 CPU `records.sort(wordIndex)`，避免用 `O(k log k)` 抵消 compaction；只排序数量远小于 records 的
最终 touched tile patches。

### 4.3 runtime-sized record array 由 binding size 限定

WGSL runtime-sized array 必须位于结构最后，元素数量由 storage buffer binding size 决定。shader 同时使用
host 传入的 `recordCapacity` 与 `arrayLength()`，实际可写上限取两者较小值；测试必须覆盖 binding size 与
params 不一致时仍不越界。

### 4.4 map / copy 仍是异步边界

sparse output 不引入第二个 compute pass。正常路径在同一 command encoder 中：

1. dispatch morphology + dense XOR + sparse append；
2. copy 固定有界 sparse output 到专用 `MAP_READ` buffer；
3. submit 一次并 map 一次。

只有 overflow / invalid-record recovery 才提交第二个只含 dense XOR copy 的 encoder 并再次 map。该额外
round trip 必须计入 overflow p95，不能藏在 fallback 或 patch 时间中。

## 5. 选项比较与决策门

| 方案                                 | 减少的成本                                  | 新成本 / 风险                             | 草案结论             |
| ------------------------------------ | ------------------------------------------- | ----------------------------------------- | -------------------- |
| dense XOR + 现有 per-set-bit builder | 无                                          | 当前 10–16 ms patch p95                   | 固定 baseline        |
| dense XOR + CPU word-scatter         | 去掉逐 set-bit 坐标 / tile 映射             | 仍扫描全量 words、回读 dense plane        | **先实现并单独资格** |
| single-pass bounded atomic records   | 减少 zero-word scan 与 sparse 成功 readback | atomic contention、额外 buffers、overflow | **条件候选**         |
| two-pass prefix-sum compaction       | deterministic compact order                 | 多 pipeline / pass / scratch / scan       | 拒绝，本版过重       |
| records CPU 全量排序                 | 便于 duplicate / stable order               | `O(k log k)`、额外 clone                  | 拒绝                 |
| GPU 直接生成 history tile payload    | 可省 Worker scatter                         | 动态 tile allocation、协议耦合、边界复杂  | 拒绝                 |
| GPU 只输出 count / bounds            | 少量 summary 成本                           | patch payload 仍需 dense readback         | 收益不足             |
| GPU-resident mutable source          | 可省 assemble / upload                      | revision replay 与恢复协议                | 拒绝                 |
| readback ring / 多 GPU job           | 潜在吞吐收益                                | 编辑 revision 必须串行                    | 拒绝                 |

### 5.1 三阶段 winner 规则

实施不得跳过以下顺序：

1. **Baseline**：v0.23.18 dense XOR + per-set-bit patch；只补测量，不改结果。
2. **Candidate A**：dense XOR + unified word-scatter。
3. **Candidate B**：bounded sparse records + 同一 word-scatter；overflow 走 dense recovery。

决策：

- Candidate A 未通过 patch p95 门：停止本版，不实现 B；保留诊断，记录 no-go。
- A 通过、B 相对 A 的联合阶段收益未通过：删除 B，v0.23.19 只交付 A。
- A、B 都通过：production 使用 B，A 同时承担 dense overflow / invalid records recovery。
- 任何 candidate total p95 未通过：不以局部 stage 改善为由保留复杂实现。

## 7. 目标架构

### 7.1 单一 shader、两种输出

```text
source packed words
  → square dilate
  → xor_word = dilated ^ source_center
      ├─ denseXor[wordIndex] = xor_word             // always
      └─ if xor_word != 0
           slot = atomicAdd(recordCount, 1)
           if slot < capacity
             records[slot] = { wordIndex, xorWord }
           else
             atomicStore(overflow, 1)
```

dense target 必须始终写入：

- 正常 sparse success 不 copy / map dense target；
- overflow 不需要第二次 morphology dispatch；
- invalid sparse records 可从已完成的 dense target 恢复；
- sparse 方案被撤回时，shader 可干净恢复成 v0.23.18 dense-only 版本。

不保留 dense-only 与 sparse 两套 production shader / pipeline；一条 gate 下只能有一个 provider 实现。

### 7.2 Worker 内结果流

```text
provider sparse output
  → parse bounded header
  → overflow? ──────────────── yes → dense target copy/map
  → validate records          invalid → dense target copy/map
  → no
  → sparse records
         │
         └──────────┐
                    ▼
            unified word-patch builder
              ├─ popcount / bounds
              ├─ word span → up to two history tiles
              ├─ patch tile tail validation
              └─ stable tile row-major sort
                    │
                    ▼
            existing morphology response
```

### 7.3 失败分层

| 阶段                                 | 结果                            | backend                    | output strategy         |
| ------------------------------------ | ------------------------------- | -------------------------- | ----------------------- |
| gate / route / adapter / budget 失败 | 既有 CPU 路径                   | `cpu`                      | `dense-cpu`             |
| sparse valid 且未 overflow           | sparse records → patches        | `webgpu`                   | `sparse-records`        |
| sparse overflow                      | dense GPU target recovery       | `webgpu`                   | `dense-overflow`        |
| sparse invariant invalid             | dense GPU target recovery       | `webgpu`                   | `dense-invalid-records` |
| sparse map/copy 失败但 device 仍可用 | 尝试 dense GPU recovery 一次    | `webgpu` 或失败后 fallback | 对应 recovery           |
| dense recovery copy/map 失败         | 既有惰性 dense alpha CPU        | `cpu-fallback`             | `cpu-after-gpu-failure` |
| device lost                          | 既有 CPU fallback / stable lost | `cpu-fallback`             | `cpu-after-device-lost` |

`overflow` 是正常、有界的数据策略分支，不得记成 `gpu-runtime-failed`，也不得使 provider 进入 unavailable。

## 8. Sparse record 二进制合同

### 8.1 WGSL 布局

候选布局：

```wgsl
struct SparseXorRecord {
  word_index: u32,
  xor_word: u32,
}

struct SparseXorOutput {
  count: atomic<u32>,
  overflow: atomic<u32>,
  reserved_0: u32,
  reserved_1: u32,
  records: array<SparseXorRecord>,
}
```

固定事实：

- header 为 16 bytes；
- record stride 为 8 bytes；
- output buffer logical bytes = `16 + recordCapacity * 8`；
- 每次 dispatch 前只需将 16-byte header 清零；超出 `count` 的旧 record bytes 不读取、不清零；
- shader capacity = `min(params.record_capacity, arrayLength(&output.records))`；
- `count` 表示尝试发布的 non-zero word 数，可大于 capacity；
- `overflow != 0 || count > capacity` 都进入 dense recovery。

### 8.2 wordIndex 与 xorWord

```text
xorWordsPerRow = ceil(core.width / 32)
wordIndex = localY * xorWordsPerRow + wordX
```

Worker 还原：

```text
localY = floor(wordIndex / xorWordsPerRow)
wordX  = wordIndex % xorWordsPerRow
bitOriginX = wordX * 32
```

约束：

- `wordIndex < xorWordsPerRow * core.height`；
- `xorWord != 0`；
- 最后一 word 超出 `core.width` 的 tail bits 必须为 0；
- 同一 `wordIndex` 不得重复；
- record 不携带 absolute x / y、session、revision 或 tile identity；这些由已验证 request 决定。

### 8.3 无序记录的验证

Worker/provider 使用一份 `ceil(totalCoreWords / 8)` 的 seen-word bitset 验证 duplicate；2048² 约 16 KiB，
4K 约 32 KiB。该 bitset：

- 在解析前清零；
- 计入 request compute ledger 与 peak diagnostics；
- 不根据 header count 扩容；
- 任一 duplicate / bounds / zero / tail 错误立即丢弃全部 sparse records，进入 dense recovery；
- 不对 record list 做全量排序。

### 8.4 为什么不把 changed summary 放进 atomic header

shader 可以额外 atomicAdd changed pixels、atomicMin / atomicMax bounds，但这会让每个 non-zero word 产生
更多 global atomics，并增加 header validation。word-patch builder 已需读取每个 record，因此使用
`popcount32` 与首尾 set bit 同步计算 summary 更简单。本版 header 只保留 count / overflow。

## 9. Capacity、准入与 overflow

### 9.1 初始 record capacity

```text
totalCoreWords = ceil(core.width / 32) * core.height
recordCapacity = max(1, floor(totalCoreWords / 4))
sparseLogicalBytes = 16 + recordCapacity * 8
```

选择 `1/4` 的原因：

- 可容纳最高 25% non-zero word density；
- 固定 copy / map logical bytes 约为 dense XOR plane 的 50%；
- 高密 workload 明确 overflow，而不是让 records 比 dense 更大；
- 2048² capacity 为 32,768 records，4K 约 64,800 records，均远低于 `u32` count 上限。

M0 必须同时报告 `1/16`、`1/8`、`1/4` 的离线命中率与理论 bytes；production 不允许超过 `1/4`。若
`1/4` 在典型 fixture 仍频繁 overflow，不改成无界 / `1/2`，而是判定 GPU sparse compaction no-go。

### 9.2 为什么不做 adaptive capacity

不根据上一请求 density 自动扩大：

- 会让相同 request 的资源准入依赖隐藏历史；
- 会在 pan / 切题后制造不可解释的 retained bytes；
- 高密 operation 本来更适合 dense recovery；
- 需要新的衰减、reset 与 diagnostics 状态。

capacity 只由当前 core shape 和固定 policy 决定。

### 9.3 overflow 流程

```text
map sparse readback
  → read count / overflow only
  → overflow=true or count>capacity
  → unmap; do not clone partial records
  → submit denseXorTarget → denseReadback copy
  → map exact dense bytes
  → unified word-patch builder
```

要求：

- 不解析、应用或 transfer partial records；
- 不重复 shader dispatch；
- overflow dense readback bytes 与第二次 submit / map wall time单独记录；
- dense recovery 成功仍是成功 WebGPU job；
- 第二次 copy/map 失败才执行一次既有 CPU fallback materialize。

### 9.4 invalid record recovery

以下全部走与 overflow 相同的 dense recovery：

- header count / overflow 组合非法；
- `wordIndex` 越界或 duplicate；
- `xorWord == 0`；
- non-zero tail bits；
- sparse mapped range 长度不符；
- record count 与 cloned payload 不符。

这类事件计入 `sparseInvariantRecoveries`，但不将 provider 标为 unavailable。首次 invariant recovery 后即
停止当前 provider session 的 sparse strategy，后续请求直接 dense XOR；record invariant 本应永不失败，
不值得为“也许是瞬态”继续支付双 readback。reset / Worker replacement 后重新开始资格。

## 10. Unified word-patch builder

### 10.1 输入形态

同一 builder 支持两个迭代器：

- dense iterator：row-major 扫描 dense XOR plane，只 yield non-zero words；
- sparse iterator：按无序 records yield `(wordIndex, xorWord)`。

builder 不关心记录来自 GPU dense、GPU sparse 或 unit golden；避免维护两份 tile patch 语义。

### 10.2 每个 word 的处理

对每个合法 non-zero word：

1. `changedPixels += popcount32(xorWord)`；
2. 用 trailing-zero / leading-zero 得到该 word 的首尾 changed x，更新 bounds；
3. 将 `[bitOriginX, bitOriginX + validBits)` 映射到 absolute image x / y；
4. 以 512 history tile 边界切成最多两个水平 span；
5. 将 span 直接 OR / overwrite 到 tile `Uint8Array` 的 flat row-major bit offset；
6. 不循环每个 set bit，不为每个 pixel 重算 tileX / tileY。

由于 history tile 宽度在 image edge 可能不是 8 / 32 的倍数，目标 bit offset 可能跨 byte。必须使用有界
byte-span write，不能把 row-aligned GPU words 直接 `Uint32Array.set()` 到 patch。

### 10.3 patch allocation 与稳定顺序

- 只为 touched tiles 分配现有 `ceil(tileWidth * tileHeight / 8)` payload；
- 一个 source word 最多触及两个水平 tiles，不跨多个 y tiles；
- sparse records 无序时，Map insertion order 不进入响应；
- 完成后按 `tileY`、再 `tileX` 排序；
- 每个 patch 的 image edge width / height、unused tail 与 core intersection 继续验证；
- 空结果返回 `patches=[]`、`changedPixels=0`、`changedBounds=null`。

### 10.4 Candidate A 的独立价值

即使 GPU sparse records 最终 no-go，word-patch builder 仍可能稳定降低 10–16 ms patch p95，且：

- 不增加 GPU buffers；
- 不增加 shader atomics；
- dense XOR fallback 与正常路径共用；
- correctness surface 主要是纯 TypeScript bit spans，容易用 golden 覆盖。

因此 A 与 B 必须分开提交、分开 A/B，不允许把收益混在一起归因。

同 bundle A/B 通过仅供 benchmark runner 使用的 request strategy selector 单选旧 per-set-bit builder 或
word-scatter；默认 production request 不携带 selector 并始终使用本版 winner。selector 不进入 store 持久化、
用户设置或公开协议，任一请求只运行一个 builder，禁止为采样在同一请求中双跑。

## 11. Buffer 与 compute ledger

### 11.1 持久 GPU buffers

候选 provider 持有：

1. packed source storage；
2. dense XOR target storage；
3. dense XOR MAP_READ buffer；
4. sparse output storage；
5. sparse MAP_READ buffer；
6. params uniform。

sparse success 不销毁 dense buffers；它们是 overflow exact recovery。所有 buffers 仍由单 owner Worker 串行
使用，不增加 readback ring。

### 11.2 逻辑字节与 capacity 字节

snapshot 必须分别报告：

```ts
gpuSourceCapacityBytes: number;
gpuXorCapacityBytes: number;
gpuReadbackCapacityBytes: number;
gpuSparseCapacityBytes: number;
gpuSparseReadbackCapacityBytes: number;
```

准入使用 grow 后的 prospective capacity，不使用本次 logical bytes 冒充 retained bytes。若 sparse 新增容量
导致 budget 不足，当前请求直接使用 v0.23.18 dense XOR path，不回退 CPU，并记录
`sparse-budget-bypass`。

### 11.3 总账本

```text
retained Worker base cache
+ source scratch extra capacity
+ seen-word validator scratch
+ JS packed source payload
+ max(JS dense XOR clone, JS sparse record clone upper bound)
+ prospective GPU source capacity
+ prospective GPU dense XOR target capacity
+ prospective GPU dense readback capacity
+ prospective GPU sparse target capacity
+ prospective GPU sparse readback capacity
+ params
<= request.computeBudgetBytes
```

overflow 路径不 clone partial sparse records，因此 JS dense clone 与 JS sparse record clone 不同时作为 live
payload；若实现无法证明生命周期不重叠，准入必须保守地按两者之和计费。

### 11.4 生命周期

- provider warming 前不分配 sparse buffers；
- gate off / unsupported / below threshold / adapter unavailable 不触发 sparse allocation；
- Candidate A 可在无 sparse buffers 时使用 dense provider；
- device lost、runtime invalidate、reset、Worker terminate、pool dispose 销毁五类 GPU buffers；
- grow-only capacity 在相同 / 较小 ROI 重复请求时不得增长；
- snapshot live bytes 在 dispose 后为 0，累计 counters 只在 pool 生命周期内保留。

## 12. 路由与回退

### 12.1 路由顺序

```text
validate request/session/revision
  → existing static WebGPU route
  → provider ready / dense preflight
  → packed cache prepare
  → sparse prospective preflight
      ├─ insufficient → dense XOR + word-scatter
      └─ admitted → sparse attempt
  → output-specific validation / recovery
  → unified patches
  → existing response/store validation
```

不因 sparse budget 不足回退 CPU；sparse 只是 WebGPU output strategy。

### 12.2 CPU fallback 保持原义

以下仍是既有 CPU 路径：

- gate disabled；
- unsupported operation；
- below pixel threshold；
- provider initializing / unavailable；
- total compute budget 连 dense WebGPU 都无法准入；
- device lost；
- sparse 与 dense GPU readback 都失败。

GPU runtime fail 后仍只 materialize dense alpha 一次，不从 records 或 dense XOR 反向构造 source。

### 12.3 原子应用不变

store 仍校验：

- response id / session / sha256；
- source revision 与 dirty tile revisions；
- patch tile bounds / dimensions / bit length / tail；
- changed summary；
- cancellation / stale generation。

任何 output strategy 都只在完整 response 通过后一次性应用；partial sparse records 永远不离开 Worker。

### 14.2 正式运行

- 同一 Linux X11 / Chrome / RTX 3090 / driver / 强制 Vulkan；
- production store / pool / Worker / provider / history / undo / save；

### 14.3 必过性能门

| 门                    | 要求                                                |
| --------------------- | --------------------------------------------------- |
| Candidate A patch p95 | 相对 v0.23.18 改善 >=35%，任一轮 >=25%              |
| Candidate B joint p95 | 相对 A 的 readback + patch 改善 >=15%，任一轮 >=10% |
| Final total p95       | 2048² / 4K 相对 v0.23.18 >=15%，任一轮 >=10%        |
| Typical overflow rate | <=5%                                                |
| Forced overflow p95   | 相对 A 恶化 <=10%                                   |

| Responsiveness        | Long Task = 0                                       |

### 14.4 保留 / 删除结论

- **Ship sparse**：A、B、total、overflow、correctness、resources 全通过。
- **Ship word-scatter only**：A 与 total 通过，但 B 增量收益、overflow 或资源门失败；删除全部 sparse 代码。
- **No-go**：A 自身未通过，或 final total 未通过；恢复 v0.23.18 builder，仅保留有用 metrics 与失败数据。
- **Inconclusive**：同 schema baseline、GPU 实机、样本数或故障矩阵不完整；不得封版为性能成功。

## 19. 风险与缓解

| 风险                                                  | 后果                        | 缓解                                                             |
| ----------------------------------------------------- | --------------------------- | ---------------------------------------------------------------- |
| patch 成本主要来自 tile allocation，不是 set-bit loop | A/B 收益不足                | Candidate A 独立门，失败即 no-go                                 |
| atomic contention 抵消 readback 节省                  | GPU wall 增长               | 典型 / 高密分开测，B 必须相对 A 有增量收益                       |
| record density 超过 25%                               | 频繁双 readback             | 固定 cap + overflow rate 门，不扩大成无界 records                |
| atomic append 顺序不稳定                              | patch order / checksum 抖动 | records unordered，final patches tile-sort                       |
| duplicate / corrupt record                            | changed summary 错误        | 有界 seen bitset + dense recovery                                |
| non-32 core tail 泄漏                                 | core 外 patch               | shader mask + Worker defensive validation                        |
| overflow 后重复 compute                               | p95 大幅恶化                | dense target always write，只 second copy/map                    |
| sparse buffers 挤占 compute budget                    | 4K 被错误回退 CPU           | sparse budget bypass → dense WebGPU                              |
| power-of-two grow 放大 sparse capacity                | retained bytes 高于 logical | 报告 actual capacity，prospective ledger；必要时独立评估对齐策略 |

## 21. 后续版本触发条件

v0.23.19 只处理 XOR output → history patch pipeline。封版后按新数据决定：

1. **tile patch allocation 仍是第一瓶颈**：评估可复用 patch slab / tile payload pool，但不得让 transfer 后
   buffer 所有权与复用冲突。
2. **GPU pass 成为第一瓶颈**：再做 separable square dilation、workgroup / subgroup 的跨平台 A/B。
3. **prepare + upload 重新成为第一瓶颈**：先复核 cache hit、dirty spans 与 bytes；只有收益上限足够才规划
   revisioned GPU source，不直接建立 mutable shadow。
4. **overflow 高频但 dense path 仍快**：保留 dense strategy，不增加 prefix-sum compaction。
5. **跨平台无 flag 矩阵通过**：另立 default-enable 决策，不在性能版本中翻转 gate。
6. **更多 morphology kernel 有真实需求**：每个 kernel 单独建立 XOR density、capacity、crossover 与 exact
   fallback，不批量扩展 shader。

任何后续项都必须由 v0.23.19 raw stage 数据触发，不能因 WebGPU 或 atomic 在技术上可用就提前实现。
