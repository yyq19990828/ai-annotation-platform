## 1. 决策

v0.24.5 实施完整的 **3D 工作台 WebGPU 实验路径**，覆盖主视图、框体精修三视图和点云相关材质，不只替换相机上色 shader。它通过工作台设置中的实验开关启用，默认关闭；关闭时继续使用当前 `WebGLRenderer + CPU 相机上色` 路径。

本版本的完成条件是“可在真实 nuScenes mini 上做可信 A/B 并安全回退”，不是“成为默认功能”。即使实验指标全部通过，v0.24.5 也保持默认关闭；只有后续独立的推广决策满足第 11 节门槛后，才允许改为正常功能。

实验路径同时解决两类瓶颈：

1. PCD 在主线程重复解析、预取只缓存原始 bytes；
2. 六路相机图切帧后才解码，Canvas `getImageData()` 回读约占 1 秒，随后再复制到 Worker 并上传每点颜色数组。

选定方案是：持久帧资源会话预解析 PCD、缓存解码后的 `ImageBitmap`；WebGPU/TSL 材质直接采样相机纹理。当前实现继续由同一持久 Worker 生成约 90 ms 的低分辨率遮挡深度图并上传 float texture，先删除约 1 秒的 Canvas 回读主瓶颈；GPU depth pass 只有在后续独立 A/B 证明额外收益后才替换它。实验路径不再执行 Canvas RGBA 回读，也不生成 `points × 3` 的 CPU 相机颜色数组。

## 2. 当前基线与原因

2026-08-24 在 `nuScenes mini / scene-0061 / 6 cameras` 上记录到：

| 场景                 |    PCD 解析完成 | 相机样本开始进入 Worker |   RGB 可见 | 主要等待                          |
| -------------------- | --------------: | ----------------------: | ---------: | --------------------------------- |
| 冷跳帧 `0 → 5`       | 点击后约 271 ms |              约 1275 ms | 约 1369 ms | 六图解码、Canvas 绘制与回读约 1 s |
| 已预取相邻帧 `5 → 6` | 点击后约 172 ms |              约 1104 ms | 约 1206 ms | 原始响应命中，但解码样本未缓存    |

Worker 内现有深度栅格与逐点上色约 91–93 ms，并不是第一瓶颈。当前路径还有两个体验放大器：新 geometry 为等待 RGB 被隐藏，以及旧帧在新帧提交前短暂保留。前一项造成空场景，后一项会让用户低估真实加载时间。

因此“只把一次性 Worker 改成持久 Worker”不足以解决问题；它仍会保留六图 Canvas 回读和整份颜色 attribute 上传。

## 3. 外部证据与技术约束

### 3.1 Supervisely 与 CVAT

Supervisely 的公开文档明确说明其 3D 点云渲染从 WebGL 迁到 WebGPU，颜色模式、点大小和对象重着色在 GPU 中完成；大场景还使用 3D tiles，只加载可见与邻近 tile。其完整前端未公开，不能据此断言它如何处理相机 JPEG/PNG、标定、遮挡、显存预算或 fallback。

CVAT 的固定源码快照仍使用 Three.js `WebGLRenderer`、`PCDLoader`、`PointsMaterial`，透视与三个正交视图各自使用 WebGL renderer。其 contextual images 没有本项目的标定相机逐点上色合同，因此 CVAT 只能作为 cuboid 编辑稳定性的参考，不能回答本项目六相机上色性能问题。

### 3.2 Three.js 约束

Three.js 官方 WebGPU 迁移说明要求 `await renderer.init()`，自定义材质迁到 TSL/node material，并说明 `WebGPURenderer` 默认优先 WebGPU、不可用时使用 WebGL2 backend。它仍是实验 renderer，部分场景可能不比 `WebGLRenderer` 快，因此必须保留真实 A/B，不能用 API 名称推断收益。

当前 Three.js `PointsNodeMaterial` 还有一个会直接影响设计的限制：WebGPU 点图元只有 1 pixel，`Points + sizeNode` 无法保留现有可调点大小。实验路径必须把可见点云改为实例化屏幕朝向四边形/精灵。否则“迁移完成”会以视觉退化换性能，测试结论无效。

## 4. 范围与非范围

### 4.1 本版本范围

- 主 3D 场景和三正交视图都使用同一种实验 renderer backend，不允许只迁主视图形成混合结论。
- 当前帧点云、邻帧参考点云、框线、gizmo、网格、坐标轴、标签、点 Mask 高亮和六平面框内裁剪全部通过 WebGPU 兼容性验收。
- 可见点云改为 instanced quad/sprite，保持现有点大小、透视衰减、正交视图观感和高度色。
- RGB 模式使用 TSL 投影、Worker 深度 texture 和相机 texture 直接采样；brightness、contrast、gamma 通过 uniform/node 更新。
- PCD 解码与统计移到持久 Worker；相邻帧缓存 parsed typed arrays 与 decoded `ImageBitmap`。
- 新增本地实验设置 `experiment.pointCloudWebGpuRenderer`，默认 `false`，刷新或重新打开 3D 任务后生效。
- 实验开启时显示实际 backend：`WebGPU`、`WebGL2 fallback` 或 `Legacy WebGL2`，并显示 fallback reason。
- 实验初始化、device lost 或资格失败时自动回退到 Legacy 路径，当前标注数据不受影响。

### 4.2 明确不做

- 不在 v0.24.5 将实验开关默认设为开启，也不删除 Legacy renderer/CPU colorizer。
- 不引入 octree、空间 tiling、服务端转码或新的点云格式；5,000 万点级场景仍属于空间流式加载计划。
- 不改变 `box_3d`、`point_mask_3d`、Scene、Task、标定和 annotation 的 API/数据库合同。
- 不增加 WebGPU 专属标注能力；实验开关只改变实现，不改变保存结果。
- 不以 `navigator.gpu` 存在作为成功；实际落到 `WebGL2 fallback` 的样本不能计入 WebGPU 性能收益。
- 不在本计划内做“实验转正常功能”的发布；第 11 节只定义后续推广门。

## 5. 架构

范围涉及超过 8 个文件和 3 个主要 consumer，数据与回退关系如下：

```text
工作台设置（本地、默认关闭、刷新生效）
        │
        ├─ off ───────────────► Legacy WebGL2 + CPU colorizer
        │
        └─ on
            ▼
      Async renderer factory ── init/资格失败 ──► Legacy WebGL2
            │ actual backend
            ├─ WebGPU
            └─ WebGL2 fallback（只作兼容样本，不算 WebGPU 提升）
            │
            ▼
 FrameResourceSession（generation + budget LRU）
   ├─ persistent Worker：PCD parse/decimate/bounds
   └─ ImageBitmap：1–6 路相机解码缓存
            │
            ├──────────────┬─────────────────┐
            ▼              ▼                 ▼
      主视图 renderer   三视图 renderer   相机投影视图
            │              │                 │
            ├─ instanced point sprites       └─ 共享标定/深度资源
            ├─ camera depth textures
            └─ TSL 直接采样 camera textures
```

### 5.1 Renderer factory 与生命周期

新增 `PointCloudRendererMode = "legacy" | "webgpu-experimental"` 和异步 factory。`PointCloudScene`、`TriViewRenderer` 不再在构造器内假设同步 `WebGLRenderer`，而是先完成 `WebGPURenderer.init()` 再挂载 canvas、controls 和 render loop。

实验设置只在工作台创建场景时读取，切换设置后提示“刷新/重新打开 3D 任务后生效”。这避免热切换 renderer 时丢失相机、选择集、未提交 draft 或 controls 状态，也让 A/B 的每轮生命周期一致。

backend 状态必须来自初始化后的实际 renderer backend，而不是 capability probe。页面记录：requested mode、actual backend、初始化耗时、adapter unavailable、init error、device lost 和 runtime fallback reason。开发环境在 X11 下即使 `navigator.gpu` 存在也可能拿不到 adapter；此时 UI 必须明确显示 `WebGL2 fallback`。

### 5.2 点云表示与交互

Legacy 路径保持 `THREE.Points + PointsMaterial`。实验路径为每个点实例化一个 camera-facing quad/sprite，并以 instance attribute 保存 position、base height color、point id 和 selection mask。node material 固定实现：

- 透视主视图按现有 size attenuation 计算屏幕尺寸；三正交视图保持当前离散 point-size 语义；
- 点 Mask 选择通过 selection attribute 叠加颜色，不覆写 base/camera color；
- 当前帧、邻帧参考点云和点 Mask 复用相同 instanced geometry 合同，但材质 owner 独立；
- picking 继续返回稳定的原点索引，decimate 后的映射不得因 quad 顶点数增加而改变；
- 框线、网格、坐标轴、CanvasTexture label、OrbitControls 和 TransformControls 使用 WebGPURenderer 支持的内置材质路径；不支持项必须在切片 A 修复或阻断该 backend 资格。

三视图继续使用单 renderer + 三个 scissor viewport。当前 cuboid 的六裁剪面迁到 node material/`ClippingGroup` 合同，并逐 viewport 更新；主视图和三视图不得因裁剪实现不同而出现点集差异。

### 5.3 GPU 相机纹理上色

每个成功解码的相机由 renderer owner 上传一份 texture，最多支持 6 路。每路相机的 `width/8 × height/8` 线性深度栅格由持久 Worker 生成，并作为 float texture 上传；这个已测约 90 ms 的阶段保留现有 10cm 遮挡语义，同时避免在 Pilot 中引入跨 renderer owner 的 render-target 生命周期。GPU depth pass 留作后续独立候选，必须以端到端 A/B 证明收益。

可见点 node material 对每个点执行既有 row-major extrinsic、可选 rect、intrinsic、透视除法和边界判断，读取相机 depth texture 做 `0.1 m` 遮挡判断，再选择归一化图像中心距最小的相机 texture。没有覆盖的点显示高度色。采样保持 nearest，brightness/contrast/gamma 只更新 node uniform。

正常实验路径不得调用 Canvas `getImageData()`，不得把整图 RGBA transfer 给 Worker，也不得生成/上传逐点 RGB attribute。单张相机失败只排除该相机；无成功相机时保持高度色并给出原因。超过 6 路相机时该帧 RGB 使用 Legacy CPU colorizer，不能静默丢相机。

### 5.4 持久帧资源会话

现有 `pointcloud.worker.ts` 升级为工作台生命周期内单实例，只负责 WebGPU 路径仍需要的 CPU 资源准备：

- `decode_pcd`：PCD parse、axis convention、decimate、height color、bounds、鲁棒取景统计；
- `cancel_generation`：快速切帧时取消未开始的旧请求；
- CPU colorize 保留在 Legacy 模块，不进入 WebGPU 正常路径。

缓存按 URL + axis + decimate 参数保存 parsed typed arrays，按 URL 保存 Blob 和 decoded `ImageBitmap`；当前帧 pin，相邻 `±1` 低优先级预解码，淘汰时确定调用 `ImageBitmap.close()`。rejected/aborted Promise 不得留在缓存。

缓存使用现有 light/standard/aggressive 性能档位的内部字节预算；预算覆盖 parsed PCD、decoded bitmap 和每个 renderer owner 的 camera/depth textures。三视图卸载必须立即释放其 GPU owner。连续遍历场景后资源必须回到预算 plateau，不能只靠 JS GC。

### 5.5 切帧时序

切帧立即清除旧帧，不让上一帧伪装成已加载；当前 geometry 提交后立即显示高度色。相机资源准备好后只发生一次高度色 → RGB 原子切换，不允许隐藏 canvas，也不允许 RGB → 高度色 → RGB 抖动。

所有 fetch、decode、Worker 和 texture upload 都携带 frame generation；只有当前 generation 能提交 UI。当前 geometry 首次 paint 后立即低优先级预取 `±1`，不再固定等待 800 ms。快速连续导航只保留最后一个高优先级当前帧请求。

### 5.6 回退与 page circuit

- `WebGPURenderer.init()` 失败：canvas 挂载前直接创建 Legacy 场景；
- 实际 backend 为 WebGL2 fallback：允许继续验证功能兼容性，但 backend badge 明示，性能数据不计入 WebGPU组；
- shader/node 资格、纹理预算或深度 fixture 失败：当前页打开 circuit，重建 Legacy 场景并重载当前帧；
- device lost：快照当前 camera、frame、选择对象和 draft PSR，dispose WebGPU owner，创建 Legacy 场景并恢复快照；
- circuit 仅在页面生命周期内生效，刷新可重试；实验设置本身不会被自动改写。

回退期间标注 mutation、undo/redo、提交质检和任务状态均使用现有 React 状态/API，不由 renderer 持有，因此不能丢数据。

## 10. A/B 性能门

固定使用 dev seed 的 `nuScenes mini scene-0061` 39 帧、六相机、standard 档；同一浏览器版本、窗口、点大小、相机轨迹分别运行 Legacy off 与 experimental on。每组记录 10 次冷跳帧、20 次已预取相邻切帧、30 秒空选旋转和 30 秒选中框 + 三视图操作。

WebGPU 实验要判定“有明显效果”，必须同时满足：

- actual backend 为 `WebGPU`；`WebGL2 fallback` 只进入兼容性报告；
- 冷跳帧 geometry first-paint p95 ≤ 250 ms，已预取相邻帧 ≤ 120 ms；
- 冷跳帧 RGB first-paint p95 ≤ 700 ms，已预取相邻帧 ≤ 250 ms，且较当前约 1.2 s warm 基线改善至少 60%；
- 选中框 + 三视图时 FPS p50 不低于 Legacy 的 120%，且 input delay p95 不高于 50 ms；若绝对 FPS 已稳定在显示器刷新率，则改用 GPU frame time 至少降低 20%；
- 250k、500k、1M 点三档中，实验路径的 steady GPU frame time 不得有任一档劣化超过 10%；
- 主线程没有新增 >100 ms Long Task，p95 blocking segment ≤ 50 ms；
- 切帧期间 0 次旧帧、0 次 canvas hidden、最多一次高度色 → RGB；
- 连续往返 39 帧三轮后 CPU/GPU 资源回到预算 plateau，owner 数不单调增长；
- 功能 parity、颜色 golden、device-lost fallback 和 Legacy E2E 全部通过。

切片 A 和切片 B 分别记录一次矩阵。若 A 使选框/三视图变慢而 B 只改善切帧，报告必须分开呈现，不能用切帧收益掩盖交互回归。

| 已预取相邻帧 RGB      |        341 ms | 189 ms | 改善约 45% |

实验路径实际 backend 为 `WebGPU`，完整图片 Canvas 回读由 42 次降为 0，两个 backend 都只创建一个
持久 Worker 且浏览器运行时错误为 0。该结果证明删除 Canvas 回读有明确方向性收益，但尚未达到 60%
暖帧改善门，冷帧 geometry 也未达到 250 ms；样本只有 3+3 次，空标注 dev 项目无法采集框体精修性能。
因此实验开关继续默认关闭，不能据此转为正常功能。框体选择和三视图功能已由带 box fixture 的真实 WebGPU
E2E 验证；六相机首帧也已人工确认真实绘出 34,688 点而非仅通过 DOM 状态。性能资格仍需按本节完整样本
矩阵另行执行。

## 11. 实验转正常功能的后续门

v0.24.5 无论结果如何都保持默认关闭。转正常功能必须另立版本/ADR，并同时满足：

1. 第 10 节真实 nuScenes A/B 全部通过，且报告记录 actual backend；
2. 至少两个不同 OS/GPU 组合在无 unsafe flags 下取得真实 WebGPU adapter 并通过核心交互矩阵；
3. 当前 Linux X11 无 adapter 环境能稳定进入 WebGL2 fallback 或 Legacy，不出现开关后无法进入工作台；
4. 连续试用中没有 P0/P1 数据丢失、device-lost 或颜色错误；
5. 用户确认交互和切帧确实改善后，再决定默认开启、继续实验或撤销 WebGPU 路径。

在这些条件完成前，文档只能称其为实验功能，不能写“WebGPU 已替代 WebGL”。

## 13. 风险与备选

- **instanced quad 比 point primitive 更重**：这正是 Pilot 必须测的核心风险；若选框/FPS 门失败，保持 Legacy 默认，不用切帧收益强推。
- **图片解码与 texture upload 仍有成本**：decoded `ImageBitmap` 预取消除 warm 重复解码；若冷帧仍慢，下一步单独评估纹理分辨率，不篡改颜色口径。
- **主/三视图显存翻倍**：按 renderer owner 计预算，三视图卸载立即 dispose；预算不足回 Legacy RGB。
- **TSL 与 CPU 投影漂移**：固定 row-major、nearest、0.1 m 合同，以 CPU 实现为 golden；不一致即 circuit。
- **WebGPU 设备可用性不稳定**：实际 backend 可见，fallback 样本不冒充 WebGPU，页面可自动回 Legacy。
- **大点云上限没有改变**：整文件 parse/decimate 仍不是空间 streaming；达到 10M/50M 点需求时继续走 tiling backlog。

拒绝“大爆炸替换默认 renderer”：没有 A/B 和跨设备验证前删除 Legacy 会让实验失败直接影响标注。也拒绝“只迁主视图”：用户最明显的卡顿发生在选框和三视图，混合 renderer 无法验证完整工作流。

如果 WebGPU renderer 没有交互收益，但 GPU texture 采样显著改善切帧，应保留测量结果，另立更小的 WebGL2/TSL 不适用替代方案；不得在本计划中悄悄改回旧结论。
