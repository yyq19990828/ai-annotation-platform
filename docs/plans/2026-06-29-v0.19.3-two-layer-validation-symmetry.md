# v0.19.3 · 两层校验对称收口（保存编排 + config-time batchable + 跨端契约）

状态：草案（draft）。接 v0.19.2「ML 能力字段消费」之后，**补齐 v0.19.2 直接暴露的三处不对称**。
全是低成本收口，无 alembic，无新依赖。

## 背景

v0.19.2 给 AI 预标注派发期加了两条能力 422（`batchable=false` 拒批量 / 分类阶段模型不产 `class` 拒），
并把画布属性落点校验泛化。但留下三处「两层模式（config-time warn + dispatch-time 422）」没闭合的缝：

| 缝 | 现状 | 后果 |
|---|---|---|
| **保存编排不校验能力** | `_validate_saved_pipeline`（`projects.py:1363`）只做结构 / 树形校验，不碰 v0.19.2 的能力判据 | 用户能把 `batchable=false` / class-less 模型的编排**存进库**，到执行 `trigger_preannotation` 才 422 —— 延迟报错 |
| **config-time 缺 batchable 预警** | dispatch-time 有 422，但前端源模型选择器没有红字预警（`downstreamModels` 已过滤 `is_interactive` 挡掉大部分下游，但源阶段与边界 case 没兜） | 用户配置期看不到，跑了才知道 |
| **校验判据两份手写** | WS1（TS 警告）与 WS2（Python 422）各写一份 batchable/class 判据 | 易漂移：改一边忘改另一边，警告与拦截脱节 |

## 目标

把上述三处补成对称的两层校验，并加一道防漂移的契约测试。

---

## WS1 · 保存编排路径补能力校验（后端）

`_validate_saved_pipeline`（`apps/api/app/api/v1/projects.py:1363`）当前仅 `PreannotateRequest` 结构校验。
本项把 v0.19.2 的两条能力判据（`_assert_batchable` + 分类阶段 class 检查）抽成可复用函数，保存路径也调用。

**未决（plan 需拍板）**：保存路径用 **422 硬挡** 还是 **响应内 warnings 软提示**？
- 论点（硬挡）：与 dispatch 对称，「存得下必跑得了」；同 backend+model 跑时本就会 422。
- 论点（软提示）：保存是配置中途态，能力快照可能滞后；硬挡可能挡住「先存草稿、之后换 backend」的合法流。
- **建议**：默认**软提示**（保存响应体加 `capability_warnings: [...]`，前端编排面板渲染），保留 dispatch-time 422 作最终把关。理由：保存 ≈ 配置期 = warn 层；执行 = 拦截层。两层语义不串。

落点：
- 抽 `_assert_batchable` + class 检查 → `app/services/pipeline_validation.py`（新文件，纯函数，吃 `(backend, model_id)` + health_meta），WS2/trigger 与保存路径共用。
- `_validate_saved_pipeline` 调用，按上面决策产出 warnings 或 422。
- `PUT /projects/{id}`（保存编排入口）响应补 `capability_warnings`（软提示方案）。

风险：低（读 health_meta，不写库）。须回归既有保存流不被误挡。

验收：保存一条含 `batchable=false` / class-less 下游的编排 → 按选定方案出 warnings 或 422；合法编排静默通过。

## WS2 · config-time batchable 预警（前端）

补上 dispatch-time 422 对应的配置期预警，让 batchable 也成完整两层。

落点：
- 源模型选择器：`apps/web/src/pages/AIPreAnnotate/hooks/usePreannotateConfig.ts` —— 选中源 model `resource_profile.batchable===false` 时给非阻断预警「该模型为交互/有状态模型，不能用于批量预标」。
- `StageCard.tsx` 下游：现 `downstreamModels` 已 `!is_interactive` 过滤；改判据为同时排除 `resource_profile.batchable===false`（更诚实），并在被排除时给一行说明而非静默消失。
- 复用 v0.19.2 已建的 `StageCaps`：加 `batchable?: boolean`，`stageWarning` 增一条 batchable 分支（与 producesClass 同构）。

风险：低（纯前端、非阻断）。

验收：源/下游选到 `batchable=false` 模型时配置期即出预警，与后端 422 判据一致。

## WS3 · 跨端契约测试（防漂移）

判据 SSOT 难跨语言共享，改用**共享 fixture + 双端断言**：一份 JSON fixture 列若干
`{model_caps, expect_warn, expect_reject}`，vitest（断言 TS 警告判据）与 pytest（断言 422 判据）各读同一份，
任一端漂移即测试红。

落点：
- `apps/web/src/__fixtures__/capability-validation-cases.json`（或放 `docs-site/dev/examples/`，双端可读的中立位置）。
- vitest：喂 `useCapabilityValidation` / `stageWarning` 断言 warn 结果。
- pytest：喂 `pipeline_validation` 纯函数断言 reject 结果。

风险：低。fixture 路径需双端都能 import（构建配置确认）。

验收：故意改单边判据 → 对应端契约测试红。

## 排期与依赖

- 三项互相独立；WS1 依赖抽出 `pipeline_validation.py`，WS3 复用它。建议 WS1 → WS3 → WS2 顺序（先有共享纯函数，再写契约，再前端）。
- 无 alembic、无版本破坏。落地范围 = WS1+WS2+WS3 全进 v0.19.3。

## 不在范围

- 把 WS1 的软提示升级为「保存即阻断」：等用户反馈「存了跑不了很意外」再议。
