# v0.19.0 — ML Backend 全局注册表 + 项目级启用（草案）

> 状态：草案。2026-06-25 创建。2026-06-29 完成 PR1 迁移 spike（见 §10）。
>
> 决策依据：[ADR-0044](../adr/0044-global-ml-backend-registry-and-project-enablement.md)。把 backend 实例从「项目子资源」上提为「全局注册表项」，项目层退化为「启用 + 覆盖配置」。minor 版本（0.19.0）反映这是一次跨前后端 + DB 迁移的架构调整。

## 0. 动机

见 ADR-0044 §Context。一句话：能力是 backend 固有的，却被复制进每个项目的 `ml_backends` 行；同一 backend 每项目重注一遍，env-only backend「看得到用不到」，多阶段 DAG 还要求项目里重复注册 ≥2 个 backend。

## 1. Goals / Non-Goals

### Goals

1. **全局注册表**：backend 注册一次（superadmin），能力快照 `health_meta.capabilities` 单份真值。
2. **env 自动 upsert**：env 配置的 backend 启动即成 `source=env` 注册项，取代 `_load_env_only_instances` 临时探测分支。
3. **项目级启用**：项目设置里勾选启用全局 backend + 项目级覆盖（阈值 / 默认变体）；预标 / DAG 下游 / `backends>=2` 门控全部读「项目已启用」集合。
4. **迁移保真**：现有 per-project `ml_backends` 行 → 去重进注册表 + 生成启用关联；历史 prediction 的 backend 溯源不丢。
5. **零协议改动**：backend `/setup` / `/predict` / `/health` 协议不变；纯平台侧注册模型重构。

### Non-Goals

- 不做 `url_override`（项目覆盖全局 URL）——见 ADR-0044，多地址应注册成两个全局项。
- 不改 backend 端代码 / 能力协议。
- 不改预标 worker 执行逻辑（仍按 `pipeline_stages` 跑）。

## 2. 数据模型

```
ml_backend_registry  (全局)
  id, name, url(unique), state, is_interactive,
  health_meta(JSONB, capabilities 单份真值),
  auth_method, auth_token, extra_params(JSONB),   # 端点接入属性,上提到全局(见下)
  source: 'manual' | 'env',
  created_at, updated_at

project_ml_backend   (项目 × 注册项)
  id, project_id(FK projects), registry_id(FK ml_backend_registry),
  enabled(bool),
  box_threshold?, text_threshold?, default_variants?(JSONB),
  unique(project_id, registry_id)
```

- 能力快照只在 `ml_backend_registry` 上；`check_health` 改为对注册表项探测、写回全局行（所有启用项目共享）。
- env backend：启动钩子按 url upsert 成 `source=env` 注册项（已注册同 url 的 manual 项不覆盖）。
- **env 注册项的回收（reconcile）**：env 里删掉某 backend 后，下次启动钩子须把「当前 env 已不存在的 `source=env` 行」**置 `state=disconnected` 而非删除**——保留行 + prediction 溯源，避免僵尸外键。manual 行不受 env reconcile 影响。
- **auth / extra_params 归全局行，不做项目覆盖**：`auth_method`/`auth_token` 是「调用该 URL 的访问凭证」（`ml_client.py:101-104` 每次请求带 `Authorization: Bearer`），`extra_params.max_concurrency` 是「该物理 backend 的并发限速闸（防显存爆炸）」（`ml_client.py:95-99`）——两者都是**端点固有属性、与项目无关**，故随 url 进全局行。项目级覆盖只保留真正业务相关的阈值/变体（`box_threshold`/`text_threshold`/`default_variants`）。
- **顺带修一个隐性限速 bug**：`max_concurrency` 的 semaphore 按 `backend_id` keyed（`ml_client.py:99`）。现状下同一物理 backend 在 N 个项目各注册一行 = N 个独立 semaphore，限速形同虚设（N×4 并发打同一 backend）。全局注册表收成「一物理 backend = 一 registry id = 一 semaphore」，限速首次真正生效。

### 启用上限与新项目默认（替代 `max_ml_backends_per_project` 语义）

- **现状**：`max_ml_backends_per_project`（`settings`，**默认 1**，`ml_backends.py:63`）限制每项目注册数，注释目的是「防显存爆炸」。
- **问题**：默认 1 与本 ADR 动机 #3（多阶段 DAG 检测→分类需 ≥2 backend）**直接冲突**——若新模型把它原样转成「最多启用 1 个」，DAG 开箱即死，等于这次重构没解决自己列的痛点。且「启用 ≠ 同时推理」：启用只是「项目可选用」，真正占显存的是 DAG **运行时并发**，用「最大启用数」当显存保护已不准确。
- **决策**：
  1. **启用不设上限（或上限放大）**，`enabled` 纯作「项目可选用」业务开关。
  2. 「防显存爆炸」改由全局行上的 `max_concurrency` semaphore 兜底——它现在终于真正 per-物理-backend 生效（见上一节）。
  3. **新建项目不自动启用任何 backend**（保持现状：新项目本就无绑定 backend）；用户在项目设置里按需勾选启用。
- `max_ml_backends_per_project` 上限校验逻辑（`ml_backends.py:61-83`）随注册端点一起退役；`GET /projects` 透出的 `ml_backend_limit`（`projects.py:215-216`）一并清理（前端「添加按钮禁用态」改由启用列表逻辑接管）。

## 3. 迁移（alembic）

1. 建两张新表。
2. 回填：`SELECT DISTINCT ON (url) ...` 把 `ml_backends` 去重进 `ml_backend_registry`（health_meta 取最新 last_checked 的那条；auth/extra_params 同取那条）；每行原 `ml_backends` 生成一条 `project_ml_backend(enabled=true)` 带其阈值/变体。
   - **去重冲突检测（auth）**：同 url 但 `auth_token`/`auth_method` 不一致时，去重会丢掉非选中行的凭证。迁移须**检测并告警**（记日志 / 迁移报告列出冲突 url），不静默吞掉。同一物理 backend 用同凭证是常态，冲突应极少；真冲突说明数据本就有问题，留给运维核对。
3. **外键 + 偏好重写：建全量 `old_id → registry_id` 映射，统一重写所有引用。** 去重是 N→1，被合并掉的 N−1 个旧 id 必然失效——所以「保留某行 id 即 registry.id 以最小化扰动」是**部分幻觉**（只救得了存活那一行，N−1 行照样要重映射）。既然全量扫描躲不掉，正式方案就是一张映射表 + 一次性重写下列全部引用，**不要**保留 `ml_backends` 表做兼容视图：
   - FK：`projects.ml_backend_id`、`predictions.ml_backend_id`（两处，`db/models/project.py:44`、`db/models/prediction.py:31,114`，均 `ondelete=SET NULL`）。
   - JSONB（**三**子键，PR1 spike 实测，见 §10 发现 #1）：`users.preferences.ai.params_by_backend`（key 是 backend id）、`model_by_backend`（key）、`interactive_backend_by_project`（value）。
   - **历史溯源保真**：N 个项目用同一物理 backend → 历史 prediction 全部重指向同一 registry 行，这正确（本就是同一模型），溯源不丢。PR1 spike 须有用例覆盖。
   - **`users.preferences.ai` 子键易漏**：`params_by_backend`（参数预设，key 是 backend id）、`model_by_backend`（key 是 backend id）、`interactive_backend_by_project`（value 是 backend id，[v0.18.31](2026-06-26-v0.18.29-ml-capability-wiring-hardening.md) 引入）三者都须一并按映射重写，否则升级后用户的参数预设/引擎/模型偏好静默丢失、回落默认。PR1 spike 已覆盖并修正了原计划漏写 `params_by_backend` 的问题。
4. **回滚：仅「迁移完成、尚未产生新数据」的窗口内干净，之后 forward-only。** down 迁移可把 registry + 关联折叠回 per-project（按 `project_ml_backend` 展开）；但一旦新模型运行产生新数据，回滚即**有损 / 有歧义**：(a) 启用在 0 个项目的全局 backend 折叠后 0 行 → 丢失；(b) 一条 registry 行被多项目启用且有 prediction 指向它 → 折叠成多行时 prediction 该归哪个项目无解。故 PR1 演练的是**空窗口双向演练**；不要向运维承诺「随时可回退」。

> 迁移是本版最高风险项，须独立 spike + 在副本库演练，确认历史 prediction join 不丢。

## 5. 前端

- **ModelMarket**：数据源切全局注册表；增 superadmin「注册/编辑/删除全局 backend」入口（复用现有能力卡）。
- **项目设置 · ML backend**：从「注册 backend」改为「**启用全局 backend** + 项目级阈值/变体覆盖」的勾选列表。
- **AIPreAnnotate**：下游 backend 选择 + `backends>=2` 门控读「项目已启用」集合（v0.18.16 DAG 的 `canAddChild` 门槛随之降低——勾选启用即可，不必重注册）。

## 7. 风险

- **迁移保真**（最高）：历史 prediction 的 backend 溯源、外键 SET NULL 语义（注意 `predictions` 为按月分区表，见 §10 发现 #2）、`users.preferences.ai` 三子键重写、env/manual 同 url 冲突、同 url 不同 auth_token 冲突。缓解：**PR1 为硬阻塞门**（见 §6）——独立 spike + 副本双向演练 + 回滚预案均通过才放行 PR2~6，否则全版本暂停回到 ADR 重评。
- **权限边界**：superadmin 删全局项 → 级联禁用各项目启用行 + 既有 prediction 溯源保留。
- **过渡兼容**：迁移期间新旧读取路径并存的窗口，倾向一次性切换 + 充分测试，不长期双写。

## 8. 验收

- 一个 backend 全局注册一次，多个项目勾选启用即可用；能力快照全局单份。
- env backend 启动自动可见可用（不再需手动注册）。
- 多阶段 DAG：项目勾选启用第二个 backend 即可加分类阶段（无需重复注册）。
- 迁移后历史 prediction 的 backend 溯源完整；全部既有预标 / 能力测试不退化。

## 9. 兼容性

- backend 协议（`/setup`/`/predict`/`/health`）零改动。
- 一次性 DB 迁移（含回滚）；外键 SET NULL 语义保留。
- 对终端用户：项目设置里「注册 backend」语义变为「启用全局 backend」，需用户手册同步。

## 10. PR1 迁移 spike 结论（2026-06-29）

实物产出：`apps/api/app/db/models/ml_backend_registry.py`（两张表模型）+ `apps/api/alembic/versions/0108_global_ml_backend_registry.py`（迁移 upgrade/downgrade）。验证方法：`pg_dump annotation → annotation_spike` 副本库，注入「同 url 跨两项目 + 冲突 auth_token + prediction/projects/三类偏好均引用被合并行」场景，跑 `alembic upgrade head` 再 `downgrade -1`，逐项断言。dev 库全程未动。

### 硬门槛判定：**PASS（带前置条件）**

| 门槛项 | 结果 |
|---|---|
| 副本库 upgrade 演练 | ✅ 干净：去重按 url（winner=last_checked 最新）、registry 单份、`ml_backends` 成功 DROP（证明 FK 全部重指干净） |
| 历史 prediction 溯源零丢失 | ✅ 被合并行的 prediction 正确重指向共享 registry 行，全库 0 悬挂 FK |
| `old_id→registry_id` 全量重写 | ✅ 覆盖 FK 三处 + 偏好三子键；E/F 断言无任何残留 loser id |
| 冲突用例（env/manual 同 url + 同 url 不同 token） | ✅ auth 冲突 `RAISE WARNING` 实测触发（仅冲突 url，单凭证不报） |
| downgrade 演练 | ⚠️ 见发现 #4：可跑通且 0 悬挂，但去重发生过即有损 → forward-only 姿态 |

### 关键发现（改了计划/代码）

1. **🔴 偏好子键是「三」个不是两个**：实测 `users.preferences.ai` 按 backend id 分桶的有 `params_by_backend`（参数预设）、`model_by_backend`、`interactive_backend_by_project`——计划/ADR 都漏了 **`params_by_backend`**。漏写它 = 升级后用户所有参数预设（box/text_threshold、conf 等）静默丢失。迁移已三键全覆盖（验证通过）。**ADR-0044 + 本计划 §3 须把「两子键」更正为「三子键」。**
2. **🔴 `predictions` 是按月分区表**（`predictions_y2026mNN` + `_default`，`relkind='p'`）。FK 在父表与每个分区都有，重指不是一条 ALTER：须 DROP 父表约束（级联各分区）→ UPDATE 父表（传播各分区，`ml_backend_id` 非分区键无行迁移）→ ADD 父表新约束。计划原文未提分区，这是被低估的复杂度，已在迁移处理。
3. **🟡 去重值碰撞非确定**：当用户对「被合并的两个 old_id」都存了 `params_by_backend` 预设，塌成一个 registry id 后保留哪份值是任取（实测保留了 loser 的 0.9 而非 winner 的 0.1）。须定一条确定规则（建议「prefer winner = registry 那份」），否则升级结果不可复现。
4. **🟡 downgrade 比想象更有损**：不止「产生新数据后」有损——**只要 upgrade 发生过去重**，回滚就还不回被合并行的原始 id/name/auth_token（registry 只留 winner 那份）。初版 `ON CONFLICT(id) DO NOTHING` 甚至丢了一个项目的绑定；改进版（多余 per-project 行发新 id、仅第一条复用 registry id 保 FK）能恢复全部绑定且 0 悬挂，但 name/auth_token 仍是 winner 的。**§3/§6「空窗口可回滚」应再收紧为「空窗口 *且* 未发生去重才接近可逆」，正式采 forward-only 姿态。**
5. **🟡 偏好 JSONB 无 downgrade 还原**：回滚后偏好仍是 registry id（空窗口下因 registry id=winner id 未悬挂，但 loser id 永久消失）。downgrade 非真逆。
6. **🟡 冲突告警可能被吞**：`RAISE WARNING` 经 asyncpg 异步迁移 runner 未必出现在 alembic stdout（本次 spike 在 stdout 未见，单独 psql 才见）。PR1 正式版应把冲突报告落到**可靠通道**（写临时审计表 / python logging），别只靠 `RAISE WARNING`。

### 放行 PR2~6 的前置条件

- 修 ADR-0044 + §3：两子键 → **三子键**（含 `params_by_backend`）。
- 定去重值碰撞规则（prefer winner）。
- 接受 **forward-only 回滚**姿态（不再承诺干净 down）。
- 冲突报告改走可靠通道。

> 结论：方案 A 的迁移在副本库验证可行，升级方向稳健；风险集中在 downgrade（已降级为 forward-only）与上面三处 🔴/🟡 待定项。补齐前置条件后可放行 PR2~6。
