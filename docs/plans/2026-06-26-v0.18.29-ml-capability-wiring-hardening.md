# v0.18.29–v0.18.31 · AI 工具栏能力接线健壮性整治(epic)

> 草案 (2026-06-26)。把「画布 AI 工具栏 → backend → 模型 → 变体」这条端到端接线链路里
> 暴露出的 4 个系统性弱点一次性收敛:**协议契约不可观测**、**prompt 受控词表未贯通全栈**、
> **`/setup` 双重拉取**、**交互后端选择持久化 scope 不对称(BUG)**。
>
> 相关:接线现状分析见会话(2026-06-26);上游交互工具栏重设计 epic
> [v0.18.25](2026-06-26-v0.18.25-interactive-ai-toolbar-redesign.md)。
> **边界**:与 [v0.19.x · ML 能力字段消费](2026-06-26-v0.19.x-ml-capability-field-consumption-draft.md) 互补不重叠
> ——那份治「model 字段的下游**消费/落点校验**(resource_profile / output_attribute_types)」,

## 0. 背景 / 缺口(源码核对)

这条链路本身质量不低(大量向后兼容、自愈回落、纯函数可测)。问题集中在 4 处:

| # | 缺口 | 证据 | 后果 |
|---|---|---|---|
| **A** | `/setup` 字段**全链路静默吞错**。平台 `_normalize_model` 逐字段 `.get(x) or default`,前端层层 fallback;`capability_registry` 已是受控词表 SSOT(task/infra/geometry)却**从不用它校验** backend 上报值。 | `ml_capabilities.py:96-146`(只用 `TASK_DEFAULT_GEOMETRY` 派生几何,不校验 task/prompt/geometry 合法性);`capability_registry.py:357-364`(`*_VALUES` 表就绪) | backend 把字段拼错 / 值越界(如 prompt 写 `boxes`、task 写 `seg`)→ 无声吞掉,表现为「工具不亮 / 候选不显示」(同 v0.18.24 类坑) |
| **B** | **prompt 受控词表不存在**,合法值散落 ≥3 处且语义不一致。 | 后端 `ml_capabilities.py:44` `_INTERACTIVE_PROMPTS`(8 个,**含 `text`**);前端 `useBackendRouting.ts:17` `INTERACTIVE_PROMPTS`(3 个,**不含 `text`**);`useMLCapabilities.ts:21` `FALLBACK_PROMPTS`(3 个,含 `text`、不含 `exemplar`) | backend 真上 `scribble` 时前端 `isInteractivePrompt()` 直接 false、工具不亮且零告警;同名概念前后端语义漂移,埋后续 bug |
| **C** | 同一个 `/setup` 被**拉两次、存两份缓存**。 | `useBackendRouting.ts:203` queryKey `["ml-backends",pid,id,"setup"]`;`useMLCapabilities.ts:59` queryKey `["ml-capabilities",pid,backendId]`;**queryFn 同为 `mlBackendsApi.setup`** | active backend 的 `/setup` 永远请求两遍,两份缓存可能短暂不一致 |
| **D** | 交互后端选择持久化 **scope 不对称(BUG)**:三层里只有它没跨设备。 | backend 选择 `useBackendRouting.ts:142-168` → **localStorage** `wb:preferred-interactive:${user}:${project}`;model 选择 `useAiToolModelPref.ts` → 服务端 `preferences.ai.model_by_backend`;variant `usePreannotateConfig.ts` → 服务端 `project.default_variants` | 用户换设备 / 清缓存后交互后端选择丢失,回落默认;与同栏的 model/variant 跨设备行为不一致,体验割裂 |

## 1. Epic 目标 / 非目标

**目标**
- A:平台接收 `/setup` 时按受控词表校验,把「未知字段 / 越界值 / 拼写错」收集成 `capabilities.warnings[]` 落 `health_meta`,模型市场可见。**不拒绝、不改既有解析行为**——纯增可观测性。
- B:`capability_registry` 新增 **PROMPTS 受控词表**(SSOT),后端 `_INTERACTIVE_PROMPTS` 与前端 3 处常量全部派生自它,消除手抄与语义漂移。
- C:合并 `/setup` 双重拉取为单一 query 缓存,零行为变化。
- D:交互后端选择迁到服务端 `preferences.ai`,跨设备持久化,与 model/variant 对齐;保持 `(user, project)` 分桶语义。

**非目标**
- 不改协议 wire 格式、不改任何 backend 的 `/setup` 输出(只校验、不要求 backend 改)。
- 不把 model 选择改成 per-project 分桶(见 §5 决策 2:维持 per-backend 是有意设计,非本 epic BUG)。
- 不碰 model 字段的下游消费/落点校验(归 v0.19.x draft)。
- 无 alembic 迁移:A 落 `health_meta`(JSONB `extra=allow`)、D 加 `preferences.ai` 子键(JSONB),均无需建列。

## v0.18.29 · 协议契约校验 + prompt 受控词表落地(A + B 后端)

> 先做这版:它既建起 B 的 SSOT(后续前端贯通的地基),又装上 A 这张「安全网」——后两版改动时
> 有可见诊断兜底。**纯增量,不改既有解析/路由行为。**

### 设计与改动

**后端**

1. **`capability_registry.py` 新增 PROMPTS 受控词表**。每条带双维度元数据,解决前后端「interactive」语义漂移:
   ```python
   @dataclass(frozen=True)
   class PromptSpec:
       id: str
       label: str
       summary: str
       requires_input: bool   # 需用户/上游显式给输入(点/框/文本/示例) → 不默认走 crop 投递
                              # = 后端旧 _INTERACTIVE_PROMPTS 语义(含 text)
       interactive_route: bool # 进画布交互工具线(逐 prompt 路由到交互后端)
                              # = 前端旧 INTERACTIVE_PROMPTS 语义(不含 text;text 归批量线)
   ```
   成员(从现状代码汇总):`none`(F/F)、`point`(T/T)、`interactive_box`(T/T)、`exemplar`(T/T)、
   `text`(T/**F**,歧义点显式化)、`scribble`/`sketch`/`mask`(T/T,预留)、`bbox`(退役,`requires_input=T`,仅兼容旧快照)。
   派生:`PROMPT_VALUES`、`PROMPTS_REQUIRES_INPUT = {p.id for p if p.requires_input}`、
   `PROMPTS_INTERACTIVE_ROUTE = {... if p.interactive_route}`。
2. **`ml_capabilities.py:44` `_INTERACTIVE_PROMPTS` 改为 `from .capability_registry import PROMPTS_REQUIRES_INPUT`**(语义等价,消除硬编码 8 元组)。
3. **`extract_capabilities` 加校验,产 `warnings`**(新函数 `_collect_warnings(setup, models) -> list[dict]`):
   逐 model 校验 `task ∈ TASK_VALUES`、`infra ∈ INFRA_VALUES`、`supported_prompts ⊆ PROMPT_VALUES`、
   `supported_geometric_outputs ⊆ GEOMETRY_VALUES`;识别「平台不认的顶层/model 键」(对已知 key 白名单求差)。
   每条 `{level, model_id, field, value, message}`。挂 `caps["warnings"] = [...]`(空则 `[]`)。
   **校验只读不改写**——非法值仍按现状原样规范化进 `models[]`,保证零回归。

**前端**

4. **`ModelCard.tsx`**(或 backend 行展开处)读 `capability.warnings`,有则渲染一枚 ⚠ 徽标 + 悬浮/展开列出
   `message`。模型市场是运维注册 backend 的地方,诊断暴露在此最合适。
5. **API 类型**:`MLBackendCapability` 加 `warnings?: CapabilityWarning[]`(`api/ml-backends.ts`)。

### 测试
- 后端:构造含越界 prompt(`boxes`)/未知 task(`seg`)/拼错 key 的 `/setup` → `extract_capabilities` 返回对应 `warnings`,且 `models[]` 规范化结果与现状逐字节一致(零回归快照)。合法 `/setup` → `warnings == []`。
- 后端:`PROMPTS_REQUIRES_INPUT` 与改造前 `_INTERACTIVE_PROMPTS` 集合相等(防迁移漂移)。
- 前端:`warnings` 非空 → ModelCard 渲染徽标;空 → 不渲染。

### 验收
- 注册一个故意上报越界字段的 backend → 模型市场该卡显示 ⚠ + 可读原因;能力解析/工具门控行为与之前一致。
- `curl -s localhost:8000/health` 报 0.18.29。

### 风险
- **校验白名单维护**:「平台不认的键」需维护一份已知 key 集合,缺漏会误报 → 初版只对**受控值越界**(task/prompt/geometry/infra)报 warning,「未知键」检测设保守白名单 + 标 `level:"info"`,避免噪音。
- registry 改动按其文件头约束:受控词表增删本应走 ADR;PROMPTS 是「补登已在协议流通的既有值」,非扩协议 → plan 内注明、可不单独 ADR(沿用 v0.14.11 既有词表惯例)。

## v0.18.31 · 交互后端选择持久化 BUG 修复(D)+ `/setup` 双拉合并(C)

> 同碰前端 routing 拉取/持久化层,一次性收敛。

### 设计与改动

**C — 合并 `/setup` 双拉**

1. 统一 `useBackendRouting` 与 `useMLCapabilities` 的 `/setup` queryKey 为同一形状
   (推荐 `["ml-backend-setup", projectId, backendId]`),两 hook 共享 React Query 缓存,active backend 不再请求两遍。
   `staleTime` 取齐(均已 5min)。**纯缓存层,无行为变化。**

**D — backend 选择迁服务端(BUG 修复)**

2. **`schemas/user.py:AIToolPreferences` 加子键**(`extra="forbid"` 需显式声明):
   ```python
   # 交互后端(引擎)选择,按 project 分桶(每项目各记用哪个交互后端);跨设备,与 model/params 对齐。
   interactive_backend_by_project: dict[str, str] = Field(default_factory=dict)
   ```
   `me.py:update_preferences` 的 `ai` 子树深合并已覆盖此键,**无需改端点**(深合并语义天然支持新子键独立 PATCH)。
3. **新 hook `useInteractiveBackendPref(projectId)`**(仿 `useAiToolModelPref`):
   读 `preferences.ai.interactive_backend_by_project[projectId]`,debounce 600ms 写回
   `{ai:{interactive_backend_by_project: {...}}}`。
4. **`useBackendRouting` 改造**:
   - 删 `storageKey`/`readStoredPreferred`/`writeStoredPreferred`(localStorage 三件套,`:142-168`)。
   - `preferredOverride` 初值改读 hook 注入的 `savedInteractiveBackendId`(替换 `:234-236` 的 localStorage 读)。
   - `setPreferredInteractiveId` 改调 hook 的 `save`(替换 `:250-256` 的 localStorage 写)。
   - **`overrideValid` 自愈逻辑保留**(`:243-247`):后端被删/不可达时回落默认规则,不变。
5. **一次性迁移(可选,低优先)**:首次加载时若服务端无值而 localStorage 有旧 `wb:preferred-interactive:*`,
   读出写入服务端再清除 localStorage。**倾向不做**——backend 选择本就轻量、丢失即回落默认,迁移代码不值;
   plan 内注明:老用户首次换设备前在本机仍读得到(若保留读 localStorage 作二级回落)。最终选「不迁移、直接切服务端」,
   接受老用户一次重选。

### 测试
- 后端:`AIToolPreferences` 加键后,三个子 hook(params/model/interactive_backend)各自独立 PATCH 互不覆盖(扩展 `test_me_preferences.py` 现有深合并用例)。
- 前端:`useBackendRouting` 单测(`resolveInteractive` 三情形 / 兜底 / reachable 降级)行为不变,持久化来源换为注入值;C 合并后 active backend 仅一次 `setup` 请求(query 调用计数断言)。
- 回归:切交互后端 → 刷新页面 / 模拟换设备(清 localStorage、保留服务端)→ 选择保持。

### 验收
- 选交互后端 → 清浏览器缓存 / 换设备登录 → 选择仍在(对齐 model/variant)。
- DevTools Network:进工作台后同一 backend 的 `/setup` 只发一次。
- `curl -s localhost:8000/health` 报 0.18.31。

### 风险
- **`extra="forbid"`**:必须先加 schema 字段再发新 payload,否则 422。前后端同版本发布。
- **deep-merge 依赖**:`interactive_backend_by_project` 独立 PATCH 不冲掉 `model_by_backend`/`params_by_backend` —— 已由 `me.py` 深合并保证,测试须覆盖三键交叉。
- **scope 一致性**:backend 选择保持 `(user, project)` 分桶(键为 projectId),勿误并入 `by_backend`;这是与 model 选择 scope 不同的**有意**区别(见 §5 决策 2)。
- **⚠ 0.19.0 迁移耦合(backend-id 作为 value)**:`interactive_backend_by_project` 的 value 与现有 `model_by_backend` 的 key **都是 backend id**。[v0.19.0 全局注册表](2026-06-25-v0.19.0-global-ml-backend-registry-draft.md) §3 迁移会 `SELECT DISTINCT ON (url)` **去重** per-project backend 行进全局注册表,**部分旧 backend id 会被合并失效**。届时这两个 `preferences.ai` 子键里存的 backend id 必须在 0.19.0 迁移脚本里**一并重映射**(否则用户引擎/模型偏好升级后静默丢失,回落默认)。已在 v0.19.0 draft §3 加入重映射清单;本版落地时无影响(那时 backend 仍 per-project、id 未变),仅作前向提示。

## 5. 开放决策点(已给推荐,可推翻)

**决策 1 — B 前端实现:codegen(已定)。**
用户确认打算给整个 registry(task/infra/geometry/prompt)上 codegen 统一对外,故 B 不再走「单点 + 契约测试」,
升级为完整 codegen 管道,详见 [v0.18.30 · 能力受控词表 codegen 管道](2026-06-26-v0.18.30-capability-registry-codegen.md)。
理由:收益从「prompt 3 处」扩大到「task/infra/geometry/prompt 全栈 + 消灭 `labels.ts` 与 `modelTaskLabel`
两份 task 映射」,且能 1:1 镜像现有 OpenAPI snapshot codegen 链路,基建成本被现成模式摊薄。

**决策 2 — D 是否把 model 选择也改 per-project。**
推荐**否**。判断:backend 选择是 per-project(「这个项目我用哪个引擎」),model 选择是 per-backend
(「这个引擎我爱用哪个模型」)——两者 scope 不同是**合理的**,真正的 BUG 仅是 backend 选择用了 localStorage。
故 D 只修存储介质(localStorage→服务端),保持 `(user,project)` 分桶,不动 model 的 `(user,backend)` 分桶。
**若产品语义其实是「同一 backend 在不同项目想各记 model」,则另立一版把 `model_by_backend` 升为
`model_by_project_backend`——但那是行为变更,不属本 epic「修不对称」的范围。**
