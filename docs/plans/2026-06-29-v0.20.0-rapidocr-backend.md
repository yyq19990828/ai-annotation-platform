# v0.20.0 · RapidOCR backend 接入（第五 backend · OCR 任务族首发）

状态：草案（draft）。minor 版本——平台**首个真实 OCR backend**，把协议早已留好的 `ocr` 任务族从
「mock 形态」激活为真实推理，并成为 v0.19.2 WS1 `text`/`language`/`orientation` 落点校验的**第一个真实 producer**。

## 背景

- 协议层早已就绪：`capability_registry.py` 有 `ocr` TaskSpec（`default_geometry=("bbox",)`，protocol_notes
  写明 `attributes.text` 必填 + 可选 `attributes.language`/`.orientation`，协议 v2 §4.1 范例 C）；
  `docs-site/dev/reference/ml-backend-protocol.md` §4.1.7 定义了 OCR result 映射
  （`ocr_text → attributes.text`；`orientation → attributes.orientation`）；mock-v2-backend 有 PaddleOCR 条目。
- 但**没有真实 OCR backend**：现有四个（yolo / gsam2 / sam3 / onnxtools）都不产 OCR。
- v0.19.2 WS1 给 `text`/`language`/`orientation` 加了落点校验，却没有 backend emit 这三类 —— 这条路从未被真实数据走通。

[RapidOCR](https://rapidai.github.io/RapidOCRDocs/latest/model_list/) 正好补这块：ONNXRuntime 引擎、
det（文本检测）+ cls（文本行方向分类）+ rec（文本识别）三段流水线、PP-OCRv4/v5 多语种（中/英/日/韩/40+），
输出文本框 + 文本 + 方向。与平台 `onnxtools-backend` 同 infra（onnx），接入成本可控。

## 目标

新建 `apps/rapidocr-backend/`，自报协议 v2.2 的 `ocr` model，`/predict` 真实跑 RapidOCR 三段，
返回 `polygon`（或 bbox）几何 + `attributes.text` / `attributes.orientation` / `attributes.language`，
端到端走通平台 OCR 读路径 + WS1 落点校验。

## 工作项

### WS1 · backend 容器骨架（仿 onnxtools-backend）

- `apps/rapidocr-backend/{main.py, Dockerfile, pyproject.toml, README.md}`，结构镜像 `onnxtools-backend`。
- 依赖：`rapidocr-onnxruntime`（CPU）或 `rapidocr-paddle`/GPU 变体（按部署）。默认 CPU（OCR det/rec CPU 友好，正好配 v0.19.5 CPU 队列）。
- `GET /setup` 自报：

```jsonc
{
  "name": "rapidocr",
  "infra": "onnx",
  "warmup_endpoint": true,
  "models": [{
    "id": "rapidocr-ppocrv5",
    "display_name": "RapidOCR · PP-OCRv5 多语种",
    "task": "ocr",
    "model_family": "rapidocr",
    "is_interactive": false,
    "composition": "composite",          // det+cls+rec 内部三段编排，一次 /predict 一气呵成
    "supported_prompts": ["none"],        // 批量自动，无交互
    "supported_inputs": ["full_image", "crop"],
    "supported_geometric_outputs": ["polygon"],   // RapidOCR 出四点框 → polygon（bbox 亦可降级）
    "output_attribute_types": ["text", "language", "orientation"],
    "output_attribute_schema": [
      {"key": "text", "label": "识别文本", "type": "text"},
      {"key": "language", "label": "语言", "type": "select", "options": [/* zh/en/... */]},
      {"key": "orientation", "label": "方向", "type": "select", "options": [/* 0/90/180/270 */]}
    ],
    "resource_profile": {"device": "cpu", "batchable": true},
    "supported_variants": [/* 语言轴 / 版本轴 PP-OCRv4|v5 / mobile|server，按 model_list 列举 */]
  }]
}
```

### WS2 · `/predict` 真实推理 + result 映射

- 接 `BatchPredictRequest{tasks:[...]}`，逐 task 跑 RapidOCR（det→cls→rec），按平台 OCR adapter 映射：
  - 每个文本行 → 一个 result：`polygon`（四点）+ `attributes.text`（rec 文本，**必填**）+ `attributes.orientation`（cls 方向）+ `attributes.language`（rec 模型语言/检测）。
  - 置信度 → prediction 一等 `score`（不入 attributes，符合 v0.19.2「score 不是输出属性」决定）。
- 返回 `BatchPredictResponse{results:[...]}`，与其它四 backend 同构（`for t in req.tasks` 顺序循环）。
- `POST /warmup`（协议 §4.4）：预热 det/cls/rec 三模型进内存池。

### WS3 · 平台读路径核验 + 接入

- 核验平台 OCR 读路径把 `attributes.text/language/orientation` 正确落库（`to_internal_shape` /
  prediction adapter）。协议 reference §4.1.7 已声明映射，但需用真实数据回归（此前只有 mock）。
- dev 接入：`docker-compose.yml` 加 `rapidocr` 服务；注册用 `172.17.0.1:<宿主端口>`（见 reference memo）。
- 文档：`docs-site/dev/ml-backend/` 补 RapidOCR 接入说明；mock-v2-backend OCR 条目可指向真实形态。

### WS4 · 端到端验证 WS1 落点校验

- 建一个启用 OCR 工具 + 配了 `text`/`language`/`orientation` 属性的项目跑 RapidOCR 预标 → 文本/语言/方向落库。
- 故意删掉项目的 language 属性 → 画布出 v0.19.2 WS1 的「采纳后该属性将丢失」警告（**首次真实触发**）。

## 风险

中高（新容器 + 真实推理 + 多语种模型管理）：
- ONNX 模型体积/下载：det+cls+rec×多语种，镜像烤模型须 rebuild（参考 sam3 经验：COPY 烤模型必 rebuild 才生效）。
- GPU 库路径坑（若上 GPU 变体）：参考 onnx backend GPU libpath memo（`LD_LIBRARY_PATH` 含 torch nvidia libs）。
- `language` 取值：RapidOCR 的语言是「rec 模型选定」而非「逐框检测」，多语种混排时 `attributes.language` 语义需明确（按所选 rec 模型标，或留空）。先 MVP：按 model variant 的语言标，文档写清。
- 几何选 polygon vs bbox：RapidOCR 出四点，优先 polygon；项目只启用 bbox 工具时由 WS1 几何兼容警告兜（v0.19.2 已有）。

## 验收

- `rapidocr` backend 注册后模型市场显示 `task=ocr` 的 model，徽标含 OCR / 可批量（吃 v0.19.4 徽标）。
- 对一张含文字图片跑预标 → 文本框 + `attributes.text` 落库可见，方向/语言按声明落库。
- 项目缺 language 承接位时画布出 WS1 警告（端到端走通前瞻落点）。
- `batchable=true` + `device=cpu` → 进 v0.19.5 CPU 队列（若 v0.19.5 已落）。

## 排期与依赖

- 与 v0.19.5 协同（CPU 队列）但无强依赖；可独立接入。
- 是 v0.20.1（属性语义角色）的**前置 producer**——先有真实 OCR 属性输出，语义角色映射才有东西可测。
- 体量大，建议独立 ADR 记「为何选 RapidOCR / OCR 几何选 polygon / language 语义边界」。

## 不在范围

- `doc_layout`（版面分析）backend：另立（协议已留 TaskSpec，RapidOCR 不含版面）。
- 逐框语言检测（per-line language）：MVP 按 rec 模型语言标；细粒度另议。
