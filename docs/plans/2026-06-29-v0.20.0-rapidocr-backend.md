## 能力分解（2026-06-29 已定）

RapidOCR 端到端 = `det → cls → rec` 三段：det 全图检测文本框（四点）并按多边形几何摆正抠出水平 crop；
cls 判断已摆正 crop 是否上下颠倒（180°）并翻正、产出 orientation；rec 对摆正 crop 识别文本。
**cls 输入是 det 抠好的 crop、只解决残留 180° 歧义，无独立标注价值 → 内化进 rec 与端到端，不单独暴露。**

对外自报三个 model（映射平台现成任务族）：

| 能力 | 平台任务 | 输入 → 输出 | composition | cls 角色 |
|---|---|---|---|---|
| **det 文本检测** | `detection` | full_image → polygon 文本框（无文本） | atomic | 无 |
| **rec 文本识别** | `ocr` | crop → `attributes.text`（+`orientation`） | atomic | **内部跑** cls 校正 + 出 orientation |
| **端到端 OCR** | `ocr` | full_image → polygon + text + orientation | composite | 内部 det→cls→rec |

平台 pipeline 可把 `det（源阶段）→ rec（下游吃 crop）` 串成编排；端到端 composite 是 RapidOCR 一次 `/predict` 全流程的便捷入口。

## 锁定模型矩阵 + 权重清单（实查 v3.9.0 model_list，2026-06-29）

RapidOCR v3.9.0 onnxruntime 引擎实有 `PP-OCRv4 / v5 / v6`（v6 **已提供**）。我们选用的 **13 个 onnx 文件**
（URL 统一形如 `https://www.modelscope.cn/models/RapidAI/RapidOCR/resolve/v3.9.0/onnx/<版本>/<组件>/<文件>.onnx`）：

| 能力 | variant（version·size·lang） | 文件 |
|---|---|---|
| det | v5 · mobile | `PP-OCRv5/det/ch_PP-OCRv5_det_mobile.onnx` |
| det | v5 · server | `PP-OCRv5/det/ch_PP-OCRv5_det_server.onnx` |
| det | v6 · tiny | `PP-OCRv6/det/PP-OCRv6_det_tiny.onnx` |
| det | v6 · small | `PP-OCRv6/det/PP-OCRv6_det_small.onnx` |
| det | v6 · medium | `PP-OCRv6/det/PP-OCRv6_det_medium.onnx` |
| cls（内化共享） | mobile | `PP-OCRv5/cls/ch_PP-LCNet_x0_25_textline_ori_cls_mobile.onnx` |
| cls（内化共享） | server | `PP-OCRv5/cls/ch_PP-LCNet_x1_0_textline_ori_cls_server.onnx` |
| rec | v5 · mobile · 通用(中英) | `PP-OCRv5/rec/ch_PP-OCRv5_rec_mobile.onnx` |
| rec | v5 · server · 通用(中英) | `PP-OCRv5/rec/ch_PP-OCRv5_rec_server.onnx` |
| rec | v5 · mobile · 英文 | `PP-OCRv5/rec/en_PP-OCRv5_rec_mobile.onnx` |
| rec | v6 · tiny · 通用 | `PP-OCRv6/rec/PP-OCRv6_rec_tiny.onnx` |
| rec | v6 · small · 通用 | `PP-OCRv6/rec/PP-OCRv6_rec_small.onnx` |
| rec | v6 · medium · 通用 | `PP-OCRv6/rec/PP-OCRv6_rec_medium.onnx` |

说明：
- **det 语言无关**：v5 用 `ch` 检测器（兼检中英拉丁），v6 用 `multi` 检测器；按 version·size 分 5 个 variant。
- **cls 语言/版本无关**：只有 mobile/server 两档，被 rec 与端到端共享（tiny/small 配 mobile cls，medium/server 配 server cls）。
- **rec 分语言**：通用(中英) = v5 ch（mobile/server）+ v6 multi（tiny/small/medium）共 5 档；英文 = v5 en（仅 mobile）1 档。v6 无独立英文（multi 已含英）。
- SHA256 校验值见 `third-party/rapidocr/python/rapidocr/default_models.yaml`，下载脚本据此校验。

## 镜像 base 决策（2026-06-29 已定）

调研结论（容器内依赖树反查）：

1. **onnxtools 的 torch 是 100% 死重**——依赖树里声明 torch 的只有 `torchvision/torchaudio/torchelastic/optree`，
   全是 pytorch base 自带，没有一个在 onnxtools 链路里。onnxtools[inference] 实际只要 `onnxruntime-gpu==1.22.0`
   + `opencv-contrib-python`。
2. **onnxruntime-gpu 1.22 自报 CUDA/cuDNN 依赖**：`[cuda]`→nvidia-cuda-nvrtc/runtime/cufft/curand-cu12，
   `[cudnn]`→nvidia-cudnn-cu12~=9.0。即「pytorch base 白送 nvidia libs + ENTRYPOINT 去 conda 捞 .so」的 hack 不必要。

决定：**两个 backend 共享 `nvidia/cuda:12.8.1-cudnn-runtime-ubuntu22.04`**（CUDA 12.8 + cuDNN 9，匹配 ort 1.22）。
- 系统 CUDA/cuDNN 走标准路径 → 免 `LD_LIBRARY_PATH` hack；删 torch 三件套。
- Ubuntu 22.04 自带 python 3.10（满足 onnxtools `>=3.10` 与 RapidOCR），apt 装 `python3 python3-pip`。
- 体积：onnxtools 18.3GB → **≈3GB**（省 ~15GB）；RapidOCR GPU 变体同 base ≈3GB。

**RapidOCR 官方 Docker 方案佐证**（`third-party/rapidocr/docker/`）：GPU 链路 `Dockerfile.onnxruntime-gpu`
就是 `FROM nvidia/cuda:12.4.1-cudnn-runtime-ubuntu22.04`——与本决策**同一模式**，仅 CUDA 小版本不同。
- CUDA 版本取 **12.8**（非官方的 12.4）：12.4 是 RapidOCR 测试下界，onnxtools 的 ort 1.22 已在 12.8 跑通；
  CUDA 12.x 小版本向后兼容，12.8 是同时满足两者的安全超集，且 onnxtools 不必从已验证的 12.8 回退。
- 照搬官方细节：opencv 用 **`opencv-python-headless`**（容器无 GUI）；系统库补 `libsm6 libxext6 libxrender1`
  + `gcc g++`（pyclipper/shapely C 扩展）；CPU 部署退化为 `onnxruntime`（官方 CPU base 是 `python:3.10-slim-bookworm`）。

**排期**：先做 **onnxtools 瘦身**（前置，验证 nvidia/cuda base + 纯 onnxruntime-gpu 在无 torch 下 CUDAExecutionProvider 仍可用），
再让 **RapidOCR 复用同一 base**。onnxtools 瘦身记为本版 `Changed`，RapidOCR 为 `Added`。

### 前置步骤 · onnxtools-backend 瘦身 ✅ 已实现（2026-06-29）

- `apps/onnxtools-backend/Dockerfile`：`FROM pytorch/pytorch:2.7.1-cuda12.8-cudnn9-devel` → `FROM nvidia/cuda:12.8.1-cudnn-runtime-ubuntu22.04`。
- apt 补 `python3 python3-pip git curl ca-certificates libgl1 libglib2.0-0`；pip 改 `python3 -m pip` 装 fastapi/uvicorn/pydantic/httpx/numpy + `onnxtools[inference] @ git`。
- ENTRYPOINT 去掉 conda 的 `LD_LIBRARY_PATH` glob hack（系统 cuDNN 在标准路径）；改 `python3 -m uvicorn`；保留 fallback CPU 行为。
- **实现偏差**：① 镜像 **6.11GB**（非预估 ≈3GB——nvidia/cuda cudnn-runtime base 本身较大 + opencv 双装，但仍较 18.3GB 降 ~12GB，torch 已彻底删除且 onnxruntime-gpu 未重复拉 nvidia pip wheel）；② 新 base 上 ubuntu 自带 setuptools 59 不支持 PEP 660，src-layout 的 `-e protocol_v2` 会退 legacy 模式把 .pth 指错目录 → 必须把 `pip install --upgrade setuptools>=68` 提到 protocol_v2 安装**之前**。
- 验收已过：镜像 6.11GB；GPU 容器内 rtdetr 真实绑定 `CUDAExecutionProvider`（BFCArena for Cuda 实分配显存）；`/predict` 完整 rtdetr+va 两段回归 200 OK（检测框 + vehicle_type/color 属性，双模型均在 CUDA）。

## 背景

- 协议层早已就绪：`capability_registry.py` 有 `ocr` TaskSpec（`default_geometry=("bbox",)`，protocol_notes
  写明 `attributes.text` 必填 + 可选 `attributes.language`/`.orientation`，协议 v2 §4.1 范例 C）；
  `docs-site/dev/reference/ml-backend-protocol.md` §4.1.7 定义了 OCR result 映射
  （`ocr_text → attributes.text`；`orientation → attributes.orientation`）；mock-v2-backend 有 PaddleOCR 条目。
- 但**没有真实 OCR backend**：现有四个（yolo / gsam2 / sam3 / onnxtools）都不产 OCR。
- v0.19.2 WS1 给 `text`/`language`/`orientation` 加了落点校验，却没有 backend emit 这三类 —— 这条路从未被真实数据走通。

[RapidOCR](https://rapidai.github.io/RapidOCRDocs/latest/model_list/) 正好补这块：ONNXRuntime 引擎、
det（文本检测）+ cls（文本行方向分类）+ rec（文本识别）三段流水线、PP-OCRv4/v5 多语种（中/英/日/韩/40+），
输出文本框 + 文本 + 方向。与平台 `onnxtools-backend` 同 infra（onnx），接入成本可控。

## 目标

新建 `apps/rapidocr-backend/`，自报协议 v2.2 的三个 model（det 原子 / rec 原子 / 端到端 composite，见「能力分解」），
`/predict` 真实跑 RapidOCR，返回 `polygon` 几何 + `attributes.text` / `attributes.orientation` / `attributes.language`，
端到端走通平台 OCR 读路径 + WS1 落点校验。

### WS2 · `/predict` 真实推理 + result 映射

- 接 `BatchPredictRequest{tasks:[...]}`，按 `model_id` 路由到对应能力，调 RapidOCR `__call__(use_det/use_cls/use_rec)` 三开关：
  - **det 原子**（`use_det=True, use_cls=False, use_rec=False`）：每个文本框 → 一个 result：`polygon`（四点）+ `score`，**无 attributes**。
  - **rec 原子**（`use_det=False, use_cls=True, use_rec=True`，输入 crop）：crop → `attributes.text`（**必填**）+ `attributes.orientation`（cls）+ `attributes.language`（按 variant），几何透传输入。
  - **端到端**（`use_det=use_cls=use_rec=True`）：每个文本行 → `polygon` + text + orientation + language + `score`。
  - 置信度 → prediction 一等 `score`（不入 attributes，符合 v0.19.2「score 不是输出属性」决定）。
- 返回 `BatchPredictResponse{results:[...]}`，与其它四 backend 同构（`for t in req.tasks` 顺序循环）。
- `POST /warmup`（协议 §4.4）：按 variant 预热 det/cls/rec 模型进内存池。

### WS3 · 平台读路径核验 + 接入

- 核验平台 OCR 读路径把 `attributes.text/language/orientation` 正确落库（`to_internal_shape` /
  prediction adapter）。协议 reference §4.1.7 已声明映射，但需用真实数据回归（此前只有 mock）。
- dev 接入：`docker-compose.yml` 加 `rapidocr` 服务；注册用 `172.17.0.1:<宿主端口>`（见 reference memo）。
- 文档：`docs-site/dev/ml-backend/` 补 RapidOCR 接入说明；mock-v2-backend OCR 条目可指向真实形态。

### WS4 · 端到端验证 WS1 落点校验

- 建一个启用 OCR 工具 + 配了 `text`/`language`/`orientation` 属性的项目跑 RapidOCR 预标 → 文本/语言/方向落库。
- 故意删掉项目的 language 属性 → 画布出 v0.19.2 WS1 的「采纳后该属性将丢失」警告（**首次真实触发**）。

## 风险

中高（新容器 + 真实推理 + 多档模型管理）：
- ONNX 模型体积/下载：13 个 onnx 文件（det 5 + cls 2 + rec 6），bind-mount 注入不打进镜像；下载脚本据 `default_models.yaml` 的 SHA256 校验。
- GPU 库路径：新 base 走 nvidia/cuda 系统 cuDNN（见「镜像 base 决策」），不再需要 torch libpath hack；缺 GPU 时 ort 自动 fallback CPU。
- `language` 取值：按 rec variant 标（通用→`universal`、英文→`en`），非逐框检测；文档写清语义边界。
- 几何选 polygon：RapidOCR 出四点；项目只启用 bbox 工具时由 WS1 几何兼容警告兜（v0.19.2 已有）。

## 验收

- `rapidocr` backend 注册后模型市场显示三个 model（det=`detection`、rec/e2e=`ocr`），徽标含可批量（吃 v0.19.4 徽标）。
- 端到端对一张含文字图片跑预标 → 文本框 + `attributes.text` 落库可见，方向/语言按声明落库。
- 平台 pipeline 串 `det → rec` 编排跑通：det 出框 → rec 吃 crop 出文本，方向由 rec 内部 cls 校正。
- 项目缺 language 承接位时画布出 WS1 警告（端到端走通前瞻落点）。
- `batchable=true` + `device` 按部署 → 进 v0.19.5 对应队列（GPU→ml / CPU→ml.cpu）。

## 排期与依赖

- 与 v0.19.5 协同（CPU 队列）但无强依赖；可独立接入。
- 是 v0.20.1（属性语义角色）的**前置 producer**——先有真实 OCR 属性输出，语义角色映射才有东西可测。
- 体量大，建议独立 ADR 记「为何选 RapidOCR / 原子(det+rec)+端到端 能力分解、cls 内化 / OCR 几何选 polygon / language 通用(中英)+英文 边界 / 共享 nvidia/cuda 瘦身 base」。

## 不在范围

- `doc_layout`（版面分析）backend：另立（协议已留 TaskSpec，RapidOCR 不含版面）。
- 逐框语言检测（per-line language）：MVP 按 rec 模型语言标；细粒度另议。
