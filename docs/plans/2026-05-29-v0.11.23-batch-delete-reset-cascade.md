# v0.11.23 · 删除/解绑批次时级联重置 task 状态 + 清 AI 预标

> Epic 切片 1/3 · 批次解绑状态修复
> 依赖：无（基于 v0.11.22 已合并的分包统一）· 用户可见：是（删批次行为变化）
> 关联：[v0.11.24 batch_predict 幂等](2026-05-29-v0.11.24-batch-predict-idempotency.md)（根治 AI 重复）· [v0.11.25 删批次 force guard](2026-05-29-v0.11.25-batch-delete-force-guard.md)（长期 UX）
> 背景：[ROADMAP §A 删除批次时 task 状态去向](../../ROADMAP.md)

## 目标

修复「删除批次只解绑、不重置」导致的三类问题（详见 ROADMAP §A）：

1. `review` / `completed` / `rejected` 的 task 解绑后变孤儿——审核半残（只在 reviewer 全局队列可见、批次树不可见）、标注员/非特权用户列表强制 `JOIN TaskBatch`（`tasks.py:194-200`）完全看不到，`rejected` 的 task 无法返工。
2. 任意状态孤儿被重分包时，`_splittable_task_ids`（不按 status 过滤）把 `review/completed/rejected` 塞进新建 `draft` 批次 → 计数污染 + 自动状态推进条件错乱。
3. AI 预标过的 task 残留 `predictions` + `prediction_based` annotation，重分包后再次预标会叠加重复标注（B-33 只修了 `reset_to_draft` 路径，`delete()` 漏）。

**核心思路**：`reset_to_draft`（`batch.py` ~866-980）现有的级联清理，正好等于本版需要的全部语义——非 pending→pending、保留人工标注、删 AI 预标 + 归零物化字段。把这段抽成 helper，让删除路径复用。

## 决策（已与用户确认）

- **重置范围**：**所有非 pending** task 一起 → `pending`（不只 review+）。理由：复用 `reset_to_draft` 零额外代码；顺带清 in_progress 的 task lock / 半途 assignee；人工标注全留，不丢工作量。
- **人工标注**：`source='manual'` 保留；`source='prediction_based'` 软删（`is_active=False`，留审计）。
- **AI 预标**：删 `predictions` / `failed_predictions` / `prediction_metas` / 本批 `batch_predict` async job；`total_predictions` 归零，重算 `total_annotations` / `is_labeled`。

## 任务

### A. 抽取级联清理 helper

文件：`apps/api/app/services/batch.py`

把 `reset_to_draft` 中「重置 task 状态 + 清 lock + 软删 AI annotation + 删 prediction 系列 + 重算物化字段」这一段（当前约 877-964 行，**不含** `batch.status=DRAFT` / `review_feedback` 等批次级字段重置）抽成私有方法：

```python
async def _reset_and_clean_batch_tasks(self, batch_id: uuid.UUID) -> dict[str, int]:
    """把批次内所有非 pending task 重置为 pending，保留人工标注，
    清掉 AI 预标（predictions / prediction_based annotations / 物化字段 / task lock）。
    供 reset_to_draft 与 delete / bulk_delete 复用。
    返回 cascade_counts（含 tasks_reset）。
    必须在 task 仍 batch_id==batch_id 时调用（清理逻辑全靠该子查询定位）。
    """
```

- `reset_to_draft` 改为：调 `_reset_and_clean_batch_tasks(batch_id)` → 再设 `batch.status=DRAFT` / 清 review 字段 → `recalculate_counters`。行为完全不变（回归测试保证）。
- 返回值并入 `cascade_counts`，新增 `tasks_reset` 键（= 原 `affected`），保持 `reset_to_draft` 现有返回 `(batch, affected, cascade_counts)` 不变。

### B. delete() 复用 helper

文件：`apps/api/app/services/batch.py` · `BatchService.delete()`

在「解绑 / 回收到 B-DEFAULT」**之前**插入清理：

```python
# B-DEFAULT 校验之后、置 batch_id 之前
await self._reset_and_clean_batch_tasks(batch_id)
# 然后才是现有的 default 回收 / batch_id=NULL 逻辑
```

- 顺序关键：清理靠 `Task.batch_id == batch_id` 子查询定位，必须先于 `batch_id` 改写。
- 老项目 B-DEFAULT 回收路径同样先清理再回收（回收到 B-DEFAULT 的 task 也应是干净 pending）。

### C. bulk_delete() 复用 helper

文件：`apps/api/app/services/batch.py` · `BatchService.bulk_delete()`（约 1022-1056）

循环内每个 `bid` 在置 `batch_id` 之前先 `await self._reset_and_clean_batch_tasks(bid)`。

### D. 取消关联数据集级联删批次路径

文件：`apps/api/app/services/dataset.py` · `unlink_project`（v0.7.3 会删用户 split 出的 batch）

确认其删批次是否走 `BatchService.delete()`：
- 若走 → 自动获得清理，无需改。
- 若自行 `DELETE TaskBatch` → 需同样先调清理 helper，否则留死角。
> 动手时先确认 unlink 的删批次实现，再决定是否补。

### E. 测试

文件：`apps/api/tests/test_batch_delete_reset.py`（新增）

1. **review/completed/rejected → pending**：建批次、task 置这些状态 + 加 manual annotation + prediction_based annotation + prediction 行，`delete()` 后断言：task.status==pending、manual annotation 仍 active、prediction_based annotation `is_active=False`、predictions 表行被删、`total_predictions==0`、`is_labeled` 按 manual 重算。
2. **AI 预标 pending task**：pending + prediction 行，`delete()` 后 prediction 被清、状态仍 pending。
3. **解绑去向**：新项目 → `batch_id=NULL`；老项目（有 B-DEFAULT）→ 回收到 B-DEFAULT 且为干净 pending。
4. **bulk_delete** 同样清理。
5. **reset_to_draft 回归**：已有行为（若有现成测试）不破；补一条断言 `reset_to_draft` 与 `delete` 清理结果一致。
6. **重分包不再污染**：delete 后 split 重分包，新 draft 批次 `completed_tasks==0` / `review_tasks==0`。

## 风险 / 决策点

- **`completed`（审核已通过）被强制改回 pending 会丢 reviewer 通过结论**——这是「强制改回」的本意，已与用户确认接受（标注本身保留）。
- **抽 helper 不能改变 `reset_to_draft` 现有返回签名 / 行为**，否则 `/batches/{id}/reset` 端点与其测试受影响。
- **unlink 级联路径**（D）是最易漏的死角，动手第一步先核实其删批次实现。
- 本版只堵「删除触发的重复预标」一条路径；`_run_batch` 本身不幂等的根因在 v0.11.24 解决。
