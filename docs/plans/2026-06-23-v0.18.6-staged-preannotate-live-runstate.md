# v0.18.6 — M6 · 运行态实时化（逐阶段进度流 + 卡上徽标 + crop 预览）

> 状态：**待实施 plan**（不开干）。创建于 2026-06-23。
>
> 定位：让「运行态可视化」名副其实。M3 的逐阶段统计只在 job **终态**写进 `result.pipeline_stages`（`tasks.py` 结尾），过程中 `_publish_progress` 的发布点都不带它，前端那条统计实际是**跑完才出**、且渲染成与 StageCard 脱节的扁平文本条。本期把逐阶段统计做成**实时流 + 卡上徽标**，并加 crop 预览帮助排查域偏移。

## 1. 目标 / 非目标

**目标**
1. **逐阶段进度实时推送**：worker 跑批过程中按步长把 per-stage 增量统计推上 WS，前端实时更新（不再等 job 完成）。
2. **统计落到卡上**：每张 StageCard（及源阶段区）显状态徽标（pending/running/done/failed）+ 实时计数（检出/目标/成功/失败），并行兄弟各一条；替换底部脱节的扁平文本条。
3. **crop 预览**：StageCard 可展开看「喂给本阶段分类器的 ROI 缩略图」样例，直观排查 crop 域偏移 / pad 是否合理。

**非目标**
- 不做 chord 并行（留 v0.18.7）；本期仍同步顺序跑，只是把进度**流式上报**。
- 不改编排语义 / 校验。
- crop 域偏移的模型侧调参（letterbox/aspect pad）只作可选 spike，不阻塞。

## 2. 详细设计

### 2.1 worker 逐阶段增量上报

现状：`_run_batch`（`tasks.py:228`）的 `_publish_progress`（`tasks.py:12`，带 `job_meta`）只在开始/结束/失败发 meta；per-stage 统计 `pipeline_stage_totals` 只在终态写 `result.pipeline_stages`（`tasks.py:619`）。

改：
- `_publish_progress` 的 `job_meta` 增可选 `pipeline_stages`（当前累加快照）。
- task 循环里按现有 5% 步长（已有 `pct % 5` 节流逻辑）顺带把 `pipeline_stage_totals` 当前快照塞进一次进度推送（复用现有 WS 通道 `project:{id}:preannotate`，不新增通道）。
- 保持终态仍写 `result.pipeline_stages`（落库真值，前端刷新/重连兜底）。

> 仍是同步顺序执行，只是把已有的累加器**中途也推一份**；无新并发模型，低风险。

### 2.2 前端实时消费 + 卡上徽标

- `usePreannotationProgress`（`hooks/usePreannotation.ts`，已订阅该 WS 通道）解析 `pipeline_stages` 增量 → 暴露给 `ProjectDetailPanel`。
- `ProjectDetailPanel`：把逐阶段统计从底部扁平条**下放到各卡**：
  - 源阶段区（顶部配置）显「检出 N 框」。
  - 每张 StageCard 右上角状态徽标 + 「目标/成功/失败」计数，颜色用语义状态类（`text-status-positive` / `text-status-caution`）。
  - 数据优先用 WS 实时快照，job 完成后回落 `useAsyncJob` 的 `result.pipeline_stages`（已有，作终态真值 + 重连兜底）。
- 徽标状态机：未跑=pending；收到该阶段首个增量=running；job 终态=done/failed。

### 2.3 crop 预览

- StageCard 增「预览 ROI」展开项：取当前项目某张样例 task + 已配源阶段，调一次源检测拿框 → 平台按本卡 `pad` 裁 1–3 个 crop 回显缩略图。
- 实现取最简：复用 v0.18.4 的 `crop_inputs_from_boxes`（presigned）产出 URL，前端 `<img>` 显示；或加一个轻量 `POST .../preview-roi` 端点返回若干 crop URL。
- 价值：用户能直观看到「分类器实际吃的是哪块图」，是排查 crop 域偏移最有效的手段。预览为可选展开，不影响主流程。

## 3. 实施步骤（每步带 verify）

1. worker `_publish_progress` 携带 `pipeline_stages` 增量 + 循环内节流推送 → verify：跑多阶段批，WS 消息中途即出现逐阶段计数且随进度增长。
2. 前端 `usePreannotationProgress` 解析 + `ProjectDetailPanel` 卡上徽标 → verify：跑批时各卡徽标 pending→running→done、计数实时变；并行兄弟各一条。
3. 终态回落 → verify：job 完成后刷新/重连，统计与 `result.pipeline_stages` 一致（不丢）。
4. crop 预览 → verify：StageCard 展开「预览 ROI」显示按当前 pad 裁的缩略图；改 pad 重取可见外扩变化。
5. 前端校验：`pnpm lint`、tsc、`ProjectDetailPanel.test.tsx` 回归 + 徽标渲染测试。
6. 版本收尾：bump 四处 + `uv lock` + openapi 快照（若加 preview-roi 端点则快照变）；重启 worker；`curl /health` 验证 0.18.6。

## 4. 验收标准

- 多阶段批跑**过程中**逐阶段计数实时可见（不再跑完才出）。
- 统计呈现在各 StageCard 上（状态徽标 + 计数），与卡一一对应，并行兄弟各一条。
- job 完成/重连后统计与终态真值一致。
- crop 预览能看到实际投递给下游的 ROI。

## 5. 风险 / 开放问题

- **WS 消息体积**：逐阶段快照随每次进度推送会增大 payload；阶段数有限（单层扇出，个位数）故可接受，仍按 5% 步长节流，不每条推。
- **实时快照与终态真值不一致窗口**：中途快照是累加中的值，终态写库为最终值；前端以「running 用快照、done 用 result」消解，注意切换时点不闪烁。
- **crop 预览额外推理成本**：预览要跑一次源检测；限样例数（1 张 task、1–3 crop）并显式「预览」按钮触发，不自动跑。
