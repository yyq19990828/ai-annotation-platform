# v0.23.32 · 审计月报 BI 物化视图

> Status: complete · 2026-08-14
>
> 触发来源：[ROADMAP「审计 BI 物化视图」](../../ROADMAP.md)
>
> 用户决策：不等待 `audit_logs` 达到约 10M 行，提前完成可上线闭环。

## 1. 现状与结论

本地开发库当前有 35,450 条审计日志，分布在 4 个月分区，子分区总占用约 20 MiB；尚未达到原定
10M 行门槛，也没有 `pg_stat_statements` 慢查询证据。现有能力已经包括：

- `audit_logs` 按 UTC 月份 RANGE 分区；
- action / actor / target / created_at / detail JSONB 索引；
- 超期分区归档到 MinIO，并可按月份回源明细；
- 审计列表、过滤和最多 50,000 行同步导出。

本版仍提前建设月报，但只增加一个 PostgreSQL 日聚合物化视图，并复用现有 Celery beat、审计页面和
Recharts。不开新服务、不引入扩展、不建立通用 BI 平台。

## 2. 版本目标与成功标准

为 super admin 提供可达的 UTC 月度审计概览：

1. 按月查看事件总数、错误事件数、每日趋势、Top action、目标类型和操作人角色分布；
2. 默认只统计业务事件，可切换为包含 `http.*` 的全部事件；
3. 点击 Top action 后复用现有审计列表的 action 精确过滤，完成从汇总到明细的下钻；
4. 历史完整日从物化视图读取，当天从当前月分区实时聚合；
5. 物化刷新延迟或失败时扩大原表补尾范围，结果保持正确，不返回静默缺数的报表。

通过标准：过去月份的月报查询计划不扫描 `audit_logs` 分区；当前月份最多扫描物化视图之后尚未覆盖的
热数据分区；同一筛选下的 BI 汇总与原表基准 SQL 计数一致。

## 3. 明确不做

- 不做自定义报表设计器、任意维度拖拽、跨表 join、定时报表邮件或 PDF；
- 不增加 ClickHouse、TimescaleDB、Cube、Metabase 或新的数据库扩展；
- 不保存 IP、target ID、detail JSON 等高基数或敏感维度的聚合副本；
- 不让项目管理员读取全局 BI；本版只开放给 super admin；
- 不把 MinIO 冷归档重新导入 PostgreSQL。月报覆盖在线保留期，过期明细继续走现有 archive API；
- 不为小数据量调整现有审计列表查询、分页和导出合同；
- 不增加可配置刷新周期或环境变量。

## 4. 数据设计

### 4.1 `mv_audit_bi_daily`

迁移 `0155` 创建日粒度物化视图，数据源只包含已经结束的 UTC 日期：

| 列              | 语义                                                   |
| --------------- | ------------------------------------------------------ |
| `day`           | `(created_at AT TIME ZONE 'UTC')::date`                |
| `action`        | 原始 action                                            |
| `target_type`   | `NULL` 归一为空字符串，保证唯一索引可用于并发刷新      |
| `actor_role`    | `NULL` 归一为空字符串，系统事件显示为“系统/未知”       |
| `status_family` | `0`=未知、`2`/`3`=成功、`4`=客户端错误、`5`=服务端错误 |
| `event_count`   | 该维度组合的事件数                                     |

唯一索引覆盖 `(day, action, target_type, actor_role, status_family)`，满足
`REFRESH MATERIALIZED VIEW CONCURRENTLY`；另加 `(day DESC)` 普通索引服务月范围读取。

视图不映射 ORM model。API 使用 SQLAlchemy `text()` 读取，避免为只读数据库对象增加伪表模型。

### 4.2 完整性与热数据补尾

视图定义排除当前 UTC 日，因此物化行一旦生成就是完整日。API 查询时：

1. 读取物化视图全局 `MAX(day)` 作为 `materialized_through`；
2. 请求月份中不晚于该日期的部分读取物化视图；
3. 其后的日期直接从 `audit_logs` 按同样维度聚合；
4. 两部分合并后再生成 totals、趋势和维度排行。

若视图为空或定时刷新连续失败，原表补尾会自然扩大到整个请求月份：性能会退化，但数字不会缺失。
响应显式返回 `materialized_through`，便于浏览器和运维判断是否处于 fallback。

### 4.3 刷新与归档顺序

- 在现有 `cleanup` 队列增加 `refresh_audit_bi_mv`；
- Celery beat 每日 `00:10 UTC` 执行并发刷新；
- 首次数据由迁移完成普通刷新，后续任务只使用 `CONCURRENTLY`；
- 刷新失败只记录稳定错误类型并返回 `{refreshed: false}`，保留上一份可读视图；
- 归档仍在每月 2 日 `03:00 UTC` 执行。在线保留期外月份不属于 BI 合同，归档后由后续刷新自然移除。

不把 refresh 写成增量表维护：审计日志在在线期内是不可变数据，每日一次全量聚合是更小、更容易回滚的
实现；出现实测刷新窗口不可接受时，再以现有视图结果为基线改为增量汇总表。

## 5. API 合同

新增：

`GET /api/v1/audit-logs/monthly-summary?month=YYYY-MM&business_only=true`

- `month` 必填并严格校验；按 UTC 自然月解释；
- `business_only` 默认 `true`，与列表页现有 scope 一致；
- 仅 `super_admin`；
- 请求早于 `AUDIT_RETENTION_MONTHS` 在线保留窗口的月份返回 `422`，并提示使用 archive 查询；
- 空月份返回完整的零值结构，不返回 `404`。

响应：

| 字段                   | 内容                                               |
| ---------------------- | -------------------------------------------------- |
| `month` / `timezone`   | 请求月份与固定 `UTC`                               |
| `materialized_through` | 物化视图已覆盖的最后完整日，可空                   |
| `totals`               | `event_count`、`error_count`、`action_kind_count`  |
| `daily`                | 月内每天的事件数和错误数，缺失日期补零             |
| `top_actions`          | 按事件数降序，最多 10 项，稳定以 action 次序破同分 |
| `target_types`         | 全量稀疏分布；空 target 显示为系统/未知            |
| `actor_roles`          | 全量稀疏分布；空角色显示为系统/未知                |

`4xx` 和 `5xx` 计入 `error_count`；没有 `status_code` 的业务审计保留在总数中但不算错误。API 不返回
原始 actor、IP、target ID 或 detail 内容。

## 6. 前端闭环

在现有审计页列表上方增加“月度概览”区域：

- 使用原生 `<input type="month">`，默认当前 UTC 月；
- scope 继续复用现有“仅业务事件 / 全部”开关，列表与 BI 同步；
- 展示事件总数、错误数、动作类型数三个 KPI；
- 使用已安装的 Recharts 展示每日事件/错误趋势和 Top action 条形图；
- 目标类型与角色使用紧凑排行，不增加第三、第四张图；
- 点击 action 条形后写入现有 action filter、回到列表第一页并同步 URL；
- BI 请求失败只让概览显示重试态，不阻断审计明细列表。

颜色继续读取 `--sc-*` 语义 token；图表提供文字数值和表格排行，不能只靠颜色表达错误状态。

## 9. 风险、回滚与前提

- **最脆弱前提**：在线审计分区在单库 PostgreSQL 上每日全量聚合仍可在维护窗口内完成。如果真实 10M
  数据刷新不可接受，保留 API/UI 合同，把数据源替换为按日增量汇总表；本版不提前承担该复杂度。
- 物化刷新失败不会阻断写入或明细查询；API 自动扩大原表补尾范围。
- 回滚先撤 UI/API 和 beat，再 `DROP MATERIALIZED VIEW`；不修改 `audit_logs`，没有业务数据迁移或丢失风险。
- 冷归档月份不进入 BI，避免为历史图表重新加载含敏感明细的归档对象。
