# v0.21.7 · 单帧分支批量逐帧预标注（执行单位 epic，最贵）

状态：**细化定稿，动手中（2026-07-03）**。母计划
[`2026-07-03-video-project-orchestration.md`](2026-07-03-video-project-orchestration.md) Phase 4 的独立落地。
依赖 v0.21.5（输入节点 execution_unit）+ v0.21.6（终态输入节点 = 纯数据源 / tracker 编排 / soft 超时护栏）。

## 定稿决策（2026-07-03，用户拍板）

- **执行引擎：二级 Celery fan-out**（硬点 6）。不走单进程逐帧 for 循环；每**段**（frame chunk）拆一个
  Celery 子任务，`chord(group(段子任务), finalize_callback)` 聚合。吞吐 + 断点续跑，代价是要做分布式进度
  合并 + 结果聚合 + 段级失败重试。
- **范围：含全局 UI 一次到位**（硬点 7）。项目侧 execution_unit 选择器 + 全局侧显式 data_type/execution_unit
  选择器同一 epic 落。
- **抽帧：全帧一等**（plan 既定），每任务帧数上限 `FRAME_PREANNOTATE_MAX_FRAMES`（默认 900，对齐 tracker
  cap），采样步长为可选降级项。

## 定稿架构（fan-out）

```
batch_predict (orchestrator, 现有入口)
  └─ 若 execution_unit=frame 且 task 是视频:
       每个视频 task →
         1. 抽全帧 (复用 _extract_video_frames, 落 VideoFrameCache, 幂等)
         2. 按 FRAME_CHUNK_SIZE 切段 → group(predict_video_segment.s(task, [f0..fN], stages, ...))
         3. chord(group, finalize_video_task.s(...))  # 段全绿后聚合该 task 统计 + 收尾
  └─ 否则: 现状单进程主循环 (图像/整段 tracker, 逐字回归)

predict_video_segment (新 worker task, 段级)
  - 对段内每帧: resolve 帧图 URL → 跑 pipeline (复用 _run_task_pipeline, 换 resolve_url)
  - box → video_bbox(frame_index) reshaper → 落库 (分批 commit)
  - 幂等: 跳过该 (task, frame) 已落库的帧 (断点续跑)
  - 段级 cancel 检查 + 段内帧数×框数上限
  - 返回段统计 {frames_done, boxes, failed}

finalize_video_task (chord callback)
  - 汇总段统计 → 该 task 收尾 + 进度推进
```

- **进度**：单进程内 for 循环的 `_publish_progress` 失效 → 改 Redis 计数器（`INCR` 已完成段/帧），
  orchestrator/finalize 读计数推 SSE。
- **地基缺口（探查新发现，plan 原先漏写）**：`execution_unit` 活在 stage 0 的 `source` 里，但
  `projects.py:1695` 的 norm **把整个 `source` 丢弃**——worker 收不到执行单位。**Phase 1 必须先把它
  plumb 进 `batch_predict`（新增顶层参数 `execution_unit`，从 stage-0 `source.execution_unit` 提取）。**

## 实现分阶段

- **Phase 1 · 地基（fork 无关）**：plumb `execution_unit` 到 worker（norm 保留 source / batch_predict 加参
  / API 提取）；`prediction.py` 加 box→`video_bbox(frame_index)` reshaper；settings 加帧上限 / chunk size /

- **Phase 3 · 前端选择器（全局 UI 一次到位）**：项目侧输入节点 execution_unit 选择器（整段序列/逐帧，

- **Phase 4 · 验证 + 文档 + 版本**：E2E（视频项目逐帧检测落 video_bbox、工作台帧号对齐、上限/超时护栏、

## 背景与动机

让**图像 backend（det/seg/分类）在整段视频逐帧跑**：输入节点 `execution_unit=frame` → 整段视频抽全帧
→ 图像 pipeline 逐帧 → 每帧落 `VideoBboxGeometry`。这打破「pipeline per-task 独立执行」，逼出执行单位
`task→frame`（未来还有 scene 聚合），是母计划判为**最贵**的一环。

## 现状断点（探查已定位）

- **执行粒度断点**：`workers/tasks.py:814` 的 `for i, task in enumerate(tasks):` 主循环 +
  `_run_task_pipeline`（`:251`）的 `:289` 单次整媒体 predict（`resolve_url=_resolve_task_url` 把整个
  task 当单一媒体输入）。**Phase 4 要把「task→一次 pipeline」改成「task→逐帧 N 次执行」。**

- **落库 schema 已有**：`VideoBboxGeometry`（`_jsonb_types.py:408`，`frame_index` + x/y/w/h）。

## 硬点清单（实现前须细化）

1. **抽帧策略**：全帧 vs 用户采样步长；整段抽全帧的存储/时间成本（长视频 × fps）。复用
   `_extract_video_frames` 落 `VideoFrameCache`，避免重复抽。
2. **帧寻址**：帧号作 sub-unit——`_run_task_pipeline` 供图从「整段 mp4 URL」改为「逐帧图 URL」
   （抽帧结果的对象存储 URL）；每帧 predict 结果落 `video_bbox(frame_index)`。
3. **落库量**：长视频 × 全帧 × 多框 → 海量 annotation，需**分批提交 + 上限保护**（防单任务撑爆库
   / 内存）。定义每任务帧数上限 + 每帧框数上限。
4. **与工作台导航一致性**：逐帧落库的 `frame_index` 口径须与视频工作台导航网格 / `VideoFrameCache`
   帧号完全对齐，否则审核时框对不上帧。
5. **worker 长任务护栏**：整段逐帧是长任务，需独立 queue / `time_limit`（与 v0.21.6 tracker 同类
   约束）；cancel 检查（`_cancel_requested`）要在帧循环内生效。
6. **fan-out 形态**：当前 `batch_predict` 是**单 worker 进程内 for 循环**（无二级 Celery fan-out）。
   逐帧是否需要二级 fan-out（每帧/每段一个子任务）以利并行 + 断点续跑，待细化定夺。
7. **输入节点显式配置 UI（v0.21.6 遗留，本 epic 补齐）**：终态输入节点是纯数据源、当前**只读**，
   `execution_unit` 尚无用户可选控件——本 epic 要上「整段序列（tracker）/ 逐帧（图像 backend 逐帧检测）」
   选择器，落到输入节点 `source.execution_unit`。两处上下文来源不同、都要改：
   - **项目侧**（`ProjectDetailPanel:205`）：`data_type` 从 `project.data_type` 自动派生（对，视频项目
     天生 video，无需手配）；但 `execution_unit` 当前**写死** `video → "video"`（`:388`，整段序列）。视频
     项目要能选「整段序列 vs 逐帧」，据此切换下游可选 backend（整段序列=tracker 源；逐帧=图像 det/seg 源）。
   - **全局侧**（`GlobalPipelineLibraryPage:158`）：无项目，`data_type` 当前从**选中源模型
     `supported_inputs` 反推**（含 video → 视频）。隐患：① 隐式，未选模型前默认「图像」；② 双输入模型
     （同时含 image+video）会被一律判成视频；③ execution_unit 恒 `整段序列`。本 epic 给全局输入节点加
     **显式 `data_type`（图像/视频）+ `execution_unit`（整段序列/逐帧）选择器**，自顶向下声明模板意图，
     取代反推——用户先声明数据源形态，再据此过滤可选源模型。

## 风险

- **体量最大**：打破执行粒度是架构级改动，牵动 worker 主循环 + 供图 + 落库 + 取消 + 队列。
- **落库爆量**：长视频全帧全框可产十万级 annotation，无上限保护会砸库。
- **一致性**：帧号口径与工作台导航/帧缓存对不齐 → 审核错位。

## 验收（待细化后补全）

- 视频项目输入节点设 `execution_unit=frame` → 整段逐帧跑图像 backend → 每帧落 `VideoBboxGeometry`。
- 工作台按帧导航，每帧框正确对应。
- 长视频有落库上限 + 超时护栏，不砸库/不饿死队列。

## 不在范围

- scene 跨帧聚合源（per-scene 比 per-frame 更贵，独立）。
- track 下游逐帧 crop 分类（frame × track 二维展开）。
- 逐帧检测跨帧连成同一对象（那是 track_id 的活，v0.21.2 已定，不在本 epic）。
