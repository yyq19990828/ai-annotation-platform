# v0.23.0 · API Services 领域化拆解计划草案

> Status: draft · 2026-07-15
>
> 前置条件：先完成 v0.22.4 跨 Backend GPU 显存互斥编排的功能实现、测试和文档收口；不得在其活跃开发期间搬动 `gpu_arbiter.py` 或 `gpu_arbiter_store.py`。

## 1. 背景

`apps/api/app/services/` 当前约 3.7 万行 Python，已有 227 个 API、worker、service 与测试文件直接导入 `app.services.*`。目录内既有领域服务、协议适配、基础设施 helper，也有大量按功能自然成组、但仍平铺在同一层级的模块。

当前主要热点包括：

| 模块或模块族 | 当前规模 | 主要问题 |
|---|---:|---|
| `gpu_arbiter_store.py` | 约 5900 行 | Python facade、Redis key、校验、数据模型和多组 Lua 原子脚本集中在单文件 |
| annotation / task / batch | 多个 1400–1600 行模块 | 业务编排、查询与转换边界较重，但跨模块调用较多 |
| export 模块族 | 多个文件、合计数千行 | packaging、通用导出、视频、点云、DAVIS、缓存已形成自然领域 |
| data manager 模块族 | 多个文件、合计数千行 | cursor、entity、track、filter 已拆分，但仍平铺在 service 根目录 |
| video / tracker 模块族 | 多个文件、合计数千行 | frame、segment、track、job、runner、adapter 形成独立子系统 |

问题不只是单文件过长，而是：

1. service 根目录无法直接表达领域边界，新代码难以判断归属。
2. 高内聚模块族使用平铺命名维持关系，导航和依赖审查成本持续升高。
3. 巨型模块中的协议、原子脚本和 Python orchestration 无法独立测试与审查。
4. 直接全量搬目录又会造成大面积 import churn，并放大循环依赖和合并冲突风险。

## 2. 结论与范围

本期采用**按领域渐进拆解、旧路径兼容、行为零变化**的方式整理 API services，不执行一次性全目录重排。

本期包含：

- 建立 service package 的命名、公开接口和依赖方向约束。
- 优先拆解 GPU arbitration、export、data management、video tracking 四个已经形成自然边界的模块族。
- 保留旧模块导入路径作为薄兼容 facade，先迁移实现，再逐步收敛内部调用方。
- 为每个迁移阶段设置独立回归门，不把多个领域混入同一个不可审查提交。
- 更新开发者文档中的 backend 分层和模块位置说明。

本期明确不做：

- 不修改 API、数据库 schema、Celery task signature、错误码或用户可见行为。
- 不借整理目录重写业务逻辑、SQL、Redis Lua 或状态机。
- 不按文件行数机械拆分所有 service。
- 不强制迁移体量小、职责单一且没有自然模块族的文件。
- 不在本期抽象通用 `BaseService`、repository 基类或统一 ML Backend 基类。
- 不删除第三方或测试仍使用的旧导入路径。

## 3. 设计原则

### 3.1 领域优先

目录按共同状态、不变量和变化原因组织，不按 `utils`、`helpers`、`managers` 等技术词堆放。

首批目标目录：

```text
apps/api/app/services/
├── gpu_arbitration/
├── exporting/
├── data_management/
├── video_tracking/
└── ...现有稳定 service
```

使用 `exporting` 而不是 `export`、使用 `data_management` 而不是 `data_manager`，避免与现有同名模块在迁移期发生包解析歧义。

### 3.2 公开 facade 稳定

每个领域 package 的 `__init__.py` 只导出被领域外部使用的稳定符号。旧文件在迁移期只做显式 re-export，不使用 `import *`，例如：

```python
# app/services/gpu_arbiter_store.py
from app.services.gpu_arbitration.store import GPUArbiterStore
from app.services.gpu_arbitration.types import GPUAllocation

__all__ = ["GPUAllocation", "GPUArbiterStore"]
```

兼容 facade 不得继续承载新实现。新增代码优先导入领域 package 的公开接口；测试只有在验证内部原语时才允许导入内部模块。

### 3.3 依赖方向

允许：

```text
API / workers
  → domain public facade
  → domain orchestration
  → domain primitives / shared infrastructure
```

禁止：

- domain primitive 反向导入 API router、Celery task 或领域 orchestration。
- 两个领域通过彼此的内部模块形成双向导入。
- 为消除循环依赖把业务类型塞入新的通用 `utils.py`。
- 兼容 facade 被领域内部实现反向依赖。

跨领域共享类型只有在确实拥有稳定独立语义时才提升到现有 schema、DB model 或专门的 shared module；单一调用点继续保持局部实现。

### 3.4 每次迁移保持可回滚

每个阶段必须满足：

1. 先记录公开符号和调用方基线。
2. 只移动一个领域，旧路径继续可导入。
3. 业务实现不与结构迁移同时重写。
4. 定向测试与完整 API 测试通过后再进入下一领域。
5. 删除旧 facade 另立后续计划，不在本期强行完成。

## 4. 目标结构草案

### 4.1 GPU Arbitration

在 v0.22.4 完成后，优先拆为：

```text
gpu_arbitration/
├── __init__.py
├── types.py
├── validation.py
├── keys.py
├── store.py
├── coordinator.py
└── scripts/
    ├── admission.py
    ├── lease.py
    ├── queue.py
    ├── transition.py
    ├── reconcile.py
    └── proof_reset.py
```

约束：

- Lua 脚本只按共享原子性边界拆分，不把同一个原子脚本切成多个运行时拼装片段。
- `scripts/` 模块不得导入 Redis client、数据库 session 或应用 settings。
- `store.py` 继续是 Redis 调用 facade；数据库锁、健康证据和 token horizon orchestration 留在 `coordinator.py` 或更明确的同领域 orchestration 模块。
- 原有 `app.services.gpu_arbiter` 与 `app.services.gpu_arbiter_store` 暂保留兼容。

### 4.2 Exporting

```text
exporting/
├── __init__.py
├── service.py
├── packaging.py
├── cache.py
├── video.py
├── lidar.py
└── davis.py
```

先做文件归位和 import 收敛，不统一不同导出格式的数据模型，不改变包内容或文件命名规则。

### 4.3 Data Management

```text
data_management/
├── __init__.py
├── service.py
├── cursor.py
├── entities.py
├── entity_filter.py
└── tracks.py
```

保持现有 SQL、分页 cursor wire 和权限过滤结果完全一致。`task_views` 仍作为独立边界保留，是否并入 data management 需在依赖审查后另行决定。

### 4.4 Video Tracking

```text
video_tracking/
├── __init__.py
├── frames.py
├── segments.py
├── tracks.py
├── adapters.py
├── jobs.py
└── runner.py
```

本阶段只收拢视频追踪子系统。通用 scene、annotation propagation 和 storage 继续由原模块拥有，避免为了目录完整复制逻辑。

### 4.5 暂缓领域

annotation、batch、project、dataset、auth/account、audit/notification 虽有进一步整理空间，但它们当前跨领域调用较多。本期只完成依赖盘点，不把它们列为必须迁移项。

## 5. 实施阶段

### P0 · 基线与护栏

- 生成四个目标领域的公开符号、调用方和测试映射。
- 记录结构迁移前的完整 API 测试结果。
- 明确 package 命名、`__all__` 与兼容 facade 规则。
- 检查是否存在现有循环导入；不得以延迟 import 掩盖新增循环。

验收：形成可核对的迁移清单，且 v0.22.4 工作树与测试已经收口。

### P1 · GPU Arbitration

- 按 types / validation / keys / scripts / store / coordinator 边界拆分。
- 保持 Redis key、Lua 内容、script 参数顺序和公开 dataclass 不变。
- 保留旧导入 facade。

验收：GPU arbiter Redis、shadow、fence、health worker 定向测试通过；完整 API 测试无新增失败。

### P2 · Exporting

- 迁移 export 模块族。
- 保留旧 import facade，并核对 worker 与 API router 调用。
- 比较代表性 image、video、LiDAR、DAVIS 导出产物。

验收：归档结构、文件名、manifest 和内容摘要与迁移前一致。

### P3 · Data Management

- 迁移 cursor、entity、filter、track 和主 service。
- 保持 keyset cursor、权限过滤和查询排序不变。

验收：data manager 定向测试通过；同一输入的分页边界与迁移前一致。

### P4 · Video Tracking

- 迁移 frame、segment、track、adapter、job、runner。
- 保持 Celery task、WebSocket 事件和追踪状态机不变。

验收：视频追踪、传播和 job service 定向测试通过；完整 API 测试无新增失败。

### P5 · 调用方收敛与文档

- 新代码和领域内部调用改用 package 公开接口。
- 旧 facade 继续保留，并标明其兼容用途；本期不安排删除日期。
- 更新 `docs-site/dev/concepts/backend-layers.md` 及实际受影响的领域概念页。
- 检查 `DEV.md` 中的旧路径和开发命令。
- 纯结构重构没有用户影响时不写用户指南；按项目规则确认是否需要 `CHANGELOG.md`。

验收：正式开发文档描述当前目录结构，plan 最终补充 `Outcome`。

## 6. 验证策略

每个阶段至少执行：

1. 旧路径和新路径公开符号 import smoke test。
2. 对应领域定向测试。
3. 完整 API pytest。
4. OpenAPI snapshot diff，确认没有非预期契约变化。
5. `rg` 检查旧符号、旧路径和文档引用；兼容 facade 中的保留引用除外。
6. `git diff --check` 与现有 lint/type check。

测试结束后清理 pytest、coverage、临时导出包和手工对比产物，不处理不属于本次测试的既有缓存。

## 7. 成功标准

- 四个目标领域拥有清晰 package 和最小公开接口。
- `gpu_arbiter_store.py` 不再同时承载数据模型、校验、全部 Lua 与 Redis facade；旧文件仅承担兼容导出。
- export、data manager、video tracking 不再依赖平铺文件名表达领域关系。
- API、Celery task signature、OpenAPI、数据库 schema 和用户行为保持不变。
- 没有新增循环依赖、隐式 `import *` 或新的泛化 `utils.py`。
- 每个阶段都可以独立回滚，不要求一次合并全部领域。

## 8. 待进一步确认

- `gpu_arbiter.py` 的数据库 orchestration 最终命名为 `coordinator.py`，还是按 fence / proof / shadow 继续细分，需要在 v0.22.4 完成后根据实际职责复核。
- `task_views.py` 应保持跨领域查询边界，还是归入 data management，需要先绘制调用图。
- video frame/segment 是否属于通用媒体基础设施而非 video tracking，需要根据非追踪调用方比例决定。
- 旧兼容 facade 的移除版本不在本草案中承诺，待仓内和插件调用全部迁移后另立计划。
