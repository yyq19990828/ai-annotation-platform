# v0.23.0 起 · API Services 领域化迁移 Epic（修订稿）

> Status: v0.23.0 released; GPU orchestration continuation scheduled for v0.23.1 · 2026-07-17
>
> 代码盘点基线：commit `3a80716e`。v0.22.4 已发布，原先“等待 GPU 显存仲裁收口”的进入门已经满足；真正实施前仍须确认目标文件没有并行 hotfix。
>
> 范围决定：四个领域不再绑定为一次发布。v0.23.0 的首个可发布切片只承诺 P0 护栏与 P1 GPU Redis ledger 拆分；后续 GPU orchestration、video tracking、exporting、data management 各自合并、验收、发布和回滚，不能成为前一切片的交付条件。

## 1. 修订结论

本计划采用“领域 package + 旧路径兼容 facade + 仓内调用方同阶段收敛”的迁移方式，但不再把约 3.1 万行目标代码作为一个不可拆的大重构。

执行约束如下：

1. 一个 PR 只处理一个可回滚边界；一个领域可以拆成多个有顺序的 PR。
2. 实现迁移、该领域仓内调用方、兼容测试和正式文档必须在同一领域阶段完成，不拖到最后集中改 import。
3. 旧 facade 在本 Epic 内不删除、不发运行时弃用告警；移除另立计划。
4. 结构迁移不夹带业务逻辑、SQL、Redis Lua、状态机或错误语义重写。
5. 每个阶段必须从“完整测试 0 失败”开始并以“完整测试 0 失败”结束，不接受“没有新增失败”作为验收。

## 3. 目标与非目标

### 3.1 目标

- 建立领域 package 的命名、公开模块、依赖方向与兼容 facade 规则。
- 先把 GPU Redis ledger 从单个 8,870 行文件拆成可独立审查的类型、key、校验、Lua 与 store。
- 后续分别收拢 GPU orchestration、video tracker、export 和 Data Manager 模块族。
- 消除目标范围内依靠局部 import 掩盖的循环依赖与 service → API 反向依赖。
- 让每个切片都能独立发布或回滚，且旧仓内外导入路径继续可用。

### 3.2 明确不做

- 不修改 HTTP / WebSocket API、数据库 schema、Celery task 名称或 signature、队列路由、错误码及用户可见行为。
- 不重写 SQL、Redis key、Lua 语义、Lua 参数顺序、状态机或导出格式。
- 不按行数机械拆分所有 service，也不要求 service 根目录最终为空。
- 不引入 `BaseService`、repository 基类、依赖注入框架或统一 ML Backend 基类。
- 不在本 Epic 迁移 `video_frame_service.py`、`video_segment_service.py`、`video_tracks.py`；它们是共享视频基础设施，不属于 tracker 私有实现。
- 不迁移 annotation、batch、project、dataset、auth/account、audit/notification 等模块族。
- 不承诺兼容第三方对旧模块私有全局、日志模块名、traceback 路径或 monkeypatch 目标的依赖。

## 4. 兼容与依赖规则

### 4.1 “行为零变化”的准确含义

必须冻结：

- API 路径、schema、状态码、错误 body 与 WebSocket channel/event。
- 数据库读写结果、查询排序、cursor wire、事务边界与 Celery task 契约。
- Redis key、hash slot、Lua 最终求值字符串、`KEYS` / `ARGV` 顺序和原子边界。
- 导出成员路径、文件名、静态内容、manifest 语义和缓存 key。
- 旧/新公开函数与类的对象 identity、call signature、枚举值和 dataclass 字段。

允许变化：

- 新实现对象的 `__module__`、traceback 文件路径和 logger 名称。
- 第一方测试对私有函数、私有常量和模块全局的 patch 路径；这些测试必须同步改到新实现模块。
- 发布提交中的版本号；结构迁移阶段 OpenAPI 必须无差异，发版时唯一允许的契约变化是 `info.version`。

### 4.2 公开符号清单

P0 为每个旧模块生成三类清单：

1. 旧 facade 必须兼容的符号。
2. 新 package 对领域外稳定公开的符号。
3. 仅供领域内部或测试使用的私有符号。

清单不能只抄现有 `__all__`。例如 `GPU_EVICTION_OPERATION` 和若干 result dataclass 已被仓内调用，却没有进入 `gpu_arbiter_store.__all__`。盘点必须同时覆盖：

- 普通 import、`from app.services import module` 与模块对象访问。
- `monkeypatch.setattr`、`unittest.mock.patch` 的字符串路径。
- 文档、脚本、worker 冷启动入口和现有 `__all__`。

### 4.3 Facade 规则

- 旧文件只做显式别名 re-export 和 `__all__`，不得使用 `import *`、wrapper、fallback import 或业务逻辑。
- `old_symbol is new_symbol` 必须成立；wrapper 会改变 identity 和签名，不允许。
- 领域内部直接导入同 package 的具体模块，不得反向导入旧 facade。
- package 根 `__init__.py` 保持最小；只有确认不会形成初始化环的稳定符号才可 re-export。GPU package 根不得 eager-import dispatch、membership、rollout control 等高层模块。
- 不用 `sys.modules` 替换模块对象，不用新的局部 import 掩盖循环。

### 4.4 依赖方向

```text
API / workers
  → domain public module
  → domain orchestration
  → domain primitives
  → db models / schemas / shared infrastructure
```

禁止：

- domain 导入 `app.api` 或 `app.workers`。
- primitive 反向导入 orchestration。
- 新领域实现导入自己的旧兼容 facade。
- 两个内部模块依靠局部 import 形成双向依赖。
- 为消除循环而新增泛化 `utils.py`。

### 5.1 P1 · GPU Redis ledger（v0.23.0 发布切片）

| `gpu_arbiter.py` | 下列职责模块；旧文件聚合 re-export |

`gpu_arbiter.py` 不得整体改名成新的巨型 `coordinator.py`，而按现有连续职责拆为：

```text
gpu_arbitration/
├── contracts.py        # dispatch request/grant/error 等 cycle-safe 契约
├── fences.py           # membership/fence DB 事务
```

`ml_client.py` 只能依赖 `contracts.py` / `policy.py` 等不会反向导入它的低层模块；需要 ML HTTP 的 `dispatch.py`、`retirement.py`、membership 与 rollout control 可以依赖 `ml_client.py`，但 package 根不得把两层一起 eager-import。

P2 为全部 7 个旧 sibling 文件保留 facade，不只保留 `gpu_arbiter.py`。

## 6. 实施阶段与进入门

### P0 · 基线、清单与护栏

1. 记录 `git status` 与目标 commit，确认目标文件和拟更新文档没有未归属改动或并行 hotfix；保留并绕开无关的用户改动，不要求清空整个工作树。
2. 预检测试 PostgreSQL / Redis 与 `TEST_DATABASE_URL` / `TEST_REDIS_URL`，跑完整 API pytest，要求 0 失败。
3. 生成目标模块的公开、私有、patch target、调用方与文档引用清单。
4. 冻结 GPU 的 15 个最终 Lua SHA-256、Redis key、method signature、enum/dataclass shape。
5. 新增最小架构测试：禁止新领域 package 导入 `app.api`、`app.workers`、自己的旧 facade，禁止目标 package 新增函数内 service import。
6. 新增参数化兼容测试框架；每个 facade 落地时补 old/new mapping，并在独立冷进程验证旧→新、新→旧两种导入顺序。

验收：完整测试 0 失败；目标调用与 patch 清单可复核；已知环有明确处理或具名 allowlist；P1 不再依赖猜测。

### P1 · GPU ledger

按以下提交边界实施：

1. 抽出 Lua 常量与共享前导；store 暂从新位置导入，最终字符串 SHA-256 不变。
2. 抽出 types、keys、validation；不改字段、默认值、异常文本或校验顺序。
3. 移动 `GPUArbiterStore`，将旧文件收敛为 facade。
4. 同阶段迁移仓内生产调用方与内部测试到新路径；旧路径只允许出现在 facade、兼容测试与历史材料 allowlist。
5. 更新正式开发文档和 `CHANGELOG.md` 的 `Unreleased / Changed`。

验收：15 个 Lua SHA-256、key、`KEYS` / `ARGV`、公开对象 identity 与签名完全一致；GPU 定向测试、冷导入、完整 pytest、OpenAPI check、ruff 与 docs check 全部通过。

P1 完成即可进入 v0.23.0 release gate，不等待 P2–P5。

### P2 · GPU orchestration

先将 `retirement` 的 ML HTTP 探测从低层 proof/fence 中分离，打破 `gpu_arbiter ↔ ml_client`；再按 fences、proofs、reconciliation、policy 的连续职责逐块抽取，最后一对一迁移其余 GPU sibling。每个抽取提交都保留旧 facade 并完成同阶段调用方迁移。

验收：目标模块图无环；`ml_client` 只依赖 cycle-safe GPU 模块；GPU 全套、health worker、dispatch wiring 与完整 pytest 通过。

### P3 · Video tracking

先下沉 task URL helper并消除 service → API 反向依赖，再迁 adapters、jobs、runner。worker、API routes、WebSocket publisher 和测试在同阶段改用新路径。

验收：Celery task 名称/signature、event channel/payload、tracker 状态机与结果序列化不变；video tracker 定向测试和完整 pytest 通过。

### P4 · Exporting

一对一迁移六个模块并同步 worker、API 与测试 import。代表性 image、video、LiDAR、DAVIS 产物按解包后的规范化内容比较；只屏蔽明确的动态时间、presigned URL、expiry 和 ZIP metadata，其他差异均失败。

验收：成员集合与顺序、静态内容摘要、文件名、manifest 语义和 cache key 不变；export 定向测试和完整 pytest 通过。

### P5 · Data management

先抽 schema、task metrics 与 task filter primitives，消除 `data_manager ↔ task_views ↔ entity_filter` 环；再迁 views、service、entities、tracks 和 cursor。Data Manager API 与 Task Views API 调用方在同阶段收敛。

验收：目标模块图无环、无领域内局部 service import；固定 fixture 的任务/对象/轨迹响应、排序、总数、分页边界与 cursor 完全一致；Data Manager + Task Views 定向测试和完整 pytest 通过。

### P6 · Epic 收口

只做全仓 allowlist 检查、总览文档复核与 plan `Outcome`；不得在 P6 再批量修改业务 import。

### 7.3 冷启动与运行态

- 每个 facade 在独立 Python 进程中按旧→新、新→旧顺序 import，并 import 相关 API / worker 入口，避免 `sys.modules` 缓存掩盖问题。
- 结构改动不需要 rebuild 镜像；合并到主工作区后重启受影响的 Celery worker 与 beat，再做 smoke。GPU 影响 control/GPU/default worker，export 影响 export worker，video tracking 影响 GPU worker。
- 不在缺少依赖、数据库或 Redis 的隔离 worktree 强行跑环境测试；代码合并回真实主工作区后统一验证。

### 7.4 中间产物清理

测试前记录既有缓存，测试后只清理由本次命令新建的 `.pytest_cache`、`.coverage`、`htmlcov`、临时导出包、规范化对比目录和 docs build 输出；不得删除用户原有缓存。结束时用 `git status --short` 确认没有测试生成物混入 diff。

## 9. 回滚与停止条件

### 9.1 回滚顺序

- 同一领域先回滚调用方迁移，再回滚新实现；旧 facade 始终保留，因此旧调用方可以立即恢复。
- P2 依赖 P1，回滚 P1 前必须先回滚 P2；P3、P4、P5 彼此不构成发布依赖，可各自回滚。
- 本 Epic 无数据库迁移、API 数据格式迁移或 Redis schema 变更，不需要数据回滚。
- worker 已加载旧模块时必须在代码回滚后重启；不通过 rebuild 掩盖挂载代码未 reload 的问题。

### 9.2 立即停止并拆出新计划的情况

- 需要改变 SQL、Lua 最终字符串、状态机、API、数据库、Celery signature 或用户行为才能完成移动。
- 兼容 facade 无法维持公开对象 identity / signature。
- 新 package 需要新增局部 import、反向依赖或扩大循环 allowlist 才能启动。
- 定向或完整测试不能达到 0 失败，或导出/分页/GPU 冻结契约出现差异。
- 目标文件出现并行 hotfix，当前基线已失效。
