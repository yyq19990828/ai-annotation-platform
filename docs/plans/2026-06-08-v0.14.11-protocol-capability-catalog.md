# v0.14.11 · 协议能力目录（与 backend 注册解耦）

> 规划日期 2026-06-08 · 单线版本。承接 v0.14.9（能力声明协议 v2）+ v0.14.10（模型市场三视图前端重构）。
>
> 本版只解决一件事：把「能力目录」从「已注册 backend 的实例清单」抽离为「协议级能力定义 + 实例填充」双层视图。无 backend 注册时目录仍然可见、可探索，并提供接入引导。

## 1. 背景

v0.14.10 把 `/model-market` 重构为 `?tab=catalog|runtime|registry` 三视图，「能力目录」面板（`CapabilityCatalogPanel`）已经做了卡片/列表、按 backend/task/infra 分组、搜索和排序。但它的数据链路仍然是：

```
adminMlIntegrationsApi.overview()  →  枚举所有项目已注册 backend
        ↓ 对每个 backend
mlBackendsApi.capabilities(projectId, backendId)
        ↓ 后端读 ml_backends.health_meta["capabilities"]
        ↓ services/ml_capabilities.extract_capabilities()
渲染 model 卡
```

即「能力目录」的可见性 100% 取决于「至少有一个 backend 注册并通过 health check」。零接入状态下，`/model-market?tab=catalog` 是一个空表格，没有任何关于"平台到底支持什么能力"的信息。

这与产品语义错位。「能力目录」在用户心智里应该回答 **「平台支持哪些 AI 标注能力？」**，而不是 **「我已经接进来的模型有哪些？」**。后者其实是「已接入模型清单」，归属于 `registry` 或 `runtime` 视图更合理。

协议层面其实已经有静态来源：

- `apps/api/app/services/ml_capabilities.py` L20-58 定义了 `INFRA_VALUES` / `TASK_VALUES` / `GEOMETRY_VALUES` / `_TASK_DEFAULT_GEOMETRY` 等受控词表。
- `docs-site/dev/reference/ml-backend-protocol.md` §4.1 + ADR-0036 是协议文字定义。

但这些静态信息今天只用作「校验入参」和「合成隐式单 model」的内部逻辑，没有作为产品资源对外暴露。

## 2. 目标

### 2.1 目标

- **G1**：新增「协议能力目录」端点 `GET /v1/ml-capabilities/protocol`，无项目作用域、无需 backend 已注册即可访问，返回 task / infra / modality / geometry 四类受控词表的完整列表 + 每条能力的人类可读元数据（label / 简介 / 推荐用途 / 协议要求 / 关联 result 字段）。
- **G2**：把协议能力定义集中到 `apps/api/app/services/capability_registry.py`，作为单一真源（SSOT）；既被现有 `extract_capabilities` / `derive_modalities` 内部消费，也被新端点对外暴露。
- **G3**：`CapabilityCatalogPanel` 改为**双层视图**——
  - 顶层：渲染 9 张 task 协议卡（detection / obb / segmentation / keypoint / classification / ocr / doc_layout / tracker / interactive_seg），无论 backend 是否注册都展示。
  - 卡片内部：把已注册 backend 的 model 按 `task` 字段挂到对应卡下；未挂任何 model 的协议卡显示「暂无接入」徽标 + CTA。
- **G4**：零接入空状态体验做成 onboarding——展示协议能力清单 + 推荐开源 backend 矩阵（Label Studio ML、X-AnyLabeling、Grounded-SAM 2 等，已在 `docs/research/` 调研过的），点击「去注册」直达 `registry` 视图。
- **G5**：保留「按 backend 看」和「按 model 看」的旧视角，不删除现有按 backend 分组能力，但默认视角切换到「按协议能力看」。

### 2.2 非目标

- **NG1**：不引入新的协议字段。task / infra / modality / geometry 受控词表保持 v0.14.9 的边界，不在本版扩展。
- **NG2**：不动 `/setup` / `/predict` 协议，不动 `ml_backends.health_meta` 存储结构。
- **NG3**：不做「协议能力描述的运营后台编辑」。元数据（label / 简介）以代码常量形式维护，配合 i18n；后续若有运营改文案诉求再单独立 ADR。
- **NG4**：不做「按协议能力一键启动 starter backend」。onboarding CTA 只跳转到 `registry` 视图，不内嵌部署能力。
- **NG5**：工作台的模型选择器在本版不动，继续消费 `/projects/{pid}/ml-backends/{bid}/capabilities`。本版只改「目录展示」侧。

## 3. 设计

### 3.1 后端：协议能力注册表

新建 `apps/api/app/services/capability_registry.py`，作为协议层元数据的 SSOT：

```python
# apps/api/app/services/capability_registry.py
"""协议级能力注册表（与 ml backend 注册解耦）.

本模块定义平台对外承诺支持的「能力清单」, 是「模型市场 / 能力目录」的协议层数据源:
- task / infra / modality / geometry 四张受控词表;
- 每条 task 的人类可读元数据 (label / 简介 / 推荐用途 / 协议要求);
- 由 capabilities/protocol API 直接对外暴露, 也被内部 extract_capabilities / 合成隐式单 model 消费。

约束:
- 与 ml_capabilities.py 中的 INFRA_VALUES / TASK_VALUES / GEOMETRY_VALUES 严格对齐 (后者将改为从本模块 re-export);
- 元数据 (label / desc / hints) 是产品文案, 改动不算 breaking change;
- 受控词表本身是协议契约, 任何增删都要走 ADR (本版不动)。
"""

from __future__ import annotations
from dataclasses import dataclass, field
from typing import Literal

TaskId = Literal[
    "detection", "obb", "segmentation", "keypoint", "classification",
    "ocr", "doc_layout", "tracker", "interactive_seg",
]
InfraId = Literal["pytorch", "onnx", "paddle", "tensorrt", "openvino", "other"]
ModalityId = Literal["image", "video", "text", "point_cloud"]
GeometryId = Literal[
    "bbox", "rotated_bbox", "polygon", "polyline", "keypoint",
    "lidar_box_3d", "point_mask_3d", "none",
]

@dataclass(frozen=True)
class TaskSpec:
    id: TaskId
    label: str               # 中文短标签 (UI 主标题)
    summary: str             # 一句话简介 (协议层语义, 不写「平台支持 N 个模型」)
    default_geometry: list[GeometryId]
    default_modalities: list[ModalityId]
    typical_models: list[str]   # 协议示例, 仅文档用途 (不暗示官方支持)
    protocol_notes: str       # 该 task 在协议 v2 下的输出约束 (引用 ml-backend-protocol §4.1)
    suggested_backends: list["SuggestedBackend"] = field(default_factory=list)

@dataclass(frozen=True)
class SuggestedBackend:
    name: str
    repo_url: str
    summary: str
    research_link: str | None   # 指向 docs/research/ 内的本平台调研结论

@dataclass(frozen=True)
class InfraSpec:
    id: InfraId
    label: str
    summary: str

@dataclass(frozen=True)
class ModalitySpec:
    id: ModalityId
    label: str

@dataclass(frozen=True)
class GeometrySpec:
    id: GeometryId
    label: str
    summary: str

TASKS: tuple[TaskSpec, ...] = (
    TaskSpec(
        id="detection",
        label="目标检测",
        summary="在图像或视频帧中输出 bbox + 类别。",
        default_geometry=["bbox"],
        default_modalities=["image", "video"],
        typical_models=["YOLO 系", "DETR 系", "Grounding DINO"],
        protocol_notes="result.type=rectanglelabels, 输出 bbox + class_name; 协议 v2 §4.1 范例 A。",
        suggested_backends=[
            SuggestedBackend(
                name="Label Studio ML Backend (YOLO)",
                repo_url="https://github.com/HumanSignal/label-studio-ml-backend",
                summary="官方示例覆盖 YOLOv8 / DETR, 适合上手。",
                research_link="docs/research/01-label-studio.md",
            ),
            SuggestedBackend(
                name="X-AnyLabeling",
                repo_url="https://github.com/CVHub520/X-AnyLabeling",
                summary="本平台 v0.14.x 重点参考的开源标注端, 自带多种检测模型。",
                research_link="docs/research/04-x-anylabeling.md",
            ),
        ],
    ),
    # ... obb / segmentation / keypoint / classification / ocr / doc_layout / tracker / interactive_seg ...
)

INFRAS: tuple[InfraSpec, ...] = (
    InfraSpec(id="pytorch", label="PyTorch", summary="原生 .pt / TorchScript 部署。"),
    InfraSpec(id="onnx",    label="ONNX",    summary="跨框架推理, 与硬件解耦。"),
    InfraSpec(id="paddle",  label="Paddle",  summary="PaddlePaddle / PaddleOCR / PP-Detection 系。"),
    InfraSpec(id="tensorrt",label="TensorRT",summary="NVIDIA GPU 高性能推理。"),
    InfraSpec(id="openvino",label="OpenVINO",summary="Intel CPU / iGPU / NPU 优化。"),
    InfraSpec(id="other",   label="其他",    summary="协议允许的自定义运行时声明。"),
)

MODALITIES: tuple[ModalitySpec, ...] = (
    ModalitySpec(id="image",       label="图像"),
    ModalitySpec(id="video",       label="视频"),
    ModalitySpec(id="text",        label="文本"),
    ModalitySpec(id="point_cloud", label="点云"),
)

GEOMETRIES: tuple[GeometrySpec, ...] = (
    GeometrySpec(id="bbox",         label="bbox",         summary="2D 轴对齐矩形。"),
    GeometrySpec(id="rotated_bbox", label="rotated bbox", summary="带旋转角度的 2D 矩形 (OBB)。"),
    GeometrySpec(id="polygon",      label="polygon",      summary="2D 多边形 (单环或 multi_polygon)。"),
    GeometrySpec(id="polyline",     label="polyline",     summary="2D 折线。"),
    GeometrySpec(id="keypoint",     label="keypoint",     summary="2D 关键点集合 (含可见性)。"),
    GeometrySpec(id="lidar_box_3d", label="3D box",       summary="3D 立体框, 用于点云标注。"),
    GeometrySpec(id="point_mask_3d",label="point mask 3D",summary="点云逐点 mask。"),
    GeometrySpec(id="none",         label="none",         summary="纯分类等无几何输出。"),
)
```

`ml_capabilities.py` 改为从 `capability_registry` re-export 受控词表，删除原本写死的元组（保留 alias 减少调用方改动）：

```python
# apps/api/app/services/ml_capabilities.py (改动)
from .capability_registry import (
    INFRAS, TASKS, MODALITIES, GEOMETRIES,
)

INFRA_VALUES = tuple(s.id for s in INFRAS)
TASK_VALUES  = tuple(s.id for s in TASKS)
```

### 3.2 前端：双层目录视图

`apps/web/src/pages/ModelMarket/CapabilityCatalogPanel.tsx` 改造点：

1. **新增 hook**：`apps/web/src/api/mlCapabilities.ts` 暴露 `useProtocolCapabilities()`，封装 `GET /v1/ml-capabilities/protocol`，`staleTime: 5 * 60_000`。
2. **默认视图改为「按协议能力（task）看」**：
   - 顶层根据 `protocolCapabilities.tasks` 渲染 9 张 task 卡（无论 backend 是否注册）。
   - 已注册 backend 的 model（来自现有 `useQueries(...)` 拉取链路）按 `model.task` 字段挂载到对应 task 卡下。
   - 顺序：先按 task 卡片排序（`protocolCapabilities.tasks` 原顺序），卡片内的 model 按 backend → name 排序。
3. **空协议卡（暂无接入）**：
   - 显示 `<Badge variant="outline">暂无接入</Badge>` + 协议简介 + `典型模型: YOLO 系 / ...`。
   - 卡片底部 onboarding 区：「推荐 backend」列出 `suggested_backends`（最多 3 个），右侧 CTA 「去注册」跳到 `?tab=registry`。
4. **已接入协议卡**：在卡片标题旁显示「N 个模型已接入」，model 子项内嵌于卡片内 grid，保留 v0.14.10 已经实现的「按 backend / task / infra 分组」作为「可选展开模式」。
5. **保留 v0.14.10 既有筛选**：搜索框、infra chips、modality chips 继续生效，但作用域是「过滤 model 子项」+「过滤可见 task 卡」（含 0 model 的卡，若用户主动搜索/过滤，仍然按协议字段匹配，匹不上则隐藏）。
6. **视图切换**：顶部「分组依据」下拉里把默认值从 `backend` 改为 `task`，但保留 `backend` / `infra` / `model_family` 选项，切换到这些选项时回到 v0.14.10 的「按已接入实例展平」逻辑（即不渲染空协议卡）。
7. **零接入空状态**：当 `overview.backends.length === 0` 且分组为默认 `task` 时，在协议卡上方增加一条横幅「平台支持以下 9 类 AI 标注能力, 当前还没有 backend 接入。」+ 「查看接入指南」+ 「去注册 backend」两个按钮。

## 7. Tradeoffs / 风险

### 7.1 协议元数据放后端 vs 前端常量

**选后端**。理由：

1. 后续 OpenAPI 自动生成 + 第三方 SDK / docs site / starter 都可以直接消费；
2. i18n 文案虽然是 UI 关注点，但 `summary` / `protocol_notes` 本质是协议层语义，前端单独维护容易和协议文档漂移；
3. 后端有现成的 `ml_capabilities.py` SSOT，本版只是把它升级为对外可见，增量小。

**代价**：前端多一次网络调用（已用 5 分钟 staleTime 缓解），且 i18n 需要后端配合（本版只提供中文 label，下一版再补英文 / Vue 现有 i18n 框架接入）。

### 7.2 onboarding 推荐 backend 列表

**选硬编码在 `capability_registry.py`**。理由：本平台已经在 `docs/research/01-04` 调研过这些开源 backend，列表稳定；运营改文案频率低于一个季度一次，不值得引入运营后台编辑。

**代价**：每次更新推荐列表需要发版。可接受。

### 7.3 空态横幅 vs 全屏 onboarding 页

**选横幅 + 协议卡同屏**。理由：用户进入 `/model-market` 时仍然能看到「平台支持什么」的全貌（9 张协议卡），而不是被一个 onboarding 全屏页打断；横幅起引导作用即可。

**代价**：首次进入信息密度略高。在文案 / 视觉层用「灰阶降权 + 暂无接入徽标」区分有/无接入卡片。

### 7.4 风险

- **R1**：`suggested_backends.research_link` 是仓库内 docs 路径，存在 docs 改名后失效的风险。单测 T1.6 已加路径校验，CI 会拦下。
- **R2**：前端 `groupBy` 默认值切换可能让重度用户「以为视图丢了」。在「分组依据」下拉旁加一行小提示「按协议能力（默认）」，并在 0.14.11 CHANGELOG 显式说明。
- **R3**：`/v1/ml-capabilities/protocol` 是无 project 作用域端点，但仍要登录。需确认现有 OpenAPI 中间件不会把它误归类到 admin 路由（写测试覆盖）。
