# v0.23.12 · ML Backend 能力漂移重新验证与接流恢复计划

> Status: Completed · 2026-07-23
>
> 前序架构：[v0.23.3 ML Backend 服务池与真实请求负载均衡地基](2026-07-20-v0.23.3-ml-backend-service-pool-load-balancing-foundation.md) · [v0.23.4 模型市场注册管理与运行时观测](2026-07-20-v0.23.4-model-market-registry-runtime-observability-redesign.md)

## 1. 结论

保留现有 capability fingerprint 漂移时自动 fail closed 的安全语义，同时补齐超级管理员可审计的恢复闭环：

1. 先预览服务池基线与实例当前能力的指纹、字段差异和阻塞成员。
2. 管理员明确确认候选指纹后，平台重新执行真实健康与 `/setup` 探测。
3. 只有探测后的指纹仍等于管理员确认值，且池内现有 active / draining 成员仍与新基线等价时，才接受新基线。
4. 同一数据库事务内更新池 capability snapshot / fingerprint、恢复目标成员为 active、递增 routing generation，并按请求显式重新启用服务池。
5. 记录包含旧指纹、新指纹、差异字段、实例 ID 和启用结果的审计事件。

如果实例已经回滚到原服务池基线，重新验证允许直接恢复 disabled 成员而不改写基线；否则“先漂移、后回滚”仍会永久卡在 disabled。

本修复不把“能力增加”自动视为安全，也不让普通 resume 绕过重新验证。模型协议的输入、输出、参数 schema、batchable 或 tracker 变化都可能改变请求合法性和调度行为，仍需人工确认。

## 2. 现状与根因

`MLBackendService._reconcile_pool_capability()` 在健康刷新发现成员能力指纹与池基线不一致时，会把成员设为 `disabled`；若该成员是 legacy instance，还会关闭服务池。该保护符合服务池成员必须可互换的不变量。

缺口在恢复侧：

- `resume_pool_member()` 明确拒绝 disabled 成员。
- 管理 API 没有能力差异预览或接受新基线操作。
- 健康检查会持续刷新实例快照，但 disabled 状态不会自动更新池基线。
- 管理页面只能看到“接流：已禁用 / 路由：阻塞”，无法理解差异或完成受控恢复。

当前生产数据中 Grounded SAM2 与 SAM3 均因预期的 mask、scribble、视频交互、batchable 和 tracker 能力扩展触发该状态；容器本身健康，GPU claim 也不是本次阻塞原因。

## 3. 目标与非目标

### 3.1 目标

- 超级管理员可读取结构化能力漂移预览。
- 接受动作具备 TOCTOU 防护：请求必须携带管理员看到的候选指纹，提交时重新探活并再次比对。
- 接受动作保持池内可互换不变量，不能让仍在接流或 drain 中的不等价成员继续存在于新基线下。
- 成员恢复、基线切换、routing generation 和可选的 pool enable 原子提交。
- 所有接受动作写审计日志，失败不产生部分状态。
- 模型市场为 disabled 成员提供明确的“审核能力变更”入口和二次确认。
- 当前 Grounded SAM2、SAM3 通过正式 API 恢复，不直接修改数据库。

### 3.2 非目标

- 不自动接受 capability superset。
- 不改变 canonicalization 或 fingerprint 算法。
- 不新增数据库表或迁移；现有 snapshot、fingerprint、traffic state 和 audit log 足够承载本修复。
- 不自动批量升级多成员池，也不替管理员选择要淘汰的不等价副本。
- 不把健康恢复、熔断恢复、GPU 容量恢复与 capability revalidation 合并成一个状态。

## 4. API 合同

### 4.1 漂移预览

`GET /admin/ml-integrations/service-pools/{pool_id}/members/{registry_id}/capability-drift`

仅超级管理员可访问，返回：

- `pool_id`、`registry_id`、`member_state`、`pool_enabled`；
- `pool_fingerprint`、`candidate_fingerprint`；
- `differing_fields`：顶层 canonical 字段名；
- `has_drift`、`can_accept`；
- `blocking_members`：当前 active / draining 且指纹不等于候选值的其他成员 ID。

预览读取最近一次已持久化的健康快照，不触发写操作。成员不属于池或池不存在时返回 404；能力快照缺失时返回 `can_accept=false`，提交接受则返回明确的 409。

### 4.2 接受当前能力

`POST /admin/ml-integrations/service-pools/{pool_id}/members/{registry_id}/capability-drift/accept`

请求体：

```json
{
  "expected_candidate_fingerprint": "64-char-sha256",
  "enable_pool": true
}
```

服务端顺序：

1. 对目标 registry 执行真实健康检查并刷新 `/setup` 能力快照。
2. 锁定 pool、目标 member、registry，并重新计算 canonical snapshot / fingerprint。
3. 若当前指纹不等于 `expected_candidate_fingerprint`，返回 409，要求重新审核。
4. 若目标不是 disabled、能力缺失、实例不健康，或存在与候选指纹不等价的 active / draining 其他成员，返回 409。
5. 写入新的 pool snapshot / fingerprint，把目标 member 置 active。
6. `enable_pool=true` 时，只有 legacy instance 已成为 active 成员才启用 pool。
7. `routing_generation` 只递增一次；整个状态变更随审计记录一起提交。

成功响应沿用 `ServicePoolAdminItem`，便于现有 query invalidation 和页面刷新。

## 5. 后端实现

- 在 capability 模块复用现有 `canonicalize_capability()`、`capability_fingerprint()` 和 `diff_capabilities()`，不复制规范化规则。
- 在 `MLBackendService` 增加只读 preview 与受锁保护的 accept 方法。
- accept 方法校验 pool/member 归属、目标状态、候选指纹、其他 routable member 等价性及 enable 前置条件。
- 管理路由负责 fresh health probe、HTTP 错误映射、事务提交与 `ml_service_pool.capability_drift_accepted` 审计。
- 错误响应使用稳定的 `error_code`，至少覆盖：
  - `ml_backend_capability_snapshot_unavailable`
  - `ml_backend_capability_changed_during_review`
  - `ml_backend_pool_capability_blocked_by_members`
  - `ml_backend_capability_revalidation_failed`
- OpenAPI snapshot 与 Web 生成类型同步更新。

## 6. 管理端交互

- 仅在超级管理员视图、成员 `traffic_state=disabled` 时显示“审核能力变更”。
- 打开对话框时请求 preview，展示旧/新指纹短值、差异字段和阻塞成员。
- `can_accept=false` 时不允许提交，并给出原因。
- 确认文案明确说明：该操作会接受新的路由能力合同、恢复成员接流；服务池当前关闭时，用户可选择同时启用。
- 提交时发送 preview 返回的完整候选指纹；成功后刷新 topology、runtime snapshot、service pools 和 registry 数据。
- 不在前端重算 fingerprint 或能力差异。

## 7. 测试矩阵

### 7.1 API / service

- 无漂移预览返回 `has_drift=false`；disabled 成员已回滚到原基线时允许重新验证并恢复。
- disabled + 漂移返回旧/新指纹和正确 differing fields。
- expected fingerprint 过期时 409，数据库状态不变。
- fresh health 失败时不接受。
- singleton legacy 成员接受后 snapshot / fingerprint 更新、member active、pool enabled、generation 递增一次。
- `enable_pool=false` 时成员恢复但池保持关闭。
- 多成员池存在不等价 active / draining 成员时拒绝。
- disabled 的不等价其他成员不阻止接受，且不会被自动恢复。
- 非超级管理员被拒绝。
- 成功写入完整审计 detail。
- 原有自动漂移 disable 测试继续通过。

### 7.2 Web

- disabled 成员显示审核入口，active / draining 不显示。
- preview 加载、无差异、可接受、阻塞和错误状态均有确定 UI。
- 确认提交携带 preview candidate fingerprint 与 enable 选择。
- 成功 toast + query invalidation；失败保留对话框并展示原因。

## 8. 文档与变更记录

- `CHANGELOG.md` 的 Unreleased / Fixed 记录“健康 ML 后端因能力升级被永久阻塞且无恢复入口”的用户可见症状。
- 用户指南补充能力漂移审核操作，使用当前态表述，不在渲染正文写版本号。
- API 由 OpenAPI snapshot 与生成类型承载，不手工维护重复接口表。
- 本变更不涉及环境变量、依赖、数据库 schema 或 Dockerfile。

## 9. 实施顺序与验收

1. 后端 service + API + 审计 + 单元测试。
2. 生成 OpenAPI / Web API 类型。
3. 管理端 hook、对话框、操作入口与测试。
4. 更新 CHANGELOG 和用户指南。
5. 运行 API 定向测试、Web 定向测试、类型检查、lint、OpenAPI 检查。
6. 通过管理 API 对 Grounded SAM2、SAM3 执行 preview 和 accept，确认：
   - `traffic_state=active`
   - `pool.enabled=true`
   - topology 显示 `routing=routable`
   - `/health` 与 `/setup` 仍为 200
   - 审计日志存在接受事件

验收后不得残留测试数据库行、临时响应文件或调试容器。
