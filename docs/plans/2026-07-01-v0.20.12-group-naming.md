# v0.20.12 · group 正名（用户组 `groups` → `user_groups`，消解与标注编组的命名冲突）

状态：草案（draft）。四问探讨 Q3 的命名消解部分。纯重构（rename），无功能变化。

## 背景

平台里两个完全不同的东西都叫「group」：
- **标注编组**：`annotation.group_id`（BigInteger，per-task 序号，Ctrl+G 把多个框绑成一组，平等成员）。
- **用户组织**：`Group` 表 / `groups` 表（UUID，把用户分到一个组织标签下）。

最实在的混淆源：**`User.group_id`（UUID，用户组）与 `annotation.group_id`（BigInt，标注组）两个
同名字段**——读代码 grep `group_id` 时无法一眼区分。

## 决策：改「用户组」侧，不动「标注编组」侧

- 标注侧 "group" 是**绘图/标注领域约定俗成**（CVAT 也叫 group）、`/annotations/group` API 已用、
  I12 特性——**不改**。
- 用户组本就该叫 `user_group`——**改它**。

## 现状（已核实，引用面小）

- `Group`（`group.py:13`，`__tablename__="groups"`，UUID 主键，name/description）是**松散用户分组
  标签，非 RBAC 核心**——角色权限走 `User.role`（SUPER_ADMIN/…/VIEWER），与 `groups` 无关。
- 关联**仅**：`User.group_id` UUID FK → `groups.id`（`user.py:22`，`ondelete=SET NULL`）+
  `User.group_name` 冗余缓存（`user.py:21`）。**无多对多表、无 group↔project/role/permission**。
- 后端引用 **<10 处**、前端 **0-1 处**（详见工作项）；无 ORM 之外的裸 SQL（除历史迁移）。风险🟢低。

## 工作项

### WS1 · 表 rename（新建迁移，不改历史迁移）

- **新建** alembic 迁移：`op.rename_table("groups", "user_groups")` +
  `op.execute('ALTER INDEX ix_groups_name RENAME TO ix_user_groups_name')`。
- **不改历史迁移 `0006_groups.py`**（已应用的迁移不回改）。Postgres `RENAME TABLE` 自动保留数据 +
  `User.group_id` 的 FK 约束（FK 跟表走，不需重建）。

### WS2 · 模型 + schema

- `group.py`：`__tablename__ = "user_groups"`；类名 `Group` → `UserGroup`。
- `schemas/group.py`：`GroupOut`/`GroupCreate`/`GroupUpdate` → `UserGroupOut`/…（`schemas/group.py` 文件
  可改名 `user_group.py`）。
- `db/models/__init__.py:2,49`：导入 + 导出改名。

### WS3 · API

- `api/v1/groups.py`（文件可改名 `user_groups.py`）：`from ... import Group` → `UserGroup`，端点内引用改名。
- `api/v1/users.py:735-778`：分配用户组端点的 `Group` 引用改名。
- **路由前缀 `/groups` 建议保留**（`router.py:90`）：`/groups` 与 `/annotations/group` 不同路径、
  不构成路由冲突，保留可**不 break 对外 API 契约**；命名冲突的根在数据库/代码层的裸 `Group`/表名，
  已由 WS1/WS2 解决。**改成 `/user-groups` 列为可选**（完整一致但破坏前端 + 外部调用，需级联改
  `api/groups.ts`）。

### WS4 · 前端

- `api/groups.ts`、`hooks/useGroups.ts`、`hooks/useUsers.ts`（`useAssignUserGroup`）、
  `components/users/EditUserModal.tsx`：类型 / 函数名随 OpenAPI 再生对齐（`GroupOut` → `UserGroupOut`）。
  若 WS3 保留 `/groups` 前缀，前端 API path 不用改，仅类型名跟随再生。

### WS5 · 可选加强：`User.group_id` → `user_group_id`

- 把 `User.group_id`/`group_name` 改成 `user_group_id`/`user_group_name`，**彻底消除两个 `group_id`
  字段撞名**（本 plan 的最实在痛点）。引用面比表名稍大（用户导出 `users.py:204`、审计
  `users.py:760`、前端用户编辑），列为**可选加强**——若做，命名冲突才算根除。

## 风险

- rename table 迁移要覆盖 index 改名；历史迁移 `0006` 不动（改它会破坏迁移链）。
- 是否改 `/groups` 路由前缀是唯一的对外破坏面决策点——默认保留。
- WS5 若不做，代码里 `Group` 类/表名虽已消歧，但 `User.group_id` 仍与 `annotation.group_id` 同名。

## 验收

- 数据库无裸 `groups` 表指用户组；grep `class Group\b` 无用户组残留。
- 用户组功能（列表/创建/分配/删除）行为不变（纯 rename）。
- （若做 WS5）grep `group_id` 能一眼区分 `user_group_id`（用户组）与 `annotation.group_id`（标注组）。

## 依赖 / 不在范围

- 独立，无前置依赖。
- **不含**跨帧对象 id 统一（`group_id` 链 → `track_id`）——那是含数据迁移的大重构，见
  `crossframe-object-id-unification`（另立项）。
