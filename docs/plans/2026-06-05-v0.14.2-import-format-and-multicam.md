## 1. 背景与目标

### 1.1 v0.14.0 / 0.14.1 之后导入侧仍存在的硬卡点

v0.14.0 立了 scene 地基,v0.14.1 让 `Shift+→` 能用。但**进数据这一头**还有两个直接阻塞:

- **D1 — ZIP 上传拍平路径**:`apps/api/app/api/v1/datasets.py` 的 `upload_zip` 把每个文件写到 `{ds.name}/{basename}`(`os.path.basename(name)`,~L452),丢掉 ZIP 内子目录。后果:点云 scene ZIP(必含 `lidar/ camera/<cam>/ calib/camera/` 三级)上传后,`pointcloud_import.group_frames` 找不到任何段名 → 整批不被识别为 scene,任务建不出来。**目前唯一能进库的路径是 `seed_pointcloud.py` 脚本直连 MinIO**,wizard 在点云场景下事实失能。
- **D2 — 多相机 + 多 scene 真实数据从未实测**:现网唯一夹具是 SUSTechPOINTS demo,3 相机 / 单 scene / 8 帧。研究里反复点名的 nuScenes(6 相机 / 一 dataset 10 scene / 每 scene ~40 帧)、KITTI(2 相机 / drive 拆分)从来没在本平台跑通过 → manifest payload 体积、三视图组件 6 路渲染压力、`axis_convention` 在真实数据上的嗅探效果、**v0.14.0 多 scene 启发式在真实数据上的命中率**,全是未知。

### 1.2 调研结论(简版,详见上一轮 Explore 报告)

| 平台 | 导入格式策略 | 给我们的启示 |
|---|---|---|
| **SUSTechPOINTS** | 固定目录 + `tools/trans_kitti_labels.py` 这类**一次性转换脚本** | 主流做法,工作量小,可控。我们应该照抄。 |
| **xtreme1** | 上传端严格校验自家结构,**不做格式适配**;角色 pattern 命名(`lidar_point_cloud_\d`、`camera_image_\d`) | 角色 pattern 是好东西,但属于上传向导抽象层,不在本期 scope。 |
| **CVAT** | `@importer` 装饰器注册 + Datumaro 后端,**但不存标定 → 不做投影** | 注册表抽象在 2 种格式时是过度设计;且 CVAT 弃标定的代价过高,不学。 |
| **三家共同空白** | **没有一家原生支持 nuScenes / Waymo**,KITTI 也只有 SUSTech / CVAT 有 | "用 UI 导入任意格式"是伪需求,真用户都先离线转。 |

→ 这一版按主流做法:**修 D1(让自家格式真能上传) + 写 nuScenes-mini 转换脚本(实测 D2)**,不做注册表/通用 importer。**关键不同于原 v0.13.13**:nuScenes 脚本现在**显式调 v0.14.0 的 `scene_svc.create_scene` + `assign_items_to_scene`**,scene_token 1:1 落到 `scenes.name`,frame_index 按 sample 顺序赋值——不再绕过 scene 模型,也不再依赖文件名启发式。

### 1.3 不在本版本

- 注册表式 importer 抽象(`@importer(name, ext)` 装饰器,留更后等格式数 ≥ 3 再说)
- xtreme1 角色 pattern 多 lidar / 多 camera bundle(本期 group_frames 路径段名硬编码不动)
- Waymo / Argoverse 适配(`TFRecord` 解包重度依赖,留更后)
- 标定增强:畸变系数(D 矩阵)、`ego_pose` 时序聚合(留 v0.15+)
- 异步多相机 timestamp 对齐(nuScenes ~50ms 偏差,本版本按 `sample` 同步,标记 `timestamp_delta_us` 到 metadata 但不补偿;真补偿留 v0.15+)
- ZIP 上传单文件 / 整包体积上限调整(沿用现有 100MB / 200MB,nuScenes-mini 单 scene 约 80MB,够用)
- `pointcloud_import.group_frames` 路径段名抽象化(把 `lidar/camera/calib` 三个 magic word 改成可配置 pattern)

### 1.4 成功判据

1. **D1 修复**:在浏览器 wizard 把 SUSTechPOINTS example ZIP(`third-party/SUSTechPOINTS/data/example/` zip 起来)选成"3D 点云"类型上传 → 后端 storage key 形如 `<ds>/lidar/<frame>.pcd`(子目录保留)→ `attach_calibration` + `build_pointcloud_tasks_for_link` 自动跑 → 任务列表出现按帧建好的 task,标定写进每帧相机 item 的 `metadata.calibration`。**v0.14.0 single-mode inference hook 自动跑**,产生 1 个 scene、8 个 lidar item 的 `frame_index = 0..7`。整个流程**不需要任何手工 SQL / MinIO 操作**。
2. **D2 单 scene 端到端**:`uv run python scripts/import_nuscenes_scene.py --scene-token <X>` → 出来 6 相机 + 1 lidar 的 platform 目录结构 → **脚本直接调 v0.14.0 scene service**:`create_scene(name=<scene_token>, source_format="nuscenes", source_metadata={scene_token, duration_s, frame_count})` + `assign_items_to_scene` → 浏览器打开第 1 帧 task,6 路相机投影框正确叠加(肉眼判定:车辆、行人在所有 6 视图里都对齐 ±5px),BEV 鸟瞰图车头朝上(因为 nuScenes 本身就是 ISO 系,`axis_convention=iso_8855`)。
3. **D2 多 scene 单 dataset 端到端**:`uv run python scripts/import_nuscenes_scene.py --scene-tokens scene-0061,scene-0103,scene-0553 --dataset-name nu-mini-multi` → **一个 dataset 装三个 scene**(三个 scene_token 各自一行,`scenes.dataset_id` 都指向同一 dataset)→ `GET /scenes?dataset_id=<id>` 返回 3 个 scene → 任一 scene 末帧的 `GET /tasks/{id}/neighbors` 的 `next` 为空(不串到下一 scene 首帧)→ 这条**直接验证 v0.14.0 § 1.4 判据 6 "跨 scene 不串"在真实数据上成立**。
4. **嗅探在真实数据可用**:对 nuScenes scene 跑 `/datasets/{id}/sniff-axis-convention`(v0.13.12 上线的端点)→ 返回 `iso_8855` 且相似度 ≥ 0.95;对 SUSTechPOINTS scene 仍返回 `sustechpoints_demo` 且 ≥ 0.9。
5. **(可选,依赖 v0.14.1)跨帧 UX 在真实多 scene 数据上不崩**:打开 nuScenes scene-0061 第 5 帧 → `Shift+→` 跳到第 6 帧 → 选中某车 → 再 `Shift+→` 直到 scene 末帧 → 再按 `Shift+→` 应该**无操作 + UI 提示"已是该 scene 最后一帧"**,**不能**误跳到 scene-0103 第 1 帧。
6. **CHANGELOG**:v0.14.2 段写明 D1 fix + nuScenes-mini importer + 多 scene 验证结论(发现的问题归入 v0.14.x+ 或 v0.15+)。
7. **docs**:`docs-site/user-guide/datasets/import-formats.md` 新建,枚举平台原生目录约定 + 列出三种数据源对应的"如何转换"说明 + **明确说"一个 dataset 可含多 scene,scene 边界由 importer 决定"**(链回 v0.14.0 scene 概念文档)。
8. `pnpm lint` / `pnpm test` / `uv run pytest -q` 全绿。

## 3. 各模块设计要点

### 3.1 ZIP 上传保留子目录(D1)

**核心改动一行**(`datasets.py` ~L452):
```python
# 旧:
storage_key = f"{ds.name}/{final_name}"  # final_name = os.path.basename(name)
# 新:
safe_relpath = _normalize_zip_relpath(name)  # 见下
if safe_relpath is None:
    skipped.append(name); continue
storage_key = f"{ds.name}/{safe_relpath}"
```

**`_normalize_zip_relpath`** 必须做的事(都在 datasets.py 内,不拆 util):
- 拒绝绝对路径(`name.startswith("/")`)
- 拒绝 `..` 段(`Path(name).parts` 含 `..`)→ 防 zip-slip
- 仍保留现有 `__MACOSX/` + 隐藏文件过滤(原 L416 那段移到这里)
- 返回规范化的 forward-slash 相对路径

**同名/同 hash 去重**:目前的去重键是 `file_name`(纯 basename)+ `content_hash`。改完后同一相对路径下的文件天然不会撞名,但**跨相对路径同名仍可能撞 `file_name` 列**(如同一 scene 里 `camera/front/000970.jpg` 与 `camera/left/000970.jpg` `file_name` 字段都是 `000970.jpg`)。**选**:**仅当 content_hash 相同时去重,file_name 撞不去重**(让 DB 接受同名),改动小,符合点云 scene 同帧号跨相机的真实情况。

**与 v0.14.0 inference hook 联动**:`upload_zip` 末尾在 v0.14.0 已经加了"该 dataset 没 scene → 跑 `scene_inference.infer_and_apply`"。本期改完路径保留后,该 hook 自动用 `per_subdirectory` 模式(v0.14.0 实现):
- 若 ZIP 顶层是已知角色名(`lidar/` / `camera/` / `calib/` / `image/` / `video/`)→ 判为单 scene,scene.name 取 dataset.name
- 若 ZIP 顶层是若干"子目录名"(如 `scene_a/` `scene_b/` 各含自己的 `lidar/` `camera/`)→ 多 scene,每子目录一 scene

(检测算法详见 v0.14.0 plan §3.3,本期是消费方,不重新设计。)

**安全网测试**(`test_datasets_upload_zip.py`):
- 上传带 `../etc/passwd` 的恶意 ZIP → 该 entry 被拒,其它正常入库
- 上传 SUSTechPOINTS example zip → storage key 都带子目录 → `group_frames` 正确分组 → `build_pointcloud_tasks_for_link` 建出 8 帧 task → **自动产生 1 个 scene、items frame_index 0..7**
- 上传"伪多 scene zip"(顶层两个子目录各含 `lidar/ camera/ calib/`)→ 自动产生 2 个 scene,每 scene 内 frame_index 独立 0..N
- dataset.data_type 非 lidar 时,上传带子目录的 zip → 仍保留子目录(D1 修复是全局的,不只点云场景)

### 3.2 nuScenes-mini 转换脚本(D2)

**文件**:`apps/api/scripts/import_nuscenes_scene.py`,自包含 ~350 行,**只依赖 numpy + Pillow**(都已是项目依赖)。**不依赖 `nuscenes-devkit`**——nuScenes JSON schema 简单,自己读 6 个 JSON 文件足够,不引入新的重依赖。

**位置说明**:放在 `apps/api/scripts/` 而非顶层 `scripts/`,与 `seed_pointcloud.py` 同目录,沿用其 PYTHONPATH 约定(`cd apps/api && uv run python scripts/...`)。

**输入**:
```bash
# 单 scene
cd apps/api
uv run python scripts/import_nuscenes_scene.py \
  --nuscenes-root /data/nuscenes-mini \
  --scene-tokens scene-0061 \
  --dataset-name nu-scene-0061

# 多 scene 共用 dataset(验证 v0.14.0 多 scene 隔离)
uv run python scripts/import_nuscenes_scene.py \
  --nuscenes-root /data/nuscenes-mini \
  --scene-tokens scene-0061,scene-0103,scene-0553 \
  --dataset-name nu-mini-multi
```

**做的事**(单 scene 流程,多 scene 重复 N 次):
1. 读 `v1.0-mini/scene.json` 找到该 scene_token 的 `first_sample_token` → 链遍 `sample.json` 拿到该 scene 的全部 sample token(典型 ~40 个)
2. 对每个 sample:
   - 读 `sample_data.json` 找到该 sample 的 `LIDAR_TOP` `.pcd.bin` + 6 个相机 jpg
   - 读 `calibrated_sensor.json` + `ego_pose.json` 算出 lidar→camera 4×4 外参(`R_camera_from_lidar`, `t`),拍成 16-float row-major
   - 读 `calibrated_sensor.json` 拿相机内参 K(3×3,9-float)
3. `.pcd.bin`(每点 5×float32: x y z intensity ring)→ ASCII PCD(只留 x y z),上传到 MinIO `<dataset_name>/<scene_token>/lidar/<frame_idx>.pcd`(`frame_idx` 用 6 位零填充)
4. 6 路相机 jpg 直接 copy 到 MinIO `<dataset_name>/<scene_token>/camera/<CAM_FRONT|...>/<frame_idx>.jpg`(不改尺寸)
5. 每相机一份 calib:`<dataset_name>/<scene_token>/calib/camera/<CAM_FRONT|...>.json` = `{extrinsic: [16], intrinsic: [9]}`(用第 1 帧的标定;nuScenes 标定 per-sample 微变但变化幅度 < 像素级,本版接受这个近似;真补偿留 v0.15+,在 metadata 里记 `timestamp_delta_us` 备查)
6. **关键 v0.14.0 联动**(原 v0.13.13 这步是"直接 ingest 完事",现在改成):
   ```python
   # 创 / 复用 dataset(metadata.axis_convention = iso_8855)
   ds = await ensure_dataset(db, display_id=f"DS-NU-{dataset_name}", ...)
   # 入 dataset_items(走 storage_service + DatasetItem 直接 add)
   await ingest_files(db, ds, scene_dir_layout)
   # 对每个 scene_token,显式建 scene + 关联 items
   scene = await scene_svc.create_scene(
       db, dataset_id=ds.id, name=scene_token,
       source_format="nuscenes",
       source_metadata={
           "scene_token": scene_token,
           "first_sample_token": ...,
           "duration_s": last_pts - first_pts,
           "frame_count": n,
           "nuscenes_version": "v1.0-mini",
       },
   )
   # 把这 N 个 sample 的 lidar + 6 cam items 按 frame_index 0..N-1 分配
   await scene_svc.assign_items_to_scene(
       db, scene_id=scene.id,
       items_in_order=lidar_items_sorted,
       shared_frame_items={cam_item.id: frame_idx for cam in 6 cams},
   )
   # calib items 仅写 scene_id(frame_index=NULL)— assign 方法的既有行为
   # 调用 build_pointcloud_tasks_for_link 建 task(它会自动跳过 inference hook,因为已有 scene)
   ```
7. 入库时 dataset `metadata_={"axis_convention": "iso_8855"}`(nuScenes 原生 ISO,**不需要旋转**)

**幂等**:固定 `display_id` 由参数派生(`DS-NU-{dataset_name}`)。逻辑:
- dataset 已存在 → 复用,跳过 dataset 创建
- 该 dataset 下指定 scene_token 已有 `scenes.name == scene_token` → 跳过该 scene
- 但仍然检查 items 是否齐全(防止半途崩了再跑)

**手动测试 checklist**(写进脚本 docstring,不进 pytest):
1. 跑脚本 → stdout 报告 `scenes=N, frames_per_scene=[...], total_items=M`
2. 浏览器开 scene-0061 第 1 帧 task → BEV 视图车头朝上
3. 选任一物体 → 6 个相机视图投影框都对齐(±5px)
4. `curl -X GET /api/v1/scenes?dataset_id=<id>` 返回 N 个 scene,scene_token 与 nuScenes 一致
5. `curl -X GET /api/v1/tasks/<scene-0061 末帧 task_id>/neighbors` → `next` 为空,**不串到 scene-0103**
6. `curl -X GET /api/v1/datasets/<id>/sniff-axis-convention` → `iso_8855` confidence ≥ 0.95
7. (若 v0.14.1 已上)主视图打开 scene-0061 第 5 帧,选某车,按 `Shift+→` 数次直到末帧,再按一次 → UI 提示不跳

**潜在阻塞 / 备选方案**:nuScenes mini 体积 ~4GB,作者可能本地没有。脚本第一行写清楚下载地址(`https://www.nuscenes.org/nuscenes#download`,选 mini split);也接受用 `--nuscenes-root=...` 指向已下载位置。若实在拿不到,fallback 是手工把 SUSTech 例的 `camera/front.json` 复制成 6 份(改 extrinsic 让光轴朝 6 个不同方向),走"伪 6 相机"路径——但这会损失"真实数据"的验证价值,只在万不得已用。

**`test_import_nuscenes_lite.py`** 不依赖真数据:把 nuScenes JSON schema 缩成最小 fixture(2 scene、每 scene 3 sample、1 cam),`tmp_path` 里造一份伪 nuScenes 根目录(JSON + tiny `.pcd.bin` + 1x1 jpg)。断言:
- 脚本能完整跑通(从 fixture 到 DB 落地)
- DB 里产生 2 个 `scenes` 行、items 的 `scene_id` 正确指向、`frame_index` 按 sample 顺序赋值
- 跨 scene neighbors 不串

### 3.3 docs:`import-formats.md`(对外口径)

**结构**(全文 ≤ 350 行):
1. **平台原生目录约定**:列出 `<ds>/lidar/`、`<ds>/camera/<cam>/`、`<ds>/calib/camera/<cam>.json` 三段约定 + **顶层多子目录 = 多 scene 的约定**(链 v0.14.0 inference 文档),每段一个真实例子
2. **上传方式**:wizard ZIP 上传(打包时必须保留三级子目录;**默认一个 ZIP = 一个 scene,除非顶层有多个非角色子目录**);命令行脚本上传(指到 `apps/api/scripts/seed_pointcloud.py` 作为范例)
3. **scene 模型基础**:30 行简介 + 链到 `docs-site/dev/concepts/scene-and-frame-index.md`(v0.14.0 文档)。要点:"上传完每个 dataset 自动有 scene;一个 dataset 可装多 scene;scene 内 frame_index 决定跨帧导航顺序"
4. **标定 JSON schema**:贴 `SensorCalibration` 三字段 + 一个 SUSTech `front.json` 实例
5. **来自其他数据集**:三个子标题
   - **SUSTechPOINTS / xtreme1 自家格式**:直接传(目录已经符合;一个 ZIP 默认单 scene)

## 5. 已知风险 / 未尽事项 → 后续 plan

- **多 lidar 数据集**:Waymo 有 5 路 lidar,nuScenes 单 lidar 不暴露这个问题。本版不处理 → 留 v0.15+。
- **同 sample 不同相机微秒级 timestamp 偏差**:nuScenes 标 6 相机非严格同步(~50ms 间隔),快速移动物体在不同相机的投影会有几像素偏差。脚本里把 `timestamp_delta_us` 写进 calib 旁路 metadata 但前端不消费 → v0.15+ 用 `ego_pose` 插值补偿。
- **`group_frames` 仍是固定路径段名匹配**:`lidar/` / `camera/` / `calib/` 三个 magic word 是英文小写硬编码。若未来要接 xtreme1 SCENE 包(用 `lidar_point_cloud_0` 等)→ 留更后引入"角色 pattern 配置"。
- **导出反向**:v0.13.12 已为 `axis_convention` 加了导出反向映射;对 nuScenes 这种已是 ISO 的数据,导出不需要反向——验证逻辑在 `--axis-frame=source` 默认走 identity,无新工作。
- **ZIP 单包 200MB 上限**:nuScenes mini 单 scene 已接近(~80MB pcd + 6 路 jpg 几十张);若要 batch 多 scene zip 上传,需要多次上传或放宽限制。**本版不放宽**,提示用户多 scene 走转换脚本而非 wizard。
- **多 scene 启发式真实命中率**:本期 nuScenes 脚本走"显式建 scene"路径(scene_token 1:1),不依赖 v0.14.0 `per_subdirectory` 启发式;但 D1 端的 ZIP 上传**会**触发该启发式。如果用户上传的伪多 scene zip 顶层目录名碰巧叫 `lidar`(角色冲突),启发式会误判为单 scene。本版 docs 里明确"不要用 `lidar/camera/calib/image/video` 作为顶层 scene 目录名";v0.14.0 plan §5.6 已经预告过这个边界。
