> **实际落地范围(2026-05-19)**:D2 笔画 timeline ✅ / D4 任务级 feedback patch/delete UI ✅。
>
> **scope 调整记录**:开工时重估 D1(ADR-0027 切单源)发现旧三表(bug_reports / annotation_comments / tasks.reject_reason)各自带独立 state machine + 子资源 + 前端 UI(BugReportDrawer 等), 不是单纯的"删 mirror 写路径"就能切, 需要独立 epic 处理 legacy 表退役。D3(DiscussionPanel 拆分)与 D5(video pin)为结构性 / stretch 工作, 无 UX 增量, 一并延期。**v0.10.21 收紧到 D2 + D4 两项可立即落地的 UX 完善**。

## Context — 与 v0.10.20 的衔接

v0.10.20 把 v0.10.19 epic 留的 5 项 UI deferred 闭合,同时把 ADR-0027 推到第二段(view + 双写)。第三段(切单源)是 ADR 决策中"删旧表写路径前的最后一步":

```
v0.10.19 第一段 → v0.10.20 第二段(✅ 已落)→ v0.10.21 第三段(本期)→ v0.11+ 删旧表
```

第三段的关键不是"加功能",而是**确认双写一致性后才能切单源**。先做对账 → 再做 backfill → 再删 legacy 写路径,顺序错就回滚成本高。

v0.10.20 留下的剩余 4 项 UI 工作量小、相互解耦,本期一并清掉,腾出 v0.11.x 的工作面给 §C.7 I9 Ellipse / I5 双图比对等新 epic。

## 5 项清单与决策

### D1 · ADR-0027 第三段 · 切单源(本期主线)

**目标**:在验证双写一致性后,把 legacy 三表的写路径删除,旧数据 backfill 到 `annotation_feedbacks`,旧表保留只读一个版本作回退。

**子步骤(严格顺序,每步独立可回退)**:

1. **双写一致性对账(开工前置)**
   - 运行 `SELECT source_table, COUNT(*) FROM v_annotation_feedback_unified GROUP BY source_table` 对比 4 个 source 总行数。
   - 写脚本 `apps/api/scripts/audit_feedback_doublewrite.py`:遍历 `bug_reports.project_id IS NOT NULL` / `annotation_comments.is_active=true` / `tasks.status='rejected' AND reject_reason IS NOT NULL` 行,对每条检查 `annotation_feedbacks` 是否有 mirror 行(按 created_at + author_id + source key 匹配)。
   - 缺失/多余 → 列入 `feedback_doublewrite_drift.csv`,人工 review。
   - **门槛**:drift < 0.1% (按 3 source 各自总行数算)才进入 step 2。drift ≥ 0.1% 必须先排障(通常是 v0.10.20 之前的历史数据,不在双写覆盖期内)。

2. **一次性 backfill migration `0078_backfill_legacy_feedbacks.py`**
   - DDL-less,纯 INSERT INTO annotation_feedbacks SELECT ... FROM bug_reports / annotation_comments / tasks 三段 UNION ALL。
   - 跳过条件:同主键 (source_table, source_id) 已在双写期落到 annotation_feedbacks 的行;`bug_reports.project_id IS NULL` 行(登录页 bug)单独走一段 migration 兜底,project_id 取系统级 placeholder UUID(讨论用 `00000000-0000-0000-0000-000000000000`,需 ADR 备注)。
   - 写入时 `kind` / `anchor_type` / `severity` 按 view 的映射规则同步;新行的 `is_active` 沿用 source(annotation_comments.is_active / bug_reports 全部 active / tasks reject 全部 active)。
   - 跑前 dry-run:`alembic upgrade --sql 0077:0078` 生成 SQL,人工 review 行数预估。
   - downgrade:`DELETE FROM annotation_feedbacks WHERE source_table != 'annotation_feedbacks'`(view 的 source_table 列保留可识别,删除 backfill 行不影响双写期间的 mirror 行,因为 mirror 行写入时未设 source_table — 等等,这里要校对一下,确认 mirror 行确实没有 source_table 列。检查 `mirror_*` helper)。

3. **删除 legacy 写路径**(同事务 commit)
   - 删 `apps/api/app/services/feedback.py` 的 `mirror_bug_report` / `mirror_annotation_comment` / `mirror_task_reject` 3 个 helper 调用(保留函数定义一个版本作回滚预留,v0.11.x 再彻底删函数)。
   - 改 `BugReportService.create`:legacy INSERT bug_reports + INSERT annotation_feedbacks 改为只 INSERT annotation_feedbacks(kind=bug)。bug_reports 表保留只读。
   - 改 `annotation_comments.py:create_comment`:同理只 INSERT annotation_feedbacks(kind=comment, anchor_type=annotation)。**注意**:此时旧 `useAnnotationComments` / `useTaskCommentsInfinite` 前端 hook 必须切到 `useFeedbacks({ kind:"comment" })` 读新表,否则前端看不到新评论。
   - 改 `tasks.py:reject_task`:`task.reject_reason` 字段保留(状态机仍用),但 INSERT 只走 annotation_feedbacks(kind=reject)。
   - 前端读端切换(关键):`useTaskCommentsInfinite` 从读 `/tasks/{id}/comments/page` 切到读 `GET /feedbacks?task_id=&kind=comment`;`useAnnotationComments` 从读 `/annotations/{id}/comments` 切到读 `GET /feedbacks?annotation_id=&kind=comment`。两个 hook 可保留旧 API 调用兼容签名,内部切到 feedbacks。

4. **回退路径(若 step 3 上线后 24h 内发现读写不一致)**
   - revert step 3 commit(reverts 写路径切换 + 前端读端切换)。
   - backfill 不 revert(annotation_feedbacks 多一份重复数据无害,旧表读路径仍工作)。
   - 重新进入双写期排障。

**关键文件**:
- 新: `apps/api/scripts/audit_feedback_doublewrite.py`(对账脚本)
- 新: `apps/api/alembic/versions/0078_backfill_legacy_feedbacks.py`(一次性 backfill)
- 改: `apps/api/app/services/bug_report.py`、`apps/api/app/api/v1/annotation_comments.py`、`apps/api/app/api/v1/tasks.py`(删 mirror 调用,改为仅写新表)
- 改: `apps/web/src/hooks/useAnnotationComments.ts` 2 个 hook 内部切到 `useFeedbacks` 入参
- ADR-0027 第三段标记 ✅ 已落,补"双写期 drift 监测结果"小节

**风险**:
- backfill 行数若 > 10k,需关注事务时长;建议分批 `INSERT ... SELECT ... LIMIT 1000 OFFSET k` 在 worker 后台跑。本期假设 dev 数据量 < 10k,生产暂未 ship。
- 前端读端切换若有遗漏,会让"已写入新表"的评论在 UI 看不见。落地前必须扫一遍 `grep -r "useAnnotationComments\|useTaskCommentsInfinite\|/comments/page" apps/web/src` 确保覆盖所有 reader。

### D2 · I4 笔画 timeline(stretch,可独立切)

**目标**:`canvas_drawing.shapes[i]` 加 `id/started_at/ended_at` 字段 + 评论卡片下方迷你 CSS flex 时间条 + hover 评论高亮对应 stroke。

**Data 协议变更**:
- `CanvasDrawingPayload.shapes[i]` 从 `{ tool, points, color, width }` 扩 `{ id, started_at: number, ended_at: number, tool, points, color, width }`(id = `crypto.randomUUID()`, ms epoch)。
- 旧记录缺 id/started_at/ended_at 字段时,timeline 不渲染(降级)。**不**做 alembic backfill,纯前端协议升级。
- pydantic schema `CanvasDrawingShape` 加 3 个 Optional 字段。

**写路径**:
- `CanvasDrawingEditor.tsx`:onPointerDown 记 `started_at = performance.now() + perfTimeOrigin`,onPointerUp 记 `ended_at`,push shape 时带 id。

**UI**:
- `CanvasDrawingPreview.tsx` 在 SVG 下方加 `<StrokeTimelineBar shapes={shapes} />`:纯 CSS flex,每条 stroke 一个 `<div>` segment,width: `(ended - started) / total_duration * 100%`,background: stroke.color。
- hover stroke 段 → `useHoveredStrokeStore.setHoveredStrokeId(id)`(新建 store,与现 `useHoveredCommentStore` 并存)。
- CanvasDrawingPreview 内 SVG 已 hover 评论时高亮全部 stroke,本期改为:`hoveredCommentId ∧ hoveredStrokeId` → 仅高亮对应 stroke;`hoveredCommentId` 单独 hover → 全部 stroke(沿用现状)。

**单测**:
- `CanvasDrawingPreview.timeline.test.tsx`:旧 shape 缺 started_at → timeline 不渲染;新 shape 全字段 → 渲染 3 段 + width 比例正确。

**关键文件**:
- 改: `apps/api/app/schemas/annotation_comment.py`(`CanvasDrawingShape` 加字段)
- 改: `apps/web/src/components/Comments/CanvasDrawingEditor.tsx`(写时间戳)
- 改: `apps/web/src/components/Comments/CanvasDrawingPreview.tsx`(timeline bar 渲染)
- 新: `apps/web/src/components/Comments/StrokeTimelineBar.tsx`
- 新: `apps/web/src/stores/useHoveredStrokeStore.ts`

- **删除 `bug_reports` / `annotation_comments` 旧表**:留 v0.11+ 切。本期旧表保留只读 + 留一个回退版本。

- **D5 video pin 完整实现**:本期 stretch,若 D1-D4 用满 PR 体量则推 v0.11.x。

## 风险与权衡

- **D1 切单源时的数据一致性**:这是本期最大风险。step 1 对账脚本是核心防线;drift 容忍度严格(0.1%)。如果 drift 高,通常是 v0.10.20 之前的历史数据,不在双写覆盖期,需要在 step 2 backfill migration 里专门处理(已纳入设计)。
- **前端 hook 切换的覆盖度**:`useAnnotationComments` / `useTaskCommentsInfinite` 被多处 import,切换时容易遗漏。开工前先 grep 全量调用点列清单,逐个验证。
- **D3 DiscussionPanel 拆分对 WorkbenchShell 1210 行的影响**:右栏拆分会让 Shell 减少 ~50 行(委托给 RightColumn),但 ResizeHandle 状态管理可能略增。本期不算大重构,WorkbenchShell 仍未触发 900 行二次拆分阈值。
- **D2 timeline 协议升级的兼容性**:新 shape 字段全 Optional,旧记录缺字段时 UI 降级不渲染 timeline,不破坏旧数据。无 migration 风险。
- **D4 UI 入口开放后的 permission edge**:`feedback.author_id === currentUserId` 在 superuser 跨用户编辑时需小心;复用 v0.10.19 落地的 server-side permission check(403 兜底),前端按钮是 UX 优化不依赖前端 enforce。
