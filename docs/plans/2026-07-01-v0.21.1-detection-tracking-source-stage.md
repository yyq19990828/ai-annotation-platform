# v0.21.1 · 检测式视频跟踪（detect-then-track）作为 pipeline 源阶段

状态：草案（draft）。承接 v0.21.0 全局编排选择器，是它的**第一个「非整图源」消费方**。
把「检测模型 + ByteTrack/BoT-SORT」的全自动多目标跟踪落成一个 pipeline 源阶段，源类型
从 `image` 扩到 `video`。

## 背景

- **现状只有交互式 tracking**：`VideoTrackerJob` 走 SAM2/SAM3 种子传播——`annotation_id`
  强制必填（人先画一帧种子框），走 `predict_interactive`（有状态、单 task），平台侧
  `video_tracker_runner.py` 做跨窗续追。它**绕过标准 `/predict`**，由 api 层 `video_tracker_adapters`
  直调。这条是「人在环、单对象、workbench 交互算子」，本 plan **原样不动**。
- **检测式 tracking 一行实现都没有**：`capability_registry.py:272` 的 `tracker` task 把
  ByteTrack/OC-SORT 列为 `typical_models` 文字示例，但 adapter 注册表只有 `mock_bbox` /
  `sam2_video` / `sam3_video`，全是交互式。
- **它和交互式是不同物种**：无种子、多对象、全自动、离线批量；**时间关联全在 backend 内**
  （ultralytics tracker），平台只投视频、收聚合 track，自己一点时间编排都不做。因此它天生
  是 pipeline 源阶段的形状 = 「`video` 源的 detection，输出多一个 `track_id`」，走**标准批量
  `/predict` + Celery pipeline**，不进交互式那条链。
- **ultralytics 原生免费**：yolo-backend 已依赖 ultralytics 8.4.x。`model.track(source,
  persist=True, tracker="bytetrack.yaml", stream=True)` 内建 ByteTrack/BoT-SORT，直接吃整段
  视频、内部解帧、逐帧出 `boxes.id`。首发零新依赖。
- **硬边界（ultralytics 文档明证）**：单帧图像无跨帧状态、产生不了有意义的 track_id。故检测式
  track 的 `supported_inputs` **只能是 `video`，不含 `full_image`/`crop`**。

## 设计定位

- 输出直接落已存在的 `VideoTrackGeometry`（`_jsonb_types.py:460`，`track_id` + `keyframes[]`），
  schema 零改动。
- backend 给的原生 int track_id → 平台映射成 `trk_<uuid>`，原 int 存 `semantic_label`
  （如 `car_3`）。`source="prediction"`。
- **坐标系**：平台内部**统一 `0-1` 归一化**（`prediction.py` 落库时 `_percent_scale` 自动检测：
  任一值 >1 视为百分比除 100，否则视为已归一）。backend **直接返回 `0-1`**（与交互式 tracker +
  现有 video 协议一致），**不要依赖百分比自动检测**——小目标 bbox 各分量可能全 <1，跨该边界有
  误判风险（参见 [[project_interactive_candidate_coords]] 的坐标系教训）。`VideoTrackKeyframe.bbox`
  存 `{x,y,w,h}` 0-1。

## 工作项（高层，细节待立项展开）

### WS1 · 协议契约扩展（`apps/_shared/protocol_v2`）

- **`vocab.py` 新建 `INPUT_VALUES` 受控词表**：`("full_image", "crop", "bbox_prompt",
  "point_prompt", "video")`。把现在散落的 `supported_inputs` 自由字符串收编（onnxtools 的
  `full_image`/`crop` 对齐进词表）。**这一步的词表本身在 v0.21.0 前置里先落**（见下），WS1 只补
  `video` 值 + 校验接线。
- **`schemas.py` 支持 track item 形状**。检测式 track 的 `/predict` 响应里，`result[]` 每项是
  一个**已聚合好的轨迹**（后端 stream 整段视频、按 `boxes.id` 聚合，平台不再聚合）：
  ```jsonc
  {
    "type": "video_track_bbox",
    "track_id": 3,                 // backend 原生 int（ultralytics boxes.id）
    "class_name": "car",
    "score": 0.87,                 // 轨迹级（均值或代表帧）
    "keyframes": [
      // bbox 用 {x,y,w,h}、0-1 归一化——对齐 VideoTrackKeyframe + 现有交互式 tracker wire
      { "frame_index": 0, "bbox": { "x": 0.102, "y": 0.201, "w": 0.080, "h": 0.065 }, "score": 0.90 },
      { "frame_index": 1, "bbox": { "x": 0.105, "y": 0.203, "w": 0.081, "h": 0.065 }, "score": 0.88 }
      // id=None 的帧（低置信）直接丢弃
    ]
  }
  ```
- **`/setup` model 条目声明**：`task="tracker"`、`supported_inputs=["video"]`、新增
  `supported_trackers=["bytetrack", "botsort"]`、`params` schema（`conf`/`iou`/`tracker`/`classes`）。
- 文档：`docs-site/dev/reference/ml-backend-protocol.md` 补「检测式 tracker（批量 `/predict`）」
  一节，与现有「§2.2 交互式 `video_tracker`」并列，讲清两者是两条链。

### WS2 · yolo-backend 实现（首发，ultralytics 原生）

- `/setup` 加 tracker model 条目（复用现有 series/size variant 矩阵中的检测权重）。
- `/predict` 新增 `context.type="tracker"` 分支：
  - `task.file_path` = 视频 signed URL；backend 流式 fetch。
  - `model.track(source, stream=True, persist=True, tracker=<bytetrack|botsort>.yaml,
    conf, iou, classes)` 逐帧收 `boxes.id`。
  - 按 track_id 聚合成 `video_track_bbox` item；坐标转百分比（复用 `predictor.py:399` 现有转换）。
- **依赖零新增**：ByteTrack/BoT-SORT + lap 由 ultralytics 自带。
- 显存：`stream=True` 逐帧，轨迹状态轻量，支持长视频（对比 SAM2 需 300 帧窗口防爆显存）。

### WS3 · onnxtools-backend 实现（跟进，不与 WS2 绑首发）

- onnxtools 无 ultralytics → 需**自带 ByteTrack 关联**（纯 numpy/scipy：IoU + 卡尔曼 + 匈牙利），
  或移植 ultralytics `trackers/byte_tracker.py`。
- `/setup` 加 `vehicle-track` model 条目（`atom`，`task="tracker"`，`supported_inputs=["video"]`）；
  复用现有 `vehicle-detect` 逐帧 RTDETR，外接 ByteTrack 状态。

### WS4 · 平台侧：pipeline 源阶段接入 `video` 源

**投递（改动极小）**：现有源阶段 `_run_batch` 已是 `batch_size=1` 逐 task 投 signed URL，且对
`file_type` image/video 一视同仁（`tasks.py:289`）。video task 天然一视频一 task，`batch_size=1`
正合适——投视频 URL、backend 内解帧，**平台投递侧几乎不改**。仅需 `_build_predict_context`
（`tasks.py:558`）透传 `type="tracker"` + tracker 选择 + params。

**超时（关键约束，必须改）**：worker 调 backend 的 `ml_predict_timeout` 默认 **100s**
（`config.py:144`，`ml_client.py:184` 用它建 httpx client），长视频整段 track 会被掐断，且无
分片重试。首版方案：
  - 加 **tracker 专属长超时**（新增 `ml_predict_timeout_tracker`，或按 `context.type` 选超时值），
    默认 300–600s；
  - backend `model.track(stream=True)` 单次整段跑（内存友好），**首版限制视频时长/帧数上限**，
    超限 `log()` 明确截断（不静默丢）；
  - 分窗续追 / 异步作业模式（像交互式 `VideoTrackerJob` 那样触发+轮询）留作规模化后续——注意
    分窗会把「跨窗 track_id 续接」推回平台侧、破坏「时间关联全在 backend 内」，故首版**不做**。

**落库（真实工作量所在）**：现在 `prediction.result` 只输出 bbox/polygon 平铺列表，**无 track_id/
keyframes 结构**。打通检测式 track → `VideoTrackGeometry` annotation 的链路：
  - `prediction.py` 的坐标转换（`_percent_scale` / `to_internal_shape`）**扩展识别
    `video_track_bbox`**：对 `keyframes[].bbox` 逐个归一化，而非只认平铺 `rectanglelabels`。
  - accept-prediction 转 annotation：`annotation_type="video_track_bbox"` +
    `geometry=VideoTrackGeometry`（`annotation.py:261/266` 的多态透传已具雏形，需**验证
    `to_internal_shape` 认这个 type**，不认则补一支）。
  - int track_id → `trk_<uuid>` 映射（一个 prediction 内建映射表），`semantic_label="{class}_{int}"`。
  - 每个 `VideoTrackKeyframe.source="prediction"`（该枚举值**已存在**，`_jsonb_types.py`，无需扩 schema）。
  - `PredictionMeta.extra.pipeline` 记录 stage 溯源（复用现有机制）。

**前端（复用）**：视频工作台已能渲染 `VideoTrackGeometry`（交互式 tracker 在用）；检测式 track 落的
是同一几何类型，渲染 + 预标注审核（`predictions` 表待审接受）**直接复用**，本版不新增画布代码。

## v0.21.0 前置调整（必须在 v0.21.0 落，否则 v0.21.1 回改选择器）

v0.21.0 WS2 选择器要「按 `supported_inputs` 判父子可达性」。若这版把 `supported_inputs` 的枚举
写死成现有 4 值、或把源阶段硬设为「吃整图」，v0.21.1 加 `video` 源时选择器 + 校验要回改。故：

1. **`supported_inputs` 受控词表 + 数据驱动过滤**：v0.21.0 在 `vocab.py` 建 `INPUT_VALUES`
   受控词表（此刻可**含 `video` 占位**，即使还没 backend 声明它），选择器 `pipelineGraph.ts` /
   `stageWarning` 的渲染与可达性判定**从词表读**，不 hardcode。
2. **源阶段「源类型」不硬设整图**：可达性逻辑里，源阶段（`parent_stage=null`）不排斥
   `supported_inputs` 含 `video` 的 backend——它应被判为合法源，只是源类型标注为 `video`。

**最小原则**：v0.21.0 只做「词表 + 过滤/可达性数据驱动化」，**不预建 video 源的专属 UI**
（那是 v0.21.1 WS4）。避免投机性抽象。

### 方向 A（编排节点 UI 去硬编码，v0.21.0 收尾随手做）

上面前置 #2 的**具体落地**：编排节点 UI 现在把「源 = 检测 = 整图」写死在 6 处，全都没读已在手的
`taskType` 与词表。v0.21.1 上 tracker（video 源）时这些会全部要回改，故随 v0.21.0 收尾一并去硬编码。

**硬编码债清单（SSOT）**：

| `components/PipelineGraphCanvas.tsx:110,127` | `"检测（源）"` / `isSource ? "检测"` |

**关键**：源节点**已经拿到 `taskType`**（项目侧 `cfg.primaryModel?.task`、全局侧 `srcOption?.model.task`），
前端词表 `capabilityVocab.gen.ts` **已有 `video` input + `tracker` task（label「视频追踪」）+ modality**。
债只在渲染层没读词表，去硬编码近乎免费。

**做法（对称已落地的 `deriveDownstreamShape`，同一套模式）**：

1. `pipelineGraph.ts` 加 `deriveSourceShape(model) → { role, icon, sourceType, producesGeometry, detail }`：
   - `role`/`label` 走 `TASKS[task].label`（detection→"目标检测"、tracker→"视频追踪"）。
   - `sourceType` 走 `supported_inputs` / `defaultModalities`（image / video / …），词表驱动，不 hardcode。
   - `producesGeometry` 由 task 判（tracker 也产几何，但语义是轨迹 track，`detail` 相应改「轨迹」）。
2. **节点头加「源类型」徽标**（图像 / 视频 / …）——这是当前完全缺失的维度：tracker 源和 detection
   源在画布上现在长得一模一样，用户分不出投的是图还是视频。徽标槽位**预留第二行**给后续「执行单位」
   （见 ROADMAP §A scene 源条目），避免 scene 落地时重排节点头。
3. 替换上表 6 处硬编码为 `deriveSourceShape` 派生；`GlobalStageInspector` 源阶段标题按 shape 动态。
4. `pipelineGraph.test.ts` 补 `deriveSourceShape` 判据锁死（detection→image 源 / tracker→video 源）。

**仍守最小原则**：只做去硬编码 + 源类型徽标（数据已在手），**不建 video 源专属编辑 UI / 不改投递校验**
（那是 v0.21.1 WS4）。

## 风险

- **推理超时**（`ml_predict_timeout=100s` 掐断长视频，无分片重试）：见 WS4 超时方案；本质是首版
  视频时长上限的来源。tracker 专属长超时是首版必须项，不是可选优化。
- **落库 schema 扩展是主要工作量**：`prediction.result` → `video_track_bbox` → `VideoTrackGeometry`
  的转换链（WS4「落库」）是本版真正的实现重心，backend 侧反而轻（ultralytics 免费）。
- **输出 payload 体量**（长视频 × 多 track × 多帧 keyframes）：首版限制视频时长/帧数上限，
  超限 `log()` 明确截断（不静默丢），落库分批。
- **track_id 稳定性**：ultralytics int id 单次 `track()` 会话内唯一；首版**单次整段 track**，
  不分窗，避免跨窗续接的 id 重编。
- **onnxtools 自带 ByteTrack 的移植成本**：故 WS3 跟进、与 WS2 解耦。
- **时序**：v0.21.0 前置须先落，再上 v0.21.1。

## 验收

- yolo-backend tracker model：投一段视频 → 返回聚合 `video_track_bbox[]`，每 track 有稳定
  track_id + 逐帧 bbox。
- pipeline 选 tracker backend 作源阶段 → 跑完落一批 `VideoTrackGeometry` 预标注，视频工作台
  能渲染轨迹、人工可审核接受。
- v0.21.0 选择器能列出 `supported_inputs=["video"]` 的 backend 且判为合法源阶段（前置生效）。

## 不在范围

- **`image_sequence`（scene 抽帧跨 task 聚合）源**：打破 pipeline 「per-task 独立执行」单位，
  逼执行单位从 task 升到 scene——最贵的一块，单独立项（见 Q4 探讨结论）。
- **检测式 track 下游逐帧 crop 分类**（帧 × track 二维展开，`roi.py` 要从「图内多框」扩成
  「track 内多帧多框」）：后续。
- **交互式 SAM2/SAM3 tracking**：原样不动。
- **ReID / BoT-SORT 外观特征调优**：首版 ByteTrack 基线。
