## 1. 本版目标

v0.23.13 先建立正确但偏保守的目标帧链路：每次缓存 miss 都可以从最近关键帧重新创建 decoder 并解码。
本版在不改变显示合同和 fallback 语义的前提下，把这条路径优化成有界、可取消、可诊断的 GOP 会话。

成功后：

- 同一 GOP 内向前逐帧只继续喂入尚未解码的 access unit；
- 同一帧的并发请求合并，旧请求不能覆盖新目标；
- 后退、跨 GOP、跨 chunk、切换任务或配置变化时会确定性 reset；
- sample manifest、chunk bytes、decoder session 和 bitmap 分层缓存，各自有明确生命周期；
- chunk bytes 与 bitmap 均按字节预算淘汰，不再只按对象数量控制；
- 只在暂停态做同 GOP 小窗口预取，播放态保持零 WebCodecs 逐帧请求；
- 所有淘汰、reset、abort 和卸载路径都释放 `VideoFrame`、`ImageBitmap` 与 `VideoDecoder`；
- 能从诊断数据区分网络、demux、decoder、bitmap 创建和缓存等待耗时。

## 2. 为什么必须独立成版

### 2.1 无状态解码会产生平方级重复工作

假设一个 GOP 有 30 个 packet，用户从 GOP 第 0 帧逐帧走到第 29 帧。每帧都从 keyframe 重解时，需要
提交：

```text
1 + 2 + ... + 30 = 465
```

个 `EncodedVideoChunk`；持久会话只需提交约 30 个。长 GOP、高分辨率和快速按方向键时，这种重复会放大
decoder queue、功耗和交互延迟。

### 2.2 数量型 LRU 不能表达真实内存

相同的 48 张 bitmap：

- 1280×720 RGBA 估算约 169 MiB；
- 1920×1080 RGBA 估算约 380 MiB；
- 3840×2160 RGBA 估算约 1.48 GiB。

所以现有 `videoDecoderCache: 24 / 48 / 96` 只能限制对象数，不能保证内存上界。chunk bytes 也需要独立预算，
不能因“只缓存 2 个 chunk”就假设安全。

### 2.3 正确性与复用的失败面不同

GOP session 引入 decoder queue、output waiter、generation、reset 和资源所有权。把它与 v0.23.13 的协议
恢复同时落地，会难以判断错误来自 sample、timestamp、Konva 接线还是 session 状态。因此本版只在前版
退出门全部通过后开始。

## 3. 范围与非目标

### 3.1 本版范围

- `VideoGopDecoderSession` 及其纯状态合同；
- 同 GOP 向前增量 decode；
- session reset、串行命令队列和 generation；
- sample manifest 与 chunk bytes 的 single-flight cache；
- bitmap / chunk bytes 字节预算；
- 同 GOP、方向感知的受控预取；
- 性能档位映射升级；
- 分阶段耗时、命中率和资源诊断；
- Vitest、hook 集成测试与可重复的本地性能脚本；
- 设置参考和 Unreleased CHANGELOG。

### 3.2 本版非目标

- 不接管连续播放和音频；
- 不实现跨 GOP 并行 decoder；
- 不保留多个活动 decoder session；
- 不把 signed URL 当长期缓存项；
- 不引入 Service Worker、IndexedDB 或持久二进制缓存；
- 不引入 Dedicated Worker；是否需要由 v0.23.15 的主线程门槛决定；
- 不新增 Range 请求、容器解析库或后端数据库字段；
- 不把实验开关改为默认开启；
- 不进行 ROADMAP 最终收口。

## 4. 冻结资源模型

### 4.1 四层资源与所有权

| 层              | 缓存键                                      | 生命周期              | 预算 / 上限     | 释放规则                     |
| --------------- | ------------------------------------------- | --------------------- | --------------- | ---------------------------- |
| sample manifest | `datasetItemId:chunkId`                     | 当前 task；内容不可变 | 最多 8 个 chunk | task 变化清空                |
| chunk bytes     | `datasetItemId:chunkId:etagOrUrlGeneration` | 短 TTL                | 字节预算        | 淘汰后释放引用               |
| decoder session | task + chunk + GOP + config fingerprint     | 当前 GOP              | 最多 1 个       | reset / dispose 时 `close()` |
| decoded bitmap  | `taskId:frameIndex`                         | 当前 task             | 字节预算        | 淘汰时 `bitmap.close()`      |

约束：

- signed URL 本身只服务一次 fetch / refresh，不作为内容身份；
- 若响应能取得 `ETag`，诊断记录但不依赖它建立功能正确性；
- sample manifest 可比 chunk bytes 活得更久，但不能跨 dataset item 混用；
- decoder output 的 `VideoFrame` 不进入 LRU；目标 output 转成 bitmap 后立即关闭；
- session 未命中的 output 立即关闭，不等待下一请求“碰运气”复用。

### 4.2 性能档位改为字节预算

在 `apps/web/src/pages/Workbench/state/performanceTier.ts` 把未被其它逻辑依赖的
`videoDecoderCache` 替换为明确资源字段：

```ts
interface WorkbenchPerformanceConfig {
  // existing fields...
  videoDecoderBitmapCacheBytes: number;
  videoChunkByteCacheBytes: number;
  videoDecodePrefetchFrames: number;
}
```

冻结初始值：

| 档位       | bitmap budget | chunk byte budget | 同 GOP 预取帧数 |
| ---------- | ------------: | ----------------: | --------------: |
| light      |        96 MiB |            32 MiB |               0 |
| standard   |       256 MiB |            96 MiB |               2 |
| aggressive |       512 MiB |           192 MiB |               4 |

说明：

- 这是缓存上限，不是预分配；
- 单张 bitmap 估算为 `codedWidth * codedHeight * 4`；
- 若单个 bitmap 大于总预算，允许把它作为当前活动帧展示，但不得写入 LRU；
- 当前正在显示的 bitmap 在新显示源生效前不能因 LRU 淘汰被关闭；
- 预算下降时同步逐出到新上限，不等待后续写入；
- chunk 实际成本使用 `ArrayBuffer.byteLength`；
- 单个 chunk 超预算时可服务当前请求，但不入 byte cache；
- 仍可设内部安全项数上限，防止大量极小对象，但字节预算是主要准入条件。

`performanceTier.test.ts` 必须断言三档的确切值，并证明切换到 light 会立即收缩已有缓存。

## 5. `VideoGopDecoderSession` 设计

### 5.1 文件与边界

新增：

```text
apps/web/src/pages/Workbench/stage/videoGopDecoderSession.ts
apps/web/src/pages/Workbench/stage/videoGopDecoderSession.test.ts
```

该模块不读取 React store、不发 HTTP 请求、不控制 Konva，只管理：

- 一个 `VideoDecoder`；
- 一份已经验证的 decode plan；
- decoder input cursor；
- output timestamp waiter；
- 串行命令队列；
- generation 与资源释放。

### 5.2 会话身份

```ts
interface VideoGopSessionIdentity {
  taskId: string;
  datasetItemId: string;
  chunkId: number;
  gopStartDecodeIndex: number;
  configFingerprint: string;
}
```

`configFingerprint` 由下列稳定字段生成：

```text
codec + codedWidth + codedHeight + description bytes
```

不把 signed URL、当前 target frame 或临时请求 id 放进 identity。

任一 identity 字段变化都必须关闭旧 decoder 并建立新 session。禁止对已 configure 的 decoder 静默换
description。

### 5.3 状态机

```text
idle
  └─ configure ─→ ready(cursor = gopStart - 1)
                      ├─ decode forward ─→ ready(cursor = target)
                      ├─ reset ─────────→ ready(cursor = gopStart - 1)
                      ├─ decoder error ─→ failed
                      └─ dispose ───────→ closed
failed
  ├─ replace identity ─→ ready
  └─ dispose ─────────→ closed
```

规则：

1. 所有 public command 进入同一 promise queue，避免 `decode()` / `reset()` 交错。
2. `targetDecodeIndex > cursor`：只提交 `(cursor, target]` 的 chunks。
3. `targetDecodeIndex === cursor`：若 bitmap cache miss，不能期待 decoder 重发旧 output；reset 后从 key
   sample 重解，或由调用者先命中缓存。
4. `targetDecodeIndex < cursor`：调用 `decoder.reset()`，重新 `configure()`，从 GOP key sample 开始。
5. 跨 GOP / chunk：销毁旧 session，创建新 session；不在同一实例内拼接身份。
6. decoder `error` callback 把当前 generation 标记 failed，并拒绝所有 waiter。
7. `flush()` 只在当前目标输入已提交后调用；不能在每个预取 frame 之间 flush。
8. `dispose()` 幂等；closed 后的新请求必须失败为可识别的 session-disposed 结果。

### 5.4 timestamp waiter

session 每次目标请求只接受一个 presentation timestamp：

```ts
interface SessionDecodeRequest {
  frameIndex: number;
  targetDecodeIndex: number;
  targetTimestampUs: number;
  generation: number;
}
```

output callback：

- timestamp 等于当前目标且 generation 仍有效：保留该 `VideoFrame`；
- timestamp 属于已经排队的预取目标：转 bitmap 后进入缓存，但不激活；
- 其它 output：立即 `close()`；
- 同一 timestamp 重复 output：保留第一张，其余关闭并计诊断；
- flush 后仍无目标 output：返回 `target_timestamp_missing`，由上层 fallback。

同一 session 内也不能用 output 数组下标匹配 frame。

### 5.5 reset 与闲置关闭

以下事件强制 reset / dispose：

- task 或 dataset item 变化；
- chunk / GOP / codec config 变化；
- 向后 seek 到当前 cursor 之前；
- document hidden 超过 30 秒；
- session 闲置 15 秒；
- WebCodecs flag 关闭；
- 性能档位变更导致当前资源策略失效；
- decoder error；
- hook 卸载。

闲置计时器只保留一个，reset / dispose 时清理；单测使用 fake timers。

## 6. 请求编排与 latest-request-wins

### 6.1 generation 合同

`useVideoPreciseFrame` 为每个可展示目标生成：

```ts
interface PreciseFrameRequestToken {
  taskId: string;
  frameIndex: number;
  generation: number;
}
```

只允许 token 与当前值完全一致的结果进入 `displayBitmap`。旧结果：

- 若资源身份仍属于当前 task，可进入 bitmap cache；
- 若 task 已变化，立即关闭；
- 不能更新 `activeFrameIndex`、fallback reason 或用户可见 loading；
- 不触发全局 toast。

### 6.2 single-flight 范围

分别维护：

- `manifestInFlight[taskId]`；
- `samplesInFlight[datasetItemId:chunkId]`；
- `chunkBytesInFlight[datasetItemId:chunkId]`；
- `decodeInFlight[sessionIdentity:targetTimestampUs]`。

相同 key 共享 promise；最后一个消费者离开时才 abort 网络请求。为避免复杂引用计数，本版 React hook 的
单任务模型可采用“当前 generation 变化不立即 abort 相同 chunk 的共享 fetch，切 task 时统一 abort”的最小
实现；结果激活仍由 generation 保证。

### 6.3 signed URL 过期

chunk fetch 返回 401 / 403 时：

1. 丢弃当前 URL；
2. 最多重新获取一次单 chunk metadata；
3. 使用新 URL 重试一次 bytes；
4. 再失败即 fallback，并记录 `signed_url_refresh_failed`。

其它错误不自动无限重试。pending chunk 的 `retry_after` 行为沿用 v0.23.13。

## 7. 受控预取

### 7.1 触发条件

预取只在以下条件同时满足时发生：

- WebCodecs flag 开启；
- 当前处于暂停态；
- 当前 precise frame 已成功显示；
- 最近一次导航方向可确定；
- 目标仍在同一 chunk / GOP；
- decoder queue 和缓存预算未超限；
- tab 可见；
- 没有用户的新前台请求等待。

播放态、dragging scrub 中和 fallback 状态都不预取。

### 7.2 窗口

- light：0；
- standard：沿最近方向最多 2 帧；
- aggressive：沿最近方向最多 4 帧；
- 方向未知时不做双向预取；
- 接近 chunk 边界时只允许预取下一 chunk 的 metadata / samples / bytes，不提前启动第二 decoder；
- 跨 GOP 的 frame bitmap 不预解码。

前台目标请求永远高于预取。新目标到达时，尚未提交 decoder 的预取取消；已经提交的 output 可以入缓存，但
不能激活。

### 7.3 不允许的优化

- 不在播放时追着 `requestAnimationFrame` 解码；
- 不同时打开前后两个 GOP decoder；
- 不预取完整长视频；
- 不把 bytes 转成 base64 存 localStorage；
- 不通过增加无限 cache 掩盖 session 复用问题。

## 8. 缓存实现

### 8.1 通用 byte LRU

可新增当前视频模块私有的最小工具：

```text
apps/web/src/pages/Workbench/stage/videoByteLru.ts
apps/web/src/pages/Workbench/stage/videoByteLru.test.ts
```

接口不做通用框架化：

```ts
interface ByteLruEntry<V> {
  value: V;
  bytes: number;
  dispose?: (value: V) => void;
}
```

必须支持：

- `get` 刷新最近使用顺序；
- `set` 覆盖旧值并正确扣减；
- `delete` / `clear` 调用一次 dispose；
- `setBudget` 立即淘汰；
- 拒绝非有限、负数 bytes；
- 精确暴露 `entries`、`bytes`、`budgetBytes`、`evictions`；
- 当前活动 bitmap 通过调用方 pin，而不是在 LRU 内引入复杂引用计数。

若仓库已有满足合同的 byte LRU，则复用并只补 `ImageBitmap.close()` 适配，不重复造轮子。

### 8.2 bitmap 活动帧所有权

切换显示帧顺序冻结为：

1. 得到新 bitmap；
2. 更新 `displayBitmap` 引用；
3. 把旧活动 bitmap 归还 LRU 或关闭；
4. 进行预算淘汰；
5. 请求 Konva `batchDraw()`。

不能先关闭旧 bitmap 再让 React / Konva 完成新画面切换，否则可能出现一帧黑屏。

### 8.3 chunk bytes cache

- 只缓存成功的完整 `ArrayBuffer`；
- pending / failed response 不入 cache；
- TTL 初值 60 秒，命中不无限续期；
- task 变化立即 clear；
- CORS / network error 不保留 rejected promise；
- 不复制一份 `ArrayBuffer` 只为统计；
- demux 的 `Uint8Array` view 生命周期不得超出对应 bytes 的使用期。

## 12. 性能验证

新增一个不依赖真实浏览器 codec 的可重复 session benchmark，输入固定 30-frame GOP：

```text
场景 A：0 → 29 顺序逐帧
场景 B：0 → 10 → 20 → 5 → 6
场景 C：快速请求 3 → 12 → 7 → 29，仅 29 可激活
```

最低断言：

- 场景 A 的 encoded chunk submit 总数不超过 30；不能退回 465；
- 场景 B 只在后退时 reset；
- 场景 C 旧请求不激活；
- 所有场景结束后 live decoder ≤ 1、live `VideoFrame` = 0；
- dispose 后 live decoder = 0、live bitmap 只剩调用方明确持有的活动项。

真实 codec、主线程 long task 与内存曲线由 v0.23.15 执行，本版 benchmark 不冒充真实浏览器资格证据。

## 13. 实施顺序

### Phase A · 资源容器

1. 实现 / 复用 byte LRU。
2. 把性能档位改为明确字节预算。
3. 为 bitmap 与 chunk bytes 建立所有权测试。

验证：预算缩减、淘汰和 close 计数全部通过。

## 16. 风险与回滚

| 风险                            | 缓解                                                    | 回滚                          |
| ------------------------------- | ------------------------------------------------------- | ----------------------------- |
| 浏览器 decoder reset 行为差异   | fake contract + v0.23.15 真机验证；异常统一重建 decoder | 回退为 v0.23.13 无状态 decode |
| bitmap 估算与浏览器真实占用不同 | 保守按 RGBA 4 bytes/pixel；真实内存门继续验证           | 下调预算，不改协议            |
| 预取抢占交互资源                | 仅暂停、同 GOP、小窗口、前台优先                        | 将三档预取全部设 0            |
| signed URL refresh 循环         | 每请求最多刷新一次                                      | 直接 fallback                 |
| session 状态复杂度引入竞态      | 单 decoder、串行 queue、generation                      | 关闭 session 复用             |

任何回滚都不得改变 `displayBitmap` 的同源合同，也不得让实验开关开启后出现黑屏。最小安全回滚是保留
v0.23.13 的正确性路径，关闭 session、预取和 byte cache。

### 偏离计划的原因

- **`videoDecoderCache` 替换语义**:§4.2 措辞为"未被其它逻辑依赖",但实测它被 `useVideoPlaybackController` 作为 `maxItems` 消费。按 §4.2 表格与 §10 的真实意图,把数量型语义替换为字节预算并同步改造消费方,而非简单删除字段。
- **`configUnsupported` 诊断**:session 把 config 失败统一映射为 `codec_unsupported` fallback reason;`VideoChunkDecoderDiagnostics.configUnsupported` 字段保留(向后兼容),session 路径不再单独递增。
- **`decodePlanToBitmap` 保留**:作为无状态回退参考实现与独立单测对象保留,计划未要求删除。
- **诊断完整度**:`lastBitmapMs` 与 react-query 层 manifest / samples / chunkByte 的命中数与耗时本版留 `null` / `0`,按 §9"本版先在 hook return 可读"由 v0.23.15 并入全局诊断。
