## 背景

`SecondaryInferenceBar` 当前列出项目**所有** crop-capable 能力，不看选中框是什么类。框多、能力多时
噪音大：选中「车」框，却把「人脸属性」「文档 OCR」也列出来。当初延后的理由是「需类→能力映射」。

## 核心难点（已核实，决定方案）

- `MLModelCapability.classes?: {index, name}[]`（`ml-backends.ts:89`）是能力的**输出类别**，不是
  「适用于哪种父框」。例：车牌检测的 `classes` 是 `[plate]`，而它适用的**父框**是「车」——二者不同名。
  故**不能**简单用「父框 class ∈ 能力 classes」过滤（几乎永不匹配）。
- 属性型能力（颜色/类型分类）适用于任意父框，天然不该被类别过滤掉。
- 结论：适用性是「父类 → 能力」的**业务映射**，能力元数据里没有，必须显式配置或软处理。

## 方案（二选一，倾向 A + C 组合）

- **A. 项目级显式映射（可选配置）**：项目设置里给「父类 → 允许的二次推理能力」白名单（缺省=全部）。
  精确但要配。存 `project` 配置（JSONB，类比 tool_bindings）。
- **B. 启发式**：按能力 task 类型软分（属性型对所有类可见；几何/检测型按名称模糊匹配）——不可靠，弃。
- **C. 软过滤不硬删（默认行为）**：默认全列，但**把「疑似不适用」的折叠/降权**，给「显示全部」开关。
  零配置即减噪，配了 A 则按白名单精确收敛。

首版：**C 为默认（软收敛 + 显示全部开关）**，**A 为可选精确覆盖**（项目配了白名单就按白名单）。

## 工作项

### WS1 · 项目级映射存储（方案 A）

- 项目配置加 `secondary_capability_map?: Record<parentClass, string[]>`（能力 id 列表；缺省/空=不限制）。
  后端 schema + 前端 project 类型；项目设置页给编辑入口（可后置，先支持 API 落库）。

### WS2 · Bar 过滤逻辑

- `useSecondaryCapabilities` 或 Bar 内：给定选中框 `class_name`，
  - 若项目配了该类的白名单 → 只列白名单能力（精确）。
  - 否则 → 属性型全列 + 几何型软降权（置灰/折叠到「更多」），配「显示全部」开关一键展开。
- 属性型（writeTarget=attributes）恒视为「适用任意类」，不被过滤。

### WS3 · 交互

- 收敛后若某框无适用能力，Bar 仍可「显示全部」兜底，不把入口彻底藏掉（避免"明明有能力却不给跑"）。

## 风险

- **过滤过度 = 藏功能**：宁可软收敛（可展开）也不硬删，保「显示全部」逃生口。
- A 映射是新项目配置面，编辑 UI 可后置；先把存储 + Bar 消费打通，UI 增量补。

## 验收

- 项目给「车 → [车牌检测]」白名单 → 选中车框只列车牌检测；选中其他类框按缺省。
- 无白名单 → 属性型全列、几何型软降权 + 可「显示全部」。
- 任意情况都有逃生口能看到全部能力。

## 依赖 / 不在范围

- **依赖 v0.20.11**。
- 不做：跨项目共享映射、能力自动推断适用父类（能力协议未提供该信息，需协议扩展，另立）。
