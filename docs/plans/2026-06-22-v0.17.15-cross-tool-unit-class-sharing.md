# v0.17.15 · 跨 tool_unit 类别共享（rename 批量 UX + alias_to 软关联）

> 源自 [ROADMAP](../../ROADMAP.md) §A 项目模块两条 P3：
> ① **rename_class 跨 unit 重命名 UX**（后端能力已就位，纯前端勾选框）；
> ② **跨 tool_unit 类别软关联 `alias_to`**（颜色/alias 继承链，读时派生层解析）。
> **红线**：不破坏 [ADR-0026](../adr/0026-tool-unit-class-and-attribute-binding.md) 强隔离底线——存储仍是每 unit 独立 `ToolClassEntry`，标注校验 `class_name ∈ 本 unit.classes` 不变；alias_to 只是显示层继承指针，绝不合并存储、绝不改标注归属。

---

## 第一部分：rename_class 批量 UX（纯前端，零风险，先发）

### 1.1 现状

后端 `POST /projects/{id}/classes/rename`（`apps/api/app/api/v1/projects.py:750-828`）的 `tool_unit_id` 早已设计成两条路径：

- 传 `tool_unit_id` → **只改该 unit**（强隔离，现状）
- **不传 → 跨所有 enabled unit 内同名类一起改**（向后兼容路径，正是「批量」语义）
- 无论哪条，annotations.class_name 始终跨 unit 一起改（不留孤儿标注）

前端 `ClassesSection.tsx:40-59` 的 `handleRename` 目前硬传 `tool_unit_id: activeUnit`，所以永远走单 unit 路径，用户要在每个 unit 重命名 N 次。

`useRenameClass`（`apps/web/src/hooks/useProjects.ts:79-96`）的 mutation vars 已含可选 `tool_unit_id?: string`，无需改 hook 签名。

### 1.2 改动（只动前端）

1. **`ClassesSection.tsx` 重命名弹窗加一个 checkbox**：「同时在所有工具集内重命名同名类」。
   - 勾选 → `rename.mutate({ old_name, new_name })`（**不传** `tool_unit_id`，走批量路径）。
   - 不勾选 → 保持现状 `{ ..., tool_unit_id: activeUnit }`。
2. **条件渲染**：只有当 `tool_bindings` 中**存在其它 enabled unit 也有同名类**时才显示这个勾选框（否则批量与单 unit 等价，勾选框无意义）。扫一遍 `project.tool_bindings` 判断 `oldName` 是否出现在 ≥2 个 enabled unit。
3. **默认不勾选**（默认=现状强隔离），守工作台设置三原则的「默认值=现状」红线。

### 1.3 验证

- 前端单测（vitest + MSW）：勾选时 mutation payload **不含** `tool_unit_id`；不勾选时含 `activeUnit`；只有 1 个 unit 有该类时勾选框不渲染。
- 后端无需改：批量路径与跨 unit annotations 更新已有测试覆盖（`apps/api/tests/test_classes_rename_tool_unit.py:72-85`）。

**工作量：约半天。无 schema / 无后端 / 无迁移。**

## 第二部分：alias_to 软关联（schema + 派生层 + 前端 UI）

### 2.1 现状与底线

`ToolClassEntry`（`apps/api/app/schemas/_jsonb_types.py:209-235`）当前四字段 `name/color/order/alias`，无 `alias_to`。ADR-0026 第 71/257 行把 alias_to 标为「本版不做，客户反馈想共享再加」——本切片正是落地这条。

强隔离底线（ADR-0026:29）：每个 enabled `tool_unit_id` 独立持有 `classes + attribute_schema`，bbox 的「人」与 region 的「人」是两条独立记录。**alias_to 不得改变这一点**：它只让 unit B 的某类在**显示取色 / alias** 上继承 unit A 同名类，存储与标注归属完全不动。

### 2.1.1 归属边界：alias_to 属项目 schema，不属工作台设置

alias_to 是**项目级类别配置**，不是 per-user 工作台偏好，**不得放进工作台设置（v0.15.3 四分树）**：

| 维度 | 工作台设置 | alias_to |
|---|---|---|
| 存储 | `User.preferences`（每用户） | `project.tool_bindings` JSONB（每项目） |
| 作用域 | 只影响自己的工作台 UI/行为 | 影响项目所有标注员的类别取色 |
| 谁能改 | 用户自己 | 项目管理员 |

alias_to 本质是 `ToolClassEntry` 上和 `name`/`color`/`alias` 并排的字段，是类别定义的一部分；存进某用户 `preferences` 会让"换人看同一项目颜色就变"，违背"全项目同名类共享色"的目的。因此它的 UI 落在**项目类别配置区 `ClassesSection`**（配 color/alias 的同一面板），与其兄弟字段同处。

> 边界细分：若未来要做"画布上是否用继承后颜色显示"这类**纯渲染开关**，那才是 per-user，可进工作台设置——但 alias_to 这条**关系数据本身**必须在项目 schema 里。数据 ≠ 要不要显示它的偏好。

### 2.2 Schema

```python
class ClassRef(BaseModel):
    tool_unit_id: str
    class_name: str

class ToolClassEntry(BaseModel):
    name: str
    color: str | None = None
    order: int | None = None
    alias: str | None = None
    alias_to: ClassRef | None = None   # 新增：颜色/alias 继承链指针
```

前端 `types.gen.ts` 自动重生成，无需手写。

### 2.3 解析放在「读时派生层」，不进 DB

`tool_bindings` 原始存储永远是单源真值（守 v0.10.22 决策，`models/project.py:55-60`）。解析只在**已有的扁平 `classes_config` 派生处**（canvas 取色同一处）发生：

- 本记录 `color`/`alias` 为空 → 沿 `alias_to` 链向上解析继承目标的值；
- 本记录显式设了 `color`/`alias` → **覆盖继承**（ROADMAP「可选叠加」语义）。

### 2.4 三个必须处理的坑（决策已定）

| 坑 | 处理 |
|---|---|
| **环引用** A→B→A | 解析带 `visited` set + `maxDepth=4`；命中环即停在当前节点用自身值兜底，不抛错 |
| **悬空引用**（目标被删/改名） | rename/delete class **不级联**改 `alias_to`（保持 surgical，不扩散写）；解析时目标不存在 → **降级用自身值**，前端 UI 把该链接标灰提示「链接已失效」 |
| **解析时机** | 仅派生扁平视图 + 导出取色时解析；存储/标注校验路径不碰 alias_to |

### 2.5 改动点

- **后端**
  - `_jsonb_types.py`：加 `ClassRef` + `ToolClassEntry.alias_to`。
  - 派生层（grep `classes_config` 派生函数）：加 `resolve_alias_chain(binding, ref)` + 环/悬空保护，输出扁平视图时填充继承后的 color/alias。
  - rename/delete 端点**不改逻辑**，但补测试断言：改名/删类后其它 unit 指向它的 `alias_to` **不被级联修改**，且解析降级到自身值。
- **前端**
  - `ClassEditor` / `ClassesSection`：加「链接到其它工具集的同名类」入口（下拉选 unit + class），写入 `alias_to`；清除链接入口。
  - 取色逻辑跟随后端派生的扁平视图（前端不重复实现解析，单一真值）。
  - 失效链接标灰 + tooltip。
- **导出**：确认 `supercategory`（工具来源）语义不受影响——alias_to 只影响显示色，导出仍按各 unit 独立类输出（ADR-0026:62-65）。
- **文档**：ADR-0026 补一段「alias_to 软关联」补遗（强调叠加层、不推翻强隔离）；同步 `dev/reference` 类别绑定相关说明。

### 2.6 验证

- 后端单测：基础继承、显式覆盖、环（A→B→A 停在自身）、悬空（目标删除后降级）、多跳链（A→B→C）。
- 前端单测：链接写入/清除 payload；失效链接渲染标灰；取色读派生视图。
- 导出回归：alias_to 不改变 COCO/YOLO 导出的类目结构。

**工作量：约 2-3 天。**
