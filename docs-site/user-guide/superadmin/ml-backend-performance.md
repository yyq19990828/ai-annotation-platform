# ML Backend 性能基准（RTX 3090）

本页给出平台四个 GPU backend 在 **NVIDIA RTX 3090（24GB）** 上、按各任务实测的性能数据，供客户做**硬件规划**与**backend / 模型选型**参考。数据全部由真实 `/predict` 调用采集，媒体经 MinIO 预签名 URL 下发（与生产派发路径一致）。

> ⚠️ **数字是环境相关的。** 本页数值针对下述特定硬件、输入尺寸、默认模型变体与单 backend 隔离场景采集，仅供**量级参考**。实际表现随显卡型号、图片分辨率、场景复杂度、模型变体、驱动 / CUDA 版本、并发布局而变化。请以本页方法学复现后据你自己的环境定容量。

## 测试环境与方法

| 项 | 值 |
|---|---|
| GPU | NVIDIA RTX 3090 24GB（各 backend 隔离在其绑定卡上测量） |
| backend 部署 | grounded-sam2 / sam3 / yolo / rapidocr（onnxtools 未在本次环境运行，**未测**） |
| 图像输入 | 真实路况图 1280×720（含 33 个目标） |
| OCR 输入 | 中英数混排文字图 323×430（17 行文本） |
| 视频输入 | 960×540、72 帧、12fps |
| 媒体下发 | MinIO http URL（backend 自行取图，含 fetch + 解码，贴合生产） |

**指标口径**（每个任务同时给两个数）：

- **纯推理**（`inference_time_ms`，backend 自报）：只算模型前后向，**不含**取图 / 解码 / 网络。反映模型本身的算力开销。
- **端到端**（wall，客户端 → backend → 客户端 p50）：含 backend 从 MinIO 取图 + 解码 + 推理 + 回传。反映**平台派发一次真实感受到的耗时**。
- **重新加载**：模型被 idle-unload（默认闲置 600s 卸载）后，下一次请求把权重搬回显存的耗时（**CUDA 上下文已热**，是常见的「唤醒」延迟）。容器**首次冷启**因还要初始化 CUDA 上下文，比此值更高（一次性）。
- **显存增量**：该模型加载后在卡上的净增占用（基线为卸载后残留的 CUDA 上下文）。
- 热延迟为预热后 15 次采样的 p50/p95；并发为 N 线程同时打同一 backend。

## 一图速览：单张请求延迟与显存

> 端到端 ~100ms 的下限主要来自 backend 取图 + 解码 1280×720（约 350KB）；纯推理才是模型开销。

### yolo-backend（ultralytics 8.4 · yolo11s，闭集/开集/分割/关键点/OBB）

| 任务 | 纯推理 p50 | 端到端 p50 | 重新加载 | 显存增量 |
|---|---|---|---|---|
| 闭集检测 detection | **16ms** | 101ms | 0.12s | +224MB |
| 实例分割 segmentation | 18ms | 110ms | 0.11s | +352MB |
| 关键点 pose | 17ms | 110ms | 0.11s | +226MB |
| 开集文本检测（yoloe-11s） | 20ms | 107ms | 0.14s | +790MB |

yolo 是最轻的 backend：纯推理 16–20ms，重新加载仅 ~0.1s（权重小、上下文热；**首次冷启** ~4s）。端到端 ~100ms 基本被取图/解码占满。

### grounded-sam2-backend（GroundingDINO Swin-T + SAM 2.1 Tiny）

| 任务 | 纯推理 p50 | 端到端 p50 | 重新加载 | 显存增量 |
|---|---|---|---|---|
| 交互点选 → mask | **11ms** | 46ms | 3.8s | +454MB |
| 交互框选 → mask | 21ms | 59ms | 3.7s | +456MB |
| 文本检测 → 框（DINO） | 186ms | 225ms | 4.3s | +1435MB |
| 文本分割 → mask（DINO+SAM，46 目标） | 455ms | 500ms | 3.6s | +3646MB |

交互点/框选（标注员在画布上点一下出 mask）**11–21ms，端到端 <60ms，体感瞬时**。文本驱动的 GroundingDINO 较重（186ms），文本→mask 因要对 46 个框逐个解码 SAM mask 升到 455ms。显存：仅 SAM ~0.5GB，DINO+SAM ~3.6GB。

### sam3-backend（SAM 3）

| 任务 | 纯推理 p50 | 端到端 p50 | 重新加载 | 显存增量 |
|---|---|---|---|---|
| 交互点选 → mask | 16ms | 48ms | 10.2s | +4456MB |
| 交互框选 → mask | 24ms | 60ms | 9.9s | +4456MB |
| 文本分割 → mask（PCS 一步，46 目标） | 190ms | 234ms | 9.5s | +5340MB |
| exemplar（示例框找相似） → mask | 76ms | 113ms | 9.3s | +5340MB |

sam3 交互延迟与 gsam2 相当（16–24ms），但**显存显著更高（4.5–5.3GB）、重新加载更慢（~10s）**。文本分割走 PCS 一步出 mask（190ms），与 DINO 检测同量级但直接给 mask；exemplar 76ms。

### rapidocr-backend（RapidOCR 3.9 · onnxruntime）

| 任务 | 纯推理 p50 | 端到端 p50 | 重新加载 | 显存增量 |
|---|---|---|---|---|
| OCR 端到端（检测+方向+识别，17 行） | 246ms | 290ms | — | ~0.7GB（常驻） |
| 仅文本检测（det） | 45ms | 86ms | — | 同上（共享） |

onnxruntime（**GPU · CUDAExecutionProvider**）：实测 rapidocr 进程在卡上**常驻约 0.7GB**（onnxruntime CUDA 上下文 + PP-OCRv5 mobile 的 det/cls/rec 三 session 共享）。基准表里「显存增量 ≈ 0」是测量假象——该上下文在基准开始前就已常驻、且 OCR 模型很小，加/卸载几乎不改变净增，**并非退回 CPU**（已用真实 ORT session 与 nvidia-smi 双重确认走 CUDA）。端到端 OCR 一张图 ~290ms；只做文本框检测 ~86ms。

## 并发标注场景

模拟「N 个标注员同时向同一个 backend 发请求」。**关键结论：交互式 backend 的模型池容量为 1（gsam2 / sam3），GPU 计算会串行化**；但因为 SAM 点选推理只有 ~10–20ms，单卡单 backend 依然能扛住高并发。

### 交互点选（SAM 点击 → mask）—— 标注主力场景

| backend | c=1 | c=2 | c=4 | c=8 |
|---|---|---|---|---|
| gsam2 点选 | 21.6 rps / 46ms | 27 rps / 70ms | 35 rps / 101ms | **36 rps / 208ms** |
| sam3 点选 | 19.9 rps / 49ms | 27.9 rps / 67ms | 31 rps / 126ms | **37 rps / 197ms** |

（rps = 吞吐；ms = 端到端 p50 延迟）

**一张 3090 上单个 SAM backend，在 8 路并发下仍稳定 ~36 次点选/秒、p50 延迟约 200ms。** 换算：即便 20 个标注员各自约每秒点一次（20 rps < 36 rps 上限），也能在 <300ms 内响应——**单卡单 backend 可从容支撑十余名并发交互标注员**。要再高就横向加卡 / 加 backend 实例。

### 批量检测（yolo 闭集检测，预标注场景）

| c=1 | c=2 | c=4 | c=8 |
|---|---|---|---|
| 9.6 rps / 104ms | 14.4 rps / 126ms | 13.7 rps / 255ms | 13.4 rps / 531ms |

模型池容量 2，吞吐约在 **~14 张/秒**见顶（受取图 + 串行化限制），继续加并发只涨延迟不涨吞吐。即单 yolo backend 批量预标注 ~14 图/秒（约 5 万图/小时量级）。

### OCR 端到端

| c=1 | c=2 | c=4 |
|---|---|---|
| 3.5 rps / 285ms | 3.9 rps / 495ms | 3.6 rps / 1047ms |

计算较重，吞吐 **~3.6 页/秒**见顶，并发上去后延迟陡增（c=4 已 >1s）。仅检测（det）可到 ~17 rps。

### 重任务并发上限（供选型参考）

| 任务 | 吞吐上限（rps） | 说明 |
|---|---|---|
| gsam2 文本→mask | ~2 | 46 目标逐个 SAM 解码，串行化明显，c=4 延迟 ~1.8s |
| sam3 文本→mask | ~5 | PCS 一步出 mask |
| sam3 exemplar | ~12 | — |

> 交互点/框选（~36 rps）与轻量检测（yolo ~14 rps）适合高并发；文本→mask、OCR 端到端属重任务，规划并发容量时按 2–5 rps 估。

## 轨迹转播（视频追踪）

平台把一段视频按**窗口**逐段转播，窗与窗之间用上一窗末帧几何**续种**。**注意分窗机制的差异**：

- **sam2_video**：窗口 300 帧，短片一窗跑完。
- **sam3 系（PVS 交互追踪 / multiplex 文本追踪）**：受 PVS memory 限制，**硬性 16 帧一窗**（`SAM3_PVS_MAX_WINDOW_FRAMES=16`），长视频要滚很多窗。

实测（960×540、72 帧片段）：

| 追踪器 | 窗口 | 首窗（含冷载） | 稳态窗（满 16 帧） | 整段 72 帧总耗时 | 短片有效 fps | 长视频稳态 fps |
|---|---|---|---|---|---|---|
| gsam2 **sam2_video** | 300f | 11.7s（72 帧一窗） | — | 11.7s | **6.2** | ~6.2 |
| sam3 **PVS 交互追踪** | 16f | 12.6s | ~2.9s/16帧 | 22.9s | 3.2 | **~5.5** |
| sam3 **multiplex 文本追踪** | 16f | 19.6s | ~4.2s/16帧 | 34.3s | 1.8 | **~3.8** |

**分窗开销拆解**（回应「要兼顾分窗实际情况」）：每窗的固定开销（视频重取 + 解码）实测**仅 ~40–50ms**，可忽略；窗口耗时几乎全是模型推理——PVS 每 16 帧窗 ~2.9s（≈179ms/帧），multiplex ~4.2s（≈260ms/帧，且每窗按文本重新检测目标，实例数逐窗浮动）。**首窗额外背 ~10s 冷加载**。

因此两种口径要分清：
- **短片段**（几十帧）由**首窗冷加载主导**，有效 fps 偏低（PVS 3.2 / multiplex 1.8）。
- **长视频**摊薄冷加载后趋于**稳态 fps**（PVS ~5.5 / multiplex ~3.8）；sam2_video 因 300 帧大窗，短长片都 ~6.2 fps。

选型建议：
- **sam2_video**：最快、长视频最省（大窗摊销），点/框种子单目标追踪首选。
- **sam3 PVS**：交互追踪（点/框 memory），稳态 ~5.5fps，但首窗冷载重、显存 ~4GB。
- **sam3 multiplex**：文本自动发现多目标（本例逐窗从「car」重检测出 25→16→…个实例），最慢，适合「不知道有哪些目标、要自动铺」的场景。

## 变体对照（尺寸 / 档位如何影响性能）

各 backend 支持多档模型变体，在速度、精度、显存、冷加载间权衡。以下为同一输入下的实测全档对照（默认档已在上文标注）。

### yolo11 检测尺寸（n / s / m / l / x）

| 尺寸 | 纯推理 p50 | 重新加载 | 显存增量 | 本例检出数 |
|---|---|---|---|---|
| n | 18ms | 0.09s | ~164MB | 33 |
| s（默认） | 17ms | 0.09s | ~224MB | 33 |
| m | 19ms | 0.13s | ~424MB | 23 |
| l | 24ms | 0.18s | ~422MB | 28 |
| x | 25ms | 0.31s | ~460MB | 23 |

即便最大的 yolo11x 在 3090 上纯推理也仅 25ms——**yolo 尺寸主要影响冷加载与显存，推理都很快**。检出数随尺寸浮动是精度/召回的权衡（大模型更保守、误检更少）。

### SAM 2 变体（tiny / small / base+ / large）

**交互点/框选**（同一张图多次点选）：SAM 会缓存图像 embedding，后续点选只走轻量 mask 解码器，故**变体对交互延迟影响很小**（~12–17ms）；尺寸差异体现在首次编码与显存：

| 变体 | 交互解码 p50 | 重新加载 | 显存增量 |
|---|---|---|---|
| tiny（默认） | 12ms | 3.6s | ~0.8GB |
| small | 17ms | 3.7s | ~0.8GB |
| base+ | ~17ms | 4.1s | ~0.9GB |
| large | 17ms | 5.4s | ~1.7GB |

**视频追踪**（逐帧编码，尺寸影响直接）：

| 变体 | 72 帧总耗时 | 有效 fps |
|---|---|---|
| tiny | 12.8s | 5.6 |
| small | 13.2s | 5.4 |
| base+ | 15.7s | 4.6 |
| large | 23.4s | 3.1 |

→ 视频追踪逐帧过编码器，**tiny→large 吞吐近腰斩（5.6→3.1fps）、显存翻倍**。追踪质量要求高时选大档，吞吐优先选 tiny/small。

### GroundingDINO 变体（Swin-T / Swin-B，文本检测）

| 变体 | 纯推理 p50 | 重新加载 | 显存增量 |
|---|---|---|---|
| Swin-T（默认） | 192ms | 3.6s | ~1.9GB |
| Swin-B | 242ms | 4.3s | ~2.2GB |

Swin-B 比 T 慢约 26%、显存多 ~0.3GB，换取更强的文本-区域对齐。

### RapidOCR mobile vs server

| 档 | 纯推理 p50 | 本例识别行数 |
|---|---|---|
| mobile（默认） | 255ms | 17 |
| server | 345ms | 18 |

server 档约慢 35%，精度略高。

## 部署选型与容量规划

**显存足迹（加载后净增，单卡共存估算）**

| backend | 显存增量 | 重新加载 |
|---|---|---|
| yolo（yolo11s 各任务） | 0.2–0.8GB | ~0.1s |
| gsam2（仅 SAM 交互） | ~0.5GB | ~3.8s |
| gsam2（DINO+SAM 文本） | ~3.6GB | ~4s |
| sam3（图像各任务） | 4.5–5.3GB | ~10s |
| rapidocr | ~0.7GB（常驻，onnxruntime CUDA） | — |

- **单张 24GB 3090** 上，yolo + gsam2 + rapidocr 轻松共存；叠上 sam3（~5GB）后总量约 10–14GB，仍在 24GB 内。**小显存卡（8–12GB）叠多个 GPU backend 时需谨慎**，多 backend 挤一张卡可能显存竞争、静默退化——详见 `ROADMAP` 的「跨 backend 显存互斥编排」。
- **重新加载 vs 保活**：idle-unload 默认 600s，闲置超 10 分钟后首个请求要付上表的重新加载（sam3 达 ~10s）。对交互延迟敏感的部署，建议给 backend 保持少量心跳流量、或调低 `IDLE_UNLOAD_SECONDS` 换常驻显存。
- **横向扩展**：单 backend 交互 ~36 rps、批量检测 ~14 rps 见顶后，靠多 GPU / 多 backend 实例横向扩，而非单实例加并发。

## 免责与复现

- 数据采于 **2026-07 的开发环境**、上述固定输入与**默认模型变体**（yolo11s / SAM 2.1 Tiny / SAM 3 / RapidOCR 3.9）。换更大变体（如 SAM 2.1 Large、GroundingDINO Swin-B）会显著抬高冷加载、显存与延迟——各档实测见上文《变体对照》。
- 端到端延迟含 MinIO 取图，随图片分辨率与网络而变；纯推理数值更接近模型的硬件上限。
- **onnxtools-backend 未在本次环境运行，未纳入测量。**
- 复现方法：对各 backend 的 `/predict` 用本页输入规格重放，分别记录响应里的 `inference_time_ms`（纯推理）与请求 wall（端到端），冷/热与并发分别采样即可。
